## 一句话答案

> 这类系统的第一原则是：**agent 的价值全部来自「能办事」，风险也全部来自「能办事」**。所以设计重心不在对话质量，而在**动作网关**——所有写操作按风险分级，统一过幂等键、dry-run 预览、补偿/回滚与金额阈值，模型的输出只是「提案」，执行权留在确定性代码手里。
> 升级人工不是失败兜底，而是一等公民：触发条件由代码判定（显式要求、连续失败、政策外、高风险、情绪升级、超预算），升级时必须把**会话摘要 + 已尝试动作 + 身份与订单 + 未完成状态**一起移交，绝不让用户重述。
> 评测要用「对话结束后的数据库状态」判定成功而不是「说得像对的」，并用 pass^k 度量一致性：要让 8 次重复全对达到 90%，单次成功率需要 $0.9^{1/8} \approx 98.7\%$。
> 容量上算力不是瓶颈，人工才是：每天 100 万会话、升级率 25% 对应约 3 125 FTE（约 1.56 亿美元/年），而算力约 1 110 万美元/年——升级率每降 1 个百分点约等于省 125 个 FTE。

## 面试官在考什么

- **有没有把「能办事」当成风险源而不是卖点**。答「接上退款 API 让 agent 自动退」的候选人，和答「先把退款按金额与可逆性分档、不可逆的走审批、所有写操作带幂等键」的候选人，是两个水平。
- **身份与鉴权是不是底线**。能不能明确说出「绝不凭对话内容认定身份」——用户说自己是机主不算认证，必须以会话绑定的已验证主体去调下游 API，并以该身份做授权判定（[[safety-06]]、[[rag-08]]）。
- **政策是数据还是提示词**。把「30 天内可退」写进 system prompt 是软约束；把它写成可执行规则（服务端求值、可单测、可按租户覆盖）才是工程。这题的高阶分水岭在这里。
- **升级人工的完整度**：触发条件、上下文移交、长事务挂起与恢复、坐席处理完如何交回 agent、以及升级率作为指标的双向解读。
- **算不算得清账**：单位会话成本、算力与人力成本的量级对比、升级率变化对 FTE 的线性影响。答不出数量级的方案无法排优先级。

常见错误答案：

- 「加一个转人工按钮，用户点了就转」——没有自动触发条件、没有上下文移交、没有挂起恢复，用户点完还要从头讲一遍。
- 「让模型自己判断这个操作该不该做/该不该转人工」——被监管者自己决定要不要被监管。模型可以给风险信号（置信度、缺失参数），档位判定必须由策略引擎按工具元数据与参数算出（[[agents-11]]）。

## 原理与推导

### 1. 需求澄清与假设（先写下来，后面所有算账都基于它）

| 维度 | 假设 | 为什么必须先问 |
| --- | --- | --- |
| 业务域 | 订单、退款、改签、账户资料、发票 | 决定工具集与政策数量 |
| 会话量 | 100 万会话/天（均值 11.6 会话/s，峰值按 2.5× 约 29 会话/s） | 决定集群与坐席容量 |
| 每会话 | 5 次模型调用、15 次工具调用 | 决定算力账与成本账 |
| 工具清单 | 约 40 个，按只读/可逆写/不可逆写分三档 | 决定护栏强度 |
| 政策 | 「30 天内可退」「改签最多一次」「超 500 元需审批」 | 必须可执行、可单测 |
| SLO | 首次响应 p95 ≤ 3 s、端到端解决 ≤ 5 min、升级后人工首次响应 ≤ 60 s | 决定升级队列与 TTL |
| 人力 | 单通人工处理 6 min（AHT 假设）、8 h/人日、5 万美元/FTE·年 | 决定升级率的经济含义 |
| 合规 | 会话与录音留存、动作全量可审计、PII 脱敏 | 决定日志与保留期 |

需求阶段要明确区分**能力**（读订单、算退款额、发起退款）与**权限**（谁能发起、上限多少）。这两者混在一起，后面必然出现「能查就能退」的越权路径。

### 2. 七层架构与选型理由

| 层 | 选型 | 理由 |
| --- | --- | --- |
| ① 接入 | 电话/IM/邮件统一成会话对象，渠道适配器只做归一化 | 会话状态必须跨渠道一致，否则用户换渠道就要重述 |
| ② 身份与鉴权 | 会话绑定已验证主体（登录态、OTP、IVR 校验），下游以 on-behalf-of 透传 | 安全底线：身份不能来自对话内容；agent 不得持有超级凭据 |
| ③ 知识与政策 | RAG 检索帮助文档（[[system-design-01]]）+ 服务端政策引擎 | 文档给「怎么解释」，政策引擎给「能不能做」；后者必须可执行 |
| ④ 决策 | agent 循环 + 工具集（[[agents-01]]），复杂度从最低档起步 | 按 Anthropic 的取向：优先最简单可控的模式，只在确有收益时加复杂度 |
| ⑤ 动作 | 动作网关：schema 校验、幂等键、dry-run、审批、审计、限流 | 所有副作用必经的唯一收口点（[[agents-10]]） |
| ⑥ 升级与人工 | 升级队列 + 坐席工作台 + 会话移交协议 | 题干显式要求，独立成节（第 4 小节） |
| ⑦ 可观测与评测 | trace 贯穿 request→session→step→tool_call→change_id（[[evaluation-07]]），离线回放 + 在线 A/B（[[evaluation-09]]） | 没有 change_id 回填，审计链在数据库边界断掉 |

三个不变量：**模型只提案，网关才执行**；**每个写操作声明逆操作，否则不得进工具集**；**升级路径永远可用，且不依赖模型是否配合**。

一次请求的数据流：渠道消息 → 会话归一化 → 身份绑定 → 意图识别与政策检索 → 决策循环（只读工具 + dry-run 预览）→ 动作网关（校验、幂等、审批）→ 执行并回填 `change_id` → 回复或升级。写路径只有这一条，读路径可以并行，于是权限判定与审计链都只有一个收口点。

### 3. 执行真实操作：五件事必须做实

**① 工具风险分级。** 只读（查订单、查物流）自动执行；可逆写（改地址、改联系方式、建工单）自动执行 + 事后审计；不可逆写（发起退款、扣款、注销账户、发对外通知）事前审批或禁止自动。判据落在 **(工具, 规范化参数, 影响范围)** 三元组，不是工具本身：同一个 `issue_refund`，8 元是低档、800 元升档（[[agents-11]]）。

**② 幂等与去重。** 用户重复说「我要退款」、IM 重投、agent 重试，都会产生同一逻辑动作。幂等键作用域必须是 `租户:工具:业务对象:意图`，服务端在事务内先查去重表：命中就返回首次结果。按假设的 1% 重复率，15 M 次/天的工具调用里有 150 k 次是重复，靠模型「记住已经退过」挡不住（[[agents-02]]）。

**③ dry-run 预览。** 先把影响算出来给用户确认：「退款 128 元，预计 3 个工作日到账，订单状态将变为已退款」。预览必须走与真实执行**相同的校验代码路径**（否则预览通过、执行失败），且只读、无副作用。预览要带对象版本（`etag`/`version`），执行时版本不一致就作废重来，否则用户确认的是过期状态。

**④ 补偿与回滚。** 用 saga 思路为每个写操作定义逆操作：改地址的逆是改回旧地址；发优惠券的逆是作废；退款的逆是反向划扣（通常不可行，所以退款属于不可逆档，只能事前审批）。补偿自身必须幂等，链越长整体回滚成功率越低，所以**不可逆步骤尽量后移到流程末尾**（[[agents-10]]）。

**⑤ 金额与权限阈值。** 单次上限、单日累计上限、同一用户同一动作的次数上限都要在网关上强制。阈值是数据不是代码，可按租户/地区覆盖，新工具默认 fail-closed（默认最高档），而不是默认放行。

### 4. 升级到人工：触发、移交、恢复

**触发条件（全部由确定性代码判定）：**

| 类别 | 判据 | 默认动作 |
| --- | --- | --- |
| 用户显式要求 | 关键词/意图分类/点按钮 | 立即升级，不劝说、不二次确认 |
| 连续失败 | 同一意图 2–3 次未解决，或工具连续失败 ≥ 2 | 升级并附失败轨迹（[[agents-02]]） |
| 政策外请求 | 政策引擎返回 `not_covered` | 升级，agent 不得自行扩大解释 |
| 高风险动作 | 金额或影响超阈值、不可逆且无审批人 | 升级到有权限的坐席 |
| 情绪升级 | 愤怒/威胁/投诉/法律与媒体提及 | 立即升级并提优先级 |
| 预算与步数 | 超步数或 token 预算 | 升级或返回结构化失败（[[agents-09]]） |

**上下文移交（最忌讳让用户重述）。** 移交包固定包含：已验证身份与联系方式、会话摘要（用户目标 + 已确认事实）、已尝试动作与结果（含失败原因）、相关订单/账户快照（带版本）、**未完成状态**（挂起中的动作、待确认的预览、已用额度）、以及建议的下一步。坐席工作台要能一键执行挂起动作，而不是自己再敲一遍。

**长事务挂起/恢复。** 挂起不能靠进程 sleep：会话状态、已完成步骤、外部副作用记录、待执行动作的规范化参数与指纹全部落库，释放 KV 与显存，恢复时按状态机重放（[[agents-07]]）。挂起的显存代价是可算的，见「数值与代码验证」第 4 小节。

**人工接回 agent。** 坐席处理完写回结构化结果（`{resolution, actions_taken, follow_up}`），agent 在同一会话里继续跟进（如「已为你登记补偿，3 天后到账，到时我再确认」）。人工也可以选择「降级回 agent 处理后续只读查询」，减少坐席占用。

**升级率是核心指标，且要双向读。** 过高说明能力不足（政策覆盖窄、工具缺失、检索差）；过低要警惕在硬扛不该扛的请求（用户反复重开、投诉率上升、社交媒体曝光）。健康的做法是给每个意图设期望升级率区间，偏离两侧都告警。

### 5. 一致性口径与单位经济

τ-bench 用「对话结束后的数据库状态 vs 标注目标状态」判定成功，并提出 pass^k 度量多次试验的一致性。口径要说清：摘要给出的 <50% 是跨任务的整体水平，论文正文给出 gpt-4o 用 function calling 的 pass^1 约 61%（τ-retail）与约 35%（τ-airline），同一模型 τ-retail 的 pass^8 低到约 25%。两条工程结论：**成功率必须看最终状态**，**必须看一致性**——偶尔成功不等于可用。

算力不是瓶颈，人力才是。按第 1 小节的假设：全走 70B 约 1 342 张 H100（约 8.05 美分/会话）；把 70% 流量路由到 8B 后约 506 张（约 3.03 美分/会话，路由增益 2.65×）；升级率 25% 对应 3 125 FTE、约 1.56 亿美元/年，是算力成本（约 1 110 万美元/年）的 14 倍。**每 1 个百分点的升级率 ≈ 125 FTE ≈ 620 万美元/年**：升级率从 25% 压到 22% 约省 1 875 万美元/年，比把 70% 流量路由到 8B 省下的 1 830 万美元/年还多；即使把全部流量压到 8B 也只省 2 620 万美元/年。这条账决定了排期：先做政策与工具覆盖把升级率压下去，再谈推理优化（[[inference-serving-12]]）。

### 6. 失败模式、降级与上线路径

**失败模式与降级。** 两条原则：**升级人工永远可用**，以及**「状态未知」比「明确失败」更危险**。

| 失败 | 风险 | 降级动作 |
| --- | --- | --- |
| 写操作超时或连接中断 | 不知道下游是否已执行 | 禁止直接重试；按幂等键回读确认，确认不了就升级人工 |
| 动作网关或下游 API 整体不可用 | 所有写路径不可用 | 只读路径继续服务，写路径统一拒绝并建工单，不做无界排队 |
| 决策模型或推理集群不可用 | 无法生成方案与参数 | 退回「收集信息 + 建工单 + 转人工」，不执行任何写操作 |
| 政策引擎不可用或政策版本不一致 | 无法判定能不能做 | fail-closed：一律升级人工，绝不按提示词里的政策自行放宽 |
| 身份或鉴权服务抖动 | 无法确认主体 | 只允许只读，写操作全部拒绝 |
| 检索质量下降、知识过期 | 解释错误、承诺错误 | 检索分数低于阈值即升级；任何引用都要带文档版本 |
| 模型跑偏、同参数反复调用 | 重复副作用或死循环 | 断路器：连续失败 ≥ 2 或同参数重复即降档或升级（见代码 `tier`） |

**上线路径（每段都能按指标回退）**：① 只读 + 建议模式，agent 只生成方案与话术，坐席点确认才执行，同时用影子执行（只算不写）比对「拟执行动作」与「坐席实际动作」的一致率；② 低风险可逆写，放开 T1 类动作、阈值压低、全量审计，盯重复操作率与投诉率；③ 高风险操作，先审批后自动，按意图逐个放开（先小额退款再大额），每个意图都要过红线集门禁——越权、重复扣款、政策违背、身份误判零容忍（[[evaluation-04]]）。

**线上要同时看工程指标与业务指标**：动作成功率、重复操作率、升级率（分意图设区间）决定能不能继续放开，投诉率与补偿成本决定这套系统是否真的省钱（[[evaluation-09]]）。

## 数值与代码验证

以下数字均按文中所标假设自行复算，两篇来源未给出这些算例；口径逐条标注在表下。

### 1. 单次模型调用的 GPU 时间

口径：70B 用 LLaMA-3-70B 形状（80 层、8 KV 头、head_dim 128、bf16，即每 token $2\times80\times8\times128\times2 = 327{,}680$ B = 320 KiB KV），8B 用 LLaMA-3-8B 形状（32 层、8 KV 头、head_dim 128、bf16，即每 token 128 KiB KV，与本仓库其它专题同一口径）；H100 SXM5 bf16 稠密 989 TFLOPs、HBM3 3.35 TB/s，70B 取 TP=8、8B 取 TP=1，prefill MFU 45%、decode HBM 有效利用率 0.7、上下文 4k、输入 2 200 / 输出 350 token。

| 配置 | prefill | TPOT | decode | GPU·s/调用 |
| --- | --- | --- | --- | --- |
| 70B TP=8 | $2\times70\text{e}9\times2200/(8\times989\text{e}12\times0.45)$ = 86.5 ms | 8.04 ms | 2 812 ms | **23.19** |
| 8B TP=1 | 79.1 ms | 7.05 ms | 2 468 ms | **2.55** |

TPOT 来自每卡每 token 的读取量。70B：$140/8 = 17.5$ GB 权重加上 $4096 \times 320\ \text{KiB} = 1.25$ GiB KV（即 1.34 GB），合计 18.84 GB，除以 $3.35\times10^{12}\times0.7$ 得 8.04 ms。8B：16 GB 权重加上 $4096 \times 128\ \text{KiB} = 0.5$ GiB KV（即 0.54 GB），合计 16.54 GB，得 7.05 ms；两次都按十进制 GB 相加、GiB 先换算再代入带宽。decode 是绝对大头（70B 下占总时间的 97%），所以压成本要先动 decode：路由小模型、量化、max_tokens（[[inference-serving-12]]）。

### 2. 集群与单位成本

口径：100 万会话/天 × 5 次调用；GPU 单价 2.5 美元/GPU·小时。

| 方案 | GPU·s/会话 | GPU 数 | 8 卡机 | 美元/天 | 美分/会话 |
| --- | --- | --- | --- | --- | --- |
| 全部 70B | 116.0 | 1 342 | 168 | 80 521 | 8.05 |
| α=0.7 路由到 8B | 43.7 | 506 | 64 | 30 348 | **3.03** |
| 全部 8B | 12.7 | 147 | 19 | 8 845 | 0.88 |

路由增益 $G = 1/(\alpha/r + 1-\alpha)$，$\alpha=0.7$、$r=23.19/2.55=9.10$，得 $G=2.65$；相对全 70B 省约 1 830 万美元/年（月成本 2.42 M → 0.91 M 美元）。注意这 2.65× 是**单位算力成本**口径，不是端到端延迟口径。

### 3. 人力 vs 算力

口径：单通人工 6 min、8 h/人日、5 万美元/FTE·年；算力取上表 α=0.7 行（约 1 110 万美元/年）。

| 升级率 | 升级量 | FTE | 人力成本/年 | 相对算力 |
| --- | --- | --- | --- | --- |
| 20% | 200 k 通/天 | 2 500 | 1.25 亿 | 11.3× |
| 25% | 250 k 通/天 | 3 125 | 1.56 亿 | 14.1× |
| 30% | 300 k 通/天 | 3 750 | 1.88 亿 | 16.9× |
| 40% | 400 k 通/天 | 5 000 | 2.50 亿 | 22.6× |

升级率对 FTE 是线性的：每 1 个百分点 ≈ 125 FTE ≈ 620 万美元/年。这张表是「政策覆盖与工具能力优先于推理优化」的量化依据，也是升级率告警阈值的来源。

### 4. 挂起会话的显存代价

口径：按 70B 档这一最坏情况算，16 k 上下文 × 320 KiB/token = 5 GiB/会话；同样上下文在 8B 档只有 2 GiB/会话。

| 同时挂起 | KV 总量 | 折合 80 GB 卡 | 占 506 张 GPU 池 |
| --- | --- | --- | --- |
| 1 000 | 5.37 TB | 67 | 13% |
| 10 000 | 53.69 TB | 671 | 133% |
| 50 000 | 268.44 TB | 3 355 | 663% |

等待人工的会话不能占着 KV cache：状态落库、显存让出、恢复时重新 prefill（或从 prefix cache 的磁盘副本恢复）。这也是「升级后人工首次响应 ≤ 60 s」这个 SLO 的隐含成本。

### 5. pass^k 与断路器

口径：各次试验独立同分布（真实系统的错误相关，这里只用来说明量级）。pass^k 定义为 k 次独立试验**全部成功**的概率，论文给出的无偏估计量是 $\mathbb{E}_{\text{task}}\left[\binom{c}{k}/\binom{n}{k}\right]$（n 次试验中成功 c 次）；下表用 $p^k$ 这个独立同分布下的简化形式。

| 单次成功率 $p$ | pass^5 | pass^8 |
| --- | --- | --- |
| 0.50 | 0.0312 | 0.0039 |
| 0.90 | 0.5905 | 0.4305 |
| 0.95 | 0.7738 | 0.6634 |
| 0.99 | 0.9510 | 0.9227 |

对照量级：τ-bench 报告 gpt-4o 在 τ-retail 的 pass^1 约 61%、pass^8 低到约 25%，正是「单次看起来能用、重复起来不可用」的形态。要让 pass^8 达到 0.90，需要 $p = 0.9^{1/8} \approx 0.9869$。另一个角度：每步失败率 1% 时，15 步会话里「至少错一次」的概率是 $1-0.99^{15} \approx 14.0\%$；失败率降到 0.5% 则约 7.2%。这就是「高风险动作必须加断路器与审批」的量化理由。

```python
# ---- 幂等执行：一次逻辑动作只产生一次副作用 ----
def execute_once(store, idem_key, tool, args, run_tool):
    """store.dedup 在 idem_key 上有唯一约束，且与副作用在同一事务内写入：
    重复调用命中唯一键 → 捕获冲突后读回首次结果；并发下也只有一个调用者能赢。"""
    hit = store.dedup.get(idem_key)                 # {tenant}:{tool}:{object}:{intent}
    if hit is not None:
        return hit["result"]                        # 重投/重试/用户点两次都走这里
    try:
        with store.tx():                            # 副作用与去重记录同一事务
            result = run_tool(tool, args)
            store.dedup.put(idem_key, {"result": result, "change_id": result["change_id"]})
    except store.DuplicateKey:
        return store.dedup.get(idem_key)["result"]  # 输掉竞争的一方返回赢家的结果
    return result

def idem_key(tenant, tool, business_object, intent):
    return f"{tenant}:{tool}:{business_object}:{intent}"   # 作用域含业务对象，不只按请求 id

# ---- 政策引擎：政策是可执行规则，不是提示词 ----
def refund_policy(order, user, policy) -> tuple[bool, str]:
    days = (order["now"] - order["paid_at"]).days
    if order["status"] == "refunded":
        return False, "already_refunded"            # 幂等语义：重复请求直接返回既有结果
    if days > policy["refund_window_days"]:
        return False, "out_of_window"               # 政策外 → 升级人工，不自行放宽
    if order["amount_cents"] > policy["auto_refund_max_cents"]:
        return False, "needs_approval"              # 超阈值 → 审批/升级
    if user["risk_flags"]:
        return False, "manual_review"
    return True, "auto"

# ---- 风险分级 + 断路器 ----
def tier(tool, args, policy, ctx) -> str:
    if tool.get("prohibited") or not tool.get("auditable", True):
        return "T3"                                  # 禁止自动执行
    if not tool["reversible"] or args.get("amount_cents", 0) > policy["irreversible_max_cents"]:
        return "T2"                                  # 事前审批
    if ctx["consecutive_failures"] >= 2 or ctx["confidence"] < policy["min_confidence"]:
        return "T2"                                  # 连续失败/低置信 → 审批或升级
    return "T1" if tool["writes"] else "T0"

def pass_hat_k(p, k):
    return p ** k                                   # pass^k：k 次独立试验全部成功
print(round(pass_hat_k(0.9, 8), 4), round(0.9 ** (1 / 8), 4))   # 0.4305  0.9869
```

## 常见追问

- **追问**：用户说「你上次答应给我退款」，怎么办？
  - 要点：以系统状态为准，不信对话里的任何声明。动作网关先查订单与去重表：已退则返回既有结果与流水号；未退则按政策重新求值（可能已超窗口）。对话内容只是「用户的主张」，不是授权凭据，也不是事实来源；这类话术本身是注入面（[[safety-01]]）。
- **追问**：怎么防止 agent 被诱导执行越权操作？
  - 要点：三层——身份层（会话绑定的已验证主体，下游 on-behalf-of 透传，绝不按对话内容认定身份）、参数层（目标对象必须在主体可操作范围内，越权参数在网关拦截）、政策层（金额与次数上限由服务端强制）。提示词里的「只能退自己的订单」是软约束，不构成控制。
- **追问**：升级人工后 agent 该不该继续听对话？
  - 要点：默认退出决策路径、保留旁听。继续输出会与坐席抢话、给出矛盾承诺；但保留只读旁听有价值——坐席处理完可由 agent 接手后续只读查询、生成摘要与跟进任务。要显式定义交回条件（坐席标记 resolved、或用户再次发起只读请求）。
- **追问**：升级率定多少合适？
  - 要点：按意图分别定，不设全局单一目标。看两侧信号：升级率骤降 + 投诉率/重开率上升，说明在硬扛；升级率居高 + 同类意图集中，说明政策覆盖或工具缺失。用「每 1 个百分点 ≈ 125 FTE」把改进排期换算成钱。
- **追问**：政策变了（比如退款窗口从 30 天改成 14 天）怎么办？
  - 要点：政策是数据不是代码，变更走配置 + 灰度 + 回归门禁（[[evaluation-04]]）。存量会话按「动作执行时刻的政策」判定并在审计里记录政策版本，否则事后无法解释某笔退款为什么合规。
- **追问**：怎么证明这套系统可以放开高风险操作？
  - 要点：三段式上线——只读+建议 → 低风险可逆写 → 高风险（先审批后自动）。每段都用红线集门禁：越权、重复扣款、政策违背、身份误判零容忍；再叠加离线回放与影子执行（只算不写）比对拟执行动作与坐席实际动作的一致率。

## 公司变体

- **面向消费者的规模化 ML 公司（Uber、Netflix、LinkedIn、Airbnb、Pinterest、Spotify）**：偏工程实现与规模账。这类公司的公开工程输出习惯把问题落到「多大规模、多少成本、SLO 多少、出故障怎么降级」上，客服场景又天然连着订单、支付、账户这些核心系统。问法常从「每天多少会话、多少比例能自动解决、升级率怎么降、单位会话成本多少、坐席容量怎么排班」切入，会追问与既有工单/CRM 系统的集成边界、灰度与回滚、以及跨地区政策差异怎么表达。
- **Sierra**：偏对话式业务 agent 的产品化实现。公开材料强调 agent 只能执行被授权的业务动作，写操作（额度、退款、改单）要有不依赖模型的确定性护栏（code gate）与升级人工的路径，并且按「成功解决」而非「对话轮次」计价。问法更可能落在动作白名单、审批流、可观测性与多租户策略覆盖上，而不是公式推导；「护栏不能把正常任务拦死」也是其语境下的常见期待（[[safety-04]]）。

以上是依据两家公开技术输出的侧重判断，不是对具体面试流程的描述。
