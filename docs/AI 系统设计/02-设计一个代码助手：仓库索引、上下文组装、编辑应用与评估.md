## 一句话答案

> 代码助手不是一件事，而是四件事：**行内补全**（250 ms 内出结果、只看光标邻域）、**对话问答**（2 s 级、靠仓库索引）、**跨文件编辑**（分钟级、靠符号图 + 补丁校验）、**agentic 任务**（十分钟级、靠工具循环与测试反馈）。四档的延迟预算、上下文来源与评测口径必须分开设计。
> 索引的主力不是向量库：结构感知切分 + 符号图（定义/引用/调用）+ 分层摘要承担召回，向量检索只补「词汇重叠低」的那一类；索引构建的算力成本可以忽略（6,000 文件仓库全量一次不到 1 美分），真正的约束是新鲜度与增量路径，而它决定了整个系统的质量上限。
> 编辑应用的关键是**落地之后的那一段**——语法/类型/测试校验、版本哈希并发控制、逐块接受与可回滚；评估必须分档，补全看接受率与延迟分位数，跨文件任务看仓库级基准，agentic 看任务成功率与 pass^k。

## 面试官在考什么

- **会不会分层。** 把「代码助手」当成一个 RAG 框图的候选人立刻出局。铺开四个场景、指出它们的延迟预算差两个数量级、上下文来源互不相同、评测指标不能复用，这一层是这道题的第一道分水岭。
- **知不知道代码不是文档。** 代码检索的难点是精确定义与调用关系，那是符号表与编译器前端的活；语义相似度在「找 `parse_config` 的调用点」这类查询上天然不可靠。能主动说清「向量检索是补充而非主力」，并知道符号图缺失时如何降级到 grep/glob，才到进阶。
- **会不会算账。** 索引一次全量库到底花多少钱？补全档 250 ms 怎么分？agentic 档贵在哪一段？能用一组明确假设算出量级、指出预算花在哪里，比背出十个技术名词更能证明工程判断力。
- **有没有想过「改坏代码」这件事。** 从模型输出到文件落地之间必须有校验与回滚：补丁匹配失败率、上下文漂移、用户并发编辑、语法破坏。漏掉这一段是这道题最常见的失分点。
- 常见错误答案：
  - 「把仓库切块、embedding、向量检索 top-k 拼进 prompt」——没有符号图、没有分层摘要、没有预算分配，也回答不了「这个仓库怎么组织」。
  - 「模型返回新文件内容，直接写回」——说不出整文件重写的 token 代价、丢内容的风险，以及校验失败后怎么办。

## 原理与推导

### 1. 需求澄清与假设（先报数字，再报架构）

先分档，因为四档的设计完全不能互换：

| 档位 | 触发方式 | 延迟预算 | 上下文来源 | 主评测指标 |
| --- | --- | --- | --- | --- |
| 行内补全 | 每次击键/停顿 | p95 ≤ 250 ms | 光标前后窗口、当前文件骨架、少量跨文件定义 | 接受率、延迟分位数 |
| 对话问答 | 显式提问 | 首 token ≤ 2 s | 仓库索引检索、当前文件、指向的文件 | 引用正确率、人工有用性 |
| 跨文件编辑 | 显式指令 | 10 s–2 min | 符号图邻域、依赖图、编辑历史与诊断 | 补丁应用成功率、编译/测试通过率 |
| agentic 任务 | 任务描述 | 2–20 min | 上述全部 + 工具结果 + 计划 | 任务成功率、pass^k、单任务成本 |

**假设**（面试时应主动报出，并接受面试官改数）：10,000 名工程师；每人每天约 300 次补全请求（日均 $3.0\times10^6/86{,}400 \approx 34.7$ QPS，按 15 倍峰均比取峰值 521 QPS）；补全档每次请求 2k（2,048）token 上下文、40 token 输出；仓库中位数 6,000 个文件、每文件约 400 行、每行约 4.2 token（约 3.5 字符/token），即约 $6{,}000 \times 400 \times 4.2 \approx 1.0\times10^7$ token 源码；agentic 档每天 2,000 个任务、平均 120k 上下文、每任务 3k 输出 token。复用本仓库既有硬件口径：H100 SXM5 bf16 稠密 989 TFLOPs、HBM3 3.35 TB/s，roofline 拐点 $989/3.35 \approx 295$ FLOP/byte；LLaMA-3-70B（80 层、GQA-8、head_dim 128、bf16）每 token KV cache 为 320 KiB。

非功能 SLO：索引新鲜度「保存后 5 s 内可检索」；**索引过期比索引缺失更糟**（返回已删除的旧签名会让模型生成编译不过的代码）；密钥与凭据绝不进上下文与日志；所有文件修改可逆。

**组件与数据流。** 四档共用一条主干，分叉在检索深度与「要不要落地写文件」：

1. **编辑器插件（客户端）**：采集光标上下文与诊断、做出口过滤（忽略文件、密钥扫描），维护本地增量索引——隐私边界的第一道闸在这里；
2. **索引与符号服务**：tree-sitter 结构切分 + embedding 建向量，LSP/编译器前端产符号图与分层摘要，按 git 内容哈希与反向 import 闭包增量更新；
3. **上下文组装器**：按档位取权重排序、按 token 预算贪心装入，产出带 `path:line-range @content-hash` 标注的 prompt；
4. **模型路由与推理集群**：补全档走小模型（prefix cache + 连续批处理），问答/编辑档走中模型，agentic 档走大模型加工具循环，工具与测试跑在沙箱里；
5. **apply 与校验**：唯一匹配 → 语法/AST → 类型/lint → 相关测试，逐级失败则回灌重试，通过后原子写 + 快照回滚；
6. **遥测与评估**：接受率、延迟分位数、补丁成功率、回滚率汇入离线任务集与发布门禁。

一次补全只走 1→3→4→1（回客户端渲染）；一次问答走 1→2→3→4；一次跨文件编辑把 5 串进来；agentic 任务在 4 与 5 之间循环，直到测试通过或步数、成本触顶（[[agents-09]]）。

### 2. 仓库索引：结构优先，向量兜底

**结构感知切分。** 按函数/类/方法切，用 tree-sitter 之类的语法解析器拿 AST 边界，而不是按固定行数切。目标 chunk 200–800 token，相邻 chunk 留约 10–15% 重叠（跨函数调用处最容易丢信息）。按行数切会把函数签名和函数体切到两个 chunk 里，两个都变得不可用——这条与 [[rag-01]] 的 chunking 原则同源，只是边界来源从「标题/段落」换成了「语法节点」。

**符号图。** 用 LSP 或编译器前端产出精确符号表：定义位置、所有引用位置、调用边、类型信息。三者分工：

- 定义与引用 → 精确回答「谁调用了这个函数」「这个符号从哪来」，向量检索在这类查询上没有保证；
- 调用图 → 用 PageRank 式的图排序给「改动影响面」打分，决定哪些文件值得进上下文；
- 类型与签名 → 生成补丁时需要的约束（参数个数、返回类型）。

**分层索引。** 文件级摘要（这个文件干什么）、模块/包级摘要（这一层怎么组织）、仓库级概览（技术栈、构建方式、目录约定）。仓库级概览回答的是「这个仓库怎么组织」这类无法用 top-k 片段回答的问题，也是 agentic 档 system prompt 里最省 token 的一段。

**增量与本地。** 用内容哈希（不是 mtime）比对 git 状态，得到脏文件集合 $D$；再沿反向 import 边取闭包 $D^{+}$，只重解析、重嵌入这一部分；删除用 tombstone，避免「源文件没了但索引里还搜得到」（内容哈希 + 闭包 + tombstone 这套通用做法见 [[rag-11]]）。RepoBench 把仓库级补全拆成三个互相衔接的任务——RepoBench-R（从其它文件检索跨文件上下文）、RepoBench-C（带跨文件与文件内上下文预测下一行）、RepoBench-P（端到端管线），这个拆分本身就是「检索质量是这条链路第一环」的论证：管线端的分数无法超过检索端。

**本地索引还是服务端索引**，这是一条隐私与延迟的取舍线：本地索引不上传源码、跟随编辑几乎零延迟，但吃用户机器资源、跨仓库与团队协作能力弱、冷启动慢；服务端索引能做跨仓库检索与团队共享的摘要，但要求代码出内网。可行解是默认本地建索引、上传加密后的摘要与向量，并把「是否允许上传源码片段用于补全」做成显式开关。对照公开资料：Cursor 侧的叙述是索引以 embedding 为主、隐私模式下请求结束后不保留代码；Claude Code 侧的叙述是**不建仓库索引**，靠 Grep/Glob 按需搜索，把「智能」放在模型决定搜什么上（两条口径见来源）。同一道题里要能把这两种路线各自的代价说清楚。

### 3. 上下文组装：把一个有限窗口花在刀刃上

组装可以写成一个打分排序问题。对候选片段 $i$，按档位取不同的权重向量 $w^{(t)}$：

$$ \text{score}(i) = w^{(t)}_{\text{prox}} \cdot \text{prox}(i) + w^{(t)}_{\text{sym}} \cdot \text{sym}(i) + w^{(t)}_{\text{sim}} \cdot \text{sim}(i) + w^{(t)}_{\text{diag}} \cdot \text{diag}(i) $$

其中 $\text{prox}$ 是与光标的距离、$\text{sym}$ 是符号图上的接近度（同文件 > 直接调用 > 传递依赖）、$\text{sim}$ 是向量相似度、$\text{diag}$ 是「是否出现在当前诊断/失败测试里」。然后按 token 预算从高到低贪心装入，装满即停。补全档的权重几乎全给 $\text{prox}$ 与 $\text{sym}$；问答档给 $\text{sim}$ 与 $\text{sym}$；编辑与 agentic 档把 $\text{diag}$ 的权重提到最高。

**代码场景独有的强信号**是编辑历史与诊断：最近的 diff（模型想知道你刚写了什么）、LSP 报错、编译器输出、失败的测试名与断言。同一段代码在「能编译」和「编译报错」两种状态下，补全的正确率完全不同。把失败测试的输出贴进上下文，等于把一个可执行的验收条件交给了模型。

**结构化注入**：每个片段用 `path:line-range @content-hash` 标注，便于模型精确引用，也便于应用补丁时校验。单文件超预算时先给骨架（导入、类与函数签名、docstring）再按需展开相关函数体，不要整文件塞入——长上下文里的位置偏差是有代价的，见 [[llm-internals-13]]。

**预算管理**：超长文件不能「截断」，要「按需裁剪」；工具输出保留尾部（栈顶的报错信息在最后几行）并给出省略提示。

### 4. 编辑应用（apply）：从模型输出到文件落地

**补丁形式的三条路线与失败模式**：

| 形式 | token 成本 | 主要失败模式 |
| --- | --- | --- |
| 整文件重写 | 高（$O(\text{文件长度})$） | 模型顺手「改进」无关代码、丢注释、长文件被截断 |
| search/replace 块 | 低 | 匹配 0 次（空白/缩进/上下文漂移）或匹配多次（改错位置） |
| unified diff | 低 | 行号漂移导致 hunk 失败；对空白的容忍度差 |

工业界的做法多是让大模型只产出「改动意图」，再用一个小的 apply 模型负责插入（Cursor 的公开叙述即此分工）。工程上更稳的是 search/replace 块 + **逐级降级匹配**：精确匹配 → 忽略行尾空白 → 忽略全部空白 → 模糊匹配后要求人工确认。

**应用前的校验流水线**（每一级失败都把诊断回灌给模型重试，见 [[agents-02]]）：

1. 补丁能否原子应用（唯一匹配）；
2. 语法校验（tree-sitter/AST 解析通过）；
3. 类型/lint 诊断（LSP 无新增 error）；
4. 相关测试子集（改动文件的测试与 import 它的测试）。

失败回灌要带**最小可复现信息**：不匹配的原文片段 + 当前文件对应位置的哈希，而不是整份报错。

**并发冲突**：用户可能同时手改。以文件内容哈希做乐观并发——应用前比对哈希，不一致就拒绝并让模型在最新内容上重生成，或退化为「展示 diff 让人来合」。

**可逆性与权限**：编辑前落快照，逐块接受/拒绝，提交走原子写（临时文件 + rename）；读用户私有代码要有边界，写操作要有沙箱与权限模式（只读、可改文件、可跑命令）。这一套与 [[agents-10]] 的可逆性设计同构，只是粒度从「一次外部副作用」细化到「一个 hunk」。

### 5. 评估与上线

| 档位 | 离线 | 在线 | 发布门禁 |
| --- | --- | --- | --- |
| 补全 | RepoBench 三任务；编辑距离；单测通过率 | 接受率、接受后保留时长、p50/p95 延迟 | 接受率不降、p95 不超预算 |
| 问答 | 引用正确率（答案能否指向真实文件行） | 追问率、人工点赞、被复制比例 | 引用正确率与点赞率不降 |
| 跨文件编辑 | 仓库级任务集 + 真实 issue 修复 | 补丁应用成功率、编译/测试通过率、回滚率 | 应用成功率 ≥ 85%、编译通过 ≥ 95% |
| agentic | 真实 issue 基准的任务成功率与 pass^k | 任务成功率、工具调用次数、单任务成本、步数与成本上限（[[agents-09]]） | 成功率与成本同时达标 |

仓库级与单文件之间的差距必须报给面试官：SWE-bench 给出 2,294 个真实 GitHub issue 及对应 PR，判定方式是补丁必须让目标测试由失败转为通过且不破坏已有测试，且论文当时表现最好的模型（Claude 2）只解决 1.96%。引用这个数字必须带年份与口径——榜单分数已被后续系统大幅刷新；它的价值在于说明「真实仓库级任务」与「单文件补全」不是同一个难度带（同一口径的展开见 [[evaluation-10]]）。

CodeRAG-Bench 的结论用作反向警示：检索高质量上下文在多种设置下确实能提升代码生成，但现有检索器在**词汇重叠有限**时仍难取到有用上下文，且生成器在上下文长度受限或整合能力不足时收益有限。这正好论证了「符号图与结构信息比纯向量检索更重要」，也说明「多塞片段」不等于「更准」。

**补全档的「有用性」很难自动度量**：接受率只是代理指标（用户可能接受后立刻删掉，所以在线还要看「接受后保留时长」），因此要定期做人工盲评——同一批真实场景下并排展示两版模型的建议、隐去来源，让工程师按「有没有省下时间」打分；盲评样本量小、成本高，只作发布门禁的辅助证据，主门禁仍是接受率与 p95。

上线节奏：离线门禁 → 影子模式（记录补全但不展示，算接受率代理指标）→ 5% 灰度 → 全量。每一步都要盯延迟分位数，因为补全档的质量感知主要由 p95 决定，而不是平均值。

## 数值与代码验证

### 索引侧的账

| 量 | 假设 | 复算 |
| --- | --- | --- |
| 仓库源码量 | 6,000 文件 × 400 行 × 4.2 token/行 | $1.01\times10^7$ token |
| chunk 数 | 500 token/chunk、12% 重叠 | $1.01\times10^7 / (500\times0.88) \approx 2.3\times10^4$ |
| embedding 算力 | 0.1B encoder（$P=10^8$）前向 $2P$ FLOPs/token | $1.01\times10^7 \times 2\times10^8 = 2.0\times10^{15}$ FLOPs = 2,016 TFLOPs |
| 全量索引 GPU 时间 | 1×H100、MFU 30% | $2016/(989\times0.30) \approx 6.8$ s |
| 全量索引成本 | H100 按 2 美元/GPU·h | $6.8/3600 \times 2 \approx 0.0038$ 美元 |
| 向量存储 | 每 chunk 一个 768 维 fp16 向量 | $2.3\times10^4 \times 768 \times 2 = 3.5\times10^7$ B ≈ 33.6 MiB |
| 增量索引 | 20 个直接改动 + 60 个反向 import 闭包 | 80 文件 = 134k token → $1.34\times10^5 \times 2\times10^8 = 2.7\times10^{13}$ FLOPs = 27 TFLOPs，MFU 30% 下单卡 91 ms |

结论：**全量索引一次不到 1 美分**（约 0.4 美分），所以「索引贵不贵」不是这道题的考点；考点是「索引过期」与「增量路径」——脏文件占 0.5%（约 30 个直接改动）时，闭包后约 120 个文件、$120 \times 400 \times 4.2 = 2.0\times10^5$ token $\times 2\times10^8 = 4.0\times10^{13}$ FLOPs = 40 TFLOPs，MFU 30% 下单卡 136 ms，成本可以忽略，但每次提交都要跑。向量存储同样是零头：33.6 MiB/仓库，1 万个仓库约 0.33 TiB（HNSW 图的开销再乘 1.5–2 倍），所以索引侧的瓶颈既不在这块算力也不在这块存储，而在新鲜度。

### 补全档的延迟预算（250 ms 怎么分）

| 段 | 预算 | 复算依据 |
| --- | --- | --- |
| 网络往返（同区域） | 25 ms | 工程取值 |
| 检索 + 提示组装 | 25 ms | 符号图查询是本地索引 |
| 排队 + 批调度 | 15 ms | 连续批处理 |
| prefill 2k token | 20 ms | $2\times1.5\times10^9\times2048/(989\times10^{12}\times0.40) = 15.5$ ms |
| decode 40 token | 90 ms | 见下表 |
| 客户端渲染 | 10 ms | 工程取值 |
| 合计 | 185 ms | 余量留给尾延迟 |

decode 单步耗时沿用 $t_{\text{step}} = (W + b\,k\,S)/\text{BW}$（$W$ 权重字节、$k$ 每 token KV、$b$ 批内序列数、$S$ 上下文长度，S = 2048）：

| 模型 | 每 token KV | b=1 | b=8 | b=64 |
| --- | --- | --- | --- | --- |
| 0.5B（24 层、GQA-4、head_dim 64，bf16） | 24 KiB | 0.31 ms | 0.42 ms | 1.26 ms |
| 1.5B（28 层、GQA-4、head_dim 128，bf16） | 56 KiB | 0.93 ms | 1.18 ms | 3.14 ms |
| 70B（80 层、GQA-8、head_dim 128，bf16） | 320 KiB | 41.99 ms | 43.39 ms | 54.61 ms |

表中的 70B 行是**单卡等效**口径：140 GB 权重本来就装不进一张 80 GB 卡，按 TP=8 切分后每卡每步只读 $140/8$ GB 权重与 1 个 KV 头，b=8、S=2048 时单步 $(17.5\times10^9 + 8\times40{,}960\times2048)/3.35\times10^{12} \approx 5.4$ ms，但要占满 8 张卡。

1.5B 在 b=8 时 40 token 的墙钟时间只要 47 ms（$40\times1.18$），装得进 90 ms；70B 单卡等效要 1.74 s，即便切成 TP=8 也要 217 ms（$40\times5.4$）并占 8 张卡——**逐字补全不能上大模型**，这不是取舍，是硬约束。

### 成本分摊

| 档位 | 负载与容量 | 成本 |
| --- | --- | --- |
| 补全 | 3.0M 次/天（均值 34.7 QPS、峰值 521 QPS）× 2k 上下文、40 token 输出 | 峰值 prefill 需求 $521\times2048 = 1.07$M tok/s，单卡 prefill 能力 $989\times0.4/(2\times1.5\times10^9)=132$k tok/s → 需 8.1 张 H100 等效；按实际用量算：每请求 prefill 15.5 ms + decode $40\times1.18/8 = 5.9$ ms = 21.4 ms → 3.0M 次 = 17.8 GPU·h/天，按 2 美元/GPU·h 约 36 美元/天 ≈ **0.36 美分/人/天**（30% prefix cache 命中后 0.28 美分）；若按峰值全天预留则是 3.9 美分/人/天 |
| agentic | 2,000 任务/天 × 120k 上下文 + 3k 输出 | prefill $2\times70\times10^9\times1.2\times10^5 = 1.68\times10^{16}$ FLOPs = 16,800 TFLOPs/任务 → 8×H100 @40% MFU 为 5.3 s/任务，即 $2{,}000\times5.3\times8 = 8.5\times10^4$ GPU·s = 23.6 GPU·h/天（仅 prefill 的自建口径，约 47 美元/天）；按 API 单价输入 3 美元/M、输出 15 美元/M：无缓存 $2.4\times10^8\times3/10^6 + 6\times10^6\times15/10^6 = 810$ 美元/天，78% prefix cache 命中后 248 美元/天 → **2.5–8.1 美分/人/天** |

两档摊到全体差约 7–23 倍（补全 0.36 美分 vs agentic 2.5–8.1 美分），但**重度用户**单看 agentic 档：20 个任务/天在无缓存时是 $20\times1.2\times10^5\times3/10^6 + 20\times3{,}000\times15/10^6 = 8.1$ 美元/天、命中缓存后 2.48 美元/天——这就是必须做分层路由与 prefix cache 的原因。另外 120k 上下文 × 320 KiB/token = 36.6 GiB KV，单张 80 GB 卡装不下（权重本身就 140 GB），必须张量并行或上下文压缩。

### 可运行校验

下面这段把上面的表逐行复算，并验证「补丁必须唯一匹配」这条不变量：

```python
H100_FLOPS, H100_BW = 989e12, 3.35e12
assert abs(H100_FLOPS / H100_BW - 295) < 1          # roofline 拐点

KV = lambda L, H, D, b=2: 2 * L * H * D * b          # 每 token KV 字节数
assert KV(80, 8, 128) == 327680                     # LLaMA-3-70B 口径 320 KiB

FILES, LINES, TOK_PER_LINE, CHUNK, OVL = 6000, 400, 4.2, 500, 0.12
tokens = FILES * LINES * TOK_PER_LINE
print(tokens, tokens / (CHUNK * (1 - OVL)))          # 1.008e7, 2.29e4
print(tokens / (CHUNK * (1 - OVL)) * 768 * 2 / 1024**2)   # 33.6 MiB 向量（每 chunk 一个）

emb = tokens * 0.2e9                                 # 0.1B encoder 前向 2P = 2e8 FLOPs/token
print(emb / (H100_FLOPS * 0.30))                     # 6.8 s
print(emb / (H100_FLOPS * 0.30) / 3600 * 2.0)        # 0.0038 美元
print(120 * 400 * 4.2 * 0.2e9 / (H100_FLOPS * 0.30) * 1e3)   # 闭包后 120 文件：136 ms

t_step = lambda P, kv, b, S: (P * 2 + b * kv * S) / H100_BW
for P, kv in ((0.5e9, KV(24, 4, 64)), (1.5e9, KV(28, 4, 128)), (70e9, KV(80, 8, 128))):
    print([round(t_step(P, kv, b, 2048) * 1e3, 3) for b in (1, 8, 64)])

prefill_ms = 2 * 1.5e9 * 2048 / (H100_FLOPS * 0.40) * 1e3          # 15.5 ms
decode_ms = 40 * t_step(1.5e9, KV(28, 4, 128), 8, 2048) / 8 * 1e3  # 5.9 ms（b=8 摊到单请求）
print(prefill_ms, decode_ms)
print(3.0e6 * (prefill_ms + decode_ms) / 1e3 / 3600 * 2.0 / 1e4 * 100)  # 0.36 美分/人/天
print((120_000 * KV(80, 8, 128)) / 1024**3)          # 36.6 GiB KV

def apply_search_replace(src, old, new):
    """补丁必须唯一匹配：0 次是漂移，>1 次是危险。"""
    n = src.count(old)
    if n == 0:
        return None, "no-match"
    if n > 1:
        return None, "ambiguous"
    return src.replace(old, new), "ok"

src = "def f():\n    return 1\n"
assert apply_search_replace(src, "    return 1\n", "    return 2\n")[1] == "ok"
assert apply_search_replace(src, "    return 1\n    return 1\n", "x")[1] == "no-match"
assert apply_search_replace("a\na\n", "a\n", "b\n")[1] == "ambiguous"
```

## 常见追问

- **追问**：为什么不直接做全仓库 embedding 检索？
  - 要点：三类查询向量检索接不住——① 精确定义/引用（「谁调用了 `parse_config`」），靠符号表；② 仓库结构（「这个仓库怎么组织」），靠分层摘要；③ 语义相近但词汇不重叠的跨文件依赖，CodeRAG-Bench 明确指出这是当前检索器的弱项。向量检索的合理位置是「符号图邻域之外的长尾候选」，而且要用路径、语言、可见性做过滤后再排序。
- **追问**：行内补全的 250 ms 怎么分配？超预算先砍什么？
  - 要点：网络 25 + 检索组装 25 + 排队 15 + prefill 20 + decode 90 + 渲染 10。超预算的砍单顺序：先砍跨文件检索（退化为当前文件骨架）→ 再减输出长度与加 speculative decoding → 最后才换更小模型。反过来先换模型会同时损失质量与接受率。p95 靠「超时就撤掉建议」保，不要让灰字卡在屏幕上。
- **追问**：怎么防止模型改坏代码？
  - 要点：四道闸——补丁唯一匹配校验、语法/AST 校验、类型与 lint 诊断、相关测试子集；每道失败都把最小诊断回灌重试。之外还要版本哈希做乐观并发、编辑前快照、原子写、逐块接受。指标上盯「回滚率」与「新增诊断数」，而不是只看「接受率」。
- **追问**：长上下文模型（百万 token）会不会让索引与上下文组装失效？
  - 要点：不会，反而更需要。整仓库塞进窗口的成本是 $O(\text{仓库大小})$ 的 prefill，且每轮都要重付；而索引把成本降到一次 $O(\text{仓库大小})$ 的离线开销。即便窗口够大，KV cache（70B 口径 320 KiB/token）也会先爆显存。窗口变大改变的是「每档能塞多少片段」，不改变「按优先级分配预算」这件事。
- **追问**：密钥与私有代码怎么处理？
  - 要点：上下文组装阶段做出口过滤——按 `.gitignore`/`.aiignore`、文件类型（`.env`、`*.pem`、凭据目录）、以及高熵字符串扫描三重剔除；日志与 trace 里对源码片段做脱敏；索引默认本地或加密上传，且「用于补全的源码片段是否出境」是显式开关。反向风险也别漏：模型可能把凭据写进代码提交，pre-commit 扫描要覆盖。见 [[safety-07]]。
- **追问**：成本怎么压？
  - 要点：按档分层路由（补全小模型、问答中模型、agentic 大模型），prefix cache 复用 system + 仓库概览 + 未改动文件前缀（agentic 档的算例里省了 78% 的输入 token），上下文预算按收益排序而非「能塞就塞」，缓存检索结果与摘要，最后才是量化。手段清单与排序见 [[system-design-09]]。

## 公司变体

- **Cursor（Anysphere）**：公开资料里 Cursor 是「VS Code 外壳 + chunk embedding 索引 + 多模型分层」的路线——索引侧以 embedding 与语义检索为主、多数套餐不在服务端保留源码文本（公开叙述没有说明索引建在本地还是服务端），Tab 走小模型且要求「一瞬出结果」，Chat/Agent 走大模型，改动由专门的 apply 模型插入文件并展示为 diff 让人逐次接受，另有隐私模式与代码不外存的叙述。据此推断这家公司的面试会**偏工程实现**：索引新鲜度与增量路径、apply 阶段的格式与校验、以及延迟分位数与成本账，会比纯检索算法更受关注。注意这些是产品公开叙述，不是其内部架构的规格；被追问时先声明口径，再给可复算的设计。
