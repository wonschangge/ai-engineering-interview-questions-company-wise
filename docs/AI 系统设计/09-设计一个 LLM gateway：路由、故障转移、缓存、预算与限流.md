## 一句话答案

> gateway 是所有模型调用的统一入口，在一条请求路径上串起五个平面：路由（选谁）、韧性（挂了怎么办）、缓存（能不能不调）、预算与限流（谁能调多少）、可观测与治理（为什么这么调、花了多少）。它的价值是把「模型选择」从散落在业务代码里的 if-else 变成可灰度、可回滚、可审计的策略，并给出跨供应商的配额与成本口径。
> 边界同样要说清：gateway **不改业务提示词语义、不判断什么算正确答案、不做业务级缓存决策**（哪些答案允许复用由业务定，它只执行策略）。
> 基准算例（10M 请求/天，4,000 token 输入 / 400 token 输出）：全量走前沿模型 18 万美元/天；规则路由 70% 到小模型 3.0×，级联（25% 升级）3.4×，叠加 20% 语义缓存命中 4.3×；自建侧 1,500 token 共享前缀再省 1,180 GPU·h/天（147.5 个 8 卡节点·小时），约 2,949 美元/天。

## 面试官在考什么

- **边界感**：能不能说清 gateway 不负责什么。把「业务 prompt 逻辑」「答案正确性」「业务级缓存决策」塞进 gateway 的方案，会在第二次需求变更时崩掉。
- **路由是否分层且有序**：规则 → 分类器/学习式 → 级联 → 语义缓存前置，从便宜到贵；并且能给出「什么查询走哪条路」的决策表与延迟预算，而不是只说「用一个小模型做路由」。
- **缓存的三套机制与失效条件**：精确、语义、prefix 三者并存，失效条件各不相同；知道语义缓存的误命中是**质量问题**而不是性能问题。
- **限流与预算能不能落到算法**：令牌桶参数、预扣加结算、单请求/日/月三层同时约束、优先级与公平性。只会说「加个 rate limit」区分不出水平。
- **韧性工程细节**：错误分类、退避抖动、熔断、降级链、流式部分输出、幂等与计费去重、跨供应商的语义差异。
- **治理**：统一 trace schema、策略执行点、影子流量与金丝雀、失败时保持静态策略。

常见错误答案：

- 把 gateway 讲成「反向代理 + 重试三次」。重试是放大器不是方案：网关 3 次 × 客户端 3 次等于把下游故障放大 9 倍，必须有重试预算与熔断。
- 报语义缓存命中率却不报误命中率。命中率 × 误命中率才是代价，20% 命中配 2% 误命中就是每天 4 万条错答。

## 原理与推导

### 1. 定位与边界

gateway 是控制面与数据面的分离体：无状态数据面做逐请求决策，控制面下发策略（路由表、阈值、配额、模型清单、降级链），状态层放计数器、缓存与账本。

| 归属 | 内容 |
| --- | --- |
| gateway 负责 | 供应商适配与协议归一（OpenAI 兼容 / 原生 API / 自建 vLLM）、路由、重试与熔断、缓存执行、配额与限流、用量计费、脱敏与日志、模型版本与灰度 |
| 业务侧负责 | prompt 模板与工具定义、什么答案算对、是否允许复用某类答案、会话状态 |
| 都不负责 | 代替评测判断模型好坏（[[evaluation-04]]）、代替检索做权限判定（[[rag-08]]） |

不设边界的直接代价：业务规则每一次变更都要改网关并重新发布，网关变成发布瓶颈；更糟的是业务语义渗进缓存 key 与路由条件后，没人能解释一条请求为什么走了某条路。

### 2. 请求路径与状态

```
client → 边缘(鉴权/租户/区域) → 精确缓存 → 语义缓存 → 预算预扣 + 限流 → 路由决策
       → 供应商 A | 供应商 B | 自建 vLLM 池 → 流式回传 → 用量结算 → trace/计费/审计
```

**需求与假设**（后面所有算例都用这组）：1,000 万请求/天、平均 4,000 输入 + 400 输出 token、峰值系数 3；多租户、多区域、流式返回；栈级 SLO 取 TTFT p95 < 1 s（[[system-design-10]]），网关自身只分到 p99 ≤ 25 ms 的额外延迟预算（见第 3 节）。

| 组件 | 状态 | 关键要求 |
| --- | --- | --- |
| 数据面（无状态） | 只持本地 LRU 与最近一次策略快照 | 按 3 AZ × 2 副本部署；单实例按 500–1,000 QPS 设计，10M/天峰值 347 QPS 有充足余量 |
| 控制面 | 路由表、配额、模型清单、降级链 | 配置下发到全量 pod 的 p99 ≤ 5 s；**控制面不可用时用最近一次快照继续服务**（fail-static），不能因为改不了配置就停止服务 |
| Redis / 计数器 | 令牌桶、并发计数、熔断状态 | 原子 `check-and-decrement`（Lua）；热 key 按租户分片 |
| 缓存层 | 精确缓存、语义索引、prefix（引擎侧） | 语义索引与精确缓存分实例；命中路径不得回源 |
| 账本 | 用量、成本、审计 | 先记账再对外承诺计费；幂等键去重 |

### 3. 路由：从便宜到贵

**① 规则路由。** 按任务类型、租户档位、区域合规、成本上限直接映射。微秒级、可预测、可解释，是生产默认层；弱点是脆，靠关键词判断意图必然有漏（「帮我看看这段 Python 为什么不跑」不含 `bug`/`error` 就漏掉了）。规则要能热更新，并用离线样本回放测出漏判率。

**② 学习式路由。** 用历史偏好数据训练一个轻量 router，在强/弱模型之间动态选择。RouteLLM 的口径是：在部分基准与模型对上把成本降低 2 倍以上（摘要原文 over 2 times in certain cases）而不牺牲回答质量，且**换掉强/弱模型对之后路由器仍能工作**（迁移性）。迁移性是它值得上的核心理由——供应商与模型代际三个月一变，规则与提示词要重写，路由器不用。代价是要有偏好数据、要离线标定阈值、要有灰度和回退。

**③ 级联（cascade）。** 先问便宜模型，置信度不足再升级。FrugalGPT 把降本手段归为提示适配、模型近似、LLM 级联三类，并报告级联在匹配最优单模型（如 GPT-4）表现的同时最多降低约 98% 成本，或在同等成本下把准确率提升约 4%（该论文自有 benchmark 与计费口径，不能直接外推到线上流量）。工程上真正难的是**置信度判定**：自评分、格式校验、引用覆盖、小 verifier 都可用，但阈值必须在标注集上标定，否则「升级率」会在上线后漂移。

**④ 语义缓存前置。** 命中即零模型成本与个位数毫秒延迟，但它改变的是答案正确性，见第 4 节。

决策表（延迟预算同时给出，合计 p99 22.5 ms，是各段 p99 相加的保守上界）：

| 信号 | 走哪条路 | 前置检查 | 失败后的动作 |
| --- | --- | --- | --- |
| 请求指纹完全一致 | 精确缓存（0.5 ms） | 哈希含 prompt 版本、模型、解码参数、租户 | 直连模型 |
| 相似度 ≥ 阈值且关键槽位一致 | 语义缓存（embed + ANN 15 ms） | 阈值 + 金额/日期/否定词比对 + 高风险类别排除 | 直连模型 |
| 共享前缀命中 | 任意模型 + prefix cache | 前缀逐 token 一致（[[inference-serving-05]]） | 正常 prefill |
| 分类、抽取、短摘要 | 小模型 | 格式校验或置信度阈值 | 升级到中档 |
| 多步推理、代码、长上下文 | 前沿模型 | 预算与上下文长度检查 | 同档备用供应商 |
| 租户要求区域合规 | 区域内的自建池或合规供应商 | 策略表命中 | 排队或拒绝，不跨界 |

鉴权与配额预扣另计 3 ms，路由分类器 4 ms。源文给出的经验规则是**路由器自身延迟不超过所选模型延迟的 10%**，所以 LLM-as-router 只用于离线或异步路径：它本身 150–300 ms，用在交互路径上会把小模型的 TTFT 优势吃光。

### 4. 缓存三层，三种失效条件

| 层 | 命中条件 | 失效条件 | 主要风险 |
| --- | --- | --- | --- |
| 精确缓存 | 请求指纹逐字节一致 | prompt/模型/参数版本变更、TTL、租户隔离 | 缓存串租户（key 里漏了租户或 ACL 范围） |
| 语义缓存 | 嵌入相似度 ≥ 阈值 | 模型或 embedding 版本变更、答案时效性 | 语义近但约束不同 → 错答 |
| prefix / prompt cache | 前缀从第一个 token 起逐 token 一致 | 前缀里出现时间戳、随机 few-shot、按请求拼接的检索结果 | 命中率归零却以为开着 |

语义缓存把「召回」问题换成了「精度」问题：余弦相似度高只代表表述相近（相似度作为排序信号的语义边界见 [[rag-02]]），**否定词、数字、日期、货币、专有名词**恰好是相似度最不敏感的地方——源文的例子是阈值 0.85 时「法国首都」与「法国首都城市」相似度 0.93 命中，而阈值调低到 0.5 就会让「法国首都」命中「德国首都」。所以三道闸门缺一不可：高阈值（0.95 量级起步）、关键槽位必须完全一致（金额、日期、布尔否定、实体 ID）、高风险请求与高风险租户直接不缓存。三者的组合效果在「数值与代码验证」的表 4 里算。

失效必须是**版本驱动**而不是只靠 TTL：缓存 key 里带 `model@version`、`prompt_version`、`embedding_version`、租户与权限域，任一项变更即自然失效（[[evaluation-08]]）；TTL 与容量淘汰只是兜底。多租户下缓存条目要带 ACL 范围并在命中后再校验一次，否则就是 [[rag-08]] 里的「缓存串租户」。

prefix caching 只认 token，问法不同但语义相同的问题本来就不该命中——那是语义缓存这一层的事，两层不能互相替代。

### 5. 故障转移与韧性

先分类再处置（沿用 [[agents-02]] 的五类错误）：

| 类别 | 例子 | gateway 动作 |
| --- | --- | --- |
| 瞬时可重试 | 429、500/502/503/504、连接超时 | 指数退避 + 抖动，尊重 `Retry-After`；**优先换供应商而不是重试同一家** |
| 配额与计费 | 402、quota exceeded | 不计入熔断（不是健康问题），切备用或降级 |
| 请求本身有问题 | 400、上下文超长、内容策略拒答 | 不重试；拒答是模型行为差异，换供应商前先在评测里验证过（[[evaluation-04]]） |
| 依赖不可用 | 连续超时、连接被拒 | 供应商级与模型级熔断，快速失败 |
| 半成功（流式） | 已吐出 n 个 token | 不可透明重试，见下 |

**流式的提交点。** 第一个 token 发出后就不能悄悄重试：客户端已经看到内容，重来会得到两段不一致的文本并重复计费。三种可选语义：显式终止并给出可续传标记（客户端从断点重发，服务端把已输出内容作为 assistant 前缀续写，前提是供应商支持这种 prefill）、直接报错让客户端重来、非交互场景先缓冲再整体返回。交互路径一般选第一种，并把「已输出 token 不计费两次」写进结算逻辑。

**幂等与去重。** 客户端与网关两侧都要带幂等键；重试沿用同一个键，账本按键去重。超时是「结果未知」而不是失败，重放前先查状态。

**重试预算与放大。** 网关 3 次 × 客户端 3 次等于 9 倍放大，故障时恰好把下游打死。规则：重试总量不超过总请求的 10%，单供应商重试上限 2 次，抖动必须加（否则所有副本同时重试形成尖峰）。熔断参数示例：连续 5 次失败或 30 秒窗口内失败率超 50% 转 open，30 秒后放探测请求转 half-open。

**降级链与可用性口径。** 主模型 → 同档备用供应商 → 小模型（响应里带功能降级标记）→ 缓存或队列（异步返回）。每一跳都要在评测集上验证过：同样的 prompt 在不同供应商上行为不同（拒答边界、JSON 严格度、工具调用格式、上下文上限），未验证的降级会把「可用性事故」换成「质量事故」。可用性上，单供应商 99.9% 时两个独立供应商的朴素组合是 $1 - (1-0.999)^2 = 99.9999\%$，但算到六位数没有意义：DNS、控制面、共享 CDN、客户端 bug 都是相关故障，真实上限由「共同依赖」决定。gateway 的目标不是把可用性乘以供应商数量，而是消除单点、把降级做成人可见的行为。

### 6. 预算与限流

**限流维度与算法。** 维度：租户 / 用户 / API key / 模型 / 路由分支 / 区域。算法用令牌桶（允许突发、参数少）：容量 $C$ 决定突发，补充速率 $r$ 决定持续速率，最大突发就是 $C$。多副本下本地令牌桶会超发（N 个 pod 就有 N 份容量），要么按 key 一致哈希到固定 pod，要么统一走 Redis Lua 原子扣减，本地只做预检。

**token 预算：预扣 + 结算。** 预扣量 = prompt 实际 token（tokenizer 精确计数）+ `max_tokens`，响应后按实际用量结算并退还差额。这个做法安全但会低估并发：4,000 输入配 `max_tokens` 4,000 时预扣 8,000 而实际用 4,400，超额预扣 1.82×，等于把可用并发砍掉近一半。改进是用**分路由的 p95 输出长度**代替 `max_tokens` 做预扣，并给预扣加 TTL（超时未结算自动释放），再加一个对账任务兜底。结算失败不能静默：宁可少算也不能漏账，漏账等于免费额度。

**三层同时约束（都按租户计）。** 全局日均是 $10^7 \times 4400 = 4.4\times10^{10}$ token，所以阈值必须落到租户维度，全局阈值没有意义。单请求上限（36k token）、日上限（1 亿 token）、月配额（20 亿 token）各拦一类滥用：单请求上限拦「一个巨型请求」；日上限拦「慢速滥用」；月配额是商务与计费口径。只设日上限不设请求速率，2,778 个满额请求就能打空一天（单请求上限 36k ÷ 日上限 1e8），按 50 QPS 只需 56 秒；只设请求速率不设单请求上限，单个 100 万 token 的上下文请求就能顶掉上千个正常请求。两层缺一不可。

**优先级、公平性与超限处置。** 按档位加权（付费租户权重高），但必须有保底：单个租户在全局利用率低于 70% 时允许借用余量，高于 70% 时被压回自己的公平份额，这样既不过早拒绝，也不让一个大租户在高峰打满。超限后按用户体验排序的四种处置：排队（仅对可等待的批量流量，$\rho$ 越高排队时间按 $\rho/(1-\rho)$ 上升，$\rho=0.8$ 时已是服务时间的 4 倍）、降级到小模型（要提示用户）、截断上下文（会掉质量，需业务同意）、拒绝并返回可行动的 `Retry-After`。告警阈值设在配额 80% 与 100%，并区分「用量增长」与「异常重试」。

**成本归因。** 每个请求把成本打到租户、功能、会话、路由分支上（[[evaluation-07]]），否则无法回答「是哪个功能把账单推高的」。

### 7. 可观测、治理与发布

统一 schema 至少记：`trace_id`、租户与 key、模型与版本、路由决策与原因（含 router 版本）、prompt 版本、输入/输出/缓存 token、缓存层与相似度分数、TTFT/TPOT（[[inference-serving-09]]）、重试次数与错误类、单请求成本、策略判定结果。原始 prompt 默认只存哈希与长度，全文按采样加密留存——日志与 trace 是 PII 泄露最常见的出口（[[safety-07]]）。

gateway 同时是**策略执行点**：内容策略与拒答规则、PII 脱敏、区域路由（数据不出境）、租户模型白名单、审计留痕。把这些放在业务侧会导致每个业务各实现一遍且口径不一。

发布用影子流量与金丝雀：新模型或新 router 先影子跑（只记录不返回），对比离线 judge、格式合法率与成本，再按租户队列灰度；护栏指标（错误率、p99、单位成本、拒答率）越线自动回滚（[[evaluation-04]]、[[evaluation-08]]）。

## 数值与代码验证

常数与仓库其它专题一致：H100 SXM5 bf16 稠密 989 TFLOPs、HBM3 3.35 TB/s、拐点 295 FLOPs/byte、2.5 美元/GPU·小时；LLaMA-3-70B 每 token KV 320 KiB。

**表 1：负载与网关自身容量**

| 量 | 计算 | 结果 |
| --- | --- | --- |
| 平均 QPS | $10^7 / 86400$ | 115.7 |
| 峰值 QPS | 115.7 × 3 | 347 |
| 全量文本落盘（不截断） | $10^7 \times 4400 \times 4$ B（4 B/token） | 176 GB/天 |
| 只存元数据（2 KiB/条） | $10^7 \times 2048$ B | 20.5 GB/天（列存 + 冷热分层，热 7 天） |

收益公式与 [[inference-serving-12]] 一致：$G = 1/(\alpha/r + 1 - \alpha)$，$\alpha$ 是分流到小模型的比例，$r = 0.018/0.0008 = 22.5$ 是成本比。级联的口径要写清：升级的 25% 付两次钱（0.0188 美元，比直接问前沿贵 4.4%），收益全部来自不升级的 75%。

| 避免写入的 KV | $1.2\times10^{10} \times 327{,}680$ B | 3.93 PB/天 |

第三行是「省 prefill 不省 decode」：前缀的 KV 在 decode 阶段仍会被读，prefix caching 减的是算力与写入，不是 decode 带宽（[[inference-serving-05]]）。

「误命中 2%」是必须离线标定的假设值：拿真实流量做人工判定，画出阈值 → 命中率/误命中率曲线，再选工作点。把错答压到万分之一（$h$ 为命中率、$\varepsilon$ 为误命中率，$h\varepsilon \le 10^{-4}$）是这道题的质量门槛。

| 项 | 参数 | 说明 |
| --- | --- | --- |
| 免费档 | $C = 60$ 请求，$r = 1$ 请求/s | 突发 60 个后按 60 请求/分钟持续 |

| 单请求上限 | 36k token | 32k 输入 + 4k 输出 |

| 月配额 | $2\times10^9$ token | 商务与计费口径 |
| 预扣膨胀 | $8000/4400 = 1.82\times$ | 按分路由 p95 输出长度预扣可压到 1.1× 量级 |
| 重试放大 | $3 \times 3 = 9\times$ | 用 10% 重试预算与熔断封顶 |

```python
BW, BF16, MFU, P_GPU, N = 3.35e12, 989e12, 0.4, 2.5, 70e9
KV_TOK = 2 * 80 * 8 * 128 * 2                    # LLaMA-3-70B：320 KiB/token
Q, S_IN, S_OUT = 10e6, 4000, 400                 # 请求/天、平均输入、平均输出
print(KV_TOK / 1024, round(BF16 / BW))           # 320.0 295  常数复核

IN_F, OUT_F, IN_S, OUT_S = 3.0, 15.0, 0.15, 0.50  # 美元/1M token
c_f = S_IN * IN_F / 1e6 + S_OUT * OUT_F / 1e6
c_s = S_IN * IN_S / 1e6 + S_OUT * OUT_S / 1e6
print(round(c_f, 4), round(c_s, 5), round(c_f / c_s, 1))   # 0.018 0.0008 22.5

def gain(alpha, r=c_f / c_s):                    # 路由收益：alpha 分流到小模型
    return 1 / (alpha / r + 1 - alpha)
print(round(gain(0.7), 2), round(c_f / (c_s + 0.25 * c_f), 2))
# 3.02 3.40   规则路由 70%；级联（25% 升级）

hit = 0.20
print(round(c_f / ((c_s + 0.25 * c_f) * (1 - hit)), 2), f"{Q * (c_s + 0.25 * c_f) * (1 - hit):,.0f}")
# 4.25 42,400   叠加语义缓存命中 20% 后的倍数与日成本（美元）

tok = Q * 0.8 * 1500                             # 1,500 token 共享前缀覆盖 80% 流量
node_h = 2 * N * tok / (BF16 * 8 * MFU) / 3600   # 分母是 8 卡整节点吞吐，故得到节点·小时
print(f"{tok:.2e}", round(node_h, 1), round(node_h * 8), round(node_h * 8 * P_GPU), round(tok * KV_TOK / 1e15, 2))
# 1.20e+10 147.5 1180 2949 3.93   节点·小时、GPU·小时、美元/天、避免写入的 KV（PB）

C, r = 60, 1.0                                   # 令牌桶：容量与补充速率
print(C, round(r * 60), round(C / r), round((S_IN + 4000) / (S_IN + S_OUT), 2))
# 60 60 60 1.82   突发 60 个、持续 60 请求/分钟、预扣 max_tokens 时的超额倍数
# 错答预算：10e6 × 0.2 × 0.02 = 40,000/天；阈值 0.95+槽位校验+高风险排除后 10e6 × 0.15 × 4e-4 = 600/天
```

## 常见追问

- **追问**：语义缓存的误命中怎么防？
  - 要点：三道闸门同时上——阈值（0.95 量级起步，用真实流量标定）、关键槽位必须逐字一致（金额、日期、数字、否定词、实体 ID，这些恰好是相似度最不敏感的地方）、高风险类别与高风险租户直接不缓存。再加两件工程措施：命中后仍做一次权限校验（防串租户），命中率与误命中率一起上报，误命中率靠抽样人工判定而不是靠相似度分数自证。
- **追问**：供应商限流（429）时怎么平滑？
  - 要点：先区分「配额耗尽」与「瞬时限流」。瞬时 429 走退避 + 抖动 + 换供应商，并读 `Retry-After` 对齐窗口；持续性 429 说明容量不够，要么按公平份额压回租户，要么走降级链。排队只对可等待流量开放，$\rho$ 超过 0.7 后排队时间按 $\rho/(1-\rho)$ 上升，用排队掩盖容量不足会把 p99 变成事故。拒绝时给可行动的 `Retry-After` 比静默降级更诚实。
- **追问**：自建推理与外部 API 如何统一编排？
  - 要点：统一到同一份抽象上——同一个请求契约、同一份用量口径（token 数与成本）、同一套 SLO。自建池（[[inference-serving-11]]）的优势是单位成本与数据边界，弱点是容量弹性差；外部 API 相反。所以路由策略上把「延迟敏感且可缓存前缀」的流量放自建，把「突发与长尾」放外部，并用同一个熔断器与降级链管理；自建侧的 prefix cache 与 continuous batching 收益要按 [[inference-serving-05]] 的 exact-prefix 规则单独核算，不能和 API 的 prompt caching 折扣混着算。
- **追问**：缓存 key 里必须放什么？
  - 要点：模型与版本、prompt 模板版本、解码参数（temperature、top_p、max_tokens）、embedding 版本与阈值版本、租户与权限域、工具定义哈希、区域。少任何一项都会出现「同样的问题不同答案」或「跨租户串数据」。权限域尤其危险：命中的是文本，授权的是人（[[rag-08]]）。
- **追问**：预算超了应该拒绝还是降级？
  - 要点：按流量类型分。交互式请求降级到小模型并在响应里标注；批量与异步请求排队；付费租户在 80% 阈值先告警再硬限；任何情况下都不静默降级质量——用户感知到「答案变差了但没人告诉我」比拒绝更伤信任。

## 公司变体

以下按各家公开技术材料与产品形态判断侧重方向，不涉及具体面试流程。

- **Perplexity**：消费级 AI 搜索，流量峰值陡、TTFT 直接决定留存，且同时用自建推理与外部模型。偏工程与产品体验：峰值下的配额与排队、答案流式体验、搜索结果与摘要的缓存分层、免费与付费档的限流差异、跨供应商的答案一致性。追问会落在「峰值时你先牺牲谁」这类取舍上，而不是论文级推导。
- **Palantir**：企业级与前置部署（AIP / Foundry 形态），同一套 gateway 要能跑在客户自己的环境里。偏治理与合规：租户与数据边界硬隔离、模型白名单与区域路由、逐请求审计留痕与成本归属到项目、客户环境内的降级（连不上外部 API 时怎么办）、策略变更的可回滚。追问会落在「这条请求为什么走了这个模型、谁批准的、怎么证明」这类可审计性问题上。
