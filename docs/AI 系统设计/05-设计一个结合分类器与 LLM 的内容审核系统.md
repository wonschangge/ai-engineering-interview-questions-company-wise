## 一句话答案

> 审核系统的目标函数是「按类目分别约束漏放率与误杀率」，不是「最大化准确率」。架构因此是**分层级联**：规则与哈希拦已知违规，小分类器对全量内容做多标签打分，只有落入灰区的样本才调 LLM 做语境判断，最后极少数送人审。分层不是为了省事，而是因为**容量事实**——日均亿级内容不可能全量人审；全量过 LLM 在算力上其实做得到（7B judge 全量约 18.5 张 H100、4,680 美元/天），真正否决它的是同步路径上的延迟与稳定性。
> 分工的依据是「谁在哪一段更强」：分类器快、便宜、可高吞吐，适合全量前置过滤并调低阈值保召回；LLM 语义理解强，适合讽刺、引用、教育语境与 coded language，以及分类器覆盖不到的类目。级联的总体召回近似 $1-(1-r_1)(1-r_2)$，而成本几乎完全由**灰区比例**决定——这个比例是本题唯一需要承诺的工程指标。
> 必须一起交付的还有：人审队列的优先级与审核员保护、申诉与误杀纠正的闭环、以及按类目分层的评测与漂移监控。少了这三样，系统只是「一个更准的分类器」。

## 面试官在考什么

- **能不能先定需求再选模型**：有害类目清单、误杀的代价（正常用户被拦的体验与留存损失）、漏放的代价（平台风险与法律合规）、以及内容量级与延迟形态（发布前同步拦截 vs 事后批量巡检）。类目没定清就开始比模型，是最常见的跑偏。
- **级联的分工与路由是否讲得具体**：分类器为什么阈值要调低、灰区由什么构成、LLM 到底解决哪一类样本、路由判据用什么量（分数带宽、类目、语言、内容长度）。只会说「分类器初筛、LLM 复核」而不给路由判据，等于没答。
- **成本与容量的算术**：日均内容量 × 每层调用比例 × 单次成本，能推出「灰区比例必须控制在多少以内」；能说清全量人审在物理上不可行（要多少人、多少钱）。
- **有没有人审闭环与治理意识**：队列优先级按危害严重度 × 传播速度而不是先到先审、审核员心理健康保护、申诉通道、审计留痕（[[agents-10]]）。
- **评测口径**：按类目报精确率/召回率、按阈值说明偏向漏放还是误杀、对抗集与领域内数据（[[evaluation-01]]、[[evaluation-02]]、[[safety-10]]）。

常见错误答案：

- 「先用小模型粗筛，再用大模型精筛，最后人工复核」——把级联说成三句话，答不出阈值怎么定、灰区多大、二级需要多少召回，也答不出为什么不能只用一个更大的模型。
- 只谈模型准确率，不谈误杀在规模下的绝对量。1% 的误杀率在亿级内容上是百万级被误伤的正常内容，这是产品事故而不只是指标问题。

## 原理与推导

### 1. 需求与目标函数：先把两类错误定价

审核系统的输出不是「有害/无害」，而是**类目 × 动作**。类目来自平台政策与辖区法规，工程上要落成一份可维护的清单：暴力、仇恨、性内容、自伤、骚扰、垃圾广告与欺诈，加上平台特有类目（例如交易平台的违禁品、金融平台的荐股与承诺收益）。每个类目单独定义动作：放行 / 打标降权 / 打标送人审 / 限流 / 拦截 / 拦截并封号。

目标函数按类目写成两个约束而不是一个分数：

$$\min_{\theta}\ \sum_c w_c \cdot \mathrm{FP}_c(\theta) \quad \text{s.t.}\ \mathrm{FN}_c(\theta) \le \epsilon_c \ \ \forall c$$

其中 $\epsilon_c$ 是类目 $c$ 允许的漏放上限，$w_c$ 是误杀一个正常内容的代价。这条式子的工程含义是：**先按类目把漏放上限钉死，再在满足上限的前提下最小化误杀**。对自伤、未成年人、恐怖主义这类类目，$\epsilon_c$ 接近 0，阈值必须偏保守；对创意写作、性教育、医学科普，$w_c$ 很大，宁可提示或软化也不拦。

**容量事实决定了不可能全量人审。** 假设日均 1.2 亿条待审内容（1 亿日活，人均 0.2 条帖子 + 1 条评论），违规占比 0.5%：

| 人审单条耗时 | 所需等效人力（24 小时无休） | @3 美元/条 日成本 |
| --- | --- | --- |
| 30 s | 41,667 人 | 3.6 亿美元 |
| 60 s | 83,333 人 | 3.6 亿美元 |
| 200 s | 277,778 人 | 3.6 亿美元 |

三行的日成本相同（人力按条计费，与耗时无关），差别在于**要雇多少人**。任何量级下这都是不可能的组织规模，所以人审只能是抽样、申诉与高危样本的通道，自动化层必须承担 99% 以上的判定量。

**延迟形态分两种，架构不同。** 发布前拦截（评论、私信、直播间弹幕）要求同步低延迟，判定必须在百毫秒量级完成；事后巡检（历史帖子、批量导入内容）可以异步，允许分钟级与批处理。混合形态最常见：同步路径只跑规则 + 分类器，命中灰区的先**隔离（quarantine）**不发布，等 LLM 判定后再放行——把延迟从用户可感知的路径上挪走。**三个失败模式要预设降级动作**：judge 超时或不可用 → 灰区一律按保守动作处理并转异步复核；人审队列积压超过 SLA → 高危类目继续拦截、其余类目切成「先放行 + 事后巡检 + 抽检」；审核链路整体不可用 → 同步路径剥到只剩 L0 规则，宁可短时放宽也不阻塞发布。每个动作都要有触发指标与一键回滚。

### 2. 分类体系与标注：这条链路比选模型重要

参考源的方法论骨架值得照抄顺序：先设计内容分类体系与标注指南 → 数据质量控制 → 用主动学习捕获稀有事件 → 用多种方法提升鲁棒性、避免过拟合。论文明确把这一串步骤（taxonomy 与 labeling instructions、data quality control、active learning pipeline、robustness 方法）当作系统成功的原因，而不是某个模型结构；它训练的是覆盖性内容、仇恨内容、暴力、自伤、骚扰等多类别的分类器，并报告这套做法产出的分类器优于开箱即用的模型（摘要口径）。

工程上要落实三件事：① **标注指南要写成可判定的判据**，每条类目配正例与反例，并显式处理「引用 vs 宣扬」「教育 vs 教唆」「新闻 vs 骚扰」这类边界；② **数据质量控制靠双人复核 + 分歧仲裁**，一致率必须用 $\kappa$ 校正后再报，边际分布会骗人（换算方法见 [[evaluation-02]]）；③ **主动学习针对稀有事件**，按不确定度与类目稀有度挑样本送标，而不是随机抽——稀有类目的正例在随机抽样里几乎抽不到。鲁棒性方法（同义改写、编码混淆、多语言、长度扰动、对抗模板）各自作为独立的增强来源，不能指望模型自己泛化。

### 3. 分层级联：每一层的职责与判据

| 层 | 典型形态 | 覆盖量 | 单条成本 | 职责 |
| --- | --- | --- | --- | --- |
| L0 规则与哈希 | 精确/模糊哈希匹配、正则、域名与文件指纹 | 全量 | 纳秒级，可忽略 | 已知违规（CSAM 哈希库、已确认的垃圾模板）零延迟拦截 |
| L1 小分类器 | 400M 级 encoder 多标签（类目 × 分数） | 全量 | ≈ 0.5 ms H100 时间/条（算力口径） | 高召回前置过滤，阈值调低，宁可多送灰区 |
| L2 LLM judge | 7B 级指令微调模型，输出类目 + 理由 | 灰区（1%–2%） | 3.9 × 10⁻⁵ 美元/条 | 语境与边界判断、coded language、解释 |
| L3 人审 | 审核员 + 工具化摘要 | 灰区的一小部分 | 3 美元/条 | 高危、申诉、策略变更期的抽样校准 |

**路由判据是这道题的题眼。** 不是「分数低于 0.9 就送 LLM」这么简单，实用的路由条件有四类：① 分数落在灰带 $[\tau_{\text{low}}, \tau_{\text{high}}]$；② 分类器对该类目整体弱（类目级校准差）；③ 内容特征触发（多语言、长度超限、含引用与代码块、会话历史里有前序违规）；④ 用户级信号（新账号、近期被处罚、速率异常）。前三类判据都在降低「把简单样本送去贵模型」的比例；这套「按请求特征在多个判定深度之间选一个」的形态与 [[system-design-09]] 的 gateway 路由同源，差别只是这里的「后端」是判定深度而不是模型档位。

**级联的召回与成本。** 设一级在违规样本上的召回为 $r_1$、在正常内容上的误报率为 $f_1$，二级在「一级漏掉的违规」上的召回为 $r_2$，则

$$\text{漏放率} = (1-r_1)(1-r_2), \qquad \text{总误杀率} \approx f_1(1-f_2^{\text{fp}}) + f_2^{\text{fp}}$$

第二式的读法是：一级的误报只有在二级也判错时才会落到用户身上，所以**二级 LLM 对误报的主要价值是把一级的误杀捞回来**——这是级联里最容易被忽略的收益。

**灰区的构成决定了整套系统的成本。** 灰区里绝大多数是正常内容：以 $r_1 = 0.86$、$f_1 = 0.70\%$、违规占比 0.5% 计，日均 91.7 万条灰区里只有 8.4 万条是真违规，其余 91% 是一级的误报。于是 LLM 层的调用量由**误报率**而不是违规率决定，降低误报率同时降低 LLM 成本与人审成本。

### 4. LLM 在审核里的四种用法

- **边界与语境判断**：讽刺、反讽、引用与转述、教育或新闻语境、群体内部的自称用法（reclaimed language）。这些样本对词袋式分类器天然不友好，也正是灰区的主体。
- **coded language 与规避手法**：拆字、同音、异体字、emoji 与谐音替换、跨轮次拼装。LLM 的上下文窗口让它能看整段对话而不是单条文本。
- **类目解释与可解释判定**：输出「命中哪条政策 + 理由 + 证据 span」，这是审核员工具与用户申诉话术的输入。分类器给不出这个。
- **类目可配置的 safeguard 形态**：参考 Llama Guard 的定位——基于一组安全风险分类法的输入-输出双向 safeguard，底座是指令微调过的 Llama2-7b，既对 prompt 分类也对模型回复分类，输出多类标签与二元决策分数；指令微调让类目与输出格式可以定制，也能用不同分类法做 zero-shot / few-shot。论文摘要口径称它在 OpenAI Moderation Evaluation 与 ToxicChat 上匹配或超过当时已有的内容审核工具。落到工程上，这对应「一个可配置类目的判定模型」这一形态，调用次数是主要成本项。

**注意 LLM 的两个结构性弱点。** ① 判定不稳定：同一段文本换一次 prompt 或换一个温度就可能翻转，必须固定解码参数、固定 rubric、并做多次采样的一致性检查；② 它不擅长「零容忍类目的高召回」——对哈希库已知的 CSAM 或已确认的垃圾模板，规则与哈希的确定性远比模型可靠。所以 L0 与 L1 不是 LLM 的前置步骤，而是各自承担 LLM 不擅长的部分。

### 5. 领域差异：模型不能直接拿来用

**用户-AI 对话不是社交媒体内容。** ToxicChat 的定位正是这一点：此前的毒性检测基准多来自社交媒体内容，而真实用户与 AI 的交互有自己独特的分布现象，该工作用来自开源聊天机器人的真实用户 query 构造基准，并系统评测了在既有毒性数据集上训练的模型，结论是它们迁移到这个领域时暴露出短板（摘要口径）。工程结论只有一条：**审核模型必须用自己业务的数据评测与微调**，公开基准上的分数不能作为上线依据。

**误杀少数群体相关文本是系统性风险，不是偶发 bug。** ToxiGen 的出发点就是「毒性检测系统常常把包含少数群体提及的文本误判为有毒」，因为那些群体本身是网络仇恨的目标，模型学到的是虚假相关（spurious correlation）；同一机制也让模型难以识别**隐式毒性**。该工作用机器生成的方式构造了 27.4 万条关于 13 个少数群体的毒性与良性陈述，并报告人工标注者难以区分机器生成文本与人类撰写文本，其中 94.5% 的毒性样本被标注者判为仇恨言论；在三个公开数据集上微调后，性能在人类撰写数据上有实质提升。这条引用同时支撑两个结论：**误杀问题真实存在且可量化**，以及**合成数据可以缓解数据稀缺**。

由此得到两条工程动作：① 评测集必须包含「提及少数群体但完全良性」的对照样本，并单独报告这类样本上的误杀率（[[safety-09]] 的切片审计方法直接可用）；② 训练数据里要把群体提及与毒性解耦——合成良性对照是成本最低的手段。

### 6. 人审与申诉的闭环

**分层处置。** 自动放行 / 打标降权 / 打标送人审 / 限流 / 拦截 / 拦截并处罚。二元处置（放行或删除）是误杀率高的直接原因：把「删除」换成「降权 + 打标」，正常内容的通过率会明显改善。

**队列优先级按危害严重度 × 传播速度排序**，不是先到先审。严重度由类目与政策决定，传播速度用互动量、转发量与时间衰减估计；高危类目（自伤、未成年人、暴力威胁）走独立的高优先级队列，且带 SLA。

**审核员的保护是硬需求**：轮换高危队列、默认展示工具化摘要而不是原始内容、限制单日高危 exposure、提供心理支持——审核员流失率直接决定系统容量。

**权限与数据边界要和判定链路一起设计**：审核台按角色最小授权，一线审核员默认只看脱敏摘要与判定证据（命中的政策条目、理由、证据 span），原始内容与用户身份要二次授权且留痕；判定记录长期留存用于审计与申诉，原始内容与截图的保留期短得多，并响应删除请求；跨辖区内容不得路由到辖区外的审核队列或模型端点，人工与模型受同一套数据驻留约束；CSAM 这类内容禁入普通队列，走受限的专门上报通道。

**申诉与误杀纠正必须存在，且结果要回灌**：申诉通道是误杀样本的主要来源，纠正后的样本进训练集与回归集（[[evaluation-02]]）。审计记录同样落在这条链路上：每次判定记录策略版本、命中类目、分数、动作、模型版本与时间戳（[[agents-10]]）。

### 7. 评测与治理

- **指标按类目报告精确率/召回率**，并显式声明阈值偏向：自伤类目走漏放优先，创作类目走误杀优先。混成一个总分等于把类目间的取舍藏起来。
- **对抗集持续更新**：隐式毒性、编码绕过、多语言、长上下文、跨轮次拼装。红队产出的绕过手法当天就要进回归集（[[safety-10]]）。
- **评测集按领域与语言分层并防污染**：业务分布与公开基准不同，必须自建；对抗样本回流训练集时按内容哈希去重（[[evaluation-06]]）。
- **漂移监控**：新黑话、新梗、新攻击手法会让分类器在一两周内失效。按类目监控分数分布与灰区比例的位移，超阈值触发重训（[[rag-07]]）。
- **输入侧与输出侧要分开审**：审核用户输入 ≠ 审核模型输出，两者的类目与判据不同（[[safety-04]]）。

## 数值与代码验证

统一口径：日均 **1.2 亿条**待审内容、违规占比 **0.5%**（60 万条）、分类器为 400M encoder、judge 为 7B 模型（32 层、GQA-8、head_dim 128、bf16，即每 token KV $2 \times 32 \times 8 \times 128 \times 2 = 131{,}072$ B = **128 KiB**）、每条 judge 输入 300 token + 输出 30 token、H100 SXM bf16 稠密 989 TFLOP/s 与 HBM3 3.35 TB/s。单价用示意值 **0.10 美元/百万输入 token、0.30 美元/百万输出 token**，人审 **3 美元/条**。这些参数是为了复算而设的，不对应任何实测基准。

| 0.72 | 72% | 0.83% | 1,163,000 | 0.97% | 98.21% | 14.5% |
| 0.80 | 80% | 0.75% | 1,016,000 | 0.85% | 97.50% | 11.8% |
| 0.86 | 86% | 0.70% | 917,000 | 0.76% | 96.43% | 9.2% |
| 0.92 | 92% | 0.65% | 827,000 | 0.69% | 93.75% | 5.8% |

（误报率按 $f_1 = 1.2\% \times 0.5/\tau$ 折算：阈值越高，进入灰区的正常内容越少，二级被要求达到的召回就越低（99.00% → 93.75%），但留下的是分类器分数最低的那批违规，**做到那个数字本身更难**——「要求低」与「容易做到」是两件事。）

三个读数：① 阈值从 0.92 降到 0.50，灰区翻一倍，二级需要达到的召回从 93.75% 升到 99.00%，**省下的二级难度换成了灰区规模**；② 灰区里九成以上是正常内容，所以 LLM 层的主要工作是把一级的误报捞回来，而不是抓漏网违规；③ 若二级召回只有 90%，$\tau = 0.62$ 时总漏放率是 $0.38 \times 0.10 = 3.8\%$，远高于 0.5% 目标——**级联的召回是乘出来的，两级都必须按漏放上限反推**。

### token、成本与算力账

| 灰区率 $g$ | judge token/天 | judge 成本/天 | FLOPs/天 | 平均算力 | H100 @35% MFU |
| --- | --- | --- | --- | --- | --- |
| 2% | 7.92 亿 | 94 美元 | 1.11 × 10¹⁹ | 128 TFLOP/s | 0.4 张 |
| 4% | 15.8 亿 | 187 美元 | 2.22 × 10¹⁹ | 257 TFLOP/s | 0.7 张 |
| 10% | 39.6 亿 | 468 美元 | 5.54 × 10¹⁹ | 642 TFLOP/s | 1.9 张 |
| 100%（全量过 LLM） | 396 亿 | 4,680 美元 | 5.54 × 10²⁰ | 6,417 TFLOP/s | 18.5 张 |

算式：每条 judge 成本为 $(300 \times 0.10 + 30 \times 0.30)/10^6 = 3.9 \times 10^{-5}$ 美元；算力按每 token 约 $2P$ FLOPs（前向，忽略 attention 的二次项）得 $2 \times 7\text{e}9 \times 330 = 4.62$ TFLOP/条。

**全量过 LLM 的真实障碍不是 GPU 而是延迟与稳定性**：18.5 张 H100 折算到 8 卡节点只有 2.3 台，钱也不是主要矛盾（4,680 美元/天）。真正否决它的是每一条内容都要等一次百毫秒级的 LLM 判定（prefill 22 ms + 30 token decode 138 ms ≈ 160 ms，见下文「延迟预算」）——同步路径的 p99 会失控，而分类器在 8 ms 内就能给出 95% 的判定。

分类器一侧的账：$1.2\text{e}8 \times 2 \times 4\text{e}8 \times 120 = 1.15 \times 10^{19}$ FLOPs/天，平均 133 TFLOP/s，按 20% MFU 折算约 **0.7 张 H100**——全量前置过滤在算力上几乎免费，成本可以忽略。

### decode 吞吐：内存带宽才是约束

judge 每生成一个 token 都要读一遍全部权重。按 $\text{每步读} = W + b \cdot S \cdot \text{KV}$、$W = 14$ GB（7B bf16）、平均上下文 $S = 165$、KV = 128 KiB/token；一条内容要 30 个 decode 步才生成完，吞吐因此是 $b/(30t)$，不是每秒步数 $b/t$：

| batch | 每步读取量 | 每步耗时（÷3.35 TB/s） | 单条 30 token | 单卡 decode 吞吐（条/s） | 单卡 decode 日处理（条） |
| --- | --- | --- | --- | --- | --- |
| 1 | 14.02 GB | 4.19 ms | 126 ms | 8.0 | 6.9 × 10⁵ |
| 32 | 14.69 GB | 4.39 ms | 132 ms | 243 | 2.1 × 10⁷ |
| 64 | 15.38 GB | 4.59 ms | 138 ms | 465 | 4.0 × 10⁷ |

灰区 138 万条/天（$\tau = 0.62$）按 decode 带宽口径只要 $1.38\text{e}6 / 4.0\text{e}7 \approx 0.03$ 张 H100；按前面「每条 4.62 TFLOP」的算力口径（单卡 35% MFU 下约 75 条/s ≈ $6.5 \times 10^6$ 条/天）是 $1.38\text{e}6 / 6.5\text{e}6 \approx 0.2$ 张——两个口径差一个量级，因为 decode 实际受带宽而不是算力限制。**结论：级联把 LLM 的算力需求压到可以忽略，瓶颈整体移到人审与工程链路。** 反过来说，如果灰区率失控到 20%，judge 成本变成 936 美元/天、需要 3.7 张 H100——依然不是灾难，所以**灰区率的意义主要不在算力，而在它决定了多少人审工位与多少误杀**。

### 人审的账

| 灰区送审比例 | 人审量/天 | 并发工位（120 s/条，16 h 窗口、85% 有效工时） | 成本/天 |
| --- | --- | --- | --- |
| 0.5% | 6,900 | 17 人 | 20,700 美元 |
| 2% | 27,600 | 68 人 | 82,800 美元 |
| 10% | 138,000 | 339 人 | 414,000 美元 |

工位按 $16 \times 3600 \times 0.85 / 120 = 408$ 条/工位/天折算并向上取整。**人审是整条链路里唯一的成本大头**（3,000 美元/千条，而 judge 是 0.04 美元/千条量级）。因此「灰区比例必须控制在多少以内」这个指标的真实含义是「人审预算必须控制在多少以内」：若人审预算上限是 25,000 美元/天，则人审量上限约 8,300 条/天。

### 误报与申诉的量级

$\tau = 0.62$ 时一级误报 $1.194\text{e}8 \times 0.97\% = 115.5$ 万条/天；若二级在误报上的纠错率为 96%，残留误判约 **4.6 万条/天**（占正常内容 0.039%，约每 2,600 条误伤 1 条）；申诉率 1% 对应 1.2 万单/天，5% 对应 5.8 万单/天。这解释了为什么申诉通道必须自动化分诊，也解释了为什么「误报率降一个千分点」比「召回涨一个百分点」更值钱：前者是 $1.194\text{e}8 \times 0.1\% = 11.9$ 万条正常内容，后者只有 $6\text{e}5 \times 1\% = 6{,}000$ 条违规。

### 延迟预算（同步拦截路径）

| 环节 | 耗时 |
| --- | --- |
| 分词与归一化 | 3 ms |
| 分类器 400M（120 token，小 batch 下由启动与调度开销主导） | 8 ms |
| judge prefill（300 token，4.2 TFLOP，≈19% MFU） | 22 ms |
| judge decode（30 token @4.59 ms/步，batch 64） | 138 ms |
| 策略判定与日志 | 5 ms |
| **同步路径合计（judge 内联）** | **176 ms** |
| 只走分类器（灰区改走隔离队列） | 16 ms |

同步路径要压在 100 ms 级，就必须让灰区内容走「先隔离、后放行」：把 138 ms 的 judge decode 挪出用户可感知的路径，用户看到「审核中」而不是等待，LLM 判定完成后放行或拦截。直播间弹幕这类无法隔离的场景只能跑 L0 + L1，命中灰区直接按保守动作处理（屏蔽该条 + 记录）。

### 样本量与区间

| 评测集规模 | 误杀 1.00% 的 95% Wilson 区间 |
| --- | --- |
| n = 2,000 | [0.65%, 1.54%] |
| n = 20,000 | [0.87%, 1.15%] |
| n = 200,000 | [0.96%, 1.04%] |

红线集用「零漏放」口径报数时，$n$ 条全过的 95% 置信上界约为 $3/n$：$n = 300$ 时约 1.0%，$n = 1,500$ 时 0.2%，$n = 3,000$ 时才到 0.1%。要在 95% 置信、80% 检出力下分辨 1.0% 与 1.5% 的漏放率，单组对固定参照比较需约 3,875 条**违规样本**（$n = (z_{1-\alpha/2}+z_{1-\beta})^2\bar p(1-\bar p)/\Delta^2$，$\bar p = 1.25\%$、$\Delta = 0.5\%$）；若两组都是估计值、按两比例检验比较，每组需约 7,750 条（同一组参数代入 $[z_{1-\alpha/2}\sqrt{2\bar p(1-\bar p)} + z_{1-\beta}\sqrt{p_1(1-p_1)+p_2(1-p_2)}]^2/\Delta^2$），两组共 1.55 万条，按违规率 0.5% 折算要累计约 **310 万次请求**——安全指标只能靠红线集与对抗集离线判定，不能靠线上 A/B 兜底。

### 复算代码

```python
ITEMS, VIOL = 120e6, 0.005                     # 日均条目、违规占比
viol, benign = ITEMS * VIOL, ITEMS * (1 - VIOL)
T_CLS, T_IN, T_OUT, P_JUDGE = 120, 300, 30, 7e9
KV7B = 2 * 32 * 8 * 128 * 2                    # 131072 B = 128 KiB/token
H100_TFLOPS, H100_BW = 989e12, 3.35e12

for tau in (0.50, 0.62, 0.72, 0.80, 0.86, 0.92):          # 表 A
    r1, f1 = tau, 0.012 * 0.5 / tau                        # 误报率按阈值折算
    gray = viol * (1 - r1) + benign * f1
    r2 = 1 - 0.005 / (1 - r1)                              # 总漏放 0.5% 反推
    print(f"{tau:.2f} gray={gray:,.0f} g={gray/ITEMS:.2%} r2={r2:.2%} "
          f"viol_share={viol*(1-r1)/gray:.1%}")

per_item = (T_IN * 0.10 + T_OUT * 0.30) / 1e6              # 3.9e-5 美元 / 条
for g in (0.02, 0.04, 0.10, 1.0):                          # 表 B
    items = g * ITEMS
    F = items * 2 * P_JUDGE * (T_IN + T_OUT)
    print(f"g={g:.0%} tokens={items*(T_IN+T_OUT):.3e} usd={items*per_item:,.0f} "
          f"H100={F/86400/(H100_TFLOPS*0.35):.1f}")

W, S = 14e9, 165                                           # 表 C
for b in (1, 32, 64):
    t = (W + b * S * KV7B) / H100_BW
    print(f"batch {b} {t*1e3:.2f} ms/step {b/(30*t):,.0f} items/s {b/(30*t)*86400:.1e} items/day")

for n, k in ((2000, 20), (20000, 200), (200000, 2000)):    # 表 D：Wilson
    p, z = k / n, 1.959963985
    d = 1 + z * z / n
    c = (p + z * z / (2 * n)) / d
    h = z * ((p * (1 - p) / n + z * z / (4 * n * n)) ** 0.5) / d
    print(f"n={n} {p:.2%} CI [{c-h:.2%}, {c+h:.2%}]")
# n=2000 1.00% CI [0.65%, 1.54%] / n=20000 [0.87%, 1.15%] / n=200000 [0.96%, 1.04%]
```

## 常见追问

- **追问**：为什么不能只用 LLM 审核，反正现在 LLM 很便宜？
  - 要点：三个理由。① 延迟与形态：全量过 LLM 意味着每条内容都要等一次百毫秒级的判定（约 160 ms），直播弹幕与私信这类同步场景不可接受，而分类器 8 ms 就能给出 95% 的判定；② 稳定性与确定性：LLM 判定会随 prompt、解码参数与上下文漂移，已知违规（哈希库）与零容忍类目必须由确定性手段兜底；③ 特定类目上分类器更稳——在多语言、隐式毒性这些类目上，微调过的专用分类器（尤其配合领域内数据）往往比通用 LLM 的 zero-shot 判定更可靠、更可校准。成本上全量过 7B judge 只要 4,680 美元/天、18.5 张 H100，所以**否掉它的从来不是钱**。
- **追问**：怎么降低对少数群体的误杀？
  - 要点：四步。① 数据：训练集里把「群体提及」与「毒性」解耦，加入大量「提及群体但完全良性」的对照样本（合成数据是成本最低的来源，见 ToxiGen 的做法）；② 阈值分群：按内容是否涉及受保护群体单独校准阈值，而不是全站一个阈值；③ 评测：把这类样本单列一层，按切片报告误杀率与置信区间（[[safety-09]]）；④ 人工复核：对这类样本的拦截动作默认走「送人审」而不是「自动删除」。
- **追问**：多语言覆盖怎么办？
  - 要点：分类器与 judge 都要按语种单独评测，退化幅度不能从英文集外推（与 tokenizer 在不同文字上的切分差异是同一类问题）。可操作的做法是：先按语种分层建立红线集；低资源语种优先靠 LLM 的 zero-shot 能力 + 多语言 encoder，高资源语种才值得单独微调分类器；语种识别本身要作为路由特征，识别置信度低时直接降级到保守动作。
- **追问**：怎么测二级（LLM）在「一级漏掉的违规」上的召回？这些样本没有标注。
  - 要点：这正是级联评测的难点。可行的做法是分层构造：① 用一级分数最高的一批违规样本（一级抓到的）与一级分数低但人工确认为违规的样本（一级漏掉的）分别建集，后者的规模靠主动学习 + 抽样人工标注累积；② 用红队对抗集补充；③ 用 LLM 自身在灰区上的多次采样一致性作为代理信号，不一致的样本优先送人审，同时回流成标注。任何情况下都要报「这个召回是在多少条标注样本上量的」，否则数字没有意义。
- **追问**：误杀一个正常内容的代价怎么和业务方对齐？
  - 要点：把两个错误翻译成同一种语言。误杀率乘以正常内容量得到「每天有多少条正常内容被误伤」，再乘以单条内容的互动价值与申诉率得到业务成本；漏放率按类目映射到合规、品牌与下架风险。然后按类目分别定阈值：漏放代价高的走低误杀容忍，误杀代价高的走低漏放容忍，中间类目用分级动作而不是拦截。阈值调整要记录理由与生效时间，并且只对后续内容生效。
- **追问**：新出现的黑话与攻击手法让分类器失效，怎么发现？
  - 要点：三个监控信号。① 类目分数分布的位移（同分布的 PSI/KL 之类统计量，方法见 [[rag-07]]）；② 灰区比例与「LLM 推翻分类器」的比例突增——这是分类器失效最灵敏的指示器；③ 用户举报与申诉里出现的新词。三者任一超阈值就触发对抗集扩充与增量微调，而不是等季度重训。

## 公司变体

`asked_at` 只有 **Meta** 一家。Meta 是这道题最自然的出题方：它长期运营超大规模内容审核，并且公开发表过本题两个关键方向的一手材料——Llama Guard 是 Meta 的输入-输出双向 safeguard 模型（安全风险分类法 + 指令微调定制类目与输出格式），本题的参考源之一；而「分类体系 → 标注指南 → 数据质量 → 主动学习 → 鲁棒性」这条链路的方法论骨架出自 OpenAI 的 undesired content detection 系统论文，两家在公开材料上的口径可以互相印证。因此这题在该语境下**工程实现与系统治理的权重明显高于模型原理推导**：更可能被追问的是分层阈值怎么定、灰区比例怎么控、人审队列与申诉闭环怎么设计、多语言与对抗手法怎么持续跟进，而不是某个分类头的数学形式。具体面试流程不在公开信息范围内，这里只描述能力落点。
