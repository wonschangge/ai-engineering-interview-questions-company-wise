## 一句话答案

> 先把「1000 万文档」换算成算力单位：按平均 10 页算是 $P = 10^7 \times 10 = 10^8$ 页，后面所有账都按页算。数据画像决定架构——版式固定的票据走「版面分析 + 模板/规则锚点」，版式多样的走「版面模型 + 字段抽取模型（文本 + 坐标）」，端到端多模态模型只适合版式多变而字段简单的场景，生产系统普遍是「规则兜底 + 模型主判」。
> 流水线切九段、每段幂等且页级可断点续跑（接入去重 → 预处理 → 版面分析 → 文本提取 → 表格结构 → 字段抽取 → 校验对账 → 人审 → 入库），并且**中间产物（文本层、版面框、表格网格）必须持久化**：它只有约 1.6 TB、月成本约 37 美元，却能把一次全量重跑从「重跑全链路约 4.1 万美元」降成「只重跑最后一跳约 2.7 万美元」。
> 账单上最贵的通常不是 GPU 而是人：按 30 秒/页、25 美元/人·时计，**每 1% 的人审率等于 8,333 人·时 = 4.17 人·年 ≈ 20.8 万美元**，比让便宜档模型跑完全部 1 亿页（2.7 万美元）贵 7.7 倍。所以这题的第一预算旋钮是置信度阈值与人审率，而不是模型选型。

## 面试官在考什么

- **会不会换算单位**：「1000 万文档」不是算力单位，「1 亿页」才是。页数决定 OCR 算力、抽取 token 量与存储体量；单位搞错一个数量级，后面所有结论都错。
- **需求澄清的深度**：文档类型与版式分布、扫描质量（DPI、倾斜、印章、手写、双面透印）、**每个字段各自的准确性要求**、时效（T+1 批处理还是小时级）、以及能否调用外部 API（PII 与合规约束）。
- **流水线契约而非模型清单**：九段各自的输入输出、失败语义、幂等键、断点粒度、死信与人工兜底，以及版面/文本/表格这些中间产物要不要落盘。
- **路线判断力**：能不能说清 OCR 依赖方案与无 OCR 端到端方案各自的代价，而不是把论文当成选型结论。
- **成本与人力的账**：单页成本 × 1 亿页、重跑成本、以及「人审率每提高一个千分点要多少人力」这条链是否算得出来。
- **可核对与可复现**：结构化字段能否回指到原图坐标、每份结果能否说清用了哪个模型与规则版本、模型升级后能否只重算受影响的部分。

常见错误答案：

- 一上来就说「用多模态大模型端到端抽」，不谈页数、字段分级、置信度校准与人审预算。端到端模型让字段级指标与阈值失去抓手，在 1 亿页规模上也很难摊薄成本与保证可复现。
- 只报一个「整页准确率 99%」就收工。1 亿页的 1% 是 100 万页错误；而金额字段错一位就是事故——整页相似度与字段级严格正确率之间没有可比性。

## 原理与推导

### 1. 需求澄清与假设：把「1000 万文档」问成「1 亿页 + 一张字段分级表」

先问六个问题，答案直接决定技术选型：

1. **文档类型与版式分布**：发票、合同、表单、报告各占多少？有多少种模板？长尾版式的占比决定要不要上通用版面模型。
2. **页数**：1000 万文档 × 平均 10 页 = 1 亿页。这是 OCR 算力、抽取 token 与存储的唯一计价单位；平均页数每差 1 页，全量成本就差 10%。
3. **扫描质量**：DPI、倾斜角、印章遮挡比例、手写比例、双面透印比例。低于 200 DPI 或倾斜超过 5° 的页面应当在预处理阶段就被识别出来，而不是让下游模型硬扛。
4. **字段清单与字段级准确性要求**：这是本题最重要的澄清项，见下表。
5. **时效**：T+1 批处理与小时级是两套架构。批处理可以把 1 亿页压进夜间的抢占式实例，小时级则要常驻容量。
6. **部署与合规约束**：合同与发票含 PII，若不允许出境或必须部署在隔离环境，外部 API 与自托管两套算账都要给。

| 字段类 | 例子 | 准确性口径 | 错误后果 | 自动化策略 |
| --- | --- | --- | --- | --- |
| 红线字段 | 金额、税额、账号、日期、PO 号 | 逐字符严格正确率 ≥ 99.9% | 付款/对账事故 | 严格格式校验 + 跨字段等式 + 与业务系统对账 + 低置信必审 |
| 普通字段 | 供应商名、地址、条款编号 | ≥ 98%，允许归一化后匹配 | 检索与统计偏差 | 归一化 + 主数据模糊匹配，匹配失败降置信 |
| 自由文本 | 备注、摘要、条款正文 | CER 口径，不设硬门禁 | 影响体验 | 只做长度与敏感词校验，不进人审 |

### 2. 架构与数据流：九段流水线与每段契约

**工作单元是页，不是文档。** 一个 10 页文档在第 9 页失败时不能重跑前 8 页；页级工作单元也让并行度与失败重试都简单一个数量级。每页在状态机里走 `pending → normalized → laid_out → text_ready → extracted → validated → (auto_ok | escalated | queued_for_review) → committed`，每个状态转换都以幂等键 `(doc_id, page_no, stage, model_version, config_hash)` 落一条结果记录。

```text
① 接入去重    PDF 字节哈希 + 内容哈希 + 页级感知哈希；格式按 magic bytes 判定，不看扩展名
② 预处理      旋转/倾斜校正、去噪、灰度化、300 DPI 归一、拆成单页
③ 版面分析    标题/段落/表格/图片/页眉页脚区域 + 阅读顺序
④ 文本提取    有文本层直接抽（近乎免费）；真扫描页走 OCR
⑤ 表格结构    单元格网格 + 表头归属 + 跨页续表标记
⑥ 字段抽取    版面 + 文本 → 目标 schema，字段级置信度
⑦ 校验与对账  格式规则、跨字段等式、与业务系统（PO/供应商主数据）对账
⑧ 人工复核    只处理低置信或红线字段校验失败的样本，结果回流为标注
⑨ 存储与索引  结构化字段 + 原文 + 坐标引用入库，供检索与下游消费
```

| 段 | 输入 → 输出 | 主失败模式 | 处理 |
| --- | --- | --- | --- |
| ① 接入去重 | 对象存储事件 → 规范化的文档记录 | 加密 PDF、损坏文件、重复投递 | 空密码尝试解密；损坏进死信队列并回执上游；重复按幂等键去重 |
| ② 预处理 | 原始 PDF → 单页位图 + 质量元数据 | 倾斜、低 DPI、装订阴影 | 质量分低于阈值直接标记 `needs_rescan`，不进模型 |
| ③ 版面分析 | 单页位图 → 区域框 + 阅读顺序 | 多栏、页眉页脚混入正文 | 按区域类型过滤页眉页脚；跨栏顺序用版面模型的 reading order 输出 |
| ④ 文本提取 | 单页位图/文本层 → 词 + 坐标 + 字级置信度 | OCR 错字、印章遮挡 | 字级置信度向下传递；低置信词在抽取阶段约束候选 |
| ⑤ 表格结构 | 表格区域 → 单元格网格 | 无线框表、合并单元格、跨页 | 结构置信度低时保留原始区域图并降级为「附原图」 |
| ⑥ 字段抽取 | 文本 + 布局 → 字段值 + 置信度 | 版式长尾、字段缺失 | 输出 schema 校验失败的字段置空而不是猜 |
| ⑦ 校验对账 | 字段集合 → 通过/降置信/拒绝 | 明细与总额不等、主数据不匹配 | 等式失败一律降置信，不自动改写数值 |
| ⑧ 人工复核 | 低置信样本 → 修正后的字段 | 队列积压 | 按字段红线优先级排序；设队列水位告警 |
| ⑨ 存储与索引 | 结构化结果 → 检索与消费接口 | 版本漂移 | 每条结果带模型/规则版本，支持按版本重算 |

### 3. 路线选择：OCR 依赖、无 OCR、模板规则的三角

**OCR 依赖方案的问题在论文里已被明确列出。** Donut 的出发点是：依赖现成 OCR 的文档理解方案有三个固有问题——**使用 OCR 的计算开销大**、**OCR 模型对语言与文档类型不灵活**、**OCR 错误会传播到后续环节**；该工作因此提出无 OCR 的端到端 Transformer，并用合成数据生成器支持多语言与多领域预训练，论文自述在多项文档理解任务上速度与精度都达到当时最好水平（这是论文口径，具体榜单随时间变化）。

另一条主流路线是**统一的多模态预训练**。LayoutLMv3 用统一的文本与图像掩码目标，加上一个词-块对齐（word-patch alignment）目标（预测某个文本词对应的图像块是否被掩码）来学跨模态对齐，论文报告同一个通用模型在文本中心任务（表单理解、票据理解、文档 VQA）与图像中心任务（文档图像分类、版面分析）上都达到当时最好水平。

把两者落到工程判断上，选型是三分的：

- **字段级准确率要求高 + 版式固定** → 模板锚点 + 规则提取优先。规则可解释、可回归测试、单页成本近零；模型只用来兜住模板匹配失败的页面。
- **版式多样** → 版面模型 + 抽取模型，抽取模型的输入是 OCR 文本与坐标（文本中心路线），因为字段级置信度、坐标回指与阈值校准在这一路线上最好做。
- **版式多变、字段简单、且需要整页语义** → 端到端模型（无 OCR 路线），代价是字段级校准与可追溯性更难。

生产系统几乎总是组合：**规则兜底 + 模型主判**。规则负责红线字段的格式与等式（金额、日期、税号），模型负责把自由版式映射到字段，二者冲突时降置信并进人审。

### 4. 版面与表格：两个有大规模公开数据支撑的子任务

版面分析不是自研难题，它是有公开大规模数据集的成熟子任务。PubLayNet 把 PubMed Central 上 100 万篇以上公开 PDF 文章的 XML 表示与内容自动对齐，产出 36 万余张带版面元素标注的文档图像，规模与主流视觉数据集同级；论文还报告在它上面预训练的模型迁移到其它文档领域时是更好的底座（论文摘要口径）。

表格结构同理。PubTables-1M 收录科学文章中近百万张表格，支持多种输入模态，包含表头与位置信息；论文特别指出此前数据集存在 **oversegmentation（过分割）** 这一 ground truth 不一致来源，并用一套规范化（canonicalization）流程处理它，规范化后训练效果与评测可靠性都提升（论文摘要口径）。这条经验直接可用：**同一张表在标注上可能有多种合法切分，若不先定义「唯一的正确答案」，模型学到的与评测测到的就不是同一件事**——自己的表格标注规范必须先写清楚合并单元格与无框线的处理规则。

两个工程取舍：

- **阅读顺序比区域检测更容易错**。多栏正文、脚注、页眉页脚、跨栏表格都会让顺序错乱，而顺序错误会让字段抽取把相邻记录的数值串到一起。做法是版面模型直接输出 reading order，并用「同一行的文本块按 x 排序、跨栏按栏序」作为一致性校验；跨页合并只在明确的续表标记（如「续表」「Continued」）下启用。
- **分辨率是一维成本杠杆**。像素数按 DPI 的平方增长：从 300 DPI 提到 400 DPI，像素数与推理成本都变成 $(400/300)^2 = 1.78$ 倍。小字号与印章细节确实需要更高分辨率，但正确做法是**只对判定为「文字过小」或低置信的区域做高分辨率二次裁剪**，而不是全量提 DPI。

### 5. 字段抽取与置信度：人审率才是第一预算旋钮

**schema 声明式**：字段名、类型、是否必需、格式约束、是否红线、归一化规则、对账来源写在一份配置文件里。抽取阶段只负责产出「值 + 置信度」，业务校验与归一化不混进模型。

**字段级置信度**由三路合成，而不是单一 softmax 概率：

$$c_{\text{field}} = \min\big(c_{\text{ocr}},\, c_{\text{model}},\, c_{\text{rule}}\big)$$

其中 $c_{\text{ocr}}$ 是该字段覆盖字符的字级置信度最小值（OCR 错一个字，字段就错），$c_{\text{model}}$ 是抽取模型的字段级概率，$c_{\text{rule}}$ 是格式与等式校验的通过标志（不通过直接置 0.1 级别的低分）。取最小值而不是乘积或平均，是因为三路各自都有「一票否决」的性质。

**阈值要由目标人审率反解**，而不是反过来。设全量错误率 $p$、目标残余错误率 $p^\star$、人审对错误的拦截率 $q$，则 $p^\star = p(1-q)$，于是 $q^\star = 1 - p^\star / p$。例如 $p = 2\%$、$p^\star = 0.5\%$ 时要求拦截 75% 的错误，阈值就定在「错误样本置信度分布」的 75 分位上——阈值高低是校准问题，不是拍脑袋问题。校准与门禁都依赖同一个前提：**一份人工标注的金标准集**，它是阈值、置信度校准与回归门禁的唯一真相来源，金额类字段在它上面零容忍，构造方法与专家成本见 [[evaluation-02]]。文档结构理解本身有多难也有公开口径：DocVQA 的 5 万问题、1.2 万余张文档图像上人类准确率 94.36%，论文指出当时的模型差距最大之处正是**需要理解文档结构**的问题——这就是字段级、分模板指标不能省的理由。

**升级比人审便宜约 36 倍**：低置信页送去更贵模型重跑是 0.00585 美元/页，送人审是 0.2083 美元/页（30 秒/页、25 美元/人·时）。所以正确顺序是「便宜模型全量 → 低置信升级到强模型 → 仍然低置信或红线字段冲突才人审」。这也解释了为什么同一条流水线里同时要有三档：**每提升一档，单价涨一个数量级上下，人力档最贵**。三档之间的路由、配额、失败转移与预算上限本身是一个 gateway 问题，做法与口径见 [[system-design-09]]。

### 6. 失败模式与取舍

| 失败模式 | 触发条件 | 影响 | 对策 |
| --- | --- | --- | --- |
| OCR 错误传播 | 低质量扫描、异体字、印章遮挡 | 字段值错，且错误原因难以定位 | 字级置信度全程传递；红线字段做双引擎交叉校验（两路结果不一致即降置信） |
| 表格过分割 | 标注规范未定义合并单元格 | 训练目标与评测口径不一致，指标虚高 | 先写规范化规范再标注；评测用单元格级匹配，不用整表文本相似度 |
| 阅读顺序错误 | 多栏、跨栏表格、页脚 | 相邻记录数值串行 | 版面模型输出 reading order + 一致性校验；不做无依据的跨页合并 |
| 印章/手写 | 印章覆盖金额、手写批注 | 遮挡区字符丢失 | 按区域分流：手写字段单独模型；印章区域掩码后重识，仍失败则人审 |
| 加密/损坏文件 | 有 owner password、传输截断 | 整批卡住 | 接入段前置校验，失败进死信队列，不阻塞同批其它文档 |
| 长尾版式 | 模板库外的版式 | 该模板下字段准确率骤降 | 按模板分桶报告指标；低置信样本回流做主动学习，模板上线走门禁 |
| 模型/规则版本漂移 | 升级抽取模型或改规则 | 同一字段跨批次口径不一致 | 每条结果记录版本三元组；新版本先在金标准集上过门禁再灰度 |

关键取舍：**覆盖率与准确率不可同时最大化**。把「字段缺失」也当成错误会逼模型去猜，而猜出来的金额比空值危险得多——红线字段的正确行为是「不确定就置空 + 进人审」。

### 7. 幂等、版本化、审计与隐私

- **幂等与断点续跑**：每段以 `(doc_id, page_no, stage, model_version, config_hash)` 为键写入结果与输出哈希；重跑时命中已有结果直接跳过。断点粒度是页，不是文档；批处理任务被抢占后能从任意页恢复。
- **中间产物持久化**：文本层、版面框、表格网格落对象存储（约 1.6 TB，月成本约 37 美元）。这是整个架构里性价比最高的一笔存储——没有它，模型升级就要重跑 1 亿页的 OCR；有它，只需重跑最后一跳。
- **版本化**：每份文档记录 `(ocr_version, layout_version, extract_version, rule_version, config_hash)`，并让指标按版本分组。否则「这周的准确率」是多个版本混合出来的数，无法归因。
- **审计与可追溯**：每个字段值都存 `(page_no, bbox)`，可以从结果一键跳到原图对应位置。这与把答案归因到具体 span 是同一类要求（见 [[rag-12]]）；区别是这里的「span」是图像坐标而不是文本区间。
- **隐私**：合同与发票含 PII，需要传输与静态加密、按角色收敛访问、以及对「谁看过原始图像」的审计日志；日志与训练数据里的 PII 处理沿用 [[safety-07]] 的口径。人审按最小权限投递：只把待复核字段的裁剪图与坐标推给审核员，而不是整份文档；保留期与删除请求要能连带清掉原图、中间产物与检索索引，否则「删了原文、向量还在」就是合规漏洞。若不允许调用外部 API，成本模型要整体换成自托管版本（表 2）。

### 8. 下游接口

结构化字段与原文一起入库：字段值进关系表供对账与统计，页级文本 + 坐标进检索索引供问答与检索（见 [[rag-10]] 对表格与多栏 PDF 的处理、[[multimodal-10]] 的多模态索引），权限按源文档继承（见 [[system-design-01]]）。增量刷新沿用 [[rag-11]] 的思路：新文档走同一条流水线，重算只针对版本变更影响到的段。

## 数值与代码验证

统一口径：总页数 $P = 10^7 \times 10 = 10^8$；GPU 取 H100 SXM5（bf16 稠密 989 TFLOPs、HBM3 3.35 TB/s，与本仓库其它专题一致），单价 2.5 美元/GPU·小时；对象存储 0.023 美元/GB·月；1 TB 按 $10^{12}$ B 计，内存量按 1024 进制。抽取阶段的模型单价（便宜档 0.15/0.60 美元每百万输入/输出 token，前沿档 3/15 美元）与表 2 的每页 1,200/150 token 都是**示意价与示意假设**，只是算例，不代表任何厂商当前定价，也不代表真实的 token 分布。人审按 30 秒/页、25 美元/人·时、2,000 人·时/人·年。存储表中各行成本按显示精度取整，合计与年化按未取整值计算。

**表 1：OCR + 版面 + 表格结构阶段（1 亿页）**

| 单卡吞吐 | 卡·时 | 一个 8 小时窗口（80% 利用率）需要的卡 | 成本 | 每页 | 每文档（10 页） |
| --- | --- | --- | --- | --- | --- |
| 1 页/s | 27,778 | 4,340 | 69,444 美元 | 0.000694 美元 | 0.00694 美元 |

这张表的读法比数字本身重要：**成本只由卡·时决定，与并行度无关**。同样的 1 亿页，5 页/s/卡 时可以是「8 卡跑一个月（24/7）」也可以是「868 卡跑一个晚上」，卡·时都是 5,556，差别只在墙钟时间与抢占式折扣。回填是一次性项目，所以选并行度的依据是「交付日期 + 能拿到多少抢占式容量」，而不是「哪种更便宜」。

纯算力的下界远低于此：按 ResNet-50 在 224² 输入的公开报数口径（约 4.1 GFLOPs，按 MAC 计则减半）等比放大到 1024² 是 20.9 倍，检测约 129 GFLOPs、版面约 86 GFLOPs、识别约 100 GFLOPs，合计约 0.38 TFLOPs/页（含 20% 余量），1 亿页即 $3.8\times10^{19}$ FLOPs，在 40% MFU 下只要 **26.5 卡·时**。真实吞吐与这个下界差 52–1,048 倍（表 1 的四档），瓶颈在小 batch、多模型串行、CPU 前后处理与 I/O——**roofline 只能当下界，容量规划必须用实测吞吐**。

**表 2：字段抽取阶段（1 亿页，每页 1,200 输入 token + 150 输出 token）**

| 路线 | 输入/输出 token | 成本 | 每页 |
| --- | --- | --- | --- |
| 便宜档 API（示意价 0.15/0.60） | 1,200 亿 / 150 亿 | 27,000 美元 | 0.00027 美元 |
| 前沿档 API（示意价 3/15） | 同上 | 585,000 美元 | 0.00585 美元 |
| 自建 70B（8×H100，MFU 40%，batch 316.5，即 $B^\star = W/k$） | 同上 | 32,242 美元（12,897 卡·时） | 0.00032 美元 |

自建 70B 的口径：prefill 为 $2NT = 2 \times 7\times10^{10} \times 1200 = 1.68\times10^{14}$ FLOPs，8 卡 40% MFU 下 53.1 ms；decode 按「每步读权重与 KV」的 roofline 计，权重 130.4 GiB、每序列 KV 0.412 GiB，权重读与 KV 读平衡的 batch 是 $B^\star = W/k = 316.5$，此时每页 decode 约 5.0 ms，合计 58.0 ms/页。两个结论：**自建 70B 与便宜档 API 同一量级（约为其 1.2 倍），比前沿档便宜 18 倍**；**prefill 占自建成本的 91%**，所以降本手段是缩短输入（只送与字段相关的区域，1,200 → 600 token 后 58.0 ms/页 降到 29.3 ms/页，省约一半）与换更小模型，而不是继续加大 batch。

反例：若把预处理后的无损灰度位图也留下，1 亿页 × 8.7 MB（300 DPI、8 bit）就多出 **870 TB**，单副本月成本约 2.0 万美元，直接让方案出局。中间位图必须用有损格式、或只对失败页保留并设短保留期。

**重跑的成本差**：中间产物落盘后只重跑字段抽取，1 亿页 2.7 万美元（便宜档）；若必须全链路重跑，还要再加 OCR/版面/表格的 5,556 卡·时（按 5 页/s/卡 即 13,889 美元），合计 40,889 美元。中间产物单副本约 1.6 TB 的月成本只有约 37 美元，却把一次全量重跑省下约 1.4 万美元——这个比值决定了「中间产物必须持久化」不是优化项而是设计前提；同一笔账也解释了增量重算：新版本只对受影响的字段与模板重跑，而不是全量。

**金标准集要多大**：3,000 页 × 双人标注 × 10 分钟/页 = 1,000 人·时（约 2.5 万美元），是一次性投入。按 rule of three，3,000 页零错误只能声称「错误率不高于 $3/3000 = 0.1\%$」；若要把这个基线估到 ±0.2 个百分点（95% 置信），二项样本量公式要求约 4,800 页，两个版本之间的比较还要按两样本公式再放大——**金标准集的规模由「要证伪多小的差异」决定，不由预算决定**。

复算代码（`python3 .work/sd06-calc.py`）：

```python
P = 10_000_000 * 10                                  # 1e8 页
H100, MFU = 989e12, 0.40                             # bf16 TFLOPs / MFU
for r in (1, 5, 10, 20):                             # 每卡页/s
    gh = P / (r * 3600)
    print(r, f"{gh:,.0f} 卡·时", f"{gh/(8*0.8):,.0f} 卡(8h窗口)", f"{gh*2.5:,.0f} 美元")
IN_T, OUT_T = 1200, 150                              # token/页
Tin, Tout = P * IN_T, P * OUT_T                      # 1.2e11 / 1.5e10
for pin, pout in ((0.15, 0.60), (3.0, 15.0)):        # 便宜档 / 前沿档示意价
    print(f"{Tin/1e6*pin + Tout/1e6*pout:,.0f} 美元")
for rr in (0.001, 0.005, 0.01):                      # 人审率：30 s/页、25 美元/人·时
    h = rr * P * 30 / 3600
    print(f"{rr:.1%}", f"{h:,.0f} 人·时", f"{h/2000:.2f} 人·年", f"{h*25:,.0f} 美元")
W, G, KV = 70e9 * 2 / 1024**3, 8, 320 * 1024         # GiB / 卡数 / B per token
k = (IN_T + OUT_T) * KV / 1024**3                    # 每序列 KV，GiB
B = W / k                                            # 权重读与 KV 读平衡：316.5
pre = 2 * 70e9 * IN_T / (G * H100 * MFU)             # prefill，s
dec = OUT_T * (W / G + B * k / G) * 1024**3 / 3.35e12 / B   # decode，s
print(f"{pre*1000:.1f} + {dec*1000:.1f} ms/页 -> {(pre+dec)*P*G/3600:,.0f} 卡·时")
print(3 / 3000)                                      # rule of three -> 0.1% 上界
```

## 常见追问

- **追问**：为什么不直接用多模态大模型端到端抽取，省掉整条流水线？
  - 要点：四个理由。① **成本**：前沿档单价是便宜档的 21.7 倍，1 亿页差 55.8 万美元；② **可复现与可校准**：端到端输出的字段级置信度要靠 prompting 或多次采样来近似，阈值难以稳定；③ **吞吐与显存**：整页图像进模型，视觉 token 数远高于等价的文本 token，单卡吞吐低一个量级，1 亿页的回填窗口难以满足；④ **可追溯**：字段值没有显式的坐标来源，审计要求「跳回原图对应位置」时给不出证据。合理用法是让它处理「版式多变 + 字段语义复杂 + 量小」的少数文档，而不是承担 1 亿页的基座。
- **追问**：手写与印章怎么处理？
  - 要点：先分流再建模，不要指望一个模型通吃。① 用页面级分类器分出「印刷为主 / 手写占比高 / 印章覆盖关键字段」三类；② 手写字段单独走手写识别模型（印刷体模型在手写上的退化成倍），并直接抬高该字段的人审权重；③ 印章覆盖的区域做掩码 + 邻域重建，仍失败就保留原图截图交人审；④ 金额类字段只要印章覆盖比例超过阈值，一律强审，不做「猜一个」的尝试。
- **追问**：模板变更或新增模板，怎么快速适配？
  - 要点：把「模板」做成数据而不是代码。① 模板定义为一份锚点 + 区域 + 字段映射的配置，加模板不改模型；② 抽取模型始终保留一个不依赖模板的通用路径作为兜底，新模板上线时先走通用路径并收集低置信样本；③ 用金标准集按模板分桶跑门禁，新模板必须在该桶上达标才能切流量；④ 模板变更要有版本号，否则「同一模板下指标变差」无法归因。
- **追问**：模型升级后怎么重跑 1 亿页？回填与稳态要不要两套系统？
  - 要点：一套系统、两种调度。① 中间产物落盘让重跑只覆盖受影响的段（从 4.1 万美元降到 2.7 万美元）；② 按 `extract_version` 做增量标记，重算任务优先级低于在线增量；③ 回填用可抢占的批处理队列，稳态用常驻小集群（按每月新增 100 万文档算，24/7 下 5 页/s/卡 只需约 1 张卡，8 小时窗口内约 3 张）；④ 两者共用同一套幂等键与结果表，避免「回填结果」与「增量结果」两份真相。
- **追问**：如果实际平均页数是 30 页而不是 10 页呢？
  - 要点：把所有账乘以 3，并检查哪一项先破。OCR 从 5,556 卡·时变成 16,668 卡·时（8 小时窗口 868 卡 → 2,604 卡，可能超出可抢占容量）；抽取从 2.7 万美元变成 8.1 万美元；存储从 32.4 TB 变成 97 TB（单副本）。**先破的通常是「可抢占容量」与「人审人力」而不是钱**，所以架构上要保证三件事可独立伸缩：批处理并行度、升级档的配额、人审队列的外包能力。
- **追问**：怎么决定哪些页面根本不值得进流水线？
  - 要点：在预处理后加一道「价值门」。① 空白页、纯图片页、重复的条款附页直接标记为 `skip`（页级感知哈希命中即跳过）；② 与被抽取字段无关的页（例如只要首页发票信息，附件页 20 页）按模板声明裁剪；③ 质量分过低的页面直接判 `needs_rescan`，不让下游模型消耗算力去猜。这道门省下的是「页数 × 单页成本」中最容易省的那部分，且它是唯一不损失红线字段准确率的省钱手段。
