## 一句话答案

> 会议助手要做成**两条链路**而不是一条：会中链路只出低延迟字幕与实时提示，不上终稿；会后链路做转写终稿、diarisation、角色归属、分章、分层摘要与行动项抽取，可以批量、可以单段重跑。
> 架构上最值钱的判断是**尽量拿到每位参会者的独立音轨**：有独立音轨时说话人归属退化成信道归属，重叠语音这个最难的问题直接消失，拿不到才回落到 VAD + 说话人嵌入 + 聚类或 EEND。
> 可信度由两件事决定——每条行动项都能回溯到带时间戳的原文，以及录音同意与权限继承在管线层面兜住，而不是在 UI 上提示一句。

## 面试官在考什么

- **会不会先澄清形态**：会中（字幕、实时提示）与会后（纪要、行动项）的延迟预算与架构完全不同；不澄清就直接画框图，后面的取舍全是白干。
- **音频链路能不能分段讲**：采集、VAD、ASR、diarisation、角色归属、时间戳对齐各有各的技术选择与失败模式，压缩成「先转写再理解」就没有信息量。
- **有没有「独立音轨」这个判断**：这是本题少有的、一句话把难度降一个量级的设计决策，也是区分「做过语音系统」与「只写过 prompt」的地方。
- **「不失真」的机制设计**：分章与分层摘要、行动项的证据链、决议与讨论分栏、低置信兜底——考的是可信度与治理，不是 prompt 技巧（[[evaluation-03]]）。
- **算账与合规**：ASR 与会后 LLM 的算力量级、幂等去重、权限继承、录音同意与声纹边界，缺一项这题就不完整（[[safety-07]]）。

**常见错误答案**：把题目简化成「ASR + 一个长 prompt 出纪要」，不区分会中与会后；或者只谈摘要质量，完全不提同意、权限、幂等与删除联动——会议内容是企业里最敏感的数据之一，跳过这几项等于没设计。

## 原理与推导

### 1. 需求澄清与假设

| 待澄清 | 本设计的默认取值 | 不澄清会怎样 |
| --- | --- | --- |
| 会中还是会后 | 两条链路：会中只出字幕与提示，会后出终稿 | 一套链路时，要么实时性不达标，要么终稿质量被流式约束拖死 |
| 采集形态 | 优先每人独立音轨（客户端上行 / SIP 分轨 / SFU 转发），回落到单路混音 | 决定了 diarisation 是「信道归属」还是「重叠语音分离」 |
| 人数与语言 | 2–20 人；中英为主，允许 code-switching；维护领域词表与热词 | 语言与口音决定 ASR 选型与热词策略（[[multimodal-07]]） |
| 输出物 | 纪要、决议、行动项（谁 / 做什么 / 何时 / 原文时间戳）、未决问题、章节索引、可搜索转写 | 输出物清单决定 schema；事后加字段等于全量重跑 |
| 集成目标 | 日历（入会与参会人名单）、IM（推送）、任务系统（建任务并指派）、CRM（客户会议）、企业检索 | 没有集成，纪要就是死文档 |
| 合规 | 录音同意显式取得且可撤回；音频默认留存 90 天、文本按组织策略；可见性等于参会人集合 | 未取得同意就录制是产品级事故（[[safety-07]]） |
| 规模 | 1 万员工、每工作日 2.5 场/人、平均 45 min；峰值 1,200 场并发 | 决定会中并发与会后批处理的容量配比 |

### 2. 数据流：一条线，两个阶段

1. **会议对象**：日历事件创建时生成 `meeting_id`，带上组织者、参会人名单、同意状态；同意是**前置门**，状态不是「已取得」就不进管线，不落盘、不处理。
2. **会中**：各路音轨 → VAD 门控 → 流式 ASR → 字幕（带临时说话人标签）→ 可选的实时提示；所有输出都是**可覆盖的临时状态**。
3. **会后**：音轨归档 → 批量 ASR 终稿 → diarisation 终稿与角色归属 → 话题分章 → 分层摘要与行动项抽取（结构化输出）→ 人工确认门 → 写回 IM / 任务 / CRM → 入库并继承权限。
4. **反馈回路**：用户的编辑（改错字、删行动项、改指派人）是评测与微调的标注来源，也是「纪要质量够不够」的直接信号。

### 3. 会中链路：延迟预算与「不上终稿」

字幕的总延迟是六段之和，口径与 [[multimodal-03]] 的六段拆解同源（滚动出字只需要起点确认，不需要等语义结束判定）：

| 段 | 口径 | 延迟 |
| --- | --- | --- |
| 采集分帧 | 20 ms 帧 + 设备缓冲 | 25 ms |
| 上行网络 | 同城往返的一半 | 40 ms |
| 网关 jitter buffer | 按抖动分布 $p_{95}$ | 35 ms |
| VAD 起点确认 | 连续 3 帧（10 ms 帧移）命中 | 30 ms |
| 流式 ASR 稳定前缀 | 声学右文 120–200 ms 后出字 | 160 ms |
| 渲染与下发 | 服务端到客户端 | 60 ms |
| 合计 | | **350 ms** |

句子「翻正」（用静音窗确认端点后把临时结果替换成 final）要再加 240 ms 静音窗与 200 ms final 解码，约 440 ms 之后；实时提示若要在同一链路上再跑一次小模型，首 token 再加 300 ms 左右（$350 + 440 + 300 = 1{,}090$ ms），整体落在 0.8–1.1 s，用户仍可接受。

结论是**会中链路不做终稿**：流式 diarisation 只有因果上下文，精度天然低于看完整录音的离线版本（[[multimodal-09]]），角色归属更需要参会人名单与全文内容线索。让会中只吐临时标签、会后跑一遍离线 pass 覆盖，是唯一能同时满足实时性与准确率的做法。

### 4. 会后链路：音频五段与一个关键判断

① **采集与声道**。独立音轨是本题的核心判断：会议平台按参会人分轨（客户端各路上行、SIP 分轨、SFU 转发）时，「谁在说」由信道直接给出，重叠语音不再需要盲分离，diarisation 的难度从研究问题降成工程问题。代价是每路 32 kbps 的额外上行（相对视频可忽略）与集成面变大——收益远大于代价。拿不到独立音轨（外部电话桥接、会议室单麦）时才回落到单路混音方案。

② **VAD 与切分**。10 ms 帧移、连续 3 帧命中确认起点，避免把键盘声与咳嗽送进 ASR；切分点要保留带重叠的窗口，否则会在边界切断话轮、制造假的说话人切换。

③ **ASR**。批量与流式分开：流式只服务 UI 预览，终稿用批量模型加双向上下文重跑一遍（专名、缩写、数字的准确率差距明显）。领域词表与热词（产品名、人名、缩写）是性价比最高的一步；多语言与 code-switching 要按语言分别记 WER，不然平均分会掩盖单语种的灾难（[[multimodal-07]]）。

④ **diarisation 与角色归属**。两条路线的定性结论可以直接引用：聚类式路线有两个结构性问题——**它不是直接优化 diarisation 误差**，且**无法正确处理说话人重叠**（Fujita 等在 EEND 论文摘要里的原话口径）；端到端神经 diarisation 用自注意力直接输出每帧的说话人活动，重叠天然是多列同时激活，论文报告它显著优于基于 BLSTM 的 EEND，也优于当时基于 x-vector 聚类的 SOTA。工程落地更常用模块化工具链：pyannote.audio 把 VAD、说话人变化检测、重叠语音检测、说话人嵌入都做成可训练模块，可组合并联合优化，并提供覆盖多个领域的预训练模型（论文称其中多数达到当时的 SOTA）。**角色归属是独立一步**：把 `SPEAKER_00/01` 映射到「主持人 / 客户 / 记录人」要靠日历参会人名单、发言与提问模式、内容线索三路信号，低置信输出 `unknown` 而不是硬猜（[[multimodal-09]]）。

⑤ **时间戳对齐**。字幕、章节、证据定位都依赖它：段级边界要收敛到几十毫秒，做法是词级强制对齐后回填，漂移几百毫秒就会让「行动项 → 原文」的跳转落到错句上。

### 5. 摘要与行动项：四道「不失真」防线

**第一道是分章 + 分层。** 两小时的会不是一次摘要任务：先按话题切分（嵌入漂移 + 语言模型的边界判定）得到章节，再逐章出摘要（每章约 $10^3$ token），最后用各章摘要合成全局纪要与行动项。这样单次请求的输入从 $2\times10^4$ 量级降到 $10^3$ 量级，长上下文的「中间丢失」不会吃掉后半场会议，失败时也只需重跑一章（[[llm-internals-13]]）。MeetingBank 的 divide-and-conquer 标注思路正是同一个方向的证据：把专业撰写的会议纪要拆成短段落并与会议的具体片段对齐，把长会议摘要分解成更小、更可管理的任务（ACL 2023）。

**第二道是 query-based 摘要。** 没有单一短摘要能覆盖多人多话题的长会议，用户真正要的是「就某个问题把相关片段找出来并总结」。QMSum 把这件事定义成新任务并给出基准：**232 场会议、1,808 个查询-摘要对**，跨多个领域；论文同时考察了 locate-then-summarize 方法，并说明人工分析显示长会议摘要对模型仍是显著挑战（NAACL 2021）。产品侧对应「这场会关于预算讨论了什么」这类追问，实现是检索 + 抽取式定位 + 生成式总结。

**第三道是行动项的证据链。** 每条行动项输出四个字段：谁、做什么、何时、**原文出处的时间戳区间**。第四项是「可核对」的全部意义——用户点一下能跳回原话，就能自己判断这条是系统理解错了还是当时确实这么说（[[rag-12]]）。同时要求**指派人必须来自参会人名单**（做白名单校验，不允许多出一个名单外的人名），日期与金额用规则复核。

**第四道是决议与讨论分栏。** 决议只从「主持人明确表态 + 决定动词 + 无后续反悔」的段落抽取，其余全部进「未决问题」；模型必须在结构上区分二者，而不是在自由文本里混着写。低置信时输出 `unknown` 并进人工确认队列（[[agents-11]]）。结构化输出用 schema 约束（谁、做什么、何时、证据、置信度），不要解析自由文本（[[agents-03]]）。

### 6. 集成、权限与幂等

- **日历**：会议对象与参会人名单的权威来源，也是角色归属的先验；会议改期要能取消已排队任务。
- **IM**：会后推送纪要摘要与行动项卡片；推送是**可撤销**的通知，不是数据源。
- **任务系统与 CRM**：行动项建成任务并指派，客户会议再写回客户档案；写外部系统必须幂等，幂等键取 `(meeting_id, 行动项指纹, pipeline_version)`，其中指纹是「指派人 + 动作 + 到期日」的归一化哈希，重试、重放与人工重跑都不能重复建任务，CRM 侧还要做字段映射与权限二次校验（[[agents-02]]）。
- **检索**：转写与纪要入库，权限继承参会人集合，并随会议删除或留存期到期做索引删除（[[rag-08]]、[[rag-11]]）；索引结构与企业级检索同构（[[system-design-01]]）。
- **幂等与版本**：一次会议的处理结果带 `pipeline_version`；换模型重跑时，行动项按指纹 diff，新增的建、消失的标 `superseded` 而不是物理删除——审计需要知道「当时系统说过什么」。

### 7. 失败模式与取舍

| 失败模式 | 触发条件 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 说话人混淆 | 无独立音轨 + 重叠说话 | 纪要整段归因反转 | 标 `unknown`/「多人同时说话」，这类会议禁用自动指派 |
| 实体错（人名、日期、金额） | ASR 专名错误 | 行动项指错人或期限错 | 参会人白名单 + 日期金额规则复核，冲突则标待确认 |
| 把讨论写成决议 | 摘要幻觉 | 治理风险，可能被当成正式决定 | 决议需证据段 + 主持人确认，其余进未决问题 |
| 重复建任务 | 重试、重放、人工重跑 | 任务系统污染 | 幂等键 + 目标系统唯一约束 |
| 越权检索 | 索引未继承会议 ACL | 合规事故 | ACL 继承 + 删除联动 + 访问审计（[[rag-08]]） |
| 长会议摘要退化 | 单次请求塞满上下文 | 后半场信息丢失 | 分章 + 分层 + 单章重跑（[[llm-internals-13]]） |
| 未取得同意 | 同意状态缺失或已撤回 | 法律与信任风险 | 同意作为前置门；撤回即停处理并删除既有产物 |

取舍上有一条明确立场：**宁可多写一条行动项，也不要漏一条。** 多写一条的代价是用户删一下（秒级），漏一条的代价是任务不被执行（可能数天）。这条偏好直接改变阈值与评测权重，后面的表 4 用数字量化。

### 8. 评测与上线门禁

- **ASR**：按口音、语言、噪声、是否重叠分群报 WER，别看总平均（[[multimodal-06]]）。
- **diarisation**：DER 是过程指标，**角色归属准确率**才是用户感知指标；报 DER 必须写清 collar 与重叠是否计分（[[multimodal-09]]）。
- **摘要**：人工评分三维——覆盖度、忠实度、简洁度；再加关键实体（人名、日期、金额）准确率。
- **行动项**：精确率/召回率分开报，并给出「漏检权重 ×5」的加权代价（召回优先）。
- **业务指标**：会后任务的实际完成率、用户编辑率、纪要打开率。用户总要改纪要，说明质量不够，而不是用户太挑剔。
- **门禁**：离线评测集 + 影子发布（新版本只生成不推送，人工对比）+ 灰度。同意、权限、删除联动必须有独立的合规测试用例，不能只靠功能测试。

### 9. 容量与成本的公式骨架

会议数 $N = N_{\text{员工}} \times n_{\text{每人每天}}$；音频时长 $H = N \cdot T$（分钟制），存储 $S = H \cdot r_{\text{编码}}$。ASR 的算力按实时率折算：

$$
\text{GPU}\cdot h_{\text{ASR}} = \frac{H}{\mathrm{RTF}}, \qquad \text{GPU}_{\text{并发}} = \frac{N_{\text{peak}} \cdot \bar{a}}{\mathrm{RTF}}
$$

会话文本的 token 数按语速与语言折算（英语约 0.75 词/token）：$T_{tok} = \dfrac{T \cdot \mathrm{WPM}}{0.75}(1+\mu)$，$\mu$ 是说话人与时间戳标记的增量。KV cache 沿用 LLaMA-3-70B 口径：

$$
\mathrm{KV} = 2 \cdot L \cdot H_{kv} \cdot d_{head} \cdot S \cdot b = 327{,}680\ \text{B/token} = 320\ \text{KiB/token}
$$

分层摘要（段长约 $\tau$ 分钟、每段输出 $g$ token、全局输出 $G$ token）的调用形状是 $n=\lceil T/\tau \rceil$ 次段级 + 1 次全局：

$$
C_{\text{flat}} = \frac{T_{tok}}{10^6}p_{in} + \frac{G}{10^6}p_{out}, \qquad
C_{\text{hier}} = \frac{T_{tok} + n g + I}{10^6}p_{in} + \frac{n g + G}{10^6}p_{out}
$$

行动项的评测代价用加权计数，$w$ 是漏检相对误报的权重：$\text{cost} = w \cdot \mathrm{FN} + \mathrm{FP}$。

## 数值与代码验证

**统一口径**：LLaMA-3-70B（80 层、GQA-8、head_dim 128、bf16）每 token KV 为 327,680 B = 320 KiB；H100 SXM bf16 稠密 989 TFLOPs、HBM3 3.35 TB/s，roofline 拐点 $989/3.35 \approx 295$ FLOPs/byte；prefill 按 $2PS$ 计，8 卡 @45% MFU = $8 \times 989 \times 0.45 = 3.56$ PFLOPS。ASR 吞吐取 **30× realtime/卡**，与 [[multimodal-03]]、[[multimodal-09]] 同一口径。模型单价是**算例假设**：强模型 3 USD / 百万输入 token、15 USD / 百万输出 token（与 [[agents-09]] 同一量级），便宜模型 0.5 / 1.5；对象存储按 0.023 USD/GB-月（[[agents-10]] 口径）。这些都不是任何供应商的报价。

| 原始 PCM 对照 | 16 kHz × 16 bit $= 115.2$ MB/h | 2.16 TB/工作日（Opus 的 8 倍） |
| 90 天留存 | $270\ \text{GB} \times 90 \times \tfrac{5}{7} = 17{,}357$ GB，$\times 0.023$ USD/GB-月 | 约 400 USD/月，约 4,800 USD/年 |
| 转写文本 | $45 \times 140 = 6{,}300$ 词 $\to 8{,}400$ token，加标记 ×1.15 $\to$ 9,660 token；纯文本约 38 kB/场 | 约 0.97 GB/工作日（比音频小约 280 倍） |

存储账的结论：**音频与文本差两个数量级，保留策略该由合规决定**，17.4 TB 的月度存储费只有几百美元。

**表 2：算力**（ASR 才是大头）

| 环节 | 算式 | 结果 |
| --- | --- | --- |
| 会后 ASR | $18{,}750\ \text{h} / 30$ | 625 GPU·h/工作日（8 h 折合 78 卡） |
| 会中 ASR（无门控） | $1{,}200 \times 5 / 30$ | 200 卡 |
| 会中 ASR（VAD 门控后） | 任一时刻平均 1.6 人在说：$1{,}200 \times 1.6 / 30$ | 64 卡（3.1× 的节省，独立音轨的第二个收益） |
| 摘要 prefill / decode（120 min 单次全局） | $2 \times 70 \times 10^9 \times 25{,}760$；$800 \times 2 \times 70 \times 10^9$ | 3,606 TFLOPs $\to$ 8×H100 @45% MFU **1.01 s**；112 TFLOPs |
| 全量摘要（45 min 均场，分层 + 分级） | 单场 $2PS \times (9{,}660 + 1{,}650 + 2{,}150) = 1.88$ PFLOPs（依次为分段输入、全局输入 $9 \times 150 + 300$、全部输出 $9 \times 150 + 800$）；$\times 25{,}000 = 4.7\times10^{19}$ FLOPs | 8×H100 机 3.7 小时，折合 **29 GPU·h/工作日** |

**ASR 的算力是摘要的约 21 倍**（625 对 29 GPU·h），所以优化顺序是 ASR 吞吐 → 摘要的输入长度 → 其余；把预算花在「换更小的摘要模型」上是错的方向。diarisation 侧同理：按 1.5 s 窗口、0.25 s 步长，每小时音频是 $3600/0.25 = 14{,}400$ 次嵌入前向，每次按 1 GFLOP 的千万参数网络量级估，18,750 h 合计约 $2.7\times10^{17}$ FLOPs，按单卡 40% MFU（396 TFLOPs）折算只有 11 GPU·分钟——**diarisation 的瓶颈是准确率与对齐逻辑，不是算力**。

**表 3：摘要策略的 token 与成本**（段长 5 min、每段输出 150 token、全局输出 800 token、全局输入 300 token 指令；表内单位为 USD/场，45 min 场景的 KV 为 $9{,}660 \times 327{,}680\ \text{B} = 3.17$ GB $= 2.9$ GiB）

| 会议时长 | 转写 token | 单序列 KV | 段数 × 段长 | 段级 KV | 单次全局 | 分层 | 分层 + 分级 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 45 min | 9,660 | 2.9 GiB | 9 × 1,073 | 335 MiB | 0.0410 | 0.0662 | **0.0238** |
| 120 min | 25,760 | 7.9 GiB | 24 × 1,073 | 335 MiB | 0.0893 | 0.1550 | **0.0420** |
| 180 min | 38,640 | 11.8 GiB | 36 × 1,073 | 335 MiB | 0.1279 | 0.2260 | **0.0565** |

这张表要读出三件事。其一，**单序列 KV 是分层最硬的动机**：两小时会议一次塞进去要占 7.9 GiB KV，8 张 80 GB 卡扣掉 131 GiB 权重后只剩约 466 GiB，只放得下几十条这样的序列；切成 1,073 token 的段之后单序列只要 335 MiB，同一张卡的 KV 预算能装下上千段。其二，**分层比单次全局贵 1.6–1.8 倍**（多出来的输出 token 是主因），买的是质量与可重跑性；其三，**段级用便宜模型 + 全局用强模型**把成本压到单次全局的一半左右（45 min 口径 0.0238 对 0.0410，即 58%），是三种策略里最省的——分层不是为了省钱，分级才是。按 45 min 的 0.0238 USD 与每年 625 万场计，全量摘要约 **14.9 万美元/年**；若只对 60% 的会议（有 3 人以上、非私聊）出纪要，降到约 **8.9 万美元/年**。

**表 4：行动项的召回优先**（每场人工标注 3.2 条行动项，漏检权重 $w=5$）

| 策略 | 召回 | 精确 | TP | FN | FP | $5\,\mathrm{FN}+\mathrm{FP}$ |
| --- | --- | --- | --- | --- | --- | --- |
| A 高精确优先 | 75% | 82% | 2.40 | 0.80 | 0.53 | 4.53 |
| B 高召回优先 | 92% | 70% | 2.94 | 0.26 | 1.26 | **2.54** |

B 的精确率低 12 个百分点，加权代价却是 A 的 0.56 倍。前提是「多写一条」的成本真的接近零——所以产品上必须有「一键删除 / 一键改派」的交互，否则这个结论不成立。

**表 5：角色归属错误如何变成错派行动项**

| 归属错误率 | 45 min（约 300 个话轮）错标话轮 | 其中落在行动项上的比例 | 后果 |
| --- | --- | --- | --- |
| 4% | 12 | 5% | 每 1.7 场出现 1 条错派 |
| 2% | 6 | 5% | 每 3.3 场出现 1 条错派 |

这就是「角色归属准确率是用户感知指标」的量化版本：同一份输出只要换个口径就能把 DER 从 11.75% 降到 9.47%（[[multimodal-09]] 的口径 C：重叠区整段不计分），用户对此毫无体感；而错派一条行动项会被立刻发现并摧毁信任。所以自动指派应该只在高置信时开启，其余一律进人工确认队列。

```python
GiB = 1024 ** 3
KV = 2 * 80 * 8 * 128 * 2                  # 327680 B = 320 KiB/token（LLaMA-3-70B，GQA-8，bf16）
WPM, MARKUP = 140, 1.15                    # 语速与标记增量
STRONG, CHEAP = (3.0, 15.0), (0.5, 1.5)    # 示意单价：USD / 百万 token
SEG_MIN, SEG_OUT, GLOBAL_OUT, SYS = 5.0, 150, 800, 300

def tokens(minutes):
    return minutes * WPM / 0.75 * MARKUP

def usd(n_in, n_out, p_in, p_out):
    return n_in / 1e6 * p_in + n_out / 1e6 * p_out

for minutes in (45, 120, 180):
    tok = tokens(minutes)
    n = int(-(-minutes // SEG_MIN))        # 段数，向上取整
    flat = usd(tok, GLOBAL_OUT, *STRONG)
    hier = usd(tok + n * SEG_OUT + SYS, n * SEG_OUT + GLOBAL_OUT, *STRONG)
    tier = usd(tok, n * SEG_OUT, *CHEAP) + usd(n * SEG_OUT + SYS, GLOBAL_OUT, *STRONG)
    print(f"{minutes:3d} min | {tok:7.0f} tok | KV {tok * KV / GiB:4.1f} GiB | {n:2d} 段 x {tok / n:.0f} tok "
          f"| 段级 KV {tok / n * KV / 1024**2:.0f} MiB | {flat:.4f} {hier:.4f} {tier:.4f} USD")

ITEMS, W = 3.2, 5.0                        # 每场人工标注行动项数；漏检权重
def cost(recall, precision):
    tp = recall * ITEMS
    return W * (ITEMS - tp) + (tp / precision - tp)
print(round(cost(0.75, 0.82), 2), round(cost(0.92, 0.70), 2))   # 4.53 2.54

ASR_RTF, HOURS = 30, 10_000 * 2.5 * 45 / 60
print(round(HOURS, 0), round(HOURS / ASR_RTF, 0))               # 18750 625 GPU.h
print(round(0.0238 * 25_000 * 250 / 1e4, 1), "万美元/年（全量摘要）")  # 14.9

DAY_GB = HOURS * 14.4 / 1000               # 表 1：Opus 32 kbps = 14.4 MB/h
print(round(DAY_GB), "GB/日", round(DAY_GB * 90 * 5 / 7), "GB 留存",
      round(DAY_GB * 90 * 5 / 7 * 0.023), "USD/月")             # 270 17357 399
P, MFU, N45 = 70e9, 0.45, tokens(45)       # 表 2：45 min 均场、分层 + 分级
FLOP = 2 * P * (N45 + 9 * SEG_OUT + SYS + 9 * SEG_OUT + GLOBAL_OUT)     # 1.88 PFLOPs/场
print(round(FLOP / 1e15, 2), "PFLOPs/场", round(25_000 * FLOP / (8 * 989e12 * MFU) / 3600, 1), "h/8 卡",
      round(25_000 * FLOP / (989e12 * MFU) / 3600, 1), "GPU.h")            # 1.88 3.7 29
print(round(1 / (300 * 0.04 * 0.05), 1), round(1 / (300 * 0.02 * 0.05), 1), "场/条错派")   # 1.7 3.3
```

这段脚本把上面五张表的主要数字复算了一遍（表 3 的三列即 `flat / hier / tier`；表 1 的存储账、表 2 的 ASR 与摘要算力、表 4 的加权代价、表 5 的场次概率都由同一组假设推出）。**算例里的假设（语速 140 词/分、标记增量 15%、ASR 30× realtime、段长 5 min、单价）都可以换成自己的数重跑，结论的量级不会变：ASR 吃掉绝大部分算力，摘要的成本与上下文结构强相关，行动项的评测必须以召回为先。**

## 常见追问

- **追问**：会中与会后能不能共用一套模型？
  - 要点：可以共用权重，但解码与上下文策略必须分成两套。会中只能因果上下文、按 chunk 出临时结果；会后可以双向上下文、可以用完整录音重跑、还可以做全局说话人聚类。设计上把「临时标签」与「终稿标签」分开存储、UI 明确标注，比强行统一精度更划算（[[multimodal-03]]）。
- **追问**：多人重叠说话怎么办？
  - 要点：三层。拿到独立音轨时重叠自动消解，这是首选；单路混音时用重叠语音检测标出重叠区间，重叠段只保留文本、不标说话人；再不行用 EEND 式模型直接输出多列活动。产品上重叠段宁可标「多人同时说话」，也不要随便挑一个人（[[multimodal-09]]）。
- **追问**：怎么避免把「讨论」写成「决议」？
  - 要点：schema 上决议与未决问题是两个字段；决议必须带原文证据区间，且只接受明确表态 + 决定动词的段落；未确认的决议在 UI 上是「待确认」状态，不进入集成写入。这条约束由评测守护：人工标注里专门有一类「被误判为决议的讨论」，作为回归用例。
- **追问**：同一场会重复处理会不会重复建任务？
  - 要点：幂等键 `(meeting_id, 行动项指纹, pipeline_version)` + 目标系统的唯一约束；重跑时做 diff，消失的条目标 `superseded` 而不是删除；写外部系统一律「先查后写 + 冲突检测」，不要依赖消息队列的去重（[[agents-02]]）。
- **追问**：多语言、code-switching 怎么处理？
  - 要点：按语种分别评测与分别设阈值，热词表按语种维护；code-switching 需要 ASR 支持语言无关的声学建模或做语言识别后分段路由，摘要侧统一翻译成组织的工作语言再生成，避免混语种输出（[[multimodal-07]]）。
- **追问**：用户总要手动改纪要，说明什么？
  - 要点：先分层定位——如果改的是错字与专名，是 ASR 问题；改的是指派人，是角色归属问题；改的是「这句话不该出现在决议里」，是抽取策略问题。三类问题的修复手段完全不同，编辑日志本身就是最有价值的评测集（[[evaluation-10]]）。
