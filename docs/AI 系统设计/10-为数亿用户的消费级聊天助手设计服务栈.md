## 一句话答案

> 先算账再画图：3 亿 DAU、人均每天 6 条消息是 18 亿请求/天，峰值 10 万 QPS；按每条 1.2k 输入、300 输出 token，峰值需要 1.2 亿输入 token/s 与 3,000 万输出 token/s。用本仓库口径（H100 SXM5 bf16 989 TFLOPs、3.35 TB/s、LLaMA-3-70B 每 token KV 320 KiB）算下来是 7,279 个 8 卡节点 ≈ 5.8 万张 GPU，按时间平均折算每百万输出 token 约 5.18 美元（峰值满载口径 1.08 美元）——**这个量级决定了整条链路必须按「省算力」而不是「省服务器」来设计**。
> 链路上真正决定体验的是流式与排队：用户感知的是 TTFT，所以流式、取消传播、排队预算要从第一跳就做；真正决定成本的是 prefill，它是 decode 的 2.8 倍。
> 工程结论是四件事：按峰值配 prefill 池 + 按显存配 decode 池并分离、用共享前缀缓存吃掉一半 prefill、用分层队列与降级阶梯守住付费 SLO、把 1 PB 级 KV 显存需求交给分层缓存而不是单卡显存。

## 面试官在考什么

- 能不能**先给算式再给架构**。这题的区分度几乎全在容量链条上：DAU → 峰值 QPS → 峰值 token/s → GPU 数 → 单位成本，每一步的假设都写在明面上。只画框图不给数字，等于没答。
- 是否知道**峰值与均值的差距决定架构**。均值口径下 1,516 个节点就够，峰值口径要 7,279 个；这 4.8 倍的差距无法靠「多买卡」抹平，只能靠排队、降级与弹性一起吃掉，因为超配的那部分在凌晨会整夜闲置。
- 是否把**prefill 与 decode 分开算**。两者一个吃算力一个吃带宽，比例由流量形状决定（这里 2.8:1），混在一起算必然算错，也解释不了为什么要 P/D 分离。
- 有没有**从 SLO 反推容量**的习惯：TTFT/TPOT 约束先定，再算 batch 上限、并发上限、goodput，而不是先买卡再压测。
- 有没有真实系统的经验感：chunked prefill 治的是尾延迟尖刺、前缀缓存治的是重复 prefill、early rejection 治的是过载，三者解决的层次不同，不能混成一句「做推理优化」。
- 能不能讲清**多租户与降级**：免费流量不能和付费流量共享同一个 batch，过载时要快速拒绝而不是无限排队。

常见错误答案：

- 「加卡就行」。不说 MFU、不说 batch、不说 KV 显存，直接给一个「几万台 H100」的数字。价格与利用率的关系是这题的核心：单卡吞吐上不去时，加卡的边际成本是线性的，而优化可能是 2–4 倍的。
- 只按平均 QPS 配容量。均值配容量在晚高峰必然雪崩，且雪崩时排队会把延迟放大成超时，超时又会触发重试，形成正反馈。
- 把「上下文 32k」当成常态设计。上下文翻倍时 KV 显存与 prefill 算力同时翻倍，而实际流量里绝大多数请求的首轮 prompt 只有一到两千 token；按 32k 配容量等于把成本乘以 8 倍以上（第 5 节复算：KV 8 倍、prefill 8.6 倍），见 [[inference-serving-09]]。

## 原理与推导

### 1. 需求澄清与假设（先把数字摆出来）

这是消费级聊天助手，不是 API 平台：流量有强烈的日周期，p95 用户对首字延迟敏感，免费用户占绝大多数。先固定一组可复算的假设，全部写进正文，改动任何一条都要重算：

| 假设 | 取值 | 依据 / 影响 |
| --- | --- | --- |
| DAU | 3 亿 | 消费级规模 |
| 每人每天消息数 | 6 条 | 18 亿请求/天 |
| 峰值 QPS | 10 万 | 按日均的约 5 倍估（日均 20,833 QPS） |
| 输入 token / 请求 | 1,200 | 系统提示 + 裁剪后的历史 + 本轮问题 |
| 输出 token / 请求 | 300 | 对话回答的典型长度 |
| 上下文窗口 | 4,096 | 超出部分靠裁剪与摘要 |
| SLO | TTFT p95 < 1 s、TPOT ≤ 25 ms、可用性 99.95% | 交互式对话的常规门槛 |
| 硬件 | H100 SXM5，80 GB HBM3，bf16 稠密 989 TFLOPs，3.35 TB/s | 与仓库其它专题一致 |
| 模型 | LLaMA-3-70B 级，GQA-8、80 层、head_dim 128、bf16 | 每 token KV 320 KiB |

峰值倍数是这张表里最需要辩护的一条。3 亿 DAU 的消费产品有明显的晚高峰，峰值与日均差 3–10 倍都出现过；这里取 5 倍，并把「怎么处理这个差距」作为架构设计的主题之一。所有下游数字都随它线性变化，所以面试时把它当作显式的调节旋钮讲出来，比背一个具体节点数更有说服力。

### 2. 请求链路：每一跳的延迟与失败模式

```
客户端（SSE/WebSocket，支持断点续传）
  └─> 边缘 / BFF（鉴权、设备指纹、L7 限流、区域路由）            +5～15 ms
        └─> LLM gateway（模型路由、前缀缓存查询、预算与配额）      +10～30 ms
              └─> 会话与状态服务（历史读取、裁剪/摘要、上下文组装）  +20～60 ms
                    └─> 检索 / 工具（需要时；可并行，有超时预算）     +50～300 ms
                          └─> 推理集群（排队 → prefill → decode）     TTFT 主导项
                                └─> 流式回传（逐 chunk 到客户端）
                    └─> 安全与合规（输入护栏前置、输出护栏逐 chunk 流式判定）
        └─> 计费与遥测（异步，出关键路径）
```

四件必须在第一跳就定下来的事：

- **流式是协议层的默认**。用户感知的延迟是 TTFT，不是 E2E；任何一跳做整包缓冲都会把体验打回「等十秒」（[[inference-serving-09]]）。SSE 与 WebSocket 二选一时，SSE 更简单、对中间层更友好，代价是需要额外的取消通道。
- **取消要能穿透到底**。用户关页面、改问题、点停止，都必须让推理集群释放 batch slot 与 KV block。没有取消传播时，废弃请求会继续占着最稀缺的资源——这正是过载雪崩的起点。
- **状态与计算分离**。会话历史是真相源，KV cache 是可重建的派生物。两者混在一起会让「迁移会话」变成不可解的问题；分开之后，KV 丢了只需重算 prefill。
- **失败要分级**。护栏服务不可用时应当 fail-open 还是 fail-closed 取决于输出类型：纯文本对话 fail-open 并记录，涉及工具执行或账户操作时 fail-closed（[[safety-04]]）。

检索与工具是可选跳：只在本轮确实需要时进入链路，且并行发起、单独设超时预算；检索超时或失败不能让整轮回答失败，要带着「检索不可用」的标记继续生成（[[system-design-01]]）。

延迟预算的分配（p95）：边缘 15 ms + gateway 30 ms + 会话组装 60 ms + 排队 200 ms + prefill 150 ms + 首 token 采样 20 ms ≈ 475 ms。剩下的余量留给检索（启用时）与护栏。注意排队 200 ms 是预算项而不是意外——峰值时段没有排队预算的设计必然违反 TTFT SLO；decode 侧同理，$b_{\max} = 384$ 时的 TPOT 是 24.46 ms，已经贴住 25 ms 的 SLO，所以并发不能再往上堆：显存上限与延迟 SLO 一起把 batch 钉在了 384。

### 3. 容量与成本算账（主线）

**第一步：流量。** 3 亿 DAU × 6 = 18 亿请求/天 = 20,833 QPS 日均；峰值按 5 倍取 $10^5$ QPS。

$$\text{峰值输出吞吐} = 10^5 \times 300 = 3.0\times10^7\ \text{token/s}, \qquad \text{峰值输入吞吐} = 10^5 \times 1200 = 1.2\times10^8\ \text{token/s}$$

**第二步：两种产能，一个吃算力、一个吃带宽。** prefill 吃算力：单请求 FLOPs 约 $2NP + 2Ld_{model}P^2$，代入 $N = 7\times10^{10}$、$P = 1200$、$L = 80$、$d_{model} = 8192$ 得 $1.68\times10^{14} + 1.9\times10^{12} \approx 1.70\times10^{14}$ FLOPs。8 卡节点在 MFU 0.40 下的有效算力是 $989 \times 8 \times 0.40 = 3.165$ PFLOP/s，于是单请求 53.7 ms、单节点 prefill 吞吐 $\approx 22{,}355$ token/s（输入侧）。

decode 吃带宽：每步要读完整份权重加 batch 内全部 KV。在显存上限处 $b_{\max} = 384$（每卡留 60 GiB 给 KV、4k 上下文，见第 5 节），单节点每步读 $140 + 384 \times 4096 \times 320\ \text{KiB} = 140 + 515 = 655$ GB（每卡 17.5 GB 权重 + 64.4 GB KV = 81.9 GB，8 卡同比），节点聚合带宽 26.8 TB/s，得 $t_{step} = 24.46$ ms，即 TPOT 24.46 ms、单节点 decode 吞吐 $\approx 15{,}702$ token/s（输出侧）。

放回 roofline 看，两个池的差异一眼可见：prefill 读 140 GB 权重做 $1.70\times10^{14}$ FLOPs，算术强度约 1,210 FLOPs/byte，远在拐点 295 之上；decode 一步读 655 GB 只做 $5.4\times10^{13}$ FLOPs，强度约 82 FLOPs/byte，稳在拐点之下。**前者按 FLOPs 配、后者按字节/秒配**，所以它们的最优 batch、并行度与扩缩容信号完全不同——这是 P/D 分离在本题里最直接的依据。

**第三步：节点数与成本。**

| 池 | 产能 | 峰值需求 | 节点数 | GPU·s/请求 |
| --- | --- | --- | --- | --- |
| prefill | 22,355 tok/s | $1.2\times10^8$ tok/s | 5,368 | 0.429 |
| decode | 15,702 tok/s | $3.0\times10^7$ tok/s | 1,911 | 0.153 |
| 合计 | — | — | **7,279（58,232 张 GPU）** | **0.582** |

比例是 prefill : decode ≈ 2.8 : 1，prefill 吃掉约 74% 的 GPU·s——**对话流量的长 prompt 短输出形状落在 prefill 一侧**，这与「聊天很便宜」的直觉相反。两池必须分开配比，这正是 P/D 分离的直接动机。

成本按每 GPU 每小时 2 美元计（含电与折旧的整机口径），分两种口径看，混用会把同一个系统说成相差五倍：

- **峰值满载口径**（集群正跑在容量上限、没有闲置卡）：峰值集群 $58{,}232 \times 2 = \$116{,}464/\text{h}$（约 280 万美元/天），每请求 $\frac{0.582 \times 2}{3600} = \$0.000323$，即每 1M 请求约 \$323；按池摊到 token 是 prefill 池 $0.20$ 美元/1M 输入 token、decode 池 $0.28$ 美元/1M 输出 token。
- **时间平均口径**（把「按峰值买卡、整晚闲置」这件事折进单位成本）：日均口径只要 1,516 个节点，即峰值集群的时间平均利用率 $1/4.8 = 20.8\%$，于是每请求 $\frac{0.582 \times 2}{3600 \times 0.208} = \$0.00155$，即**每 1M 请求约 1,555 美元、每 1M 输出 token 约 5.18 美元**。两者相差 4.8 倍，差值就是「为峰值付钱」的价格。

第二种口径才是对外的成本基准，也直接导向本节后面所有优化：把 20.8% 的利用率提上去（错峰定价、离线批处理、夜间降级与下线一批池子）等于按比例降本，而降低峰值算力（前缀缓存、chunked prefill、P/D 分离的 goodput 收益）等于缩小分子。拿到这个数字后再去对照公开的 API 价格才有意义——自建成本高于对方售价时，买的其实是采购周期与闲置风险（[[inference-serving-11]] 讨论自建与外部 API 的混合）。

### 4. 推理集群：五个具体机制，各治一种病

| 机制 | 治什么病 | 论文口径 | 本题里的量化收益 |
| --- | --- | --- | --- |
| continuous batching + paged KV | static batching 的空转与 KV 碎片 | 受操作系统虚拟内存与分页启发，KV cache 近零浪费、支持请求内与跨请求共享，同延迟下吞吐提升 2–4 倍，序列越长、模型越大收益越明显 | decode 池的并发上限从「按最长可能输出预留」变成按实际占用分配（[[inference-serving-02]]、[[inference-serving-03]]） |
| chunked prefill | 长 prompt 独占 iteration 造成的 ITL 尖刺 | 把 prefill 切成近似等长的块、构造无停顿调度；Mistral-7B 单 A100 上 2.6×、Yi-34B 双 A100 上 3.7×、Falcon-180B 配流水并行 5.6× 服务容量 | 4k prompt 不切块会在同批所有请求上留一个约 188 ms 的 ITL 台阶，切到 512 token 只剩约 23 ms（[[inference-serving-14]]） |
| prefill/decode 分离 | 两个相位的资源错配与相互干扰 | 把两阶段放到不同 GPU，并按 TTFT/TPOT 分别优化资源与并行策略；满足 90% 以上请求延迟约束的前提下可服务 7.4 倍请求或收紧 12.6 倍 SLO | 这题里 prefill:decode = 2.8:1 且随流量形状变化，只有分离才能各自扩缩（[[inference-serving-15]]） |
| KVCache 中心的分层缓存 | 单卡显存装不下并发 KV | 利用 GPU 集群中闲置的 CPU/DRAM/SSD 做分离式 KV 缓存，用 KVCache 中心调度器在有效吞吐与 SLO 间权衡，并针对过载设计基于预测的提前拒绝；真实负载下让 Kimi 多处理 75% 请求、模拟场景吞吐最高提升 525% | 第 5 节的账显示：按 4k 上界算的热需求 1.07 PB 比 decode 池 0.99 PB 的 KV 预算还多 9%，单卡显存装不下峰值并发，分层与复用是必需项 |
| 前缀复用（radix/block） | 系统提示与工具定义被重复 prefill | RadixAttention 用基数树做 KV 复用、压缩有限状态机加速结构化输出，多类负载上吞吐最高提升 6.4 倍 | 见第 5 节：吃掉约一半 prefill 算力 |

注意力内核用 FlashAttention 的 IO 感知分块：它不减少 FLOPs，而是减少 HBM 与 SRAM 之间的读写（[[llm-internals-05]]）；并行与量化按 Efficiently Scaling Transformer Inference 的解析模型选多维切分——该文在 540B 模型上用 int8 权重量化做到低 batch 29 ms/token、大 batch 76% MFU，并指出多查询注意力让上下文长度可扩大 32 倍（口径为 PaLM 540B、2048 token 上下文、TPU v4）。

### 5. 上下文与状态：显存账与成本账

并发量由 Little 定律给：单请求时长 ≈ $25\ \text{ms} \times 300 + 0.5\ \text{s} \approx 8.0$ s，于是峰值并发 $\approx 10^5 \times 8.0 = 8\times10^5$ 条。

$$\text{KV 热需求（4k 上界）} = 8\times10^5 \times 4096 \times 320\ \text{KiB} = 1.07\ \text{PB}$$

1.07 PB 是**上界口径**（每条并发都按 4k 算）；按解码期间的平均序列长度 1.35k token（1.2k 输入 + 输出从 0 涨到 0.3k）算是 0.35 PB。分母这边，按 $b_{\max} = 384$ 配出来的 decode 池只有 $1{,}911 \times 8 \times 60\ \text{GiB} = 896\ \text{TiB} \approx 0.99\ \text{PB}$：**上界需求比它多 9%，平均口径才留 2.8 倍余量**。这个差值说明的不是「装得下」，而是显存只够容纳「平均负载 + 一部分长尾」——晚高峰、长会话、工具返回的长文档会把长尾集中起来，一旦触发驱逐就要重算 prefill，于是延迟与算力一起恶化。7,279 个节点按每卡 60 GiB 合计是 3.33 PiB，但那是把 prefill 池的空闲显存也算进来的账，要把它变成可寻址的 KV 池就得付出分离式缓存的复杂度。所以答案是四件事一起做：共享前缀命中 + 近期历史复用 + DRAM/SSD 分层缓存 + 长会话摘要，而不是指望单卡显存。

系统提示与工具定义是这个结构里最划算的部分。设系统提示 2,000 token、前缀缓存命中率 40%，则每条请求省下 800 个 prefill token：

$$\Delta = \frac{\text{preflops}(800)}{P_{\text{eff}}} \times 8 = 0.285\ \text{GPU·s/请求} \;\Longrightarrow\; \text{省下 } 3{,}579 \text{ 个 prefill 节点（总算力的 } 49.2\%\text{）}$$

按日均流量折算，全天省下 $1.8\times10^9 \times 0.285 / 86400 \approx 5{,}900$ GPU·天（峰值口径是 2.85 万 GPU·天）；若按「系统提示 2,000 token × 每天 10 亿请求」这个常用标尺，则是 $3{,}300$ GPU·天 $\approx 15.8$ 万美元/天（@\$2/GPU·h 的裸算力价），占总算力的比例不变，仍是 49%。同时单请求 TTFT 少 35.7 ms。**而缓存本身的存储代价小到可以忽略**：这是全体用户共享的同一个前缀，10 个变体加起来只有 $10 \times 2000 \times 320\ \text{KiB} \approx 6.1$ GiB。反过来，如果为 3 亿用户各存一份 2,000 token 的个人历史 KV，就是 196.6 PB——**共享前缀近乎免费，按用户缓存历史则每一条都要付存储费**，两件事必须分开讲（[[inference-serving-05]]）；也因此缓存命名空间要按租户与模型版本隔离：系统提示这类与用户无关的前缀可以全局共享，用户历史只能命中自己的命名空间，否则「命中别人的前缀」既是正确性问题，也是数据泄漏。

长上下文是另一侧的账：上下文从 4k 到 32k 时 KV 显存按 8 倍增长，prefill 算力涨得更多（注意力项超线性，同一套常数复算是 8.6 倍），而 [[llm-internals-13]] 指出长上下文中段的信息还会被系统性忽略——**花 8 倍成本换来的召回率并不线性**，所以默认上下文应当由评测决定，而不是取模型支持的上限。

### 6. 多租户、公平性与失败模式

分层是第一原则：**免费、付费、企业三类流量用独立的池或至少独立的调度权重**。同一张卡上混跑时，一条免费用户的长 prompt 会拖长同批所有请求的 ITL，付费 SLO 无法用「平均」来兜底。典型配置是付费池按 goodput 配、免费池按吞吐配并接受更长排队。

过载处理按下面的顺序执行，越靠前的越先启用，越靠后的只在更严重时动用：

1. **准入控制与配额**：每用户/设备/IP 的 token 桶，超限返回 429 并给出 retry-after。
2. **优先级队列 + 提前拒绝**：不是无限排队。Mooncake 针对过载场景的预测式提前拒绝策略值得直接借用——预测该请求在 SLO 内无法完成时立刻拒绝，比让它排队 30 秒后超时便宜得多，也不会诱发重试风暴。
3. **降级阶梯**：换小模型（8B 级，成本降一个数量级）→ 限制输出长度（300 → 150 token）→ 关闭工具与检索 → 返回缓存/静态答案 → 最后才排队并明确告知。
4. **熔断与隔离**：单租户或单区域异常不能拖垮全局，按区域、按模型版本独立熔断。
5. **重试纪律**：只在幂等且可取消的层级重试，且带抖动与预算上限；重试必须复用原始 request id 以便去重。

失败模式清单（面试时按「组件 → 症状 → 兜底」讲）：

| 组件 | 失败症状 | 兜底 |
| --- | --- | --- |
| 边缘 / BFF | 区域故障、鉴权抖动 | 多区域 + 就近接入 + 故障区域摘除 |
| gateway | 路由错误、预算误判 | 无状态多副本、配置灰度、路由规则可回滚（[[system-design-09]]） |
| 会话服务 | 历史读延迟尖刺 | 读写分离 + 本地缓存 + 降级为「只带最近 3 轮」 |
| 推理集群 | decode worker 崩溃丢 KV | 请求级重做 prefill，需从 router 层重走流程并保证幂等 |
| 前缀缓存 | 缓存节点失效导致 prefill 洪峰 | 按「随时可能全失效」设计：容量按 0% 命中率配（第 3 节的 7,279 个节点就是无缓存口径），缓存层容忍节点失效与冷启动 |
| 护栏服务 | 超时 | 按输出类型选 fail-open/fail-closed，并单独配额（[[safety-04]]） |

### 7. 发布、可靠性与评测

- **多区域**：至少三个区域，区域间按用户就近接入；会话状态跨区域复制，KV cache 不复制（丢了重算）。区域故障切换的验收标准是「切换后 TTFT p95 不劣化 2 倍」。
- **滚动升级与灰度**：模型版本、引擎版本、prompt 版本三者独立灰度，任一维度都要能一键回滚（[[evaluation-08]]）。推理集群滚动升级时按节点池轮转，保证任一时刻至少留出一个完整池的容量。
- **容量与质量的联合实验**：新模型上线要同时看三条曲线——质量（离线评测集 + 在线 A/B，[[evaluation-09]]）、延迟（TTFT/ITL 分位数）、成本（每 1M token）。一个质量高 1 分但成本 2.5 倍的模型，只有在它能显著改变留存时才值得上；这三条曲线必须同一张看板。
- **可观测性**：请求级 trace 串起 gateway 决策、排队时长、prefill/decode 耗时、护栏耗时与成本，按租户与模型版本聚合（[[evaluation-07]]）。
- **SLO 与错误预算**：TTFT p95 < 1 s、ITL p99 < 100 ms、可用性 99.95%（每月约 21.6 分钟）。错误预算烧穿即冻结非必要变更，而不是继续上功能。

## 数值与代码验证

上面的表格由这段代码复算，常数口径写死在开头；脚本保存在 `.work/` 下，不随仓库提交。

```python
N, L, D_MODEL, H_KV, D_HEAD, BYTES = 70e9, 80, 8192, 8, 128, 2   # LLaMA-3-70B, bf16
BW1, PEAK1, MFU, NODE = 3.35e12, 989e12, 0.40, 8                 # H100 SXM5 稠密算力
P_EFF = PEAK1 * MFU * NODE                                        # 3.165 PFLOP/s（= 989 × 8 × 0.4）
K, W = 2 * L * H_KV * D_HEAD * BYTES, BYTES * N                  # 320 KiB/token, 140.0 GB
print(P_EFF / 1e12, BW1 * NODE / 1e12, PEAK1 / BW1)               # 3164.8 26.8 295.2

I, O, CTX, PEAK = 1200, 300, 4096, 1.0e5                          # 峰值 10 万 QPS
preflops = lambda P: 2 * N * P + 2 * L * D_MODEL * P * P          # 含因果注意力项
t_pre = preflops(I) / P_EFF                                       # 53.7 ms
node_pre = I / t_pre                                              # 22,355 输入 tok/s
w_card, k_card = W / NODE, K / NODE                               # 每卡 17.5 GB 权重、40 KiB/token KV
b_max = int(60 * 1024**3 / (k_card * CTX))                        # 384（每卡留 60 GiB 给 KV）
t_step = (w_card + b_max * k_card * CTX) / BW1                    # 24.46 ms（按单卡带宽）
node_dec = b_max / t_step                                         # 15,702 输出 tok/s

n_pre, n_dec = PEAK * I / node_pre, PEAK * O / node_dec
print(n_pre, n_dec, n_pre + n_dec, (n_pre + n_dec) * NODE)        # 5368.0 1910.6 7278.6 58229
g_pre, g_dec = t_pre * NODE, O / node_dec * NODE
print(g_pre, g_dec, g_pre + g_dec)                                # 0.429 0.153 0.582
print((g_pre + g_dec) * 2 / 3600 * 1e6, (g_pre + g_dec) * 2 / 3600 * 1e6 / O)
                                                                  # $323 / 1M 请求 ; $1.08 / 1M 输出 token（峰值满载）
print(g_pre * 2 / 3600 * 1e6 / I, g_dec * 2 / 3600 * 1e6 / O)      # $0.20 /1M 输入 token ; $0.28 /1M 输出 token（按池摊）
print((g_pre + g_dec) * 2 / 3600 / 0.208 * 1e6,
      (g_pre + g_dec) * 2 / 3600 / 0.208 * 1e6 / O)               # $1,555 / 1M 请求 ; $5.18 / 1M 输出 token（时间平均）
print(round(n_pre + n_dec) * NODE * 2)                            # $116,464 / h（7,279 个节点的整数口径，@$2/GPU·h）

SYS, HIT = 2000, 0.40                                             # 系统提示与命中率
saved = SYS * HIT                                                 # 800 token/请求
d_gpu_s = preflops(saved) / P_EFF * NODE                          # 0.285 GPU·s/请求
print(d_gpu_s, n_pre * saved / I, n_pre * saved / I / (n_pre + n_dec))   # 0.285 3578.7 49.2%
print(PEAK * 86400 * d_gpu_s / 86400, 18e8 * d_gpu_s / 86400,
      1e9 * d_gpu_s / 86400 * 24 * 2)                             # 峰值全天 28,523 GPU·天 ; 日均 5,942 ; 10 亿请求/天 $158,464
print(10 * SYS * K / 1024**3, 3e8 * SYS * K / 1e15)               # 6.1 GiB ; 196.6 PB

conc = PEAK * (25 * O / 1e3 + 0.5)                                # 8.0e5 条并发
print(conc * CTX * K / 1e15, conc * (I + O / 2) * K / 1e15)        # 4k 上界 1.07 PB ; 解码期平均 1.35k token 是 0.35 PB
print(n_dec * NODE * 60 * 1024**3 / 1e15)                         # decode 池 0.98 PB = 896 TiB（= 1,911 × 8 × 60 GiB）
print((n_pre + n_dec) * NODE * 60 * 1024**3 / 1e15)               # 全集群 3.75 PB = 3.33 PiB（含 prefill 池空闲显存）
```

与源文对照：源文给出的是「token → 嵌入 → Transformer → 逐 token 采样」的请求内部流程与「KV cache 随输出增长、真正的瓶颈是显存/内存而不是算力」的定性结论，以及 KV cache 与 KV cache 压缩、PagedAttention、FlashAttention、continuous batching、prefix caching、prefill/decode 分离、speculative decoding 等手段地图；本节把其中的显存瓶颈与批处理收益量化成了具体的节点数与美元。论文数字都带口径引用：DistServe 的 7.4×/12.6× 是「多种模型与应用下、90% 以上请求满足 TTFT/TPOT 约束」的对比结果；Sarathi-Serve 的 2.6×/3.7×/5.6× 是尾部延迟约束下的服务容量，硬件分别是单 A100、双 A100、配流水并行的 Falcon-180B；Mooncake 的 75% 是真实负载、525% 是模拟场景；SGLang 的 6.4× 是多类负载上的最好结果；vLLM 的 2–4× 与「序列越长、模型越大收益越明显」都是 PagedAttention 论文（SOSP 2023）摘要里「与 FasterTransformer、Orca 相比、同等延迟下吞吐」的口径，本页通过 [[inference-serving-02]] 引用该文（它不在本页参考源清单里）。第 3、5 节的节点数、PB 与美元数字都是按本节声明的假设自行推导的，不属于任何论文结论。

## 常见追问

- **追问**：为什么不直接堆 GPU？
  - 要点：堆卡只解决算力总量，不解决三个结构性浪费。① 单请求 decode 是带宽受限的：不管加多少卡，产出一个 token 都得把整份权重读一遍（TP 只是把它拆到多张卡上，聚合字节数不变），只有 batch 能让这次读取摊到多条请求上（[[inference-serving-09]]）；② KV 碎片让显存利用率可能只有一半，paged KV 把同延迟下的吞吐提高 2–4 倍，等于把卡数减半；③ 峰值倍数是 5 倍，按峰值买卡意味着 79% 的时间在浪费。先做调度与缓存，再加卡——顺序反了，成本曲线是指数的。
- **追问**：峰值流量怎么处理，难道按峰值配？
  - 要点：配「峰值的一部分 + 弹性 + 排队 + 降级」。给出三层：基线容量按日均的 1.5 倍常驻；弹性容量按预测曲线提前 15 分钟扩容（模型加载与 CUDA graph 捕获要几分钟到十几分钟，做不到秒级弹性）；超出部分进优先级队列并按降级阶梯处理。关键指标是「拒绝率」而不是「排队长度」——排队 30 秒后的超时比立刻拒绝更贵。
- **追问**：自建和外部 API 怎么混？
  - 要点：把 gateway 做成统一入口后，自建池与外部 API 池是同一层的两个后端（[[system-design-09]]、[[inference-serving-11]]）。分工规则通常是：稳态基础流量自建（边际成本最低）、突发与长尾模型走外部 API（省采购周期与闲置）、对延迟或数据驻留有硬要求的走自建。要显式管理三件事——两边的 token 计费口径不同、两边的 prompt 缓存语义不同、降级时把流量切过去要预留对方配额。
- **追问**：前缀缓存听起来是白捡的，有什么代价？
  - 要点：三个代价。① 失效管理：系统提示或工具定义一改，全量缓存同时失效，会瞬间产生 prefill 洪峰，所以缓存要版本化并且改版要灰度；② 命中判定必须精确到 token，差一个 token 就不能复用，因此 prompt 模板要避免把时间戳、随机 id 放在前缀里；③ 长会话里用户历史的前缀在每轮都会变化，缓存收益随轮次衰减，需要显式设计「共享前缀 + 会话级回退到摘要」的两级结构（[[inference-serving-05]]、[[agents-07]]）。
- **追问**：MFU 你取 0.40，依据是什么？
  - 要点：0.40 是端到端 MFU 的保守取值，与仓库其它专题（[[inference-serving-09]]）一致。注意区分两个口径：仓库其它专题引用的 Prefill vs Decode 源文说「大 prompt 下数学单元忙着 90% 上下、decode 只有 20–40%」，那是算力单元的瞬时占用率；端到端 MFU 还要扣掉 kernel 间隙、集合通信、attention 的读写与调度空泡，两者不是一回事。把 MFU 从 0.40 改成 0.45，prefill 时间从 53.7 ms 降到 47.7 ms、prefill 节点从 5,368 降到 4,772——**结论的量级不变，这也说明容量结论对 MFU 不敏感，对流量假设敏感**。
- **追问**：这题最常见的运维事故是什么？
  - 要点：相关性故障。三个典型场景：所有客户端在整点同时刷新导致流量脉冲、缓存 TTL 对齐导致同一秒集体失效、灰度期间新旧模型共享同一个前缀缓存导致 KV 布局不兼容。解法分别是加抖动、把 TTL 随机化、按模型版本隔离缓存命名空间。

## 公司变体

- **Anthropic**：安全与可靠性优先的视角。这家公开强调 RLHF/Constitutional AI 与「helpful, honest, harmless」的取舍，也公开过推理侧的分层与 scaling 讨论，因此这道题在它语境里常被追问「护栏放在链路的哪一跳、流式输出如何做逐 chunk 判定、过载时 fail-open 还是 fail-closed」，容量账是前提而不是重点。
- **OpenAI**：产品与平台双视角，偏工程。公开材料里有大量关于流式、模型路由、用量分层的讨论，所以追问集中在「免费与付费如何隔离」「多模型路由与降级」「单位 token 成本怎么压」，通常要求候选人从真实的请求分布出发给容量数字。
- **Google DeepMind 与 Google AI**：偏系统与硬件协同。这条线的公开工作（PaLM 推理的解析模型与多维切分、TPU 上的服务栈）把「用什么并行策略、MFU 能到多少、attention 的内存流量怎么省」当成一等公民，因此容量账会被要求给到 kernel 级别；系统设计轮通常与推理优化轮合并考核。
- **Meta**：偏规模化基础设施与开源生态。公开的 Llama 系列与推理栈工作让「自研 vs 开源引擎」「单个集群的规模与故障域」「多租户配额」成为高频话题，容量题常以「给定集群规模能服务多少 DAU」的反向形式出现。
- **xAI**：偏集群工程与交付速度。公开信息围绕大规模 GPU 集群的快速建设与训练/推理混部，因此这题容易被引向「集群互联与放置」「推理与训练如何共享资源」「在硬件到货节奏受限时如何排优先级」。

以上是根据各家公开技术材料与岗位方向的侧重判断，具体题目以实际面试轮次为准。

7. [Efficiently Scaling Transformer Inference](https://arxiv.org/abs/2211.05102)（延伸），Pope et al.（Google），2022-11-09。第 4 节的解析模型选多维切分、int8 权重量化下低 batch 29 ms/token、大 batch 76% MFU、多查询注意力使上下文长度可扩大 32 倍，均取自摘要（口径为 500B+ 参数模型上的 Pareto 前沿、PaLM 540B、2048 token 上下文、TPU v4）。
8. [FlashAttention: Fast and Memory-Efficient Exact Attention with IO-Awareness](https://arxiv.org/abs/2205.14135)（延伸），Dao et al.，NeurIPS 2022，2022-05-27。第 4 节采用的「IO 感知分块减少 HBM 读写」取自摘要；摘要的原话是 exact attention 用 tiling 减少 HBM 与 SRAM 之间的读写，「不减少 FLOPs」是 exact 的直接推论（标题即 Exact Attention），不是摘要里的原话。
