## 一句话答案

> 这题是两笔账。**容量账**：1000 万篇 × 20 页 × 500 token = $10^{11}$ token，按 400 token 切块（10% overlap）约 $2.8\times10^8$ 个 chunk，768 维 fp16 是 384 GB 裸向量；加上 HNSW 图边、chunk id、BM25 倒排、元数据与 ACL 位图，单份常驻约 616 GB——这个数字直接否掉"一台机器一套内存索引"，并倒推出分片方式与索引形态。**权限账**：ACL 必须在召回阶段以 pre-filter 下推，取回 top-$k$ 再过滤在可见比例 $f=1\%$ 时 recall@10 只有 0.1，补偿倍数是 $1/f$。
> 链路走「连接器 + 解析切块 + hybrid 召回（BM25 + 稠密，RRF 融合）+ cross-encoder 重排 + 带引用生成 + 输出侧白名单校验」，权限用索引期物化、检索期强制、生成期校验三层强制。可承诺的三个数字：TTFT p95 ≤ 2 s、端到端 p95 ≤ 8 s、权限变更最坏生效 p99 ≤ 60 s（紧急撤回 ≤ 5 s）。

## 面试官在考什么

- **先澄清再画图**：文档量、页数、token 数、日增量、用户与并发、TTFT/E2E 的 SLO、权限模型（文档级 ACL / 组继承 / 多租户）、必须支持的能力（引用、拒答、审计）——这些没写在明面上，后面所有算账都是空中楼阁。第一句话就画架构框图的候选人，通常也算不出容量。
- **容量账能不能算**：chunk 数、向量字节数、索引内存、倒排规模、元数据与 ACL 的开销，以及"这些数字为什么决定索引选型与分片"。
- **权限下推是否成为直觉**：说不清"为什么不能后过滤"、给不出 $f$ 与补偿倍数的量化关系，这题的核心就不及格。
- **时效承诺是否敢写数字**：权限撤销"最坏多久生效"必须是一个能写进 SLA 的数，而不是"很快"。
- **成本与评测的闭环**：成本大头落在哪一段（多半答成存储或 embedding，实际是生成）、评测集怎么分层、权限与注入为什么进红线集、灰度怎么扩量。

常见错误答案：

- "先取 top-k，再按 ACL 过滤一下"，或者"把用户组写进 filter 参数但把候选深度保持不变"。前者在 $f$ 很小时召回塌陷且越权文本已经进过 reranker、prompt 与日志；后者只是把过滤换了个写法，没有补偿候选深度。
- 把权限判定交给模型："在 system prompt 里说明只能引用该用户有权限的文档"。模型是概率组件，且可被文档内容注入，授权判定必须由可审计的代码在检索层完成；同时漏掉权限缓存与结果缓存的 TTL，会让"已撤销"的文档继续出现在答案里。

## 原理与推导

### 1. 需求澄清与假设（后续算账全部基于此表）

| 维度 | 明面假设 | 对设计的影响 |
| --- | --- | --- |
| 语料 | 1000 万篇，平均 20 页、500 token/页，共 $10^{11}$ token | 决定 chunk 数、向量量、embedding 算力 |
| 文档形态 | 70% 数字原生（约 80 KB/页）、30% 扫描件（约 400 KB/页） | 需要 OCR 支线；原始存储 35.2 TB |
| 增量 | 每天新增/修改 20 万篇（2%），删除 1 万篇 | 决定增量管道与日成本 |
| 用户 | 5 万员工，峰值并发 500，峰值 50 QPS，日均 25 万次查询 | 决定副本数与 p95 容量 |
| SLO | TTFT p95 ≤ 2 s、端到端 p95 ≤ 8 s、检索 recall@100 ≥ 0.90 | 决定重排候选数与上下文条数预算 |
| 权限 | 文档级 ACL + 组继承；100 个租户、每租户约 50 个组；每文档平均属 3 个组 | 决定 ACL 表示与过滤下推方式 |
| 能力 | 引用可回溯到 span、无答案明确拒答、全量审计 | 决定输出侧校验与日志口径 |
| 不可妥协 | 跨租户与越权内容零泄露 | 决定三层强制点与红线集 |

### 2. 容量与索引规模：数字先于架构

chunk 数按 $N_c = \dfrac{10^7 \times 20 \times 500}{400} = 2.5\times10^8$ 计；把 10% overlap 算进去，步长是 $400\times0.9=360$，$N_c = 10^{11}/360 = 2.78\times10^8$，比不扣 overlap 的粗算高 11.1%。后续用 $2.5\times10^8$ 作为记账基准，并在需要时乘以 1.11 的修正。

索引内存的来源逐项可加：

$$\text{bytes/chunk} = \underbrace{2d}_{\text{fp16 向量}} + \underbrace{8M}_{\text{HNSW 第 0 层边}} + \underbrace{8}_{\text{id}} + \underbrace{256}_{\text{元数据}}, \qquad d=768$$

$M=32$ 时每 chunk 为 $1536+256+8+256=2056$ B，$2.5\times10^8$ 条即 **514 GB**；其中向量 384 GB、图边 64 GB、id 2 GB、元数据 64 GB。再加 BM25 倒排（按原文文本体积的 0.25 倍计，约 100 GB）与 ACL 位图（每租户 50 组 × 该租户 250 万 chunk / 8 bit ≈ 15.6 MB，100 个租户合计 1.6 GB），总量 **616 GB**。结论有三条：① 单机 768 GB 勉强放一份，但副本、重建的蓝绿双份、以及查询期的临时内存都放不下，必须分片；② 分片键选租户（后文解释权限原因），每片 250 万 chunk 约 5 GB，反而小到可以整片驻留；③ 想要单机省内存就得换索引形态：IVF-PQ 把 $m=96$ 的码压到 $96+8=104$ B/chunk，全场只要 **26 GB**，代价是量化误差吃 recall，必须过采样后回表重排。

ACL 的表示方式也被这个账约束：如果按 chunk 内联 500 个组标识（跨部门共享文档的最坏情形）就是 $500\times8=4000$ B/chunk，$2.5\times10^8$ 条合计 1000 GB（1 TB），直接不可行；语料共 5000 个组（$100\times50$），全库稠密位图是 $5000\times2.5\times10^8/8$ bit = 156 GB，所以位图也必须按租户切分到 100 片（每片 1.6 GB）。可行形态是"每 chunk 内联 3 个组 = 24 B"配合"组 → chunk 位图"做粗筛。

### 3. 权限隔离：过滤必须发生在召回阶段

**三层强制点。** 索引期把文档 ACL 物化进 chunk 元数据（连同 `acl_version`）；检索期把 ACL 作为可过滤字段注入 ANN 搜索与 postings 过滤，过滤在候选生成内部生效；生成期只允许已授权 span 进入上下文，并在输出后按引用白名单复核。任何一层缺失都会留下不同的漏洞面。

**为什么不能后过滤。** 记用户可见比例为 $f$（授权集合大小 / 语料大小）、ANN 或 BM25 返回候选数为 $K$、需要的上下文条数为 $m$。权限与相关性近似独立时：

$$E[\text{可返回条数}] = fK, \qquad \text{recall@}m \approx \min\!\left(1, \frac{fK}{m}\right), \qquad K \ge \frac{m}{f}$$

$f=1\%$、$K=100$、$m=10$ 时 recall@10 只有 0.1；要拿满 10 条必须把 $K$ 开到 $m/f = 1000$，而重排 1000 对 (query, chunk) 的开销是 100 对的 10 倍——按这里的口径就是 320 ms 而不是 32 ms，这还没算 HNSW 图遍历被过滤条件打断的额外损失（链到 [[rag-09]] 的过滤与多租户一段）。

**权限模型。** 文档级 ACL 为真值来源；组是继承层，用户 → 组的展开（含嵌套组）要递归求解并缓存成位图或倒排集合；`acl_version` 随目录事件（SCIM / webhook）自增。查询期只做一次集合运算：把"用户有效主体集合"翻译成过滤条件，与租户条件一起下推。Elasticsearch 的 document-level security 是这条路线的现成参照：角色里用 Query DSL 声明可见文档，并支持把当前用户注入角色查询（`{{_user.username}}`、`{{_user.metadata.group_id}}`），即把 ACL 表达成查询期过滤条件而不是结果集上的后置判断。它同时给出了两条必须抄进设计说明的边界：① 文档级安全只作用于读 API，不作用于写 API，所以写入路径要另做鉴权；② 它挡不住聚合泄露——用户仍可能得知只存在于无权文档中的字段名与词项，并数出无权文档的条数，因此面向用户的接口要关掉自由聚合与词项枚举。

**多租户：共享索引 + 强制过滤 vs 按租户分区。** 取舍不是"哪个更安全"，而是"隔离强度与运维成本换到哪一档"：

| 方案 | 隔离强度 | 过滤性能 | 运维成本 | 适用 |
| --- | --- | --- | --- | --- |
| 共享索引 + 强制 pre-filter | 依赖过滤实现正确性，单点错误影响全体 | 过滤选择率低时 HNSW 遍历受损，需要过滤感知的遍历或位图跳过 | 一套索引、一套升级、成本最低 | 租户数多、单租户语料小、接受软隔离 |
| 按租户分区索引 | 物理隔离，越权要靠跨分区 bug 才会发生 | 分区内无过滤开销，小分区可以 flat | 100 套索引的副本与重建放大，跨租户查询要 fan-out | 强合规租户、租户语料足够大 |
| 混合 | 大租户独立分区，长尾共享 | 各自最优 | 两套机制并存 | 现实中常见 |

分片键与租户对齐是这套账里最省事的一步：分区后单租户索引只有 $2.5\times10^6$ 条、约 5 GB，可以整片常驻，权限过滤退化成"选对分区"，同时天然获得租户级的限流与审计边界。

**权限变更时效。** 最坏暴露窗口是两项之和：

$$T_{\text{expose}} = T_{\text{index lag}} + T_{\text{cache TTL}}$$

把 ACL 物化延迟定在 30 s（目录事件 → 连接器 → 更新 chunk 元数据）、授权缓存 TTL 定在 30 s，可承诺 p99 ≤ 60 s；对"立即撤回"这类紧急操作走事件强制失效 + 查询期拒绝优先（以源系统实时校验兜底），压到 ≤ 5 s。缓存键必须含 `acl_version` 与 `index_version`，否则结果缓存会让旧权限继续生效到自然过期。

### 4. 检索链路与每一段的选择

```text
query → 网关(身份/租户) → 权限服务(有效主体集合 + acl_version)
      → 改写/HyDE → ┬ BM25 top-100   ┐
                    └ ANN  top-100   ┴→ RRF(k=60) → cross-encoder 重排 100→10
      → 上下文组装(去重/按来源分组/4k token 预算) → 生成(带引用) → 输出校验(引用白名单 + 越权拦截)
```

- **查询理解**：多轮对话里的指代与省略必须改写，否则 BM25 那一路基本废掉；HyDE 对"用户不知道用什么词描述"的场景收益最大，代价是多一次生成（链到 [[rag-05]]）。
- **hybrid 召回**：BM25 与稠密各取 100，用 RRF($k=60$) 融合。融合用排名而不是分数，避免两路分数量纲不可比；$k=60$ 时"两榜都靠前"比"单榜第一"更值钱（链到 [[rag-02]]）。
- **重排**：cross-encoder 把 100 对压到 10，是精度提升最明显的一段，代价是 100 次前向（表 4 里 32 ms）——这也是候选深度不能无限放大的原因（链到 [[rag-03]]）。
- **上下文组装**：按来源去重（同一文档相邻 chunk 合并）、同文档限流、按引用友好排序；预算固定 4k token，超出按"每来源至少保留一段 + 其余按重排分"裁剪，避免长文档挤掉所有其他来源。
- **生成与输出校验**：要求逐句带引用 id；输出后校验引用 id 必须落在本次授权的 span 集合内，并做越权词项兜底拦截。生成侧永远是软约束，硬边界在检索层（链到 [[rag-12]]、[[safety-01]]）。

**全局性问题**（"这一季度所有合同的风险点"）纯检索答不了：它本质是 query-focused summarization，不是显式检索任务。可选增强是 GraphRAG 的做法——用 LLM 分两阶段建图索引（先从源文档抽实体知识图谱，再为紧密相关实体群预生成社区摘要），回答时由每个社区摘要生成部分回答、再汇总成最终回答；论文在 100 万 token 量级数据集的一类全局 sensemaking 问题上，相对常规 RAG 基线在回答的 comprehensiveness 与 diversity 上有显著改进。这条路径按语料子集（合同、政策、复盘）离线构建，不覆盖全量语料，也不用于事实型查询。

**无答案时拒答**：检索层用分数阈值与"最优命中与次优命中的间隔"双条件触发，生成层要求"证据不足就直说"，并把拒答率与误拒率一起纳入评测——接地失败的度量口径见 [[evaluation-03]]。

### 5. 新鲜度、版本与运维

- **增量写入**：连接器做 chunk 级 diff，只重嵌变化的 chunk；删除先写 tombstone 立即在过滤层生效，再靠后台压实回收向量与图边（长期不压实会让 recall 静默下滑，链到 [[rag-11]]）。
- **版本绑定**：索引元数据记录 `(model_id, dim, normalize, chunker_version)`。换 embedding 模型不能"打补丁"，必须整索引重建 + 别名原子切换，否则同一 query 会在两套语义空间里各召回一半。重嵌入的触发条件写死：模型换代、切块策略改版、维度变更、语料分布漂移超过阈值。
- **权限与内容解耦**：ACL 走独立快通道更新，不等重嵌入；权限字段与内容字段分版本号，避免"改了权限就得重建整个索引"。
- **蓝绿与成本**：重建期间要同时容纳两份索引（$616\times2$），分片滚动切换可以避免整机房翻倍。

### 6. 评测、红线与上线

成功指标分四层：检索层 recall@100 / nDCG@10；生成层接地率与引用准确率；任务层成功率与人工采纳率；安全层权限零越权、注入零成功。评测集 100–500 条分层构造——事实型 40%、多跳 20%、全局性 15%、无答案 15%、权限 10%——权限与注入用例作为**红线集**进回归门禁，一票否决且不可与其他指标加权（口径与统计判定见 [[evaluation-04]]，分层构造见 [[evaluation-02]]）。注意红线集的正确表述：$n$ 条全过只能说违规率上界约 $3/n$，300 条全过对应"不高于约 1%"，不能宣称是 0。

上线按影子流量 → 内部 5% → 按租户灰度扩量，每一档都带权限用例的在线抽检；容量按峰值 50 QPS 与 p95 SLO 压测，网关侧的配额与限流见 [[system-design-09]]，多租户服务栈的容量取舍见 [[system-design-10]]。

| 全量回填 embedding | $10^{11}\times2.2\times10^8$ FLOPs @35% MFU | 17.7 GPU-h（一次性） |
| 每日增量 embedding（20 万篇 = $2\times10^9$ token ≈ 556 万 chunk） | 同上 @10% MFU（小批量效率低） | 1.24 GPU-h/天 |
| 重排 | $9.50\times10^{12}$ FLOPs/query × 25 万 @30% | 2.2 GPU-h/天 |
| prefill | $6.3\times10^{14}$ FLOPs/query × 25 万 @8×H100 45% | 98.3 GPU-h/天 |
| decode $b=32$ | 日解码 $10^8$ token（25 万 × 400）；每步每卡读权重 17.5 GB + KV 5.9 GB，3.35 TB/s、70% 带宽 | 69.3 GPU-h/天 |
| decode $b=96$ | 同上，权重被摊薄 | 34.7 GPU-h/天 |
| 合计 | 生成占 GPU 时间的 167.6/171.0 | 171 GPU-h/天 ≈ 5,132 GPU-h/月 ≈ 21,970 美元/月 |
| 索引内存 | 两副本 1.23 TB（24 × 64 GB 节点，0.25 美元/节点-小时 示意价） | 4,380 美元/月 |
| 对象存储 | 36.2 TB（原始 35.2 TB + 解析产物约 1 TB）× 0.023 美元/GB-月 | 833 美元/月 |
| 每查询 GPU 成本 | 171 × 4.28 / 25 万 | 约 0.0029 美元 |

结论与直觉相反：**月成本的大头是 GPU 时间（21,970/27,183 ≈ 81%），而 GPU 时间里生成占 98%，对象存储只占 3%**；全量回填 embedding 只要 17.7 GPU-h。降本顺序因此是"减上下文条数（10 → 6 条把 prompt 从 4.5k 压到 2.9k，prefill 省 36%）→ 小模型路由 + 结果缓存 → 提高 decode batch 把权重读取摊薄"，而不是先优化索引。

```python
# 复算：chunk 数、内存、decode 成本、post-filter 塌陷
TOK = 10_000_000 * 20 * 500          # 10^11
chunks = TOK / 400                   # 2.5e8（记账口径）
chunks_ov = TOK / (400 * 0.9)        # 2.78e8（含 10% overlap）
vec = chunks * 768 * 2 / 1e9         # 384 GB
hnsw = chunks * (768 * 2 + 8 * 32 + 8) / 1e9   # 450 GB
total = hnsw + 0.25 * (TOK * 4 / 1e9) + chunks * 256 / 1e9 + 1.6
print(chunks, round(chunks_ov / 1e8, 2), vec, hnsw, round(total))

# decode：每步每卡读权重 + KV，批量越大摊得越薄；ETA 是有效带宽占比
W, kv, BW, ETA = 140e9, 327_680, 3.35e12, 0.7
for b in (32, 96):
    step = (W / 8 + b * 4500 * kv / 8) / BW      # 理论读一遍的耗时
    tok_cost = 8 * (step / ETA) / b              # GPU-s/token
    print(b, round(step * 1e3, 2), round(tok_cost * 1e8 / 3600, 1))   # GPU-h/天

# post-filter 的期望返回条数与 recall 上界
for f in (1.0, 0.1, 0.01, 0.001):
    print(f, min(1, f * 100 / 10), 10 / f)
```

解码为什么是带宽受限而非算力受限可以一句话说清：单个 token 的权重读取是 140 GB，算力是 $2\times70\text{e}9=1.4\times10^{11}$ FLOPs，算术强度约 1 FLOP/B；$b=96$ 时权重加 KV 共 282 GB、FLOPs 涨到 $1.34\times10^{13}$，强度也只有 47.7 FLOP/B，仍远低于 H100 的脊点 295 FLOPs/byte——所以 decode 只能靠 batching 摊薄权重读取，这也解释了表 5 里 $b=32$ 与 $b=96$ 成本差 2 倍。

数据与口径的不确定性：PDF 单页体积、原文文本 0.25 倍的倒排膨胀比、0.25 美元/节点-小时 的内存节点价与 0.023 美元/GB-月 的对象存储价、25,000 美元/月 的节点摊销价都是**便于复算的示意假设**，不是外部报价；GPU 与内存单价换成自建或包年口径会整体平移，但"生成占大头、索引内存次之、存储最少"的排序不变。

## 常见追问

- **追问**：1000 万文档一定要向量检索吗？关键词够不够？
  - 要点：不够，但也不能只靠稠密。语料里 ID、错误码、型号、合同编号这类精确串只有 BM25 靠得住，语义改写与跨语言查询只有稠密靠得住，两类失败在真实流量里同时存在，所以默认 hybrid + RRF（[[rag-02]]）。向量这一路的代价就是表 1、表 2 里的 384 GB 与 616 GB；如果预算不够，先做的是分层与量化，而不是砍掉一路召回。
- **追问**：多租户共享索引的过滤性能怎么保证？
  - 要点：三件事——过滤条件在召回复用同一份（BM25 与 ANN 都要注入，最典型的事故是漏掉一路）；候选深度按 $1/f$ 补偿并接受成本，或改用过滤感知的图遍历 / IVF 位图跳过；分片键与租户对齐，让过滤退化成"选对分区"。用表 3 说明不补偿的后果。
- **追问**：权限变更延迟怎么压到秒级？
  - 要点：把 ACL 变成独立快通道——目录事件驱动、只更新 chunk 的 ACL 字段不重嵌内容；缓存键含 `acl_version` 并对撤销事件强制失效；紧急撤回走查询期实时校验 + 拒绝优先。可承诺的数：常规 p99 ≤ 60 s（30 + 30），紧急 ≤ 5 s（$T_{\text{expose}}$ 公式）。
- **追问**：成本大头在哪一段？怎么降？
  - 要点：表 5 里 GPU 时间占月成本约 81%，其中生成（prefill + decode）占 GPU 时间的 98%；降本顺序是减上下文条数、小模型路由与结果缓存、提高 decode batch，最后才是索引侧（PQ 把 616 GB 压到 26 GB 省的是内存，不是这条账的大头）。
- **追问**：全量重建和重嵌入什么时候必须做？
  - 要点：换 embedding 模型、改切块策略、改维度、语料分布显著漂移时必须整索引重建 + 别名切换，因为混版向量会让同一 query 落在两套语义空间；重建成本是 17.7 GPU-h 算力 + 两份 616 GB 的内存窗口。
- **追问**：无答案时怎么做到不编？
  - 要点：检索层用分数阈值 + 最优/次优间隔触发拒答，生成层允许并奖励"证据不足"，评测里把拒答率与误拒率分开统计；接地失败的度量口径见 [[evaluation-03]]。

## 公司变体

以下取向依据各家公开产品与文档形态，不涉及具体面试原题。

- **OpenAI**：偏端到端产品形态与评测驱动。公开的检索工具形态是"按存储单元隔离 + 元数据属性过滤 + 引用回传"，所以追问通常落在无答案拒答怎么评、成本与延迟预算怎么定、权限边界放在平台层还是应用层。
- **Microsoft**：偏企业检索的合规落地。权限真值来自协作平台的 ACL 继承、共享链接、组嵌套与外部访客，重点是连接器侧 ACL 同步与"权限变更事件驱动索引更新"，会追问最坏暴露窗口与审计口径（与 [[rag-08]] 同一取向）。
- **Amazon（AWS）**：偏托管服务拼装与多租户运维——对象存储 + 向量库 + 托管模型，按租户做资源隔离、配额、备份与可用区；最可能问"共享索引还是每租户一套"的实际运维与成本差，以及容量与 SLO 怎么用压测证明。
- **Databricks**：偏"权限就是数据平台的元数据"。数据目录侧的细粒度权限（行过滤、列脱敏、血缘）是现成参照，问题会往"把 ACL 建模成 catalog 元数据 + 在查询计划里尽早下推过滤条件"的方向走，也就是前述的 pre-filter 思路。
- **Scale AI**：偏数据与评测管线出身。更关注评测集怎么分层构造、标注口径与一致性怎么控、人工复核与质量 SLA 怎么度量，而不是索引内部结构；准备时要把评测集规模、红线集判定与接地度量讲实。
