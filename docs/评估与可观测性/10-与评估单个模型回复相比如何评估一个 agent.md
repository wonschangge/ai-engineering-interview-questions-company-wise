## 一句话答案

> 评估对象变了：单条回复评的是「一个输入到输出的映射」，agent 评的是「一条轨迹的分布 + 环境终态」。指标要分三层——结果层（任务成功率、pass^k、终态校验）、过程层（步数分布、工具选择与参数正确率、政策遵循、轨迹可回放）、成本层（token、墙钟、工具调用、人工介入率）。
> 两个关键推论：**结果对不等于过程对**（可能靠试错撞对，也可能靠硬编码绕过判定），**单次成功率不是可靠指标**（同一任务多次运行结果不同）。τ-bench 的例子最直接：gpt-4o 这类 function calling agent 在零售域 pass^1 是 61.2%、航空域 35.2%，而零售域 pass^8 掉到 25% 以下。
> 判定方式也要换：不看 agent 说了什么，看它把环境改成了什么样——对话结束后比对数据库终态与标注目标状态。

## 面试官在考什么

- **是否理解评估对象变了**：从「打分一个输出」变成「打分一条轨迹与环境终态」，并能说清「结果对但过程错」与「过程对但结果错」两类样本各自怎么处理——前者决定评测能不能防作弊，后者决定失败归因会不会冤枉模型。
- **有没有把非确定性当一等公民**：同任务重复 $k$ 次、报 pass^k 而不是单次成功率、知道 pass^k 与 pass@k 方向相反、知道 pass^k 不能拆成 $(\text{pass}^1)^k$。
- **判定层级的设计能力**：优先用终态比对、测试通过、schema 校验这类可执行判定；rubric 与 LLM judge 只做兜底，且要先与人类标注对齐（[[evaluation-01]]）。
- **过程层与成本层指标是否齐**：只报成功率的答案既解释不了「为什么失败」，也回答不了生产上真正关心的成本与延迟。
- **评测工程直觉**：环境可重置、依赖与种子固定、任务与测试隔离、隐藏测试集、抽样与早停、失败轨迹进回归门禁（[[evaluation-04]]）。

常见错误答案：

- 把单轮 LLM 的套路直接搬过来：给最终答案打 1–5 分，或用文本相似度比对回复。这类做法会把「过程全错但结论碰巧对」和「答案对但违反政策」都判成成功。
- 只报一次运行的成功率，或者要求轨迹与某条参考轨迹 exact match。前者不可复现；后者把多解任务（同一个终态有多条合法路径）误判成失败。

## 原理与推导

### 1. 评估对象：从一次映射到一条轨迹加一个终态

单轮回复的评估可以写成 $f_\theta: x \mapsto y$，指标是 $S(y, y^*)$ 或者 judge 给的偏好分。agent 不是这个结构：它在环境 $\mathcal{E} = (\mathcal{S}, \mathcal{A}, T)$ 上按策略 $\pi$ 展开一条轨迹

$$\tau = (s_0, a_0, o_0, s_1, a_1, o_1, \dots, s_T)$$

其中动作 $a_t$ 包括工具调用、对用户的追问、写类副作用，$s_T$ 是环境终态。要评的量因此是

$$\mathbb{E}_{\tau \sim \pi}\big[\, r_{\text{action}}(s_T, s^*) \cdot r_{\text{output}}(s_T, \text{reply}) \,\big]$$

期望作用在整条轨迹上。τ-bench 的奖励就是这个形式：$r_{\text{action}}$ 判对话结束时的数据库状态是否等于标注的目标状态，$r_{\text{output}}$ 判回复里有没有把必要信息说全，两者相乘——终态改对了但没告诉用户也算失败。

这个形式化直接推出三个与单轮评估不同的地方：

1. **多解**：到达同一终态可以有很多条合法轨迹，所以不能拿轨迹与一条参考答案做 exact match。
2. **同策略多结果**：同一任务跑两次可能一次成功一次失败，单次运行不构成对能力的估计。
3. **长度与成本可变**：轨迹长度 $T$ 本身是策略的输出，成本随 $T$ 增长，因此成本是评估指标而不是运维细节。

### 2. 结果对不等于过程对：四象限

| 过程 | 结果 | 典型成因 | 处置 |
| --- | --- | --- | --- |
| 对 | 对 | 真的会做 | 正样本，进能力回归集 |
| 错 | 对 | 试错撞对、硬编码绕过、读到测试或答案文件 | 最危险的一格：靠过程指标与对抗变体抓（换参数、换同义表述重跑） |
| 对 | 错 | 环境抖动、工具超时、判定过严、最后一步漏说信息 | 归因到环境或判定，不要记成模型能力问题 |
| 错 | 错 | 常规失败 | 分类后转回归用例 |

只报结果指标，第二行会被当成好样本，模型迭代会朝「更容易碰巧成功」的方向走；只报过程指标，第三行会被误判成能力缺陷。两者必须同时存在。

### 3. 非确定性：pass^k 才是一致性口径

非确定性的来源至少有五处：采样温度、用户模拟器的随机性（τ-bench 把 agent 温度设为 0.0、用户模拟设为 1.0，主结果仍然每任务至少跑 3 次试验）、工具与外部世界的随机性、超时与并发调度、上下文组装顺序。

pass^k 的定义是「同一任务 $k$ 次独立试验全部成功」在任务上的平均。若某任务跑 $n$ 次成功 $c$ 次，无偏估计量是

$$\hat{\text{pass}}^k = \mathbb{E}_{\text{task}}\left[\binom{c}{k} \middle/ \binom{n}{k}\right], \qquad \hat{\text{pass}}@k = 1 - \mathbb{E}_{\text{task}}\left[\binom{n-c}{k} \middle/ \binom{n}{k}\right]$$

两个指标方向相反：pass@k 随 $k$ 上升（至少一次成功，衡量探索上限），pass^k 随 $k$ 下降（每次都成功，衡量可交付的一致性）。面向用户的上线门槛看 pass^k，离线挖能力看 pass@k。

容易犯的另一个错是把 pass^k 近似成 $(\text{pass}^1)^k$。任务异质性使 $\mathbb{E}[p^k] \ge (\mathbb{E}p)^k$（Jensen 不等式），第 4 节的数值例子里 $k=8$ 时相差 7 倍，这个近似会系统性低估一致性；但 pass^k 随 $k$ 单调下降的性质不变，当门槛依然成立。

平均值还有一层掩盖：$\mathbb{E}[c/n]$ 相同的两组任务，「所有任务都 60% 成功」与「一半任务 100%、一半任务 20%」是完全不同的产品，后者有一半场景对用户随机不可用。

### 4. 判定层级：能验终态就不要验文本

按可复现性与抗绕过能力从高到低：

1. **环境终态比对**：数据库、文件系统、外部系统的资源状态。τ-bench 的 $r_{\text{action}}$ 就是这个口径——比的是数据库终态，agent 怎么描述自己做过什么不影响它（$r_{\text{output}}$ 只额外要求把必要信息告知用户）。
2. **可执行断言**：测试通过、编译通过、类型与 schema 校验。SWE-bench 的方法论就是把 issue 对应 PR 的测试当判定——补丁必须让目标测试由失败转为通过，同时不破坏已有测试。
3. **结构化约束检查**：工具参数是否合法、动作是否在政策允许范围内、有没有调用不存在的工具。τ-bench 只把一部分政策做成了 API 层拦截（例如用错 payment id 直接报错），论文明确说明满分不保证政策遵循（未经用户确认就下单也可能 $r=1$），所以规则遵循要单独建检查项。
4. **rubric 与 LLM judge**：只在没有客观判定时使用，且要先与人类标注对齐、量化偏差（[[evaluation-01]]）。
5. **人工抽查**：每周过一小批轨迹做校准，成本高，不能作为主判定。

排序理由很实际：判定越靠前越难被绕过。把 judge 放最前面最典型的失效是「话术漂亮但事情没做」——轨迹里一次写操作都没有，最终回复却描述得头头是道。

### 5. 三层指标体系

| 层 | 指标 | 备注 |
| --- | --- | --- |
| 结果层 | 任务成功率（pass^1）、pass^k、终态校验通过率、部分完成率 | 终态口径优先；pass^k 进上线门槛 |
| 过程层 | 步数分布（p50/p95/p99）、工具选择正确率、参数正确率、无效或重复动作比例、政策遵循率、工具失败后的恢复率、过早终止率 | 用来解释失败与防作弊，也是轨迹回放的检查表 |
| 成本层 | 每任务 token、每任务美元、墙钟时长、工具调用次数、人工介入率 | agent 的「贵」来自多次运行乘多步，必须按任务统计 |

指标要按任务桶（类型、难度、风险等级）分层看。全局平均最典型的失效是：某类高风险任务整体崩掉，却被大量简单任务的成功率盖住。

### 6. 环境与任务：公开基准能给什么、不能给什么

| 基准 | 环境与任务 | 判定口径 | 论文自报数字 |
| --- | --- | --- | --- |
| WebArena | Docker 化的四个可运行自建站点（电商、论坛、协作开发、内容管理），812 个长程网页任务，环境可重置到确定性初始状态 | 任务执行的功能正确性 | 最佳 GPT-4 agent 端到端成功率 14.41%，人类 78.24% |
| SWE-bench | 12 个 Python 仓库的真实 issue 与对应 PR，共 2294 个任务实例，需在执行环境里跨函数、跨文件改动 | 仓库测试 | 论文当时最强的 Claude 2 只解决 1.96% |
| GAIA | 466 个需要推理、多模态、浏览与工具使用的真实问题 | 答案唯一、可精确校验 | 人类 92%，带插件的 GPT-4 15%；官方保留 300 题答案用于 leaderboard |
| τ-bench | 用户模拟器 + 领域 API + 政策文件，航空与零售两个域 | 对话结束后的数据库终态 vs 标注目标状态；pass^k 衡量一致性 | gpt-4o pass^1 零售 61.2%、航空 35.2%（按域加权 48.2%），零售 pass^8 低于 25%；单任务最多 30 个动作 |

四个基准的共同点在方法论上：**任务真实、判定客观（答案唯一，或测试与终态可验）、环境可执行**；WebArena、SWE-bench、τ-bench 这三个自建环境还都要求能重置到确定性初始状态。照这几条造自己的任务集，比抄题目有用。

局限也要说清：基准饱和（强模型分数挤在天花板，区分度消失）、真实世界差距（公开任务分布与自家产品不同）、环境漂移（外部依赖变化使历史分数不可比）、题目泄露与污染（[[evaluation-06]]）。结论是公开基准用来定位能力上限与横向对齐，产品决策靠自建任务集。

### 7. 评测工程的六个动作

1. **环境可复现**：容器化镜像、锁定依赖版本、每次运行前重置状态、固定随机种子与时间、隔离外部网络或对依赖做录制回放。
2. **评分器分层**：客观判定为主，judge 兜底；judge 的 prompt 也要纳版本管理。
3. **非确定性处理**：同任务 $k$ 次运行，报 pass^k 与分布（均值、方差、最差任务），不报单次结果。
4. **防作弊**：任务与测试隔离（agent 的运行环境里看不到测试与答案）、隐藏测试集、对同一任务做参数扰动与同义改写探测过拟合、审计轨迹里有没有读取答案文件或写入特判分支。
5. **预算控制**：评测成本约为「任务数 × 重复次数 × 单次任务成本」，用分层抽样、并行、步数上限压住；只关心 pass^k 门槛时可以早停——某任务首次失败后它对 pass^k 的贡献已经是 0。
6. **可回放**：每步记录输入、动作、观察、耗时与 token，轨迹能重放才谈得上算过程指标（[[evaluation-07]]）。

### 8. 用评测驱动迭代的闭环

- **失败分类**：按成因给失败轨迹归类，而不是按「哪个任务失败」归类。有实证口径的分类可以直接借用：MAST 从 7 个框架的 1642 条轨迹归纳出 3 类 14 种多 agent 失败模式（口径见 [[agents-06]]）；τ-bench 把失败归为三类——参数或信息填错、决策与规则遵循错误（论文标注占整体失败的 25%）、复合请求只完成一部分。两者的共同结论是失败主要出在系统设计与执行层（规格、协作、规则遵循、验证），而不是模型的知识不足。
- **转回归用例**：每个高频失败模式固化成任务 + 判定，进 [[evaluation-04]] 的门禁；门禁同时看 pass^1 与 pass^k，避免「平均值不变但一致性变差」的改动溜过去。
- **在线监控**：任务完成率、步数分布、工具错误率、人工介入率、成本分位，做长期趋势与告警（[[evaluation-09]]）。
- **轨迹诊断**：长任务还要看漂移类症状（目标遗忘、上下文污染），见 [[agents-12]]。

### pass^k 不能拆成 (pass^1)^k

取四个等权任务，单次成功率分别为 0.9 / 0.7 / 0.5 / 0.3：

| $k$ | 异质任务 $\mathbb{E}[p^k]$ | 独立同分布近似 $(\mathbb{E}p)^k$ | 倍数 |
| --- | --- | --- | --- |
| 1 | 0.600 | 0.600 | 1.0 |
| 2 | 0.410 | 0.360 | 1.1 |
| 4 | 0.242 | 0.130 | 1.9 |
| 8 | 0.123 | 0.017 | 7.3 |

$k=8$ 时两者差 7 倍：难任务恒难、易任务恒易带来的正相关把一致性抬到近似值之上。pass^k 要用真实重复试验估计，不能从 pass^1 推算；它随 $k$ 单调下降这一点不变，当门槛依然成立。

### 单次运行要多少任务才能分辨两个模型

真值 $p = 0.5$、每个任务只跑一次时，成功率估计的标准误是 $\sqrt{p(1-p)/n}$：

| 任务数 $n$ | 标准误 | 95% 置信区间半宽 |
| --- | --- | --- |
| 20 | 0.112 | ±21.9 个百分点 |
| 50 | 0.071 | ±13.9 个百分点 |
| 200 | 0.035 | ±6.9 个百分点 |
| 500 | 0.022 | ±4.4 个百分点 |

20 个任务各跑一次，区间宽度是 ±22 个百分点——两个模型差 10 个点在**单次运行**的规模上完全不可区分。要在 80% 功效、双尾 5% 下检出 10 个百分点的差距，独立设计每组约需 393 个任务。**配对设计更省**：让两个模型跑同一批任务、只比较结果不一致的任务（McNemar 思路），任务难度带来的方差被消掉，所以固定一批种子任务反复使用既省预算又提高灵敏度。

### 评测预算与早停

按 τ-bench 的口径（单次试验 0.38 + 0.23 = 0.61 美元），200 个任务跑满 8 次约为 $200 \times 8 \times 0.61 \approx 976$ 美元。

只关心 pass^k 门槛时可以提前停某个任务：某任务只要失败一次，它对 pass^k 的贡献就是 0，剩下的试验不必跑。在前面那组任务（0.9/0.7/0.5/0.3）上，$k=8$ 的期望试验次数分别是 5.70 / 3.14 / 1.99 / 1.43，平均 3.06 次，节省约 62%，同一批任务的成本从约 976 美元降到约 374 美元。pass@k 不能这样早停——它需要完整的 $n$ 次试验才能估计「至少成功一次」。

### 代码：终态校验 + pass^k 的最小评测骨架

```python
import statistics
from math import comb

def run_suite(agent, env, tasks, k, max_steps=30, gate_only_pass_k=True):
    """每个任务独立跑 k 次；每次运行前把环境重置到确定性初始状态。"""
    per_task = []
    for task in tasks:
        successes = 0
        for trial in range(k):
            env.reset(seed=task.seed + trial)        # 重置状态与随机种子
            trace = agent.run(task.instruction, env, max_steps=max_steps)
            ok = verify_final_state(env.dump_state(), task.goal_state)   # 判定看终态
            record_trace(task.id, trial, trace, env)  # 步数/token/工具调用进过程层指标
            successes += int(ok)
            if not ok and gate_only_pass_k:
                break                                 # 首次失败已使该任务的 pass^k 为 0
        per_task.append(successes)
    return per_task

def verify_final_state(actual, goal):
    """只比较任务相关的状态切片：数据库行、文件、外部资源。"""
    return all(actual[key] == value for key, value in goal.items())

def pass_hat_k(n, c_list, k):
    return statistics.mean(comb(c, k) / comb(n, k) for c in c_list)

def pass_at_k(n, c_list, k):
    return statistics.mean(1 - comb(n - c, k) / comb(n, k) for c in c_list)

# 要报 pass^1 与 pass@k，就得让每个任务跑满 k 次
c_list = run_suite(agent, env, tasks, k=8, gate_only_pass_k=False)
print("pass^1", pass_hat_k(8, c_list, 1), "pass^8", pass_hat_k(8, c_list, 8))
print("pass@8", pass_at_k(8, c_list, 8), "worst", sorted(c_list)[:5])

# 只看 pass^k 门槛时才可以早停
gated = run_suite(agent, env, tasks, k=8, gate_only_pass_k=True)
print("gate pass^8", pass_hat_k(8, gated, 8))
```

`verify_final_state` 只读环境、不读 agent 的输出，这是防作弊的关键：agent 无法通过措辞影响判定。`sorted(c_list)[:5]` 报的是最差任务而不是均值，因为一致性风险藏在尾部；`comb` 在 $k > n$ 时返回 0，两个估计量都不需要额外分支。早停只对 pass^k 有效：提前停下的任务 $c$ 不再来自 $n$ 次完整试验，$c < k$ 使 $\binom{c}{k} = 0$ 仍然成立，但 pass^1 会系统性偏低，pass@k 则完全无法估计。

## 常见追问

- **追问**：怎么评估「过程正确但结果偶然失败」？
  - 要点：先判断失败能否归因到环境（工具超时、外部数据变化、并发冲突），把这类运行单独统计成「环境性失败」而不是能力失败。做法是同一任务重跑，并把录制好的观察回放进去：回放成功而真实运行失败，问题在环境稳定性；回放也失败，才是策略问题。
- **追问**：能不能给中间步骤自动打分（过程奖励模型 PRM）？
  - 要点：可以，但它是**排序信号**而不是判决。PRM 适合在同一任务的多条轨迹之间做相对比较、给搜索提供引导；局限是标注成本高、跨域迁移差、对「看似合理但其实错」的步骤容易给高分。落地方式是 PRM 只用于采样与排序，最终判定仍用终态校验。
- **追问**：在线评估一个有真实副作用的 agent 要注意什么？
  - 要点：先在沙箱 + 假数据上跑；影子模式（只记录动作不执行）看策略；灰度时限制权限与额度；写操作要可逆或可补偿、可审计，高风险动作走人工审批（[[agents-10]]、[[agents-11]]）。线上评估不能只看成功率，还要盯不可逆副作用的次数。
- **追问**：pass^k 与 pass@k 的区别，什么时候用哪个？
  - 要点：pass@k 是 $k$ 次里至少一次成功（探索能力，用于采样与候选生成），pass^k 是 $k$ 次全部成功（一致性，用于面向用户的上线门槛）。两者在同一份试验数据上会给出相反结论，报告时不能只报一个。
- **追问**：为什么 agent 评测不能只用 LLM judge？
  - 要点：轨迹长（几十到上百步）会稀释 judge 的注意力；任务多解使 judge 缺少稳定参照；judge 对「话术好」的偏好会系统性奖励没做事但会解释的轨迹。judge 适合在客观判定缺失时兜底，且必须先在人类标注的小样本上量化一致率（[[evaluation-01]]）。
- **追问**：公开基准分数很高，能不能直接推断产品里可用？
  - 要点：不能。基准饱和会让分数失去区分度，公开任务分布与产品任务分布不同，还有污染与泄露风险（[[evaluation-06]]）。基准用来定位能力上限；产品决策要用自己采样的真实任务集，并固定成可重复的回归集。

## 公司变体

四家都在面试里问过这道题，侧重点按公开的技术风格推断（不涉及具体面试流程）：

- **Scale AI**：偏评测基础设施与数据口径。追问会落在判定本身——rubric 怎么写、judge 与人类的一致率怎么量化、任务集怎么采样才代表真实分布、污染与泄露怎么防。回答时把判定层级和「judge 先对齐再使用」讲实。
- **Moonshot AI**：偏工程落地与成本。除结果指标外，会关心轨迹可观测性、长轨迹下的上下文压缩、评测吞吐与费用，以及自建任务集如何随产品迭代维护。
- **智谱 AI**：偏原理推导与基准设计。pass^k 的统计含义、环境与任务怎么构造才既有区分度又可复现、判定为什么必须落在终态，这类「为什么」会被追问到底。
- **Cognition**：偏真实任务闭环（编码类 agent）。重点在真实仓库任务上的端到端成功率、轨迹回放与失败归因，以及评测到产品迭代的闭环：失败轨迹如何转成回归用例并进门禁。
