## 一句话答案

> 在线评估回答三件事：某个改动（prompt / 模型 / 检索 / 排序 / 工具策略）在**真实流量**上是否更好、代价多大、风险多大。用四级阶梯推进：离线回归拦明显退化 → 影子流量比对输出与开销（不影响用户）→ 小流量按用户或会话随机化的 A/B（带护栏）→ 全量放量；每一级事前写好「继续 / 停止」判据。
> 日志的验收标准是**可归因**：每条记录都要能回答「哪个版本、哪次实验、哪一个请求、用户看到什么、用户做了什么」。模型版本、prompt 版本、索引版本、策略版本必须和 experiment/variant 一起落库，缺一项就只能靠猜，见 [[evaluation-08]]。
> 采样按分层定率：错误、超时、慢请求、有显式反馈的**全采**，正常流量 1%–10%，高风险场景抬高；采样率由「要发现多小的退化」反推、由成本封顶。A/B 只用于产品与算法假设；安全、隐私与合规策略走评审与灰度发布，不拿用户做随机实验。

## 面试官在考什么

- 有没有**推进阶梯**意识：四级各自的证据要求与继续/停止判据，以及为什么不能跳过影子流量直接全量——影子能把「输出差异」和「系统开销」分开看。
- 日志 schema 的完整度：版本四元组、实验分组、召回与工具轨迹、延迟分解、隐式反馈、脱敏。要求能说到字段名，而不是「记一些埋点」。
- 采样是**算出来的**还是拍的：分层依据、采样率与最小可检测效应（MDE）及成本的关系、「质量指标必须能按版本切分」这条硬要求。
- 统计纪律：主指标与护栏、随机化单位、事前 MDE、实验时长、多重比较、分流不均（SRM）与连续窥视。
- 边界感：哪些改动不允许随机实验；隐式反馈的选择性偏差如何用抽样人工评估交叉验证。

常见错误答案：

- 「接个 A/B 平台，$p<0.05$ 就上线」。没说随机化单位、护栏指标，也没说日志里要有哪些版本字段——即使赢了也不知道为什么赢，输了也无法定位。
- 把「上线后看大盘指标涨没涨」当在线评估：没有对照组，流量结构变化、季节性与同期其它改动全混在一起，还容易演变成「多次窥视后挑显著的那一次发布」。

## 原理与推导

### 1. 四级推进阶梯：每一级都要有门禁

| 级别 | 流量与影响 | 证据 | 继续判据 | 停止判据 |
| --- | --- | --- | --- | --- |
| L0 离线回归 | 固定 eval set，零真实流量 | 主指标与红线用例结果 | 主指标非劣（容差事前定）、红线全过 | 任一红线用例失败，或主指标跌破容差 |
| L1 影子流量 | 复制真实请求跑新链路，用户看旧输出 | 新旧输出差异分布、延迟与成本开销 | 差异集中在预期范围、影子开销不反噬线上 | 影子错误率或资源占用拖垮线上 |
| L2 小流量灰度 A/B | 1%–5% 流量，按用户或会话随机，带护栏 | 真实行为指标 + 护栏指标 | 主指标显著为正且护栏不破 | 任一护栏破线，自动停机并回滚 |
| L3 放量 + 长期对照 | 25% → 50% → 100%，保留 1% holdback | 同 L2，外加长尾分桶 | 各级判据一致，长尾不退化 | 任一长尾分桶回归即回退 |

L0 的判据、红线用例与非劣容差怎么定，见 [[evaluation-04]]。阶梯的意义在于**每一级的证伪成本递增**：离线回归几分钟能跑完，拦掉九成明显退化的改动；影子流量不需要用户承担风险，能把「模型能力变化」与「工程开销变化」拆开，但拿不到真实行为反馈（用户根本没看到新输出）；只有 A/B 能回答「更好」，因为「更好」最终由用户行为定义；长尾问题在整体指标里往往看不见，见 [[evaluation-05]]。

### 2. 日志：一条能被归因的记录

| 字段组 | 关键字段 | 为什么必须 |
| --- | --- | --- |
| 请求与会话 | request_id、session_id / conversation_id、turn_index、retry_of | 会话级指标的分母；重试与重复投递要去重 |
| 主体与环境 | tenant_id（哈希）、user_id（哈希）、入口、客户端版本、locale、是否付费 | 长尾与低资源分桶；脱敏后仍可做群体分析 |
| 版本四元组 | model + revision / 权重哈希、prompt 模板 id + 渲染后内容哈希、检索索引快照 id + embedding 版本 + reranker 版本、工具与策略版本 | 没有版本标注的日志无法归因 |
| 检索轨迹 | 改写后的查询、召回 doc id 与分数、重排后 top-k、最终被引用的 doc id | 区分「没检索到」与「检索到但没用」 |
| 工具轨迹 | 工具名、参数摘要（脱敏 + 哈希）、状态码、重试次数、单步耗时 | agent 失败定位与审计的原始素材 |
| 生成 | 输入 / 输出 token（含缓存命中）、finish_reason、是否截断、结构化输出校验结果 | 成本口径与「答一半」类故障 |
| 延迟与成本 | 排队、检索、prefill（TTFT）、decode（TPOT）、工具、端到端；按真实计费口径折算成本 | 护栏指标；把体验退化定位到具体阶段 |
| 质量信号 | judge 分数 + judge 版本、规则指标（引用覆盖率、拒答率、检索命中率） | 抽样评估的产物，必须带版本才能纵向比较 |
| 隐式反馈 | 是否采纳（复制 / 插入 / 继续）、是否重新生成、是否切换候选、是否追问或改写、点踩、会话长度、是否放弃 | 唯一全量可得的「真实偏好」，但是弱标签且有偏 |
| 实验与采样 | experiment_id、variant、assignment_unit、assignment_ts、是否曝光、sampling_stratum、sampling_rate | 事后切分与加权还原的前提 |

几个容易漏的点：版本标注用**内容哈希**而不是人工命名，检索链路任何一环改动都会自动体现在日志里，缺了这一层，线上指标掉了只能靠猜，版本管理与回滚也失去了判据（见 [[evaluation-08]]）；检索轨迹与工具轨迹分别是 RAG 与 agent 的排障入口，前者回答「没检索到还是没用好」（见 [[evaluation-03]]），后者同时是操作审计材料（见 [[agents-10]]）；隐式反馈要先写清楚信号定义（什么算「采纳」、多长的沉默算「放弃」），否则每个人算出来的采纳率都不一样。此外，原始输入输出属于敏感数据，写入前脱敏、分桶存储、按保留期清理，需要原文复核的走审批与加密桶。

### 3. 采样：分层、定向、可切分

1. **错误与超时全采**：5xx、超时、解析失败、护栏命中，一条不漏——这些都是低频高信息量样本。
2. **慢请求全采**：超过 SLO 或落在 p99 之外的请求全留，用于延迟归因。
3. **正常请求按比例随机采样**：1%–10%，用请求 id 或会话 id 的哈希落桶，保证可复现、可去重、与分流相互独立。
4. **高风险 / 高价值场景抬高采样率**：付费租户、法律医疗金融等高风险领域、低资源语言、新上线工具，宁可多花 judge 成本。
5. **人工复核队列按风险分层**：护栏命中、低置信、高价值样本优先，同时保留一个**均匀随机子样本**，用来估计整体分布、校正队列偏差，见 [[evaluation-03]]。

采样率不能拍，要从两端夹出来：一端是「要发现多小的退化」，另一端是「预算允许多少条 judge 调用」。硬要求是**质量指标必须能按版本与实验组切分**，所以抽样要独立于分组，并且每个「variant × stratum」都要有最小样本数，否则上线决策会被某个分层的空缺卡住，见 [[evaluation-07]]。轻量规则指标可以全量算（便宜），judge 只跑抽样（贵），两者分层使用。

### 4. 对什么做 A/B，不对什么做

| 可实验对象 | 典型假设 |
| --- | --- |
| prompt 版本 | 改写系统提示或 few-shot 能提升任务成功率而不增加拒答 |
| 模型与解码参数 | 换模型 / 调 temperature 的收益是否覆盖延迟与成本上升 |
| 检索与重排配置 | top-k、混合权重、reranker 开关对引用质量的影响 |
| 上下文长度与 chunk 策略 | 更长的上下文是否真的提升答案质量，还是只增加成本 |
| 缓存策略 | prefix cache 命中率提升不改变输出分布 |
| 工具与 agent 策略 | 步数上限、是否启用 agentic 检索（多轮检索 vs 单轮） |
| 交互与呈现 | 引用展示方式、澄清提问时机、候选排序 |

**不做随机实验的对象**：安全与合规策略（内容过滤强度、拒答边界、地域与年龄限制）、隐私处理方式（保留期、脱敏规则、训练数据使用）、计费口径与法律条款。随机实验的伦理前提是「组间差异可接受且可撤销」，对安全和隐私改动这个前提不成立——对照组用户在不知情的情况下承担了风险。这类改动走评审 + 分阶段灰度 + 回滚预案，灰度只观察不比较优劣。

策略类改动里最容易被低估的是检索形态本身：从单轮检索切到多轮 agentic 检索会同时改变答案质量、延迟分布与 token 成本，主指标赢了也可能把延迟护栏顶穿，所以它必须带着延迟与成本护栏一起实验，见 [[rag-06]]。

### 5. 实验设计的统计纪律

1. **主指标 + 护栏指标**：主指标只有一个（如任务成功率或采纳率），护栏覆盖质量底线、延迟、成本、安全四类；护栏破线一律停机，不因为主指标好看而放行。
2. **样本量与 MDE 事前定**，写进实验登记单（假设、主指标、护栏、样本量、分析口径、时长），事后再补的都是解释而不是检验。
3. **随机化单位**：请求、会话、用户三选一。同一会话里一半走旧一半走新会割裂体验并污染指标，长会话产品按用户或会话随机；单位与指标粒度不一致时要算设计效应（见「数值与代码验证」）。
4. **实验时长至少覆盖一个完整周期**（通常 ≥7 天，含工作日与周末），并警惕新奇效应：新交互在头两天常被抬高，看的是稳态而不是首日峰值。
5. **多重比较与序贯**：主指标唯一；子群分析预先声明并做校正；要看中间结果就用序贯方法（alpha spending 或 always-valid 区间），不要「看几次 $p$ 值，显著就停」——护栏监控与决策检验要分开，监控用固定阈值。
6. **隐式反馈的选择性偏差**：会点踩、会点采纳的用户不是全体用户的代表，沉默的多数没有任何信号。用行为指标（采纳率、放弃率、追问率、会话长度）与**随机抽样的人工评估**交叉验证，两者方向不一致时以抽样评估为准并去查行为信号的埋点定义。
7. **不选择性披露**：分析与判据事前注册，不允许「只发布赢的那次」「事后挑一个显著的切片」。这一条是与公开榜单最本质的区别（下一节）。

### 6. 从 Chatbot Arena 借方法，防 Leaderboard Illusion 的坑

Chatbot Arena 是「成对比较 + 统计排名」的工程范例：同一 prompt 给两个模型、由用户投票，再用 Elo / Bradley-Terry 类模型把成对胜负还原成全局排名。论文自报的数据口径是**累计超过 24 万张众包投票**，并验证了众包问题足够多样且有区分度、众包投票与专家评分者的一致性良好——这解释了为什么成对比较 + 众包可以支撑排名，前提是这种一致性被验证过而不是假定。

《The Leaderboard Illusion》给出的是机制反例，论文自报的发现包括：私测择优与选择性披露会让分数产生偏置（Meta 在 Llama-4 发布前测试了 27 个私有变体）；数据获取不对称——Google 与 OpenAI 分别获得约 **19.2%** 与 **20.4%** 的 arena 数据，而合计 83 个开放权重模型只拿到约 **29.7%**。内部 A/B 存在同构风险：平台方可以「多测几个变体只报最好的」「拉到显著为止」「事后挑切片」。防火墙有三道：分配由平台随机执行并留下 assignment 日志（可审计，不靠自报）、主指标与判据事前注册、不确定就按原口径重跑而不是挑一次赢的。

### 7. 风险控制：小流量、自动停机、长期对照、长尾

- **小流量起步**（1%–5%），`variant` 的放量是独立决策，不与首次实验结果自动绑定。
- **自动停机与回滚**：护栏指标破线、错误率或成本超阈值时自动切回对照，回滚路径要演练过（没演练过的回滚等于没有回滚）。
- **长期 holdback**：永久保留 1% 对照流量，用来发现缓慢漂移——否则「每次实验都小赢」会累积成整体退化而无人察觉。
- **长尾分桶监控**：按 locale、租户规模、入口、请求类型分别看指标，防止整体被大流量场景掩盖，见 [[evaluation-05]]；低资源语言与小租户要显式设最小样本量，否则它们永远不进决策。

## 数值与代码验证

### 样本量由 MDE 反推（自算，$\alpha=0.05$ 双侧、power 80%）

二值指标每臂样本量：

$$n = \frac{2\left(z_{1-\alpha/2} + z_{1-\beta}\right)^2 p(1-p)}{\Delta^2} = \frac{15.70\, p(1-p)}{\Delta^2}$$

其中 $z_{0.975}=1.9600$、$z_{0.80}=0.8416$，故 $2(1.9600+0.8416)^2 = 15.698$。

| 基线率 $p$ | $\Delta=2$pp | $\Delta=1$pp | $\Delta=0.5$pp |
| --- | --- | --- | --- |
| 0.50（采纳率之类） | 9,811 | 39,244 | 156,978 |
| 0.30 | 8,241 | 32,965 | 131,861 |
| 0.10 | 3,532 | 14,128 | 56,512 |
| 0.05（缺陷率 / 拒答率之类） | 1,864 | 7,456 | 29,826 |

连续指标（延迟、成本等）用 $n = 15.70\,\sigma^2/\Delta^2$：要检测 $0.02\sigma$ 的位移需要每臂 39,244 条，$0.05\sigma$ 需要 6,279 条，$0.1\sigma$ 需要 1,570 条。表里所有数字都由这两个公式直接算出（`.work/` 下的复算脚本），不是引用值。

### 采样率 = 质量预算的旋钮（示意价）

假设每天 500 万次请求，judge 每次读 8k 输入 token、写 100 token；示意价输入 0.30 美元 / 百万 token、输出 1.20 美元 / 百万 token（**只是算例，不代表任何厂商当前定价**），单条判定成本 0.00252 美元：

| 采样率 | 判定样本 / 天 | 每臂 / 天 | 一日数据可检测 $\Delta$（$p=0.05$） | 相对 | judge 成本 / 天 | 成本 / 30 天 |
| --- | --- | --- | --- | --- | --- | --- |
| 0.1% | 5,000 | 2,500 | 1.73pp | 34.5% | 12.60 美元 | 378 美元 |
| 1% | 50,000 | 25,000 | 0.55pp | 10.9% | 126 美元 | 3,780 美元 |
| 10% | 500,000 | 250,000 | 0.17pp | 3.5% | 1,260 美元 | 37,800 美元 |
| 100% | 5,000,000 | 2,500,000 | 0.055pp | 1.1% | 12,600 美元 | 378,000 美元 |

采样率提高 10 倍，可检测的绝对差异缩小 $\sqrt{10}\approx 3.16$ 倍，成本线性上涨。0.1% 与 1% 之间不是「省点钱」的差别，而是「只能看见灾难性退化」与「能看见一次 prompt 改动的影响」的差别。

### 连续窥视会把 5% 的假阳率抬到约 10%（自算模拟）

把零假设下的 $z$ 统计量看成信息量累积过程中的随机游走（终点标准差为 1），在 $K$ 个等间隔时间点各做一次 $\alpha=0.05$ 的双侧检验，每格 40,000 次模拟、随机种子固定：

| 窥视次数 $K$ | 1 | 2 | 5 | 10 | 20 | 50 | 100 | 1000 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 实际假阳率 | 4.9% | 5.3% | 5.9% | 7.0% | 7.5% | 8.5% | 8.8% | 9.6% |

连续窥视的渐近值可由反射原理给出：$\Pr(\sup_{t\le 1}|B(t)| \ge 1.96) \approx 4(1-\Phi(1.96)) = 2\alpha = 10\%$，与 $K=1000$ 时的 9.6% 吻合。实验平台每天弹一次显著性提示，等价于反复窥视；正确做法是事前定样本量、到期判读，或者用序贯检验（alpha spending、always-valid 置信序列），而护栏监控用固定阈值、不参与决策检验。

### 随机化单位的设计效应

若按用户随机、按请求统计，平均每用户 $\bar{m}$ 次请求、用户内相关系数 $\rho$，有效样本量

$$n_{\text{eff}} = \frac{n}{1 + (\bar m - 1)\rho}$$

$\rho=0.2$、$\bar m=4$ 时设计效应为 $1+3\times0.2=1.6$：同样多的请求，等价样本量只有 $n/1.6$，MDE 要乘 $\sqrt{1.6}\approx 1.26$。反向的杠杆是方差缩减：用预实验期的同一指标作协变量（CUPED 思路），相关系数 $\rho$ 时调整后方差约为原来的 $1-\rho^2$；$\rho=0.7$ 即降到 0.51，等同于样本量翻倍。

### 分流不均（SRM）的检测阈值

总流量 1,000,000、计划 50/50 时，卡方统计量 $\chi^2 = 4d^2/N$（$d$ 为单臂偏离 $N/2$ 的计数），1 自由度下 $p = \operatorname{erfc}\sqrt{\chi^2/2}$：

| 观测（对照 / 实验） | 失衡 | $\chi^2$ | $p$ |
| --- | --- | --- | --- |
| 501,000 / 499,000 | 0.10pp | 4.000 | 0.046 |
| 501,645 / 498,355 | 0.165pp | 10.82 | 0.001 |
| 502,000 / 498,000 | 0.20pp | 16.00 | $6.3\times10^{-5}$ |

百万级流量下 0.165pp 的失衡就足以在 $p<0.001$ 水平判为 SRM。因为 SRM 会在每个实验里天天跑（多重比较），告警阈值应取 $p<0.001$ 而不是 0.05——上表第一行那种 0.1pp 的抖动在日粒度上很常见。

### 日志体量

5,000,000 请求/天 × 约 6KB 结构化记录 ≈ 30GB/天；全量保留 90 天约 2.7TB。分层保留更现实：全量 7 天（约 210GB）+ 1% 抽样长留（约 0.3GB/天，一年约 110GB）。日志 schema 的设计要在这个预算内取舍：把高基数字段（完整输出文本）放冷存，把版本、分组、指标、延迟分解这些窄字段放热存以便按任意维度切分。

### 代码：稳定分桶的分流与采样、样本量、SRM

```python
import hashlib
from math import erfc, sqrt

ZA, ZB = 1.959963984540054, 0.8416212335729143  # alpha=0.05 双侧、power=80%

def bucket(key, salt=""):
    """稳定分桶：同一 key 永远落同一桶，重试与重复投递不改变采样/分流结果。"""
    digest = hashlib.blake2b((salt + key).encode(), digest_size=8).digest()
    return int.from_bytes(digest, "big") % 10_000          # 万分比

def assign(key, experiment, arms=("control", "treatment")):
    return arms[bucket(key, experiment) % len(arms)]

def should_sample(key, rate_bp):
    return bucket(key, "sample") < rate_bp

def sample_decision(req):
    """返回 (是否采样, 分层名)；分层名进日志，后续按层加权还原整体指标。"""
    if req["status"] != "ok" or req["timed_out"]:
        return True, "errors"                              # ① 错误/超时全采
    if req["latency_ms"] > req["slo_p99_ms"]:
        return True, "slow"                                # ② 慢请求全采
    if req["explicit_feedback"]:
        return True, "feedback"                            # ③ 有显式反馈全采
    if req["risk_tier"] == "high":
        return should_sample(req["request_id"], 500), "high_risk"   # ④ 5%
    return should_sample(req["request_id"], 100), "normal"          # ⑤ 1%

def required_n(p, delta):
    return 2 * (ZA + ZB) ** 2 * p * (1 - p) / delta ** 2

def srm_p(n_a, n_b):
    """SRM：两臂卡方优度检验，1 自由度 p = erfc(sqrt(chi2/2))。"""
    n = n_a + n_b
    chi2 = (n_a - n / 2) ** 2 / (n / 2) + (n_b - n / 2) ** 2 / (n / 2)
    return chi2, erfc(sqrt(chi2 / 2))
```

本机实测输出：`assign("u-42", "exp-rag-v3")` 恒为 `control`（重复调用三次结果一致）；一条延迟 900ms、无显式反馈、普通风险的正常请求返回 `(False, "normal")`；`required_n(0.05, 0.005)` 得 29,826（与上表一致）；`srm_p(501000, 499000)` 得 `(4.0, 0.0455)`。分流与采样必须走同一个稳定哈希，否则重试、重复投递会让人被分到两组。

## 常见追问

- **追问**：隐式反馈有偏，怎么用？
  - 要点：把它当**弱标签**而不是 ground truth。做法是三条并行：给每个信号写死定义（复制/插入算采纳、30 秒无动作算放弃）；用抽样人工评估或 judge 作为参照，报告「行为指标 × 人工标签」的一致率，一致率低就说明信号定义有问题；所有结论用行为指标与抽样评估交叉验证，方向冲突时以抽样评估为准。
- **追问**：会话级指标还是请求级指标？
  - 要点：看决策对象。请求级指标灵敏、样本量大，适合检测单点退化（检索命中、结构化解析失败）；会话级指标贴近体验（任务是否完成、是否放弃、会话长度），但样本量小、方差大。通常主指标用会话级（与用户价值对齐），护栏与诊断用请求级；随机化单位取会话或用户，避免同会话跨组。
- **追问**：A/B 显示质量赢了，但延迟和成本都涨了，怎么决策？
  - 要点：换算成同一单位再比——把质量增益折算成「每千次请求的额外成功任务数」，把成本与延迟折算成预算与 SLO 占用，看是否在护栏预算内。若在预算边缘，做一次**更小 MDE、更长时长**的实验确认增益稳健，或者试试只在高价值场景启用新链路（分层放量），而不是全量二选一。
- **追问**：多轮交互的 agent 怎么在线评估？
  - 要点：单轮指标会漏掉「多轮才完成」和「中途放弃」。要记录任务级轨迹（会话内从目标到终态的完整链路）、定义任务成功率与平均步数，并用 pass^k 类一致性口径看「重复执行是否稳定」，见 [[evaluation-10]]、[[evaluation-04]]。
- **追问**：用 LLM judge 做在线采样指标，最大的风险是什么？
  - 要点：judge 版本漂移。judge 模型或 prompt 一改，历史分数就不能比了，所以 judge 版本必须进日志、跟着分数一起报；同时保留一个固定的小校准集，每次换 judge 都跑一遍校准，报告与人工标注的一致率变化。
- **追问**：实验期间来了一个紧急安全修复，怎么处理？
  - 要点：安全修复不进实验、直接全量发布，同时记录一个「环境变更」事件打点到实验时间线，分析时截断或加协变量。不要为了保住实验的纯净性延迟安全修复——那不是统计问题，是排序问题。

## 公司变体

Perplexity 的产品形态是带引用的答案引擎：查询理解、检索与重排、答案生成、引用展示串在一条链路上，并且是流式输出。这类岗位的在线评估问题通常**偏工程实现**而不是纸面推导：追问会落在「日志里怎么标检索与 reranker 版本」「引用质量用什么全量规则指标、什么交给抽样的 judge」「首 token 延迟怎么进护栏」「真实查询分布上的流量倾斜与长尾 query 怎么采样」。统计部分一般不需要从零推导公式，但会被要求说清随机化单位、样本量来源与实验时长，以及在流量结构随热点查询剧烈波动时如何保证分流稳定。

需要说明的是：以上只依据公开可见的产品形态推断面试侧重，不涉及该公司的具体面试流程与轮次。
