## 一句话答案

> 回归门禁是一个函数：输入是「一个变更（prompt / 模型版本 / 检索配置 / 代码）+ 候选版本」，输出是**通过或拒绝 + 证据**（每个指标集合上的差值点估计与置信区间）。三条硬要求——自动化、可复现、统计上可信；「跑一遍看看感觉还行」不是门禁。
> 判定逻辑是分层的：红线集一票否决，核心能力集不允许显著退化，目标能力集必须显著提升，性能与成本集守住预算；每一层的主指标、阈值和最小可检测差异（MDE）都在跑之前写死在配置里。
> 与代码 CI 的本质差别在于判定是统计的：同一版本重跑就会波动，所以先要量出「flaky 水位」，只有超过水位的差异才算真差异；又因为评测依赖 judge，**judge 版本必须和 prompt、模型版本一起锁**。样本量通常远小于代码测试，它只能拦住「大到值得拦」的退化——这一点要对团队讲明白，别让它冒充质量保证。

## 面试官在考什么

- **能不能把门禁当接口来定义**：输入、输出、触发时机、失败行为的边界是否清晰，而不是一上来就谈「我们用什么工具跑评测」。
- **有没有把统计显著性当成工程约束**：会不会算样本量、会不会用配对比较、知不知道为什么同一版本重跑会有差异、知不知道 MDE 与样本量的换算关系。
- **裁决规则的优先级是否想清楚**：红线、核心能力、目标能力、成本延迟谁先谁后，冲突时怎么判，阈值是事前定的还是事后调的。
- **懂不懂 LLM 门禁与代码 CI 的差异**：非确定性、评测集固定带来的偏差、judge 漂移、样本量小导致的检出力上限。
- **工程与治理的完整度**：CI 时间窗与成本预算、结果如何贴回 PR、历史结果入库与 flaky 检测、豁免流程、评测集自身的维护与 Goodhart 防范。

常见错误答案：

- 把门禁等同于「跑一遍 eval 套件，分数没掉就过」。缺 MDE、缺置信区间、缺 flaky 水位，等于用噪声当信号，改动一多就会出现「过了门禁但线上变差」和「明明更好了却被拦」两类事故。
- 只设计指标不设计裁决：红线集、核心集、目标集的通过条件混成一个加权总分。加权总分会让「安全退化 2 个点、平均分涨 0.5」判成通过，而红线类退化是不可交易的。
- 声称「样本量越大越好，直接全量跑」。忽略 CI 时间窗与逐样本成本，也忽略一个事实：在固定评测集上把样本量堆大，压下去的只是抽样噪声，压不掉评测集本身的偏差。

## 原理与推导

### 1. 门禁的接口与三类输出

```text
输入：change = {prompt_hash, model_id, retrieval_config, code_sha, judge_id, decode_params}
      candidate = 变更后的产物；baseline = 当前生产版本（或主干）
输出：verdict ∈ {pass, fail, needs_more_data}
      evidence = 每个（集合, 指标）的 {点估计, 置信区间, 样本量, 生效阈值, 判定依据}
```

三类输出都要有，`needs_more_data` 不是偷懒：当样本量不足、或差异落在「灰区」（置信区间跨过 0，或下界低于 MDE，即无法确认真实差异已达到 MDE）时，强行二值化只会把噪声包装成结论，正确做法是扩容重跑或升级到人工会审。

可复现要求把影响输出的全部输入都落进 `change`：prompt 与 system prompt 的哈希、模型与快照 id、judge 版本、解码参数（temperature、top_p、max_tokens）、检索配置与索引版本、评测集版本、随机种子。任何一项不在记录里，两次结果就没有可比性。

### 2. 测试集分层与各自的角色

| 集合 | 规模参考 | 主指标 | 通过条件 | 变更评审 |
| --- | --- | --- | --- | --- |
| 红线集 | 数百条 | 违规率、越权率、注入成功率 | 0 容忍（口径见第 5 节） | 需安全 owner 签字 |
| 核心能力集 | 千级 | 准确率、任务完成率、格式合规率 | 不允许显著退化 | 常规评审 |
| 目标能力集 | 数百条 | 本次变更要提升的那个指标 | 必须显著提升（$\ge$ MDE） | 常规评审 |
| 性能与成本集 | 复用流量分布 | p50/p95 延迟、输出 token 数、每百万 token 成本 | 不超预算 | 常规评审 |
| flaky 校准集 | 数百条 | A/A 差值的分布 | 只用于标定水位，不作裁决 | 常规评审 |

性能与成本集的指标口径、TTFT/TPOT 与每百万 token 成本怎么算，见 [[inference-serving-09]]；降本手段的排序见 [[inference-serving-12]]。这两者是门禁的输入约束，不是门禁本身要解决的问题。

分层的意义在于「冲突时谁优先」是事先写好的。红线集与安全、injection 相关题目的关系见 [[safety-01]]。

### 3. 指标、阈值与 MDE：全部事前声明

每个集合在配置文件里声明主指标、方向（越大越好 / 越小越好）、阈值、MDE、最小样本量与目标检出力。阈值事后调是门禁失效的最常见原因：一旦允许「这次先放宽一点」，门禁就从判据退化成记录。

MDE 的定义要说准：**MDE 是我们希望在给定检出力（通常 80%）下能稳定检测出的最小真实差异**，不是「小于这个值就一定没影响」。样本量按 MDE 反推（第 4 节），反过来也成立：样本量定死之后，可检测的下限就定死了，报数时必须一起报出来。

### 4. 统计判定：配对比较、置信区间与样本量

**为什么必须配对。** 候选与基线跑同一批样本，得到配对数据 $d_i = s_i^{\text{cand}} - s_i^{\text{base}}$，判定只看 $\bar d$：

$$\bar d = \frac{1}{n}\sum_i d_i, \qquad SE = \frac{\sigma_d}{\sqrt{n}}, \qquad \text{拒绝 } H_0 \iff |\bar d| > z_{1-\alpha/2}\, SE$$

配对把「样本难度」这一项从方差里消掉：同一道难题在两侧都难，差值接近 0，$\sigma_d^2$ 只剩采样随机性贡献的那部分，远小于两组独立样本的方差之和。这也是同一变更重跑波动更小的原因——它减的是抽样方差，不减模型本身的随机性。

**样本量。** 在 $\alpha = 0.05$（双侧）、检出力 $1-\beta = 0.80$ 下：

$$n \approx \frac{(z_{1-\alpha/2} + z_{1-\beta})^2\,\sigma_d^2}{\delta^2} = \frac{7.85\,\sigma_d^2}{\delta^2}$$

其中 $\delta$ 是 MDE。两类常见指标代入不同的 $\sigma_d^2$：

- 二值准确率（配对）：只有「一侧对一侧错」的不一致对提供信息。设不一致率 $p_d$，则 $\sigma_d^2 \approx p_d - \delta^2$（推导见下），$n \approx 7.85\,(p_d - \delta^2)/\delta^2$；判定统计量是 McNemar 形式 $z = (n_{01}-n_{10})/\sqrt{n_{01}+n_{10}}$。
- 连续分数（judge 打 0–1 分、通过率以外的质量分）：$n = 7.85\,\sigma_d^2/\delta^2$ 直接可用。

二值配对的方差推导：设 $n_{01}$ 是「基线错、候选对」的条数，$n_{10}$ 反之。$d_i \in \{-1, 0, +1\}$，均值 $\bar d = (n_{01}-n_{10})/n$，方差 $\sigma_d^2 = E[d^2] - \bar d^2 = (p_{01}+p_{10}) - \delta^2 = p_d - \delta^2$。这一步是本节的近似所在：它用总体不一致率 $p_d$ 代替随样本波动的观测不一致率，且把 $p_{01}$、$p_{10}$ 当作已知——当期望不一致对 $n\,p_d$ 落到个位数时，精确检验的检出力会明显低于设计值，所以样本量公式要用在 $n\,p_d \gtrsim 25$ 的区间（边界算例见「数值与代码验证」一节）。

**同分布假设。** 两次评估必须用同一批样本、同一套 judge 与解码参数，否则方差里混入的是分布差异而不是变更效应。

**judge 冻结规则。** 评测本身依赖 judge，而 judge 会漂移。门禁配置里锁 judge 的模型 id、prompt 哈希与版本号；**judge 与候选必须同时换或同时不换**（对应 [[evaluation-01]] 里的 judge 偏差与校准问题）。否则一次 judge 升级会让所有指标平移，门禁读到的「改进」或「退化」可能全部来自 judge。

**非确定性的处理与 flaky 水位。** LLM 有采样随机性，候选与基线都要跑 $k$ 次；若两侧各跑 $k$ 次，$\sigma_d^2$ 近似降到 $1/k$，样本量同比降到 $1/k$，这通常比把 $n$ 扩大 $k$ 倍便宜。同时用 A/A 标定水位：拿同一个版本跑两遍，得到 $\bar d_{A/A}$ 的分布，取它的 95 分位作为「真差异」的下限；比自己算的 $SE$ 更可信，因为它把评测脚本、缓存、限流、调度抖动全都算进去了。

### 5. 裁决规则：红线优先，其次目标与核心

```text
if red_line.violations > 0                      -> fail（一票否决，不看其它指标）
if |core.delta| 的 CI 与 0 不重叠 且方向为退化   -> fail
if target.delta <= 0 或 CI 下界 < MDE           -> needs_more_data / fail（看灰区规则）
if cost.p95_tokens > budget 或 p95_latency > SLO -> fail
其余情况                                        -> pass
```

四点容易踩的地方：

- **红线用上界而不是点估计**。零容忍的正确表述是「违规率的 95% 置信上界低于某个值」；$n$ 条全过时，用 rule of three 给出的上界约为 $3/n$（复算见「数值与代码验证」一节），所以 300 条全部通过只能说「违规率不高于约 1%」，不能声称是 0。
- **成本与延迟看绝对预算**：p95 输出 token 数、p95 端到端延迟、每百万 token 成本超预算即拦，不参与显著性检验。
- **一次只拦一个变量**：PR 里同时改 prompt、换模型、动检索配置时，门禁的结论无法归因。要求拆分变更，或至少在报告里把三者的影响分开跑。
- **灰区要有明确规则**：CI 跨 0 或跨 MDE 时返回 `needs_more_data`，并给出「还需要多少样本才能判定」，而不是让人凭感觉拍。

### 6. 时间窗与成本预算

门禁必须在 CI 时间窗内跑完，否则团队会用「先合了再补跑」绕开它。可用手段：分片并行、对不涉及变更的集合复用缓存、把全量回归放到夜间流水线。

以核心集 1200 条、每条生成与打分各一次计，逐样本调用数为 $1200 \times 2 = 2400$；若每条采 3 次、候选与基线各跑一遍，则为 $1200 \times 3 \times 2 \times 2 = 14400$ 次调用。若平均每次调用消耗 1200 token，整个门禁约消耗 1700 万 token 量级的推理量——这个量级决定了「缓存基线结果」和「只在受影响的样本上重跑」是必需品，而不是优化项。

检出力是硬约束，把它和 CI 时间窗放在一起看：若核心集只有 1200 条、不一致率 20%，按第 4 节公式，2 个百分点的 MDE 需要约 3900 条样本。两者只能这样调和——PR 触发跑抽样（几百条，只拦大退化，MDE 约 5%），夜间跑全量并做统计判定；用户明确要求的改动不等待夜间，但要走审批记录。

### 7. LLM 门禁与代码 CI 的差别

| 维度 | 代码 CI | LLM 回归门禁 |
| --- | --- | --- |
| 判定 | 布尔，确定性 | 统计，同一版本重跑会波动 |
| 结果 | 可复现（同输入同结论） | 可复现需要固定种子与 $k$ 次重复的统计量 |
| 依赖 | 编译器、测试框架 | judge（有版本、有偏差、会漂移） |
| 样本量 | 用例可全跑 | 采样，检出力有上限 |
| 典型失效 | 测试脆弱、偶发失败 | 噪声被当成信号、阈值被事后放宽 |
| 门槛形状 | 通过或不过 | 通过上界、MDE、灰区与扩容规则 |
| 维护对象 | 测试用例 | 评测集 + judge + 阈值 + flaky 水位 |

结论：门禁只能拦住「大到值得拦」的退化。把它说成质量保证会同时误导工程师和业务方；它的真正定位是**发布前的风险闸门**，闸门的高度（MDE）由样本量与预算决定，并且要说出来。

### 8. 三段串联与治理

离线门禁拦明显退化，灰度拦真实分布问题，线上指标兜住剩下的，见 [[evaluation-09]]。三段之间要有约定：离线门禁的 MDE 决定灰度要放多大流量才能检出同一量级的差异。

治理上有五件事必须有明确归属：

- **豁免流程**：谁能豁免、理由与到期时间记录在哪、是否需要 owner 签字。无记录的口头豁免等于没有门禁。
- **失败修复路径**：门禁失败先看逐条 diff（哪些样本从对变错），再判断是回归、评测集问题还是 flaky；三者对应的动作完全不同。
- **结果入库与回贴**：每次门禁的 change 哈希、各集合的差值与 CI、当批 A/A 水位一起入库，用来画趋势、并判断某次波动是脚本 flaky 还是真回归；PR 上回贴一行结论（判定 + 差值 + 置信区间）并附失败样本的逐条 diff 链接，使每次判定都能追溯到具体的 change 与样本。
- **评测集维护**：评测集要随产品演进更新，否则团队会转向「为了过门禁而优化」，踩进 Goodhart 陷阱，见 [[evaluation-05]]。
- **阈值与红线的变更评审**：红线集的任何修改需要单独评审，不能被业务指标讨价还价；阈值调整要记录理由与生效时间，只允许在事前生效。

## 数值与代码验证

以下数字由本节的代码在固定随机种子下复算，口径写死在常数里。参考来源（openai/evals、promptfoo 文档）提供的工具形态是「数据集 + 评分器 + CI 集成」，它们不规定统计判定口径，因此本节的计算均为自行推导。

### 样本量要求（$\alpha=0.05$ 双侧，检出力 0.80，$z^2$ 系数取 7.85）

| 不一致率 $p_d$ | MDE 2% | MDE 3% | MDE 5% | MDE 10% |
| --- | --- | --- | --- | --- |
| 0.05 | 974 | 429 | 150 | 32（见下） |
| 0.10 | 1955 | 865 | 307 | 71 |
| 0.15 | 2936 | 1301 | 464 | 110 |
| 0.20 | 3917 | 1737 | 621 | 150 |
| 0.25 | 4898 | 2173 | 778 | 189 |
| 0.30 | 5879 | 2609 | 935 | 228 |

表中的 $n$ 一律向上取整（`math.ceil`），与手算值可能差 1。$p_d = 0.05$、MDE 10% 那一格是公式的失效边界：它期望的不一致对只有 $n\,p_d \approx 1.6$ 对，精确 McNemar 检验的检出力实测只有 0.03（见复算代码），也就是**公式在小不一致对区间会给出过小的样本量**。门禁实现里要加护栏——期望不一致对少于约 25 对时不用近似判据，改用精确检验并要求更多样本。

### 连续指标的样本量（同一个 7.85 系数）

| 配对差的标准差 $\sigma_d$ | MDE 0.5% | MDE 1% | MDE 2% | MDE 5% |
| --- | --- | --- | --- | --- |
| 0.10 | 3140 | 785 | 197 | 32 |
| 0.20 | 12559 | 3140 | 785 | 126 |
| 0.30 | 28256 | 7064 | 1766 | 283 |

结论：**低于 1 个百分点的 MDE 在千级样本上不可检测**。若每条采 3 次，$\sigma_d$ 按 $1/\sqrt{k}$ 收缩，上表的样本量约降为 $1/k$——这就是「重复采样换样本量」的定量形式。

### 一处完整算例

核心集 1200 条，浮动通过率从 90.0% 到 92.1%（$\bar d = 0.021$），配对差的标准差取 $\sigma_d = 0.20$：

$$\bar d = 0.021,\quad SE = \frac{0.20}{\sqrt{1200}} = 0.0058,\quad CI_{95\%} = [0.0097,\ 0.0323]$$

区间不含 0，判为显著改善。若 $\sigma_d = 0.30$，$SE = 0.0087$，$CI = [0.0040,\ 0.0380]$，仍显著，但下界只剩 0.4 个百分点——**「显著」与「够大」是两件事，报告里必须同时给点估计与 MDE 对照**。

### 复算代码

```python
import math, random

# 1) 样本量：alpha=0.05 双侧、power=0.80
Z = 1.959963985 + 0.841621234          # 手算常数；z^2 = 7.849（常见库取 1.96 与 0.84，得 7.85）
def n_binary(p_d, delta): return math.ceil(Z**2 * (p_d - delta**2) / delta**2)
def n_cont(sd, delta):    return math.ceil(Z**2 * sd**2 / delta**2)

print([n_binary(0.20, d) for d in (0.02, 0.03, 0.05)])   # [3917, 1737, 621]
print([n_cont(0.20, d)   for d in (0.01, 0.02, 0.05)])   # [3140, 785, 126]
for k in (1, 2, 3, 5, 8):                                 # 每条采样 k 次
    print(k, n_cont(0.20 / math.sqrt(k), 0.02))           # 785 393 262 157 99

# 2) 配对判定：点估计 + 正态近似 CI，再补一个精确 McNemar
def mcnemar_exact(b, c):
    n = b + c
    if n == 0: return 1.0
    k = min(b, c)                                        # 精确条件检验，条件在 n 上
    tail = sum(math.comb(n, i) for i in range(k + 1)) / 2**n
    return min(1.0, 2 * tail)

def paired_verdict(n01, n10, n):
    d = (n01 - n10) / n
    se = math.sqrt((n01 + n10) - (n01 - n10)**2 / n) / n   # 配对差值标准误（二值口径）
    return d, (d - 1.96*se, d + 1.96*se), mcnemar_exact(n01, n10), se

# 1200 条、+1 个百分点：CI 跨 0（[-0.016, 0.036]）、精确 p = 0.49，判为无差异
print(paired_verdict(132, 120, 1200))
# 1200 条、+10 个百分点：CI 不跨 0（[0.063, 0.137]），显著
print(paired_verdict(324, 204, 1200))
# 反例：红线集 300 条里只有 1 条被判违规。统计上 p = 1.0，但裁决规则是一票否决
print(paired_verdict(1, 0, 300))

# 3) Monte Carlo：验证上表的检出力，并量出 flaky 水位
random.seed(7)
def power_binary(p_d, delta, n, trials=2000):
    b, c = n * (p_d + delta) / 2, n * (p_d - delta) / 2
    rej = 0
    for _ in range(trials):
        bb = sum(random.random() < b / n for _ in range(n))
        cc = sum(random.random() < c / n for _ in range(n))
        rej += mcnemar_exact(bb, cc) < 0.05
    return rej / trials

print(power_binary(0.20, 0.00, 1200, 3000))   # 假阳性率 ≈ 0.033（目标 0.05，精确检验偏保守）
print(power_binary(0.20, 0.02, 3917))         # ≈ 0.79，与 80% 设计一致
print(power_binary(0.20, 0.05, 621))          # ≈ 0.79
print(power_binary(0.05, 0.10, 32))           # ≈ 0.03：期望不一致对仅 1.6 对，公式失效
# 全表复核（20000 次抽样）：p_d=0.05/0.10/0.20/0.30 配 MDE 5% 或 10% 时，
# 实测检出力落在 0.72–0.80；只有期望不一致对接近 1 的那格塌到 0.03。

# 4) rule of three：n 条红线全过时的 95% 上界
for n in (100, 300, 1500):
    print(n, f"{3/n:.4%}")                    # 3% 1% 0.2%
```

`paired_verdict` 的方差按二值配对口径取 $\sigma_d^2 = p_d - \delta^2$，用的是正态近似；不一致对少时用 `mcnemar_exact`（条件二项检验），它在小样本下偏保守。上面这段 Monte Carlo 同时给了两个实现细节的依据：**假阳性率**（A/A 下 1200 条样本、20% 不一致率时实测约 0.033，低于名义 0.05，因为精确检验是保守的）与**检出力**（设计点附近实测 0.72–0.80）。A/A 复跑 $R$ 次得到的 $\bar d$ 的经验标准差近似为 $\sqrt{2}\,\sigma_d/\sqrt{n}$（两侧各引入一份抽样方差），把它与该批次 $|\bar d_{A/A}|$ 的 95 分位一起入库，作为后续判定「真差异」的水位。

## 常见追问

- **追问**：样本量太小、噪声压过信号怎么办？
  - 要点：四步按性价比排序。① 配对——同一批样本跑两侧，把样本难度从方差里去掉；② 重复采样 $k$ 次取均值，方差按 $k$ 收缩，样本量等价降为 $1/k$；③ 分层——红线集与核心集用固定样本、目标集用大样本，别让所有指标共用一套样本量；④ 先跑 A/A 量出水位，把阈值设在水位之上，宁可漏拦也不误拦。最后一条是先决条件：不知道水位，任何阈值都是拍的。
- **追问**：怎么防门禁过拟合？团队天天盯着它调 prompt。
  - 要点：把评测集分成可见的 dev 集与不可见的 held-out 集，门禁判定只看 held-out；定期轮换部分样本、把线上新出现的失败样本补进来；同时看「提升来自哪些样本」，如果提升集中在少数样本上，多半是过拟合而不是通解。Goodhart 的失效模式与评测集更新的关系见 [[evaluation-05]]。
- **追问**：离线门禁过了，线上还是退化怎么办？
  - 要点：先分清三类原因。① 分布差异：离线集的样本分布与线上不同，门禁的 MDE 再小也测不到没见过的样本；② 指标错配：离线主指标与业务指标不是同一个东西（例如离线优化了答案准确率，线上掉的是首 token 延迟）；③ 交互效应：变更确实变好了，但与线上其它组件叠加产生退化。动作分别是补线上样本进评测集、把业务指标加进门禁的成本与体验集合、用灰度分层验证，见 [[evaluation-09]]。这也是离线门禁必须与灰度串联的原因。
- **追问**：多模型、多租户怎么做不同门禁？
  - 要点：门禁是「集合 × 指标 × 阈值」的配置，按模型或租户各复制一份，共享红线集与判定引擎。差异点在三处：红线的严格度（合规场景零容忍、内部工具可放宽但要记录）、成本与延迟预算（不同套餐的 SLO 不同）、目标集合（不同客户关注的能力不同）。公共部分必须共享，否则口径分裂会让「门禁通过」失去全局含义。
- **追问**：门禁失败之后，团队第一件事做什么？
  - 要点：看逐条 diff，把样本分成四类：从对变错（真回归，看是否集中在某类输入）、从错变对（改进）、双错（与本次变更无关，属于集合已有的失败）、双对（无信息）。真回归优先修，双错样本进评测集维护队列；如果两侧差值在 A/A 水位的正常范围内，则判为 flaky，修评测脚本而不是改 prompt。
- **追问**：门禁跑一次要花多少钱、多久？怎么压缩？
  - 要点：成本 ≈ 逐样本调用数 ×（输入 + 输出 token 单价）。压缩手段：缓存 baseline 结果（基线不变就不重跑）、只对受影响的样本重跑（prompt 差异定位到模板片段）、shard 并行、夜间全量 + PR 抽样。时间上给门禁设硬预算（例如 10 分钟），超时就降级为「抽样跑 + 异步全量」，而不是无声地让门禁变慢——变慢的门禁一定会被绕过。

## 公司变体

`asked_at` 里只有一家，因此这节的判断范围也只限于它。

- **Anthropic**：偏工程实现与评测方法论，且带明显的安全导向。公开技术材料里可以看到两条一致的取向：Constitutional AI 把「无害」拆成一份写下来的原则清单，再用它驱动 critique–revision 与偏好模型，也就是说「判据要先写成文本、再拿去自动判定」；Anthropic 发布的模型与系统卡（system card）则逐条报告安全评测的口径、触发条件与阈值，而不是只给一个总分。这两点正对应本题要考的东西——分层判据、可复算的口径、红线单独评审。落到这道题上的常见期待是：红线集与核心能力集分层、统计判定口径可复算、judge 与 prompt/模型版本一起锁、以及把「门禁能拦什么、拦不住什么」说清楚。是否要求现场推导样本量或写出判定公式，取决于面试轮次（工程轮更可能要求落到 CI 集成与失败处理）。

以上是基于公开技术材料与岗位方向的侧重判断，不涉及任何具体面试流程，具体题目以实际面试轮次为准。
