## 一句话答案

> LLM-as-judge 是拿一台**有已知系统偏差的仪器**去测量模型输出：先划边界，把能被精确验证的部分（单测、执行结果、schema、数值、约束）交给可验证验证器，剩下的开放式质量才交给 judge；再按「范式 → rubric → prompt → judge 模型 → 聚合 → 成本」六步落地。
> 偏差靠协议纠正，不靠 prompt 里写一句「请客观公正」：位置交换（两种顺序都指向同一答案才算胜，否则记平局）、长度控制与长度回归校正、跨家族 judge panel、双盲、用成对比较替代绝对打分、复杂推理交给可验证手段。
> judge 要能当门禁，前提是校准过：一致率按子集拆开看、有金标准回归集、judge 模型或 prompt 变更后必须重跑。MT-Bench 论文自报 GPT-4 judge 与人类一致率 85%、人类之间 81%（MT-bench 第一轮，仅非平局票口径），这是特定 benchmark + 特定 prompt 的数字，不是通用保证。

## 面试官在考什么

- **会不会先划边界**：这道题真正的分水岭是「哪些东西根本不该交给 judge」。把事实核对、数值正确性、代码是否可运行交给一个概率模型打分，后面所有校准都是在给错误的测量目标做精修。
- **能不能把偏差讲成三元组**：机制（为什么会产生）+ 纠正协议（具体怎么做，能落成代码）+ 监控指标（线上怎么发现它又回来了）。只报偏差名字说明是背的。
- **是否把 judge 当仪器而不是当裁判**：一致率的定义与随机基线、按子集拆解一致率、可重复性（同输入多次打分的方差）、金标准回归集——没有校准过的 judge 分数不能进发布决策。
- **聚合与成本意识**：位置交换让调用翻倍，panel 再乘一个系数，prompt 变长还会再乘；抽样、缓存、可验证前置门如何把成本压回来。
- **治理**：judge 的模型与 prompt 版本要进版本管理，与被评系统构成同一个发布版本；高风险场景保留人工抽检。

常见错误答案：

- 「用最强的模型当 judge 就很准了」——把论文里特定 benchmark 上的 80%+ 一致率当成通用保证，既不给口径也不给子集拆解。
- 「在 prompt 里写『请公平、不要偏好长答案』就算处理了偏差」——不做位置交换、不做人工校准，直接把 pointwise 均分当门禁阈值。
- 「上个版本的 judge 打了 4.2 分，这个版本 4.5 分，说明变好了」——judge 版本或 prompt 一换，分数尺度就漂移，不重跑基线就没有可比性。

## 原理与推导

### 1. 先划边界：有精确判定器的任务不交给 judge

判据只有一句：**这个任务有没有便宜、确定、可执行的判定器**。

| 交给可验证验证器 | 留给 judge |
| --- | --- |
| 单测 / 编译 / 类型检查是否通过 | 命名、可读性、注释是否讲清意图 |
| JSON 是否符合 schema、字段是否齐全 | 措辞是否得体、语气是否符合品牌 |
| 数值结果是否等于参考答案（容差内） | 推导过程的解释是否自洽、易跟随 |
| 引用是否真实存在、原文是否支撑该结论 | 综合多个来源后的综述是否完整均衡 |
| 是否命中禁用词、是否越过拒答红线 | 拒答是否过于生硬、是否给了替代路径 |

排序原则是「先规则、后 judge」：能用检索命中、正则、执行结果判掉的样本，不要消耗 judge 调用，也不要让 judge 的噪声污染这些维度的信号。判断力有限的维度才需要 judge，这也正是 judge 的失败率最高的地方。

论文给出了这条边界的实证：在 10 道数学题、交换位置共 20 次判定中，GPT-4 judge 把错误答案判成正确的比例，默认 prompt 是 14/20。更值得注意的是失败机制——**GPT-4 单独被问时能解出这道题，却在看到两个候选答案后被带偏**。也就是说，数学与多跳推理这类任务即使 judge 有知识也不可靠，应当交给执行器或专门的验证器（[[finetuning-10]] 的 verifier 就是训练侧的同源设计）。

### 2. 范式选择：pointwise / pairwise / 列表排序

| 范式 | 输出 | 适合 | 主要风险 |
| --- | --- | --- | --- |
| pointwise 打分 | 单条回答 1–5 分（或按 rubric 多维度） | 大规模回归、趋势监控、绝对阈值初筛 | 分数聚集在 4–5；换 judge 版本后整体平移；对细微差别不敏感 |
| pairwise 比较 | A 胜 / B 胜 / 平局 | 模型与 prompt 的 A/B 决策、门禁对比 | 组数随候选数平方增长；位置偏差直接变成胜率偏差 |
| 列表排序 | 把 $k$ 个候选一次排序 | 候选多、想一次拿到排序 | 位置偏差更强且更难做交换校正；$k$ 大时长上下文稀释注意力 |

工程上的组合是「用 pairwise 做决策，用 pointwise 做监控」：门禁比较两个版本时用成对比较（相对判断更稳、平局有明确语义），日常趋势看 pointwise 分布（可扩展性好）。论文对 single-answer grading 的评价是双向的：它给出相对稳定的内部 rubric、与人类的一致率并不低，但**绝对分数在更换 judge 模型时比相对结果更容易波动**，且难以辨别特定样本对之间的细微差别。

### 3. rubric 与 prompt：把评分标准做成可判定的量

rubric 写不到「可判定」就等于没写。三件事必须落实：

1. **每档有锚点描述**，且锚点描述的是可观察特征（是否覆盖了 X 点、是否给出了可执行的步骤、是否引用了给定文档），不是形容词（「很好」「较差」）。
2. **给参考答案或要点清单**（reference-guided）：论文的数学题判错率因此从 14/20 降到 3/20，是三种手段里最强的一种。
3. **把风格与内容拆成独立维度**，否则风格偏差会串到总分上。

prompt 的结构按「先证据、再理由、后结论」排：先让 judge 引用被评文本里的具体片段作为证据，再写判断理由，最后输出结构化 JSON。理由是链式判断把打分从一次直觉输出变成一次小推理，同时让证据字段成为可审计的抓手；JSON 则是为了解析与离线复算。只要求「给个分数」，得到的是尺度漂移最快的那种分数。

### 4. judge 模型选择

- **能力下限**：judge 至少要和被评模型同档，否则它会漏掉被评模型犯的错。
- **家族独立性**：judge 的家族不应与训练数据生成、prompt 合成、被评模型中的任何一环同源，否则同族风格被系统性抬高（管道级的偏好泄漏）。
- **专用 evaluator**：开源专用评测模型是可选项，好处是数据不出内网、可自托管、成本可控，并且支持用户自定义评分标准。Prometheus 2 的论文口径是：在 4 个 direct assessment 与 4 个 pairwise ranking 基准上，与人类及专有 judge 的相关性与一致性在所有被测开源 evaluator LM 中最高，同时支持直接评估、成对排序与自定义标准（论文自报）。
- **更换即重校准**：judge 换代等于换仪器，历史分数不能直接续用。

### 5. 偏差清单与纠正协议（本题核心）

位置偏差可以写成一个最小模型。设内容信号为 $s$（正表示回答 A 更好），$\beta$ 是对「第一个位置」的偏好强度，$\sigma$ 是 logistic 函数，则同一对回答在两个顺序下的判定概率分别是

$$p_1 = \sigma(\alpha s + \beta)\ (\text{A 在前}), \qquad p_2 = \sigma(\alpha s - \beta)\ (\text{A 在后})$$

交换位置后取平均：

$$\bar p = \frac{\sigma(\alpha s + \beta) + \sigma(\alpha s - \beta)}{2}, \qquad \left.\frac{\partial \bar p}{\partial \beta}\right|_{\beta=0} = 0$$

一阶项抵消，位置偏差的影响被压到二阶。这就是「交换位置」不是玄学而是消除一阶偏差的原因。

| 偏差 | 机制 | 纠正协议 | 监控指标 |
| --- | --- | --- | --- |
| 位置偏差 | 偏好固定位置（论文怀疑来自训练数据或自回归的从左到右结构） | 交换顺序各判一次，两次指向同一答案才判胜，否则记平局；或在大规模下随机化位置 | 位置一致率；偏向第一个位置的比例 |
| 长度 / 啰嗦偏差 | 把「更长」当成「更详细」 | rubric 显式声明长度不是质量；长度对齐后再评；把长度作为协变量做回归校正；分数与长度指标一起上报 | 分数与回答长度的 Spearman 相关 |
| 自我增强 / 同族偏差 | 对自身风格更熟悉，判定时偏向同族输出 | 换不同家族 judge；跨家族 panel 取多数或均值；用专用 evaluator | 各模型在本家族 judge 下的胜率差 |
| 谄媚 / 权威 / 从众偏差 | 被断言、专家口吻、多个先前答案带偏 | 双盲（不告知模型身份）；去除诱导性上下文；不把期望答案或其它 judge 的结论放进 prompt；要求引用被评文本作为证据 | 金标准集里「自信的错误答案」canary 的通过率 |
| 分数聚集 / 尺度漂移 | 档位锚点模糊，绝对分集中在高分区间 | 改用成对比较；细粒度 rubric；强制区分（排序或 n 选一）；固定锚点示例；报告分布而非只报均值 | 分数直方图、各档位占比随时间的变化 |
| 推理能力有限 | judge 自己不会做这道题，且会被候选答案误导 | 先自己解题再评判（CoT）；给参考答案（reference-guided）；直接交给可验证验证器 | 数学 / 多跳子集的判错率 |
| 风格偏差 | 偏好 bullet、正式语气等表面特征 | rubric 里写清目标风格；风格与内容分维度打分；必要时先规范化格式 | 成对样本中「内容相同、格式不同」的胜率 |
| 偏好泄漏（管道级） | 生成训练数据 / 合成 prompt 的模型与 judge 同源，评测被污染 | 让 judge 家族与生成链路中的所有模型家族都不同 | 离线分数与线上真实指标的长期背离 |

自我增强偏差要按保守口径处理：论文观察到的现象是**某些 judge 偏爱特定模型**（GPT-4 给自己高约 10% 的胜率、Claude-v1 给自己高约 25%），但论文同时明确说明，受数据量与差异幅度限制，**无法确定这构成 self-enhancement bias**。工程上按「可能存在」处理（跨家族 panel），而不是当成已证结论引用。

### 6. 聚合协议：把单次判定变成可复算的统计量

- **位置交换**：两次一致才算胜；不一致记平局。这是论文 §3.4 采用的保守方案，代价是判定变少、有效样本变小。
- **panel（jury）**：2–3 个不同家族的 judge，多数票或均值。它同时压低自我增强偏差与单模型噪声，代价是调用数线性增长。
- **多样本采样**：同一 prompt 跑 $m$ 次（温度 > 0），用均值或众数代替单次结果，用于估计 judge 自身的可重复性。
- **分层聚合**：先按类别 / 语言 / 长度分位分别聚合，再看总体。总体持平掩盖子集退化是回归门禁最常见的漏检。

### 7. 校准：一致率、随机基线与 κ

论文对「一致率」的定义是：**随机抽取两个不同类型的 judge（个体不同）在随机一道题上给出相同判断的概率**。这个定义里藏着两个必须一起报的口径：

- **是否计入平局与不一致票**。论文用两个 setup：S1 计入非平局、平局与因位置偏差产生的不一致票（不一致按平局计），随机基线 $R=33\%$；S2 只计非平局票，$R=50\%$。
- **Kappa 化**。把一致率换算成扣掉偶然一致的 $\kappa = (p_o - p_e)/(1 - p_e)$ 后，同一份数据的数字会明显变小（见下一节的换算）。报一致率时必须同时报随机基线，否则读者无法判断这个数字意味着什么。

还需注意：**人类标注本身有噪声**，人类之间的一致率就是现实的上界参考。论文在 MT-bench 上报告人类之间为 81%（第一轮，S2 口径），因此「judge 达到人类之间一致性的量级」是比「judge 达到 100%」更合理的验收标准。

校准流程：先人工标注一批样本（含边界样本：两个完全相同的回答、只被加长的列表、位置敏感对、语气自信但内容错误的答案、以及平局样本）→ 算总体与分项一致率、$\kappa$、平均绝对差 → 差异大的子集回到 rubric 与 prompt 迭代 → 定稿后这批样本冻结为金标准回归集 → judge 模型或 prompt 每次变更都在它上面重跑。

### 8. 版本、门禁与成本

- **可重复性先于准确性**：同一输入重复打分方差过大时，讨论准确率没有意义。先测方差，再定「分数差多少才算变」。
- **版本化**：judge 模型 id、prompt 版本、rubric 版本、解码参数一起构成 judge 版本号，与被评系统版本一起记录；换了任一环节就要重跑基线（[[evaluation-08]]）。
- **偏差看板**：位置一致率、分数与长度的相关性、人工抽检子集上的分歧率，按 judge 版本画趋势；离线分数与线上真实反馈背离时先看这三条（[[evaluation-09]]）。
- **成本**：单样本成本 $C = N \cdot K \cdot M \cdot (\bar T_{\text{in}} c_{\text{in}} + \bar T_{\text{out}} c_{\text{out}})$，其中 $K$ 是 judge 数、$M$ 是每 judge 的调用次数（位置交换即 $M=2$）。论文给出的一个直接量级：few-shot 示例虽然把位置一致率从 65.0% 提到 77.5%，但更长的 prompt 让 API 调用成本变为 4 倍，因此论文默认仍用 zero-shot。
- **省钱手段**：可验证前置门先过滤、金标准集全量 + 全量集抽样、结果按 (样本 hash, judge 版本) 缓存、长回答先做长度对齐与摘要。

| 数据规模 | MT-bench 80 题 8 类、58 名专家标注者、约 3K 票；Arena 一个月约 30K 票，抽 3K 单轮票分析，2114 个独立 IP | 论文 §2、§4.1 |

把上面的「一致率」换算成 $\kappa$（本人按论文表格数字换算，论文未直接给 $\kappa$）：

| 对比 | 一致率 | 随机基线 | $\kappa$ |
| --- | --- | --- | --- |
| GPT-4 judge vs 人类（S1） | 66% | 33% | 0.49 |
| GPT-4 judge vs 人类（S2） | 85% | 50% | 0.70 |
| 人类 vs 人类（S1） | 63% | 33% | 0.45 |
| 人类 vs 人类（S2） | 81% | 50% | 0.62 |

同一份数据，换口径就从 66% 变到 85%；再 $\kappa$ 化，85% 对应 0.70、66% 对应 0.49。这就是为什么「我们的一致率有 85%」这句话本身不构成验收证据。

位置交换的效果也可以解析地算出来（本人按 $\sigma$ 定义直接计算，$s=0$ 即两个回答等价）：

| 位置偏好强度 $\beta$ | 单次判定的「先出现者胜率」 | 交换后取平均 | 严格口径的位置一致率 | 记平局的比例 |
| --- | --- | --- | --- | --- |
| 0.5 | 0.6225 | 0.5000 | 0.4700 | 0.5300 |
| 1.0 | 0.7311 | 0.5000 | 0.3932 | 0.6068 |
| 1.5 | 0.8176 | 0.5000 | 0.2983 | 0.7017 |

读数方式：两个回答等价时，单次判定会给先出现者约 62%–82% 的胜率；交换取平均后精确回到 50.00%（一阶项严格抵消）。代价是严格口径下可判定的比例只剩 $2\sigma(\beta)(1-\sigma(\beta))$，$\beta=1$ 时约 39%，其余 61% 记平局——交换位置买到的是无偏，付出的是有效样本量与成本。

一致性口径的陷阱可以用一个人工构造的算例说明（**合成数据，仅用于演示口径差异，不代表任何真实实验**）：200 条 5 分制评分，judge 与人类的混淆矩阵如下。直接算一致率是 0.770，扣掉偶然一致后未加权 $\kappa = 0.673$，线性加权 $\kappa = 0.777$，Spearman $\rho = 0.877$，平均绝对差 0.250 分。

同一张表还能说明边际分布的杀伤力：若人工标注有 70% 落在 4 分，一个**恒定输出 4 分**的 judge 就有一致率 0.70，但 $\kappa = 0$——它没有提供任何区分信息。只看一致率会把这种空转的 judge 放进门禁。

最后是门禁的噪声地板（二项近似，本人计算）：$n=500$、通过率 $p \approx 0.8$ 时标准误约 1.79 个百分点，95% 置信区间半宽约 3.5 个百分点；$n=100$ 时半宽约 7.8 个百分点。所以「新版本通过率从 80% 掉到 77%」在 500 条样本上还不足以判退化，阈值必须留出这个余量——这一条直接决定 judge 分数能不能当门禁。

下面这段骨架把交换协议与偏差监控固化下来（judge 调用抽象成 `call_judge`，可离线用 mock 跑通）：

```python
import json
from statistics import mean

# spearman(xs, ys)：用平均秩处理并列值的 Spearman 相关，实现从略（约 15 行）

PAIRWISE_PROMPT = """你是评审。先写出判断依据，再在最后一行给出结论。
评分标准（rubric）：
{rubric}
问题：
{question}
回答 1：
{a}
回答 2：
{b}
只输出 JSON：{{"reason": "...", "evidence": "...", "winner": "A" | "B" | "tie"}}"""


def judge_pair(question, a, b, rubric, call_judge):
    """一次成对判定：a 固定在「回答 1」（即先出现）的位置。"""
    return json.loads(call_judge(PAIRWISE_PROMPT.format(rubric=rubric, question=question, a=a, b=b)))


def swap_protocol(question, ans_a, ans_b, rubric, call_judge):
    """保守方案：交换顺序各判一次，两次都指向同一答案才算胜，否则记平局。"""
    first = judge_pair(question, ans_a, ans_b, rubric, call_judge)   # ans_a 在前
    second = judge_pair(question, ans_b, ans_a, rubric, call_judge)  # ans_b 在前
    flip = {"A": "B", "B": "A", "tie": "tie"}
    second_as_a = flip[second["winner"]]          # 统一成「以 ans_a 为参照」的胜负
    consistent = first["winner"] == second_as_a
    return {"winner": first["winner"] if consistent else "tie",
            "consistent": consistent,
            "first_pass": first["winner"]}


def bias_report(rows):
    """rows 元素含 consistent / first_pass / score / answer_chars 四个字段。"""
    return {
        "n": len(rows),
        "position_consistency": round(mean(r["consistent"] for r in rows), 4),
        "win_rate_of_first_slot": round(mean(r["first_pass"] == "A" for r in rows), 4),
        "spearman_score_vs_length": round(spearman([r["score"] for r in rows],
                                                  [r["answer_chars"] for r in rows]), 4),
    }
```

用 mock judge 验证这套指标能读出被注入的偏差（固定随机种子，注入「第一个位置命中率 0.675、比 0.5 高 17.5 个百分点」，两个回答内容完全相同）：读到 `win_rate_of_first_slot = 0.6745`、`position_consistency = 0.4375`（理论上 $2 \times 0.675 \times 0.325 = 0.4388$）、`spearman_score_vs_length = 0.0124`（分数与长度本来就独立，应当接近 0）。三个指标各司其职：位置胜率暴露偏差，位置一致率给出「有多少样本真的判得动」（其余按保守协议记平局），长度相关性守住 verbosity 偏差的回归口。

## 常见追问

- **追问**：pointwise 与 pairwise 怎么选？
  - 要点：要「哪个版本更好」用 pairwise，要「质量趋势」和绝对阈值用 pointwise。理由是相对判断对尺度漂移不敏感、平局语义明确，而绝对分数在换 judge 版本时整体平移。实践中门禁用 pairwise，监控用 pointwise。
- **追问**：什么时候必须回到人工？
  - 要点：三类场景——判分会直接触发高风险动作（封禁、医疗、法律、对外承诺）；judge 与人工在该子集的一致率显著低于整体；rubric 本身要改（新维度无法由旧标注校准）。常规做法是抽检 + 分歧样本回流，而不是全量人工。
- **追问**：judge 与可验证验证器怎么组合？
  - 要点：先规则后 judge，规则能判的维度不进 judge；必须同时看的维度分开报告，不做加权求和（否则噪声会被权重藏起来）。顺序上是「执行器判定 → 规则过滤 → judge 评剩下的开放式维度」。
- **追问**：judge 的分数能跨版本比较吗？
  - 要点：不能。judge 模型、prompt、rubric、解码参数任一变化都会改变分数尺度。要比较就重跑基线，或在同一批次里同时评两版（成对比较）来消掉尺度项。
- **追问**：judge 与人类分歧时听谁的？
  - 要点：先看分歧是否集中在某个子集（长度、语言、类别），再看人类标注本身的一致率——人类之间只有约 81%（论文 MT-bench 口径），judge 达到同一量级说明它的分歧已经和标注噪声同量级。论文的做法值得借鉴：把 judge 的判断回放给人类，75% 被认为合理、34% 的人类愿意改选。
- **追问**：怎么判断 judge 被长度或风格带偏了？
  - 要点：把 live 流量上的分数与长度、格式特征算相关，看它随时间是否漂移；金标准集里放「内容相同、只被复述加长」和「内容相同、格式不同」的对照样本（论文的重复列表攻击就是这类探针），它们的通过率就是偏差的回归测试。

## 公司变体

**Perplexity**：从公开产品形态看，这题在他们语境里偏**工程实现**，而不是 rubric 的数学推导。原因是产品形态决定的：Perplexity 的答案是带引用的检索问答，判分里权重最高的是「回答是否被检索到的来源支撑、引用是否真实且对得上结论」——这部分可以用可验证手段（引用是否存在、片段是否支撑断言）先判掉，真正留给 judge 的是综合性、完整性与表达质量。同时作为面向消费者的搜索产品，单次查询的成本与延迟被压得很紧，所以这题容易顺着追问到：judge 怎么抽样、缓存键怎么设计、怎样用便宜的规则前置门把 judge 调用量降下来、以及 judge 模型家族与被评模型（自研 Sonar 系列）的关系如何处理（同源会引入管道级偏好泄漏）。仓库题单显示同一家还问了在线评估（[[evaluation-09]]），两条线大概率会被连起来问：离线 judge 的分与线上真实反馈对不上时，你先怀疑哪一侧。以上只依据公开产品形态与工程约束描述侧重，不涉及任何具体面试轮次。
