## 一句话答案

> 两趟扫描就够了：正向把前缀积写进输出数组（`out[0] = 1`、`out[i] = out[i-1] * nums[i-1]`），反向只用一个标量 `suffix` 从右往左把后缀积乘回去，总乘法次数 $3n-2$、时间 $O(n)$，输出数组之外只多一个整数。两条不变量要能当场背出来：正向结束时 `out[i]` 是 $i$ 之前所有元素的积；反向第 $i$ 步时 `suffix` 是 $i$ 之后所有元素的积。
> 面试官真正在测的是口径：输出数组不算额外空间（这是 $O(1)$ 额外空间成立的前提）、反向遍历不能写 `nums[::-1]`（它会静默复制整个数组，是现场最常见的失分点）、累加器要用 int64（「答案落在 32 位内」不等于「中间量落在 32 位内」）。
> 除法版不是更优解而是必须会讲的坑：要按零的个数分三种情况显式记账，`//` 在整除条件被破坏时会静默错一位；而且它要求输入可反向回放，真正的流式输入只能走「第一趟求总积与零计数、第二趟分块输出」这条路。
> 这题在生产里就是 leave-one-out 统计与序列 log 概率的前缀和：前者把逐元素重算的 $O(n^2)$ 压成 $O(n)$，后者解释了为什么概率必须存 log 之和而不是连乘——fp32 下 46 个概率 0.1 的 token 就连乘成 0。

## 面试官在考什么

- **能不能把「除自身以外」拆成一左一右两个可复用的量。** 结构就是 $out[i] = \prod_{j<i} nums[j] \times \prod_{j>i} nums[j]$，正反各扫一趟即可；不会拆的人会写成循环里对每个 $i$ 重新切片求积的 $O(n^2)$。
- **空间口径是否主动挑明。** 题目要求 $O(1)$ 额外空间，前提是「输出数组不计入额外空间」；不把这条先说出来，答案在面试官眼里就是不完整的。反例是 `nums[::-1]`（隐式复制）与「另开一个长度 n 的后缀数组」。
- **数值意识。** int32 上限 2.147×10^9、int64 上限 9.223×10^18（19 位十进制），19 个 10 连乘就越过 int64；即使答案保证在 32 位内，中间量仍可能到 6.44×10^10。能把累加器写成 int64 并给出终值断言，是这题最直接的区分点。
- **除法版会不会讲坑。** 零元素必须显式记账（个数 + 位置），不是靠 `try/except` 兜住；`//` 的向下取整语义与整除前提要说清；还要说明它要求输入可回放，与无除法版不是互相替代。
- **边界与验证是否落成断言。** 单个零、两个零、全零、全负数、含 ±1、$n = 2$、元素贴在 $|nums[i]| \le 30$ 边界，以及输入未被修改、没有长度与 $n$ 同阶的辅助数组，都应该在代码里显式检查（$n = 1$ 属非法输入，题面写的是 $n > 1$）。
- **能不能接住 follow-up。** 向量化与 $O(1)$ 额外空间互斥、并行前缀扫描的两种算法（Hillis–Steele 与 Blelloch）、GPU 上这是带宽题而不是算力题——按 Meta 的节奏（技术初筛 45 分钟 2 道题、onsite 两轮编程），写码要压在 15 分钟内，留时间给这些追问。

常见错误答案：

- 反向遍历写成 `for v in nums[::-1]`。切片会复制 $n$ 个元素，$O(1)$ 额外空间当场失效；正确写法是 `reversed(nums)` 或下标逆序。
- 只给除法版。零的个数为 1 时，`p / nums[i]` 会把所有位置都算成 0，只有零所在的位置等于非零元素之积；面试官接着问「不用除法怎么办」就只能现场重写。
- 把「答案在 32 位内」当成「全程可以走 int32」。这是本题最贵的一处静默错误：C++/Java 里它会表现为悄悄变号或变 0，而不是报错。

## 原理与推导

### 1. 开写前把五件事钉成口径

| 要问的事 | 默认口径 | 为什么必须先钉 |
| --- | --- | --- |
| 允许用除法吗 | 题面没禁，但 follow-up 一定禁 | 直接交无除法版可以省掉一轮重写 |
| 输出数组算额外空间吗 | 不算（本题 $O(1)$ 额外空间的前提） | 不先挑明，任何实现都可能被质疑空间不达标 |
| 结果保证落在 32 位内吗 | 题面隐含保证，配合 $\lvert nums[i] \rvert \le 30$、$n \le 10^5$ | 没有这条保证，最坏答案是 $30^{99999}$，约 1.48×10^5 位十进制，任何定长类型都装不下 |
| 输入可以被改写吗 | 生产默认不允许 | 答案是「只读输入 + 写输出数组」，原地改写 nums 会污染调用方 |
| $n = 1$ 怎么办 | 非法输入（题面写 $n > 1$） | 要么抛错要么返回 `[1]`，不能静默给出错值 |

据题库总导读整理的公开信息，Meta 部分 2026 年的流程新增了 AI 辅助编程轮，分三段：探索并修复问题、实现新功能、扩展并改进系统。这题的后两段正好是「把 $O(n)$ 额外空间压到 $O(1)$」与「补上溢出与零元素口径」，所以两趟版和除法版都要能当场互换，并说清各自的适用条件。

### 2. 主解：两趟扫描、两条不变量、$3n-2$ 次乘法

第一趟正向把前缀积落到输出数组：

$$out[0] = 1,\qquad out[i] = out[i-1] \times nums[i-1]\quad (1 \le i \le n-1)$$

**不变量**：第 $i$ 轮开始时 `out[i-1]` 等于 $nums[0..i-2]$ 的积（$i = 1$ 时是空积 1），本轮写回之后 `out[i]` 就是 $i$ 之前所有元素的积。这一趟 $n-1$ 次乘法。

第二趟反向用一个标量累乘后缀：

$$suffix \leftarrow 1;\quad out[i] \mathrel{*}= suffix;\quad suffix \mathrel{*}= nums[i]\quad (i = n-1, \dots, 0)$$

**不变量**：第 $i$ 轮开始时 `suffix` 等于 $nums[i+1..n-1]$ 的积，因此 `out[i]` 先被补上右半部分，再吸收 $nums[i]$ 供下一轮使用。$i = 0$ 之后没人再读 `suffix`，最后一次 `suffix *= nums[0]` 是死代码，省掉它才是 $3n-2$：正向 $n-1$ 次、反向 $n + (n-1)$ 次；不省就是 $3n-1$。

反向遍历只能用 `reversed(nums)` 或 `range(n-1, -1, -1)`。`nums[::-1]` 会分配一条长度 $n$ 的列表，$n = 10^5$ 时多出 0.8 MB（即 800000 B = 781.25 KiB；本文 KB/MB 按 1000 进制记，KiB/MiB 按 1024 进制记），而且它违反了题目刚要求的空间约束——这道题最典型的现场失分点就在这一行。

### 3. 除法版：零元素记账与整除语义

$p = \prod nums[i]$，按零的个数分三种情况（不是分两种，也不是靠异常兜底）：

| 零的个数 | 正确结果 | `p / nums[i]` 逐元素相除会怎样 |
| --- | --- | --- |
| 0 | $p / nums[i]$ | 正确 |
| 1（位置 $z$） | 只有 $out[z]$ 等于其余元素之积，其它位置全 0 | 全部算成 0，$z$ 处还踩除零 |
| $\ge 2$ | 全 0 | $p$ 已是 0，逐元素相除到处是 0/0 |

零元素必须显式记账（个数与位置），不要写 `try/except ZeroDivisionError` 把逻辑藏进异常路径。另一个细节是整数除法语义：Python 的 `//` 向下取整，只要 $p$ 不再是 $nums[i]$ 的整数倍（中间量被截断、元素是浮点、或符号处理不当），结果就会静默错一位——例如 `999999999 // 2` 得 499999999，而 $499999999 \times 2 = 999999998$。稳妥写法是符号与绝对值分开处理并断言整除。

更关键的是适用条件：无除法版要求输入可反向回放；真正的流式（不可回放）输入只能走「第一趟求总积与零计数、第二趟分块输出 $p / nums[i]$」。所以两个版本不是互相替代，而是「能否回放输入」这个场景开关下的选择。

### 4. 数字口径：暴力、溢出与下溢

**与暴力法的差距是这题的骨架。** 暴力对每个 $i$ 重算一遍，乘法次数 $n(n-1) \approx n^2$；两趟版是 $3n-2$。$n = 10^5$ 时是 9.9999×10^9 对 299998，相差 3.33×10^4 倍——两趟扫描消掉的正是前缀的重复计算。

**上溢。** int32 上限 2.147×10^9、int64 上限 9.223×10^18（19 位十进制），所以 19 个 10 的连乘（10^19）就越过 int64。题面的保证通常写成「任意前缀/后缀积落在 32 位内」，此时定长 int32 恰好在边界上；但只要契约弱化成「答案落在 int32 内」，反向那一趟的 `suffix *= nums[i]` 就会到「答案 × |nums[i]|」的量级，最坏 2.147×10^9 × 30 = 6.44×10^10，超 int32 但仍在 int64 内。结论是工程默认：**累加器一律 int64，最后再断言结果落在 int 范围内。**

**对策是搬到对数空间。** 前缀和 $\sum \log\lvert nums[i] \rvert$ 加负号个数的奇偶决定结果，代价是相对误差随 $n$ 线性累积：fp32 的 $\varepsilon = 1.19\times10^{-7}$，$n = 10^5$ 时最坏约 $n\varepsilon = 1.19\%$（实测顺序累加 10^5 个 log 的相对误差 6.9×10^−6，远小于上界，因为误差是随机游走而不是同向累加），而且 `log(0)` 未定义，必须单独走零计数分支。

**下溢。** fp32 最小正规数是 $2^{-126} = 1.175\times10^{-38}$，最小次正规数是 $2^{-149} = 1.401\times10^{-45}$：连乘 126 个 0.5 恰好落在正规数下界，127 个进入次正规，150 个就彻底变成 0（fp64 的最小正规数是 $2^{-1022} = 2.225\times10^{-308}$，1074 个 0.5 到最小次正规数，1075 个归零）。换成真实概率更严重：每个 token 的概率取 0.1 这种偏乐观的值，fp32 到第 46 个 token、fp64 到第 324 个 token 就归零，8k 上下文无论哪个精度都必然下溢。这就是生产里序列似然一律存 log 概率之和、绝不连乘概率的原因，也是这道玩具题在生产里必须换口径的落点。

### 5. 向量化、并行前缀扫描与 GPU 带宽

`np.cumprod` 或 `np.multiply.accumulate` 可以配合 `out=` 直接写进复用的输出数组，但有两个坑：① 整数 dtype 的溢出是**静默回绕**，不报错也不抛异常，必须显式 `dtype=object`（走 Python 任意精度整数，慢）或 float64 并自行校验；② 后缀那一趟要么再开一个长度 $n$ 的临时数组（$n = 10^5$、int64 时 800000 B = 781.25 KiB，直接违反 $O(1)$ 约束），要么退化成标量逆序写回，也就是逐元素 Python 循环。所以面试里的正确交法是两趟 Python，把向量化留作「如果额外空间放宽到 $O(n)$ 我会怎么改」的追问答案。

再往上一层是并行前缀扫描：Hillis–Steele 工作量 $n\log_2 n$、轮数 $\log_2 n$（$n = 10^5$ 时是 1.7×10^6 次操作、17 轮）；Blelloch 把工作量降到 $O(n)$（上下扫各一趟、2n−2 = 199998 次），代价是轮数变成 $2\log_2 n$（34 轮）。上到 GPU 之后这是带宽题而不是算力题：int32 每元素读 4 B、写 4 B，一次乘法折 0.25 FLOP/byte（按一次乘加 2 FLOP 计），比 H100 的 roofline 拐点 295 FLOPs/byte（bf16 dense 989 TFLOPs ÷ 3.35 TB/s）低约 1180 倍；$n = 10^5$ 的 400 KB 数据在 3.35 TB/s 下的读取下界只有 119 ns，而 kernel launch 本身是 µs 量级——这个规模上 GPU 不划算。

### 6. Meta 场景：从 leave-one-out 到投产三个坑

这个前缀/后缀结构在生产里就是 leave-one-out 统计：推荐与广告特征里「去掉当前这一条之后」的归一化量（总和减自身、留一均值、留一乘积）。朴素做法对每个元素重算一遍是 $O(n^2)$——$n = 10^5$ 时 10^10 次乘加，按后面实测的 56 ns/元素乘加口径约 9.4 分钟，而两趟版在 17 ms 量级，差 3.3×10^4 倍。同一套口径在三处复现：Llama 侧的序列 log 概率用前缀和而不是连乘（见下溢数字）；采样侧的 top-p 需要对排序后的概率做累积前缀再对过滤结果重新归一化（[[coding-05]]）；设施侧是缓存与索引结构里「按字节记账、按常数时间摘挂」的同一类取舍（[[coding-06]]）。向量检索里的对应关系也很直接：FAISS 这类库的 `IndexFlatL2` 对每次查询扫全量是 $O(N \cdot d)$，生产上换成 IVF/HNSW 这类近似索引，与本题「两层扫描替代逐元素重算」是同一种「先建可复用结构、再线性摊开」的思路。

上线时最容易踩的三个坑：

- **输入数组常常是共享的。** 一个 batch、特征缓存、embedding 矩阵的一行都可能被多处引用，原地改写 nums 会污染调用方；「$O(1)$ 额外空间」指的是输出数组之外的空间，不是允许破坏输入。
- **结果类型与溢出必须在接口契约里写死。** 保证落在 int32 就断言，不保证就走 log 空间或任意精度整数，并给上溢、下溢、零元素计数埋点；否则线上表现为「数字悄悄变 0 或变号」，没有任何报错。
- **规模超过内存时改用流式两趟**（先总积与零计数、再分块输出），这时无除法版不可用，必须在设计阶段就确认输入是否可回放。顺便一个量级对照：被省掉的那条长度 $n$ 的 int64 后缀数组是 800000 B（781.25 KiB），约等于 2.5 个 token 的 LLaMA-3-70B KV cache（320 KiB/token；LLaMA-3-8B 是 128 KiB，仓库统一常数）——单看不大，但在按并发预留资源的服务里，「每人一点」的 $O(n)$ 分配正是容量规划要掐掉的部分。

```python
# 参考实现：无除法、O(n) 时间、输出数组之外只多一个整数
def product_except_self(nums):
    n = len(nums)
    if n <= 1:                       # 题面写 n > 1，非法输入要显式处理
        raise ValueError('nums must have length > 1')
    out = [1] * n
    for i in range(1, n):            # 正向：out[i] = nums[0..i-1] 的积
        out[i] = out[i - 1] * nums[i - 1]
    suffix = 1                       # 反向：suffix = nums[i+1..n-1] 的积
    for i in range(n - 1, -1, -1):
        out[i] *= suffix
        if i:                        # i == 0 之后没人读 suffix，这一步是死代码
            suffix *= nums[i]
    return out


def with_division(nums):
    """除法版：零的个数 + 位置显式记账；整除断言挡住 // 的向下取整。"""
    n = len(nums)
    zeros = [i for i, v in enumerate(nums) if v == 0]
    if len(zeros) >= 2:
        return [0] * n
    if len(zeros) == 1:
        z = zeros[0]
        out = [0] * n
        rest = 1
        for j, v in enumerate(nums):
            if j != z:
                rest *= v
        out[z] = rest
        return out
    total = 1
    for v in nums:
        total *= v
    for v in nums:
        assert total % v == 0, 'p 不是 nums[i] 的整数倍，// 会静默错一位'
    return [total // v for v in nums]


def brute(nums):                     # O(n^2) oracle，只用于小规模对照
    return [__import__('math').prod(nums[:i] + nums[i + 1:]) for i in range(len(nums))]
```

```python
# 定向用例 + 随机对照 + 两条不变量
import random

directed = [
    ([1, 2, 3, 4], [24, 12, 8, 6]),
    ([1, 0], [0, 1]),                    # n = 2 且含零
    ([0, 0], [0, 0]),                    # 两个零
    ([0, 0, 3, 4], [0, 0, 0, 0]),        # 两个零：全 0
    ([0, 1, 2, 3], [6, 0, 0, 0]),        # 单个零：只有零位置非 0
    ([-1, -2, -3, -4], [-24, -12, -8, -6]),
    ([-1, -2, -3], [6, 3, 2]),           # 符号由负号个数奇偶决定
    ([1, -1, 1, -1], [1, -1, 1, -1]),    # 含 ±1
    ([-1, 1, 0, -1], [0, 0, 1, 0]),      # 零在中间
    ([30, -30], [-30, 30]),              # 元素贴在 |nums[i]| <= 30 边界
    ([2, 2, 2], [4, 4, 4]),
    ([2] * 31, [2 ** 30] * 31),          # 答案 2^30 = 1073741824，仍在 int32 内
    ([2] * 32, [2 ** 31] * 32),          # 答案 2^31 = 2147483648 = int32 上限 + 1，越界一个单位
    ([-2] * 32, [-2 ** 31] * 32),        # 答案恰好等于 int32 下限 -2147483648
]
for nums, want in directed:
    assert product_except_self(nums) == want and with_division(nums) == want

random.seed(20260928)
for t in range(1000):
    n = random.randint(2, 40)
    pool = [0, 0, 0, 0, 1, -1, 2, -2, 30, -30] if t % 3 == 0 else [1, -1, 2, -2, 30, -30]
    nums = [random.choice(pool + [random.randint(-30, 30) for _ in range(4)]) for _ in range(n)]
    want = brute(nums)
    assert product_except_self(nums) == want and with_division(nums) == want

probe = [0, -1, 30, 2, -2, 0, 7]
snapshot = list(probe)
product_except_self(probe)
with_division(probe)
assert probe == snapshot, '输入被改写了'          # 不变量 1：nums 逐元素未变
# 实测：14 组定向用例 + 1000 组随机（零比例人为调高）全部与 O(n^2) oracle 逐位一致
# 其中 [2] * 32 的答案是 2^31 = 2147483648，正好比 int32 上限大 1——用它标出契约边界
```

```python
# 溢出与下溢的复算（numpy 2.2.6）
import numpy as np
a = np.full(12, 30, dtype=np.int32)
print(np.multiply.accumulate(a, dtype=np.int32)[-1])   # 403968000（30^12 静默回绕）
print(np.multiply.accumulate(a.astype(object))[-1])    # 531441000000000000（真实值）
x = np.float32(1.0)
for _ in range(150):
    x = np.float32(x * np.float32(0.5))
print(x)                                               # 0.0：126 个仍在正规数内，150 个归零
print(next(k for k in range(1, 400) if np.float32(0.1) ** k == 0))   # 46（fp32）
print(next(k for k in range(1, 400) if 0.1 ** k == 0.0))             # 324（fp64）
```

除法版的落坑点也实测过：`999999999 // 2` 得 499999999，而 499999999 × 2 = 999999998，差一位且不报错。numpy 的溢出还有一个陷阱：不显式写 `dtype` 时，Linux 上 int32 数组会被提升到平台整数，`np.multiply.accumulate(a)` 看起来「没溢出」，这个坑必须显式 `dtype=np.int32` 才能复现——所以生产代码里 dtype 要写死，不能靠默认。

## 常见追问

- **追问**：为什么反向遍历不能写 `nums[::-1]`，它和 `reversed(nums)` 有什么区别？
  - 要点：切片会新建一条长度 $n$ 的列表，`reversed()` 返回迭代器、不复制。$n = 10^5$ 时这一行多 0.8 MB，正好把题目要求的 $O(1)$ 额外空间变成 $O(n)$；实测 tracemalloc 峰值从 0.763 MiB 涨到 1.526 MiB，差额就是这条数组。
- **追问**：如果允许用除法，怎么写才不出错？
  - 要点：分三种情况；先数零的个数并记住位置，1 个零时只有零位置非 0，≥2 个零时全 0；然后才轮到 $p / nums[i]$。整数除法要断言整除，符号与绝对值分开处理，否则 `//` 的向下取整会静默错一位。还要说明它要求输入可回放：真正流式的输入只能「先总积与零计数、再分块输出」。
- **追问**：结果保证落在 int32 内，为什么累加器还要用 int64？
  - 要点：保证落在 32 位内的是**答案**，不是中间量。反向那一趟的 `suffix *= nums[i]` 在弱契约下可达 2.147×10^9 × 30 = 6.44×10^10，超 int32；19 个 10 连乘就越过 int64。工程默认是 int64 累加 + 终值断言，「答案在 32 位内」不等于「中间量在 32 位内」。
- **追问**：数会溢出成天文数字，怎么在数据结构层面绕开？
  - 要点：搬到对数空间，前缀和 $\sum \log\lvert nums[i] \rvert$ 加负号个数的奇偶，代价是相对误差随 $n$ 线性累积（fp32 的 $\varepsilon = 1.19\times10^{-7}$，$n = 10^5$ 最坏约 1.19%，实测顺序累加是 6.9×10^−6），且 log(0) 未定义要单独走零计数分支。这正对应生产里序列似然存 log 之和而不是概率连乘：fp32 下 46 个概率 0.1 就下溢为 0，8k 上下文的连乘在 fp64 下也撑不住（324 个归零）。
- **追问**：能不能用 NumPy 向量化，把两趟都写成 `cumprod`？
  - 要点：能但要付代价。前缀那趟可以 `out=` 复用输出数组；后缀那趟要么再开长度 $n$ 的临时数组（$n = 10^5$、int64 时 800000 B = 781.25 KiB，违反 $O(1)$），要么退化成标量逆序写回。另外整数 dtype 的溢出是静默回绕（30^12 在 int32 里是 403968000，真实值 531441000000000000），要 `dtype=object` 或 float64 并自行校验。实测只做正向一趟的 `np.multiply.accumulate` 比纯 Python 快约 5 倍（3.84 ms 对 19.10 ms，$n = 10^5$）。
- **追问**：如果数据大到内存放不下呢？
  - 要点：改成流式两趟：第一趟只求总积与零的个数（$O(1)$ 空间），第二趟分块重放原输入、按块输出 $p / nums[i]$，并处理唯一零位置的正确值。这条路线的前提是输入可回放；不可回放就只能落盘或接受近似。此时无除法版不可用，要在设计阶段就确认这个前提。
- **追问**：并行或 GPU 上这题会变成什么？
  - 要点：并行前缀扫描。Hillis–Steele 工作量 $n\log_2 n$、轮数 $\log_2 n$（$n = 10^5$ 是 1.7×10^6 次操作、17 轮）；Blelloch 工作量 $O(n)$ 但要上下扫两趟。GPU 上它是带宽题：int32 每元素读 4 B 写 4 B、一次乘法折 0.25 FLOP/byte，比 H100 的 295 FLOPs/byte 拐点低约 1180 倍，而 $n = 10^5$ 的读取下界只有 119 ns，远小于 kernel launch 开销，所以这个规模不该上 GPU。
