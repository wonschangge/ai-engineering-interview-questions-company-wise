## 一句话答案

> 双指针加计数：右指针每步把一个字符纳入窗口，`have` 记录「计数已达标的字符种类数」，`need` 是 T 的不同字符**种类数** $\text{len}(\text{Counter}(T))$ 而不是 $|T|$；当 `have == need` 时窗口就是 T 多重集的一个覆盖，此时用 `while` 连续左移并在每一步刷新最优长度。时间 $O(|S| + |T|)$、额外空间 $O(k)$：右指针共前移 $|S|$ 次、左指针总共最多前移 $|S|$ 次（本机实测合计恰好 $\approx 2|S|$），计数结构只与字符集大小 $k$ 有关；$k \le 128$ 时用长度 128 的定长 int 数组就是真正的 $O(1)$ 空间（1080 B），只有 Unicode 语料才退回 dict。
> 三条不变量决定了实现的对错：覆盖是多重集覆盖（重复字符必须逐字符满足，位掩码与集合都不行）、`have` 只在计数**跨过阈值的那一步**增减（写成 `>=` 或每步重算都会错或变慢）、收缩必须 `while`（`if` 版在 T 含重复字符时会漏掉更短窗口，实测反例见下）。
> 三个必然追问的落点：T 变成上万个模式时先 Aho-Corasick 定位候选再在事件序列上滑窗；S 是 10 GB 日志时用单遍在线版只保留窗口与 $O(k)$ 计数，但返回内容必须缓冲窗口、因此要给窗口长度上界或接受二次扫描；S 是 UTF-8 字节流时必须先解码成 code point 再开窗，按字节开窗会把一个 code point 切成两半产生 U+FFFD。

## 面试官在考什么

- **能不能把不变量写出来，而不是背模板。** 覆盖的定义是 $\forall c \in T,\ \text{cnt}(c) \ge \text{need}(c)$。这一条直接判掉位掩码（只能表达「出现过」，不能表达重复次数）与集合方案，也解释了为什么 `have` 必须按字符逐个维护。
- **`need` 的口径。** 必须是不同字符种类数。把 `need` 写成 `len(T)` 是这道题最典型的错：T 含重复字符时阈值永远达不到，窗口一次都收不紧（T = `AAB` 时正确 `need = 2`，写成 `len(T)` 就是 3）。
- **增量更新（delta）是否理解。** 加入 `s[right]` 时 `cnt[c] += 1` 并且只在 `cnt[c] == need[c]` 那一步 `have += 1`；移出 `s[left]` 时只在 `cnt[c] == need[c] - 1` 那一步 `have -= 1`。写成 `>=`、或者每步重算 `all(cnt[c] >= need[c])`，都说明只是在背代码。
- **收缩语义。** `while` 不是经验写法，而是不变量的直接翻译；能说出为什么「右指针一步只引入一个字符，窗口失效只可能由一次左移造成」的人，才算真懂双指针的单调性。
- **复杂度与常数。** 时间 $O(|S| + |T|)$ 的依据是两个指针各自单调（总前移量 $\le 2|S|$），空间 $O(k)$ 只看字符集不看 $|S|$。热路径用定长数组躲开哈希与对象分配；`Counter(s[left:right+1]) >= need` 这种写法会把每次判定变成 $O(\text{窗口长度})$，整体退化到 $O(|S|^2)$。
- **规模与字符定义。** 追问会立刻走到 T 上万模式、S 是 10 GB 日志、S 是 UTF-8 字节流这三条线：能不能在动手前问清「字符」是 code point、grapheme cluster 还是 token。

常见错误答案：

- 用 `have = len(T)` 或用一个 64 位掩码判定覆盖，测试用例里 T 全是不同字符时全过，一遇到 `AAB` 这类 T 就错。
- 用 `if` 代替 `while` 收缩，或者每次判定直接比较切片后的 `Counter`——前者得到的是错误答案，后者正确但复杂度退化，两种都会在面试里被追问到。

## 原理与推导

### 1. 先把口径写死

- 窗口是左闭右闭的 $[left, right]$，长度 $right - left + 1$。
- 覆盖成立当且仅当窗口内每个字符的计数都不小于 T 中的计数（多重集覆盖）。
- 返回最左的最短窗口；不存在时返回空串；T 为空按约定返回空串。
- 窗口单位默认 code point（下面第 6.3 节讨论其它单位）。

### 2. 两条不变量

**(a) `have == need` 等价于窗口是 T 的一个覆盖。** 定义 $K_{\text{ok}} = \{c : \text{cnt}(c) \ge \text{need}(c)\}$，`have` 就是要维护 $|K_{\text{ok}}|$。维护规则是：`cnt[c]` 从 `need[c] - 1` 涨到 `need[c]` 时 `have += 1`，从 `need[c]` 掉到 `need[c] - 1` 时 `have -= 1`。只要这两条只在「跨过阈值」的那一步触发，`have` 就恒等于 $|K_{\text{ok}}|$，任何时刻都比较安全；`>=` 会让重复字符把同一种类重复计入，窗口还没覆盖就被判为有效。

**(b) 收缩必须 `while` 而不是 `if`。** 反例（本机搜索到的一例）：`S = CABACBBC`、`T = BC`。`if` 版在 `right = 2` 处得到一个有效窗口 `CAB`（长度 3）后只左移一位就继续前进，此后再没回到能刷新答案的状态，最终返回 `CAB`；`while` 版在同一步一直收缩到「再移一步就失效」，并在 `right = 5` 处刷新为 `CB`（长度 2），与暴力解一致。T 含重复字符时更明显：`S = ABAABABBAB`、`T = BBB`，`if` 版返回 `ABAABAB`（长度 7），`while` 版返回 `BABB`（长度 4）。

**为什么 `while` 恰好正确、而不是试出来的。** 右指针每一步只引入一个字符，而覆盖是单调的：窗口扩大不会破坏覆盖，缩小才可能破坏。因此加入 `s[right]` 之后窗口要么本来就无效、要么已经是覆盖；一旦是覆盖，就应当一直左移直到「再移一步就失效」为止，这个「直到」就是 `while have == need`。循环条件不是经验常数，而是不变量的直接翻译。收缩循环内部要**先记录答案、再移出字符**，顺序反了就会漏掉刚好等于当前窗口的最优解。

### 3. delta 更新：只在计数跨过阈值那一步动 `have`

```text
right 前移：cnt[c] += 1；if cnt[c] == need[c]: have += 1
left  前移：cnt[c] -= 1；if cnt[c] == need[c] - 1: have -= 1
```

对不在 T 中的字符，`need[c] = 0`：加入时 `cnt[c]` 变成 1，而 `1 == 0` 为假，`have` 不动；移出时 `cnt[c]` 变成 0，而 `0 == -1` 为假，`have` 也不动。这一条让窗口里可以自由夹带无关字符，不需要特判。

逐步跟踪 `S = ADOBECODEBANC`、`T = ABC`（`need = 3`），只列 `have` 发生变化或刷新最优的步骤：

| right | s[right] | 纳入后 have | while 收缩次数 | 本轮刷新 | 收缩后 left |
| --- | --- | --- | --- | --- | --- |
| 0 | A | 1 | 0 | 无 | 0 |
| 3 | B | 2 | 0 | 无 | 0 |
| 5 | C | 3 | 1 | `ADOBEC`（长度 6） | 1 |
| 10 | A | 3 | 5 | 无 | 6 |
| 12 | C | 3 | 4 | `BANC`（长度 4） | 10 |

最终答案是 `BANC`。注意 `right = 10` 那一行的 5 次收缩一次都没刷新最优（窗口 `DOBECODEBA` 长度 10），而 `right = 12` 收缩到 `left = 9` 时窗口恰好是 `BANC`——这两行就是「记录必须在收缩循环内部、且循环要跑到底」的证据。

### 4. 复杂度：$2|S|$ 的常数与 $O(k)$ 的空间

右指针前移 $|S|$ 次，左指针在 `while` 里一共最多前移 $|S|$ 次（left 只增不减，且不超过 right + 1），所以指针操作总数是 $2|S|$ 量级。本机实测（随机字母流、T 取 26 个字母）：$|S| = 10^4 / 10^5 / 10^6$ 时左右前移合计为 $1.992|S|$、$1.999|S|$、$2.000|S|$；最坏形状 `a`×100000 + `b`（T = `ab`）也是 $2.000|S|$。加上构建 `need` 的 $O(|T|)$，时间就是 $O(|S| + |T|)$。

计数结构的大小只取决于字符集 $k$，与 $|S|$ 无关：$k \le 128$ 时用 `list` 长度 128（实测 1080 B），是真正的 $O(1)$ 空间；字典版的空间是 $O(k)$（`cnt` 里每个不同字符一个键），实测 `dict` 在 $k = 26 / 200 / 2000$ 时为 1176 / 9312 / 73816 B。**复杂度口径是摊还而不是绝对 $O(1)$**：哈希表定位摊还 $O(1)$，链表式结构的指针操作才是严格 $O(1)$（[[coding-06]] 实测 5 万到 100 万条目下单次 `get` 耗时基本不变，而 `put` 因节点分配与 cache 局部性涨 1.6 倍）。这正是热路径用定长数组加 `ord` 索引的理由：躲开哈希与对象分配的常数，而不是改善渐近。

「每步重算」的代价要能说清：`all(cnt[c] >= need[c] for c in range(k))` 把每次判定变成 $O(k)$，最坏形状下每个位置都要扫满 $k$ 个条目。本机实测（$k = 128$、26 字母随机流）整体慢 40.4×（$|S| = 10^4$）与 42.7×（$|S| = 10^5$）；ASCII 域只是常数惩罚，Unicode 语料 $k$ 上万时才会真正超时。

### 5. Python 实现的三个退化写法

1. **答案判定里出现 `s[left:right+1]` 或 `Counter(...) >= need`**：单次判定 $O(\text{窗口长度})$，窗口很长时整体变成 $O(|S|^2)$。实测 `s = a×n + b`、`T = ab` 时（最小窗口是整串尾巴），切片版每字符耗时随 $n$ 线性增长：$n = 2000 \to 16000$ 时 59,482 → 558,894 ns/字符（每翻倍 $n$ 翻倍），比同形状的线性版（本机约 350 ns/字符）慢 169.9× → 1596.8×，而两者答案相同——它错在复杂度不在结果。
2. **`need` 用 `len(T)`**：T 含重复字符时窗口永远收不紧，返回空串或过长窗口。
3. **在循环里分配 `Counter`**：每次新建计数对象会把 GC 压力带进热路径；正确做法是原地维护 `cnt`、`have`、`need`、`best` 四个量。

### 6. 三个必然追问

#### 6.1 T 变成上万个模式

题意从「T 的字符多重集」变成「上万个词表模式」时，滑窗骨架不变，变的是「什么事件让窗口有效」。做法是先用 Aho-Corasick 对 S 做一遍扫描，把每个模式的出现位置列成候选事件序列，再在这条事件序列上做同一套双指针：计数单位从字符换成模式，`need` 是模式数，`have` 只在某个模式的计数跨过阈值时增减，复杂度是 $O(|S| + \text{匹配数})$，而不是 $O(|S| \times \text{模式数})$。模式数极大且只要求判定存在性时，可以先用位图或布隆过滤器预筛（倒排表取最短表再校验），代价是假阳性必须在校验阶段剔除。这里的思路与本题完全同源：把「每次重扫一遍」换成增量维护。

#### 6.2 S 是 10 GB 日志

双指针本来就是单遍算法，左右指针都单调，所以在线版可以直接吃掉流式输入：只需要窗口缓冲、$O(k)$ 计数、以及最优窗口的**长度与端点**。关键取舍在这里——**精确的最小窗口可以单遍求出，但要返回窗口内容就必须缓冲整段窗口**，最坏情况下（整条输入构成一个窗口）缓冲是 $O(|S|)$。守住内存只有两条路：给窗口长度设上界 $L$（超过上界即判定不存在，此时回答的是「是否存在长度 $\le L$ 的窗口」），或者第一遍只记录长度与端点、第二遍再取内容（等价于要求可重放或随机访问）。换句话说单遍流式能给你「长度」，给不了「内容」，除非接受 $O(L)$ 的缓冲。

数字口径（CPython 3.10 单线程纯 Python，299.5 ns/字符；本篇 GB 一律按 $1\ \text{GB} = 10^9$ B 的十进制，而 KV cache 的 320 KiB 是 $320 \times 1024 = 327{,}680$ B 的 1024 进制）：10 GB 按 ASCII 1 B/字符算是 $10^{10}$ 个字符，约 2995 s ≈ 49.9 min；同一 10 GB 若是中文 UTF-8（3 B/字符）是 $3.33 \times 10^9$ 个字符，约 998 s ≈ 16.6 min；混合 1.5 B/字符约 1997 s ≈ 33.3 min。对照 H100 3.35 TB/s 的带宽，读 10 GB 只要 $10^{10} / (3.35 \times 10^{12}) \approx 3.0$ ms（估算口径：纯带宽下限，未计 IO 与解码），也就是瓶颈差在每字符常数上，与带宽无关。

把题目接回生产：滑动窗口计数是限流器的近亲，近似口径的收益很实在——Cloudflare 对 4 亿次请求、27 万个不同来源的分析中只有 0.003% 被错误放行或错误限流，估计速率与真实速率的平均差距 6%，没有来源在低于阈值时被误限（[[coding-07]]）。但本题要求的是**精确覆盖，没有近似余地**：近似计数换来的是「两个数就能表示窗口状态」，而精确最小窗口必须保留逐字符计数。这条对比本身才是考点。另一把尺子：10 GB（十进制 $10^{10}$ B）约等于 70B 模型 3.05 万 token 的 KV cache（320 KiB/token，[[llm-internals-02]]；若把 10 GB 读成 10 GiB，同一笔账是 3.28 万 token），滑动窗口的字节流规模与推理内存是同一个量级，这也是它值得被追问的原因。

#### 6.3 S 是 UTF-8 字节流，「字符」到底指什么

同一段文本在不同语言里的「字符」不是一回事（实测）：

| 样本 | Python `str`（code point） | Java `char`（UTF-16 code unit） | UTF-8 字节 |
| --- | --- | --- | --- |
| `A` | 1 | 1 | 1 |
| `中` | 1 | 1 | 3 |
| `🙂` | 1 | 2 | 4 |
| `é`（NFC 单码点） | 1 | 1 | 2 |
| `e` + U+0301（组合音标） | 2 | 2 | 3 |
| ZWJ 家庭 emoji `👨‍👩‍👧`（3 人） | 5 | 8 | 18 |

Python 的 `str` 是 code point（emoji 算 1 个），Java 的 `char` 是 UTF-16 code unit（emoji 算 2 个），C++ 的 `char` 是字节，而 S 在生产里常常就是 UTF-8 字节流。**按字节开窗会把一个 code point 切成两半**：把 `中文` 的 6 个字节在第 1 / 2 字节处切开、按 `errors='replace'` 解码只得到 U+FFFD，在第 4 / 5 字节处切开得到 `中` 加一个 U+FFFD，只有切在第 3 字节（对齐边界）才是 `中` 与 `文`（严格模式下这些切分直接抛 `UnicodeDecodeError`）。正确做法是用增量解码器把字节流还原成 code point 再开窗（[[coding-09]] 实测：`codecs.getincrementaldecoder('utf-8-sig')()` 喂入任意 1/2/3 字节切分都能完整还原），退一步至少要求窗口端点落在非连续字节上（UTF-8 的连续字节是 `0b10xxxxxx`，端点不能是它们）。

窗口单位还要显式选一次：code point、grapheme cluster（组合音标、ZWJ emoji、肤色修饰都算一个「用户看见的字符」）、还是 tokenizer 的 token。**跨语言的 token 换算不是常数**：同一份「1000 字符」预算，英文是 203 token、中文是 783 token（[[coding-10]] 实测，`o200k_base` 口径，比值 3.86×）。所以「最小窗口」按字符计价还是按 token 计价会直接改变最优解——本机构造的例子：同一条 S 里按字符最短的是 `a中b`（3 字符 / 3 token），按 token 最短的是 `axxb`（4 字符 / 2 token）。如果这道题的窗口最终要喂给模型，计价单位就必须在动手前定死，否则「最优」是假的（[[coding-04]]）。

## 数值与代码验证

```python
from collections import Counter

def min_window(s, t):
    """双指针 + 定长数组计数：时间 O(|S| + |T|)，额外空间 O(k)。

    need[c] 是字符 c 在 T 中的计数；have 是「计数已达标的字符种类数」。
    """
    if not s or not t:
        return ''
    need = [0] * 128
    for ch in t:
        if ord(ch) >= 128:
            raise ValueError('非 ASCII 域，请用 dict 版')   # Unicode 走 dict
        need[ord(ch)] += 1
    kinds = sum(1 for x in need if x)      # need = 不同字符种类数，不是 len(T)
    cnt = [0] * 128
    have = 0
    left = 0
    best_len = len(s) + 1
    best_l = 0
    for right, ch in enumerate(s):
        o = ord(ch)
        cnt[o] += 1
        if cnt[o] == need[o]:              # 只在跨过阈值的那一步
            have += 1
        while have == kinds:               # 收缩必须 while，且先记录后移出
            if right - left + 1 < best_len:
                best_len = right - left + 1
                best_l = left
            o = ord(s[left])
            cnt[o] -= 1
            if cnt[o] == need[o] - 1:
                have -= 1
            left += 1
    return '' if best_len > len(s) else s[best_l:best_l + best_len]


def min_window_generic(s, t):
    """dict 版：Unicode 域（k 为不同字符数），口径与数组版完全一致。"""
    if not s or not t:
        return ''
    need, cnt, have, left = Counter(t), {}, 0, 0
    best_len, best_l = len(s) + 1, 0
    for right, ch in enumerate(s):
        cnt[ch] = cnt.get(ch, 0) + 1
        if cnt[ch] == need[ch]:
            have += 1
        while have == len(need):
            if right - left + 1 < best_len:
                best_len, best_l = right - left + 1, left
            c = s[left]
            cnt[c] -= 1
            if cnt[c] == need[c] - 1:
                have -= 1
            left += 1
    return '' if best_len > len(s) else s[best_l:best_l + best_len]


def covers(w, t):
    cw, ct = Counter(w), Counter(t)
    return all(cw[c] >= k for c, k in ct.items())


def brute(s, t):
    """对拍用暴力解：按窗口长度递增枚举，第一个覆盖就是最左最短。"""
    if not s or not t:
        return ''
    n = len(s)
    for L in range(len(t), n + 1):
        for l in range(n - L + 1):
            if covers(s[l:l + L], t):
                return s[l:l + L]
    return ''


def check(s, t):
    """三断言加最左约定；brute 按长度递增枚举，天然给出最左最短。"""
    mw = min_window if max(map(ord, s + t), default=0) < 128 else min_window_generic
    w = mw(s, t)
    if w:
        assert covers(w, t)                        # 1) 计数满足 need
        assert not any(covers(s[l:l + L], t)       # 2) 不存在更短的有效窗口
                       for L in range(1, len(w)) for l in range(len(s) - L + 1))
        i = s.find(w)
        assert 0 <= i and i + len(w) <= len(s)     # 3) 端点落在 [0, |S|)
    assert w == brute(s, t)
    return True
```

## 常见追问

- **追问**：为什么不能用位掩码或哈希集合判定覆盖？
  - 要点：覆盖是多重集覆盖。64 位掩码只能表达「字符出现过」，T = `AAB` 时它和 T = `AB` 无法区分，会返回过短却无效的窗口。集合同理。只有逐字符计数才能表达重复次数，这也是 `have` 要和 `need[c]` 比较而不是和 0/1 比较的原因。
- **追问**：`have` 的更新为什么必须写 `==`，写成 `>=` 会怎样？
  - 要点：`>=` 会让同一个字符种类在计数持续增长时被反复 `+1`，`have` 提前达到 `need`，窗口还没覆盖就被判为有效。实测反例 `S = BBBAABBB`、`T = BAAAA` 返回的 `BB` 连 A 都没有。移出侧同理：必须 `cnt[c] == need[c] - 1` 才 `have -= 1`，不能无条件减。
- **追问**：多个等长最小窗口，返回哪一个？
  - 要点：约定返回最左，实现上用严格小于 `if length < best_len` 更新（不写 `<=`）即可自然满足；等长窗口如果写 `<=` 就会返回最右。口径要写进函数注释，因为测试用例会同时覆盖两种情况。
- **追问**：T 是上万个模式而不是字符集，怎么办？
  - 要点：先 Aho-Corasick 单遍扫描 S 得到模式出现事件序列，再在事件序列上做同一套滑窗（计数单位从字符换成模式，`need` 是模式数），复杂度 $O(|S| + \text{匹配数})$。模式极多又只需判定存在性时用位图或布隆过滤器预筛加倒排校验，假阳性在校验阶段剔除。
- **追问**：S 是 10 GB 日志，还要精确答案吗？
  - 要点：双指针是单遍算法，在线版只保留窗口缓冲、$O(k)$ 计数和最优长度/端点即可求出精确最优**长度**；返回内容需要缓冲窗口，最坏 $O(|S|)$，所以要么给窗口长度上界 $L$（此时回答的是「存在长度 $\le L$ 的窗口吗」），要么第一遍记长度、第二遍取内容。不要把它和限流器的近似滑动窗口混为一谈：那套近似（4 亿请求下 0.003% 错放或错限、平均差 6%，[[coding-07]]）省内存但不满足精确覆盖。
- **追问**：S 是 UTF-8 字节流，直接按字节开窗行不行？
  - 要点：不行，会把 code point 切成两半产生 U+FFFD（`中文` 在第 1/2/4/5 字节处切开实测都会解出 U+FFFD，只有第 3 字节是对齐边界）。用增量解码器还原成 code point 再开窗，或保证端点落在字节边界。同时要显式选窗口单位：code point、grapheme cluster 还是 token——同一份 1000 字符预算英文 203 token、中文 783 token（[[coding-10]]），计价单位会改变谁是最优解。
