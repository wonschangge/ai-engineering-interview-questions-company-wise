## 一句话答案

> 接入方式只有三大类，差别在于「视觉信息在哪一步与语言混合」：
> ① **投影/适配器（adapter）**——视觉塔（ViT 式 patch 编码）先出特征，再经投影层映射成 LLM 的 token 嵌入，之后完全走语言模型的自注意力。工程上最常见，因为视觉塔与 LLM 可以解耦、独立升级，视觉嵌入还能离线缓存。
> ② **交叉注意力（cross-attention）**——LLM 的若干层插入对视觉特征的交叉注意力（Flamingo 式）。视觉 token 不进入自回归上下文，能省 KV，但架构改动大、训练更难。
> ③ **早融合/统一 token 化**——把图像 patch 与文本 token 拼成一个序列，用同一个 Transformer 处理（可引用 ViT 的 patch 化前提与 LayoutLMv3 式统一掩码预训练）。
> 视频的特殊变化可以概括成四件事：**帧采样策略**（选哪些帧比选多少帧更重要）、**时间位置编码**（时间维必须进入位置语义）、**token 预算爆炸**（帧数 × 每帧 token 数，动辄十万级，直接决定 KV 与延迟）、以及**音频轨与跨模态对齐**（真正的视频理解要联合语音/音乐/画面）。
> 可引用的工程口径来自 LongVILA：长视频场景下作者把问题拆成**训练系统、长上下文数据、以及训练流程**三条主线（并强调序列并行等系统能力是把长视频真正跑起来的前提）——这说明视频的瓶颈是**系统与数据工程**，不只是模型结构。

## 面试官在考什么

- **能否把「接入」讲成三条路线的取舍**，而不是只说「加一个投影层」。尤其要能说出各自的成本：早融合表达能力强但视觉 token 占据上下文；适配器最易工程化；交叉注意力省 KV 但改架构。
- **视觉 token 的数量账**是否算得出来：patch 数 = 像素面积 / patch 面积（再按合并倍率缩小），这条式子决定了延迟、KV 与可承受的帧数。
- **视频与图像的本质区别**：图像是「一次性」的空间理解，视频是**时空 + 因果**；因此需要帧间建模（时间注意力/时间位置编码）、关键帧选择（信息密度不均）、以及长上下文能力（把几十万 token 塞进模型，可引用 LongVILA 把长视频问题拆成系统/数据/流程三条主线的做法）。
- **工程侧的取舍**：分辨率换帧数（总 token 预算固定时如何分配）、前缀缓存（同一视频多次提问复用 KV）、以及抽帧与音频转写的**预处理管线**（可引用的对照是仓库既有多模态专题里「视觉编码本身不是瓶颈、瓶颈在视觉 token 进入 LLM 之后」的结论）。
- **评测**：视频问答、时序定位（temporal grounding）、长视频摘要；要注意「抽帧评测」与「真实流式理解」的差距。

**常见错误答案**

- 「把视频当一组图片分别编码再拼接」——忽略时间位置编码与帧间关系，模型无法回答「先发生了什么」。
- 「帧越多越好」——token 预算线性增长，延迟与 KV 不可承受；关键帧选择与分辨率-帧数权衡才是重点。
- 「多模态就是加一个投影层」——忽略训练阶段（对齐/指令微调）、数据配比与灾难性遗忘（纯视觉数据训练会损伤语言能力）。
- 「长视频只要把上下文扩到 1M 就行」——还要解决位置外推、注意力成本、以及训练系统的序列并行（可引用 LongVILA 的三条主线）。

## 原理与推导

### 1. 三条接入路线的对比

| 路线 | 视觉信息何时进入语言 | 优点 | 代价 | 典型代表 |
| --- | --- | --- | --- | --- |
| 适配器/投影 | 编码后投影为 token，进入自注意力 | 解耦、可缓存、易工程化 | 视觉 token 占用上下文与 KV | LLaVA 式、Qwen-VL 式 |
| 交叉注意力 | 在若干层以 cross-attn 注入 | 视觉 token 不进 KV，省显存 | 架构改动大、训练复杂 | Flamingo 式 |
| 早融合/统一 token | 与文本拼成同一序列从头处理 | 跨模态交互最充分 | 视觉 token 成本最高；需统一预训练 | LayoutLMv3 式、统一 Transformer |

**选择依据**：训练资源与升级节奏。适配器最适合「视觉塔与 LLM 分别迭代」的产品节奏，早融合最适合「跨模态强耦合」的任务（文档理解、图文混排）。

### 2. 视觉 token 的数量账（一切成本从这里出发）

$$N_{\text{patch}}=\frac{H}{p}\cdot\frac{W}{p},\qquad N_{\text{token}}=\frac{N_{\text{patch}}}{m^{2}}$$

图像：$1024^2$、$p=16$、$m=2$ ⇒ $4096/4=1024$ 个 token。
视频：$T$ 帧 × 每帧 $N_{\text{token}}$。取 $T=256$ 帧、每帧 256 token ⇒ 65,536 token；$T=544$、每帧 256 ⇒ 139,264 token。

这条式子决定了三件事：**KV 显存**（139,264 × 320 KiB ≈ 42.5 GiB，70B 级口径）、**prefill 算力**（$2NP\approx19.5$ PFLOPs，8×H100 @ MFU 45% 约 5.5 s）、以及**上下文长度**（直接吃掉整个窗口预算）。

### 3. 视频特有的四个变化

1. **帧采样**：均匀采样会漏掉关键动作；常用做法是**场景切换检测 + 运动量/显著性打分**后再采样，并在答案需要细粒度时对局部做高帧率二次采样（两阶段：粗看全片 → 精看片段）。
2. **时间位置编码**：需要把「第几帧」编码进位置语义。可引用的做法是 M-RoPE 式的三维分解——把位置分解到时间、高、宽三个分量（时间分量在图像上固定、在视频上按帧推进），使同一套编码同时支持图像与视频。
3. **token 预算与分辨率-帧数权衡**：总预算固定时，$T\times N_{\text{token}}(H,W)$ 是一个守恒式——提高帧率就要降分辨率，反之亦然。任务不同最优分配不同（动作识别要帧率，文字识别要分辨率）。
4. **音频与跨模态对齐**：真实视频理解要联合语音（转写/说话人）、音乐与环境声、以及画面；跨模态对齐（谁在说、说什么、画面上在做什么）是难点，也是「视频理解」区别于「多帧图像理解」的地方。

### 4. 训练与系统

- **训练阶段**：① 对齐（冻结 LLM 训投影层）→ ② 多模态指令微调（联合训练）→ ③ 长视频/长上下文阶段。数据配比必须保留纯文本，否则语言能力退化（灾难性遗忘）。
- **系统**：长序列需要序列并行/上下文并行、激活检查点、以及分块注意力；可引用 LongVILA 的做法——它把长视频训练明确拆成**训练系统（含序列并行）、长上下文数据、训练流程**三条主线并开源了对应系统，说明长视频的可行性高度依赖系统工程。
- **服务**：视频前缀的 KV 复用（同一视频被多次提问）、预处理与推理解耦（抽帧、音频转写离线做）、以及按「视频 token 数」而非按请求计费的调度。

### 5. 评测

| 任务 | 判据 | 陷阱 |
| --- | --- | --- |
| 视频问答 | 精确匹配/模型判分 | 抽帧评测高估真实流式理解能力 |
| 时序定位 | 时间区间 IoU | 只评测「是否提到事件」而不评时间 |
| 长视频摘要 | 人工 + 事实一致性 | 摘要看似流畅但与视频无关（幻觉） |
| 跨模态对齐 | 说话人-内容对应准确率 | 只用转写文本评测会忽略画面信息 |

## 数值与代码验证

### 表 1：分辨率-帧数守恒（总预算 131,072 token，$p=16$，$m=2$）

| 分辨率 | 每帧 token | 可容纳帧数 | 适用任务 |
| --- | --- | --- | --- |
| 224² | 49 | 2,674 | 粗略动作/场景分类 |
| 448² | 196 | 668 | 一般视频问答 |
| 896² | 784 | 167 | 含文字/细节的场景 |
| 1792² | 3,136 | 41 | 文档/小字（帧数极少） |

**读法**：这是一条硬守恒——想把帧数提上去就必须降分辨率。实际系统常用「粗采样低分辨率 + 命中片段高分辨率二次采样」来绕开这个守恒。

### 表 2：长视频的成本（70B 级骨干，8×H100 @ MFU 45%）

| 场景 | 视觉 token | prefill 时间 | KV（320 KiB/token） |
| --- | --- | --- | --- |
| 32 帧 × 256 | 8,192 | 0.32 s | 2.5 GiB |
| 128 帧 × 256 | 32,768 | 1.29 s | 10.0 GiB |
| 544 帧 × 256 | 139,264 | 5.48 s | 42.5 GiB |
| 544 帧 × 256，但 KV 复用（同视频 5 次提问） | 139,264（首次） | 首次 5.48 s，后续 ≈ 0 | 42.5 GiB 复用 |

口径：prefill 用 $2NP$；KV 用仓库统一常数（70B 级 320 KiB/token）；时间按 8 卡峰值 × MFU 45%。最后一行说明**前缀缓存对视频场景的收益远大于文本场景**（首次 5.48 s，后续几乎免费）。

### 可运行代码

```python
# 1) token 预算守恒与两阶段采样
KiB, GiB = 1024, 1024**3
KV_70B = 320 * KiB
P_70B, TFLOPS, MFU, GPUS = 70e9, 989e12, 0.45, 8
eff = TFLOPS * MFU * GPUS

def tokens_per_frame(h, w, p=16, m=2):
    return (h // p) * (w // p) // (m * m)

print("表 1：固定总预算 131,072 token 下的分辨率-帧数守恒")
for h, w in [(224, 224), (448, 448), (896, 896), (1792, 1792)]:
    tpf = tokens_per_frame(h, w)
    print(f"  {h}x{w:<5} 每帧 {tpf:>5,d} token -> 可容纳 {131072//tpf:>5,d} 帧")

print("\n表 2：长视频 prefill 与 KV（70B 级，8xH100 @ MFU 45%）")
for frames in (32, 128, 544):
    n = frames * 256
    flops = 2 * n * P_70B
    print(f"  {frames:>4} 帧 x256 token = {n:>7,d} token  prefill {flops/eff*1000:8.1f} ms  "
          f"KV {n*KV_70B/GiB:6.2f} GiB")

# 两阶段采样：粗看全片 -> 命中片段精看
def two_stage(frames_total=544, coarse_tpf=49, fine_tpf=784, fine_frames=16, topk=3):
    coarse = frames_total * coarse_tpf
    fine = topk * fine_frames * fine_tpf
    return coarse, fine, coarse + fine
c, f, tot = two_stage()
print(f"\n两阶段采样：粗看 {c:,} token + 精看 {f:,} token = {tot:,} token"
      f"（对比全片高分辨率 {544*784:,} token，省 {1-tot/(544*784):.1%}）")

# 2) KV 复用的收益：同一视频多次提问
base_prefill_ms = 2 * (544 * 256) * P_70B / eff * 1000
for q in (1, 3, 5, 10):
    with_cache = base_prefill_ms + (q - 1) * 8          # 后续每次只处理新问题（约 8 ms）
    without = base_prefill_ms * q
    print(f"  同一视频提问 {q:>2} 次：无缓存 {without/1000:7.2f} s，有前缀缓存 {with_cache/1000:6.2f} s"
          f"（省 {(1-with_cache/without):.1%}）")

# 3) 帧采样策略对比：均匀 vs 场景切换优先（用合成「信息量」曲线）
import random, math
random.seed(53)
T = 600
info = [abs(math.sin(i/40)) * random.uniform(0.5, 1.5) for i in range(T)]   # 信息量随时间波动
def uniform_pick(k):
    step = T / k
    return [int(i*step) for i in range(k)]
def scene_pick(k):
    # 贪心：每次选信息量最大且与已选帧间隔 >= T/(2k) 的帧
    picked, min_gap = [], T // (2*k)
    for _ in range(k):
        cands = [i for i in range(T) if all(abs(i-j) >= min_gap for j in picked)]
        if not cands:
            break
        picked.append(max(cands, key=lambda i: info[i]))
    return sorted(picked)
K = 16
u, s = uniform_pick(K), scene_pick(K)
print(f"\n帧采样（K={K}）：均匀采样覆盖信息量 {sum(info[i] for i in u):.2f}，"
      f"场景优先覆盖 {sum(info[i] for i in s):.2f}"
      f"（提升 {(sum(info[i] for i in s)/sum(info[i] for i in u)-1):.1%}）")
print("在动作/事件稀疏的视频里，这个差距会更大——这就是「选哪些帧比选多少帧更重要」")
```

预期输出要点：表 1 显示分辨率与帧数的硬守恒（1792² 时只剩几十帧可用）；表 2 里 544 帧的 prefill 约 5.5 s、KV 约 42.5 GiB（与仓库既有多模态专题同口径）；**两阶段采样省掉大部分 token**（示例约 80%+）；前缀缓存在多次提问下把总耗时从数十秒降到数秒；帧采样策略对比说明「选哪些帧」比「选多少帧」更能保住信息量。

## 常见追问

- **追问**：视觉塔该冻结还是联合训练？
  - 要点：分阶段——先冻结 LLM 只训投影（对齐），再联合微调（让视觉表示适配语言任务）；全程联合训练成本高且容易破坏语言能力。数据配比里必须保留纯文本。
- **追问**：视频理解为什么比图像难这么多？
  - 要点：时间维（因果、顺序、动作）需要额外建模；token 预算是图像的量级倍数；长上下文训练需要系统支持（可引用 LongVILA 把系统/数据/流程拆开处理的做法）；评测也更难（时序定位、流式理解）。
- **追问**：怎么在固定预算下判断该给帧数还是给分辨率？
  - 要点：看任务的信息瓶颈——文字/细节密集（文档、菜单、小字）给分辨率；动作/事件密集给帧率。工程上用两阶段（粗看 + 精看）同时兼顾，而不是在单一配置上妥协。
- **追问**：为什么说「视觉编码本身不是瓶颈」？
  - 要点：视觉塔的算力相对 LLM 侧小两个量级（仓库既有多模态专题的结论：336px CLIP-L 规模约 0.35 ms 量级，而千级视觉 token 进入 70B 后需要百毫秒到秒级）。优化重点应放在 token 预算与 LLM 侧。
- **追问**：多模态模型的语言能力会不会退化？
  - 要点：会。多模态指令数据会改变输出分布（更短、更爱描述画面），必须混入纯文本指令数据并监控纯文本基准；这是灾难性遗忘的常见形态（串 [[multimodal-01]]）。
- **追问**：如何去评一个视频理解模型？
  - 要点：分任务（问答/时序定位/摘要/对齐）+ 分时长（短视频 vs 长视频）+ 明确抽帧口径；并做「答案是否真的依赖画面」的对照实验（把视频换成静态帧或纯转写，看分数掉多少）。
