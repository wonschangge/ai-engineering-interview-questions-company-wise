## 一句话答案

> 从 8 卡到数千卡不是「同一件事换更大的机器」，而是四层失效按顺序暴露：**显存**（混合精度 Adam 下 16 B/param，70B 的模型状态就是 1120 GB = 1043 GiB，8 卡连静态开销都装不下）→ **机内通信**（TP 每层 2 次前向 + 2 次反向 all-reduce，$t=8$ 在 H100 上相对开销 38.4% 峰值口径 / 19.2% 于 50% MFU，一旦跨出 NVLink 域再乘 9）→ **跨机通信**（DP 每步一次梯度 all-reduce，70B、$d=64$ 时每卡收发 275.6 GB，NDR IB 上串行 5.51 s，只能靠大 batch 与重叠摊薄）→ **系统可靠性**（数千卡按天出故障，checkpoint、重启、数据序与 loss spike 判定都变成一等公民）。
> 应对方式只有两条判据：**显存决定要不要切**（FlashAttention、选择性重算、序列并行压激活，ZeRO/FSDP 分片模型状态），**带宽决定在哪里切**（TP/SP 留在单个 NVLink 域内 $t \le 8$，PP 走低带宽点对点，DP/EP 跨机堆规模），总卡数等于 $t \times p \times d \times e$。
> 收口不看加了多少卡，而看四件套：MFU、有效训练时间占比、重启次数、通信时间占比。

## 面试官在考什么

- 能不能给出失效的**顺序**（显存 → 机内通信 → 跨机通信 → 可靠性），每一步的切法、代价与数字，而不是并行名词表。
- 会不会算两本账：16 B/param 的模型状态、$sbh(34+5as/h)$ 的激活；以及各类通信量的增长率（TP 相对开销 $\propto (t-1)$ 且与 batch 无关，DP 反比于每卡每步 token 数，PP 与层数无关）。
- 知不知道每种切法的物理边界：TP 由 $P/W$ 与 NVLink 域决定，PP 由气泡与 micro-batch 数决定，ZeRO-3 由 all-gather 次数与 1.5× 通信决定。
- 是否把数千卡当成系统问题而不是算子问题：慢节点、故障重启、checkpoint 写放大与阻塞、数据管线吞吐、数值稳定性。
- 能不能用实测指标收口，并把 MFU 掉点定位到算力、通信、数据三类原因之一（[[inference-serving-07]]）。

常见错误答案：

- 只答「换更大的集群」。规模上去以后显存、通信、故障率三件事同时变贵，不做切法设计就是烧钱买无效算力。
- 把 TP 推到跨机，或用大 batch 去救 TP 的通信开销（TP 的相对开销与 batch 无关，救不回来）；以为 ZeRO/FSDP 是免费的显存（ZeRO-3 是基线 DP 的 1.5× 通信，而且不切激活）。
- 拿 MFU 掉点直接归因于通信，不看 NCCL 的 bus bandwidth 是否已到链路峰值、小 GEMM 效率与数据管线；以及把「8 卡上延长训练时间换效果」当成数千卡上的选项。

## 原理与推导

### 1. 失效顺序：四层依次暴露

这条链是本题答案的骨架：显存是 8 卡阶段就会撞上的墙；把模型切开之后，机内 NVLink 的带宽被 TP 吃掉；再跨机，DP 与 PP 的通信开始定价；规模到数千卡，单卡与单链路的偶然开销被放大成集群级的可靠性问题。

| 层级 | 何时暴露 | 主要失效 | 对策 |
| --- | --- | --- | --- |
| 显存 | 8 卡就能碰到 | 16 B/param 的模型状态、$5as^2b$ 的激活 | FlashAttention、选择性重算、SP、ZeRO/FSDP |
| 机内通信 | 单机多卡 | TP 每层 4 次 all-reduce，$t$ 越大越亏 | $t \le 8$ 留在 NVLink 域；用 SP 换激活而不是加 $t$ |
| 跨机通信 | 推过单机边界 | DP 的梯度 all-reduce、PP 的点对点 | 大 batch 与梯度累积摊薄 DP；PP 走低带宽链路；分桶与反向重叠 |
| 系统可靠性 | 数千卡 | 慢节点、故障重启、checkpoint、数据管线、loss spike | 自动重启 + 可复现数据序、异步分片 checkpoint、MFU 与有效训练时间收口 |

### 2. 第一层：显存账

**模型状态 16 B/param。** bf16 参数 2 + bf16 梯度 2 + fp32 主权重 4 + Adam 一阶 4 + 二阶 4，$M_{\text{states}} = 16N$。70B 是 1120 GB（1043 GiB），至少 14 张 80 GB 卡；摊到 8 张是 140 GB/卡，**还没算激活就已经放不下**——这是「8 卡方案在千亿级失效」的第一个答案。

**激活每层 $sbh(34+5as/h)$ 字节**（Megatron Table 2 口径，系数已含 fp16 宽度与 dropout mask；见 [[finetuning-09]]）。取 $s=4096$、$b=1$、$h=8192$、$a=64$：$5as/h = 160$，每层 6.51 GB，其中 $5as^2b = 5.37$ GB（正好 5 GiB）占 82.5%；只把序列降到 2048，这一项仍是 $34sbh$ 的 2.35 倍。80 层一起算是不重算、不并行的 520.8 GB，与 1120 GB 的模型状态同一量级：两层账加起来，8 卡在任何方向都没有余量。

**三条削减手段，各有代价。** ① FlashAttention 从实现上不再物化 $s \times s$ 的分数矩阵，激活从 $O(s^2)$ 降到 $O(s)$（[[llm-internals-05]]），等价于直接删掉 $5as^2b$ 项；代价是 $K/V$ 块被重复读、反向要重算。② 选择性重算只重算 attention 里那三张 $s^2$ 矩阵，每层降到 $34sbh$（本配置 1.14 GB/层）；GPT-3 省 70% 激活只加 2.7% FLOPs，MT-NLG 省 65% 加 1.6%，而全量重算要付 30%–40% 的执行时间开销。③ 序列并行（SP）把非 TP 区按序列切开，那些本来被复制 $t$ 份的激活变成每卡 $1/t$：只有 TP 时每层每卡是 $sbh(10+24/t+5as/(ht))$、TP+SP 是 $sbh(34/t+5as/(ht))$（[[inference-serving-07]]），$t=8$ 时即 1.107 GB 对 0.814 GB（1.36×）；扣掉两边同样被 $t$ 除的 attention score 项（每卡 0.671 GB）后是 $13sbh$ 对 $4.25sbh$，即 3.06×。注意口径：这 3.06× 与 $s$ 无关（两项都 $\propto s$），随 $s$ 变大的是 SP 省下的绝对量 $10sbh(1-1/t) = 8.75sbh$（$\propto s$，本配置 80 层共约 23.5 GB），而含 score 项的总激活比值反而从 $s=1024$ 的 1.95× 收敛到 $s=16384$ 的 1.10×。SP 复用 TP 通信组，通信量与 TP 相同、不额外占卡。

**优化器状态分片。** ZeRO 三阶段每参数是 $4+12/d$、$2+14/d$、$16/d$ 字节，70B、$d=64$ 时 1120 GB 依次降到 293.1 / 155.3 / 17.5 GB。代价是 ZeRO-3（FSDP）每层计算前要 all-gather 参数、反向后 reduce-scatter 梯度，通信升到基线 DP 的 1.5×，必须靠 prefetch 与计算重叠，藏不住就吃掉收益；而且它只切模型状态，**不切激活**。

口径提醒：上面这张 ZeRO 账是**纯 DP**（$t=p=1$）口径。真实配置里参数与梯度先被 $t \times p$ 切掉，优化器状态再在 DP 组内分片：4096 卡取 $t=8$、$p=8$、$d=64$ 时，每卡 bf16 参数 2.1875 GB + 梯度 2.1875 GB + fp32 优化器状态 0.2051 GB ≈ 4.58 GB，其余显存留给激活、通信缓冲与碎片。两笔账不能混算。

### 3. 第二层：通信的带宽约束与增长率

| 策略 | 通信算子 | 每卡通信量 | 相对开销随什么变 | 物理半径 |
| --- | --- | --- | --- | --- |
| TP | 每层 2 次 all-reduce（前向）+ 2 次（反向） | $8\frac{t-1}{t}bshc$ 每层（$t=8$ 时 112 KiB/token/层） | $\propto (t-1)$，与 batch 无关 | 单个 NVLink 域，$t \le 8$ |
| DP | 每步 1 次梯度 all-reduce | $2\frac{d-1}{d}Nc$（70B、$d=64$：275.6 GB/步） | 反比于每卡每步 token 数 | 跨机，必须分桶并藏进反向 |
| PP | stage 边界点对点 | $bshc$ 每次单向（64 MiB） | 与层数无关，随 micro-batch 数 | 可放低带宽链路 |
| EP | 每层 dispatch + combine 两次 all-to-all | $2k\frac{E-1}{E}hc$（28 KiB/token/层） | 随 token 数（动态）、路由不均 | 跨机，需容量因子或 aux loss |

**TP 的亏救不回来。** 每层前向 2 次、反向 2 次 all-reduce，相对开销 $r_{\text{TP}} = \frac{4(t-1)LhcP}{3NW} \propto (t-1)$。70B（$L=80$、$h=8192$、$c=2$）在 H100 上 $t=8$ 是 38.4%（峰值口径）/ 19.2%（50% MFU）；把 $W$ 从 NVLink 的 450 GB/s 换成 NDR IB 的 50 GB/s（×9）就是 172.8%。这就是 $t \le 8$ 的量化理由，也是「TP 不能出机」最硬的证据。

**DP 的亏可以用大 batch 救。** 每步一次 all-reduce，每卡收发约 $2Nc$；70B 的 bf16 梯度是 140 GB，$d=64$ 时每卡 275.6 GB（上界口径 $2Nc = 280$ GB），IB 上串行 5.51 s。相对开销反比于每卡每步 token 数：4096 token 时 1.59（280 GB 口径 1.61），65536 token 时 0.10。所以手段是分桶、与反向重叠，以及把每卡每步 token 数做大。

**PP 便宜到可以跨机。** 每个 micro-batch 在每个 stage 边界只单向传一份 $bshc$；$t=8$、$p=8$、$L=80$ 时，TP 在同样一段 stage 里单向要发 $4\frac{t-1}{t}\frac{L}{p}bshc = 2240$ MiB，是 PP 那 64 MiB 的 35 倍。代价是气泡（见下节）和它救不了的激活显存。

**EP 与 TP 同量级但性质相反。** MoE 走 EP 时每 token 每层两次 all-to-all 共 $2k\frac{E-1}{E}hc$；$k=2$、$E=8$、$h=4096$、bf16 下是 28 KiB，与 $t=8$ 的 TP 的 56 KiB 同量级。差别在于 TP 对称、静态、可预测，EP 随 token 数增长、路由动态、专家负载天然不均，要靠容量因子丢 token 或辅助损失平衡（[[llm-internals-10]]）。

口径：所有通信量按 **NCCL 算法通信量**报（一次 all-reduce 每卡 $2\frac{t-1}{t}$ 乘张量字节，也就是 NCCL 报 bus bandwidth 的口径），不要与张量大小或单次消息大小混着说。

### 4. 第三层：并行度乘积与拓扑映射

总卡数等于 $t \times p \times d \times e$，SP 复用 TP 通信组不额外占卡：4096 卡典型分解是 $8 \times 8 \times 64$，1024 卡是 $8 \times 8 \times 16$。映射规则一句话——**带宽决定在哪里切**：TP/SP 留在单个 NVLink 域内（H100 上是 8 卡），PP 用低带宽点对点跨机，DP/EP 用来跨机堆规模，并让同一 DP 组的梯度 reduce 尽量落在机内交换机之下，减少跨 spine 流量；EP 的通信组与 TP 不重叠，专家内部还能继续用 TP 切矩阵。

并行度不是越大越好：分得越细，单卡 GEMM 越小、collective 次数与固定延迟占比同时上升，显存省下来的收益会被这两项吃掉。判据只能是实测 MFU 与 NCCL 时间占比，公式只用来排除明显不可行的配置。

### 5. PP 的气泡：两种调度不能互相代入

GPipe 的 fill-drain 调度气泡是 $(p-1)/(m+p-1)$（$p=8$、$m=64$ 时 9.9%），1F1B 是 $(p-1)/m$（同参数 10.9%）。后者真正的收益不是气泡更小，而是**激活从 $O(m)$ 降到 $O(p)$**：GPipe 必须把 $m$ 个 micro-batch 的激活留到反向，所以它依赖 rematerialization。再切虚拟 stage 可把气泡降到约 $(p-1)/(vm)$，代价是点对点通信次数乘 $v$。可执行判据必须带调度口径：按 GPipe 的 $(p-1)/(m+p-1)$，要让气泡不超过 10% 取 $m \ge 9(p-1)$（$p=8$ 时 63 个 micro-batch，气泡恰好 10.0%）；换成 1F1B 的 $(p-1)/m$，同一个 $m=63$ 是 11.1%，要压到 10% 以内得取 $m \ge 10(p-1) = 70$。

两条必须接住的追问：PP **不省激活显存**（要保持利用率就得同时存多个 micro-batch 的激活，它只解决参数与优化器状态）；PP 的通信与层数无关，所以能放在低带宽链路上。

### 6. 第四层：数千卡才暴露的系统问题

**① 慢节点与同构假设破裂。** 一次 collective 要等最慢的 rank：单卡降频、ECC 报错、NVLink 降速、某台机器上多跑了一个进程，都会把整步拖长。对策是 rank 放置的拓扑感知（同 TP 组落在同一 NVLink 域、同 PP 组落在相邻层级）与故障节点替换流程（摘除、替换、重新加入，而不是重启全集群）。

**② 故障频率与容错。** 故障率 $\lambda = G/\text{MTBF}$。按单卡 MTBF 10 万小时的假设口径，4096 卡集群平均 24 小时掉一次（≈0.98 次/天），16384 卡是每 6 小时一次（3.93 次/天）——上万卡的集群每天都会有节点掉，训练必须假设随时会挂。对策：周期性 checkpoint + 自动重启；重启后**可复现的随机数与数据序**（保证 token 流一致，不静默重复或跳过数据）；把有效训练时间占比与重启次数当一等指标。

**③ checkpoint 的写放大与阻塞。** 70B 的 checkpoint 逻辑体量是 bf16 参数 140 GB + fp32 优化器状态 840 GB = 980 GB。如果每个 rank 各写自己那份（参数 2.1875 GB + 优化器分片 0.2051 GB），4096 卡会写出 9.8 TB：其中 8.96 TB 来自参数，而参数在 64 个 DP 副本里只有 140 GB 是唯一的（8.82 TB 属重复写入）；优化器分片那 4096 × 0.2051 GB ≈ 840 GB 本身不重复。所以必须去重，并按 FSDP/DTensor 风格分片并行保存。落盘要异步（先写、再 barrier、训练继续），保存前后不能让两份状态同时驻留显存。

**④ loss spike 与数值稳定性。** 静默数据损坏、偶发跳 batch、回滚 checkpoint 都需要判定标准，否则每次抖动都要人判断。工程手段：bf16 归约与 logits 用 fp32 累加、优化器 eps 与梯度裁剪、按 step 号跟踪 loss 的健康区间，偏离就回滚到最近 checkpoint 并跳过那段数据窗口。

**⑤ 数据管线必须与算力匹配。** 分词、打包、shuffle 在 CPU 侧吞吐不够时 GPU 就在等数据。4096 卡在 50% MFU 下是 4.82M token/s（417B token/天），数据管线要按这个量级设计并留余量；MFU 掉点首先要能定位到算力、通信还是数据。

**⑥ 大 batch 不是免费的。** schedule 长度必须与实际训练 token 数匹配，否则中间 checkpoint 的 loss 被系统性高估——Chinchilla 指出 Kaplan 的关键偏差之一正是固定 schedule（[[llm-internals-09]]）。8 卡上这只是一个实验设计问题，数千卡上 batch 被放大之后，它会变成真实的成本错误。

### 7. Meta 口径

公开的 Llama 训练栈是 Megatron 风格 TP + PP + DP 组合加 ZeRO/FSDP（[[inference-serving-07]] 的公司变体），面试落点因此是这一串：集群拓扑怎么排、$t/p/d$ 怎么配、MFU 掉点怎么查、故障恢复与 checkpoint 怎么设计。若引用 Meta 自己的集群口径：Llama 3 405B 的公开技术报告口径是在 16K 张 H100 上训练、持续吞吐在 400 TFLOPS/GPU 量级（对 989 TFLOPS 峰值约 40% MFU）。这两条不在本篇 front matter 来源内，按原文口径标注、未做复算；它们的用处是给「数千卡上 MFU 报 40% 上下属正常、容错是一等设计目标」一个现实锚点。

## 常见追问

- **追问**：为什么 TP 通常不超过 8？
  - 要点：三个原因叠加。① 相对开销 $\propto (t-1)$，$t=8$ 时已经是 38.4%（峰值口径）/ 19.2%（50% MFU）；② 跨出 NVLink 域后单向带宽 450 → 50 GB/s，同一份通信时间乘 9；③ 每卡矩阵变小，GEMM 效率与 collective 固定延迟占比同时恶化。8 卡 NVLink 域是硬件给定的事实上界。
- **追问**：ZeRO / FSDP 是不是免费的显存？
  - 要点：不是。ZeRO-1/2 通信量与基线 DP 相同，ZeRO-3 升到 1.5×（梯度 reduce-scatter + 前向 all-gather + 反向 all-gather ≈ 6 B/param），而且三者都不切激活。切得越深，all-gather 次数越多、单次消息越小，跨机时通信会吃掉收益；必须靠 prefetch 与计算重叠把 all-gather 藏起来。
- **追问**：PP 既不省激活显存，凭什么还能在大规模里用？
  - 要点：因为它省的是通信。每个 micro-batch 只在 stage 边界单向传一份 $bshc$，与层数无关，比 TP 在同一段 stage 的通信低 $4\frac{t-1}{t}\frac{L}{p}$ 倍（本配置 35×），所以能放在低带宽链路上，把跨机带宽留给 DP 与 EP。代价是气泡（GPipe 口径用 $m \ge 9(p-1)$ 压到 10% 以内，1F1B 要 $m \ge 10(p-1)$）与激活显存的 $O(m)$ 需求。
- **追问**：数千卡上 checkpoint 间隔怎么定？
  - 要点：把两笔成本写成 $\text{overhead}(T) = C_w/T + \lambda T/2 + \lambda L_r$（$C_w$ 单次写盘与同步、$L_r$ 重启加载、$\lambda = G/\text{MTBF}$），最优间隔 $T^{\ast} = \sqrt{2C_w/\lambda}$。按假设口径（单卡 MTBF 10 万小时、$C_w = 5$ min、$L_r = 10$ min），4096 卡的最优是 2.02 h、有效训练时间 91.8%，而 15 min 一存反而只有 74.3%。缩短 $L_r$（异步分片保存、按 rank 并行读回）比加密 checkpoint 更有效。
- **追问**：MFU 掉点，怎么定位是算力、通信还是数据？
  - 要点：四步。① 看 Nsight Systems 里 NCCL kernel 的时间占比；② 用 nccl-tests 量 all-reduce 的 bus bandwidth 是否接近链路峰值——占比高且 bus bandwidth 到峰，是切法问题；占比高但 bus bandwidth 很低，是消息太小或没重叠，先调 bucket 与 overlap；③ 看单卡 GEMM 效率与 kernel 时间线里的空隙，判断是不是并行度太大；④ 看 dataloader 等待时间与 token/s，判断数据管线是否拖后腿。
- **追问**：MoE 为什么要单独引入 EP，而不是用 TP 切专家？
  - 要点：TP 切专家意味着每个 token 都要经过所有 TP rank 的专家计算，通信量与激活都不可接受；EP 让每个 token 只去 top-$k$ 个专家所在的卡，把模型容量与单 token FLOPs 解耦。代价是 all-to-all（$k=2$、$E=8$、$h=4096$、bf16 下 28 KiB/token/层）随 token 数增长、路由动态、负载天然不均，要靠容量因子丢 token 或辅助损失平衡；另外 MoE 的总参数与激活参数是两个账本，显存按总参数算、算力按激活参数算（[[llm-internals-10]]）。
