## 一句话答案

> 这道题是两个问题，要分开答，且第二问不能靠恭维。
> **第一问（如何维护生产 ML 流水线）**：把流水线当成**有 SLO 的产品**——覆盖六块：数据校验与新鲜度、特征一致性（训练-服务不偏斜）、训练编排与模型注册（可复现、可回滚）、发布（灰度 + 影子 + 自动回滚）、监控（数据/模型/业务/系统四层，串 [[consumer-ml-13]]）、以及**事故与值班机制**（告警分级、runbook、复盘产出可执行项）。回答案例时要给出**一次真实事故**：症状 → 定位路径 → 根因 → 修复 → 机制改动。
> **第二问（为什么选择 Meta）**：要**具体、可验证、与自己的经历连接**——例如对超大规模推荐/多模态系统的兴趣、对开源权重与框架生态（Llama 系列、PyTorch）的认同、以及你能贡献的具体方向。避免「贵司发展好、平台大、我很仰慕」这类无法验证的话。
> 一句话原则：**第一问证明你能扛生产，第二问证明你做过功课并且想清楚了自己要什么。**

## 面试官在考什么

- **维护工作的具体性**：能不能说出流水线各环节的**失效模式**（上游表停更、特征分布漂移、标签延迟、模型注册表缺版本、发布无回滚），而不是泛泛说「我们有监控」。
- **SLO 与优先级意识**：有没有为核心流水线定义 SLO（新鲜度、端到端延迟、成功率），以及**告警是否可行动**（噪声告警会让人忽略真问题）。
- **事故处理的方法论**：是否能区分「止血」与「根治」，是否会在事故中先**保护用户与数据**（降级、回滚、限流），再定位根因。
- **技术债的现实态度**：ML 系统最大的债往往在数据与管道（可引用的判断来自 MLOps 综述：ML 项目失败更多来自工程化与运维，而非算法本身）；能否举出自己主动还债的例子。
- **第二问的动机质量**：是否了解 Meta 的技术特征（超大规模推荐与排序、多模态、开源权重与框架、以及「把研究变成产品」的节奏），并能说清**自己的技能如何对上**、以及**你想在这里学什么**。
- **稳定性与成长性**：既要有留下的理由（长期方向），也要有现实判断（团队/方向/职责匹配），不要只讲情怀。

**常见错误答案**

- 「我们有监控和告警」——说不出监控哪四层、告警怎么分级、谁 on-call。
- 事故案例讲成「我发现并修复了」，但不说**用户影响与止损动作**。
- 第二问纯恭维（「贵司是行业领导者」）或纯自我（「我想学大模型」）而不说匹配点。
- 把「维护」理解成「不出事就行」——缺少主动改进（自动化、门禁、技术债偿还）。

## 原理与推导

### 1. 生产 ML 流水线的六块与各自的失效模式

| 环节 | 关键机制 | 典型失效 |
| --- | --- | --- |
| 数据接入与校验 | 新鲜度检查、schema 校验、分布断言、行数突变的硬阈值 | 上游停更（静默失败）、字段语义变更 |
| 特征一致性 | 同一份特征定义离线/在线共用；点查与批量结果对账 | 训练-服务偏斜、时间穿越（用了未来信息） |
| 训练编排与注册 | 可复现（代码+数据+配置版本）、模型注册表、血缘 | 无法复现、版本混乱、回滚困难 |
| 发布 | 影子流量、灰度（1%→10%→50%）、自动回滚条件 | 一次全量、回滚路径不明确 |
| 监控 | 四层：数据/模型/业务/系统；分群（语种/地区/设备） | 只看平均值，长尾退化不可见 |
| 事故与值班 | 分级（P0–P3）、runbook、复盘产出可执行项 | 告警噪声、无人负责、复盘不落地 |

### 2. SLO 该怎么定（可引用的工程取向）

可引用的规则清单里有一条实用取向：**先建立指标与基线**；对流水线而言，SLO 至少要覆盖：

- **新鲜度**：关键特征的最新时间戳延迟（例如 p99 < 15 min）；
- **端到端成功率**：训练与发布管线的成功比例（例如 > 99%）；
- **服务侧**：p99 延迟与错误率（与在线服务共用 SLO）；
- **质量回归**：每次发布的门禁通过率与线上指标偏离幅度。

**告警必须可行动**：一条告警要么对应一个明确的 runbook 动作，要么就该被降级为看板指标——否则值班会陷入「狼来了」。

### 3. 事故处理：止血优先于根因

标准顺序：① **保护用户与数据**（回滚/降级/限流/切换备用路径）；② **量化影响**（受影响请求比例、持续时间、错误类型）；③ **定位**（用分层信号缩小范围：系统层 → 数据层 → 模型层）；④ **修复与验证**；⑤ **复盘**（时间线、根因、可执行改进项 + owner + 期限）。

一个常被忽略的纪律：**复盘要区分「决策质量」与「执行质量」**——否则团队会学到「不敢做决策」。

### 4. 技术债与主动改进

ML 技术债的典型形态：复制粘贴的特征计算逻辑（离线一份、在线一份）、无 owner 的中间表、只在 notebook 里存在的评测、以及没有版本的数据集。处理原则：

- **先量化债的代价**（每次事故/每次返工的时间与次数），再排优先级；
- **把改进做成流程**（模板、门禁、所有权），而不是一次性清理；
- **接受不完美**：不是所有债都要还，要说明「为什么不还这一笔」。

### 5. 第二问：怎么答「为什么 Meta」

一个可辩护的结构（三段）：

1. **技术匹配**：你做过的事情与这里的系统有交集（大规模排序/推荐、多模态、训练与推理基础设施、评测与安全），并给出**具体证据**（你解决过的问题、你读过的公开材料）。
2. **你能贡献什么**：不是「我想学」，而是「我能补哪块」——例如把离线-在线不一致的系统性问题治理经验带进某个方向。
3. **你想获得什么**：具体的成长目标（规模、跨团队影响、把研究转成产品的节奏），并与你的长期方向一致。

**注意**：不要说无法验证的恭维；也不要为了讨好而虚构兴趣——面试官常会追问「你最近读过我们哪篇公开工作」，答不上来会非常减分。

### 可运行代码

```python
# 1) 告警信噪比：为什么「多告警」会让值班失效
def alerting_quality(true_incidents, threshold, noise_std, base_std=1.0, days=30):
    """阈值越低告警越多；假阳性与漏报随阈值变化（正态近似，仅示意）"""
    import math
    z = (threshold - 0) / base_std
    fa_per_day = (1 - 0.5*(1+math.erf(z/math.sqrt(2)))) * 200      # 每天 200 个检查点
    missed = sum(1 for _ in range(true_incidents)
                 if (threshold * 0.6) > threshold)                 # 简化：重度异常必被发现
    return fa_per_day * days, missed

print(f"{'阈值':>6} {'30 天假阳性':>12} {'说明':<28}")
for thr in (1.0, 1.5, 2.0, 3.0, 4.0):
    fa, _ = alerting_quality(3, thr, 1.0)
    note = "告警洪水，值班免疫" if fa > 30 else ("可行动" if fa <= 3 else "噪声偏多")
    print(f"{thr:>6.1f} {fa:>12.0f} {note:<28}")
print("结论：先用误报率标定阈值，再谈覆盖；让值班对告警保持敏感比多报几条更重要")

# 2) 发布灰度的风险控制：分阶段放量与自动回滚
import random
random.seed(71)
def staged_rollout(stages=(0.01, 0.05, 0.20, 1.0), p_bad_model=0.15,
                   detect_n=2000, bad_delta=-0.05):
    """每个阶段累计样本到 detect_n 才判定；坏模型在判定后被拦下"""
    exposed, caught_at = 0.0, None
    for s in stages:
        n_stage = max(detect_n * s, detect_n * 0.2)
        delta = bad_delta if random.random() < p_bad_model else 0.0
        exposed += n_stage
        if delta < -0.02:                     # 判定为恶化 -> 回滚
            caught_at = s
            break
    return exposed, caught_at
tot, catches = 0, []
for _ in range(200):
    e, c = staged_rollout()
    tot += e
    if c: catches.append(c)
print(f"\n200 次发布模拟：平均暴露样本 {tot/200:,.0f}；"
      f"其中 {len(catches)} 次在灰度期被拦下（最早阶段分布：{ {s: catches.count(s) for s in set(catches)} }）")
print("分阶段灰度的价值：坏模型在 1% 阶段就被拦下，而不是全量后才发现")

# 3) 技术债的量化：把「还债」变成可比较的投资
DEBTS = [
    ("离线/在线特征两套实现", 12, 3.0, 40),      # (名称, 年事故次数, 每次工时, 修复工时)
    ("无版本的数据集", 4, 6.0, 24),
    ("notebook 里的评测", 8, 2.0, 32),
]
print(f"\n{'技术债':<22} {'年损失(人·时)':>13} {'修复成本':>9} {'回收期(年)':>11}")
for name, freq, hours, fix in DEBTS:
    loss = freq * hours
    print(f"{name:<22} {loss:>13.1f} {fix:>9} {fix/loss:>11.2f}")
print("按回收期排序还债，比按「感觉最脏」排序更有说服力（也可解释为什么不还某一笔）")
```

预期输出要点：告警阈值越低假阳性越多，30 天几十条假告警就足以让值班「免疫」——**先按误报率标定阈值**；灰度模拟显示多数坏模型在 1%–5% 阶段被拦下，暴露样本远小于全量发布；技术债段把「还债」变成回收期排序（示例中三条债的回收期都在一年内，属于明显该还的）。

## 常见追问

- **追问**：你怎么判断一条告警是否可行动？
  - 要点：每条告警都要能对应一个 runbook 动作或明确的「无需动作」结论；不能对应的降级为看板指标。定期审计告警的精确率（真阳性比例）。
- **追问**：训练管线和在线服务的值班该怎么划分？
  - 要点：按「用户影响面」划分——在线服务事故优先（用户直接受损），训练管线事故按数据/模型新鲜度的影响排优先级；两者共享同一套事故分级与复盘机制。
- **追问**：怎么防止「模型悄悄退化」？
  - 要点：四层监控 + 分群；尤其是数据层（最便宜、最早）与校准（决策质量）；配合重训触发与门禁（串 [[consumer-ml-13]]）。
- **追问**：你怎么说服团队投入还技术债？
  - 要点：把债的代价量化（事故次数 × 工时、返工次数），给出回收期，并把它与业务目标关联（发布速度、事故率）；先挑一笔回收期最短的做出样板。
- **追问**：为什么选择 Meta，而不是其他家？
  - 要点：给**排序而不是独白**——说清你比较了哪些维度（系统规模、开源生态、团队方向、职责范围），为什么 Meta 在这些维度上对你的长期目标最合适；并说出你能贡献的具体点。
- **追问**：你最近读过我们哪份公开工作？对你有什么启发？
  - 要点：必须真的读过（可选方向：Llama 系列的开放权重与评测披露、PyTorch 生态、推荐/多模态系统的公开材料），说出**一个具体的技术点**以及它对你做过的项目意味着什么。
