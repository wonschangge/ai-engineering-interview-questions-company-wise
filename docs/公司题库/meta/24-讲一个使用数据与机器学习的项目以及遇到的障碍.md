## 一句话答案

> 这题是一道**结构化叙述题**：面试官要听到的不是「我用了什么模型」，而是**你如何把业务问题翻译成可学习的问题、又如何在数据与工程的现实里把它做成**。所以答案用四段式：
> ① **问题与指标**：原始业务问题是什么、成功指标怎么定（以及为什么它不是模型指标）；
> ② **数据**：数据从哪来、标签怎么构造、你发现并修了哪些数据缺陷；
> ③ **建模与迭代**：基线是什么（先规则/简单模型）、每一步改动的增量是多少；
> ④ **障碍与解决**：障碍必须**分类并落到具体动作**——数据类（缺失、标签噪声、偏斜）、方法类（分布不匹配、指标代理错）、工程类（延迟、回填、线上不一致）、组织类（需求变化、跨团队依赖）。
> 最后给一个**可核查的数字**（增量、成本或时间节省），并说清它的口径。障碍讲得越具体、越贴近机制，可信度越高；「数据质量不好，我们清洗了一下」是最弱的答法。

## 面试官在考什么

- **能否把业务目标翻译成指标**：会不会主动谈「上线前先定义指标与基线」（可引用的工程取向来自 Google 的规则清单：先建指标与基线，再谈模型复杂度）。
- **数据工作是否真实做过**：标签是怎么来的（人工标注/日志回填/规则生成）、有多少噪声、如何验证标签质量；有没有处理过**训练-服务偏斜**这类只有真做过才会遇到的坑（串 [[consumer-ml-04]]）。
- **障碍的归因深度**：是否能把「模型不 work」拆成「数据问题 / 目标问题 / 工程问题」；是否知道 MLOps 的常见失败模式（可引用 MLOps 综述与映射研究：把 MLOps 的挑战按数据管线、模型构建、部署三条管线分类，并指出很多项目失败在「无法从实验走到生产」而不是模型本身）。
- **迭代纪律**：有没有「先简单后复杂」的痕迹（先基线再模型、先少量特征再上百特征），以及每次改动是否量化了增量。
- **诚实度**：会不会承认做过但没成功的尝试，以及从中学到什么（与 [[meta-25]] 的「判断错误」互为呼应）。

**常见错误答案**

- 全程讲技术栈（用了什么框架、什么模型），不说指标与增量。
- 障碍只说外部原因（数据脏、需求变、算力不够），不说自己做了什么判断。
- 报一个无法解释的漂亮数字（例如「准确率 99%」），被追问口径就崩。
- 把「模型上线」当终点，不提上线后的监控与迭代（串 [[consumer-ml-13]]）。

## 原理与推导

### 1. 四段式与每段的必答项

| 段 | 必答项 | 常见追问 |
| --- | --- | --- |
| 问题与指标 | 业务问题、成功指标、护栏指标、基线 | 为什么是这些指标？护栏是什么？ |
| 数据 | 来源、规模、标签构造、质量检查 | 标签噪声多大？怎么发现与处理？ |
| 建模与迭代 | 基线、每步改动、增量与显著性 | 为什么选这个模型？增量多少、显著吗？ |
| 障碍与解决 | 分类 + 具体动作 + 结果 | 如果重来会怎么做？ |

### 2. 障碍的分类（把「困难」讲成机制）

1. **数据类**：缺失与稀疏（新用户/新物品）、标签噪声（标注者不一致）、选择偏差（只有被曝光的数据有标签）、时间穿越（特征用了未来信息）。
2. **方法类**：训练与线上分布不一致、代理指标与真实目标脱节（优化 CTR 得到标题党）、类别不平衡与代价不对称。
3. **工程类**：训练-服务偏斜、特征回填不可得、延迟预算不足、模型版本与回滚缺失。
4. **组织类**：需求与口径变更、上下游依赖、评测集归属不清。

**每一类都要配一个「我做的具体动作 + 结果」**，否则只是抱怨。

### 3. 一个可复用的叙事模板（压缩到 90 秒）

> 「目标是 X（业务指标），我们把它拆成 Y（模型指标）+ Z（护栏）。我先用规则/简单模型做基线，得到 A；在数据上发现 B（具体缺陷），修掉后升到 C；接着换成 D 模型，再升到 E（相对基线 +F%，A/B 显著）。最大的障碍是 G（分类），我用 H（具体动作）解决，代价是 I。上线后我建立了 J（监控/重训触发）。」

模板的价值在于**每句话都可被追问且都有答案**。

### 4. 为什么「先基线后模型」是可辩护的策略

从工程经济学看：基线的信息价值最高（它给出可比较的下界），而模型复杂度的边际收益递减。可引用的规则清单里有一条直接对应：**在优化模型之前先把管道与指标建好**——因为大多数「模型不行」实际上是管道与指标问题。这也是 MLOps 综述强调的重点：ML 项目的失败更多来自工程化与运维，而不是算法。

### 表 2：把「障碍」量化成代价的例子（示意）

| 障碍 | 可量化代价 | 动作 |
| --- | --- | --- |
| 标签噪声 20% | 有效样本量打 8 折；若用噪声标签训练，AUC 可能损失数个百分点 | 加标注复核 + 用一致性过滤 |
| 特征缺失 15% | 回退默认值会让该人群预测质量下降 | 补一个「是否缺失」的指示特征 + 分群监控 |
| 反馈延迟 7 天 | 早期读数系统性低估 | 用代理指标 + 标签到齐后回填复核 |

### 可运行代码

```python
# 项目叙述里的关键数字：从模型增量到业务价值的换算与显著性检验
import math, random
random.seed(67)

def two_prop_test(kA, nA, kB, nB):
    pA, pB = kA/nA, kB/nB
    p = (kA+kB)/(nA+nB)
    se = math.sqrt(p*(1-p)*(1/nA+1/nB))
    if se == 0: return 0.0, 1.0
    z = (pB-pA)/se
    # 双尾 p 值的正态近似
    pval = 2*(1-0.5*(1+math.erf(abs(z)/math.sqrt(2))))
    return z, pval

nA = nB = 200_000
kA, kB = int(nA*0.030), int(nB*0.0315)      # 3.00% -> 3.15%
z, p = two_prop_test(kA, nA, kB, nB)
print(f"CTR 3.00% -> 3.15%（n={nA:,}/组）：z={z:.2f}, p={p:.2e} -> "
      f"{'显著' if p < 0.05 else '不显著'}")

# 换算成业务价值（与 consumer-ml-14 同口径）
DAU, EXP_PER_USER, CVR, AOV, TAKE = 1_000_000, 40, 0.05, 55.0, 0.20
def daily(delta_ctr):
    clicks = DAU*EXP_PER_USER*delta_ctr
    orders = clicks*CVR
    gmv = orders*AOV
    return clicks, orders, gmv, gmv*TAKE
d = daily(0.0015)
print(f"增量：点击 {d[0]:,.0f}/天，订单 {d[1]:,.0f}/天，GMV {d[2]:,.0f}/天，抽成 {d[3]:,.0f}/天")

# 障碍量化：标签噪声如何影响有效样本与结论
def noise_effect(n, noise, auc_clean=0.80):
    n_eff = n*(1-noise)
    auc_noisy = auc_clean - 0.35*noise           # 线性近似，仅用于量级示意
    return n_eff, auc_noisy
for noise in (0.05, 0.20, 0.40):
    n_eff, auc = noise_effect(100_000, noise)
    print(f"  标签噪声 {noise:.0%}: 有效样本 {n_eff:,.0f}，AUC 近似由 0.800 降到 {auc:.3f}")
print("面试里报「我们清洗了数据」不如报「噪声 20% 时 AUC 近似损失若干，我用 X 手段降到 5%」")

# 「先基线后模型」的增量分解（讲清每一步贡献）
steps = [("规则基线", 0.62), ("+ 曝光/位置特征", 0.66), ("+ 用户行为序列", 0.70),
         ("+ 多任务头", 0.715), ("+ 校准", 0.72)]
prev = None
for name, auc in steps:
    gain = "" if prev is None else f"（+{auc-prev:.3f}）"
    print(f"  {name:<18} AUC {auc:.3f} {gain}")
    prev = auc
print("把每一步的增量讲清楚，比只报最终数字更有说服力，也更容易被追问时不崩")
```

预期输出要点：显著性检验显示 3.00% → 3.15% 在 20 万/组下显著（$p$ 极小），而更小的差异需要更多样本；业务换算把 CTR 增量变成每日 GMV 与抽成（可直接用于面试叙述）；标签噪声段给出「噪声 → 有效样本与 AUC 损失」的量级；最后一段演示**增量分解叙事**（每一步 +0.04、+0.04、+0.015、+0.005，说明边际收益递减）——这正是面试官想听的迭代纪律。

## 常见追问

- **追问**：这个项目里最难的技术判断是什么？
  - 要点：挑一个**有取舍**的判断（例如为了延迟放弃一个更强但更慢的模型、或为了可解释性选简单模型），说清当时的判据与被放弃的选项。
- **追问**：如果数据量只有十分之一，你还会这么做吗？
  - 要点：会改策略——优先规则/特征工程/迁移学习，减小模型复杂度，并用更严格的离线评估防过拟合；说明你理解「数据量决定方法选择」。
- **追问**：你怎么知道模型上线后没有退化？
  - 要点：监控（数据层/模型层/业务层/系统层）+ 重训触发 + 护栏指标；并给出具体阈值与复盘窗口（串 [[consumer-ml-13]]）。
- **追问**：这个项目里你和别人的分歧是什么？
  - 要点：给一个真实分歧与解决方式（用数据/小实验而非争论定胜负），体现协作与影响他人的能力（与 [[meta-25]] 的模糊决策呼应）。
- **追问**：如果重来一次，你会改哪一步？
  - 要点：指出当时**最脆弱的假设**与更便宜、更早的验证动作（例如先做一周的影子流量而不是先训大模型）。
- **追问**：为什么这个指标能代表业务价值？
  - 要点：说清价值链（模型指标 → 用户行为 → 业务指标 → 财务）与衰减在哪一段，并给出护栏为什么能兜住风险。
