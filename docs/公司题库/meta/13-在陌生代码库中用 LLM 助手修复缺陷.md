## 一句话答案

> 答成一套**带外部判据的五段流程**，而不是工具清单：**复现并锁定判据 → 用检索与插桩定位到最小上下文 → 单点最小改动 → 定向测试 → 全量回归**，每一段都以一条跑得起来的命令或一个由红转绿的测试收尾，最后复述取舍。写码不占大头，占大头的是把「某个行为出了问题」变成可复现、外部可判定的判据。
> 三个评分点要主动交代：① 每一步都有可执行的外部判据（命令、测试、可观察的状态 diff），不靠「我觉得好了」；② 每一行 diff 都能解释为什么改这一处、怎么知道改对了；③ 说清助手在哪几段提速（检索、样板、补丁草稿、测试骨架），在哪几段必须自己接管（理解契约、并发与副作用、验收口径）。
> 一句话的边界：**助手给的「根因」在变成 diff 并通过一次可执行观察之前只是假设**，验证器必须比对外部状态而不是助手自评。

## 面试官在考什么

- **是不是先立判据再动手**：Meta 2026 年部分流程新增的 AI 辅助编程轮分三阶段——探索并修复问题、实现新功能、扩展并改进系统——第一阶段考的就是排障流程。整轮通常压在 45 分钟到 1 小时，合理节奏是复现 8 分钟、定位 12 分钟、单点修改 8 分钟、定向测试 7 分钟、全量回归 6 分钟、收尾复述 4 分钟（建议口径，按题目难度浮动）。
- **有没有可复现的最小失败用例**：SWE-bench 的判定口径就是「补丁必须让目标测试由失败转为通过，且不破坏已有测试」，2,294 个真实 issue、12 个 Python 仓库，论文当时最强的 Claude 2 只解决 1.96%（2023-10 口径，榜单已被后续系统大幅刷新）。仓库级修复本身就极难，先复现再动手是唯一会收敛的路径。
- **检索与上下文组装是不是有策略**：陌生仓库里权重最高的信号是诊断输出与失败的测试（失败测试名加断言等于把可执行的验收条件交到手上），其次是由报错栈出发的定位链（栈帧 → 符号名 → grep 定义与引用 → 调用方），而不是一上来做语义相似度检索。
- **改动是不是最小的，验收是不是外部的**：助手自评「已修复」不构成验证器；验证必须是测试结果、终态 diff、schema 校验或不变量断言。这一点是生产系统与演示稿的分界线。
- **权限与边界有没有想过**：默认只读起步、写文件与执行命令要显式授权与沙箱、进上下文之前做出口过滤、不可逆操作留快照与审计。

常见错误答案：

- 把题目答成工具测评：「我会用 Claude Code 的 Grep 找文件、Edit 改代码、Bash 跑测试」——没有判据、没有最小复现、没有回归，也没说清助手在哪一段不可信。
- 直接让助手读一堆文件、一次给出完整补丁，跑一遍测试通过就结束：跳过了基线（本来就红的失败被算进自己账上）、跳过了定向测试与全量回归，也解释不了 diff 里每一行为什么这么改。

## 原理与推导

### 1. 第一步不是读代码，而是把行为钉成判据

入场先找三类入口：构建与测试命令、CI 配置、仓库里的项目记忆文件（`CLAUDE.md`／`AGENTS.md` 这类自动加载的常驻说明）。先跑一遍现成测试套件拿基线，把「本来就红」的失败排除在自己账外——这不是洁癖，而是归因的前提。然后写最小失败用例：一个 failing test，或一行命令的复现脚本，让它稳定失败。

判据必须外部可判定。可用的验证器只有四类：测试结果（红转绿）、程序终态 diff（数据库行、文件内容、响应字段）、schema 与类型校验、不变量的断言。助手说「我改好了」只是文本。SWE-bench 这一点做得最干净：判定不看你改了几行，只看目标测试与既有测试的通过状态。

### 2. 定位靠检索与符号，而不是把仓库塞进上下文

两条公开路线要能对比。第一条不建仓库索引，靠 grep／glob 按需搜索，把智能放在「模型决定搜什么」上（Claude Code 的公开叙述明确说没有特殊索引，逐层收窄：成千文件 → 少量命中文件 → 只读真正相关的两三个文件）。第二条是结构感知切分加符号图（定义／引用／调用边）加文件级与仓库级分层摘要，向量检索只补词汇重叠低的长尾（Cursor 等商业 IDE 助手的公开叙述如此，实现细节未逐一核验）。

索引的钱不是瓶颈。按作业单口径复算：6,000 文件 × 400 行 × 4.2 token/行 ≈ $1.008 \times 10^7$ token；用 $2NT$ 估嵌入算力，H100 bf16 稠密 989 TFLOPs、MFU 30%（≈296.7 TFLOPs）、租价 \$2/GPU·h，N=110M 的 code encoder 全量一次只要 7.47 s ≈ \$0.0042，换成 7B 级模型是 475.6 s ≈ \$0.264（63.6 倍）。真正的瓶颈是新鲜度：保存后增量路径要秒级可检索，而**索引过期比索引缺失更糟**——返回已删除的旧签名，助手会照着写出编译不过、跑不起来的代码。

组装侧三条纪律：片段一律带 `path:line-range` 加内容哈希标注；按 token 预算从高到低贪心装入；装入的每一片都能说出「为什么是它」。在我复算的语料里，200 行片段的标注开销是 14.4 token，占片段 0.70%——很便宜，但它是过期检测与引用溯源的唯一凭据。

### 3. 假设—验证循环：短步、检查点、反事实重跑

不要一次要一个完整补丁，而是每轮只让助手读少量相关文件、提出**一个**假设、做一个最小改动，然后把外部观察（测试输出、日志、状态 diff）回灌。这就是 ReAct 的 Thought → Action → Observation 在生产里的形态。口径：HotpotQA 的人工标注里，CoT 的失败模式中 56% 是幻觉，ReAct 是 0%；代价是 ReAct 有 23% 的失败变成「检索没查到有用信息」——**外部反馈的质量直接决定循环的质量**。

步数要切短并加检查点。每步 0.95 的正确率跑 20 步只剩 35.8%（半衰期 13.5 步）。把 20 步切成 $L$ 段、段末放验证器（以概率 $c$ 抓到失败段并允许一次重试）时：

$$p_{\text{seg}} = p^{s}, \qquad p_{\text{eff}} = p_{\text{seg}} + (1-p_{\text{seg}})\,c\,p_{\text{seg}}, \qquad P_{\text{整体}} = p_{\text{eff}}^{L}$$

代入 $p=0.95$、$s=5$、$c=0.9$、$L=4$：段成功 0.7738，段有效 0.9313，整体 75.2%，期望 24.07 步（+20.4%）。所以本题落到五段带判据的流程，而不是让助手连着改五个文件最后一起验证。

归因前先固定变量：commit、依赖与运行时版本、构建产物、模型与提示版本——缺了这些，后面每一步都无法归因。**换一个更强的模型等于顺手改了变量**，只能当 A/B 实验做，不能当修复手段。区分「能力不足」与「上下文管理不当」的判据是反事实重跑：把目标步骤放进只含任务说明、当前状态与该步所需文件的干净上下文重跑多次，成功率显著回升就是上下文问题（污染、位置偏置、压缩丢约束），仍稳定失败才是缺信息或缺工具。

### 4. 定位「第一次偏离」，而不是解释最后一步为什么错

把失败轨迹与已知正常路径对齐做 diff（按符号名、参数、返回结构对齐），或对状态做二分回放，$m$ 步最多 $\lceil \log_2 m \rceil$ 轮就能收敛到第一次变坏的那一步（40 步 6 轮，实测最坏 6 轮、平均 5.40 轮）。有 git 历史时先用 bisect 做同一件事；没有历史就沿调用链或数据流插桩二分——加日志、断言不变量、缩小输入——把范围切到最小复现。

对齐 diff 比逐句读日志强，因为它直接给出「哪一步开始与正常路径不一致」。在验证用的样本仓库里，正常路径会调用两次 `discounts.rate_for`，失败路径只调用一次，第一次偏离就是那次**缺失的调用**——根因在缓存键，而不在折扣规则本身。

### 5. 最小改动与四道补丁闸门

交付两样东西：最小改动本身，和证明它不回归的测试。补丁形式的失败模式要点名：整文件重写成本随文件长度线性上涨，助手还爱顺手改进无关代码、丢注释，长文件会被截断；search/replace 块便宜，但会匹配 0 次（空白与上下文漂移）或匹配多次（改错位置）；unified diff 会因行号漂移让 hunk 失败。

落地四道闸，任一级失败就把最小诊断回灌重试：**唯一匹配校验 → 语法／AST 解析 → 类型与 lint 无新增诊断 → 相关测试子集**（改动文件加 import 它的文件）。对外可以报「应用成功率 ≥ 85%、编译通过率 ≥ 95%」这组门禁口径（自设目标，不是实测值）。两条工程坑必须点出：以文件内容哈希做乐观并发（应用前比对哈希，不一致就拒绝并在最新内容上重生成，或退化为展示 diff 让人来合）；写操作前落快照、逐块接受、提交走原子写。

错误路径按类处置：只有瞬时错误才有限重试，参数错误不重试而是回灌可操作信息，语义失败当事实。重试放大是 $(r+1)^L$——三层各重试 2 次就是 27 倍，所以「多试几次」不是可靠性策略。

### 6. 验收：定向测试、全量回归与 pass^k

最小复现要转成永久回归测试并进发布门禁（离线门禁 → 影子 → 灰度）。验收口径用任务成功率加 $\text{pass}^k$（同一任务重复 $k$ 次全部成功），而不是单次通过或平均值：$\tau$-bench 口径下最好的 function calling agent 在零售域 $\text{pass}^1$ 约 61.2%、航空域约 35.2%，零售域 $\text{pass}^8$ 掉到 25% 以下——**一次修好不等于稳定修好**。所以「本地跑绿了」只是入场券，回归测试与门禁才是交付物。

### 7. 权限与安全边界

助手默认只读起步（只允许读文件、跑测试），写文件与执行命令要有显式授权与沙箱。进上下文之前做出口过滤：按 `.gitignore`／`.aiignore`、`.env` 与 `*.pem` 一类文件、高熵字符串三重剔除，日志与轨迹里的源码片段脱敏，私有代码是否上传外部服务做成显式开关。反向风险同样要防——助手可能把凭据写进代码，pre-commit 扫描要覆盖。

不可逆操作（提交、推送、删文件、改数据库、发消息）保留快照、回滚路径与审计记录：每一步的工具名、归一化参数、原始返回、当时生效的模型与提示版本都要落盘，否则事后无法复现一次失败，也无法二分定位。最后是分水岭：**并发、性能与数据竞争一类的缺陷，在没有运行时可观测性时模型只能猜**——正确顺序是先补日志、指标与最小基准（口径化的延迟与吞吐），再让助手基于新证据提假设；涉及数据契约、权限边界与发布时机的判断必须自己拍板。

## 数值与代码验证

本节全部数字来自本机实跑：脚本 `.work/lane-a/meta13_verify.py`（纯标准库，Python 3.10.12），语料是仓库自身文本（该次运行时快照：228 文件、75,224 行）加一个自建的多文件样本仓库 `.work/lane-a/meta13_repo/`（17 文件、475 行，Python 服务加 `README.md`／`CLAUDE.md`，含一处跨文件缺陷：症状在 `tests/test_pricing.py`，根因在 `service/pricing.py` 的缓存键）。token 一律用 `len(text)//4` 代理，耗时类数字受机器负载影响、看量级即可。

| 项 | 口径 | 结果 |
| --- | --- | --- |
| 向量存储 | 768 维 fp32 / int8 | 35.2 MiB / 8.8 MiB 每仓库 |
| 向量存储 | 1536 维 fp32 / int8 | 70.3 MiB / 17.6 MiB 每仓库 |
| 全量嵌入（N=110M） | $2NT$，296.7 TFLOPs（989×30%） | 7.47 s ≈ 0.00208 GPU·h ≈ \$0.0042 |

| 单文件增量（1,680 token） | 保存后重嵌入 | 1.25 ms（110M）／79.3 ms（7B），全量是它的 6,000 倍 |

结论：索引算力是零钱，瓶颈在新鲜度与增量路径。作业单口径的向量占用是 33.6 MiB，我用 200 行/块、768 维 fp32 复算是 35.2 MiB（差 4.6%，差异来自分块粒度；换 1536 维翻倍，int8 量化降到四分之一）。**索引过期比缺失更糟**在样本仓库上可以直接演示：建好符号索引后把 `discounts.rate_for` 重命名为 `rate_for_v2`，基于旧签名生成的调用报 `AttributeError: module 'service.discounts' has no attribute 'rate_for'`；加上内容哈希校验后该片段被拒（拦截 1/1），要求重新检索。

表 3：上下文组装（实测语料）

| 项 | 实测 |
| --- | --- |
| 本仓库文本语料 | 228 文件、75,224 行 → 1,025,406 token，13.63 token/行（文档为主） |
| 样本仓库（服务代码 + 项目记忆） | 17 文件、475 行 → 3,297 token，6.94 token/行 |
| 与 4.2 token/行 口径的偏差 | 样本代码偏 1.7 倍、文档语料偏 3.2 倍（4.2 ≈ 17 字符/行的紧凑代码） |
| 片段（200 行）+ `path:line-range@hash8` 标注 | 平均 2,050 + 14.4 token，标注占 0.70% |
| 32,000 token 预算 | 装 15 个片段 = 3,000 行，只覆盖全部语料的 4.0% |
| $1.008 \times 10^7$ token 对上下文 | 200K 窗口装 2.0%（要 50.4 个窗口）；1M 窗口装 9.9%（要 10.1 个）；全发一遍 \$30.2 |

所以「把仓库塞进上下文」不是态度问题而是算术问题：样本仓库里「把相关的 7 个文件都读一遍」只花 1,830 token（占 55.5%），同一个比例放到 6,000 文件仓库就是 $5.6 \times 10^6$ token，超出任何窗口——陌生大仓库必须检索。

表 4：补丁形式与漂移（样本仓库真实代码，200 个 4 行区域）

| 场景 | 精确／严格口径 | 归一化／模糊口径 |
| --- | --- | --- |
| 锚点唯一性 | 1 行锚点 94.9% 唯一 | 3 行锚点 99.3% 唯一 |
| search/replace：块被加了尾随空格 | 1 次 0 / 0 次 200 | 200 / 0（只归一化尾随空白即可救回） |
| search/replace：缩进 4→2 空格 | 1 次 27 / 0 次 173 | 200 / 0（需同时归一化缩进） |
| unified diff：hunk 上方插入 $k \ge 1$ 行 | 严格行号 100% 失败 | ±50 行模糊定位 100% 成功，偏移恰好 $+k$ |
| 整文件重写 vs 最小编辑 | 19／29／77 行文件是 2.3× / 3.9× / 9.4× | 最小编辑稳定在 33–71 token |

这几行分别对应四道闸的必要性：1 行锚点有 5.1% 的概率匹配到多处（必须拒绝并要求更长上下文），3 行锚点仍有 0.7%；统一 diff 的行号不可信，必须允许按上下文重新定位；归一化也不是万能药——块内空行被折叠时，200 个区域里仍有 31 个在两种匹配器下都匹配 0 次，这类补丁只能重新生成。整文件重写不是「更保险」，它把成本从常数变成了 $O(\text{文件长度})$。

## 常见追问

- **追问**：为什么不直接把整个仓库喂给助手？
  - 要点：算术上不成立。$1.008 \times 10^7$ token 的仓库要 50.4 个 200K 窗口，全发一遍按 \$3/百万 token 是 \$30.2 且每次追问都重付；更糟的是无关片段会稀释位置权重并挤掉诊断输出。正确做法是先把失败测试与报错栈放进上下文（它们权重最高），再沿着栈帧 → 符号名 → grep 定义与引用 → 调用方逐跳取片段，每片带 `path:line-range@hash8`。
- **追问**：如果索引／检索返回的签名已经过期怎么办？
  - 要点：比对内容哈希，不一致就拒绝该片段并要求重新检索，绝不在旧签名上生成代码。实测把 `discounts.rate_for` 重命名后，基于旧索引生成的调用直接 `AttributeError`；哈希校验拦截 1/1。索引过期比索引缺失更糟，因为缺了会退化成搜索，过期会静默生成不可用代码。
- **追问**：怎么证明助手改的这一处是对的，而不是碰巧让测试过了？
  - 要点：四道闸加一次归因。唯一匹配（1 行锚点 5.1% 会匹配多处）→ 语法／AST → 类型与 lint 无新增诊断 → 相关测试子集；再加上轨迹对齐说明「第一次偏离」就在这一处。最后把最小复现固化成永久回归测试，进离线门禁。
- **追问**：助手说它修好了，但你发现没修好，接下来怎么做？
  - 要点：先做反事实重跑，区分「能力不足」与「上下文管理不当」——把该步放进干净上下文（任务说明 + 当前状态 + 该步所需文件）重跑，成功率回升就是上下文问题（污染、位置偏置、压缩丢约束）；仍稳定失败才是缺信息或缺工具。归因前先固定变量（commit、依赖版本、模型与提示版本），换模型只能当 A/B 实验做。
- **追问**：并发、性能这类缺陷，助手能帮上什么？
  - 要点：没有运行时可观测性时模型只能猜。正确顺序是先补日志、指标与最小基准（口径化的延迟与吞吐），再让助手基于新证据提假设。在样本仓库上，争议点是缓存键，而缓存命中数（hits/misses）正是那个「先补的指标」——它把「第二次报价偏低」直接指向缓存。
- **追问**：权限上你会怎么设？
  - 要点：默认只读起步，写文件与执行命令要显式授权并跑在沙箱里；出口过滤三重剔除（忽略文件、凭据类文件名、高熵字符串），实测朴素高熵在真实语料上误伤 89.0%，所以要路径规则先行；不可逆操作留快照与审计（工具名、归一化参数、原始返回、模型与提示版本），私有代码外发做成显式开关，pre-commit 覆盖「助手把凭据写进代码」的反向风险。
- **追问**：时间只有 45 分钟，怎么排？
  - 要点：复现 8 分钟（跑基线 + 写最小失败用例）、定位 12 分钟（日志与插桩二分、轨迹对齐）、最小改动 8 分钟、定向测试 7 分钟、全量回归 6 分钟、收尾复述 4 分钟。写码本身不占大头，宁可少改一行也要把判据说清——面试官追问的是「你怎么知道改对了」。
