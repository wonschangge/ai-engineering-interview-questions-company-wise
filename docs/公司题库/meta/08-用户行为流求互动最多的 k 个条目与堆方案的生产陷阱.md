## 一句话答案

> 第一问是三段式：先把「互动最多」的口径写死（加权分、同用户去重、统计窗口、迟到、并列、可见性），再做一次哈希计数 $O(n)$，最后用大小 $k$ 的最小堆 $O(m\log k)$ 或一次选择取前 $k$——$n$ 是事件数，$m$ 是窗口内不同条目数，这两个量必须分开记账。
> 第二问的答案不是「堆更慢」，而是**堆的前提在生产里不成立**：堆要求完整计数表已经在手，而用户行为流只有一遍、窗口滑过无法回填，条目基数到 $10^9$ 时精确计数表按 80.0 B/条要 80.0 GB、单机放不下；把各分片本地 top-$k$ 归并还会漏掉全局第一——实测条目 X 在 5 片里各出现 7 次、全局 35 次排第一，却不在任何一片的本地前三里。
> 生产解法是概率结构 + 显式误差形状 + 计数同步更新、榜单异步发布。堆本身没有被淘汰，被淘汰的是「只靠堆」。

## 面试官在考什么

- **Meta 现场口径**（README.zh-CN.md 的 Meta 一节）：技术初筛 45 分钟内 2 道编程题，onsite 还有两轮编程；2026 年部分流程加入 AI 辅助编程三阶段（探索并修复问题、实现新功能、扩展并改进系统）。所以第一问要在 10 分钟内交出能跑、带边界断言的实现，第二问才是区分度所在。
- **复杂度记账**：全排序 $O(n\log n)$、哈希计数 + 最小堆 $O(n\log k)$／额外空间 $O(k)$、哈希计数 + 一次选择（`argpartition`／quickselect）期望 $O(n)$，三档都要给，并说清各自的常数在什么输入上翻盘。
- **契约先于代码**：加权互动分、同用户去重、统计窗口、迟到事件、并列 tie-break、可见性过滤、$k$ 边界——这些不写死，两个实现就是两个答案。
- **生产批判的四条**：基数无界（状态放不下）、事件流只有一遍（前提不成立）、跨分片本地归并漏全局第一（分布式语义错）、口径变更要能重放。
- **近似算法与可观测**：说得出 Misra-Gries／Space-Saving 的保留保证与计数方向，报得出误差上界、更新吞吐、内存上限、p99 更新延迟这四项。
- **与 [[meta-06]] 的分工**：那篇负责同族三题（K 近点、top-k 频次、最少会议室）的机制与复杂度记账，本篇只负责用户行为流这一题的口径、三档实现与流式／分布式生产批判，两篇互相引用但不重复。

常见错误答案：

- 「堆是 $O(n\log k)$，生产也没问题」——答不出堆的成立前提是「完整计数表已在手」，也给不出内存分段数字与淘汰策略。堆的价值在 $O(k)$ 空间与单遍增量，不在绝对速度：本次实测 $n=10^6$、$k=10$ 时 `heapq.nsmallest` 28.2 ms 对 `np.argpartition` 10.7 ms（2.6×）。
- 把「保留有保证」与「计数只高估」说成同一个算法的性质。Misra-Gries 的计数是下界、保留阈值 $N/(k+1)$；Space-Saving 的计数是上界、保留阈值 $N/k$。
- 第二问只答「数据量大、内存放不下」，没有分段数字、没有淘汰与衰减策略、没有迟到与归并口径。

## 原理与推导

### 1. 先定义「互动最多」，再写代码

题面里的「互动最多」在生产里不是一个整数，而是一整套必须先与产品方确认的定义：

| 口径 | 必须先确认什么 | 不写死的后果 |
| --- | --- | --- |
| 加权互动分 | 点赞／评论／转发／长按／观看时长的权重表，且随榜单一起版本化 | 权重没确认就等于把口径偷偷定死；改权重等于换榜单 |
| 同用户去重 | 同一 `(user, item)` 在窗口内只算一次 | 刷量、脚本与客户端重试会把榜单直接打穿 |
| 统计窗口 | 滚动 24 小时／自然日／会话内，边界左闭右开 | 窗口决定「最多」的答案，跨窗口的分数不可比 |
| 迟到事件 | watermark 与宽限期，超期丢弃还是旁路补算 | 同一窗口每重算一次，top-$k$ 就变一次 |
| 并列 tie-break | 分数降序 + 条目 id 升序（或稳定输入序） | 同一份数据两次请求返回不同的 top-$k$ |
| 可见性 | 已下架／不可见／地域受限的条目是否过滤 | 榜单出现点不开的条目 |
| $k$ 边界 | $k\le0$ 返回空；$k\ge$ 条目数返回全部 | 崩溃或死循环 |
| 返回值 | 是否带分数、是否分页、是否稳定排序 | 前端展示顺序与后端契约不一致 |

八条里任何一条缺失，「同一个问题」就有两个正确答案。这正是面试官用来判断「写过生产代码还是只刷过题」的地方——先花两分钟把这张表讲出来，比多写十行代码得分更高。

### 2. 第一问的三档实现

整条流水线是「计数 → 选择」：计数是 $O(n)$ 时间、$O(m)$ 空间；选择才轮到堆、快速选择或全排序。

| 档位 | 第二步实现 | 时间 | 额外空间 | 适用区间 |
| --- | --- | --- | --- | --- |
| 朴素 | 计数表全排序 | $O(m\log m)$ | $O(m)$ | $k$ 与 $m$ 同量级，或本来就要全序 |
| 期望解 | 大小 $k$ 的最小堆（`heapq.nsmallest`） | $O(m\log k)$ | $O(k)$ | $k\ll m$；数据增量到达、不能留全量 |
| 更优解 | 一次选择（`np.argpartition`／quickselect） | 期望 $O(m)$，最坏 $O(m^2)$ | $O(m)$ 索引 | 计数表已在内存，一次取前 $k$ |
| 特例 | 按互动分分桶的桶排序 | $O(n)$ | $O(n)$ + 桶数组 | 分数是整数且上界已知，且完整计数表在手 |

两个 Python 细节（与 [[meta-06]] 同源）：① `heapq` 是小顶堆，要留分数最大的 $k$ 个就取 `(-分数, 条目)` 的 $k$ 个最小项；② 不可比较的载荷放进元组第二项会在分数并列时抛 `TypeError`，tie-break 必须写进 key。第一步的实现层次直接决定吞吐：本次实测 $n=2\times10^6$、基数 74,695 时，`Counter(list)` 的 C 路径 109.0 ms（18.3 M 事件/秒），纯 Python 循环 180.0 ms（11.1 M 事件/秒）。[[meta-06]] 记录的 11.1 M 次/秒正是后者的口径。

### 3. 选型靠实测，不靠复杂度表

「$O(m\log k)$ 比 $O(m\log m)$ 好」只在 $k$ 真远小于 $m$ 时成立，而且语言层的比较常数会吃掉渐进优势。$n=10^7$ 个 float32 分数上的选择对全排序（`argpartition` + 对 $k$ 项精排，对比 `argsort`）：

| $k$ | $k/n$ | 全排序 | 选择 | 排序/选择 |
| --- | --- | --- | --- | --- |
| 10 | $10^{-6}$ | 1177.6 ms | 89.3 ms | 13.19× |
| 100,000 | 0.01 | 1324.3 ms | 87.9 ms | 15.06× |
| 2,000,000 | 0.2 | 1258.9 ms | 318.0 ms | 3.96× |
| 5,000,000 | 0.5 | 1303.9 ms | 737.2 ms | 1.77× |
| 9,000,000 | 0.9 | 1400.9 ms | 1419.9 ms | 0.99× |

$k/n\le0.01$ 时选择便宜 13–15 倍，$k/n\approx0.9$ 时已经不再划算——「$k$ 接近 $n$ 就直接排序」这条线要按自己的语言与 dtype 实测。同一份计数表（$n=2\times10^6$、基数 74,695、最大频次 271,655）取 top-100 的三档：全排序 40.5 ms、最小堆 8.6 ms、桶排序 107.3 ms——桶数组长度 271,656，分配本身的代价让桶排序比堆慢 12.5 倍，三档的 top-100 频次剖面完全一致，差异在开销不在答案。

### 4. 第二问：堆在生产里被否掉的四条

**第一条：基数无界。** 堆的前提是「完整计数表已经在手」。按每条目 80.0 B 的元数据口径（与 [[coding-06]] 一致；本篇实测 Python `dict` 存 100 万条 int→int 的 `tracemalloc` 峰值是 82.5 B/条，同一量级）：$10^7$ 个 key 约 0.8 GB、$10^8$ 个约 8.0 GB、$10^9$ 个约 80.0 GB，最后一行已经超出单机内存——精确方案连「可堆的数据」都拿不到。而计数吞吐根本不是瓶颈：单机 18.3 M 事件/秒相当于 $1.59\times10^{12}$ 事件/天，即使把业务峰值按 1 M 事件/秒的估算口径放进同一台机器，计数还剩 18 倍余量。**瓶颈在状态，不在速度**，所以「换更快的语言重写堆」解决不了第二问。

替代路线有三条。概率结构（Misra-Gries／Space-Saving）用 $O(k)$ 空间换近似，误差形状见第 5 节；按 key 分片加两级聚合把状态摊到多机；以及把内存上限当成硬约束写进口径——什么时候淘汰冷 key、计数是否需要衰减。Redis 的 Key eviction 文档给的正是这套取舍：`maxmemory` 到顶后按策略淘汰，`allkeys-lru` 与 `volatile-lru` 是「所有 key 都可淘汰」与「只有带 TTL 的 key 可淘汰」两条不同语义；LRU 本身是近似的，随机采样若干 key 比较空闲时间（文档示例 `maxmemory-samples 5`，并说明取 10 已非常接近真 LRU），文档给的理由是「真 LRU 更费内存」；LFU 用一个 0–255 的概率计数器（Morris counter）估频次，默认在约 100 万次请求时饱和、每 1 分钟衰减一次（`lfu-log-factor 10`／`lfu-decay-time 1`）。榜单同理：不淘汰、不衰减，昨天的爆款会永久占据今天的榜。

**第二条：事件流只有一遍。** 堆要求先有全量计数，而用户行为流只有一遍、窗口滑过就无法回填，这个前提在流式场景里根本不成立。迟到事件（移动端离线补报、跨机房时钟漂移）必须给出 watermark 与宽限期口径，超期丢弃或旁路补算，否则同一窗口每重算一次 top-$k$ 就变一次。工程上的正确分工是**计数同步更新、榜单异步发布**——这与 Cloudflare 那条取舍同构：精确结构要在请求路径上做多次非原子操作，于是他们把计数改成异步执行，只把「是否开始限流」一个比特留在请求路径上。

**第三条：跨分片归并会漏掉全局第一。** 反例（实跑）：5 个分片，条目 X 在每片都出现 7 次，而每片本地前三分别是自家的 10／9／8 次条目。各片本地 top-3 归并出来的前三全是 `a0_0`／`a1_0`／`a2_0`，X 的全局频次是 35、真实排第一，却不在任何一片的本地前三里。两种分片语义必须分清：

- 按 key 分区（同一个 key 完整落在单片）时，本地 top-$k$ 归并是精确的：若 X 是全局前 $k$，它在自己那片里不可能掉出前 $k$，否则那片里有 $k$ 个 key 的频次高于 X 的全局频次。实测 200 组随机流、每片取 top-10 求和归并，与全局前 10 全等。
- 按事件分区（按用户、按机房、按时间）时没有这个保证：同一个 key 被拆到多片，全局最热的条目完全可能每片都只是第 4 名。用合成模型量化（5 个分片权重 0.50／0.20／0.15／0.10／0.05，1000 个条目，20 万事件，全局热度 Zipf(1.15)，每个「条目×分片」再乘一个 lognormal(0, σ) 独立噪声）：σ=0（各片热度一致）时本地归并的 recall@10 = 1.000；σ=1（同一内容在不同地区热度差 2–3 倍）时降到 0.955，40 次里 18 次有漏项、最差 0.9。这是估算口径的合成实验，但结论很硬：**漏不漏取决于「key 是否完整落在单片」与「全局热的是否每片也热」，而不取决于候选预算多大**。

修正只有两条：按 key 做一次 shuffle 全局聚合（代价是一轮网络与热 key 倾斜，单个爆款条目会把某个分片打热，需要本地预聚合 + 两级聚合），或改用近似算法并显式声明误差形状。

**第四条：口径一变就要重放。** 窗口长度、权重表、过滤规则、去重口径任意一条变更，历史榜单都得按新口径重算，否则线上表现是「榜单悄悄变了」而不是报错。计数与榜单因此必须版本化：口径版本随状态一起存，否则两天的 A/B 数据根本不可比。

### 5. 近似算法的保证要分清

Misra-Gries 与 Space-Saving 都是 $O(k)$ 空间，但性质不同：

| 算法 | 状态 | 保留保证 | 计数方向 | 误差形状 |
| --- | --- | --- | --- | --- |
| Misra-Gries | $k$ 个计数器 | 频次 $>N/(k+1)$ 的项一定在表内 | 下界（只低估） | 低估不超过 $N/(k+1)$ |
| Space-Saving | $k$ 个计数器 | 频次 $>N/k$ 的项一定在表内 | 上界（可能高估） | 高估量由替换时的最小计数决定，误差上界与 $N/k$ 同阶 |
| 精确计数 + 堆 | $O(m)$ | 精确 | 精确 | 无，代价是内存随 $m$ 增长 |

实测（$N=10^5$、$k=50$、目标项真值 2,500，20 次重复）：Misra-Gries 的估计中位数 552，低估 1,948——理论下限是 $2{,}500-1{,}960.78=539.2$，也就是它逼近的是**下界**而不是真值，20 次全部保留；Space-Saving 的估计中位数 2,501，高估 1，20 次全部保留。两者都保住了这个项，但「保留有保证」与计数方向是两件事，不能写成同一个算法的性质。[[meta-06]] 在同一组参数下记录过 MG 估成 1,939 的流，两次结果都落在 $N/(k+1)$ 的保证之内，差别只在流序。

### 6. 上线口径与可观测

上线判据不是「跑得对」，而是误差上界、更新吞吐、内存上限、p99 更新延迟四项都能报出来。配套五件事：

1. **判定与发布分离**：计数同步更新、榜单异步发布；发布按窗口**增量**更新，而不是每次全量重算。本次实测 $10^8$ 个分数上全量重排 20.4 s 对选择 1.27 s（16.0×，与 [[coding-11]] 记录的 18.4× 同一口径）；窗口增量只需在滑动时减去过期桶、加上新桶。
2. **三个可关掉的开关**：同用户去重、机器人／刷量过滤、计数衰减，每个都能单独关闭做 A/B，用来区分真热点与刷量。不能区分这两者的榜单，在被刷的时候是最后一个知道的。
3. **确定性输出**：并列按条目 id 升序；同一份数据两次请求必须逐字节一致，否则缓存与对账会出现幽灵差异。
4. **重放能力**：事件本身不可变，口径在查询侧版本化；窗口长度、权重表、过滤规则每次变更都能读历史事件按新口径重算，否则验证一次口径变更只能靠「等一周」。
5. **状态账**：$10^8$ 个 key 的 8.0 GB 状态在 H100 的 3.35 TB/s 上只读一遍要 2.39 s，这是任何「每次全量重算」方案的下限；H100 的 roofline 拐点是 $989/3.35\approx295$ FLOPs/byte，而这个任务几乎没有 FLOPs，纯带宽与状态。

## 数值与代码验证

环境：AMD Ryzen 9 8945HX（32 线程）、62 GiB DDR5、Python 3.10.12、numpy 2.2.6；脚本 `.work/lane-a/meta08_verify.py`、`.work/lane-a/meta08_verify_b.py`，正文代码块的逐字副本与断言在 `.work/lane-a/meta08_docblock.py`（全部通过）。共享机器上有其它负载，计时项取多次运行的最小值。单位口径：GB／TB 十进制，KiB／GiB 1024 进制。

```python
import heapq
from collections import defaultdict


def top_k_engaged(events, k, *, action_weight, window, visible=None,
                  watermark=None, dedup_user=True):
    """events: (ts, user, item, action)，按 ts 非降序；window 左闭右开。

    契约：k<=0 返回 []；k>=条目数返回全部；分数降序，同分按条目升序；
    权重表、窗口、可见性、去重口径全部显式传入，不给默认值。
    """
    if k <= 0:
        return []
    lo, hi = window
    seen, score = set(), defaultdict(float)
    for ts, user, item, action in events:
        if not (lo <= ts < hi):                 # 窗口左闭右开
            continue
        if watermark is not None and ts > watermark:
            continue                            # 超过水位线：迟到事件丢弃
        if visible is not None and item not in visible:
            continue                            # 已下架／不可见条目不进榜
        if dedup_user and (user, item) in seen:
            continue                            # 同一用户对同一条目只算一次
        seen.add((user, item))
        score[item] += action_weight[action]
    pairs = score.items()
    if len(pairs) <= k:
        return sorted(pairs, key=lambda kv: (-kv[1], kv[0]))   # k 大于等于条目数
    if k <= max(1, len(score) // 10):
        return heapq.nsmallest(k, pairs, key=lambda kv: (-kv[1], kv[0]))   # 大小 k 的堆
    return sorted(pairs, key=lambda kv: (-kv[1], kv[0]))[:k]   # k 接近基数：排序／选择
```

print([k for k, _ in sorted(merged.items(), key=lambda kv: (-kv[1], kv[0]))[:3]])

## 常见追问

- **追问**：为什么说你的堆方案在生产环境里可能是错的？
  - 要点：四条，每条都要带数字。① 基数无界：堆要完整计数表，$10^9$ 个 key 按 80.0 B/条是 80.0 GB，单机放不下；② 事件流只有一遍、无法重扫，堆的前提不成立，迟到还要 watermark 与宽限期；③ 跨分片本地 top-$k$ 归并会漏全局第一（X 每片 7 次、全局 35 次却不在任何本地前三里）；④ 口径变更（窗口、权重、过滤）要能重放。补一句：单机 18.3 M 事件/秒说明瓶颈在状态不在速度，堆并没有被淘汰，被淘汰的是「只靠堆」。
- **追问**：$k$ 远小于基数时，到底用堆还是用一次选择？
  - 要点：看数据在哪。计数表已在内存、只要前 $k$ 个，用选择（$k/n\le0.01$ 时比全排序便宜 13–15 倍）；要求 $O(k)$ 空间或数据是增量到达的，用堆。但别假设堆更快：Python 里 $n=10^6$、$k=10$ 时 `heapq.nsmallest` 28.2 ms 对 `np.argpartition` 10.7 ms。堆的收益是空间与增量，不是常数。
- **追问**：并列时怎么保证确定性？
  - 要点：把 tie-break 写进比较键：`(-分数, 条目 id)`。这样同分按 id 升序，同一份数据两次请求字节级一致；代价是 key 多一个字段。若产品接受「任意 $k$ 个」，也要在接口文档里写明，否则测试会偶发失败、缓存会出现幽灵 key。
- **追问**：Misra-Gries 和 Space-Saving 选哪个？误差怎么对产品说？
  - 要点：两者都是 $O(k)$ 计数器，保留保证不同（$N/(k+1)$ 对 $N/k$），计数方向相反（下界对上界）。要让产品看见「至少这么多」用 Misra-Gries，要让榜单不缺人用 Space-Saving（代价是可能高估）。实测里 MG 的中位估计 552 对真值 2,500——**它保证的是保留，不是精度**；把误差上界写进接口返回值和看板，而不是口头解释。
- **追问**：迟到事件超过宽限期怎么办？
  - 要点：先定口径再写代码：watermark 之前的事件走旁路补算（回填到已发布的窗口要触发重算与版本号），超期太久的直接丢弃并计入单调递增的丢弃计数。关键是「丢弃」必须有指标，否则丢的是哪部分流量永远说不清；同时用乱序延迟的 p99 来定宽限期，而不是拍一个数字。
- **追问**：单个爆款条目把一个分片打热怎么办？
  - 要点：两级聚合：分片内先做一次本地预聚合（例如按条目 hash 分桶的局部计数），再只把 top 候选发到聚合层，把 shuffle 量从「每事件一条」压到「每候选一条」。代价是误差与实现复杂度上升；如果热点是可预测的（置顶内容、直播），就把它单独走一条旁路，别让全局聚合为它让路。
