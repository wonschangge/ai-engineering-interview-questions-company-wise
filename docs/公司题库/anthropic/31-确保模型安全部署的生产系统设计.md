## 一句话答案

> 「安全部署」不是一个检查表，而是**一条流水线 + 三道闸 + 一个反馈环**：
> **流水线（五阶段）**：能力评估 → 发布门禁 → 分级发布 → 在线监控 → 回滚/下线。
> **三道闸**：
> ① **准入闸（上线前）**：预注册的评估套件（红线集 + 能力评估 + 滥用测试），**结论能否决发布**；判据要事先写死（阈值、样本量、判据方向），否则闸门会变成仪式（串 [[anthropic-27]] 的统计纪律）；
> ② **限流闸（上线中）**：**分级发布**——影子（shadow，不影响用户）→ 金丝雀（canary，小流量）→ 逐步放量 → 全量；每一级的**放量判据**是「关键指标没有超出阈值」，而不是「没看到问题」；
> ③ **熔断闸（出事后）**：**可一键回滚**（模型版本、提示、工具权限、检索索引都要能回滚）+ 明确的**回滚判据**（谁有权、看哪个指标、多长时间内决策）。
> **一个反馈环**：线上发现 → 固化成语料/评估用例 → 进入下一次准入闸（事故不重复犯）。
> 四件最容易被忽略、但决定成败的事：
> - **能力引出（elicitation）**：评估要主动把最坏能力「引出来」（越狱、多轮诱导、工具组合），而不是等它自然出现；
> - **权限最小化**：模型能力再强，部署时给它的权限也要按任务给（串 [[anthropic-28]] 的危险三角）；
> - **可观测的门禁**：监控指标必须与门禁判据**同源**（否则线上看到的「正常」和上线前的「通过」是两套语言）；
> - **组织层面的「否决权」**：安全评估方必须有权阻断发布，且这个权力要写在流程里而不是靠人情。
> 一句话判据：**部署安全 = 事先写好「什么算不安全」 + 让发布必须通过它 + 出事能在分钟级退回去。**

## 面试官在考什么

- **是否把「安全部署」拆成可执行阶段**：能说出五阶段、三道闸，并给出每阶段的**判据与责任人**——而不是罗列「要评估、要监控」。
- **判据是否预先写死**：阈值、样本量、判据方向、以及**谁能否决**；这一条区分「真门禁」与「仪式」。
- **分级发布的量化**：金丝雀放多少流量、放多久、用什么统计判据决定放量（见下表与代码）——这是最容易被问穿的地方。
- **回滚的工程现实**：模型回滚容易，但**提示、工具权限、检索索引、缓存**都要能回滚；还要能回滚「已经产生的副作用」（发送的邮件、写库的数据）——后者靠可撤销窗口与幂等设计（串 [[anthropic-28]]）。
- **监控什么**：滥用信号（越权尝试、注入攻击）、能力信号（危险能力的请求分布）、质量信号（幻觉率、拒答率）、系统信号（p99、错误率）；并且要区分「我的模型变了」与「用户变了」。
- **闭环**：事故/越狱是否固化成语料并进入回归；评估是否定期轮换以防过拟合（串 [[anthropic-27]]）。
- **组织与流程**：谁评估、谁批准、谁值班、升级路径；以及「发布压力」下的护栏（例如：不允许跳过评估，只能缩小范围）。
- **诚实**：不承诺「零风险」，而是给出**残余风险 + 处置预案**（发现后多久能止损）。

**常见错误答案**

- 只讲「上线前做一轮红队」——没有分级发布、没有监控、没有回滚。
- 门禁没有否决权（「评估提供了参考意见」）。
- 只监控基础设施指标（QPS、错误率），不监控滥用与能力信号。
- 回滚只考虑模型权重，忽略提示/工具/索引/缓存。
- 把安全与迭代对立起来（「要安全就没法快速迭代」）——正确做法是**用自动化把门禁做快**，而不是取消门禁。

## 原理与推导

### 1. 五阶段流水线

```
① 能力评估（离线）
   红线集 + 危险能力评估 + 滥用/注入测试 + 系统卡（记录限制与已知失效）
② 发布门禁（决策）
   预注册判据 → 通过/有条件通过（带限制）/阻断；结论可审计
③ 分级发布（在线）
   影子 → 金丝雀（1%–5%）→ 逐步放量（10/25/50%）→ 全量，每级有停留时间与放量判据
④ 在线监控（持续）
   滥用信号 / 能力信号 / 质量信号 / 系统信号；异常 → 自动降级或人工介入
⑤ 回滚与下线（应急）
   版本回滚 + 提示/工具/索引回滚 + 副作用处置 + 事后复盘固化成语料
```

**每阶段都必须有「退出判据」**（promotion criteria）与「否决者」（owner），否则流水线会退化为走过场。

### 2. 分级发布的量化：要多少流量才能发现问题

设要检出的问题发生率 $p$（例如「有害输出率从 0.5% 升到 1.5%」），金丝雀流量比例为 $f$、日请求量 $R$，则金丝雀每天能观察到的样本 $n=fR$。**至少检出一次**的概率为 $1-(1-p)^{n}$。

| 日请求 $R$ | 金丝雀 $f$ | 每日样本 | 检出 1% 问题的概率 | 检出 0.1% |
| --- | --- | --- | --- | --- |
| 100 万 | 1% | 10,000 | ~100% | 63% |
| 100 万 | 0.1% | 1,000 | 63% | 10% |
| 10 万 | 5% | 5,000 | ~100% | 39% |

**结论**：金丝雀比例不能拍脑袋定——**它由「要检出多小的问题」反推**。若要检出 0.1% 量级的问题，金丝雀当日样本需要上万条（或延长观察时间、或叠加离线评估）。

**同时对「回归」做统计判据**：比较金丝雀与基线组的指标差异，按两比例检验估样本量（串 [[anthropic-27]]）；**不要在样本不足时宣布「没问题」**。

### 3. 监控指标的四组（缺一组就会盲）

| 组 | 指标示例 | 异常含义 |
| --- | --- | --- |
| 滥用信号 | 注入尝试率、越权工具调用、异常外发 | 攻击面被触达 |
| 能力信号 | 危险能力请求分布、拒答率变化 | 能力/边界漂移 |
| 质量信号 | 幻觉率（引用可溯性）、任务成功率、人工抽检通过率 | 体验/正确性下降 |
| 系统信号 | p99 TTFT/TPOT、错误率、KV 占用 | 性能与容量（串 [[anthropic-17]]） |

**关键**：四组要**同源可比**——线上指标的计算方式必须与门禁评估一致，否则无法判断「上线前通过、上线后异常」。

### 4. 回滚设计（比监控更容易被忽略）

| 对象 | 回滚方式 | 难点 |
| --- | --- | --- |
| 模型版本 | 路由切回旧版本（保留 N-1 与 N-2） | 版本兼容（接口/提示/工具） |
| 提示/系统指令 | 配置中心版本化 + 一键切换 | 提示与模型版本的耦合 |
| 工具权限 | 权限策略版本化 + 立即收紧 | 已发出的调用无法撤回 |
| 检索索引 | 索引别名切回旧版本（蓝绿） | 新数据一致性（串 [[anthropic-24]]） |
| 缓存 | 版本号参与缓存键 → 自然失效 | 否则回滚后仍返回新结果 |
| **副作用** | 可撤销窗口（发送后 30 s 可撤回）、幂等键、补偿事务 | 已产生的外部效果无法完全回收 |

**演练**：回滚必须**定期演练**（像故障演练一样），否则真出事时才发现「回滚不了」（例如旧模型版本已被清理、提示与旧模型不兼容）。**目标：从决策到生效 ≤ 5 分钟。**

### 5. 组织与流程（技术的另一半）

- **否决权**：安全评估团队对发布有**阻断权**，写进流程；
- **分级审批**：能力提升越大、权限越高 → 审批层级越高（例如触及新能力/新工具权限必须升级）；
- **值班与升级**：谁在 7×24 值班、什么样的信号触发呼叫、多久必须响应；
- **发布窗口与冻结期**：重大事件期间冻结发布，避免「边救火边改模型」；
- **记录与审计**：每次发布的评估结论、批准人、限制条件、回滚点都要留档（事后复盘与合规都需要）。

### 6. 残余风险与处置（必须写出来）

- 承认**无法穷尽**所有滥用方式；
- 说明**发现到止损的时间**（检测延迟 + 决策延迟 + 生效延迟）；
- 准备**对外沟通**模板（影响范围、缓解措施、用户应采取的行动）；
- 把每次事件的根因与语料**固化进回归集**，并在下一次门禁中验证修复有效。

## 数值与代码验证

### 表 1：金丝雀放量的统计判据（示例）

| 阶段 | 流量 | 最短停留 | 放量条件 | 回滚条件 |
| --- | --- | --- | --- | --- |
| 影子 | 0%（复制流量） | 1 天 | 无崩溃、指标与基线同分布 | 任何异常 |
| 金丝雀 | 1% | 1 天 | 有害率未上升且样本量达判据 | 有害率上升超阈值 |
| 小流量 | 10% | 1 天 | 同上 + 人工抽检通过 | 任一红线触发 |
| 半量 | 50% | 1 天 | 同上 | 同上 |
| 全量 | 100% | — | 持续监控 | 熔断 |

### 表 2：检测能力 vs 金丝雀规模（日请求 100 万，$P=1-(1-p)^n$）

| 金丝雀流量 | 每日样本 | 检出 1% 问题 | 检出 0.1% 问题 | 检出 1% 所需停留 |
| --- | --- | --- | --- | --- |
| 0.1% | 1,000 | 100% | **63.2%** | 0.30 天 |
| 0.5% | 5,000 | 100% | 99.3% | 0.06 天 |
| 1% | 10,000 | 100% | **100%** | 0.03 天 |
| 5% | 50,000 | 100% | 100% | 0.01 天 |

**这里有一个反直觉但重要的结论**：**「至少检出一次」很容易**——1% 的金丝雀一天就有 1 万条样本，连 0.1% 量级的问题都能 100% 撞上；**真正的约束是「可靠地比较差异」**（见第二节的放量判据）：

| 要检出的上升幅度 | 基线 0.5% | 基线 1% | 基线 2% |
| --- | --- | --- | --- |
| +0.2 pp | 23,379 | 42,646 | **80,592** |
| +0.5 pp | 4,669 | 7,743 | 13,795 |
| +1.0 pp | 1,553 | 2,317 | 3,823 |

**读法**：要证明「有害率上升了 0.2 个百分点」需要**每组数万条**样本——在 1% 金丝雀（每天 1 万条）下意味着**要观察好几天**。所以金丝雀规模与停留时间应当**由「最小需要发现的变化幅度」反推**，而不是拍脑袋。

### 可运行代码

```python
# 安全部署的量化部分：金丝雀样本量与检出概率、放量判据、回滚时效预算
import math
from dataclasses import dataclass
from typing import Dict, List, Tuple

# 1) 金丝雀要多大才能发现问题？至少检出一次的概率
def detect_prob(p: float, n: int) -> float:
    return 1 - (1 - p) ** n

def required_n(p: float, target: float = 0.95) -> int:
    return math.ceil(math.log(1 - target) / math.log(1 - p))

print("① 金丝雀规模 vs 检出能力")
R = 1_000_000                     # 日请求量
print(f"  {'金丝雀流量':>10} {'每日样本':>10} {'检出1%问题':>11} {'检出0.1%问题':>12} {'检出1%需停留':>12}")
for f in (0.001, 0.005, 0.01, 0.05, 0.10):
    n = int(R * f)
    days = required_n(0.01) / n if n else float("inf")
    print(f"  {f:>10.1%} {n:>10,d} {detect_prob(0.01, n):>11.1%} "
          f"{detect_prob(0.001, n):>12.1%} {days:>11.2f} 天")
print("  读法：1% 金丝雀一天能可靠发现「1% 量级」的问题，但发现「0.1% 量级」只有 63%；")
print("        要发现更小的问题，必须「更大流量 / 更长停留 / 离线评估」三者至少选一")

# 2) 放量判据：比较金丝雀与基线的有害率差异（两比例检验的样本量）
def two_prop_n(p1: float, p2: float, alpha: float = 0.05, power: float = 0.8) -> int:
    pbar = (p1 + p2) / 2
    return math.ceil(2 * (1.96 + 0.84) ** 2 * pbar * (1 - pbar) / (p1 - p2) ** 2)
print("\n② 放量判据需要多少样本（比较金丝雀 vs 基线的有害率）")
for base in (0.005, 0.01, 0.02):
    for delta in (0.002, 0.005, 0.01):
        n = two_prop_n(base, base + delta)
        print(f"  基线 {base:.1%} -> 上升 {delta:.1%}（到 {base+delta:.1%}）："
              f"每组需要 {n:>7,d} 条样本")
print("  读法：要检出「有害率上升 0.2 个百分点」需要每组上万条 —— 这直接决定金丝雀规模与停留时间；")
print("        反过来，样本不足时「没看到上升」不能作为放量依据")

# 3) 回滚时效预算：检测 -> 决策 -> 生效，总时长决定影响面
@dataclass
class RollbackBudget:
    detect_s: float
    decide_s: float
    apply_s: float
    @property
    def total_s(self) -> float:
        return self.detect_s + self.decide_s + self.apply_s
    def affected_requests(self, qps: float) -> float:
        return self.total_s * qps

print("\n③ 回滚时效预算（影响面 = 总时长 × QPS）")
QPS = 1_000
cases = [
    ("自动化熔断（指标触发）", 60, 30, 60),
    ("人工值班响应", 600, 300, 120),
    ("发现问题时已下班", 3600, 1800, 300),
]
for name, d, dec, a in cases:
    b = RollbackBudget(d, dec, a)
    print(f"  {name:<22} 总 {b.total_s:>6.0f} s  影响请求 ≈ {b.affected_requests(QPS):>10,.0f} 条")
print("  读法：把「检测」自动化能省下一个数量级的影响面 —— 这是熔断闸最值钱的投入；")
print("        目标是「决策到生效 ≤ 5 分钟」，并且要定期演练（否则真出事时回滚不了）")

# 4) 回滚可演练性检查：哪些对象能回滚、需要多久
ITEMS: Dict[str, Tuple[bool, int, str]] = {
    "模型版本":      (True,  120, "保留 N-1/N-2 权重与路由开关"),
    "系统提示":      (True,  30,  "配置中心版本化，一键切换"),
    "工具权限":      (True,  60,  "策略版本化；已发出的调用不可撤回"),
    "检索索引":      (True,  300, "索引别名蓝绿切换"),
    "缓存":          (True,  0,   "版本号参与缓存键则自动失效"),
    "已发送的邮件":   (False, 0,  "只能靠可撤销窗口 + 事后沟通（不可完全回滚）"),
}
print("\n④ 回滚清单与时效（RTO 目标：决策到生效 ≤ 5 分钟）")
for name, (can, secs, note) in ITEMS.items():
    status = f"{secs:>4} s" if can else "不可回滚"
    print(f"  {name:<14} {status:>8}  {note}")
print("  读法：把「不可回滚的对象」显式列出来（本例是已发出的邮件）——")
print("        对这些对象必须在事前加约束（审批/可撤销窗口），而不是指望事后回滚")

# 5) 门禁的判据模板：每个条目都要有阈值、样本量与否决权
@dataclass
class GateItem:
    name: str
    threshold: str
    sample_size: int
    owner: str
    can_block: bool
GATE: List[GateItem] = [
    GateItem("红线集（有害输出）", "严重度≥高 的输出 = 0", 500, "安全评估", True),
    GateItem("越狱/注入回归", "攻击成功率不高于上次发布 +2 pp", 300, "红队", True),
    GateItem("能力评估（危险能力）", "无新增可操作的危险能力", 100, "能力评估", True),
    GateItem("质量回归", "任务成功率下降 ≤ 1 pp", 2000, "产品评估", False),
    GateItem("性能回归", "p99 TTFT 上升 ≤ 10%", 5000, "平台", False),
]
print("\n⑤ 门禁条目模板（有阈值、有样本量、有 owner、有否决权）")
for g in GATE:
    print(f"  {g.name:<22} 阈值：{g.threshold:<28} n={g.sample_size:>5} "
          f"owner={g.owner:<6} 可否决={'是' if g.can_block else '否'}")
print("  读法：没有样本量与否决权的门禁条目等于没有；")
print("        质量/性能条目通常只做「条件通过（带限制）」，安全条目必须能阻断")
```

预期输出要点（实跑）：① 金丝雀规模表给出一个反直觉结论：**「至少检出一次」很容易**（1% 金丝雀一天 1 万条样本，连 0.1% 量级的问题都能 100% 撞上；0.1% 金丝雀对 0.1% 问题只有 63.2%），**真正的约束是可靠比较**；② 而放量判据要的是可靠比较：检出**+0.2 个百分点**的上升需要每组 **2.3 万–8.1 万条**样本（取决于基线水平），在 1% 金丝雀下意味着要观察数天——**金丝雀规模与停留时间应当由这个数字反推**；③ 回滚时效预算显示**自动化熔断（总 150 s）与人工响应（1,020 s）的影响面差一个数量级**（本机口径 1,000 QPS 下 15 万 vs 102 万请求）；④ 回滚清单把「**不可回滚的对象**」（已发送的邮件）显式列出，提醒这类对象必须靠事前约束；⑤ 门禁条目模板强调**阈值 + 样本量 + owner + 否决权**四要素缺一不可。

## 常见追问

- **追问**：如果业务压力要求快速发布，怎么不破坏门禁？
  - 要点：**缩短门禁时间而不是取消门禁**——把评估自动化（回归集 nightly、指标自动计算、结论自动生成）；允许「分级放行」（先在受限功能/受限用户群上线）；对确需紧急发布的，走**带限制的例外流程**（记录批准人、缩短观察窗口、加严监控、预先写好回滚）。
- **追问**：如何判断线上异常是模型问题还是用户行为变化？
  - 要点：**对照组**——保留一小部分流量走旧版本（或按用户分桶做 A/A 与 A/B），对比同分布用户群；同时看输入分布是否漂移（提示长度、语言、任务类型）。没有对照就无法归因。
- **追问**：安全评估如何避免「对评估集过拟合」？
  - 要点：私有留出 + 定期轮换 + 只报告最终一次结果 + 记录评估集访问；把「评估集访问次数」当作需要管理的资源（串 [[anthropic-27]]）。
- **追问**：怎样让门禁在组织里真正生效？
  - 要点：写进流程（谁能否决、升级路径）、把否决权与「发布责任人」分离、对跳过的例外要求书面批准与后续补测；并让门禁结果**公开可见**（团队内看板），形成社会压力。
- **追问**：模型能力提升很快，旧的门禁条目会不会失效？
  - 要点：会——门禁套件需要**随能力演进**更新（新增危险能力项、加严阈值）；把「门禁套件本身的版本与依据」也纳入审计，避免「用去年的标准评估今年的模型」。
- **追问**：小团队没有专门的安全团队怎么办？
  - 要点：用**自动化 + 外部评估**替代常设团队：自动化红线回归 + 定期第三方评估 + 明确一名有否决权的 owner（可以是兼职）；关键是**否决权必须有人持有**。
