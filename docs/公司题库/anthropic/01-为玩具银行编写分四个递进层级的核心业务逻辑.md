## 一句话答案
> 四层递进（账户与余额 → 转账与多账户 → 时间、计息与对账 → 并发、回滚与审计）真正的分水岭在第 1 层：把业务动作收敛成开户、存取、转账、明细几个入口，统一返回 `{ok, code, balance, tx_id}` 结构体，业务拒绝走返回值、只有实现错误才抛异常、绝不用 print 或异常类型当判分依据；再把写路径切成「解析 → 幂等查表 → 校验 → 结算 → 存储」五段，后面三层才可能只新增一段，而不是回头改散落各处的 if。
> 两条不可协商的表示：金额一律用整数最小单位（分），时间一律用整数毫秒且由 clock 依赖注入；每笔操作之后都要能用**公开状态**复算三条不变量——Σ余额 == Σ流水 delta、余额非负、转账两腿之和为 0。
> 第 4 层是最常见的失分点：写操作必须带幂等键加去重表（TTL 与容量是两套正交机制，仍在 TTL 内的键绝不淘汰），读-改-写必须在同一个临界区（实测无锁 check-then-act 在 16 线程 × 20 次下放行 102–109 次，而额度只有 100），批量工作必须既有界又有有序过期索引（实测单次清 64 条 0.297 ms，一次清 20 万条 487.4 ms）。

## 面试官在考什么
- **契约有没有在第 1 层冻结**：入口数是常数级、返回同构、拒绝与错误分层（业务拒绝 vs 实现错误）、结果只走返回值。这决定了第 4 层是「加一段」还是「推倒重来」。
- **seam 留得对不对**：解析、幂等查表、校验、结算、存储五段是否各自独立可测；黑盒评测器只看公开返回值与最终状态，所以「不变量能不能在外部复算」比内部结构漂亮更重要。
- **金额与时间的表示**：会不会用二进制浮点、元与分之间有没有隐式转换、计息是否依赖浮点秒、clock 能不能注入（测试里显式推进而不是 sleep）。
- **不变量意识**：能不能当场写出总账守恒、余额非负、两腿平衡，并用固定种子的随机操作序列自证，而不是靠手工点检。
- **并发与幂等是机制还是口号**：读-改-写是否原子、跨账户加锁顺序、幂等键落在哪一层、去重表的 TTL 与容量口径（容量满时淘汰未过期键等于放弃幂等）、批量工作是否有界。
- **常见错误答案**：一类是把 `print` 到 stdout 或 `InsufficientFundsError` 之类的异常当成业务拒绝——评测器读的是返回值与最终状态，异常类型不是契约的一部分；另一类是金额用 float 元、时间用 `time.time()` 直接相减——前者让最便宜的相等断言在第 6 次操作就失效（实测），后者在 NTP 回拨时把同一小时计了两次息（实测多补 417 分）。

## 原理与推导
### 1. 四个递进层级与第 1 层要冻结的契约

| 层级 | 需求新增 | 契约里新增什么 | 会打穿前一层的写法 |
| --- | --- | --- | --- |
| L1 账户与余额 | 开户、存款、取款、查余额 | `Result` 四字段 + 错误码表 | 用异常做业务拒绝、用 stdout 汇报 |
| L2 转账与多账户 | 转账、每笔限额、多账户 | `transfer(src, dst, amount)`、两腿同临界区 | 把转账实现成「调用两次单账户接口」 |
| L3 时间、计息与对账 | 时间戳、计息、挂起交易过期、日终切分 | `clock` 参数、`hold / capture / sweep_expired` | 计息写成后台定时器、直接读墙钟 |
| L4 并发、回滚与审计 | 并发安全、幂等、审计、错误隔离 | `idem_key` 参数、审计日志、冲正（void） | 在 L1 的存取函数里散落加锁与去重 |

入口固定成少数几个（`open_account / deposit / withdraw / transfer / balance / statement`，外加运维入口 `sweep_expired`），全部返回 `Result(ok, code, balance, tx_id)`：业务拒绝是 `ok=False` 加一个稳定错误码（`NO_SUCH_ACCOUNT`、`INVALID_AMOUNT`、`INSUFFICIENT_FUNDS`、`LIMIT_EXCEEDED`、`DUPLICATE`），异常只留给实现错误。写路径切成五段：① 解析（类型与形状，在任何副作用之前判定）；② 幂等查表（命中即原样重放，副作用为零）；③ 校验（拒绝只写审计、不动余额）；④ 结算（一腿或两腿，在同一个临界区内完成）；⑤ 存储（余额 + append-only 审计日志 + 幂等表）。第 4 层要加的东西全部落在 ② 与 ⑤，L1–L3 一行都不用改——这就是「四层递进」真正在考的东西。

### 2. 金额：整数最小单位，不是 float

| 口径 | 实测 | 后果 |
| --- | --- | --- |
| float 元累加 | 100 万次 ×0.01 元后余额 10000.000000171856，与精确值差 $1.719 \times 10^{-7}$ 元 | 第 6 次操作起 `余额 == 期望` 就判假，评测器只要用相等断言就随机失败 |
| 元与分的隐式转换 | 0.01–10000.00 元的 100 万个分值金额里，`int(元 × 100)` 丢 1 分的占 65,624 个（6.5624%） | 0.29 元变成 28 分，误差系统性存在、与金额分布相关 |
| Decimal 元 | 20 万次累加：int 分 114.0 ns/次、Decimal 450.3 ns/次（4.0×） | 精确，代价是可测的常数因子；适合做最终舍入策略的参照实现 |

浮点的问题不只在「误差小」上：它是**表示误差**，而账本的第一性要求是「等式必须成立」。用 bf16 存余额这个极端例子最能说明量级：bf16 只有 7 位显式尾数，1 万元（$10^6$ 分）附近的可表示间距是 $2^{19-7} = 4096$ 分 = 40.96 元，10 万元账户是 655.36 元，100 万元账户是 5242.88 元——40.96 元以内的差额在 bf16 里根本不存在。金额追求的不是小数位多，而是**可精确比较**。

### 3. 第 2 层：两腿原子性与加锁顺序
转账的两条腿必须落在同一个临界区，否则会出现可被观测到的「扣了没加」中间态。实测（A 起始 200,000 分、B 为 0，写侧转 20,000 笔 × 7 分，观测方在另一线程固定采样 200,000 次）：

| 写法 | 观测到总账不守恒 | 说明 |
| --- | --- | --- |
| 先 `A.balance -= amt`，让出 GIL，再 `B.balance += amt` | 115,283 / 200,000（57.642%） | 评测器只要并发读一次总账就能抓到 |
| 两腿在锁内完成，读侧走同一把锁的原子快照 | 0 / 200,000 | 写侧一致，读侧也要一致 |
| 两腿在锁内完成，读侧在锁外**分别**读两个账户 | 0–1 / 200,000 | 撕裂读概率低但非零，所以读接口必须给一致快照 |

单账户的「先查余额再扣款」同理是两个步骤：无锁版本在 16 线程 × 20 次取 1 分、余额 100 分的场景下放行 102–109 次、最终余额 −9…−2 分；把读-改-写收进同一临界区后放行恰好 100 次、余额 0、不变量违反 0 次。跨账户要同时拿两把锁时必须按账户 id 排序（实测按参数顺序加锁时，双向并发转账在 5 次尝试中有 1 次 3 s 内未完成，即循环等待；改按 id 排序后 0 次），且锁内只做内存操作、不做 IO。多实例部署时把余额收进单写入者（一个进程或一条原子命令），或用版本号做乐观并发加带幂等键的重试。

### 4. 第 3 层：时间可注入、懒计息与有界批次
时间一旦进入规格，第一件事是把 `clock` 变成构造参数、测试里显式推进，并把边界口径写死在实现旁：`now >= expire_at` 即失效（到期前 1 ms 仍有效）。计息用懒结算，记 `last_accrued_ms`，只在账户被触碰时补算：$\text{whole}, \text{residue} \leftarrow \operatorname{divmod}(\text{balance} \times r_{bp} \times \Delta ms + \text{residue},\ 10\,000 \times 86\,400\,000)$，分母是「1 bp 的日利率 × 一天的毫秒数」，全程整数运算。**余数必须累计**：每次结算都丢零头的话，粒度越细丢得越多——余额 1 万元、日利率 1 bp（年化 3.65%，即 1 元/天）时，每秒结算一次（86,400 次）的丢零头版本拿到 0 分，每小时结算（24 次）拿到 96 分，而余数累计版本在三种粒度下都是 100 分。`elapsed <= 0`（时钟冻结或回拨）时既不补、也不回退 `last_accrued_ms`，这是唯一安全的动作。两个反例都用「余额 1 万元、日利率 100 bp」的放大口径量过：不夹紧直接整除的写法在回拨瞬间计出 −417 分，余额凭空少 4.17 元；clamp 但顺手写 `last = now` 的写法在时钟恢复后对同一小时重复计息，1 小时的真实利息 416 分被记成 833 分（多 417 分）。挂起交易的清扫同理必须**有界 + 有序索引**：20 万笔同时过期时，最小堆索引单次最多清 64 条只要 0.297 ms、一次清完要 487.4 ms；而只限批大小、每次扫全表的写法单次清 64 条要 123.494 ms——**批大小约束不住单次开销**。堆里的死条目（已确认或已作废）靠 `seq` 版本号跳过并当指标暴露：20 万笔挂起、确认 10 万笔后清扫，堆里留有 100,000 条死条目（占堆 33.3%）。

### 5. 第 4 层：幂等、审计与错误隔离
- **幂等键是写接口的一部分**，不是调用方自己加的重试逻辑：调用超时无法判断对方是否已处理完，所以每个写操作都带 `idem_key`，去重表存「键 → 首次结果快照」，命中时原样返回（`code = DUPLICATE`、`tx_id` 与首次一致），副作用恰好一次。实测同一请求重放 2,000 次（16 线程并发）：没有幂等表时 2,000 次全部真扣、余额从 100,000 掉到 86,000（少 140 元）；有幂等表时只扣一次（余额 99,993），码分布为 1 个 OK + 1,999 个 DUPLICATE，且只有一个 `tx_id`。
- **TTL 与容量是两套正交机制**（Redis 把 `volatile-*` 与 `allkeys-*` 做成两套策略也是同一道理）：TTL 决定「多久以后不再需要去重」，容量决定内存上限。容量满时把仍在 TTL 内的键按 LRU 淘汰，等于在高负载下悄悄放弃幂等——实测容量 1,000、TTL 600 s、5,000 个不同键时，LRU 策略的重放造成 5,000 次二次副作用；改成「只清过期、绝不淘汰未过期键」后二次副作用 0 次，代价是 4,000 次新请求被拒（fail-closed，把不确定性挡在门外而不是放进账本）。
- **过期扫描不能挂在写路径上**：每次写入都遍历全表筛过期的写法，2 万次带幂等键的写入要 12,726.5 ms；改成只在容量满时从队头连续弹出（TTL 统一时插入顺序就是过期顺序）只要 108.9 ms，相差 116.9×。容量要按峰值 QPS × TTL 预留：每条去重记录实测 239.1 B（键 37 字符、值含 `tx_id`），10,000 QPS × 600 s = 600 万条 = 1.43 GB——这两个数字必须一起定。
- **审计日志 append-only**：余额变更、拒绝、挂起、回滚、计息各写一条，靠 `ref` 与 `group` 串起一笔业务的两条腿。收益是「冲正」而不是「改历史」：过期挂起用 +amount 的 void 条目回滚，评测器与对账程序都能用同一份日志复算。
- **错误隔离**：一个非法金额不能污染整批（日终、利息入账、过期清扫一起跑的批次），结算必须逐笔进行；不要用 `asyncio.TaskGroup` 这类「一个失败全组取消」的语义承载「每笔独立」（[[coding-08]] 实测 5 个子任务里 1 个失败，另外 4 个被连带取消）。
- **重试只对可重试错误做**，退避用 full jitter：$\text{sleep} = U(0,\ \min(cap,\ base \cdot 2^{n-1}))$。虚拟时间模拟（100 个客户端同时被拒、服务端 5 req/s、桶深 5、$base = 0.5$ s、$cap = 8$ s、200 个种子）实测：无抖动时首轮重试时刻标准差 0.000（95 个客户端在同一瞬间重试）、总尝试 900.0 次、全部完成 63.50 s；换成 full jitter 后标准差 0.143、100 ms 窗口峰值到达从 95.0 降到 34.2、完成时间 22.36 s。0.143 与 $0.5/\sqrt{12} = 0.144$ 吻合，说明采样确实落在 $U(0, 0.5)$ 上。

### 6. 面对黑盒评测器：自证，而不是猜隐藏用例
- **把不变量写成可运行的断言**：`Σ balance == Σ journal delta`、所有余额 $\ge 0$、每笔转账两腿 delta 之和为 0、同一幂等键重放不改变余额与流水条数。四条都能只用公开状态复算，评测器想怎么读都不怕。
- **固定种子的随机回放**：2000 次随机操作（开户、存取、转账、挂起、推进时钟、清扫）每一步都断言四条不变量。实测流水 2,072 条中 `void`（过期回滚）183 条、`reject`（未动余额）71 条，合计 254 条 = 12.3% 的常驻流水是回滚或拒绝记录（前者抵消此前的挂起、后者不动余额）——按常驻条数估计业务量会系统性高估，所以账本口径要按「有效流水」而不是「条数」给。
- **等价变换**：同一操作序列用 4 种随机账户建立顺序（种子 1–4）回放，5 个账户的最终余额与流水合计逐位一致；[[coding-09]] 对同一段流做 12 种固定长度加 2000 次随机切分的手法，在银行版就是「随机操作序列 + 随机金额 + 随机顺序」。
- **把前几层冻成回归门槛**：每加一层都回放前面所有用例。评测器按四段给分，第 4 层把第 1–3 层打回去是最常见的失分方式。

### 7. 玩具实现离真实银行还差在哪
内存里的「原子」只保证单进程：真实系统要 WAL 与持久化、要跨服务事务或补偿（转账只成功一腿必须能回滚，不能把不一致留给调用方）、多币种要有舍入策略与汇率快照；审计要真的 append-only 且能回答「谁在何时改了什么、如何对账与冲正」；限额、风控与人工复核通道要独立于交易路径；可观测性要覆盖每笔操作的 trace、成功率、拒绝率、重试率与 P99。还有一条边界：对账与异常检测可以上模型，但**不能进热路径**。按本仓库统一口径算这笔账——LLaMA-3-70B 每 token 的 KV cache 是 320 KiB（GQA 8 个 KV 头、head_dim 128、80 层、bf16），32 条 8k 上下文就是 $32 \times 8192 \times 320\ \text{KiB} = 80$ GiB，单张 80 GB 卡已经放不下；换成 LLaMA-3-8B（128 KiB/token）是 32 GiB。而 decode 的算术强度约 1 FLOP/byte，远低于 H100 SXM5 的 roofline 拐点 $989/3.35 \approx 295$ FLOPs/byte（bf16 dense 989 TFLOPs、HBM 3.35 TB/s），所以 LLM 侧的复核只能抽样或离线批处理，不能逐笔挂在交易上。

## 数值与代码验证
环境：Python 3.10.12（CPython）、AMD Ryzen 9 8945HX（32 线程）/ Linux x86_64；测量期间机器上还有别的负载（load average 约 20），所以墙钟类数字给 5 次取中位数、并发类数字给 5 次运行的区间、观测类数字给该次运行的值，而逐位可复现的（精度、记账、幂等、边界）数字不受调度影响。脚本：`.work/anthropic/bank.py`（参考实现）、`.work/anthropic/doc_snippet.py`（下面第一段实现补全后的完整可运行版本）、`.work/anthropic/doc_assert.py`（断言片段，从 `doc_snippet` 导入）、`.work/anthropic/doc_verify_from_md.py`（把下面两个代码块原样抽出、补上省略成员后实跑）、`.work/anthropic/verify.py`（全部数字的来源，2,048 条断言，`python3 .work/anthropic/verify.py` 实跑 94.6 s 全部通过）。下面这段实现是 `doc_snippet.py` 的核心节选（省略 `Account` 类、`__init__` 字段声明、`open_account`、`hold` 与 `_tx / _now_ms / _reject / check_invariants` 等内部工具，补齐后即为完整文件）。

```python
class Result(NamedTuple):                # 统一返回：业务拒绝走 ok/code，不抛异常
    ok: bool
    code: str                            # OK / NO_SUCH_ACCOUNT / INVALID_AMOUNT / DUPLICATE ...
    balance: int                         # 单位：分
    tx_id: str                           # 审计与幂等重放的锚点

class Bank:
    DAY_MS = 86_400_000

    def deposit(self, a, amt, idem_key=None):  return self._submit("deposit", a, amt, idem_key)
    def withdraw(self, a, amt, idem_key=None): return self._submit("withdraw", a, amt, idem_key)
    def transfer(self, s, d, amt, idem_key=None): return self._submit("transfer", s, amt, idem_key, d)

    def balance(self, account_id):
        with self._lock:
            acct = self._accounts.get(account_id)
            if acct is None:
                return Result(False, NO_SUCH_ACCOUNT, 0, "")
            self._accrue(acct, self._now_ms())     # 读之前先结算，否则读到旧值
            return Result(True, OK, acct.balance, "")

    def _submit(self, kind, account_id, amount, idem_key, dst=None):
        # ① 解析：形状问题在任何副作用之前判定
        if not isinstance(amount, int) or isinstance(amount, bool):
            return Result(False, INVALID_AMOUNT, 0, "")
        with self._lock:                           # 单写者：一把可重入锁
            src = self._accounts.get(account_id)
            if src is None or (kind == "transfer" and dst not in self._accounts):
                return Result(False, NO_SUCH_ACCOUNT, 0, "")
            now_ms = self._now_ms()
            # ② 幂等查表：命中即原样重放，副作用为零
            cached = self._dedup_get(idem_key, now_ms)
            if cached is not None:
                return Result(False, DUPLICATE, cached.balance, cached.tx_id)
            if idem_key is not None and self._dedup_full(now_ms):
                return Result(False, DEDUP_FULL, src.balance, "")
            # ③ 校验：拒绝只写审计，不动余额
            for acct in [src] + ([self._accounts[dst]] if dst else []):
                self._accrue(acct, now_ms)
            if amount <= 0:
                return self._reject(INVALID_AMOUNT, src, kind)
            if self._limit is not None and amount > self._limit:
                return self._reject(LIMIT_EXCEEDED, src, kind)
            if kind != "deposit" and src.balance < amount:
                return self._reject(INSUFFICIENT_FUNDS, src, kind)
            # ④⑤ 结算 + 存储：两腿在同一临界区内完成，没有「扣了没加」的中间态
            if kind in ("deposit", "withdraw"):        # 单腿：存 / 取只差符号
                sign = 1 if kind == "deposit" else -1
                src.balance += sign * amount
                tx_id = self._tx(kind, account_id, sign * amount)
            else:
                src.balance -= amount
                group = "tr-%d" % (self._seq + 1)
                tx_id = self._tx("transfer", account_id, -amount, group=group)
                self._accounts[dst].balance += amount
                self._tx("transfer", dst, +amount, group=group)
            out = Result(True, OK, src.balance, tx_id)
            self._dedup_put(idem_key, now_ms, out)
            return out

    # 懒计息：整数分 × 整数毫秒 × 余数累计，den = 10000(bp) × 一天的毫秒数
    def _accrue(self, acct, now_ms):
        if acct.last_ms is None:
            acct.last_ms = now_ms
            return 0
        elapsed = now_ms - acct.last_ms
        if elapsed <= 0:
            return 0                                # 时钟冻结或回拨：不补、也不回退 last
        acct.last_ms = now_ms
        whole, acct.residue = divmod(acct.balance * acct.rate_bp * elapsed + acct.residue,
                                     10_000 * self.DAY_MS)
        if whole:
            acct.balance += whole
            self._tx("interest", acct.id, +whole)
        return whole

    def sweep_expired(self, max_remove=None):       # 有界批次 + 有序索引
        limit = self._sweep_batch if max_remove is None else max_remove
        now_ms, removed = self._now_ms(), 0
        with self._lock:
            while self._expire_heap and removed < limit:
                expire_ms, seq, tx_id = self._expire_heap[0]
                if expire_ms > now_ms:
                    break                           # 堆顶未过期 ⇒ 其余都没过期
                heapq.heappop(self._expire_heap)
                rec = self._pending.get(tx_id)
                if rec is None or rec[3] != seq:
                    self.stats["stale_heap"] += 1   # 已确认/已作废的死条目，当指标暴露
                    continue
                del self._pending[tx_id]
                self._accounts[rec[0]].balance += rec[1]
                self._tx("void", rec[0], +rec[1], ref=tx_id)
                removed += 1
        return removed

    def _dedup_get(self, key, now_ms):
        rec = self._dedup.get(key) if key is not None else None
        if rec is None:
            return None
        if now_ms >= rec[0]:                        # 恰好等于 expire_at 即失效
            del self._dedup[key]
            return None
        return rec[1]

    def _dedup_full(self, now_ms):                  # True = 拒绝这次写入
        if len(self._dedup) < self._dedup_capacity:
            return False                            # 未满不清理：过期扫描不进热路径
        while self._dedup:                          # TTL 统一 ⇒ 插入序即过期序
            key = next(iter(self._dedup))
            if self._dedup[key][0] > now_ms:
                break
            del self._dedup[key]
        return len(self._dedup) >= self._dedup_capacity   # 未过期的键绝不淘汰

    def _dedup_put(self, key, now_ms, result):
        if key is None:
            return
        self._dedup[key] = (now_ms + int(self._dedup_ttl * 1000), result)   # 插入序即过期序
```

## 常见追问
- **追问**：为什么不用 Decimal 存金额？
  - 要点：Decimal 精确，代价是可测的常数因子（实测 20 万次累加是 int 的 4.0×），而且它把「保留几位、怎么舍入」变成运行时配置；整数最小单位把精度写进类型，比较、求和、哈希都天然精确。跨币种或按比例计息时，用整数分子加余数累计（本文的计息实现）比 Decimal 更容易复现。
- **追问**：幂等键应该由谁生成、放在哪一层？
  - 要点：由调用方在**第一次尝试之前**生成并跨重试保持不变（客户端 UUID，或服务端在入口按业务字段派生）；去重表放在写路径第二步，覆盖「余额变更 + 审计 + 返回快照」全部副作用。服务端每次重试都重新生成，等于没有幂等。
- **追问**：去重表会不会太大？
  - 要点：容量必须 ≥ 峰值 QPS × TTL；实测每条 239.1 B，10,000 QPS × 600 s 就是 600 万条 = 1.43 GB。要么按这个口径预留内存，要么把去重下沉到持久化存储；容量不足时选 fail-closed（拒绝新请求）而不是淘汰未过期键，因为后者会静默地重复扣款。
- **追问**：并发下怎么保证余额不会被写坏？
  - 要点：单机把读-改-写收进同一临界区（无锁版实测超发 102–109/100）；跨账户按 id 排序加锁避免循环等待（未排序实测 5 次里 1 次死锁）；锁内只做内存操作；多实例时把余额收进单写入者，或用版本号做乐观并发 + 带幂等键的重试。
- **追问**：计息为什么用懒结算而不是定时任务？时钟回拨怎么办？
  - 要点：定时器要后台线程、会 tick 抖动、测试不可控；懒结算按时间差结算，结果只依赖时间差。`elapsed <= 0` 时既不补也不回退时间戳（实测幼稚写法在回拨时要么倒扣 417 分、要么对同一小时重复计息），余数按分子口径累计以免丢零头（实测每秒结算的丢零头版 1 天利息为 0）。
- **追问**：第 3 层的日终批次为什么强调有界？
  - 要点：一次清 20 万条过期挂起要 487.4 ms，是把前两层延迟打穿的量级；切成单次 64 条后是 0.297 ms，但前提是**有序索引**——只限批大小而每次扫全表的写法单次仍要 123.494 ms。批量任务还要逐笔结算、单笔失败不牵连整批。
