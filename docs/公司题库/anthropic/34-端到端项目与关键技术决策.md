## 一句话答案

> 这道题的得分点**不在项目多大，而在决策密度**。面试官想听的是：**你在信息不完整时如何做取舍、依据是什么、事后被证明对不对**。所以答案按「五段式」组织，其中**第三段（决策）要占一半时间**：
> ① **背景与约束**（30 秒）：业务问题、成功指标、以及**真实约束**（人手、时间、成本、合规、遗留系统）；
> ② **我的角色与范围**（15 秒）：我负责哪一段（端到端意味着**从指标定义到上线运维**），团队几人、我做了什么决定；
> ③ **关键决策 2–3 个**（主体）：每个决策讲**四件事**——当时的选项、我选的依据（数据/成本/风险）、放弃的代价、**事后来看对不对**；
> ④ **结果与口径**（30 秒）：可核查的数字 + **它是怎么算的**（基线是什么、样本多大、区间多宽）；
> ⑤ **如果重来**（15 秒）：一处不同的做法 + 为什么（这一问几乎没有候选人主动讲，讲了就是加分项）。
> **决策要挑「有真实分歧」的**：所有人都同意的事不叫决策。好的候选决策长这样：
> - 「先上规则基线还是直接上模型」；
> - 「为延迟砍功能，还是为功能放宽 p99」；
> - 「自建检索还是买现成的」；
> - 「先服务 3 个客户做深，还是铺 30 个客户做宽」。
> 一句话判据：**把「我做了什么」换成「我在什么信息下、放弃了什么、选了什么、后来被证明如何」**。

## 面试官在考什么

- **决策密度 vs 工作量罗列**：说「我搭了 12 个服务」不如说「我砍掉了 3 个服务，因为它们让上线时间翻倍而收益不确定」。
- **依据是否可追溯**：是拍脑袋、跟风、还是基于测量与估算（成本模型、试点数据、用户访谈）？**能说出「当时的数字」最有力**。
- **是否承认取舍的代价**：只讲收益的决策叙述听起来像宣传；能说出「这个选择让我们失去了 X」才可信。
- **事后复盘的能力**：能否指出哪一步判断错了、什么时候发现的、以及如果重来会怎么做。
- **口径意识**：结果数字必须带口径（基线、样本、区间）——这与 [[anthropic-27]] 的统计纪律同源；含糊的「提升了 30%」会被追问穿。
- **与岗位的相关性**：Anthropic 关心的是「在不确定性下做负责任取舍」的能力，所以**涉及安全/滥用/权限的决策**（如果项目里有）应当被突出。
- **叙事控制**：能否在 3–5 分钟内讲完并留出追问空间，而不是把所有细节一次倒出。

**常见错误答案**

- 按时间线流水账（「先是……然后……再然后……」），没有决策。
- 只讲技术亮点（用了什么框架、什么模型），不讲取舍。
- 数字没有口径（「性能提升了几倍」——相对什么？）
- 把团队成果说成个人成果，或反之（面试官会追问边界）。
- 讲到失败时归因于外部（「需求老变」），不反思自己的判断。
- 没有「如果重来」，显得没有复盘习惯。

## 原理与推导

### 1. 五段式时间分配（5 分钟版本）

| 段 | 时长 | 内容要点 | 常见失误 |
| --- | --- | --- | --- |
| ① 背景与约束 | 30 s | 业务问题 + 指标 + 约束 | 讲太多业务背景 |
| ② 角色与范围 | 15 s | 我负责什么、团队多大 | 模糊化个人贡献 |
| ③ 关键决策 | **2.5–3 min** | 2–3 个有分歧的决策 | 这里讲太少 |
| ④ 结果与口径 | 30 s | 数字 + 口径 | 无口径 |
| ⑤ 如果重来 | 15 s | 一处不同 + 原因 | 省略 |

**判据**：如果面试官在你讲完后只问「结果数字怎么来的」，说明③讲够了、④需要补；如果一直追问「那你当时为什么这么选」，说明③缺依据。

### 2. 单个决策的四要素模板

1. **选项**：当时至少两个可行方案（只有一个方案的「决策」其实是执行）；
2. **依据**：数据、成本模型、风险、或者时间约束——**要能说出具体数字或来源**；
3. **代价**：选它意味着放弃什么（延迟、钱、可扩展性、团队精力）；
4. **验证**：事后用什么证据判断它对不对（指标、事故、用户行为），以及**如果错了是怎么发现的**。

### 3. 决策的量化：把「我觉得」变成「算过」

常见的三类可算决策：

| 决策类型 | 算式 | 例子 |
| --- | --- | --- |
| 成本/收益 | $\text{收益}-\text{成本}$，含机会成本 | 自建检索 vs 采购：自建省 3 万美元/年但多花 2 人月 |
| 期望值与不确定性 | $EV=\sum p_i v_i$ | 「先做深 3 个客户」：$0.6\times$大单 $+0.4\times$小单 |
| 延迟成本 | $\text{CoD}=\text{每日损失}\times\text{延期天数}$ | 上线晚 2 周 = 少 14 天收入 × 转化率 |

**注意**：面试里**不需要精确**，但需要**显示出你算过**（「我当时估的是 2 人月对 3 万美元一年，所以两年回本」）。这就是「工程判断」的证据。

### 4. 结果口径的三件套

报任何改善都必须带：**基线**（改之前是多少）、**样本**（测了多少、覆盖什么）、**区间**（不确定性）。示例表述：

> "上线后 6 周，在我们埋点的 1,200 个会话上，'需要人工改写'的比例从 34% 降到 19%；置信区间约 ±3 个百分点。注意这批用户比全量更活跃，所以对全量外推要打折。"

**这种表述的可信度远高于「效果提升了 44%」**。

### 5. 敏感话题的处理（对应 Anthropic 的关注点）

如果项目涉及安全/权限/滥用/隐私：
- **不要淡化**：把它作为决策讲，说明你如何权衡「能力开放 vs 风险」；
- **给出机制而非态度**：例如「默认只读 + 写操作需审批 + 全量审计」，而不是「我很重视安全」（串 [[anthropic-28]]）；
- **承认残余风险**：你无法消除的部分是什么、怎么监控与处置（串 [[anthropic-31]]）。

### 表 1：决策记录模板（示例）

| 决策 | 选项 | 依据 | 代价 | 事后验证 |

### 可运行代码

```python
# 把项目里的关键决策算给面试官看：期望值、延迟成本、回本周期、结果口径
from dataclasses import dataclass
from typing import Dict, List, Tuple
import math

# ---------- 1) 期望值：先做深 3 个客户 vs 铺开 30 个 ----------
def expected_value(outcomes: List[Tuple[float, float]]) -> float:
    """outcomes: [(概率, 收益)，...]"""
    return sum(p * v for p, v in outcomes)

deep = expected_value([(0.6, 400_000), (0.4, 100_000)])         # 深：单客户大单概率高
wide = expected_value([(0.30, 15_000)] * 3) * 10                 # 宽：30 客户 × 30% 转化
print("① 期望值决策（单位：美元）")
print(f"  做深 3 个客户：EV = 0.6×400k + 0.4×100k = {deep:,.0f}")
print(f"  铺开 30 个客户：EV = 30×0.3×15k = {wide:,.0f}")
print(f"  结论：{'做深' if deep > wide else '铺开'}（差额 {abs(deep-wide):,.0f}）")
print("  读法：面试里不用精确，但要能说出「我当时估的是这个量级」")

# ---------- 2) 自建 vs 采购：两年回本测算 ----------
@dataclass
class BuildVsBuy:
    saas_usd_per_year: float
    build_person_months: float
    loaded_cost_per_month: float
    maintenance_pct: float = 0.2
    def build_cost_year1(self) -> float:
        return self.build_person_months * self.loaded_cost_per_month
    def cumulative(self, years: int) -> Tuple[float, float]:
        build = self.build_cost_year1()
        saas = 0.0
        for y in range(years):
            build += self.build_cost_year1() * self.maintenance_pct if y else 0
            saas += self.saas_usd_per_year
        return build, saas
    def payback_years(self) -> float:
        for i in range(1, 121):
            years = i / 12
            b, s = self.cumulative_frac(years)
            if b <= s:
                return years
        return float("inf")
    def cumulative_frac(self, years: float) -> Tuple[float, float]:
        build = self.build_cost_year1() + self.build_cost_year1() * self.maintenance_pct * max(0.0, years - 1)
        saas = self.saas_usd_per_year * years
        return build, saas

case = BuildVsBuy(saas_usd_per_year=30_000, build_person_months=2, loaded_cost_per_month=12_000)
print("\n② 自建 vs 采购（示例：年费 3 万美元 vs 2 人月 + 20% 年维护）")
print(f"  第一年自建成本 = 2 人月 × $12k = ${case.build_cost_year1():,.0f}")
for years in (1, 2, 3):
    b, s = case.cumulative(years)
    print(f"  {years} 年累计：自建 ${b:,.0f}  采购 ${s:,.0f}  "
          f"差价 ${s-b:+,.0f}")
print(f"  回本时间 ≈ {case.payback_years():.1f} 年")
print("  读法：这类算式让「我觉得自建更划算」变成可检验的判断；")
print("        同时要说清代价——放弃供应商的持续迭代（案例里两年后功能落后约半年）")

# ---------- 3) 延迟成本：为延迟砍功能是否值得 ----------
def cost_of_delay(daily_revenue: float, conv_loss_per_100ms: float,
                  delay_ms: int, days: int) -> Dict[str, float]:
    loss_pct = conv_loss_per_100ms * (delay_ms / 100)
    return {"转化损失": loss_pct, "每日损失": daily_revenue * loss_pct,
            "总损失": daily_revenue * loss_pct * days}
print("\n③ 延迟成本（日为单位的收入 5 万美元、每 100 ms 转化损失 1%）")
for ms, days in ((100, 30), (300, 30), (300, 90)):
    r = cost_of_delay(50_000, 0.01, ms, days)
    print(f"  延迟 +{ms} ms 持续 {days} 天：转化 -{r['转化损失']:.1%}，"
          f"累计损失 ≈ ${r['总损失']:,.0f}")
print("  读法：把「性能 vs 功能」的争论换算成钱，决策依据就从口味变成算术（串 [[anthropic-15]]、[[anthropic-17]]）")

# ---------- 4) 结果口径：点估计 + 区间 ----------
def wilson_ci(successes: int, n: int, z: float = 1.96) -> Tuple[float, float]:
    """Wilson 区间（比 Wald 在小样本与极端比例下更稳）"""
    if n == 0:
        return (0.0, 1.0)
    p = successes / n
    denom = 1 + z * z / n
    center = (p + z * z / (2 * n)) / denom
    half = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / denom
    return (max(0.0, center - half), min(1.0, center + half))
print("\n④ 结果口径（报告必须带的三件套：基线、样本、区间）")
for before, after, n in ((408, 228, 1200), (68, 38, 200)):   # 34% 与 19% 对应的计数
    lo_b, hi_b = wilson_ci(before, n)
    lo_a, hi_a = wilson_ci(after, n)
    print(f"  n={n}: {before/n:.1%} [{lo_b:.1%}, {hi_b:.1%}] -> "
          f"{after/n:.1%} [{lo_a:.1%}, {hi_a:.1%}]")
print("  读法：同一套口径能让「34% → 19%」这种说法站得住；")
print("        而「提升 44%」因为没基线、没区间，面试官只能当作形容词")

# ---------- 5) 决策密度自检：你的叙述里有几个真决策？ ----------
@dataclass
class Decision:
    name: str
    had_alternatives: bool
    had_evidence: bool
    had_cost: bool
    verified_later: bool
    def score(self) -> int:
        return sum([self.had_alternatives, self.had_evidence, self.had_cost, self.verified_later])
D: List[Decision] = [
    Decision("检索自建 vs 采购", True, True, True, True),
    Decision("先深后宽", True, True, True, True),
    Decision("为延迟砍功能", True, True, True, False),
    Decision("用了某个流行框架", False, False, False, False),
]
print("\n⑤ 叙述自检：每个「决策」是否具备四要素（选项/依据/代价/事后验证）")
for d in D:
    print(f"  {d.score()}/4  {d.name}"
          + ("   <- 这不是决策，是执行" if d.score() == 0 else ""))
print("  读法：把不满足四要素的条目从「决策」里删掉，或者补齐它的依据与代价 ——")
print("        这一步能让你的项目叙述从「我做了什么」变成「我怎么判断的」")
```

预期输出要点（实跑）：① 期望值决策把「先深还是先宽」从直觉变成数字（做深 \$28 万 vs 铺开 \$13.5 万）；② 自建 vs 采购给出**回本时间**（示例约 **0.8 年**：第一年自建 \$2.4 万 vs 采购 \$3 万）与逐年差价，同时提醒必须说清放弃的代价；③ 延迟成本把「性能 vs 功能」的争论换算成钱（+300 ms 持续 30 天累计损失约 \$4.5 万），让取舍可讨论；④ **结果口径**用 Wilson 区间给出「34% → 19%」的置信范围（同一套口径在 $n=200$ 时区间明显更宽——提醒小样本不能过度宣称）；⑤ 决策密度自检把「用了某个流行框架」这类条目打成 0/4 并标记为「这是执行，不是决策」——**这一条最能立刻提升你的叙述质量**。

## 常见追问

- **追问**：如果项目失败了呢？
  - 要点：照同样的五段式讲，把「关键决策」换成「关键误判」，**重点放在检测时间与止损动作**（什么时候发现、多久决策、损失多少）；失败故事比成功故事更能展示复盘能力（串 [[anthropic-36]]）。
- **追问**：你个人具体做了什么（团队成果如何切分）？
  - 要点：明确边界——"我负责指标定义与检索链路，模型侧由同事负责；那个决策是我提的，但落地是两人一起做的"。**主动切分比含糊其辞可信**。
- **追问**：这个数字怎么算的？
  - 要点：给基线、样本量、区间与偏差提示（如「该群体偏活跃」）；如果记不清，**说清口径与量级**比编造精确数字好。
- **追问**：有没有你坚持但后来被证明错了的决定？
  - 要点：这是高价值追问——给出一个具体判断、当时的依据、以及**是什么证据让你改变**；不要选「无关痛痒」的小错（显得回避），也不要选灾难级错误（显得不可靠）。
- **追问**：你怎么知道这个功能上线是「成功」的？
  - 要点：讲**上线后验证设计**：对照组、观测窗口、主要指标与护栏指标（例如「主指标提升但错误率不能上升」）；没有验证设计的「成功」只是感觉。
- **追问**：如果预算砍一半，你会砍什么？
  - 要点：现场做一次取舍演练——保住**最关键的用户路径 + 可验证的最小范围**，把可延迟的部分明确写出来；这一问考的就是「决策密度」是否真实。
