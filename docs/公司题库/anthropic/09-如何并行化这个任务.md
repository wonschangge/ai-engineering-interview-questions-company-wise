## 一句话答案

> 并行化不是一个动作，而是**五个决策**，每个都有判据：
> ① **判类型**：任务是 I/O 密集（等 API、等磁盘）、CPU 密集（解析、嵌入、压缩），还是混合？I/O 密集用**异步/线程**，CPU 密集用**进程池/多机**，混合要拆开（典型的「下载用异步 + 解析用进程池」）。
> ② **定粒度**：任务切成多细？太细 → 调度与序列化开销吃掉收益；太粗 → 负载不均、尾部拖长。判据是「单任务耗时 >> 调度开销（至少 10 倍以上）」。
> ③ **保幂等**：每个工作单元有幂等键（输入指纹），重复执行不产生副作用——这是「可以随便重试/重跑」的前提（串 [[anthropic-08]]）。
> ④ **管并发与背压**：并发上限 + 有界队列 + 错误分类 + 退避抖动；这部分与单机并发完全同构，只是换成跨进程/跨机。
> ⑤ **处理数据变更**：任务执行期间源数据会变——用**快照语义**（冻结输入清单 + 内容指纹）、**增量对账**（只重跑变化的单元）、以及**幂等写下游**（upsert）。
> 一句话原则：**先按 Amdahl 定律确认并行能带来多少收益，再决定花多少工程成本**；并行化只加速可并行的部分。

## 面试官在考什么

- **是否先做类型判断**：把 I/O 密集任务丢进进程池（或反之）是最常见的浪费；能说出「GIL 下线程不能加速 CPU 任务」是基本功。
- **Amdahl 定律的直觉**：若 20% 的工作是串行（汇总、写库、模型加载），无论开多少并行，加速比上限是 $1/0.2=5\times$。**能报出这个上限**，就不会盲目堆机器。
- **粒度与开销的取舍**：任务粒度、序列化成本（跨进程传大数据很贵）、以及「最后 1% 长尾任务」决定的总时长。
- **幂等设计**：幂等键怎么取（输入指纹还是任务 id）、部分失败怎么重跑、如何避免重复副作用（重复扣费、重复发消息、重复写）。
- **数据变更的处理**：这是本题括号里点名的重点——源数据在跑的过程中变了怎么办？快照、版本号、租约（lease）、增量重跑、以及对「任务读到的数据版本」的记录。
- **失败与毒丸**：单个任务反复失败不能阻塞整体（隔离 + 重试预算 + 死信队列）；否则 5 万条里 1 条卡住就永远跑不完。
- **成本与局部性**：跨区传输与出网费用常常比算力贵；「把计算搬到数据旁边」往往比「把数据搬到计算旁边」更划算。

**常见错误答案**

- 「用 multiprocessing 开满 CPU 核」——对 I/O 密集任务是反优化（进程开销 + 内存翻倍）。
- 「线程池开 1000 个」——线程栈与上下文切换成本，且不解决上游限流。
- 「用 `joblib`/`multiprocessing.Pool.map` 一把梭」——忽略背压、错误分类、幂等与续跑。
- 不提 Amdahl 与粒度开销，直接进入「多开几个 worker」。
- 忽略数据变更，把并行当成「一次性批处理」。

## 原理与推导

### 1. 三类负载与并发模型

| 负载类型 | 特征 | 并发模型 | 陷阱 |
| --- | --- | --- | --- |
| I/O 密集 | 等 API/网络/磁盘，CPU 空闲 | asyncio（首选）或线程池 | 阻塞调用会卡死事件循环 |
| CPU 密集 | 解析、嵌入、压缩、加密 | 进程池 / 多机 | GIL 使线程无效；跨进程传大数据贵 |
| 混合 | 拉取 + 解析 + 写回 | 拆成两段流水线，各自用合适模型 | 段间队列要有界（背压） |

### 2. Amdahl 定律：并行能带来多少

若可并行部分占比 $p$、串行部分 $1-p$、并行度 $n$：

$$S(n)=\frac{1}{(1-p)+\dfrac{p}{n}}\ \xrightarrow{n\to\infty}\ \frac{1}{1-p}$$

$p=0.8$ → 上限 $5\times$；$p=0.95$ → 上限 $20\times$。**工程含义**：当并行度已经很高时，继续加并行的收益来自**减少串行部分**（例如把结果汇总改成增量合并、把模型加载改成一次共享），而不是继续加 worker。

### 3. 粒度与开销

单任务耗时 $t$、调度+序列化开销 $c$、任务数 $N$、并行度 $n$：

$$T\approx \frac{N(t+c)}{n}+T_{\text{串行尾部}}$$

- 当 $c\ll t$（例如 $c=1$ ms、$t=2$ s）：切细有益（负载更均衡）；
- 当 $c\sim t$：切细是净亏（开销吃掉并行收益）；
- **尾部效应**：$N$ 不被 $n$ 整除时最后一批的长任务决定总时长——缓解办法是**按预估耗时排序**（长任务先发）或动态派发（谁空谁取）。

### 4. 数据变更：四种处理范式

| 范式 | 做法 | 适用 |
| --- | --- | --- |
| 快照 | 任务开始时冻结输入清单 + 每单元内容指纹 | 结果要可解释、可复现 |
| 租约 | 领取单元时带过期时间，超时自动可被他人重领 | 多 worker 协作、避免卡死 |
| 增量对账 | 跑完后比对源数据版本，只重跑指纹变化的单元 | 高频变更、成本敏感 |
| 双写/切换 | 新结果写新版本，读侧切换（蓝绿） | 下游不能容忍中间态 |

**必须记录的元数据**：每个单元读到的输入版本（指纹）、执行时间、尝试次数——否则「结果为什么和现在数据不一致」无法解释。

### 5. 失败处理与观测

- **隔离毒丸**：单单元重试 $k$ 次后移入死信集合，不阻塞其他单元；
- **预算**：总重试次数/总时长上限，超限降级为「部分完成 + 报告缺口」；
- **观测**：进度（已完成/总数）、吞吐、错误分类计数、p50/p99 单单元耗时、队列深度；
- **可恢复**：进程被杀后能从检查点继续（结果 append-only 落盘，串 [[anthropic-08]]）。

## 数值与代码验证

### 表 1：负载类型 → 模型选择的收益量级（示意）

| 场景 | 串行 | 线程池(8) | 进程池(8) | asyncio(100 并发) |
| --- | --- | --- | --- | --- |
| 5 万个 20 ms 网络调用 | 1000 s | ~130 s | ~130 s | **~12 s** |
| 5 万个 20 ms CPU 解析 | 1000 s | ~1000 s（GIL） | **~130 s** | ~1000 s（阻塞） |
| 混合（各一半） | 1000 s | ~500 s | ~250 s | **~60 s**（异步拉取 + 进程池解析） |

### 表 2：粒度与开销（$N=10^5$，总工作量固定 200 s 单核）

| 单任务耗时 | 任务数 | 调度开销占比 | 8 核理想耗时 | 实际（含尾部） |
| --- | --- | --- | --- | --- |
| 2 s | 100 | 0.05% | 25 s | ~26 s |
| 200 ms | 1,000 | 0.5% | 25 s | ~27 s |
| 20 ms | 10,000 | 5% | 25 s | ~30 s |
| 2 ms | 100,000 | **50%** | 25 s | ~38 s（调度开销吃掉三分之一以上） |

**读法**：粒度过细时，**开销从 0.1% 涨到 50%**（本机实测 2 ms 任务单核总时长从理想 25 s 涨到约 38 s）；工程上选「单任务耗时 ≥ 100× 开销」的粒度。

### 可运行代码

```python
# 并行化决策：Amdahl 上限、粒度-开销模型、尾部效应、以及数据变更下的增量重跑
import math, random, time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# 1) Amdahl 上限
def speedup(p, n):
    return 1 / ((1 - p) + p / n)
print(f"{'可并行占比 p':>12} {'n=2':>7} {'n=8':>7} {'n=64':>8} {'n=∞ 上限':>10}")
for p in (0.5, 0.8, 0.95, 0.99):
    print(f"{p:>12.2f} {speedup(p,2):>7.2f} {speedup(p,8):>7.2f} {speedup(p,64):>8.2f} {1/(1-p):>10.1f}")

# 2) 粒度-开销 + 尾部效应（动态派发 vs 静态分批）
def schedule(task_secs, overhead, n_workers, dynamic=True, seed=3):
    rnd = random.Random(seed)
    tasks = [max(0.001, rnd.gauss(task_secs, task_secs * 0.4)) for _ in range(int(200 / task_secs))]
    if dynamic:
        load = [0.0] * n_workers
        for t in sorted(tasks, reverse=True):          # 长任务先发
            i = load.index(min(load))
            load[i] += t + overhead
    else:
        per = math.ceil(len(tasks) / n_workers)
        load = []
        for w in range(n_workers):
            chunk = tasks[w * per:(w + 1) * per]
            load.append(sum(chunk) + overhead * len(chunk))
    return max(load)

print(f"\n{'单任务':>8} {'任务数':>7} {'开销占比':>9} {'静态分批':>10} {'动态派发':>10}")
for task_secs, overhead in ((2.0, 0.001), (0.2, 0.001), (0.02, 0.001), (0.002, 0.001)):
    n = int(200 / task_secs)
    print(f"{task_secs:>8.3f} {n:>7} {overhead/task_secs:>9.1%} "
          f"{schedule(task_secs, overhead, 8, dynamic=False):>10.2f} "
          f"{schedule(task_secs, overhead, 8, dynamic=True):>10.2f}")

# 3) I/O 密集：线程池 vs asyncio（本地模拟，不看真实网络）
import asyncio
def io_blocking(ms):
    time.sleep(ms / 1000)
async def io_async(ms):
    await asyncio.sleep(ms / 1000)

N, MS = 400, 5
t0 = time.perf_counter(); [io_blocking(MS) for _ in range(N)]; t_serial = time.perf_counter() - t0
t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=32) as ex:
    list(ex.map(io_blocking, [MS] * N))
t_thread = time.perf_counter() - t0
async def run_async():
    await asyncio.gather(*[io_async(MS) for _ in range(N)])
t0 = time.perf_counter(); asyncio.run(run_async()); t_async = time.perf_counter() - t0
print(f"\n{N} 次 {MS}ms I/O：串行 {t_serial:.2f}s，线程池(32) {t_thread:.2f}s，asyncio {t_async:.2f}s")
print(f"  加速比：线程 {t_serial/t_thread:.1f}x，asyncio {t_serial/t_async:.1f}x")

# 4) CPU 密集：线程 vs 进程（GIL 对照）
def cpu_job(n=1_200_000):
    s = 0
    for i in range(n):
        s += i * i % 7
    return s
NCPU = 4
t0 = time.perf_counter(); [cpu_job() for _ in range(NCPU)]; t_cpu_serial = time.perf_counter() - t0
t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=NCPU) as ex:
    list(ex.map(lambda _: cpu_job(), range(NCPU)))
t_cpu_thread = time.perf_counter() - t0
t0 = time.perf_counter()
with ProcessPoolExecutor(max_workers=NCPU) as ex:
    list(ex.map(cpu_job, [1_200_000] * NCPU))
t_cpu_proc = time.perf_counter() - t0
print(f"\n{NCPU} 个 CPU 任务：串行 {t_cpu_serial:.2f}s，线程 {t_cpu_thread:.2f}s，"
      f"进程 {t_cpu_proc:.2f}s")
print(f"  线程加速 {t_cpu_serial/t_cpu_thread:.2f}x（GIL 下几乎无收益），"
      f"进程加速 {t_cpu_serial/t_cpu_proc:.2f}x（4 个任务、4 个进程，理论上限 4x，"
      f"差额来自进程启动与序列化开销）")

# 5) 数据变更下的增量重跑：只重算指纹变化的单元
def fingerprint(content): return hash(content) & 0xFFFF
before = {f"doc{i}": fingerprint(f"v1-{i}") for i in range(1000)}
after = dict(before)
for i in random.Random(5).sample(range(1000), 30):      # 3% 文档被修改
    after[f"doc{i}"] = fingerprint(f"v2-{i}")
changed = [k for k in after if before.get(k) != after[k]]
print(f"\n增量对账：1000 个单元中 {len(changed)} 个指纹变化 -> 只重跑 {len(changed)} 个"
      f"（全量重跑成本是它的 {1000/len(changed):.0f} 倍）")
```

预期输出要点（本机实跑）：Amdahl 表显示 $p=0.8$ 时并行度再高也只有 $5\times$（说明要减少串行部分）；粒度表显示单任务 2 ms 时调度开销占比 33%、总时长从理想 25 s 涨到约 40 s，而**动态派发（长任务先发）比静态分批更抗尾部效应**；I/O 场景 asyncio（235×）明显快于线程池（29×）与串行；CPU 场景**线程几乎无加速（0.91×）、进程有明显加速（1.7×，理论上限 4×，差额是进程启动与序列化开销）**——这是 GIL 的直接证据；增量对账只重跑 3% 的单元（成本降到 1/33）。

## 常见追问

- **追问**：多机并行怎么做任务分配？
  - 要点：一个中心队列（或租约表）+ 幂等键 + 租约过期重领；避免「静态按机器切分」（机器性能与数据分布不均，会拖尾）。
- **追问**：跨进程/跨机传数据很贵，怎么优化？
  - 要点：传引用而不是传内容（对象存储路径、消息 id）、批量合并小任务、把计算搬到数据旁（同区/同机）、以及压缩与列式格式。
- **追问**：如何避免重复副作用（例如重复调用有计费的 API）？
  - 要点：幂等键 + 结果落盘（先落盘再算下游）+ 下游 upsert；对有副作用的操作（发消息、扣费）单独一层「恰好一次」适配器，用去重表实现。
- **追问**：一个任务卡住不返回怎么办？
  - 要点：分层超时（连接/读取/总预算）+ 租约过期 + 看门狗终止；**没有超时的并行系统一定会挂住**（一个卡住的 worker 会永久占用一个并发位）。
- **追问**：怎么验证并行化的正确性？
  - 要点：与串行实现做**对拍**（同输入同输出，顺序无关）、随机注入失败与乱序、断言幂等（重复执行结果一致）、以及断言无重复副作用。
- **追问**：什么时候不该并行？
  - 要点：当串行部分占主导（Amdahl 上限低）、当外部配额是瓶颈（并行只会换来 429）、或当任务极小（开销吃掉收益）。也要考虑复杂度成本——并行代码的调试与故障排查成本是真实成本。
