## 一句话答案

> 这个需求的核心是**把「会话」从「一条消息」升级为一个有序的任务队列**，并在四个冲突目标间取平衡：**顺序性**（问题 2 可能引用答案 1）、**并行性**（互不依赖的问题应当能同时跑）、**上下文共享**（同一会话的公共前缀应当只算一次）、**可取消/可编辑**（用户会在生成中途插话或改主意）。
> 设计要点：
> ① **会话 = 队列 + 依赖图**：每个问题是一个任务，带 `depends_on`（是否引用前面的回答）；无依赖的任务可并行；
> ② **上下文分层**：稳定前缀（系统提示 + 长期记忆）→ 会话已确认历史 → 本轮问题。**只有稳定前缀能长期命中缓存**；并行分支会**共享前缀**（用 KV 复用/基数树式共享，串 [[inference-serving-05]]）；
> ③ **调度**：会话内串行（保证顺序语义）vs 会话间并行（吃满 GPU）；对无依赖问题做**受控并行**（上限 2–4，避免用户看到「答案乱序」）；
> ④ **流式多路复用**：一条连接里多路流要能区分（`question_id` 标注每个 chunk）、有明确的结束事件、支持中断（用户插话 = 取消或缩窗）；
> ⑤ **一致性语义**：用户插话时，正在生成的问题有**三种处理**（跑完再处理新的 / 立即取消 / 缩到最近句号再停）——必须选一个并写进产品语义；
> ⑥ **计量**：按问题分别记账（token 归因），因为「一个会话」不等于「一次计费」。
> 一句话判据：**顺序语义决定「能不能并行」，缓存结构决定「并行划不划算」**。

## 面试官在考什么

- **是否识别出真实冲突**：顺序性 vs 并行性、缓存共享 vs 分支独立、流式体验 vs 取消语义。只说「起个队列」是不够的。
- **依赖建模**：哪些问题真的依赖前面的回答（「那它的复杂度呢？」依赖前文），哪些是独立的（「顺便帮我算一下 3 的平方」）。**依赖判定本身可以用一个小模型/规则做**（低成本分类）。
- **缓存与 KV 共享的具体机制**：共享前缀如何复用 KV（同一前缀的块引用计数）、并行分支如何「分叉」而不重复 prefill、以及**缓存命中率对成本的影响**。
- **取消与插话的语义**：这是产品级难点——用户插话时是「抢占」还是「排队」？抢占会让当前答案半途而废（浪费 token），排队会显得迟钝。能否给出可配置策略与默认值。
- **多路流的工程细节**：单连接多流的分帧、顺序保证、错误隔离（一个问题的失败不能污染整条连接）、以及重连后的续传（从哪个问题、哪个 token 继续）。
- **可观测与计量**：每个问题的 TTFT/TPOT、排队时长、token 归因、以及「会话总成本」。
- **边界情况**：同一问题被重复提交（幂等）、会话过长（压缩/分叉）、跨设备同时提问（冲突解决）。

**常见错误答案**

- 「把它们拼成一个 prompt 一起问」——答案边界模糊、无法单独取消、计费无法归因。
- 全部串行——浪费并发，用户等得久（每个问题都要重新 prefill 长历史）。
- 全部并行——破坏顺序语义（「那第二点呢？」在上下文里还没有第一点）。
- 忽略取消：用户插话后旧答案继续生成并计费。
- 忽略缓存导致每个并行分支都从头 prefill 同一段历史（成本翻倍）。

## 原理与推导

### 1. 会话任务模型

```
Conversation
 ├─ 稳定前缀：system_prompt + tools + long_term_memory      ← 长期缓存
 ├─ 已确认历史：Q1/A1, Q2/A2, ...                            ← 只读、可缓存
 └─ 待处理队列
     ├─ Q3（depends_on: A1）      → 需 A1 就绪后执行
     ├─ Q4（depends_on: A3）      → 链式
     └─ Q5（独立，无依赖）        → 可立即并行
```

**状态机**（每个问题）：`queued → waiting_deps → prefilling → decoding → done | cancelled | failed`。

### 2. 顺序性 vs 并行性：三种执行模式

| 模式 | 规则 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 严格串行 | 一次只跑一个，按提交顺序 | 语义最简单、答案顺序自然 | 慢（用户在等） |
| 受控并行 | 无依赖的可并行（上限 $P$） | 吞吐高、感知快 | 答案可能乱序呈现（需要 UI 处理） |
| 全并行 | 全部同时跑 | 最快 | 破坏「引用前文」的语义，缓存共享复杂 |

**工程默认**：**受控并行 + 依赖判定**——用一个轻量分类器（规则 + 小模型）判断「这个问题是否引用了前面的回答」，引用了就排队，没引用就并行。$P$ 建议 2–4（再多会让用户看到乱序，也会挤占其他会话的容量）。

### 3. 上下文共享：前缀缓存与 KV 分叉

设稳定前缀 $S$（2,000 token）、每轮问答 $u$（400 token）：

- **串行**第 $n$ 问的输入：$S+(n-1)u+u_{\text{new}}$ → 未命中部分只有 $u_{\text{new}}$（前缀全命中）；
- **并行**：$k$ 个分支共享 $S+(n-1)u$ 这段前缀 → 只需 **1 次 prefill**，随后各自 decode（KV 块引用计数 + 写时复制）；
- **若不共享**：$k$ 个分支各做一次 $S+(n-1)u$ 的 prefill → 算力浪费 $k$ 倍于前缀的部分。

$$\text{节省}=\frac{(k-1)\big(S+(n-1)u\big)}{k\big(S+(n-1)u\big)+k\,u_{\text{new}}}\approx\frac{k-1}{k}$$

**结论**：并行分支越多，不做 KV 共享的浪费越大（$k=4$ 时浪费约 75% 的前缀 prefill 算力）。

### 4. 插话（interrupt）的三种语义

| 策略 | 行为 | 用户体验 | 成本 |
| --- | --- | --- | --- |
| 跑完再说 | 当前答案跑完，再处理新问题 | 顺序清晰但迟钝 | 无浪费 |
| 立即抢占 | 取消当前生成，转去处理新问题 | 响应快 | 已生成 token 全部浪费，且答案不完整 |
| 软抢占 | 生成到最近句末/段末再停，保留部分结果 | 折中（推荐默认） | 少量浪费 |

**关键**：无论选哪种，都要**显式告知**（「已停止生成，回答可能不完整」），并把已生成的部分作为可用的部分结果保留（不要丢弃——用户可能只需要前半段）。

### 5. 流式多路复用

单连接（SSE/WebSocket）承载多路流时必须定义帧格式：

```
event: delta
data: {"question_id": "q5", "seq": 12, "text": "..."}

event: done
data: {"question_id": "q5", "finish_reason": "stop", "tokens": 312}

event: error
data: {"question_id": "q3", "code": "rate_limited", "retry_after_ms": 800}
```

**要求**：① 每个 chunk 带 `question_id`（前端按问题分桶渲染）；② `seq` 单调（重连后据此续传）；③ `done` 必须显式（否则前端无法区分「暂停」与「结束」）；④ 单路错误不能关闭整条连接（错误隔离）。

### 6. 计量与归因

- **按问题记账**：$\text{cost}(q)=(\text{in}_q^{\text{miss}}\cdot p_{\text{in}}+\text{in}_q^{\text{cache}}\cdot p_{\text{cache}}+\text{out}_q\cdot p_{\text{out}})$；
- **共享前缀的成本归属**：两种做法——① 记在「第一个触发它的分支」（简单但可争议）；② **按分支摊分**（更公平，推荐用于团队/API 计费）；
- **缓存节省也要可见**（「本次因缓存节省 X token」），否则用户会误判成本来源。

## 数值与代码验证

### 表 1：三种执行模式的端到端时间（4 个问题、每问 300 输出 token、TPOT 25 ms）

| 模式 | 总时间（估算） | 用户感知 | 顺序语义 |
| --- | --- | --- | --- |
| 严格串行 | $4\times(0.4\text{s prefill}+7.5\text{s decode})\approx31.6$ s | 慢 | 正确 |
| 受控并行（P=4，共享前缀） | $\approx0.4+7.5=7.9$ s + 少量调度 | 快 | 需 UI 标注顺序 |
| 全并行不共享前缀 | 8.1 s 但算力浪费约 75% 前缀 prefill | 快 | 可能被破坏 |

### 表 2：插话策略的取舍（已生成 200/500 token 时插话）

| 策略 | 丢弃的 token | 用户额外等待 | 部分结果 | 推荐场景 |
| --- | --- | --- | --- | --- |
| 跑完再说 | 0 | 最久（剩余 300 token ≈ 7.5 s） | 完整 | 批处理/后台任务 |
| **软抢占（生成到句末）** | **0** | 不到一个句子（≈1 s） | **保留可用** | **交互式默认** |
| 立即抢占 | 已生成的全部（本例 200） | 0 | 丢弃 | 「停下！」这类明确指令 |

**读法**：软抢占看起来「两全」，但它把额外的等待转嫁给了用户；立即抢占最省时间却让用户丢失已看到的内容。所以正确的做法是**把它做成可配置项**，并始终显式告知（「已停止生成，回答可能不完整」）。

### 可运行代码

```python
# 会话内多问题的调度模拟：增量依赖判定 + 受控并行 + 前缀共享 + 插话语义
import asyncio, time
from dataclasses import dataclass
from typing import List, Optional

SPEEDUP = 20          # 演示用加速倍数（真实延迟 = 输出值 × 20）

@dataclass
class Question:
    qid: str
    text: str
    depends_on: Optional[str] = None
    out_tokens: int = 300
    status: str = "queued"
    emitted: int = 0
    ttft_ms: float = 0.0

def classify_dependency(text: str, answered: List[str]) -> Optional[str]:
    """轻量依赖判定：出现指代/追问线索且已有回答，才依赖最近的一问"""
    if not answered:
        return None
    cues = ("那", "它", "这个", "上述", "刚才", "继续", "呢")
    return answered[-1] if any(c in text for c in cues) else None

class Session:
    """单会话：稳定前缀共享（只 prefill 一次）+ 受控并行"""
    def __init__(self, prefix_tokens=2000, per_turn_tokens=400, max_parallel=2,
                 prefill_ms_per_1k=20.0, tpot_ms=25.0):
        self.prefix_tokens, self.per_turn = prefix_tokens, per_turn_tokens
        self.max_parallel = max_parallel
        self.prefill_ms_per_1k, self.tpot_ms = prefill_ms_per_1k, tpot_ms
        self.history_tokens = 0
        self.prefix_prefills = 0               # 共享前缀只 prefill 一次
        self.answered: List[str] = []
        self._lock = asyncio.Lock()

    async def answer(self, q: Question) -> None:
        q.status = "prefilling"
        async with self._lock:                 # 前缀只算一次（模拟 KV 块共享）
            if self.prefix_prefills == 0:
                self.prefix_prefills += 1
                await asyncio.sleep((self.prefix_tokens / 1000
                                     * self.prefill_ms_per_1k) / 1000 / SPEEDUP)
        q.ttft_ms = self.prefix_tokens / 1000 * self.prefill_ms_per_1k
        q.status = "decoding"
        for i in range(q.out_tokens):
            await asyncio.sleep(self.tpot_ms / 1000 / SPEEDUP)
            q.emitted = i + 1
        q.status = "done"
        self.history_tokens += self.per_turn
        self.answered.append(q.qid)

    async def interrupt(self, q: Question, strategy: str) -> dict:
        """两种插话语义，如实计量「被丢弃的 token」与「额外等待」"""
        emitted = q.emitted
        if strategy == "immediate":
            await asyncio.sleep(0)              # 立刻停：已生成的都作废
            q.status = "cancelled"
            return {"丢弃 token": emitted, "额外等待 ms": 0}
        # 软抢占：生成到最近句末（每 40 token 一个句末）再停，部分结果保留可用
        target = min(q.out_tokens, ((emitted // 40) + 1) * 40)
        extra_tokens = target - emitted
        await asyncio.sleep(extra_tokens * self.tpot_ms / 1000 / SPEEDUP)
        q.emitted = target
        q.status = "cancelled"
        return {"丢弃 token": 0,                    # 部分结果交给用户，不算丢弃
                "额外等待 ms": extra_tokens * self.tpot_ms}

async def run(mode: str):
    sess = Session()
    # 混合了「独立问题」（可并行）与「追问」（必须排队等前文）
    texts = ["解释一下 KV cache", "顺便帮我写个快排", "再给个二分查找的模板",
             "那它的显存怎么算", "刚才那个的复杂度是多少"]
    qs = [Question(f"q{i+1}", t) for i, t in enumerate(texts)]
    if mode == "serial":
        for q in qs:
            q.depends_on = classify_dependency(q.text, sess.answered)
            await sess.answer(q)
    else:
        # 增量判定：每次都基于「已完成」的回答决定能否并行
        pending = list(qs)
        parallel_ready = []
        while pending:
            q = pending.pop(0)
            q.depends_on = classify_dependency(q.text, sess.answered)
            if q.depends_on is None and q is not qs[0]:
                parallel_ready.append(q)
            else:
                if parallel_ready:                       # 先把可并行的批次跑完
                    sem = asyncio.Semaphore(sess.max_parallel)
                    async def guarded(x):
                        async with sem:
                            await sess.answer(x)
                    await asyncio.gather(*[guarded(x) for x in parallel_ready])
                    parallel_ready = []
                await sess.answer(q)
        if parallel_ready:
            sem = asyncio.Semaphore(sess.max_parallel)
            async def guarded(x):
                async with sem:
                    await sess.answer(x)
            await asyncio.gather(*[guarded(x) for x in parallel_ready])
    return sess, qs

async def main():
    for mode in ("serial", "parallel"):
        t0 = time.perf_counter()
        sess, qs = await run(mode)
        dt = (time.perf_counter() - t0) * 1000
        print(f"{mode:<9} 演示耗时 {dt:>7.0f} ms  前缀 prefill 次数 {sess.prefix_prefills}  "
              f"完成 {sum(1 for q in qs if q.status == 'done')}/{len(qs)}")
        for q in qs:
            print(f"    {q.qid} 依赖={q.depends_on or '无':<4} 状态={q.status:<7} "
                  f"TTFT={q.ttft_ms:>6.0f} ms")
    print("\n读法：")
    print("  · 串行模式前缀只 prefill 一次，但总时长随问题数线性增长；")
    print("  · 受控并行共享前缀（prefix_prefills 仍为 1），总时长明显缩短；")
    print("  · 增量依赖判定让「那它的显存怎么算」排队等前一问，"
          "而「顺便帮我写个快排」被判为独立并并行执行")

    print("\n插话策略（已生成 200/500 token 时插话）：")
    for strategy, label in (("soft", "软抢占(生成到句末)"), ("immediate", "立即抢占")):
        sess = Session()
        q = Question("qx", "长回答", out_tokens=500)
        task = asyncio.create_task(sess.answer(q))
        await asyncio.sleep(200 * 25 / 1000 / SPEEDUP)
        stat = await sess.interrupt(q, strategy)
        task.cancel()
        print(f"  {label:<16} 丢弃 {stat['丢弃 token']:>3} token  "
              f"用户额外等待 {stat['额外等待 ms']:>5.0f} ms")
    print("  读法：立即抢占丢弃全部已生成内容（用户要从头再来）；软抢占保留部分结果、")
    print("        代价是多等不到一个句子的时间 —— 交互式默认应当用软抢占")

asyncio.run(main())
```

预期输出要点（实跑）：① **串行模式**前缀只 prefill **1 次**，5 个问题耗时约 3,150 ms；**受控并行**把两个独立问题（「顺便帮我写个快排」、「再给个二分查找的模板」）合成一批执行，前缀仍只 prefill 1 次而总耗时降到约 2,500 ms；同时依赖判定让「那它的显存怎么算」与「刚才那个的复杂度是多少」**排队等前文**——顺序语义与并行收益同时拿到；② 插话策略对照给出正确方向的记账：**立即抢占丢弃当时已生成的 119 token**（用户得从头再来），**软抢占丢弃 0 token**（部分结果保留可用），代价是**多等不到一个句子**（本例 25 ms。注意：绝对数字随调度抖动，看的是方向与量级）。

## 常见追问

- **追问**：依赖判定错了怎么办（把独立问题判成依赖）？
  - 要点：宁可**保守**（判成依赖只是慢一点；判错了会破坏语义）。另外可以给用户显式控制（「这个问题不依赖上文」开关），并记录判定准确率作为指标。
- **追问**：并行分支的 KV 怎么共享？
  - 要点：共享前缀的 KV 块按引用计数共享，分支进入不同内容时**写时复制**（copy-on-write）新块；工程上就是 PagedAttention/基数树那套机制（串 [[inference-serving-05]]）。
- **追问**：多路流怎么处理重连？
  - 要点：帧里带 `question_id` + 单调 `seq`；服务端保留最近窗口（或可重放缓冲），重连时客户端上报「已收到的最大 seq」，服务端从那里续传；已 `done` 的问题不回放。
- **追问**：会话太长怎么办？
  - 要点：三层——① 稳定前缀（系统提示 + 摘要）压缩；② 近期消息保留原文；③ 更早内容转成结构化摘要或可检索记忆；同时**分叉**（新建会话并继承摘要）比无限增长更好。
- **追问**：跨设备同时提问怎么解决？
  - 要点：会话只有一个权威写入点；设备提交时带本地序列号，服务端分配全局顺序；冲突时以服务端顺序为准并把两边的消息都保留（不同分支），避免「丢消息」。
- **追问**：一个会话并发几个问题合适？
  - 要点：由**用户感知**（乱序容忍度）与**系统容量**（KV 显存）共同决定；交互式默认 2–4，后台批处理可以更高；关键是把它做成**按 SLO 分级**的可配置项，而不是硬编码（串 [[anthropic-17]] 的通入控制）。
