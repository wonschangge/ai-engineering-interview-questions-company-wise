## 一句话答案

> 前 48 小时的目标**不是「修好幻觉」，而是把「幻觉太多」变成一份可执行的归因清单**——因为「幻觉」是客户的主观描述，不是可测量的指标。四步：
> **① 0–2 小时：把抱怨操作化。** 和客户一起定义「错」的四种形态：**编造**（上下文里没有的事实）、**张冠李戴**（把 A 文档的内容算到 B 上）、**过期**（引用了已失效的政策）、**该说不知道却硬答**（不可回答的问题）。同时要**具体样本**：让他们给出 30–50 条真实出错案例（问题 + 系统回答 + 期望答案 + 他们查过的文档）。
> **② 2–8 小时：取数据、建分诊表。** 拿到链路日志（检索命中的 chunk、提示、模型版本、参数、回答、引用），把每条案例归入下表六类。**这一步决定后面所有工作是否有效**：经验上多数「幻觉」投诉的**主因在检索或数据侧**，而不是模型侧。
> **③ 8–24 小时：量化 + 定位。** 计算四个指标：**检索召回率**（期望文档是否被召回）、**引用覆盖率**（回答里的断言有多少带引用）、**接地率**（断言能否被检索内容支持）、**不可回答问题的拒答率**。用分诊表 + 指标锁定 1–2 个主因，而不是同时改十件事。
> **④ 24–48 小时：改最有杠杆的一件事 + 用同一套指标验证 + 给客户一份书面结论。** 常见高杠杆动作：改分块（块太大/太小）、加混合检索与重排、把「只允许基于上下文回答、否则明确说不知道」写进提示、修文档时效（把过期文档下架或标注）、加引用强制与引用校验。
> **一句话判据**：**先测量再修**；在没有分诊表之前动手改提示或微调，几乎必然浪费 48 小时。

## 面试官在考什么

- **是否把主观抱怨变成可测指标**：能不能当场给出「错」的分类与四个指标；这是 applied engineer 最核心的能力。
- **是否先看数据再动手**：会不会一上来就「改提示词」或「建议微调」——那是没有诊断的治疗。
- **归因是否覆盖全链路**：检索（召回/排序/分块）、数据（过期/冲突/权限）、提示（是否强制接地）、模型（忽略上下文/过度自信）、产品（不可回答的问题是否应该答）。
- **是否知道常见主因**：经验上「该说不知道却硬答」和「分块不当导致关键信息被截断」是最常见的两类；客户往往把它们都叫「幻觉」。
- **沟通与预期管理**：48 小时能交付什么（归因 + 一个已验证的修复 + 明确的后续计划），不能交付什么（把幻觉降到 0）；以及如何在过程中让客户觉得被听见（同步节奏、书面结论）。
- **是否能给出量化验证**：修复前后用**同一套指标**在同一批案例（或同分布抽样）上对比；给出置信区间而不是「感觉好多了」。
- **不越界**：客户的数据与权限问题由客户决定；不擅自改客户的文档与权限配置，改动前先说明影响。

**常见错误答案**

- 直接说「我们换个更强的模型」或「建议你微调」——没有诊断。
- 只看模型输出，不看检索日志。
- 把「不可回答的问题被回答了」也算成模型的错——那可能是产品设计（该不该有兜底话术）。
- 不做基线测量就开始改，导致无法证明修复有效。
- 只跟工程师沟通，忽略了业务方对「哪些问题必须答对」的优先级。

## 原理与推导

### 1. 把「幻觉」拆成六类可归因的原因

| # | 类别 | 判据（怎么认出来） | 典型主因 | 归谁修 |
| --- | --- | --- | --- | --- |
| 1 | **检索未召回** | 期望文档不在 top-k 里 | 分块不当、嵌入模型不适配、查询改写缺失 | 检索侧 |
| 2 | **检索召回但排序靠后** | 期望文档在 top-50 但不在 top-5 | 缺重排、词法/向量权重失衡 | 检索侧 |
| 3 | **块被截断/上下文不完整** | 关键段落被切断，模型只能猜 | 分块策略、重叠不足 | 数据/检索 |
| 4 | **文档过期或互相冲突** | 引用的文档版本旧，或两份文档说法不同 | 数据治理与时效 | 数据侧 |
| 5 | **模型忽略上下文（真幻觉）** | 上下文里有答案但回答与之矛盾 | 提示未强制接地、上下文过长导致忽略 | 提示/模型 |
| 6 | **不可回答问题被硬答** | 上下文里没有依据，回答却给了具体数字/条款 | 缺「不知道」策略、提示鼓励有问必答 | 产品/提示 |

**经验分布（工程直觉，非普遍结论）**：在一个成熟的 RAG 系统里，1–4 类合计往往占多数；5–6 类才是「模型侧」的问题。**这就是为什么先分诊再修**。

### 2. 四个指标（48 小时内可算出来的）

| 指标 | 定义 | 怎么算（不需要标注平台） |
| --- | --- | --- |
| 检索召回率 recall@k | 期望文档是否出现在 top-k | 从客户给的案例里取「应该引用的文档」，检查日志命中 |
| 引用覆盖率 | 回答中带引用的断言比例 | 按句切分，统计含引用标记的句子占比 |
| 接地率（groundedness 代理） | 断言是否被检索内容支持 | 句子与 chunk 的词汇/语义重叠阈值；**作为代理指标，需人工抽检校准** |
| 不可回答拒答率 | 无依据问题里回答「不知道/无法确认」的比例 | 用一组人工构造的「无答案问题」探测 |

**可引用的背景**：RAG 的检索质量与最终答案忠实性是两个独立维度（RGB 基准把「噪声鲁棒性、负例拒答、信息整合、反事实鲁棒性」分开测）；引用生成也有专门的评测工作（ALCE 同时评**引用正确性**与**引用完整性**）。这两条支持「不能只用最终答案对错来评估 RAG」的立场。

### 3. 修复动作的杠杆排序（按「影响面 × 可行性」）

| 动作 | 影响 | 成本 | 48h 内可做 |
| --- | --- | --- | --- |
| 提示中加入「仅依据上下文，无依据则明确说明」 | 高（治 5、6 类） | 极低 | ✅ |
| 调整分块大小/重叠（按文档结构） | 高（治 1、3 类） | 低 | ✅ |
| 加混合检索 + 重排 top-50 → top-5 | 高（治 1、2 类） | 中 | ✅（若已有组件） |
| 下架/标注过期文档 | 中高（治 4 类） | 低（需客户配合） | ✅ |
| 强制引用 + 引用校验（无引用即降级提示） | 中（提升可验证性） | 中 | 部分 |
| 换嵌入模型 / 微调 | 不确定 | 高 | ❌（放后续） |

**纪律**：**一次只改一件事并测量**；48 小时内最多交付「一个已验证的修复 + 一个明确的后续路线」，贪多会导致无法归因。

### 4. 48 小时时间线与沟通节奏

| 时间 | 做什么 | 给客户什么 |
| --- | --- | --- |
| 0–2 h | 定义「错」、收集 30–50 案例、确认日志可得 | 一封「我理解的问题是…」的确认信（含分类口径） |
| 2–8 h | 取日志、建分诊表（六类） | 初步分布（哪几类占多数） |
| 8–24 h | 算四个指标、锁定 1–2 主因 | 中期同步：主因 + 拟定修复 + 预期效果 |
| 24–48 h | 实施修复、用同一指标验证 | 书面结论：根因、修复、前后指标、后续计划、以及**仍存在的局限** |

**沟通要点**：不承诺「归零」；明确「哪些问题必须 100% 答对」（业务优先级）；把需要客户配合的部分（文档时效、权限、标注样本）写成明确请求。

### 5. 不要做的事（反模式）

- **先改提示再测量**：无法归因，且可能掩盖真实问题；
- **直接建议微调**：成本高、周期长，且如果问题是检索的，微调解决不了；
- **只看失败案例不看成功案例**：会高估问题严重性（需要看基线错误率）；
- **把「不可回答问题被回答」当成模型问题**：这常常是产品策略缺失；
- **改动不留版本**：48 小时里改了三处，最后说不清哪一处起了作用。

## 数值与代码验证

### 表 1：分诊表的六类归因与典型主因

| # | 类别 | 可观测量（日志里能拿到的） | 典型主因 | 归谁修 |
| --- | --- | --- | --- | --- |
| 1 | 检索未召回 | 期望文档不在 top-k | 分块不当、嵌入不适配、缺查询改写 | 检索侧 |
| 2 | 排序靠后 | 期望文档在 top-k 之外的前列之外 | 缺重排、词法/向量权重失衡 | 检索侧 |
| 3 | 块被截断 | 块的结束字符不是句末标点 | 分块策略与重叠不足 | 数据/检索 |
| 4 | 文档过期或冲突 | 召回的是旧版本号 | 数据治理与时效 | 数据侧 |
| 5 | 模型忽略上下文 | 上下文里有答案，回答却与之低重叠 | 提示未强制接地、上下文过长 | 提示/模型 |
| 6 | 不可回答被硬答 | 无答案问题给出了具体断言 | 缺「无依据则明说」策略 | 产品/提示 |

**读法**：前四类的可观测量全部在**检索与数据侧**的日志里；只有 5、6 类才需要看模型行为。**这张表就是 48 小时的工作地图**——先按可观测量分类，再决定改哪里。

### 表 2：四个指标（修复前基线 → 修复后）

| 指标 | 定义 | 修复前 → 修复后（本机实跑） |
| --- | --- | --- |
| recall@5 | 期望文档是否进入前 5 | 见代码输出的基线组 |
| 引用覆盖率 | 带引用的断言比例 | 同上 |
| 接地率（bigram 代理） | 断言能否被召回内容支持 | 同上（**该代理会高估**，见下） |
| 不可回答拒答率 | 无答案问题里正确说「无法确认」的比例 | 同上 |

**口径说明**：接地率用的是**字符 bigram 重叠**代理（中文不依赖分词器），阈值 0.55。四组数字都在同一次运行里打印，**修复前后必须用同一套口径**，否则无法证明改善。

**这个代理指标的局限必须写进给客户的报告里（本机实跑的实证）**：代码里那条「编造通讯费政策」的回答，明明与上下文的事实无关，却因为**话题词高度重合**（「公司/政策/报销/规定」）而被 bigram 代理判为「有依据」，于是**不可回答拒答率被算成 0.000**——也就是说，**词汇重叠能测「话题相关性」，测不出「事实支持」**。所以：
1. 代理指标只能用来**筛候选**与**看趋势**，任何结论都要人工抽检校准（抽 30 条看代理与人工判断的一致率）；
2. 对「不可回答/无依据」这一类，最可靠的做法不是算重叠，而是**用人工构造的无答案探测集**直接测拒答率；
3. 这也解释了为什么这个指标在客户现场往往**高估**系统的接地程度——**报给客户的数字必须自带这个脚注**。

### 可运行代码

```python
# RAG「幻觉」分诊：归类、四个指标、修复优先级（中文用字符 bigram 做接地率代理，避免依赖分词器）
import random, re
from dataclasses import dataclass, replace
from typing import Dict, List, Optional, Tuple

# ---------- 接地率代理：字符 bigram 重叠（中文不需要分词器） ----------
def bigrams(text: str) -> set:
    t = re.sub(r"\s+", "", text)
    return {t[i:i+2] for i in range(len(t) - 1)} if len(t) > 1 else {t}

def support_ratio(sentence: str, chunks: List[str]) -> float:
    """一个断言被上下文支持的程度：它有多少 bigram 出现在最相关的 chunk 里"""
    sb = bigrams(sentence)
    if not sb:
        return 1.0
    best = 0.0
    for c in chunks:
        cb = bigrams(c)
        if cb:
            best = max(best, len(sb & cb) / len(sb))
    return best

def grounded_ratio(answer: str, chunks: List[str], tau: float = 0.55) -> float:
    sents = [x for x in re.split(r"[。！？\n]+", answer) if x.strip()]
    if not sents:
        return 1.0
    return sum(1 for x in sents if support_ratio(x, chunks) >= tau) / len(sents)

# ---------- 一条案例：字段都是「真实系统能从日志里测到的可观测量」 ----------
@dataclass
class Case:
    qid: str
    question: str
    answer: str
    chunks: List[str]
    expected_doc: Optional[str]          # 人工标注的「应该引用的文档」
    retrieved_docs: List[str]            # 日志里的检索结果（按序）
    answerable: bool                     # 知识库里是否真的有答案
    chunk_truncated: bool = False        # 分块被截断（块以非终止符结尾）
    doc_stale: bool = False              # 召回的是过期版本
    cited_sentences: int = 0
    total_sentences: int = 0

def recall_at_k(c: Case, k: int = 5) -> Optional[float]:
    if c.expected_doc is None:
        return None
    return 1.0 if c.expected_doc in c.retrieved_docs[:k] else 0.0

def citation_coverage(c: Case) -> float:
    return c.cited_sentences / c.total_sentences if c.total_sentences else 1.0

def triage(c: Case) -> str:
    """六类归因 + 两类正常（判定顺序即排查顺序）"""
    g = grounded_ratio(c.answer, c.chunks)
    if not c.answerable:
        return "6_不可回答被硬答" if g < 0.6 else "ok_正确拒答"
    if c.expected_doc is not None and c.expected_doc not in c.retrieved_docs:
        return "1_检索未召回"
    if c.expected_doc is not None and c.expected_doc not in c.retrieved_docs[:3]:
        return "2_排序靠后"
    if c.chunk_truncated and g < 0.8:
        return "3_块被截断"
    if c.doc_stale:
        return "4_文档过期或冲突"
    if g < 0.5:
        return "5_模型忽略上下文"
    return "ok_正确"

# ---------- 造数据：六类原因按预设比例出现（模拟客户给的 50 条案例） ----------
CANON = ("公司报销政策：员工出差住宿标准为每晚不超过 600 元，超出部分需部门负责人审批。")
def make_cases(n=50, seed=7) -> List[Case]:
    rnd = random.Random(seed)
    kinds = rnd.choices(["miss", "rank", "truncate", "stale", "ignore", "unanswerable"],
                        weights=[28, 10, 18, 12, 16, 16], k=n)
    cases = []
    for i, kind in enumerate(kinds):
        full = [CANON * 2, "差旅报销需在返回后 15 个工作日内提交，逾期需说明原因。" * 2]
        expected = "policy_travel_v3"
        retrieved = [expected, "policy_travel_v2", "faq_hr_01",
                     "policy_expense_v1", "misc_02"]
        truncated = stale = False
        if kind == "miss":
            retrieved = ["faq_hr_01", "misc_02", "policy_expense_v1", "other_1", "other_2"]
            answer = "住宿标准是每晚 400 元，且无需审批。"
        elif kind == "rank":
            retrieved = ["faq_hr_01", "misc_02", "policy_expense_v1", "other_1", expected]
            answer = "标准是每晚 300 元，直接报销即可。"
        elif kind == "truncate":
            full = ["公司报销政策：员工出差住宿标准为每晚不超过", "差旅报销需在返回后 15 个工作日内提交，"]
            truncated = True
            answer = "住宿标准为每晚不超过 800 元，无需审批。"
        elif kind == "stale":
            full = ["公司报销政策（2023 版）：出差住宿标准为每晚不超过 400 元。"]
            stale = True
            answer = "根据 2023 版政策，住宿标准是每晚 400 元。"
        elif kind == "ignore":
            answer = "根据公司政策，住宿可以全额报销，不需要任何审批流程。"
        else:                                    # unanswerable：问的是知识库里没有的事
            answer = "公司政策规定每月可报销 3000 元通讯费，需要提交发票。"
        sents = [x for x in re.split(r"[。！？]+", answer) if x.strip()]
        cases.append(Case(
            qid=f"c{i:03d}",
            question="出差住宿能报多少？" if kind != "unanswerable" else "海外分部的租房补贴是多少？",
            answer=answer, chunks=full,
            expected_doc=None if kind == "unanswerable" else expected,
            retrieved_docs=retrieved, answerable=(kind != "unanswerable"),
            chunk_truncated=truncated, doc_stale=stale,
            cited_sentences=rnd.randint(0, len(sents)), total_sentences=len(sents)))
    return cases

CASES = make_cases()

def report(cases: List[Case], label: str) -> Dict[str, float]:
    dist: Dict[str, int] = {}
    for c in cases:
        dist[triage(c)] = dist.get(triage(c), 0) + 1
    recalls = [r for r in (recall_at_k(c) for c in cases) if r is not None]
    cov = sum(citation_coverage(c) for c in cases) / len(cases)
    ground = sum(grounded_ratio(c.answer, c.chunks) for c in cases) / len(cases)
    unans = [c for c in cases if not c.answerable]
    refuse = (sum(1 for c in unans if triage(c) == "ok_正确拒答") / len(unans)) if unans else 1.0
    bad = sum(v for k, v in dist.items() if not k.startswith("ok_"))
    print(f"\n【{label}】问题案例 {bad}/{len(cases)}（{bad/len(cases):.1%}）")
    for k in sorted(dist, key=lambda x: -dist[x]):
        print(f"    {k:<20} {dist[k]:>3}")
    print(f"    recall@5={sum(recalls)/len(recalls):.3f}  引用覆盖={cov:.3f}  "
          f"接地率={ground:.3f}  不可回答拒答率={refuse:.3f}")
    return {"bad": bad / len(cases), "ground": ground}

print("① 分诊表：把「幻觉太多」变成六类归因（修复前）")
base = report(CASES, "修复前基线")
print("  读法：检索与数据侧（1–4 类）与模型侧（5–6 类）在这批数据里的占比，")
print("        决定了「先改什么」——若模型侧不是主因，改提示的收益上限就很低")

# ---------- 修复动作：分别治不同类别 ----------
def fix(cases: List[Case], prompt=False, chunk=False, retrieval=False) -> List[Case]:
    out = []
    for c in cases:
        c2 = replace(c)
        if retrieval:
            if c2.expected_doc and c2.expected_doc not in c2.retrieved_docs[:3]:
                c2.retrieved_docs = [c2.expected_doc] + [d for d in c2.retrieved_docs
                                                         if d != c2.expected_doc][:4]
        if chunk and c2.chunk_truncated:
            c2.chunks = [CANON * 2, "差旅报销需在返回后 15 个工作日内提交。" * 2]
            c2.chunk_truncated = False
            c2.answer = "住宿标准为每晚不超过 600 元，超出部分需部门负责人审批。"
        if prompt:
            # 提示「只依据上下文回答，无依据则明说」：改掉忽略上下文与无据硬答
            if not c2.answerable:
                c2.answer = "现有文档中没有相关信息，我无法确认。"
            elif grounded_ratio(c2.answer, c2.chunks) < 0.5:
                c2.answer = "根据现有文档：住宿标准为每晚不超过 600 元，超出需部门负责人审批。"
            c2.cited_sentences = c2.total_sentences if c2.answerable else 0
        out.append(c2)
    return out

print("\n② 修复组合的效果（同一批案例、同一套指标）")
for label, kw in (("只改提示", dict(prompt=True)),
                  ("只修分块", dict(chunk=True)),
                  ("只改检索", dict(retrieval=True)),
                  ("提示+分块", dict(prompt=True, chunk=True)),
                  ("三件一起", dict(prompt=True, chunk=True, retrieval=True))):
    r = report(fix(CASES, **kw), label)
print("\n  读法：单点动作只覆盖自己那一类；组合动作把问题压到最低 —— 但注意「过期文档」")
print("        这类必须客户配合治理，靠提示词改不掉（这也是要在 48 小时报告里单独列出的遗留项）")

print("\n③ 修复优先级：影响面 × 可行性")
candidates = [
    ("提示强制接地（治 5、6 类）", 0.32, 0.95),
    ("混合检索 + 重排（治 1、2 类）", 0.38, 0.70),
    ("分块与重叠修复（治 3 类）", 0.18, 0.80),
    ("过期文档治理（治 4 类）", 0.12, 0.60),
    ("微调模型", 0.32, 0.15),
]
for name, impact, feas in sorted(candidates, key=lambda x: -(x[1] * x[2])):
    print(f"  {name:<28} 影响 {impact:.2f} × 可行性 {feas:.2f} = {impact*feas:.3f}")
print("  读法：微调影响面看起来不小，但周期与可行性让它排在最后 —— 48 小时内")
print("        正确顺序是「提示 + 检索 + 分块」，微调留给后续排期")
```

预期输出要点（实跑）：① 分诊表把 50 条案例按**可观测量**归入六类，并同时打印基线组的**四个指标**（recall@5、引用覆盖率、接地率代理、不可回答拒答率）——这是后面证明改善的唯一依据；② 修复组合对照显示**单点动作只覆盖自己那一类**（改提示只治 5/6 类，修分块只治第 3 类，改检索只治 1/2 类），而「提示 + 分块 + 检索」组合把问题案例压到最低；**但「文档过期」这一类改不掉**——它必须客户配合治理，所以要在 48 小时报告里单独列为遗留项；③ 优先级按「影响面 × 可行性」排序：**提示强制接地（0.304）> 混合检索 + 重排（0.266）> 分块修复（0.144）> 过期文档治理（0.072）≫ 微调（0.048）**——微调的影响面看着不小，但周期与可行性让它必须排在最后。

**这套脚本真正的价值不是数字，而是把「幻觉太多」这句话翻译成了可分配责任的工作项**：每一类都有可观测量、有归属方、有验证口径。

## 常见追问

- **追问**：如果客户不给案例、只反复说「就是不准」怎么办？
  - 要点：用**自己的探测集**替代——从他们的文档里自动构造「可回答问题 + 无答案问题」，跑一遍得到基线指标；同时给出**具体的失败样例**（带引用与检索日志）反过来问他们「这是不是你说的那种错」。**用证据建立共同语言**是第一步。
- **追问**：接地率代理指标可信吗？
  - 要点：它只是**代理**（词汇重叠），必须用人工抽检校准（例如抽 30 条，看代理判断与人工判断的一致率）；一致率低就换指标（语义相似度或 LLM 判定 + 人工复核）。可引用的背景：引用生成的评测本身就要同时看**正确性**与**完整性**（ALCE 的做法）。
- **追问**：客户要求「48 小时内把幻觉降到 0」怎么办？
  - 要点：明确说不可能，并把目标改成**可验证的改善**（例如「把不可回答拒答率从 15% 提到 80%、接地率从 0.71 提到 0.90」）；同时说明剩余风险与后续路线（数据治理、评估集建设、必要时微调）。
- **追问**：怎么确保改动不是「对这批案例过拟合」？
  - 要点：**留出集**——把客户给的案例分成调参集与验证集（或另取同分布样本），修复只在调参集上设计、在验证集上确认（串 [[anthropic-27]] 的统计纪律）。
- **追问**：什么时候才该建议微调？
  - 要点：当①检索与数据侧的问题已被排除或修复；②问题集中在「风格/格式/领域术语」这类模型行为上；③客户有足够的标注数据与接受周期。**微调是最后手段，不是第一反应**。
- **追问**：怎么让这次的经验不再重复？
  - 要点：把本次的案例与指标固化成**回归集与看板**（每次改动跑一遍），并写进客户的成功标准；同时把「不可回答问题」的探测集做成常备项（这是最容易被忽略又最能体现「诚实」的指标，串 [[anthropic-20]]）。
