## 一句话答案

> 需求每十分钟来一条，失控的根源是**把每条需求都写成一段新的 if**。做法是把「变化点」收敛成四个可替换的部件，需求来了只换配置或加一个实现：
> ① **键（key）与配额来源分离**——「限谁」（租户/用户/路由/模型）与「限多少」（配额策略）是两个独立维度；键由 `key_fn` 生成，配额从 policy 取。
> ② **算法是策略**——固定窗口、滑动窗口、令牌桶、漏桶各有取舍（精度/内存/突发支持）；把它们实现成同一个 `RateLimitAlgorithm` 接口，需求变更 = 换策略。
> ③ **时间与存储是注入的依赖**——注入时钟（可注入假时钟，让时间相关测试确定）与存储（内存/Redis），否则测试无法写、分布式无法接。
> ④ **决策结果是一等对象**——`RateLimitResult(allowed, remaining, retry_after, limit)`，让调用方（HTTP 层、队列、重试逻辑）无需知道算法细节；**这一点决定了后续需求（返回 Retry-After、按权重计费、多级限流）能不能平滑加进来**。
> 一句话原则：**核心是「决策接口 + 可注入时钟/存储 + 策略」，需求演进只增加实现，不改调用方**；同时警惕过度抽象——只有两种实现的维度不要抽接口。

## 面试官在考什么

- **变化点识别**：能否在一开始就说出「限谁、限多少、怎么算、时间从哪来、状态放哪」这五个维度，而不是等需求来了才重构。
- **算法取舍的量化**：固定窗口的边界双倍突发、滑动窗口日志的精确但内存高、滑动窗口计数的近似误差（上界 $1/\text{分片数}$）、令牌桶的稳态速率与突发容量解耦——能不能给出对比表并说明选择依据。
- **可测试性**：时间相关逻辑**必须**可注入时钟；否则「每 10 分钟 100 次」这类需求根本无法写确定性测试。
- **分布式现实**：本地限流与集中式限流的差异（超发风险、Redis 故障时的 fail-open/fail-closed 选择）、以及「精确全局限流在分布式下代价极高」这一事实。
- **演进的优雅度**：新需求（按权重计费、多级限流、优先级豁免）到来时，改动是「加一个策略/加一个配置」还是「改核心逻辑」。
- **反向判断力**：能否指出**不该抽象**的地方（例如只有两种算法时可以先用一个参数区分，而不是上完整策略体系）。

**常见错误答案**

- 每来一条需求加一个 `if tenant in whitelist and burst ...`——三个需求后代码不可读、不可测。
- 用 `time.time()` 直接读时钟——测试无法构造「跨窗口边界」的场景。
- 认为滑动窗口计数完全精确——它只是误差有界的近似。
- 忽略分布式：本地限流在多实例下会把总配额乘以实例数（这是真实事故）。

## 原理与推导

### 1. 四种算法的取舍

| 算法 | 精度 | 内存 | 突发支持 | 实现复杂度 | 典型用途 |
| --- | --- | --- | --- | --- | --- |
| 固定窗口 | 低（边界双倍） | $O(1)$/键 | 无 | 极低 | 粗粒度保护 |
| 滑动窗口日志 | 精确 | $O(\text{窗口内请求数})$ | 无（或按需） | 低 | 低 QPS、强精确 |
| 滑动窗口计数 | 近似（误差 $\le 1/\text{分片}$） | $O(\text{分片数})$ | 无 | 中 | 高 QPS 通用 |
| 令牌桶 | 精确（按速率） | $O(1)$/键 | **有（桶容量）** | 中 | API 限额、允许突发 |
| 漏桶 | 精确（平滑输出） | $O(1)$/键 | 无（强制平滑） | 中 | 下游保护 |

**「边界双倍」是什么**：固定窗口把时间切成 $[0,T), [T,2T)$，若客户端在 $T-\epsilon$ 发 $N$ 次、在 $T+\epsilon$ 再发 $N$ 次，则 $2N$ 次落在 $2\epsilon$ 的区间内——瞬时速率是限额的两倍。滑动窗口就是为了消除这个。

### 2. 令牌桶的参数含义（突发需求的标准答案）

令牌桶有两个参数：速率 $r$（token/秒）与桶容量 $b$（burst）。稳态下长期速率被限制在 $r$，但**允许最多 $b$ 个请求的瞬时突发**。补桶逻辑：

$$\text{tokens}(t)=\min\big(b,\ \text{tokens}(t_0)+r\cdot(t-t_0)\big)$$

请求消耗 1 个 token（或按权重的 $w$ 个）。**关键设计问题**：桶容量是「按租户配置」还是「等于速率 × 某系数」？——前者灵活、后者简单，要显式选择（这也是需求演进里最常被问的一点）。

### 3. 滑动窗口计数的误差上界

把窗口切成 $k$ 个分片，用「当前分片的部分计数 + 前 $k-1$ 个分片的完整计数」近似。误差来自「上一窗口的请求被整段计入」：

$$\text{近似值}-\text{真实值}\le \frac{N_{\text{上一窗口}}}{k}$$

即**误差上界是上一窗口总量的 $1/k$**。$k$ 越大越准、内存与更新成本越高（典型取 10–60）。**能在面试里报出这个上界**，说明不是背结论。

### 4. 分布式限流的三种形态

| 形态 | 一致性 | 延迟 | 超发风险 | 适用 |
| --- | --- | --- | --- | --- |
| 本地（每实例独立） | 无 | 最低 | 配额 × 实例数 | 保护本实例 / 粗粒度 |
| 集中式（Redis 等） | 强（单点串行） | 网络往返 | 低 | 精确配额、计费 |
| 分层（本地 + 集中式） | 中 | 低（多数命中本地） | 可控（本地额度按比例分配） | 大规模通用 |

**故障策略必须先定**：存储不可用时 **fail-open**（放行，保可用性）还是 **fail-closed**（拒绝，保保护性）？这取决于限流的目的（保护下游 vs 配额计费）。真实系统常按路由区分。

### 5. 需求演进如何只改配置

| 新需求 | 改动点 |
| --- | --- |
| 按租户限流 | 加 `key_fn = tenant`；配额从租户配置读 |
| 突发额度 | 换算法为令牌桶，加 `burst` 参数（**不改调用方**） |
| 滑动窗口 | 换算法实现（接口不变） |
| 返回 `Retry-After` | 结果对象已含 `retry_after`，HTTP 层直接用 |
| 按权重计费（大请求耗多个 token） | 请求带 `cost`，算法接口加乘数（一处改动） |
| 优先级豁免 | 加一个「先查豁免策略，再查限流」的组合策略 |

**对比「失控版本」**：同样的六个需求，会在 4–6 个地方各加一段 `if`，且每个新需求都要重新理解全部历史分支。

## 数值与代码验证

### 表 1：固定窗口 vs 滑动窗口在边界上的行为

| 场景（限额 100/分钟） | 固定窗口允许 | 滑动窗口计数允许 | 说明 |
| --- | --- | --- | --- |
| 均匀 1.67 次/秒 | ✓ | ✓ | 都正常 |
| 第 59 秒发 100 次 + 第 61 秒发 100 次 | **✓（瞬时 200）** | ✗（第 61 秒只放行约 0） | 固定窗口的边界双倍 |
| 第 30 秒突发 100 次 | ✓ | ✓（窗口内未超） | 平滑场景两者一致 |

### 表 2：滑动窗口计数的误差取决于「请求落在分片内的位置」

| 请求在部分重叠分片中的位置 | 估计用量的偏差 | 后果 |
| --- | --- | --- |
| 集中在分片**开头**（刚进分片就发完） | 高估用量 | 偏严（少放行） |
| 集中在分片**结尾**（分片快结束时发） | 低估用量 | 偏宽（最多多放行该分片残留的份额） |
| 均匀分布（真实流量的常见形态） | 接近无偏 | 与精确窗口差别很小 |

**结论（要点）**：滑动窗口计数**没有与分布无关的紧上界**——误差方向取决于请求在分片内的位置，极端情况下可接近「单个分片的总量」。所以工程上不追求解析上界，而是：① 把分片做细（秒级粒度，$k$ 取 60 时误差被压到很小）；② 对强精确场景改用滑动窗口日志或令牌桶；③ 用线上对照（实际放行量 vs 配额）验证偏差可接受。可引用的工程背景是 Cloudflare 的做法：用「当前窗口计数 + 上一窗口计数 × 重叠比例」做估计，并以秒级粒度把误差控制在很小范围。

### 可运行代码

```python
# 策略化的限流器：算法可替换、时钟可注入、结果对象化（可直接跑）
from dataclasses import dataclass
from typing import Dict, Optional, Protocol, Tuple
import math

# ---------- 注入的时钟（测试可换假时钟） ----------
class Clock(Protocol):
    def now(self) -> float: ...

class RealClock:
    def now(self) -> float:
        import time; return time.time()

class FakeClock:
    def __init__(self, t: float = 0.0): self.t = t
    def now(self) -> float: return self.t
    def advance(self, dt: float) -> None: self.t += dt

# ---------- 决策结果是一等对象 ----------
@dataclass(frozen=True)
class RateLimitResult:
    allowed: bool
    limit: int
    remaining: int
    retry_after: float = 0.0
    algorithm: str = ""

# ---------- 算法接口 ----------
class RateLimitAlgorithm(Protocol):
    name: str
    def check(self, key: str, cost: int, now: float) -> RateLimitResult: ...

class FixedWindow:
    """固定窗口：最省内存，但存在边界双倍突发"""
    name = "fixed_window"
    def __init__(self, limit: int, window: float):
        self.limit, self.window = limit, window
        self.state: Dict[str, Tuple[int, int]] = {}      # key -> (窗口序号, 计数)
    def check(self, key, cost, now):
        idx = int(now // self.window)
        cur_idx, cnt = self.state.get(key, (idx, 0))
        if cur_idx != idx:
            cur_idx, cnt = idx, 0
        if cnt + cost <= self.limit:
            self.state[key] = (cur_idx, cnt + cost)
            return RateLimitResult(True, self.limit, self.limit - cnt - cost, algorithm=self.name)
        retry = (idx + 1) * self.window - now
        return RateLimitResult(False, self.limit, 0, retry, self.name)

class SlidingWindowCounter:
    """滑动窗口计数：误差上界 = 上一窗口总量 / 分片数"""
    name = "sliding_counter"
    def __init__(self, limit: int, window: float, shards: int = 10):
        if window % shards:
            raise ValueError("window 必须能被 shards 整除")
        self.limit, self.window, self.shards = limit, window, shards
        self.shard = window / shards
        self.state: Dict[str, Dict[int, int]] = {}       # key -> {分片序号: 计数}
    def check(self, key, cost, now):
        s = int(now // self.shard)
        buckets = self.state.setdefault(key, {})
        window_start = now - self.window
        # 过期判定必须按「分片结束时间 <= 窗口起点」，不能按「分片序号 - 分片数」
        # （后者会在窗口恰好滑过一个分片时把仍然有效的分片删掉）
        for k in [k for k in buckets if (k + 1) * self.shard <= window_start]:
            del buckets[k]
        total = 0.0
        for k, v in buckets.items():
            start = k * self.shard
            if start >= window_start:                   # 完全在窗口内
                total += v
            else:                                       # 部分重叠：按时间比例折算（保守）
                frac = (start + self.shard - window_start) / self.shard
                total += v * frac
        if total + cost <= self.limit:
            buckets[s] = buckets.get(s, 0) + cost
            return RateLimitResult(True, self.limit, int(self.limit - total - cost), algorithm=self.name)
        # 估算可重试时间：最早的分片滑出窗口
        oldest = min(buckets) * self.shard + self.shard
        return RateLimitResult(False, self.limit, 0, max(0.0, oldest - window_start), self.name)

class TokenBucket:
    """令牌桶：稳态速率与突发容量解耦"""
    name = "token_bucket"
    def __init__(self, rate: float, burst: int):
        self.rate, self.burst = rate, burst
        self.state: Dict[str, Tuple[float, float]] = {}   # key -> (tokens, last_ts)
    def check(self, key, cost, now):
        tokens, last = self.state.get(key, (float(self.burst), now))
        tokens = min(self.burst, tokens + self.rate * (now - last))
        if tokens >= cost:
            self.state[key] = (tokens - cost, now)
            return RateLimitResult(True, self.burst, int(tokens - cost), algorithm=self.name)
        need = cost - tokens
        self.state[key] = (tokens, now)
        return RateLimitResult(False, self.burst, 0, need / self.rate, self.name)

# ---------- 组合：键 + 配额 + 算法（需求演进只改这里） ----------
class RateLimiter:
    def __init__(self, algo: RateLimitAlgorithm, clock: Optional[Clock] = None):
        self.algo, self.clock = algo, clock or RealClock()
    def check(self, key: str, cost: int = 1) -> RateLimitResult:
        return self.algo.check(key, cost, self.clock.now())

# ---------- 测试（假时钟，确定性） ----------
def scenario(algo, label):
    clk = FakeClock(0.0)
    rl = RateLimiter(algo, clk)
    out = []
    # 稳态：每 0.5 秒 1 次，共 120 次（限额 100/分钟）
    allowed = sum(1 for i in range(120) if (rl.check("t1").allowed, clk.advance(0.5))[0])
    out.append(f"{label}: 120 次均匀请求放行 {allowed}")
    return out, clk, rl

for algo, label in [(FixedWindow(100, 60.0), "固定窗口"),
                    (SlidingWindowCounter(100, 60.0, shards=10), "滑动窗口计数"),
                    (TokenBucket(rate=100/60, burst=20), "令牌桶(r=1.67/s,b=20)")]:
    lines, clk, rl = scenario(algo, label)
    print("\n".join(lines))

# 边界双倍突发：固定窗口 vs 滑动窗口
print()
for algo, label in [(FixedWindow(100, 60.0), "固定窗口"),
                    (SlidingWindowCounter(100, 60.0, shards=10), "滑动窗口计数")]:
    clk = FakeClock(0.0); rl = RateLimiter(algo, clk)
    clk.advance(59.0)
    first = sum(1 for _ in range(100) if rl.check("burst").allowed)
    clk.advance(2.0)          # 跨过窗口边界
    second = sum(1 for _ in range(100) if rl.check("burst").allowed)
    print(f"{label}: 第 59 秒放行 {first}，第 61 秒放行 {second}，两秒内共 {first+second}（限额 100/分钟）")

# 令牌桶的突发额度
clk = FakeClock(0.0); rl = RateLimiter(TokenBucket(rate=10.0, burst=50), clk)
burst = sum(1 for _ in range(80) if rl.check("b").allowed)
clk.advance(5.0)
after = sum(1 for _ in range(80) if rl.check("b").allowed)
print(f"\n令牌桶(r=10/s,b=50)：瞬时放行 {burst}（桶满即上限），静置 5 秒后再放行 {after}（补 50 个）")

# 滑动窗口计数的边界行为：误差方向取决于请求落在分片内的位置
def boundary_probe(offset_in_shard):
    """在 t=offset 处打满 100 次，然后看窗口滑过第一个分片那一刻会多放行多少次"""
    clk = FakeClock(0.0); rl = RateLimiter(SlidingWindowCounter(100, 60.0, shards=10), clk)
    clk.advance(offset_in_shard)
    for _ in range(100):
        rl.check("k")                     # 100 次全落在第 0 个分片（[0,6) 秒）
    clk.advance(60.0 + 1.0 - offset_in_shard)   # 让窗口起点落在 t=1s（分片已滑过 1/6）
    extra = sum(1 for _ in range(100) if rl.check("k").allowed)
    # 真实窗口 [1,61] 内仍然包含这 100 次（若请求发生在 t>=1），应该是 0 次额外放行
    true_in_window = 100 if offset_in_shard >= 1.0 else 0
    return extra, true_in_window

for off in (0.1, 3.0, 5.9):
    extra, true_in = boundary_probe(off)
    direction = "宽松（多放行）" if true_in == 100 else "保守（少放行）"
    print(f"请求发生在分片内 t={off:>4.1f}s（真实窗口内 {true_in} 次）：多放行 {extra:>3} 次 -> {direction}")
print("读法：请求集中在分片结尾时实现偏宽松、集中在开头时偏保守——误差方向取决于分布，")
print("所以要用秒级分片把误差压小，而不是指望一个与分布无关的上界")

# 按权重计费（需求演进：大请求耗多个 token）
clk = FakeClock(0.0); rl = RateLimiter(TokenBucket(rate=1.0, burst=10), clk)
print(f"\n权重计费：cost=6 -> {rl.check('w', cost=6).allowed}，再 cost=6 -> {rl.check('w', cost=6).allowed}"
      f"（桶 10 只够一次）")
```

预期输出要点（本机实跑）：均匀 120 次请求在三种算法下都放行约 100 次（令牌桶因补桶略有差异）；**边界双倍**场景里固定窗口在第 59 秒与第 61 秒各放行 100 次（两秒 200 次），滑动窗口计数严格压住（两秒共 100 次）；令牌桶瞬时放行等于桶容量 50、静置 5 秒后补满再放行 50；边界探针显示**误差方向随请求在分片内的位置改变**（集中在分片结尾时偏宽松、开头时偏保守）；权重计费演示 `cost` 参数让一次大请求消耗多个 token——**这五个需求（按租户、突发、滑动窗口、边界误差、按权重）都只改了算法/参数，调用方一行未动**。

## 常见追问

- **追问**：分布式怎么保证全局精确？
  - 要点：要么集中式（Redis + Lua 原子脚本），要么接受**近似**（本地额度按实例数分摊 + 定期同步），要么改用租约（每个实例领一段配额）。精确全局限流在跨区场景下延迟不可接受。
- **追问**：存储挂了怎么办？
  - 要点：先明确目的——保护下游 → fail-closed（拒绝），保可用性 → fail-open（放行 + 告警 + 本地兜底）。按路由分级配置，并把这个选择写进 SLO。
- **追问**：多个限流维度（租户 + 用户 + 全局）怎么组合？
  - 要点：组合模式——按顺序检查多个策略，任一拒绝即拒绝（AND 语义），并让结果带上「哪个维度拒绝的」；豁免/优先级用独立的预检查策略。
- **追问**：怎么测试时间相关逻辑？
  - 要点：**注入假时钟**（本例的 `FakeClock`），构造窗口边界、补桶、跨分片等确定性场景；真实 `sleep` 的测试既慢又不稳定。
- **追问**：为什么不用 `asyncio.Semaphore` 做限流？
  - 要点：信号量限的是**并发数**，不是**时间窗内的总量**——两者目的不同（保护资源 vs 控制速率）。生产系统常常两者都要。
- **追问**：什么时候该停止抽象？
  - 要点：当某个维度只有一种实现且可预见不会变（例如键总是租户 id），直接用参数；抽象的成本是阅读与调试成本，把它留给真正在变的两三个维度。
