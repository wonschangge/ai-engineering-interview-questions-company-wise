## 一句话答案

> 调度器只做四件事：**准入**（现在能不能收）、**选择**（谁先跑）、**重试**（跑几次）、**终结**（什么算完成）。契约先定死：`submit(task, *, priority=0, run_at=None, delay=None, deadline=None, idempotency_key=None, max_attempts=3) -> handle`，状态机 `queued → leased/running → succeeded | failed | retry_scheduled | dead_lettered`，终态只结算一次，于是可以随时断言 `sum(各终态计数) == 提交数`。
> 选择用最小堆，键必须是可比较的三元组 `(priority, run_at, seq)`：只用 `(priority, run_at)` 时两个同键任务会让 `heapq` 退去比较任务对象、Python 3 直接 `TypeError`；用 `id()` 补平局则让出队顺序取决于进程的分配历史，不可复现。延迟任务单独一个按 `run_at` 排序的堆，**堆顶未到期 ⇒ 其余全部未到期**是唯一需要的剪枝，绝不能每秒扫全表。
> 并发上限约束的是**在途任务数**而不是队列长度，两者混为一谈一上量就露馅；背压要有两道闸门（待调度队列 + 已领取槽位），退避的 `sleep` 必须放在信号量**外面**，否则重试会把并发额度一起睡掉。
> 但在写第一行代码前先回答「该不该上通用调度器」：固定步数、固定依赖的流水线用 cron 或队列就够，把选择权交给模型才需要调度、预算与公平性。

## 面试官在考什么

- **契约与状态机是否先于代码**：四件事的边界、`submit` 的参数（`run_at`/`delay`/`deadline`/`idempotency_key`/`max_attempts`）、六个状态、三个终态，以及「终态只结算一次」这条可断言的守恒。开口能说清「什么时候不该上调度器」比背框架更值钱——Anthropic 在 Building Effective Agents 里的取向是先找最简单可控的方案，只在确有收益时增加复杂度。
- **堆键与复杂度是不是真懂**：三元组键为什么必须有 `seq`、`seq` 为什么必须单调递增、延迟堆为什么只看堆顶、到期回收为什么必须切有界批次。这四点在 15 分钟里最容易露怯。
- **公平性是机制还是口号**：严格优先级 + 无上限突发会饿死低优先级；能落地的是优先级老化与等待上限，而且必须说清「优先级」（谁先跑）与「配额」（总共能跑多少）是两套参数。
- **并发与背压能不能落到数字**：信号量只圈在途数、退避睡在信号量外、`raise` 与 `block` 的取舍、内存上界是 $O(\text{队列上限} + \text{槽位} \times \text{单任务峰值})$，以及「按请求调度 ≠ 按成本调度」。
- **失败分类、重试预算与抖动**：429/5xx/超时可重试，4xx 重试一百次还是同样的错误，语义失败当事实，幻觉出来的目标回报可用清单；`Retry-After` 优先于任何客户端公式；总预算不等式能背出来，抖动不是可选项。
- **分布式四机制与可观测**：原子领取、租约与心跳、幂等与至少一次、调度延迟/队列深度/在途数/重试率/终态计数/尾延迟进指标，且限流与重试是一个闭环。

常见错误答案：

- 把「并发上限」写成「队列长度上限」；或者用 `asyncio.TaskGroup` 承载「每个任务独立」的语义（本机 5 个子任务 1 个失败，TaskGroup 完成 0 个、独立 Future 完成 4 个）。
- 退避公式背得熟，但 `sleep` 写在信号量里、不读 `Retry-After`、不做总时限检查，deadline 被拖爆还以为是退避的锅（退避合计 0.35 s，单次尝试超时 5 s × 4 次 = 20 s）。

## 原理与推导

### 1. 四件事、状态机与守恒断言

准入只回答「现在能不能收」（队列上限、租户配额、幂等键去重）；选择只回答「谁先跑」（堆键、公平性）；重试只回答「跑几次、隔多久」（分类、退避、预算）；终结只回答「什么算完成」（终态与结算）。四个问题分开，状态机才有意义：`queued → leased/running → succeeded | failed | retry_scheduled | dead_lettered`。其中 `leased`（已领取、结果未知）是分布式的必需态，它把「超时」显式表达成**未知**而不是失败。终态只结算一次的价值在于可断言：`sum(各终态计数) == 提交数` 一条断言同时抓丢任务、重复投递与重复结算。本机 200 个任务（含 20 个瞬时失败重试、20 个参数错误、40 个延迟任务）的终态是 `{succeeded: 180, failed: 20}`，守恒成立，在途峰值 8 = 上限。

### 2. 两个堆：键必须是可比较的三元组

只用 `(priority, run_at)` 时，同优先级同 `run_at` 的两个任务会让元组比较落到第三个元素——任务对象，Python 3 直接抛 `TypeError`（本机在第二次 `heappush` 就复现）。用 `id()` 补平局更隐蔽：id 是进程内地址，出队顺序由分配历史决定——同一份输入在两个进程里，id 排序相对提交顺序的逆序对占比是 0.01% 与 32.76%，两个进程之间 100% 的位置不同（Python 3.10.12 同口径为 8.57% / 0% / 29%）。正解是 `(priority, run_at, seq)`（约定数值越小越优先，与 Unix nice 一致，最小堆直接可用），`seq` 由 `itertools.count()` 单调递增，保证 FIFO 平局与跨重启可复现。延迟任务用第二个按 `run_at` 排序的堆。关键性质只有一条：**堆顶未到期，其余全部未到期**，所以每个 tick 只看堆顶是 $O(1)$。本机 20 万条延迟任务跑 100 个 tick：扫全表 319 ms（3.10 上 572 ms），只看堆顶 3.3 ms（2.5 ms），差 98–229 倍。堆顶到期后回收必须**有界**：一次清完 20 万条 136 ms，单批 64 条 0.12 ms（3.10 上 155 ms / 0.19 ms；[[coding-06]] 的缓存口径是 575.3 ms vs 0.27 ms），清尾切成有界批次才不会在主循环上砍出长尾。周期任务要区分一次性的 `run_at` 与下一跳 `next_run`：读命中续期式的滑动语义会让索引无界膨胀（[[coding-06]] 实测 1000 个键读 100 万次，堆从 1000 条撑到 1,001,000 条约 95 MiB）。

### 3. 公平性：优先级是顺序，配额是总量

严格优先级 + 无上限突发会饿死低优先级。本机口径（4 个 worker、每任务 1 ms ⇒ 容量 4000 任务/s、0.6 s 内约 3000 个高优先级任务持续到达、20 个低优先级任务）：低优先级中位与最大等待都是 0.90 s，洪水不停就无限期。两条可落地的机制：

- **老化**：等待折算成有效优先级 $\text{eff} = p - t_{\text{wait}} / W$，$W$ 是「等多久相当于升一级」。它保证的不是「X 秒内被服务」，而是「每一个新到的更高优先级任务最多再把它推迟 $\Delta p \cdot W$」：本机 $W = 0.02$ s、$\Delta p = 10$ 时，低优先级任务 0.33 s 被服务（上界 0.2 s 加上它前面那批积压的服务时间）。
- **等待上限**：任何任务等待超过 $W_{\max}$ 就必须被选中（取等待最久者），把尾部钉死：$W_{\max} = 20$ ms 时低优先级中位/最大等待 0.024/0.027 s。反例是「跳过次数上限」按全局选择次数计数：饱和时所有任务的计数同步上涨、同时触发，本机实测 1.11/1.12 s（中位/最大），比严格优先级还差；上限必须定义在**等待时长**上。

优先级与配额要拆成两套参数：优先级决定谁先跑，配额决定总共能跑多少。多租户按加权公平份额分配，全局利用率低于阈值（如 70%）时允许借用余量、高于阈值就压回自己的份额（[[system-design-09]]）；用同一个数字兼任两者是生产事故的常见起点（[[coding-07]]）。

### 4. 时间：单调时钟、单一时钟源、有界清扫

内部一律用 `time.monotonic()`；墙钟只用于把「几点几分」换算成持久化的 `run_at` 与展示。跨实例的到期判定必须由单一时钟源给出，实例本地时钟做惰性结算会被反复记账。本机口径（$r = 100/\text{s}$、$b = 10$、1 s 内 6000 次请求、两实例同时处理）：单一时钟源放行 109 次（上限 $b + rT = 110$）；本地时钟在时钟差 0/0.2/1/5/50 ms 时分别放行 109/169/409/1609/6000，多出来的额度正好是 $\text{每实例请求数} \times \text{skew} \times r = 3000 \times \text{skew} \times 100$（[[coding-07]] 同口径实测 119/359/1559/6000）。一次 NTP 回拨会凭空补出额度，所以 `elapsed <= 0` 时既不补充、也不回退 `last`。到期回收与容量淘汰是两套正交机制（Redis 的 `volatile-*` 与 `allkeys-*` 就是这个口径，[[coding-06]]）。

### 5. 并发上限与背压：两道闸门，退避睡在外面

信号量约束的是**在途任务数**，不是队列长度；两者相等只在恰好饱和的那一刻成立。退避的 `sleep` 必须在信号量**外面**：本机 16 个任务各重试一次、并发 4，睡在里面 243 ms、睡在外面 67 ms，差 3.6 倍（[[mistral-01]] 同机制、16 个任务各 3 次尝试：1,404 ms vs 602 ms，差 2.33 倍）。背压两道闸门——待调度队列（收不收）与在途槽位（能跑几个）——只做一道，等待任务会无界增长。本机口径（40 个任务、队列上限 4、槽位 2、每任务 50 ms）：`raise` 接纳 4 个、以 `QueueFull` 拒 36 个、墙钟 103 ms；`block` 全部接纳、墙钟 1007 ms，理论下限 $40 \div 2 \times 50\ \text{ms} = 1000$ ms（[[coding-08]] 是 4/36 与 503–507 ms、下限 500 ms）。内存上界 $O(\text{队列上限} + \text{槽位} \times \text{单任务峰值})$ 要能直接说出来。按请求调度 ≠ 按成本调度：LLaMA-3-70B 每 token 的 KV cache 是 320 KiB（$2 \times 80\ \text{层} \times 8\ \text{个 KV 头} \times 128 \times 2\ \text{B}$），4096 token 上下文占 $4096 \times 320\ \text{KiB} = 1.25$ GiB，按 H100 3.35 TB/s 读一遍是 0.40 ms；8×H100 扣掉权重 141 GB 与工作区 20 GB 后，KV 池剩约 479 GiB（单卡按 80 GiB 计），只够约 383 条并发 4k 请求（按 2.5 \$/GPU·h 租这些卡，就是每分钟都要摊的固定成本）。真正稀缺的是 token 而不是请求数，所以对外限流要用 RPM + ITPM/OTPM 双轴（[[coding-07]]），调度器也要按 token 给任务计价。

### 6. 失败分类、重试预算与抖动

先分类再处置（[[coding-12]] 的四类）：429/5xx/连接超时可重试；4xx 参数错误不重试，重试一百次还是同样的错误；语义失败（空结果、无权限）当事实；幻觉出来的目标或工具名回报可用清单。服务端给了 `Retry-After` 就听它的，它比任何客户端公式都准。基准等待 $d_n = \min(d_{\max}, d_0 2^{n-1})$，单次实际等待取 full jitter $U(0, d_n)$。预算不等式：$\text{总预算} \ge \text{排队窗口} + \sum_{n<A} d_n + A \times \text{单次尝试超时}$，且超时逐层递减（总预算 → 单次尝试 → 连接），每次退避前检查剩余预算。$d_0 = 0.05$、$d_{\max} = 2$、$A = 4$ 时基准退避合计只有 0.35 s、full jitter 期望 0.175 s（本机实测 0.205 s，是三次退避的实抽之和），但单次尝试超时 5 s 意味着最坏 20.35 s：退避只占 1.7%，deadline 是被尝试超时拖爆的。成功率口径：单次失败率 0.3、允许 4 次时整次成功率 $1 - 0.3^4 = 99.19\%$，期望尝试 $1/0.7 = 1.4286$ 次。剩余预算不够「退避 + 一次尝试」时，正确动作是进 `dead_lettered` 并带原因（本机实测终态即 `dead_lettered`）。重试要有次数与总时限两个上限，一轮结算后只重试失败项。

抖动不是可选项：无抖动时所有 worker 在同一失败时刻用同一公式算出同一个 $d_n$，同一时刻再撞向服务端。本机口径（100 个任务同时失败、$d_1 = 0.05$ s、2000 轮均值）：首轮重试时间的标准差 0 / 0.0072 / 0.0144（无 / equal / full），5 ms 窗口内首轮重试峰值 100 / 47.7 / 27.7，与理论值 $d/\sqrt{12} = 0.0144$、$d/(2\sqrt{12}) = 0.0072$ 一致；AWS 的 OCC 模拟口径（100 个竞争客户端、网络延迟均值 10 ms 方差 4 ms）是加抖动后调用次数减少一半以上、完成时间显著改善，Equal Jitter 略差于 Full Jitter。调度器自己最常制造惊群：定时任务整点触发、worker 在同一毫秒拉取——触发时刻要加 splay、拉取要加随机退避，否则「解决惊群」的组件本身就是雪崩源头。

### 7. 分布式四机制与可观测闭环

① **原子领取**：Redis 单条 `EVAL`（单键串行执行）或 DB 的 `SELECT … FOR UPDATE SKIP LOCKED`。本机口径（16 线程 × 20 次请求、全局额度 100、注入 0.1 ms 往返）：原子路径放行 100 次、超出 0；先 `GET` 再 `SET` 放行 320 次、超出 220（[[coding-07]] 完全一致：100/0 与 320/+220）。② **租约与心跳**：worker 领取带 TTL，进程死亡后靠租约过期重新入队；本机（TTL 100 ms、任务耗时 300 ms）不续租时任务被执行 2 次，每 30 ms 心跳续租后 1 次——租约的三块代价（粒度漏发、需求不均、进程死亡）要主动说。③ **幂等与至少一次**：超时无法判断对方是否已处理，`leased` 就是这件事的表达，所以每个任务带幂等键、写操作幂等消费（同一任务投递两次：无幂等键副作用 2 次、有幂等键 1 次）；取消只影响调用方的 Future，在途执行收不回来，副作用走补偿；错误隔离不能靠 `TaskGroup`（本机 5 个子任务 1 个失败，TaskGroup 完成 0 个，独立 Future 完成 4 个）。④ **可观测与闭环**：调度延迟（enqueue→start）、队列深度、在途数、重试率、各终态计数、P99 任务时长都要进指标（[[evaluation-07]]）；本机 200 任务跑批的调度延迟 p50/p99 是 24.6/47.1 ms、任务时长 p50/p99 是 1.26/12.18 ms、队列峰值 200、重试率 0.10。终止与预算口径参考 [[agents-09]]：模型自报完成不可单独采信，预算耗尽时返回「部分结果 + 原因 + 可续跑」而不是继续重试。限流与重试是一个闭环：退避参数必须和服务端令牌桶对齐（共享速率的桶 + 突发额度，RFC 2697 的思维），否则「重试预算」只是自我安慰。

## 数值与代码验证

下面两段代码是本机实跑的调度器核心（`.work/lead/anthropic03_block.py` 的第 1–78 行与第 82–118 行，与文件逐字一致），仅标准库，Python 3.11.0 与 3.10.12 都跑过；完整跑批在 `.work/lead/anthropic03_sched.py`，分布式三项在 `.work/lead/anthropic03_dist.py`。

```python
"""anthropic-03 调度器核心（仅标准库）：准入 → 选择 → 重试 → 终结。"""
import asyncio
import heapq
import itertools
import random
import time

QUEUED, LEASED, RETRY = "queued", "leased", "retry_scheduled"
SUCCEEDED, FAILED, DEAD = "succeeded", "failed", "dead_lettered"
TERMINAL = {SUCCEEDED, FAILED, DEAD}


class QueueFull(Exception): pass          # raise 背压策略的拒绝信号
class Retryable(Exception): pass          # 429/5xx/超时：可重试
class Permanent(Exception): pass          # 4xx 参数错误：重试一百次还是同样的错误


class Scheduler:
    """priority 数值越小越优先；就绪堆键 = (priority, run_at, seq, task)。"""

    def __init__(self, run, *, max_inflight=4, queue_limit=None, on_full="raise",
                 max_attempts=3, d0=0.05, dmax=2.0, aging=0.02, max_wait=0.05,
                 attempt_timeout=1.0, rng=None):
        self.run, self.rng = run, rng or random.Random(0)
        self.max_inflight, self.queue_limit, self.on_full = max_inflight, queue_limit, on_full
        self.max_attempts, self.d0, self.dmax = max_attempts, d0, dmax
        self.aging, self.max_wait = aging, max_wait
        self.attempt_timeout = attempt_timeout
        self.ready, self.delayed = [], []              # 两个堆：就绪 / 延迟
        self.seq = itertools.count()                   # 单调递增，唯一的平局键
        self.sem = asyncio.Semaphore(max_inflight)     # 闸门 2：在途槽位
        self.queued, self.inflight, self.peak = 0, 0, 0
        self.settle = {SUCCEEDED: 0, FAILED: 0, DEAD: 0}    # 终态只在这里 +1
        self.submitted, self.retries, self._closing = 0, 0, False

    def _key(self, t):                                 # seq 唯一 ⇒ 永远比不到任务对象
        return (t["priority"], t["run_at"], t["seq"], t)

    async def submit(self, tid, *, priority=0, delay=None, run_at=None, deadline=None,
                     idempotency_key=None, max_attempts=None):
        if self.queue_limit is not None and self.queued >= self.queue_limit:    # 闸门 1
            if self.on_full == "raise":
                raise QueueFull(f"队列已满（{self.queue_limit}）")
            while self.queued >= self.queue_limit:     # block：等消费者腾出位置
                await asyncio.sleep(0.0002)
        now = time.monotonic()
        t = {"tid": tid, "priority": priority, "seq": next(self.seq), "attempts": 0,
             "state": QUEUED, "submit_at": now, "start_at": None, "done_at": None,
             "run_at": run_at if run_at is not None else now + (delay or 0.0),
             "deadline": deadline, "idem": idempotency_key or tid,
             "max_attempts": max_attempts or self.max_attempts}
        heapq.heappush(self.delayed if t["run_at"] > now else self.ready, self._key(t))
        self.queued += 1
        self.submitted += 1
        return t

    def _promote(self, limit=64):
        """延迟堆唯一的剪枝：堆顶未到期 ⇒ 其余全部未到期；到期回收切有界批次。"""
        now, moved = time.monotonic(), 0
        while self.delayed and self.delayed[0][1] <= now and moved < limit:
            *_, t = heapq.heappop(self.delayed)
            heapq.heappush(self.ready, self._key(t))
            moved += 1
        return moved

    def _select(self):
        self._promote()
        if not self.ready:
            return None
        now = time.monotonic()
        oldest = min(self.ready, key=lambda x: x[1])
        if now - oldest[1] >= self.max_wait:           # 等待上限：硬保证，选等最久的
            chosen = oldest
        else:                                          # 老化：等待折算成有效优先级
            chosen = min(self.ready, key=lambda x: x[0] - (now - x[1]) / self.aging)
        self.ready.remove(chosen)
        heapq.heapify(self.ready)                      # O(n)：生产上换分层桶 + 定期重建
        return chosen[3]
```

```python
    async def _run_one(self, t):
        while True:
            t["attempts"] += 1
            t["state"] = LEASED
            t["start_at"] = t["start_at"] or time.monotonic()     # 调度延迟从这里算
            left = None if t["deadline"] is None else t["deadline"] - time.monotonic()
            async with self.sem:                       # 只圈在途数，不圈队列长度
                self.inflight += 1
                self.peak = max(self.peak, self.inflight)
                try:
                    await asyncio.wait_for(
                        self.run(t),
                        self.attempt_timeout if left is None else min(self.attempt_timeout, left))
                    err = None
                except Exception as exc:               # 超时与 429/5xx 都在这里分类
                    err = exc
                finally:
                    self.inflight -= 1
            if err is None:
                return self._settle(t, SUCCEEDED)
            if isinstance(err, Permanent) or t["attempts"] >= t["max_attempts"]:
                return self._settle(t, FAILED if isinstance(err, Permanent) else DEAD)
            t["state"] = RETRY
            self.retries += 1
            base = min(self.dmax, self.d0 * 2 ** (t["attempts"] - 1))
            wait = self.rng.uniform(0, base)            # full jitter：不许算出同一个等待
            if t["deadline"] is not None and time.monotonic() + wait + self.attempt_timeout > t["deadline"]:
                return self._settle(t, DEAD)            # 退避会吃掉剩余预算：放弃，别拖爆 deadline
            await asyncio.sleep(wait)                   # 睡在信号量外，不吃并发额度

    def _settle(self, t, state):
        assert t["state"] not in TERMINAL, f"{t['tid']} 重复结算"
        t["state"], t["done_at"] = state, time.monotonic()
        self.settle[state] += 1

    def assert_conservation(self):
        assert sum(self.settle.values()) == self.submitted, "终态结算次数 ≠ 提交数"
```

## 常见追问

- **追问**：为什么不像 cron 那样每秒扫一遍，或者干脆用现成的调度框架？
  - 要点：先说结论再给证据。扫全表是 $O(n)$/tick，延迟堆只看堆顶是 $O(1)$：20 万条 × 100 tick 是 319 ms 对 3.3 ms（98 倍）。框架的问题不是不能用，而是它把准入、选择、重试、终结四件事打包，你无法按业务分别调参；Anthropic 的取向是先用最简单可控的方案，确有收益再增加复杂度。
- **追问**：任务堆积到队列上限时，拒绝还是阻塞？
  - 要点：拒绝保住尾延迟、把降级责任交回上游（`QueueFull` + `Retry-After`），阻塞保住吞吐但把排队延迟转嫁给调用方：本机 40 个任务、队列 4、槽位 2 时是「接纳 4/拒 36，103 ms」对「全接纳 1007 ms（下限 1000 ms）」。生产上按优先级分流：可等待的批量流量阻塞，交互式流量拒绝并降级。
- **追问**：一个任务失败会不会影响同批其他任务？取消呢？
  - 要点：不能。`TaskGroup` 的语义是「第一个非 `CancelledError` 的失败取消组内其余任务」，本机 5 个子任务 1 个失败时它完成 0 个，独立 Future 完成 4 个（[[coding-08]]）。每个任务一个独立句柄、终态只结算一次；取消只影响调用方的 Future，在途执行收不回来，副作用要靠幂等键或补偿。
- **追问**：定时任务为什么不能只写 `run_at`？
  - 要点：一次性的 `run_at` 与周期任务的下一跳 `next_run` 是两种语义。读命中续期式的滑动 TTL 会让索引无界膨胀（[[coding-06]] 实测 1000 个键读 100 万次把堆撑到 1,001,000 条约 95 MiB）；周期任务要在结算时算下一跳并覆盖旧的 `run_at`，同时给触发时刻加 splay，避免整点惊群。
- **追问**：多实例部署时最容易错在哪？
  - 要点：三处。领取不原子（先 `GET` 再 `SET`：额度 100 却放行 320 次）；到期判定用了实例本地时钟（时钟差 1 ms 就放行 409 次而上限 110）；把超时当失败直接重放（超时的正确语义是结果未知，先按幂等键对账，且租约要带 TTL 与心跳）。可观测上把调度延迟、队列深度、在途数、重试率、终态计数与 P99 任务时长一起上报，否则故障时无法区分「积压」与「下游慢」（[[evaluation-07]]）。
