# Harvey 面试题库

这一家的题有一个统一的前提：**交付物是法律工作产品，而它的错误会变成错误的法律意见。**
所以**"格式"与"召回"这两件在别处是工程细节的事，在这里是合规问题。**

**第一件事是"文档结构决定一切"。**
**按字符数切会把一个条款切成两半，而半个条款可能语义反转**；
**定义在第 8 页、使用在第 140 页，相距 132 页、约 66,000 token，而两者词面交集只有 4 个词（Jaccard 0.167）**——
**所以"按相似度检索"在原理上就解决不了这个问题**；
**而 Word 会把一个 95 字符的段落切成 5 个 run，所以"直接替换文本"会破坏 XML。**
**这一家的技术难点几乎都不在模型上，而在文档的表示上。**

**第二件事是"成本结构与直觉相反"。**
**90,000 个格子的 token 成本只有 \$405**，**而人工复核是 450 小时、约 \$45,000——占全成本的 94%**；
**所以在 5,000 份文档的规模上，"优化推理"是最后一位的杠杆**，
**第一位是"降低复核率"**（它同时省钱与省时间）。

**第三件事是"漏报与误报不对称"。**
**漏报的成本约是误报的 20 倍**（因为前者会变成错误的法律意见），
**所以检索场景的阈值要偏向"宁可误报"**——
**而修订场景恰恰相反（精确率优先，因为误改一处会让律师核对全部）。**
**同一家公司里两种相反的取舍，判据是"下游后果"。**

准备这一家时，建议把**"条款边界"**、**"字符偏移"**、**"分母口径"**这三条练熟。
它们分别解释了"怎么切"、"怎么引用回原文"、"怎么报一个率"。

## 准备建议

1. **先建立"条款边界"的直觉**：**半个条款可能语义反转**（01）。**这一条决定了后面所有设计——切分、检索、修订都建立在"条款是原子"这个前提上。**
2. **02 与 03 是"检索的两端"**：**02 讲"检索在原理上失效的场景"、03 讲"什么时候干脆不检索"**。**合起来看才知道检索的边界在哪。**
3. **04 的 run 切分值得单独记**：**95 字符 → 5 个 run**。**这是一个"看起来是文本问题、实际是 XML 问题"的典型**，也解释了为什么"直接替换"会坏。
4. **05 与 10 共享同一套数字**：**90,000 格、1.35 亿 token、\$405、450 小时**。**05 讲架构怎么定、10 讲成本怎么算——两者的结论都是"人工才是瓶颈"。**
5. **07 的分母口径是"报数纪律"**：**同一批数据按 claim 是 15.0%、按 answer 是 35.0%**。**任何对外报的率都必须写清分母。**
6. **08 的"提示无效"是一个通用教训**：**模型无法知道上下文里没有的事实**。**凡是"要求模型注意某个外部事实"的提示，都要先问"那个事实在上下文里吗"。**
7. **09 的缓存问题最容易被漏**：**KV 前缀缓存按 token 序列做键，所以命中就是泄露**。**任何"共享缓存"的设计都要先问"共享边界与权限边界一致吗"。**
8. **11 的"先验证前提"是最实用的排查习惯**：**40% 的反馈里前提不成立**。**这一条不只适用于法律场景。**
