## 一句话答案

> **不要跟客户的结论争论，把结论变成可检验的假设。** 具体七步：
> ① **先问动机**：客户真正想要的是什么？——**(a) 成本**、**(b) 数据控制/合规**、**(c) 差异化质量**、**(d) 供应商风险**、**(e) 「我们也要有自己的模型」的组织诉求**。**五种动机对应完全不同的方案**，而且 (b)(e) 用 RAG 也能满足（自托管 + 私有索引）；
> ② **把「想要自己的模型」翻译成可度量的验收标准**：任务成功率、语气/品牌一致性、响应延迟、**每工单成本**、数据边界、**知识更新时延**（政策变了多久能生效）；
> ③ **设计公平的对照实验（bake-off）**：同一套**留出评测集**（从真实工单按时间切分）跑三条臂——**prompt 基线 / RAG / 在工单上 LoRA**；关键纪律：**评测集里的工单绝不能进训练集**（否则 LoRA 的分数是假的）；
> ④ **预注册判据**（写下来、双方签字）：例如"若 LoRA 在任务成功率上比 RAG 高 **>5 个百分点**、且每工单成本更低，就上 LoRA；否则上 RAG，LoRA 作为可选增强"；
> ⑤ **算清总拥有成本**：训练 + 标注 + **服务** + **刷新**（见下）——**这一步往往能改变结论**；
> ⑥ **尊重非技术约束**：若合规要求数据不出域，**RAG 与 LoRA 都可以自托管**；若客户需要「专属」的组织感受，**每租户一个 LoRA 适配器**就能满足（共享基座、感知上「有自己的模型」），**知识仍走 RAG**——这是最常见的双赢解；
> ⑦ **承认客户可能是对的**：工单场景里 LoRA 确实可能赢——**品牌语气统一、严格结构化字段输出、高并发下的单位成本、领域术语**，以及**检索质量不可靠**（工单库很脏、没有结构）时。
> **两个决定性论据（本轮的量化部分）**：
> - **知识会漂移**：工单里的大量内容是**会变的政策与产品知识**——RAG 更新索引是**分钟级、几乎零成本**，而微调需要**周期性重训**（标注 + 训练 + 评测 + 发布），**每次都是固定成本**；
> - **评测污染**：如果拿「用来微调的同一批工单」做评测，**测出来的提升有相当一部分是记忆而非能力**（见下文量化）。
> 一句话判据：**「我们要自己的模型」不是技术需求，而是需要被翻译的需求**——翻译成判据之后，让数据说话。

## 面试官在考什么

- **是否避免正面对抗**：能否不在「RAG vs 微调」上辩论，而是**把争论转化为可测量的实验**（这是本题最核心的软技能 + 硬技能结合点）。
- **动机拆解**：能否把「想要自己的模型」拆成五种动机，并指出哪些用 RAG/自托管也能满足。
- **实验设计的严谨性**：留出集、时间切分、**训练/评测不重叠**、配对比较、样本量——缺一项，结论就不可信。
- **预注册**：能否在实验前把判据写下来（防止事后解释数据）。
- **TCO 的完整性**：训练成本只是小头，**服务成本 + 刷新成本 + 标注成本**才是大头；能否算出**知识漂移带来的周期性重训**这一项。
- **非技术约束的处理**：合规、数据边界、组织诉求——能否给出既满足约束又不牺牲技术合理性的方案（LoRA 适配器 + RAG）。
- **诚实与可更新**：能否明确列出「如果出现这些证据，我就改判」（并且真的愿意改）。
- **交付视角**：能否给出**下一步与时间盒**（例如两周做完 bake-off），而不是无限期讨论。

**常见错误答案**

- 用技术论证压客户（「RAG 是业界最佳实践」）——忽略动机与非技术约束。
- 直接照做（放弃专业判断，做出必然失败的项目）。
- 用**同一批工单**既训练又评测（结论虚高，必然翻车）。
- 只比质量不比成本/延迟/维护。
- 不做预注册，事后挑对自己有利的指标。
- 忽略「知识更新时延」这个客户真正在意的运维指标。
- 把「客户坚持」当成非黑即白（要么全 RAG 要么全微调，不给组合方案）。

## 原理与推导

### 1. 动机 → 方案映射

| 客户说的 | 真实动机 | RAG 能否满足 | 微调是否必要 |
| --- | --- | --- | --- |
| 「我们想要自己的模型」 | 组织诉求/控制感 | ✅（自托管 + 私有索引） | 不必，但**每租户适配器**能满足感知 |
| 「数据不能出我们的边界」 | 合规 | ✅（自托管 RAG 同样不出域） | 不必 |
| 「回答要贴合我们的政策」 | 知识 | ✅（**且更新更快**） | 不必（微调注入知识效果差） |
| 「语气要像我们的客服」 | 行为/风格 | ❌（RAG 改不了语气） | **需要** |
| 「要严格输出这些字段」 | 格式 | ⚠️（约束解码可部分解决） | 通常需要 |
| 「单工单成本要降下来」 | 成本 | 部分（缓存/路由/精简 prompt） | 可能（缩短 prompt + 小模型） |

**读法**：**只有「行为/格式/成本」这三类动机才真正指向微调**；「知识/合规/控制」用 RAG（可自托管）就能满足——**这是说服客户的关键论据，因为它没有否定客户的诉求**。

### 2. 评测污染：为什么「用同一批工单」会骗人

设评测集有 $m$ 条工单，其中被用于微调的比例为 $\rho$，模型对「见过」的样本通过率 $p_{\text{mem}}\approx0.95$，真实泛化能力 $p_{\text{real}}$：

$$\hat p=\rho\,p_{\text{mem}}+(1-\rho)\,p_{\text{real}}$$

**例**：$p_{\text{real}}=0.55$、$\rho=0.5$（一半评测集进过训练）→ 表观 **0.75**，虚高 **20 个百分点**——足以让「LoRA 完胜 RAG」的错误结论成立。

**对策**：**时间切分**（用训练数据截止之后的新工单做评测）+ 去重检测 + 明确记录训练集来源。

### 3. TCO：训练只是小头，刷新才是大头

$$\text{TCO}_{12m}=\underbrace{C_{\text{train}}}_{\text{一次性}}+\underbrace{(C_{\text{label}}+C_{\text{train}}+C_{\text{eval}}+C_{\text{release}})\times R}_{\text{周期性刷新}}+\underbrace{C_{\text{serve}}\times12}_{\text{服务}}$$

其中 $R$ = 一年内的刷新次数，取决于**知识漂移速度**：

$$R\approx\frac{\text{每年实质性政策/产品变更次数}}{\text{可接受的知识陈旧窗口}}$$

**例**：每季度有一次政策大改（4 次/年）、可接受陈旧窗口 1 个月 → 需要 **12 次/年**（若每次都重训）。而 RAG 侧的对应操作只是**增量索引更新**（分钟级、近似零边际成本）。

**这就是本题最有说服力的算术**：**微调的固定成本会被「知识更新频率」放大**。

### 4. 三条臂的公平对照实验

| 要素 | 要求 |
| --- | --- |
| 评测集 | 从真实工单**按时间切分**留出；覆盖主要意图与长尾；含红线项（幻觉、错误政策） |
| 训练集（LoRA 臂） | 与评测集**零重叠**；注意 PII 脱敏 |
| 基线（prompt 臂） | 同一模型 + 精心设计的 prompt（few-shot + 结构化约束）——**必须是最强的基线**，否则胜之不武 |
| RAG 臂 | 同一模型 + 检索（索引来自政策文档与历史工单的知识化整理） |
| 统计 | **配对比较**（同一工单跑三臂）→ 样本量更省；报置信区间而非单点 |
| 成本 | 每臂都记：训练/标注一次性 + 每工单推理成本 + 延迟 |
| 判据 | **实验前**写定（例如「高 5 个点且成本更低」），并约定复评日期 |

**样本量口径**（配对设计，检出差异 $\delta$）：$n\approx\frac{(z_{1-\alpha/2}+z_{\text{power}})^2\sigma_d^2}{\delta^2}$；若配对差值标准差 $\sigma_d=0.3$、$\delta=0.05$ → **约 283 对**；$\delta=0.03$ → 约 785 对（串 [[anthropic-27]] 与 [[cognition-07]] 的样本量口径）。

### 5. 组合方案（最常见的落地形态）

```
知识（政策、产品、历史处理方式）→ RAG（索引可增量更新、可引用、可鉴权）
行为（语气、格式、术语、拒答边界）→ LoRA 适配器（每租户一个，共享基座）
```

**好处**：① 满足「我们有自己模型」的组织诉求；② 知识更新不必重训；③ 服务成本可控（共享基座）；④ 质量与合规可分别度量。**代价**：多一套适配器运维（版本管理、路由、A/B）。

### 6. 如果客户仍然坚持微调（而数据表明 RAG 更优）

处理顺序：① **确认判据是否被曲解**（是否漏了成本/维护）；② 用**小范围、可回滚的试点**满足客户的探索欲（时间盒 4–6 周，明确「不达标就回退」）；③ **合同化风险**（明确谁承担刷新成本与质量责任）；④ **记录分歧**（把技术建议与最终决定都写进文档）——**专业性的体现是「说清楚 + 记录下来」，而不是「拒绝执行」。**

```python
def contaminated(p_real: float, overlap: float, p_mem: float = 0.95) -> Dict[str, float]:

# ---------- 2) TCO：刷新成本是微调的真大头 ----------
@dataclass
class TCO:
    name: str
    one_time: float                 # 一次性（标注 + 首次训练 + 评测搭建）
    refresh_cost: float = 0.0       # 每次刷新（重训 + 重新评测 + 发布）
    refreshes_per_year: float = 0.0
    serve_month: float = 0.0        # 服务/月
    def total(self, months: int = 12) -> Dict[str, float]:
        refresh = self.refresh_cost * self.refreshes_per_year * (months / 12)
        serve = self.serve_month * months
        return {"一次性": self.one_time, "刷新": refresh, "服务": serve,
                "合计": self.one_time + refresh + serve}

      f"（当前 $90,000，需降 {1-need_one_time/90_000:.0%}）")
print("  （b）若保持 12 次/年刷新，LoRA 需要每月服务成本比 RAG 低多少才追平？")
need_serve = (LORA12 - RAG12) / 12
print(f"      需要每月多省 ${need_serve:,.0f} —— 即服务成本要从 $12,000/月 降到 "
      f"${12_000-need_serve:,.0f}/月（{'不可行' if need_serve > 5_000 else '可行'}）")
print("  （c）若两者服务成本相同，LoRA 需要多少次/年以下的刷新？")
for R in (0, 2, 4, 12):
    lora_r = TCO("LoRA", one_time=90_000, refresh_cost=18_000, refreshes_per_year=R,
                 serve_month=11_000).total()["合计"]
    rag_r = TCO("RAG", one_time=60_000, refresh_cost=2_000, refreshes_per_year=R,
                serve_month=11_000).total()["合计"]
    print(f"      年刷新 {R:>2} 次：LoRA ${lora_r:,.0f} vs RAG ${rag_r:,.0f} -> "
          f"{'LoRA 更省' if lora_r < rag_r else 'RAG 更省'}")
print("  读法：**在本例参数下，无论刷新多少次 RAG 都更省** —— 因为 LoRA 的劣势同时来自")
print("        ① 更高的一次性成本（标注 + 训练 + 评测搭建）与 ② 更高的服务成本（专用/适配器运维）；")
print("        **要追平，必须同时满足「知识几乎不变」且「服务成本显著更低」两个条件** —— 而工单场景两条都不满足")

def paired_n(delta: float, sd_diff: float = 0.3, alpha: float = 0.05,
             power: float = 0.8) -> int:
    return math.ceil((z(1 - alpha / 2) + z(power)) ** 2 * sd_diff ** 2 / delta ** 2)
print("\n④ 配对对照实验的样本量（同一工单跑三臂，配对差值 sd=0.3）")
print(f"  {'要检出的差异':>10} {'需要配对数':>10} {'含义':<24}")
for d in (0.10, 0.05, 0.03, 0.01):
    n = paired_n(d)
    note = "小试验即可" if n <= 300 else ("需要上千条" if n <= 2000 else "不现实（改判据）")
    print(f"  {d:>10.0%} {n:>10,} {note:<24}")
print("  读法：**检出 5 个百分点的差异只需约 283 对**（同一条工单跑三臂）——两周内可完成；")
print("        但想证明「高 1 个点」需要数万对，工程上不可行，所以要**在实验前把判据设在可检出的量级**")

# ---------- 5) 预注册判据：把结论提前写下来 ----------
@dataclass
class Criterion:
    name: str
    threshold: float
    weight: float
def decide(results: Dict[str, float], criteria: List[Criterion]) -> Tuple[str, str]:
    """results 里给出各臂在各判据上的差值（LoRA - RAG）"""
    wins = sum(c.weight for c in criteria if results.get(c.name, 0) >= c.threshold)
    total = sum(c.weight for c in criteria)
    ratio = wins / total
    if ratio >= 0.6:
        verdict = "LoRA（微调为主）"
    elif ratio >= 0.2:
        verdict = "组合（知识走 RAG、语气/格式走 LoRA 适配器）"
    else:
        verdict = "RAG"
    return verdict, f"满足 {wins:.1f}/{total:.1f} 权重的判据"
CRIT = [Criterion("任务成功率差值", 0.05, 3.0),
        Criterion("每工单成本差值(反向)", 0.0, 2.0),
        Criterion("语气一致性差值", 0.10, 2.0),
        Criterion("知识更新时延(反向)", 0.0, 1.0)]
print("\n⑤ 预注册判据的判定（示例结果：LoRA 在语气上赢、在成功率与成本上不赢）")
CASES = [
    ("LoRA 全面领先", {"任务成功率差值": 0.06, "每工单成本差值(反向)": 0.01,
                    "语气一致性差值": 0.12, "知识更新时延(反向)": -0.5}),
    ("LoRA 只在语气上赢", {"任务成功率差值": 0.01, "每工单成本差值(反向)": -0.01,
                       "语气一致性差值": 0.14, "知识更新时延(反向)": -0.8}),
    ("RAG 全面领先", {"任务成功率差值": -0.03, "每工单成本差值(反向)": -0.02,
                    "语气一致性差值": 0.02, "知识更新时延(反向)": -0.9}),
]
for label, res in CASES:
    verdict, why = decide(res, CRIT)
    print(f"  {label:<20} -> **{verdict}**（{why}）")
print("  读法：**「LoRA 只在语气上赢」这一行就是最常见的真实结果**，它直接导出组合方案：")
print("        知识走 RAG、语气走 LoRA 适配器 —— 既满足客户诉求，又不背上重训知识库的成本")
```

预期输出要点（实跑）：① 污染模拟显示**一半评测集进过训练就虚高 20 个百分点**（55% → 75%），足以让结论反转，所以必须**按时间切分评测集**；② 12 个月 TCO 显示 **LoRA 的重训成本被刷新频率放大**（单次 \$18k × 12 次/年 = **\$216k/年**）：RAG \$216,000 vs LoRA **\$450,000**（2.08×），而这部分**不带来质量优势**；③ 追平条件的分析比「敏感性曲线」更有说服力：在本例参数下**无论刷新多少次 RAG 都更省**——LoRA 要追平需要**同时满足**「知识几乎不变（一次性成本压到 ≤\$48,000，即降 47%）」**且**「每月服务成本比 RAG 低 \$19,500（不可行）」，而工单场景两条都不满足；④ 配对样本量表显示**检出 5 个百分点只需约 283 对**（两周可完成），而「证明高 1 个点」需要数万对（不可行，所以判据要设在可检出的量级）；⑤ 预注册判据的判定把「LoRA 只在语气上赢」这一常见真实结果**直接导出为组合方案**。

## 常见追问

- **追问**：客户是 CTO，说「就要微调」，怎么办？
  - 要点：**先给动机留出空间**（可能是组织/预算/战略诉求，而不是技术判断）。做法：① 把 bake-off 的时间盒压到**两周**（成本很低，谁都不会反对）；② **把判据提前写下来**（包括「若 RAG 胜出，微调作为第二阶段增强」）；③ 若仍要微调，**用小范围试点 + 明确回退条件**，并**书面记录技术建议与最终决定**。**专业不等于说赢，而是让决策有依据、风险有归属。**
- **追问**：工单数据有 PII，能用来训练吗？
  - 要点：三层——① **脱敏**（正则 + NER 双重，覆盖姓名/电话/邮箱/身份证/卡号）；② **合法性**（客户是否授权用于训练？很多合同明确禁止）；③ **隔离**（训练环境与生产隔离、访问审计、留存期限）。**若任一层不满足，就不能训。**
- **追问**：如果检索质量很差（工单库很脏）呢？
  - 要点：这是**真正支持微调的场景之一**。但先问：能不能**把知识整理成结构化文档**（FAQ/政策库）再做 RAG？整理成本通常低于持续重训成本。**若确实无法整理（知识只存在于非结构化对话里），微调或「检索 + 微调」组合才合理。**
- **追问**：怎么判断「知识更新时延」这个指标的权重？
  - 要点：问客户**业务后果**——政策变更后多久必须生效？如果答案是「当天」，那 RAG 是唯一可行方案（索引更新分钟级）；如果答案是「下个季度」，微调的重训窗口也能接受。**把技术指标翻译成业务后果，权重自然就出来了。**
- **追问**：bake-off 的评测集怎么建才不被客户质疑？
  - 要点：① **抽样规则写下来**（按时间、按意图分层、按语种）；② **标注指南公开**（什么算通过）；③ **双人标注 + 一致性报告**；④ **留出集不参与任何调参**；⑤ **红线项单独列出**（幻觉、错误政策）。**让客户参与标注与判据制定**，结论才容易被接受。
- **追问**：如果最后上了 LoRA，怎么避免「知识过时」？
  - 要点：**不要让 LoRA 承担知识**——把知识留在 RAG 索引里，LoRA 只管语气/格式；这样知识更新仍走索引（分钟级）。若 LoRA 里混入了知识，就必须**把「重训周期」写进 SLA 与预算**，并监控「政策变更 → 重训上线」的实际时延。
