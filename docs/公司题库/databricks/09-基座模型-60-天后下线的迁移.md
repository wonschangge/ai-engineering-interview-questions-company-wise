## 一句话答案

> 这题的**真正问题是后半句**：「为此事先必须具备哪些条件？」——因为**60 天足够做迁移，但前提是那些条件在四个月前就建好了**。所以答案分两段：
> **A. 事先必须具备的七项（缺一项，60 天就会变成一次赌博）**
> ① **模型抽象层**：模型名不硬编码在业务代码/提示里，走统一网关 + 配置化路由（含超时、重试、限流、成本计量）；**有「模型能力矩阵」**（上下文长度、结构化输出、工具调用、多模态、缓存支持）；
> ② **固定评测集 + 回归门禁**：任务级判据 + 红线（否则「没有质量回退」**无法证明**）；且评测集**不参与任何调参**；
> ③ **可回放的真实流量样本**：覆盖长尾与对抗输入（用于 shadow 对比，而不只是跑公开榜单）；
> ④ **版本化与灰度/回滚能力**：**prompt / 模型 / 工具 schema / 检索索引**四者都可独立版本化与回滚（「换模型」往往要连带换 prompt，两者必须能一起灰度、一起回退）；
> ⑤ **成本与延迟基线**：每请求成本、p50/p95 延迟——否则新模型可能「质量没退但账单翻倍/延迟超标」，而这**同样是质量回退**；
> ⑥ **契约测试**：结构化输出 schema 合法性、工具调用格式、拒答/安全行为、上下文长度边界——**这些是最容易在换模型时静默破坏的地方**；
> ⑦ **配对评测能力**：同一批请求同时跑新旧模型（配对比较比独立抽样省样本，见下）。
> **B. 60 天迁移计划（带 gate）**
> | 阶段 | 天数 | 动作 | Gate |
> | --- | --- | --- | --- |
> | 盘点与冻结 | D0–5 | 影响面盘点（哪些调用点、哪些模型特定技巧）、冻结非必要变更、校准评测集与基线 | 评测集可跑 + 基线记录 |
> | 候选与归因 | D5–15 | 2–3 个候选模型跑回归，**逐项/逐群差异归因** | 至少一个候选在红线项上不劣 |
> | 适配 | D15–30 | prompt 迁移、工具 schema 对齐、契约测试；必要时用 LoRA 补偿行为差异 | 契约测试全绿 |
> | Shadow + Canary | D30–45 | 镜像真实流量比对；按**样本量**决定 canary 时长与比例 | 分群无回退 + 成本/延迟达标 |
> | 放量 | D45–55 | 10% → 50% → 100%，保留回滚开关 | 连续观察窗口内指标稳定 |
> | 下线与复盘 | D55–60 | 关闭旧模型、清理兼容代码、复盘并更新能力矩阵 | 复盘产出改进项 |
> 一句话判据：**「没有评测集，就没有'不造成质量回退'这句话」**——你可以完成迁移，但你无法**知道**自己有没有回退。

## 面试官在考什么

- **是否把重点放在「事先条件」**：题目在问「如何替换」，但真正的考点是「**为什么你需要四个月前就准备好**」。能否先讲条件再讲计划。
- **抽象层与契约**：能否指出**模型名硬编码**与**模型特定 prompt 技巧**是迁移的最大障碍；以及结构化输出/工具调用这类**契约**最容易静默破坏。
- **评测的可用性**：能否区分「跑公开榜单」与「跑自己的任务级评测集」，并说明后者才是判据。
- **分群**：能否坚持**按意图/语言/长度分群报告**——平均不变但某一群崩掉是最典型的迁移事故（串 [[anthropic-27]]）。
- **配对比较与样本量**：能否用「同一批请求跑新旧模型」降低样本需求，并给出「多久能检出多大回退」的估算。
- **成本与延迟也是质量**：能否把 p95 延迟与每请求成本纳入 gate（换模型后 prompt 变长/缓存失效都可能让成本翻倍）。
- **兜底方案**：许可允许时私有部署旧模型、关键路径保留回退、或明确接受降级并调整 SLO 与沟通——能否分层给出。
- **时间盒与决策**：60 天的计划要有 gate 与「什么时候放弃某候选」的判据，而不是「尽力而为」。

**常见错误答案**

- 直接讲「我会用新模型跑一遍测试」（没有评测集、没有分群、没有 gate）。
- 忽略成本与延迟（只比质量）。
- 不做 shadow，直接 canary 到 100%。
- 忽略 prompt 的模型耦合（换模型却不改 prompt，或改了却没有版本化）。
- 没有回滚预案（旧模型下线后发现问题就无路可退）。
- 只报平均指标（分群崩掉看不见）。
- 把 60 天全用在「找最像的模型」上，而不是「建立可验证的迁移流程」。

## 原理与推导

### 1. 为什么「事先条件」决定成败

设迁移的**检出能力**为 $P(\text{检出回退})$，它取决于评测集覆盖度 $c$、样本量 $n$ 与判据灵敏度 $\delta$：

$$P(\text{检出})\uparrow\ \text{当}\ c\uparrow,\ n\uparrow,\ \delta\ \text{更贴近业务后果}$$

**四个月前没建评测集 → 今天 $c\approx0$ → 迁移只能是「上线后才知道」**。这就是题目的要害：**60 天买不到评测集覆盖度**（它需要历史流量与标注积累）。

### 2. 配对比较：为什么它能省样本

对同一批请求分别用旧模型 $A$ 与新模型 $B$ 跑，得到**配对差值** $d_i$。检验「无回退」用的是差值的标准差 $\sigma_d$，而非各自方差：

$$n\approx\frac{(z_{1-\alpha/2}+z_{\text{power}})^2\sigma_d^2}{\delta^2}$$

**因为同一个请求在两个模型上的难度是相关的**，$\sigma_d\ll\sigma$，所以配对设计常能把所需样本减少 **2–5 倍**。代价是要能**回放同一批请求**——这正是「可回放流量样本」这条事先条件的价值。

### 3. 检测滞后的代价（为什么 shadow 比 canary 便宜）

设回退影响 $q$ 比例请求、每个受影响请求的损失为 $\ell$、日请求量为 $V$，若在**上线后** $D$ 天才检出：

$$\text{回退代价}\approx q\cdot V\cdot\ell\cdot D$$

而在 shadow/canary 阶段检出的代价只是**评测与观察成本**（人力 + 影子流量成本）。**例**：$q=5\%$、$V=10^5$/日、$\ell=\$2$、$D=3$ 天 → **\$30,000**；而一次完整的 shadow + canary（两周、5% 流量）成本通常**低一个数量级**。

**结论**：**把检出点前移是最便宜的保险**——这也是为什么 60 天计划里 D30–45 要留给 shadow/canary。

### 4. 分群：平均指标会骗人

迁移事故的典型形态：**总体成功率不变，但某个分群崩掉**。所以要按**意图/语言/输入长度/工具使用**分群报告，并对每个分群设**非劣性判据**（串 [[anthropic-27]]）：

$$\text{对每个分群 }g:\quad \hat p_B^{(g)}\ge \hat p_A^{(g)}-\delta_g$$

**若某分群样本量不足 → 明确标注「未验证」**，而不是默认通过。

### 5. 契约测试清单（最容易被静默破坏的地方）

| 契约 | 破坏后的表现 | 测试方式 |
| --- | --- | --- |
| 结构化输出 schema | 下游解析失败/字段缺失 | 对 schema 做**批量合法性校验**（含边界输入） |
| 工具调用格式 | 工具选错/参数缺失 | 固定工具场景的**回归用例** |
| 拒答/安全行为 | 该拒的不拒（合规风险） | 红线用例（必须拒答的输入集） |
| 上下文长度边界 | 长输入被截断/报错 | 长度阶梯测试 |
| 缓存命中行为 | 成本突增（缓存失效） | 成本对比（同流量跑两模型） |
| 流式与取消语义 | 首字延迟变化、取消不生效 | 端到端延迟与取消测试 |

### 6. 兜底分层（旧模型下线后才发现问题怎么办）

| 层级 | 手段 | 前提 |
| --- | --- | --- |
| 最优 | **私有部署旧模型**（许可允许） | 有许可 + 有算力 |
| 次优 | **关键路径保留异构路由**（对高风险子集用另一个替代模型） | 多模型抽象层已建 |
| 再次 | **能力降级 + 调整 SLO + 明确告知** | 有沟通与补偿机制 |
| 兜底 | **人工兜底通道**（复杂/高风险请求转人工） | 有人工团队与流程 |
**要点**：这些都**必须事先准备**——旧模型一旦下线，临时准备是来不及的。

```python
def n_independent(delta: float, p: float = 0.8, alpha: float = 0.05,
                  power: float = 0.8) -> int:
    return math.ceil(2 * (z(1 - alpha/2) + z(power)) ** 2 * p * (1 - p) / delta ** 2)
def n_paired(delta: float, sd_diff: float = 0.35, alpha: float = 0.05,

    return math.ceil((z(1 - alpha/2) + z(power)) ** 2 * sd_diff ** 2 / delta ** 2)

@dataclass
class Rollout:
    daily_requests: int = 100_000
    impact_share: float = 0.05          # 回退影响的请求比例
    loss_per_request: float = 2.0       # 每个受影响请求的损失（美元）
    def cost(self, days_at_exposure: float, exposure: float = 1.0) -> Dict[str, float]:
        affected = self.daily_requests * exposure * self.impact_share * days_at_exposure
        return {"受影响请求": affected, "代价($)": affected * self.loss_per_request}

# ---------- 3) 分群非劣性：平均没退，某群崩了 ----------
@dataclass
class Segment:
    name: str
    n: int                     # 该群样本量
    p_old: float               # 旧模型成功率
    p_new: float               # 新模型成功率
    def delta_noninferiority(self, margin: float = 0.03) -> Dict[str, object]:
        delta = self.p_new - self.p_old
        # 配对差值的标准误（用两比例近似，仅作演示）
        se = math.sqrt(max(1e-9, self.p_old*(1-self.p_old)/self.n
                           + self.p_new*(1-self.p_new)/self.n))
        return {"delta": delta, "se": se, "通过": delta >= -margin,
                "样本充足": self.n >= n_paired(margin, sd_diff=0.35)}
SEGS = [
    Segment("短问答", 2_000, 0.88, 0.89),
    Segment("长文档摘要", 800, 0.82, 0.81),
    Segment("工具调用（多步）", 400, 0.75, 0.68),      # ★ 崩了
    Segment("多语言", 150, 0.70, 0.66),                 # ★ 样本不足
]
print("\n③ 分群非劣性检查（margin = 3 个百分点；平均可能完全看不出问题）")
print(f"  {'分群':<18} {'样本':>6} {'旧':>6} {'新':>6} {'差值':>7} {'判定':<16} {'样本充足':>8}")
for s in SEGS:
    d = s.delta_noninferiority()
    verdict = ("通过" if d["通过"] else "**回退**") + ("" if d["样本充足"] else "（样本不足）")
    print(f"  {s.name:<18} {s.n:>6} {s.p_old:>6.2f} {s.p_new:>6.2f} {d['delta']:>+7.2f} "
          f"{verdict:<16} {('是' if d['样本充足'] else '否'):>8}")
avg_old = sum(s.p_old * s.n for s in SEGS) / sum(s.n for s in SEGS)
avg_new = sum(s.p_new * s.n for s in SEGS) / sum(s.n for s in SEGS)
print(f"  加权平均：旧 {avg_old:.3f} -> 新 {avg_new:.3f}（差 {avg_new-avg_old:+.3f}）")
print("  读法：**加权平均只差 0.4 个百分点，但「工具调用」群掉了 7 个点** —— 只看平均就会带着事故上线；")

score = sum(p.readiness for p in PRE) / len(PRE)
print(f"  平均就绪度 {score:.2f}；红线未达标 {len(failed)} 项 -> "
      f"{'迁移不可控（先补红线）' if failed else '可以按 60 天计划推进'}")
print("  读法：**最致命的缺口是评测集（就绪度 0）** —— 没有它就没有「不造成质量回退」这句话；")
print("        而评测集的覆盖度靠历史流量与标注积累，**60 天买不到**，只能现在开始建")

# ---------- 5) 60 天计划的 gate ----------
@dataclass
class Phase:
    name: str
    days: str
    action: str
    gate: str
PLAN = [
    Phase("盘点与冻结", "D0-5", "影响面盘点（调用点/模型特定技巧）、冻结非必要变更、校准评测集与基线",
          "评测集可跑 + 基线记录完整"),
    Phase("候选与归因", "D5-15", "2–3 个候选跑回归，逐项/逐群差异归因", "至少一个候选在红线项上不劣"),
    Phase("适配", "D15-30", "prompt 迁移、工具 schema 对齐、契约测试、必要时 LoRA 补偿", "契约测试全绿"),
    Phase("Shadow + Canary", "D30-45", "镜像真实流量比对；按样本量决定 canary 时长与比例", "分群无回退 + 成本/延迟达标"),
    Phase("放量", "D45-55", "10% → 50% → 100%，保留回滚开关", "连续观察窗口内指标稳定"),
    Phase("下线与复盘", "D55-60", "关闭旧模型、清理兼容代码、更新能力矩阵", "复盘产出改进项"),
]
print("\n⑤ 60 天迁移计划（每阶段都有 gate）")
print(f"  {'阶段':<16} {'天数':>7} {'动作':<44} Gate")
for ph in PLAN:
    print(f"  {ph.name:<16} {ph.days:>7} {ph.action[:42]:<44} {ph.gate}")
print("  读法：**D30–45 留给 shadow + canary 是计划里最关键的一段**（把检出点前移）；")
print("        每一段的 gate 都是「可否进入下一阶段」的判据，而不是进度汇报")
```

预期输出要点（实跑）：① 配对设计把样本需求**降低约 62%**（检出 5 个百分点：1,005 → **385**；3 个百分点：2,791 → **1,069**；1 个百分点：25,117 → **9,615**），前提是能回放同一批请求；② 检测滞后的代价从 shadow 的**近乎为零**（不影响用户）到全量后 3 天才检出的 **\$30,000**——**把检出点前移是最便宜的保险**；③ 分群检查显示**加权平均只差 0.7 个百分点，但「工具调用」群掉了 7 个点、「多语言」掉 4 个点**（只看平均就会带着事故上线），且四个分群的样本量都未达配对所需规模，应标注「未验证」而非默认通过；④ 事先条件就绪度（平均 0.51）显示**5 项红线未达标**，其中最致命的是**任务级评测集（就绪度 0.0）**与契约测试（0.3）——没有评测集就没有「不造成质量回退」这句话；⑤ 60 天计划的每一阶段都有 gate，其中 **D30–45 的 shadow + canary 是关键段**。

## 常见追问

- **追问**：如果四个月前什么都没准备，60 天怎么办？
  - 要点：**降低目标的野心**：① 用**现有日志**快速重建一个「小而准」的评测集（200–500 条真实请求 + 人工标注），先覆盖**高危分群**（工具调用、长文档、多语言）；② 优先做 **shadow**（不需要用户参与）；③ **保留旧模型的最长可用期**（与供应商谈延期/私有部署许可）；④ 对未验证的分群**降低放量比例或加人工审核**。**承认「无法完全证明」并显式管理风险**，比假装有评测更专业。
- **追问**：为什么不能直接把 prompt 抄到新模型上？
  - 要点：prompt 里往往有**模型特定的技巧**（特定的分隔符、few-shot 格式、角色设定、JSON 触发词），换模型后效果会漂移；而且**上下文长度、工具 schema、缓存行为**都可能不同。所以要**把 prompt 也当作待迁移资产**：版本化、逐条回归、必要时重写。
- **追问**：成本翻倍但质量没退，算不算「质量回退」？
  - 要点：**算**。若单位经济性被破坏（例如每次会话成本翻倍、毛利率为负），业务上等同于回退。所以成本与延迟必须进 gate，并与业务方一起定阈值（而不是技术团队自己定）。
- **追问**：怎么处理「新模型在长尾更好、在主流更差」？
  - 要点：**按业务价值加权**而不是按样本量加权——主流场景的绝对量决定整体损失。做法：分层加权评分 + 对高危分群设红线；若权衡后仍不达标，考虑**按分群路由**（主流走旧模型/另一候选，长尾走新模型）。
- **追问**：旧模型下线后才发现问题怎么办？
  - 要点：三层兜底（事先准备）：① 私有部署旧模型（许可允许时）；② **异构路由**（关键路径切到替代模型）；③ **人工兜底**。若都没有，只能**接受降级 + 调整 SLO + 主动沟通**——**这正是「事先条件」的价值所在**。
- **追问**：怎么让供应商变更不再变成事故？
  - 要点：建立**「模型生命周期」流程**：① 能力矩阵与依赖清单（哪些功能依赖模型特定行为）；② **定期（季度）跑迁移演练**（用当前候选模型跑评测集，保持「随时可换」）；③ 与供应商约定**下线预警期**；④ 把「可替换性」作为架构评审的一项指标。
