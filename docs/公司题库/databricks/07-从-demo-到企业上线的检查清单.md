## 一句话答案

> Demo 与生产的差别**不在功能，而在「出事时会发生什么」**。所以检查清单围绕九个维度，每个维度都要有**可验证的产出物**（不是「我们做了」，而是「这是证据」）：
> ① **质量与评测**：从**真实流量**抽样的任务级评测集 + 回归集 + **红线项**；离线指标与线上指标都要；**有明确的放量门禁**（串 [[evaluation-10]]）；
> ② **数据与合规**：PII/敏感数据识别与脱敏、数据驻留、留存期限、访问控制、**是否用于训练**（默认不用于）、审计留痕、对用户的披露；
> ③ **安全**：prompt injection 的分层防御、**工具最小权限**、密钥管理（短期凭证）、出网白名单、沙箱隔离（串 [[safety-01]] 与 [[cognition-08]]）；
> ④ **可靠性与 SLO**：延迟预算（p50/p95）、**错误预算**、超时与重试（**必须幂等**）、**降级路径**（小模型/缓存/转人工）、容量与压测、限流；
> ⑤ **成本控制**：单次请求成本估算、**预算上限与告警**、缓存与模型路由、按租户配额（串 [[databricks-06]] 的成本口径）；
> ⑥ **可观测性**：**端到端 trace**（每一步的输入/输出/耗时/token/成本）、错误分类、用户反馈采集、**可回放调试**、告警与看板；
> ⑦ **变更管理**：prompt/模型/工具/索引**全部版本化**、灰度（shadow → canary → 放量）、**回滚计划并演练过**、特性开关；
> ⑧ **治理与文档**：用例审批与风险分级、人工监督边界、模型卡/系统说明、**事故响应与值班 runbook**、明确负责人；
> ⑨ **发布就绪**：**kill switch（且测试过）**、支持与客服培训、成功指标看板、上线后复盘节奏。
> **两个量化判据**（本轮的「可算」部分）：
> - **就绪度评分**：把九个维度加权（**红线项必须 100%**，其余按分），得出 go/no-go，而不是靠感觉；
> - **灰度要多久才能发现问题**：由**样本量与效应大小**决定——若线上指标方差大，1% 灰度的 1 小时可能什么都发现不了（串 [[anthropic-27]] 的样本量口径）。
> 一句话判据：**「怎么知道它坏了？怎么在 5 分钟内退回去？出了事谁负责？」**——三问答不上来，就不该上线。

## 面试官在考什么

- **是否以「出事」为中心**：好的答案围绕**失败与恢复**（降级、回滚、kill switch、值班），而不是功能清单。
- **评测的严肃性**：能否坚持「真实流量抽样 + 任务级判据 + 红线项 + 门禁」，而不是「我们人工试了觉得不错」。
- **合规与数据**：能否主动提到 PII、留存期限、**是否用于训练**、审计；企业场景里这几项常常是硬门槛。
- **成本上限**：能否给出「单次请求成本 + 月预算 + 超限降级」的做法（而不是上线后账单爆炸）。
- **可观测性的可操作性**：能否说清「trace 里要有什么字段」以及「如何回放一次失败请求」（这是排障能力的前提）。
- **灰度与回滚的量化**：能否指出**灰度时长与样本量有关**，并给出「多大流量、多久能检出多大回归」的估算。
- **治理与责任**：能否给出负责人、审批流程、事故分级与响应 SLA；以及**人工监督的边界**（哪些动作必须人工确认）。
- **诚实**：承认有些项在原型阶段做不到，并给出「临时缓解 + 上线后补齐」的路径（而不是假装都做了）。

**常见错误答案**

- 只列功能与准确率，不提回滚、降级、值班。
- 没有红线项（所有指标都可以「以后再补」）。
- 不做成本上限（上线后账单失控）。
- 可观测性只记「请求成功/失败」，没有 trace 与可回放。
- 灰度没有门禁与时长依据（「灰一天看看」）。
- 忽略合规（把客户数据直接送进第三方 API、或用于训练）。
- 没有 kill switch，或从来没演练过。

## 原理与推导

### 1. 就绪度评分（红线 + 加权）

把九维度拆成条目，每条给「必须通过（红线）」或「加权分」：

$$\text{就绪度}=\begin{cases}\text{No-Go} & \text{任一红线未通过}\\[2pt] \sum_i w_i s_i\ (\text{其余条目}) & \text{红线全通过}\end{cases}$$

**红线的典型集合**（示例）：① 有可运行的 kill switch 且演练过；② 回滚计划已演练（含数据回滚）；③ 评测红线项全部通过；④ 敏感数据处理与合规审批完成；⑤ 成本上限与告警已生效；⑥ 值班与事故响应流程已就位。

**为什么红线优先**：加权分可以被「其他项都很好」补偿，但**「无法回滚」或「合规未批」是二值的**——不能被补偿。

### 2. 灰度：多久能发现问题（样本量口径）

设基线指标为 $p_0$（例如成功率 0.95），希望检出回归 $\delta$。要在灰度流量中检出，需要样本量：

$$n\approx\frac{2(z_{1-\alpha/2}+z_{\text{power}})^2\,p_0(1-p_0)}{\delta^2}$$

**例**：$p_0=0.95$、$\delta=0.02$（2 个百分点）→ $n\approx1{,}830$ 次请求。若灰度 1%、系统 QPS 20 → 灰度流量 0.2 次/秒 → **需要约 2.5 小时**才能积累这个样本。

**读法**：**灰度时长不是拍出来的**——它由「要检出多大回归」与「灰度流量」共同决定。**要更早发现，就得提高灰度比例或选更敏感的指标**（例如错误率的绝对变化、p95 延迟、或业务侧的质量信号）。

### 3. 降级链（必须有，且要分级）

| 触发 | 降级动作 | 用户可见影响 |
| --- | --- | --- |
| 主模型超时/限额 | 路由到小模型 | 质量略降 |
| 检索不可用 | 用缓存答案/明确告知 | 可能过时 |
| 工具调用失败 | 重试（幂等）→ 转人工 | 延迟上升 |
| 成本超预算 | 限流 + 排队 | 部分请求变慢 |
| 质量红线告警 | **回滚到上一版本** | 恢复旧行为 |
| 安全事件 | **kill switch** | 服务停止（可接受） |

**关键**：降级链要**预先定义并可观测**（「什么时候自动切、切了之后告警给谁」），而不是临场决定。

### 4. 可观测性的最小字段集

一次 agent 请求的 trace 至少要能回答：

| 问题 | 需要的字段 |
| --- | --- |
| 它做了什么？ | 每一步的工具调用 + 参数 + 返回摘要 |
| 花了多少？ | 每步 token 数、成本、耗时 |
| 为什么失败？ | 错误分类（超时/限流/工具错/模型拒答/校验失败） |
| 用的哪个版本？ | prompt/模型/工具/索引版本号 |
| 能不能复现？ | 输入 + 随机种子（若有）+ 检索命中的文档 id |
| 用户满意吗？ | 反馈信号（点赞/追问/人工接管） |

**没有版本号与可回放，事故复盘就只能靠猜。**

### 5. 变更管理与放量节奏

```
shadow（不影响用户，比对输出）
  → canary 1%（门禁：错误率、p95、成本、质量抽检）
  → 10% → 50% → 100%
每级都有：进入条件（上一级达标多久）、回滚触发（红线）、观察窗口（由样本量决定）
```

**回滚要覆盖四类对象**：**模型版本**、**prompt 版本**、**工具/权限配置**、**检索索引**（索引回滚常被忽略：换索引后检索质量变了，回滚代码没用）。

### 6. 治理与责任（企业场景的硬要求）

| 项 | 内容 |
| --- | --- |
| 用例审批 | 谁批准了这个用例、风险等级如何 |
| 人工监督边界 | 哪些动作必须人工确认（付款、删除、对外发送） |
| 披露 | 用户是否知道在与 AI 交互（很多地区要求） |
| 事故响应 | 分级（P0/P1）、响应时限、通知对象、对外沟通口径 |
| 文档 | 模型卡/系统说明、已知限制、评测结果 |
| 责任人 | 业务负责人 + 技术负责人 + 合规联系人 |

```python
@dataclass

    name: str

    score: float           # 0-1 完成度
    redline: bool = False  # 红线：必须 100%

class Dimension:
    name: str
    items: List[Item]
    def redlines_ok(self) -> bool:
        return all(i.score >= 0.999 for i in self.items if i.redline)
    def weighted(self) -> float:
        total = sum(i.weight for i in self.items)
        return sum(i.weight * i.score for i in self.items) / total if total else 0.0

# ---------- 2) 灰度时长：多久能发现回归 ----------
def n_for_delta(p0: float, delta: float, alpha: float = 0.05,
                power: float = 0.8) -> int:
    return math.ceil(2 * (z(1 - alpha / 2) + z(power)) ** 2 * p0 * (1 - p0) / delta ** 2)
def canary_hours(total_qps: float, canary_pct: float, p0: float,
                 delta: float) -> Dict[str, float]:
    n = n_for_delta(p0, delta)
    canary_qps = total_qps * canary_pct
    return {"需要样本数": n, "灰度QPS": canary_qps,
            "需要小时": n / canary_qps / 3600 if canary_qps > 0 else float("inf")}

print(f"  {'总QPS':>7} {'灰度比例':>9} {'要检出回归':>11} {'需要样本':>10} {'灰度QPS':>9} {'需要小时':>9}")

    Degradation("主模型超时/限流", "路由到小模型", "质量略降", True),
    Degradation("检索不可用", "用缓存答案并标注时效", "可能过时", True),
    Degradation("工具调用失败", "幂等重试 → 转人工", "延迟上升", True),
    Degradation("成本达预算上限", "限流 + 排队", "部分请求变慢", True),
    Degradation("质量红线告警", "回滚到上一版本", "恢复旧行为", False),
    Degradation("安全事件", "kill switch 停止服务", "服务中断（可接受）", False),
]
print("\n③ 降级链（必须预先定义、可观测、有告警对象）")
print(f"  {'触发':<22} {'动作':<24} {'影响':<18} {'自动':>5}")
for d in CHAIN:
    print(f"  {d.trigger:<22} {d.action:<24} {d.user_impact:<18} "
          f"{('是' if d.automatic else '否（需人确认）'):>5}")
print("  读法：前四级可自动（有明确阈值），**后两级必须人工确认**（避免误杀正常服务）——")
print("        但要保证人工路径**随时可达**（值班 + 一键开关）")

# ---------- 4) 风险排序：先补哪些缺口 ----------
@dataclass
class Risk:
    name: str
    likelihood: float      # 0-1
    impact: float          # 0-1（1 = 灾难）
    mitigation_gap: float  # 0-1（1 = 完全没做）
    def priority(self) -> float:
        return self.likelihood * self.impact * self.mitigation_gap
RISKS = [
    Risk("无法回滚（回滚未演练）", 0.5, 0.9, 1.0),
    Risk("成本失控", 0.6, 0.5, 0.2),
    Risk("prompt 注入导致越权工具调用", 0.3, 0.9, 0.3),
    Risk("PII 泄漏到第三方", 0.2, 1.0, 0.1),
    Risk("检索质量回退未被发现", 0.5, 0.6, 0.6),
    Risk("灰度期看不出问题（样本不足）", 0.7, 0.5, 0.8),
    Risk("值班缺失导致事故无人响应", 0.3, 0.7, 0.9),
]
print("\n④ 风险排序（可能性 × 影响 × 缓解缺口）——先补得分最高的")
print(f"  {'风险':<30} {'可能性':>7} {'影响':>6} {'缺口':>6} {'优先级':>7}")
for rk in sorted(RISKS, key=lambda x: -x.priority()):
    print(f"  {rk.name:<30} {rk.likelihood:>7.2f} {rk.impact:>6.2f} "
          f"{rk.mitigation_gap:>6.2f} {rk.priority():>7.2f}")
print("  读法：**优先级 = 可能性 × 影响 × 缓解缺口** —— 高可能 × 高影响但已缓解的项不该排第一；")
print("        「无法回滚」与「值班缺失」这类「缺口=1」的项应当排在最前（它们也常被列进红线）")
```

预期输出要点（实跑）：① 就绪度评分显示**红线优先**：本例 **5 个红线项未到 100%**（离线回归集 0.9、工具最小权限 0.9、预算上限告警 0.9、**回滚演练 0.4**、**kill switch 0.0**），因此**加权总分 0.73 也是 No-Go**——红线是二值的，不接受「差不多」；② 灰度时长表显示**灰度多久能发现问题由样本量决定**：基线 95%、要检出 2 个百分点的回归需 **1,865 个样本**，在 1% 灰度、总 20 QPS 下要 **2.6 小时**（检出 5 个百分点只需 299 样本、0.4 小时）——**提高灰度比例或换更敏感的指标才能更早发现**；③ 降级链把六级预案写清，其中**前四级可自动、后两级必须人工确认**（避免误杀）；④ 风险排序用**可能性 × 影响 × 缓解缺口**给出补齐顺序（「无法回滚」「值班缺失」排在前面）。

## 常见追问

- **追问**：原型阶段很多东西做不到，是不是就不能上线？
  - 要点：不是——要区分**「上线前必须有」**与**「上线后限期补齐」**。红线项（回滚、kill switch、合规、成本上限、值班）**必须上线前有**（哪怕是最简版本，例如手工回滚脚本+演练记录）；其余可以带计划上线，但**要有负责人与截止日期**，并写进上线审批。
- **追问**：`shadow` 模式怎么做？
  - 要点：把**真实流量复制一份**给新版本（不返回给用户），比对两边输出（一致性、质量评分、成本、延迟）。注意：**有副作用的工具调用必须屏蔽**（只能用只读工具或 dry-run），否则 shadow 会真的改数据。
- **追问**：怎么定义「质量红线」？
  - 要点：三类——① **绝不能发生**（越权操作、泄漏、给不安全建议）；② **必须达标**（任务成功率、结构化输出合法率）；③ **不能回退**（相对基线的通用能力）。红线要**可自动判定**（规则/裁判模型/人工抽检组合），并**接到告警与回滚**上。
- **追问**：成本上限怎么设才合理？
  - 要点：按**业务价值**倒推（每单毛利 → 可接受的每次会话成本），再设**日/月预算 + 告警阈值（50%/80%/100%）**与超限动作（限流、降级路由、暂停非关键功能）。**关键是超限动作要提前定义，而不是超了再开会。**
- **追问**：可观测性最少要记什么？
  - 要点：**每一步的输入/输出摘要 + 工具调用 + token/成本/耗时 + 版本号 + 错误分类**，并支持**按请求 id 回放**。没有版本号与回放，复盘只能靠猜；没有成本字段，账单超了也不知道是谁。
- **追问**：上线后怎么持续保证质量？
  - 要点：① **线上质量信号**（点赞/追问率/人工接管率/任务完成率）；② **定期离线回归**（每周跑评测集）；③ **漂移监控**（输入分布、检索命中率、工具失败率）；④ **变更即回归**（任何 prompt/模型/索引变更都跑门禁）；⑤ **季度复盘**（红线是否仍合适、成本是否仍合理）。
