# Cognition（Devin、Windsurf）面试题库

这家公司的面试风格是**「动手 + 判断力」**：一轮实战的 agent 构建或调试、一轮基础设施设计、一轮 agent 评估，
面向客户的岗位再加一轮 deployed engineering 场景。所以这个题库的九道题也分成两类——
**要么让你当场设计一个能跑的东西**（八小时构建、执行环境、评估方案），
**要么让你在两种看似矛盾的做法之间给出判据**（multi-agent 的两种立场、云端 vs 编辑器内）。

贯穿全套的一条主线是**上下文工程**：八小时构建里它占两小时，代码定位题讲的是「怎么让上下文更准」，
multi-agent 题的核心不变量是「上下文必须共享」，RL 题的动作空间必须与部署的 harness 一致。
第二条主线是**可验证性**：能跑测试的才算完成、判据能被绕过的通过率不算成绩、有界可检测可回滚才算安全。

## 这家公司的面试怎么准备

**第一，准备一个「能跑的最小 agent」，而不是一堆框架名。** 面试官会追问「第 20 步上下文多大」「工具输出怎么截断」「怎么判断它做完了」。
本库第 01、03 两篇给出的都是可复算的数字（窗口占比、步数、token、hit@k），**用数字回答比用架构图回答有效得多**。

**第二，凡是「两种做法之争」，先找不变量再谈边界。** multi-agent 题的标准答案是「共享上下文 + 写入单线程」；
云端 vs 编辑器内题的答案是「状态权威性 / 延迟预算 / 环境归属」三条轴。**不要站队，要给判据。**

**第三，判据必须可验证，且要假设它会被攻击。** 第 04、07、08 三篇是同一件事的三个侧面：
奖励会被刷（改测试）、通过率会被虚高（弱判据 + 污染）、权限会被注入利用（confused deputy）。
**能主动说出「我的指标会被怎么骗」，是这一家最看重的信号。**

**第四，客户题要给漏斗、约束与停止条件。** 第 09 题的得分点是**评审产能约束**与**盈亏平衡规模**——
不是「我们推广得多好」，而是「在什么规模上成立、什么条件下应该停」。
