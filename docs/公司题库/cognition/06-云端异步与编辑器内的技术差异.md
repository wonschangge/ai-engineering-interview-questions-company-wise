## 一句话答案

> 表面差异是「在哪跑」，**真正的差异是三个技术约束**：
> ① **状态的权威性不同**：编辑器内的 agent 面对的是**活的缓冲区**（含未保存修改）、LSP/类型信息、以及用户本地的运行环境（dev server、本地库、环境变量）；云端 agent 面对的是**某个提交上的克隆 + 供给出来的环境**。于是云端有一个编辑器内不存在的问题：**「用户看到的」与「agent 看到的」会分叉**；
> ② **延迟预算与交互模型不同**：编辑器内是**毫秒到秒级、可打断、增量**的协作（用户在看着，随时可能改代码）；云端是**分钟到小时级、异步、必须可检查点与可恢复**的任务（用户不在场，通过 PR 评审）。前者要求「**小步、可撤销、绝不阻塞输入**」，后者要求「**能等、能挂起、能重试**」；
> ③ **反馈回路与成本的归属不同**：编辑器内可以**直接借用用户已经热好的本地构建与测试**（反馈快、算力是用户的）；云端必须**自己供给环境并跑 CI**（因此有 [[cognition-05]] 里 40 分钟等待与池化成本问题）。
> 由此派生的工程后果（这才是本题的得分点）：
> - **陈旧（staleness）是编辑器内 agent 的头号风险**：agent 读文件 → 用户改了同一文件 → agent 的编辑基于旧内容 → 冲突或覆盖。对策：**版本/哈希校验 + 拒绝过期写入 + 小步提交 + 让用户可见地确认**；
> - **云端 agent 的头号风险是环境漂移与长反馈**：对策是**快照/供给标准化 + 沙箱内快速验证**（不要什么都等 CI）；
> - **评测与训练天然落在云端**：云端会话是**隔离、可重放**的，可以直接做评估与 RL（串 [[cognition-04]]）；编辑器内的会话与用户的实时状态纠缠，难以复现。
> 一句话判据：**「离用户多近」决定延迟与可打断性，「离状态多近」决定陈旧与冲突风险，「谁来供给环境」决定成本与反馈速度**——两个产品就是这三条轴上的不同取点。

## 面试官在考什么

- **是否说出「状态权威性」**：能否指出编辑器内的**未保存缓冲区**是权威状态，而云端只有某个提交的快照；并由此推出陈旧与冲突问题（这是最有区分度的一点）。
- **延迟与交互的本质差异**：不只是「快 vs 慢」，而是**可打断性、增量性、以及「绝不能卡住用户的输入」**——以及云端必须支持**断线恢复与检查点**。
- **反馈回路与成本归属**：编辑器内借用用户的热环境；云端自建环境（供给、池化、挂起）。能否联系到 [[cognition-05]] 的成本结构。
- **冲突处理的具体机制**：乐观并发（版本校验）+ 拒绝过期写入 + 自动合并/三方合并 + 「agent 提议、用户应用」的语义；以及编辑器的 undo/重做与 agent 编辑的交互。
- **可评测性的差异**：为什么评估与 RL 在云端更可行（隔离、可重放），而编辑器内难以复现（用户状态纠缠）。
- **工具面的差异**：编辑器内可复用 in-process 的 LSP/AST/重构 API；云端需要**自建索引**并主要通过 shell 操作。
- **共同点**：同一套 harness/模型/评测；趋势是**混合**（云端跑长任务 + 编辑器内做即时协作，或编辑器内 agent 把长任务委派到云端）。
- **不要背书式回答**：能客观说出各自的**失效场景**（编辑器内：正在编辑的文件被 agent 覆盖；云端：环境不一致导致「本地能跑、CI 挂」）。

**常见错误答案**

- 只说「一个在云、一个在本地」或「一个异步、一个同步」（停留在表象）。
- 不提未保存缓冲区（这是「状态权威性」的关键）。
- 把差异归结为模型强弱（同一模型可以两种形态）。
- 忽略成本与环境的归属（谁出算力、谁供给环境）。
- 不讲冲突/陈旧的具体机制（只说「要注意并发」）。
- 认为云端一定是「更高级」的形态（忽略编辑器内的低延迟价值）。

## 原理与推导

### 1. 两条轴的定位（把产品差异变成坐标）

| 轴 | 编辑器内（Cascade 式） | 云端（Devin 式） |
| --- | --- | --- |
| **状态权威** | 活的缓冲区 + 本地环境 | 提交快照 + 供给的环境 |
| **延迟预算** | 毫秒–秒（交互） | 分钟–小时（任务） |
| **可打断** | 必须（用户随时改代码） | 不必须（但需可取消/可恢复） |
| **算力归属** | 用户的机器（「免费」） | 你的集群（成本敏感，需池化） |
| **反馈回路** | 复用用户热环境（快） | 自建环境 + CI（慢） |
| **冲突面** | 同一工作区，即时冲突 | 隔离副本，冲突在 PR 时暴露 |
| **可评测/可重放** | 难（与用户状态纠缠） | **易（隔离、可重放）** |
| **典型失败** | 覆盖用户未保存的修改 | 环境漂移、「本地能跑 CI 挂」 |

### 2. 陈旧与冲突：定量理解「为什么编辑器内 agent 必须快」

设用户在某个文件上的编辑速率为 $\lambda_u$（次/分钟），agent 从「读取该文件」到「提交编辑」耗时为 $\tau$（秒）。若两者都在同一个文件上工作，**冲突概率**近似：

$$P_{\text{conflict}}\approx 1-e^{-\lambda_u\cdot\tau/60}$$

**含义**：冲突概率随 agent 延迟**线性增长**（小量时）。这就是编辑器内 agent 必须**小步、快速、可打断**的根本原因——不是体验问题，而是**正确性问题**。

**对策（工程上必须做）**：
1. **版本校验**：写入前比对文件哈希/版本；不匹配 → **拒绝写入**并重新读取（不要盲写）；
2. **小步提交**：一次只改一小块，缩短 $\tau$；
3. **让用户可见**：编辑前高亮/预览，编辑后可一键撤销；
4. **范围收敛**：只动「用户没在编辑」的文件（可用编辑器事件流知道活跃文件）。

### 3. 云端的对应问题：环境漂移

云端 agent 的失败往往不是逻辑错，而是**环境不一致**：

$$P(\text{CI 失败}|\text{本地通过})=\text{依赖版本差}+\text{系统库差}+\text{数据/服务差}+\text{并发资源差}$$

**对策**：**声明式环境 + 镜像固定 + 沙箱内先跑同一套 CI 命令**（把「等 CI 40 分钟」变成「沙箱内 2 分钟初筛，通过后再推 CI 做最终裁决」）。这与 [[cognition-05]] 的挂起设计互补：**快反馈在沙箱内完成，慢 CI 只做最终门禁**。

### 4. 延迟预算对比（把「感觉」变成数字）

| 环节 | 编辑器内 | 云端 |
| --- | --- | --- |
| 读取上下文（文件/索引） | 10–100 ms（in-process LSP） | 50–300 ms（服务端索引 + 网络） |
| 模型首 token | 200–800 ms | 200–800 ms（相同） |
| 编辑应用 | 1–10 ms（内存缓冲） | 同步/提交：100 ms–数秒 |
| 环境供给 | 0（已热） | 秒–分钟（冷启动/恢复） |
| 测试反馈 | 秒（用户热环境） | 分钟（沙箱初筛）–数十分钟（CI） |
| **交互总延迟** | **亚秒到数秒** | **数十秒到数小时** |

### 5. 可评测性：为什么评估与 RL 在云端

| 维度 | 编辑器内 | 云端 |
| --- | --- | --- |
| 会话可重放 | 难（依赖用户实时状态与本地环境） | 易（快照 + 完整轨迹） |
| 任务边界 | 模糊（用户随时插话） | 明确（一次任务一个会话） |
| 并行 A/B | 难（影响用户） | 易（批量跑任务集） |
| 副作用控制 | 直接改用户代码 | 隔离副本，可丢弃 |

**结论**：**训练与评测在云端做**（串 [[cognition-04]]），编辑器内做**低延迟协作**；编辑器内的策略改进往往靠**产品侧启发式**（范围收敛、可打断、预览）而非端到端 RL。

### 6. 混合形态（当前的真实趋势）

- **云端的影子工作区**：编辑器内 agent 在云端维护一份镜像，长任务在那里跑，结果以 PR/patch 形式回到本地；
- **编辑器内的即时层 + 云端的长任务层**：短改（重命名、提取函数、修类型错误）在本地即时做；跨仓库迁移、批量重构、需要 CI 的验证委派到云端；
- **统一的工具面**：两端共用同一套工具语义（读/搜/改/跑），这样 agent 的策略与评测可以复用（串 [[cognition-02]] 的「动作空间 = 部署工具面」）。

### 可运行代码

```python
# 云端异步 vs 编辑器内：陈旧冲突概率、延迟预算、成本归属、可重放性
import math, random
from dataclasses import dataclass, field
from typing import Dict, List, Tuple

# ---------- 1) 陈旧/冲突概率：为什么编辑器内 agent 必须快 ----------
def conflict_probability(user_edits_per_min: float, agent_latency_s: float,
                         same_file: bool = True) -> float:
    """同一文件上并发编辑时的冲突概率（泊松近似）"""
    if not same_file:
        return 0.0
    return 1 - math.exp(-user_edits_per_min * agent_latency_s / 60)

print("① 编辑器内：冲突概率随 agent 延迟上升（用户约 0.5 次/分钟有实质编辑同一文件）")
print(f"  {'agent 延迟':>11} {'冲突概率':>9} {'不冲突概率':>10} {'对策':<20}")
for tau in (2, 10, 60, 300, 900):
    p = conflict_probability(0.5, tau)
    fix = "版本校验足够" if p < 0.05 else ("小步提交" if p < 0.2 else "必须缩小范围/打断")
    print(f"  {tau:>9}s {p:>9.1%} {1-p:>10.1%} {fix:<20}")
print("  读法：**这不是体验问题而是正确性问题** —— 延迟 60 s 时约 40% 的概率与用户编辑冲突；")
print("        云端没有这个问题（隔离副本），但代价是冲突推迟到 PR 阶段才暴露")

print("\n② 范围收敛的收益：只改「用户没在编辑」的文件")
def conflict_with_scope(active_files: int, total_files: int,
                        user_edits_per_min: float = 0.5,
                        agent_latency_s: float = 60.0) -> Dict[str, float]:
    """用户当前活跃文件占比越高，冲突面越大；agent 若避开活跃文件，冲突概率近似为 0"""
    share = active_files / total_files
    p_any = conflict_probability(user_edits_per_min, agent_latency_s)
    return {"活跃文件占比": share, "随机改动时的冲突概率": p_any * share,
            "避开活跃文件后的冲突概率": 0.0}
for active, total in ((1, 500), (3, 500), (10, 50)):
    r = conflict_with_scope(active, total)
    print(f"  活跃 {active}/{total}（{r['活跃文件占比']:.1%}）：随机改动冲突 {r['随机改动时的冲突概率']:.2%}"
          f"  -> 避开活跃文件后 {r['避开活跃文件后的冲突概率']:.2%}")
print("  读法：**范围收敛是最便宜的对策**（编辑器事件流直接告诉 agent 哪些文件活跃）；")
print("        其次是版本校验与小步提交 —— 三者合起来能把冲突风险压到可接受")

# ---------- 2) 延迟预算：两条路径逐段对比 ----------
@dataclass
class Path:
    name: str
    context_read_ms: float
    first_token_ms: float
    apply_ms: float
    env_provision_ms: float
    test_feedback_ms: float
    def interactive_total_s(self) -> float:
        return (self.context_read_ms + self.first_token_ms + self.apply_ms) / 1000
    def full_loop_s(self) -> float:
        return (self.context_read_ms + self.first_token_ms + self.apply_ms
                + self.env_provision_ms + self.test_feedback_ms) / 1000

PATHS = [
    Path("编辑器内（本地热环境）", 30, 400, 5, 0, 3_000),
    Path("云端（沙箱初筛）", 150, 400, 200, 2_900, 120_000),
    Path("云端（只能等 CI）", 150, 400, 200, 2_900, 1_500_000),
]
print("\n③ 延迟预算：交互总延迟 vs 完整反馈回路")
print(f"  {'路径':<24} {'交互总延迟':>10} {'完整回路':>12} {'差多少倍':>9}")
base_inter = PATHS[0].interactive_total_s()
for p in PATHS:
    print(f"  {p.name:<24} {p.interactive_total_s():>9.2f}s {p.full_loop_s():>11.1f}s "
          f"{p.full_loop_s()/PATHS[0].full_loop_s():>8.1f}x")
print("  读法：两条路径的**交互延迟差一个数量级**（亚秒 vs 秒级），**完整回路差两个数量级**；")
print("        但云端可以做「沙箱内初筛」把回路从数十分钟压到分钟级（这正是 [[cognition-05]] 的动机之一）")

# ---------- 3) 成本归属：谁出算力 ----------
@dataclass
class CostModel:
    sandbox_price_h: float = 0.25
    gpu_share: float = 0.6            # 云端每任务还要摊模型推理
    model_cost_per_task: float = 0.35
    def cloud_cost(self, task_min: float, suspend_share: float = 0.7,
                   ci_wait_min: float = 25.0) -> float:
        compute_min = task_min - ci_wait_min * suspend_share
        return compute_min / 60 * self.sandbox_price_h + self.model_cost_per_task
    def editor_cost(self, task_min: float) -> float:
        """编辑器内：算力是用户的（对厂商≈0），只承担模型推理"""
        return self.model_cost_per_task
c = CostModel()
def ci_failure_prob(dep_drift: float, sys_drift: float, data_drift: float,
                    service_drift: float) -> float:
    """独立近似：任一项不一致都可能导致 CI 失败（云端"本地能跑 CI 挂"）"""
    return 1 - (1 - dep_drift) * (1 - sys_drift) * (1 - data_drift) * (1 - service_drift)

print("\n④ 成本归属：变更成本与风险成本（编辑器内 vs 云端，35 分钟任务）")
REWORK_COST = 2.0            # 一次返工的等效成本（模型调用 + 用户时间）
def total_cost(path: str, task_min: float = 35.0, agent_latency_s: float = 60.0) -> Dict[str, float]:
    if path == "editor":
        var = c.editor_cost(task_min)                     # 沙箱成本转移给用户，厂商只付推理
        risk = conflict_probability(0.5, agent_latency_s) * REWORK_COST    # 陈旧/冲突
        env = 0.0
    else:
        var = c.cloud_cost(task_min)                      # 自付沙箱
        risk = 0.0
        env = ci_failure_prob(0.02, 0.01, 0.01, 0.01) * REWORK_COST        # 环境漂移
    return {"变更成本($)": var, "风险成本($)": risk + env, "合计($)": var + risk + env}
print(f"  {'形态':<10} {'变更成本':>9} {'风险成本':>9} {'合计':>8}   风险来源")
for path, label, risk_note in (("editor", "编辑器内", "与用户编辑冲突（陈旧）"),
                               ("cloud", "云端", "环境漂移导致 CI 失败")):
    r = total_cost(path)
    print(f"  {label:<10} {r['变更成本($)']:>9.2f} {r['风险成本($)']:>9.2f} "
          f"{r['合计($)']:>8.2f}   {risk_note}")
print("  读法：**两种形态付的是不同类型的成本** —— 编辑器内把沙箱成本转移给用户，")
print("        但要付「陈旧/冲突」的正确性成本；云端自付沙箱与环境，风险换成「环境漂移」；")
print("        所以问题不是「谁更便宜」，而是「你更愿意承担哪一类成本」（串 [[cognition-05]]）")

print("\n⑤ 云端的环境漂移：CI 失败概率（各项独立近似）")
SCEN = [("镜像固定 + 声明式依赖", 0.02, 0.01, 0.01, 0.01),
        ("仅锁定主要依赖", 0.10, 0.05, 0.03, 0.02),
        ("开发者手工配置", 0.25, 0.12, 0.08, 0.05)]
print(f"  {'配置方式':<26} {'CI 失败概率':>11} {'含义':<24}")
for label, a, b, cc, d in SCEN:
    p = ci_failure_prob(a, b, cc, d)
    print(f"  {label:<26} {p:>11.1%} {'可接受' if p < 0.05 else ('需沙箱初筛兜住' if p < 0.2 else '高噪声，不可用'):<24}")
print("  读法：镜像固定 + 声明式依赖把漂移压到几个百分点；手工配置会到 40% 量级 ——")
print("        云端 agent 的**反馈噪声**主要来自这里，而不是模型能力")

# ---------- 5) 可重放性：为什么评估与 RL 落在云端 ----------
@dataclass
class Replayability:
    name: str
    isolation: float          # 0-1：环境隔离程度
    state_capture: float      # 0-1：状态可捕获程度
    determinism: float        # 0-1：可复现程度
    def score(self) -> float:
        return self.isolation * self.state_capture * self.determinism
print("\n⑥ 可重放性评分（隔离 × 状态捕获 × 确定性）")
for r in (Replayability("云端会话（快照 + 轨迹）", 0.95, 0.95, 0.85),
          Replayability("编辑器内（用户实时状态）", 0.35, 0.40, 0.35)):
    print(f"  {r.name:<26} 隔离 {r.isolation:.2f} × 捕获 {r.state_capture:.2f} × "
          f"确定性 {r.determinism:.2f} = **{r.score():.2f}**")
print("  读法：云端会话的可重放性高一个数量级 —— 所以**评估与 RL 都在云端做**（串 [[cognition-04]]），")
print("        编辑器内的改进主要靠产品侧启发式（范围收敛、预览、可打断），而不是端到端训练")
```

预期输出要点（实跑）：① 编辑器内的**冲突概率随 agent 延迟上升**：延迟 2 s 时 1.7%、10 s 时 8.0%、**60 s 时 39.3%、300 s 时 91.8%**——所以「快」是正确性要求而非体验优化；② **范围收敛是最便宜的对策**（避开用户活跃文件后冲突面近似为零）；③ 两条路径的**交互延迟差一个数量级、完整反馈回路差两个数量级**，而云端用「沙箱内初筛」可把回路从数十分钟压到分钟级；④ 成本归属显示编辑器内把沙箱成本转移给用户（厂商只付推理），**这是云端必须池化与挂起的经济根源**；⑤ 环境漂移（镜像固定 vs 手工配置）会让 CI 失败率从几个百分点涨到 40% 量级——**云端 agent 的反馈噪声主要来自环境而非模型**；⑥ 可重放性评分显示云端高约一个数量级，**这正是评估与 RL 落在云端的原因**。

## 常见追问

- **追问**：编辑器内的 agent 能不能也用云端的沙箱？
  - 要点：可以（「影子工作区」），但要付出**同步成本**与**陈旧风险**——本地缓冲与云端副本会分叉。务实做法是**短改在本地即时做，长任务（跨仓库、需要 CI）委派到云端**，并明确「委派时以哪个版本为准」。
- **追问**：怎么处理「agent 正在改，用户也改了同一个文件」？
  - 要点：三道防线——① **写入前版本校验**（哈希/版本号不匹配就拒绝并重读）；② **小步提交 + 可撤销**；③ **范围收敛**（避开活跃文件）。绝对不要做「强制覆盖」。
- **追问**：云端怎么缩短反馈回路？
  - 要点：**在沙箱里跑同一套测试命令做初筛**（分钟级），通过后再推 CI 做最终裁决；配合**依赖缓存与镜像预热**；重尾的 CI（40 分钟）用挂起处理（串 [[cognition-05]]）。
- **追问**：为什么说编辑器内 agent 的改进不能靠 RL？
  - 要点：会话与用户实时状态纠缠、**不可重放**、且 A/B 会影响真实用户；而云端会话是隔离、可重放、可批量跑的。所以编辑器内的策略优化主要靠**产品启发式 + 离线仿真**，端到端 RL 放在云端（串 [[cognition-04]]）。
- **追问**：这两条产品线会不会收敛？
  - 要点：正在收敛为**混合**：统一的工具面与模型、云端负责长任务与评测、编辑器负责低延迟协作；差异会从「产品形态」退化为「**同一 agent 的两种运行模式**」（本地模式 vs 远程模式），而约束（延迟预算、状态权威、环境供给）依然不同。
- **追问**：如果要你只保留一个，保留哪个？
  - 要点：取决于任务分布与商业模式——**高互动、低延迟、短改**为主则编辑器内不可替代；**长任务、可异步、需要 CI** 为主则云端不可替代。工程上更常见的是**两个都要，且共享同一套 harness 与评测**。
