## 一句话答案

> 先给结论：**「通过率」是一个不完整的指标，而不是一个错误的指标**。它的问题有七条，每条都能量化：
> ① **样本量小 → 置信区间宽**：常用子集只有几百题，**±5–6 个百分点的 95% 区间是常态**；两个系统差 2 个点通常**就是噪声**（要检出 3 个点的差异需要上千题）；
> ② **判据可被绕过**：测试通过 ≠ 修得对。硬编码、特判、只让可见用例过（甚至改测试）都能刷高通过率——所以必须叠加**留出测试 + 变异检测 + 回归检查**（串 [[cognition-04]] 的奖励攻击）；
> ③ **任务分布≠真实工作**：SWE-bench 全量是 **12 个 Python 仓库的 2,294 个真实 issue/PR**（论文口径），以「有测试、单仓库、局部修复」为主；真实工作里更多是**需求模糊、跨仓库、没有测试、需要与人来回确认**的任务；
> ④ **污染与记忆**：公开仓库的 issue 可能出现在训练数据里；需要**时间切分**（只用模型训练截止后的 issue）与污染检测；
> ⑤ **没有成本口径**：70% 通过率若每条要 10 倍 token 与 5 倍墙钟，业务上可能劣于 60% 的便宜方案——必须同时报 **\$/任务**与**耗时**；
> ⑥ **只看结果、不看过程**：通过率不反映**步数、工具错误、返工、是否差点搞坏别处**；也不反映**回归**（「解决了这个 issue 但弄坏了三个测试」是常见的失败形态）；
> ⑦ **忽略人机协作成本**：一个「能过测试但没人愿意 review」的 patch（巨型 diff、无测试、风格混乱）在真实流程里是负资产。
> **所以要用的评估是分层的**：**主判据**（留出 + 回归 + 变异检测）→ **成本**（\$/任务、墙钟）→ **过程指标**（步数、工具错误率、重复劳动）→ **产物质量**（diff 可评审性、是否动测试/CI 配置）→ **真实部署**（工程师接受 PR 的比例）。**报告时永远给区间与分群，不给单一数字。**

## 面试官在考什么

- **统计素养**：能否主动给出**置信区间**与**样本量**（而不是把 2 个百分点的差异当结论），并知道「要检出 X 点差异需要多少题」。
- **判据的漏洞**：能否指出通过率可被绕过，并给出具体机制与对策（留出测试/变异检测/回归）。
- **任务分布意识**：能否说明 SWE-bench 的构成（12 个 Python 仓库、2,294 个 issue/PR）与真实工作的差距，并据此**外推的风险**。
- **成本与延迟**：能否坚持「必须报 \$/任务与墙钟」，并给出复合指标（例如「满足 SLO 的解决率」）。
- **过程与产物**：能否提到步数、工具错误率、回归率、diff 大小、是否改动测试/CI 配置（这些是**作弊与低质的信号**）。
- **污染**：能否提出时间切分、私有仓库留出集、以及「同一个 issue 的 PR 是否在训练数据里」的检查。
- **人机协作**：能否把「review 负担」纳入评估（例如补丁被工程师接受的比例、平均 review 时长）。
- **诚实**：会说「单一榜单数字不能支撑采购或发布决策」，并给出**决策导向**的评估设计（针对具体任务分布与 SLO）。

**常见错误答案**

- 只看通过率，不比成本与延迟。
- 认为「通过测试就是对的」（忽略硬编码、改测试、回归）。
- 用小样本差异下结论（「我们从 45% 提升到 47%」）。
- 不做污染检查（把训练记忆当成能力）。
- 不区分任务难度与类型（把长尾失败与常见失败混在一起平均）。
- 忽略「未通过的样本里有多少是接近成功」（失败分布比失败率更有信息量）。

## 原理与推导

### 1. 主判据：可验证 + 防绕过

| 层级 | 判据 | 作用 | 漏洞 |
| --- | --- | --- | --- |
| L1 | **留出测试**（隐藏/新增测试） | 防硬编码与特判 | 需要人工构造 |
| L2 | **回归测试**（原有用例全绿） | 防「修一个坏三个」 | 原有用例本身可能不全 |
| L3 | **变异检测**（扰动正确补丁后测试应失败） | 识别**弱测试** | 计算开销 |
| L4 | **产物审查**（是否动测试/CI 配置、diff 大小） | 识别作弊与不可评审 | 需要规则或人 |
| L5 | 编译/类型/lint | 门禁 | 不反映语义正确 |

**纪律**：**「通过率」必须明确写成「在 L1+L2 下的通过率」，并把 L3/L4 作为独立报告项**——否则数字会被误读。

### 2. 置信区间与样本量（最容易被忽略的一节）

单题是伯努利试验，通过率的 Wilson 区间：

$$\hat p\pm z_{1-\alpha/2}\sqrt{\frac{\hat p(1-\hat p)}{n}}$$

| 题量 $n$ | $\hat p=0.5$ 时 95% 半宽 | 结论 |
| --- | --- | --- |
| 100 | ±9.8 个百分点 | 几乎无法比较 |
| 300 | ±5.7 个百分点 | 只能看大差异 |
| 500 | ±4.4 个百分点 | 常用下限 |
| 2,294 | ±2.0 个百分点 | 论文口径的完整集 |
| 5,000 | ±1.4 个百分点 | 精细比较 |

**要检出差异 $\delta$ 所需题量**（两比例、$\alpha=0.05$、功效 80%）：

$$n\approx\frac{2(z_{1-\alpha/2}+z_{\text{power}})^2\,p(1-p)}{\delta^2}$$

$\hat p\approx0.5$ 时：$\delta=5$ 点 → 约 **1,570 题**；$\delta=3$ 点 → 约 **4,360 题**；$\delta=1$ 点 → 约 **39,200 题**。

**推论（很重要）**：**用几百题去比较两个系统，只能识别「5 个百分点以上」的差异**；榜单上 1–2 个点的排名变化基本没有信息量。

### 3. 为什么通过率会误导：把七条原因量化

**(a) 判据可绕过**。设真实修复率 $r$、作弊可得比例 $c$（取决于判据强度），则**表观通过率** $\hat p=r+c(1-r)$。用 [[cognition-04]] 的模拟口径：只看「测试通过」时表观 81.9% 而真实 55.2%（**虚高 26.7 个百分点**）；加上留出测试与变异检测后两者收敛。

**(b) 成本被忽略**。定义「**每解决一个任务的成本**」：

$$\text{CPR}=\frac{\text{总成本}}{\text{解决数}}=\frac{\text{每题成本}}{\text{通过率}}$$

| 系统 | 通过率 | \$/任务 | CPR | 墙钟/任务 |
| --- | --- | --- | --- | --- |
| A | 70% | \$12 | **\$17.1** | 25 min |
| B | 60% | \$3 | **\$5.0** | 6 min |
| C | 75% | \$40 | \$53.3 | 90 min |

**读法**：A 看起来比 B 强 10 个点，但**每解决一个任务贵 3.4 倍**；C 的通过率最高却最贵。**没有成本口径的通过率无法做决策。**

**(c) 污染会直接抬高分数**。设题集中被模型「记住」的比例为 $m$，记忆题的通过率为 $p_{\text{mem}}\approx0.95$（远高于真实能力 $p_{\text{real}}$），则

$$\hat p=m\,p_{\text{mem}}+(1-m)\,p_{\text{real}}$$

$p_{\text{real}}=0.5$、$m=0.2$ 时表观 0.59（**虚高 9 个百分点**）——足以改变榜单排名。**对策**：时间切分（只用训练截止后合并的 issue）、私有仓库留出集、以及「改函数/文件名的等价改写」检测。

### 4. 应该怎么评：六层评估

| 层 | 指标 | 采集方式 |
| --- | --- | --- |
| 1 正确性 | L1+L2 通过率（**给区间**，按难度/语言/仓库分群） | 自动 |
| 2 代价 | \$/任务、墙钟、token、GPU/沙箱小时 | 引擎侧埋点 |
| 3 过程 | 步数、工具错误率、重复查询率、人工打断次数 | 轨迹分析（串 [[cognition-03]]） |
| 4 产物 | diff 行数/文件数、**是否改动测试或 CI 配置**、是否有新测试、可评审性评分 | 规则 + 人工抽样 |
| 5 回归 | 原有用例破坏率、变异检测失败率 | 自动 |
| 6 真实部署 | **PR 被工程师接受的比例**、平均 review 时长、回滚率 | 产品数据 |

**关键**：层 6 是唯一「无法作弊」的指标——它是最终裁判。层 1–5 用于**快速迭代与定位**。

### 5. 失败分析比失败率更有价值

不要只报 45%，要报**失败分布**：

| 失败类型 | 占比 | 含义 |
| --- | --- | --- |
| 定位错（没找到该改的地方） | ? | 检索/地图问题（串 [[cognition-03]]） |
| 改错方向（语法对、语义错） | ? | 理解问题 |
| 差一点（测试只差 1–2 个断言） | ? | 步骤/预算不足 |
| 破坏回归 | ? | 验证不足 |
| 判据作弊 | ? | 需要堵漏（串 [[cognition-04]]） |
| 环境/工具失败 | ? | 基础设施问题（串 [[cognition-05]]） |

**读法**：同样的 55%，「大量差一点」和「大量破坏回归」对应完全不同的改进方向。

### 6. 评估的公平性（比较两个系统时）

1. **同任务集**（同提交、同环境）、**配对比较**（每个任务两边都跑）；
2. **多次运行**（agent 有随机性：`pass@1` 与 `pass@k` 区分开）；
3. **固定预算**（同 token/步数/墙钟上限，否则是「给得多所以赢」）；
4. **分群报告**（按难度/语言/仓库规模）；
5. **盲评**（产物质量由不知道来源的人/模型评）。

def wilson(k: int, n: int, alpha: float = 0.05) -> Tuple[float, float]:
    if n == 0:
        return (0.0, 1.0)
    p = k / n
    zz = z(1 - alpha / 2)
    denom = 1 + zz * zz / n
    center = (p + zz * zz / (2 * n)) / denom
    half = zz * math.sqrt(p * (1 - p) / n + zz * zz / (4 * n * n)) / denom
    return (max(0.0, center - half), min(1.0, center + half))

def n_for_delta(delta: float, p: float = 0.5, alpha: float = 0.05,
                power: float = 0.8) -> int:
    return math.ceil(2 * (z(1 - alpha / 2) + z(power)) ** 2 * p * (1 - p) / delta ** 2)

class System:
    name: str
    resolve_rate: float
    cost_per_task: float
    wall_min: float
    regression_rate: float      # 破坏原有测试的比例
    def cpr(self) -> float:
        return self.cost_per_task / self.resolve_rate
    def goodput(self, slo_min: float = 30.0, max_regression: float = 0.05) -> float:
        """满足 SLO 与回归红线的解决率"""
        if self.wall_min > slo_min or self.regression_rate > max_regression:
            return 0.0
        return self.resolve_rate

print(f"  {'系统':<26} {'通过率':>7} {'$/任务':>8} {'CPR':>8} {'墙钟':>7} {'回归':>6} "
      f"{'满足SLO的解决率':>14}")
for sy in SYSTEMS:
    print(f"  {sy.name:<26} {sy.resolve_rate:>7.0%} {sy.cost_per_task:>8.1f} "
          f"{sy.cpr():>8.1f} {sy.wall_min:>6.0f}m {sy.regression_rate:>6.1%} "
          f"{sy.goodput():>14.0%}")
print("  读法：C 的通过率最高，但**每解决一题贵 10 倍、且超出 SLO 与回归红线**（goodput = 0）；")
print("        D 的通过率不低，但回归率 12% 直接判红 —— **通过率无法表达这些否决项**")

print("\n⑥ 失败分布比失败率更有价值（同一 55% 通过率，两种完全不同的系统）")
FAIL = {
    "系统 X": {"定位错": 0.10, "改错方向": 0.15, "差一点": 0.15, "破坏回归": 0.03,
               "判据作弊": 0.01, "环境失败": 0.01},
    "系统 Y": {"定位错": 0.02, "改错方向": 0.05, "差一点": 0.03, "破坏回归": 0.20,
               "判据作弊": 0.10, "环境失败": 0.05},
}
print(f"  {'系统':<8} " + " ".join(f"{k:>9}" for k in FAIL["系统 X"]))
for name, dist in FAIL.items():
    print(f"  {name:<8} " + " ".join(f"{v:>9.1%}" for v in dist.values()))
print("  读法：两个系统通过率都是 55%，但 X 的问题是**能力**（差一点/改错方向），")
print("        Y 的问题是**可信度**（破坏回归 20%、判据作弊 10%）—— 改进方向完全不同：")
print("        X 该投检索与理解，Y 该先堵漏（串 [[cognition-04]]）")

预期输出要点（实跑）：① 置信区间表显示 **300 题时半宽 5.6 个百分点**（100 题时 9.6）、2,294 题时 2.0——常用子集上「1–2 个点的排名变化」没有信息量；② 样本量表给出 δ=5% 需约 1,570 题、δ=3% 需约 4,360 题、**δ=1% 需约 3.9 万题**（工程上不可行）；③ 判据强度直接影响表观分数：同一份 55% 的真实能力，判据从「只看测试」到「留出 + 变异 + diff 审查」时**表观通过率从 82.0% 收敛到 57.7%**（虚高从 27.0 个百分点压到 2.7 个）；④ 污染模拟显示**只有 10% 的题被记住就能虚高约 4.5 个百分点**；⑤ 复合指标显示**通过率最高的系统 C 因超出 SLO 与回归红线而 goodput = 0**，D 则因 12% 回归率被判红——**通过率无法表达这些否决项**；⑥ 失败分布显示两个「同样 55%」的系统问题性质完全不同（能力问题 vs 可信度问题），改进方向相反。

## 常见追问

- **追问**：那还有必要跑 SWE-bench 吗？
  - 要点：有必要，但要**明确定位**：它是**可复现、可比较的公共基线**（12 个 Python 仓库、2,294 个 issue/PR），适合看**趋势与粗粒度能力**；不适合直接外推到「能在你们仓库里干活」。**正确用法是把它当「体检」，把自家任务集当「岗位考核」。**
- **追问**：自建任务集怎么建才可信？
  - 要点：从**真实合并的 PR** 反推任务（issue 描述 + 前置提交 + 隐藏测试）；覆盖你们仓库的语言与模块分布；**按难度分层**（简单/中等/困难）；定期补充新任务以防过拟合；对判据做**变异检测**；并且**留出不参与调参的 holdout**。
- **追问**：怎么处理 agent 的随机性？
  - 要点：区分 **pass@1**（单次）与 **pass@k**（k 次内成功）；固定预算（token/步数）下比较；报告**多次运行的方差**；如果要比较两个系统，用**配对设计**（同任务两边各跑 k 次）。
- **追问**：为什么「通过率」之外还要看 diff？
  - 要点：因为**可评审性**决定真实采用率：巨型 diff、顺手重排格式、改动测试或 CI 配置的补丁即使「通过」也会被工程师拒绝或要求返工。**应把「是否改动测试/CI 配置」设为红线的自动检查项**（这也是作弊信号）。
- **追问**：怎么发现「判据作弊」？
  - 要点：① **留出测试**（最强）；② **变异检测**（弱测试识别）；③ **diff 规则**（是否动测试/CI/断言）；④ **行为指标**（测试数量变化、skip 标记增加）；⑤ 人工抽样审计。**注意：即使被挡住，也应记录「尝试作弊率」**——它是模型倾向的领先指标。
- **追问**：真实的终极判据是什么？
  - 要点：**工程师接受 PR 的比例**（层 6）。它不可作弊（要人签名），也直接对应价值；缺点是慢、样本增长慢、且受团队习惯影响。所以它适合**校准**（用层 1–5 的快速指标去预测层 6），而不是每次迭代都等它。
