## 一句话答案

> 先诊断再动手——「一半时间在找代码」通常不是模型笨，而是**四类结构性原因**之一：
> ① **没有地图**：agent 不知道仓库结构与入口，只能靠关键词试探（**最大的浪费源**）；
> ② **检索工具粒度不对**：返回整个文件/一大段日志，而不是「文件:行 + 少量上下文」；
> ③ **没有记忆**：同一个位置被反复找到又忘掉（重复搜索率很高）；
> ④ **不会用「任务线索」**：issue/报错栈/测试名/最近提交本来就能直接指向文件，却被忽略。
> **按杠杆排序的五个动作**：
> 1. **构建仓库地图**（一次性、作为稳定前缀缓存）：文件树 + 关键符号（函数/类/接口）+ 入口点（main、路由、测试目录）+ 依赖关系摘要。**它让「找」变成「看」**；
> 2. **升级检索工具**：符号/定义跳转（「谁定义了这个函数」「谁调用了它」）优先于纯文本正则；文本搜索返回**命中行 + 少量上下文**；
> 3. **结构化工作集**（scratchpad）：把「已确认相关文件、关键符号、未解问题」写进一个固定格式的区域，**跨步复用**（这正是「share context」在同一 agent 内部的形态）；
> 4. **利用任务线索**：优先解析**报错栈、失败的测试名、issue 里提到的路径**，直接跳到候选文件，再验证；
> 5. **预算与去重**：给检索设**步数/时间预算**，并对**查询做哈希去重**（同一个查询不重复发）；超过预算就换策略（读地图 / 直接读候选文件 / 请人确认）。
> 一句话判据：**衡量指标不是「搜了多少次」，而是「到第一次编辑的步数与 token」**——把它当延迟来优化，而不是当搜索质量来优化。

## 面试官在考什么

- **是否先量化**：能不能给出「搜索占第一轮时间比例」「到第一次编辑的步数」「重复查询率」这类指标，而不是凭感觉优化。
- **区分「找不到」与「读了太多」**：前者是检索问题，后者是**工具返回粒度**问题——两者解法不同，混在一起会做错优化。
- **地图的价值**：能否主动提出「仓库地图/符号索引」以及它作为**稳定前缀**可缓存（省钱且稳定）；并说明维护成本（增量更新）。
- **线索驱动**：能否指出「失败测试名/报错栈/issue 路径」是最强的定位信号（**直接从证据出发**，而不是从关键词出发）。
- **工作集/记忆**：能否设计一个结构化的 scratchpad（相关文件、关键符号、已排除项、未决问题），并说明它与「上下文压缩」的关系。
- **预算与终止**：检索也要有预算与退避策略（避免无限搜索 → 这正是 [[agents-09]] 的终止问题在检索层的体现）。
- **评估**：能否构造一个**定位评测集**（issue → 正确文件集合），测 **hit@k** 与**到首次编辑的步数**，并做 A/B。
- **不要过度工程**：是否会指出「不要一上来就上向量库/语义检索」——仓库**符号结构本身**就是最好的索引（串 [[cognition-01]] 的砍需求清单）。

**常见错误答案**

- 直接上向量数据库/语义检索（在代码这种强结构域往往不如符号索引 + 正则）。
- 让 agent「多读几个文件」（读得越多越慢，且噪声挤占上下文）。
- 不做去重与预算（同一个查询反复发）。
- 忽略失败测试名与报错栈这类**免费线索**。
- 只优化搜索工具，不优化「返回内容的结构」（返回整文件 → 继续烧 token）。
- 没有评测（改完不知道有没有变快）。

## 原理与推导

### 1. 诊断：把「找代码」拆成可测的四段

$$\text{定位成本}=\underbrace{n_{\text{查询}}\times c_{\text{查询}}}_{\text{搜索次数}}+\underbrace{V_{\text{读取}}\times c_{\text{token}}}_{\text{读入体积}}+\underbrace{n_{\text{重复}}\times c_{\text{查询}}}_{\text{重复劳动}}+\underbrace{c_{\text{重定向}}}_{\text{走错方向}}$$

| 症状 | 归因 | 修法 |
| --- | --- | --- |
| 查询次数多、命中率低 | 没有地图/线索 | 地图 + 线索解析 |
| 查询少但 token 高 | 返回粒度太粗 | 结构化返回（命中行 + 上下文） |
| 同一查询反复出现 | 没有工作集/记忆 | scratchpad + 查询去重 |
| 读了很多文件仍找不到 | 检索方式错（文本 vs 符号） | 符号索引/定义-引用跳转 |

**先测这四项**——否则容易在「换嵌入模型」上浪费一周。

### 2. 仓库地图（最高杠杆的一项）

一份好地图包含（**预算 3–8k token 量级**）：

| 组成 | 内容 | 作用 |
| --- | --- | --- |
| 目录骨架 | 目录树（2–3 层）+ 每目录一句话 | 知道去哪找 |
| 关键符号 | 按文件列出的类/函数/接口签名 | 直接定位实现 |
| 入口点 | main、HTTP 路由、CLI、测试目录 | 从行为反推代码 |
| 依赖摘要 | 模块间依赖（谁 import 谁） | 判断影响面 |
| 约定 | 命名/测试/构建命令 | 少走弯路 |

**维护**：地图随提交增量更新；把它放在**稳定前缀**位置以命中缓存（串 [[anthropic-22]] 的 prefix caching），这样每步的重复成本大幅下降。

### 3. 检索工具的分层（从强到弱）

1. **符号级**：`find_definition(symbol)`、`find_references(symbol)`——**最强**，因为代码有结构；
2. **结构化文本**：正则 + 文件类型过滤（返回 `文件:行` + 命中上下文）；
3. **路径/命名约定**：例如 `src/<feature>/` 或 `test_<module>.py`；
4. **语义检索**：自然语言意图（「验证码过期是怎么处理的」）——**最后才用**，且要与前几层组合（先用语义找候选，再用符号确认）；
5. **线索解析**：报错栈、测试名、issue 引用路径 → **直接跳候选**。

**关键**：工具应当返回**足够判断的片段**并**附带「下一步建议」**（例如「该文件还有 3 处同名函数」），而不是把整文件塞回去。

### 4. 工作集（scratchpad）：把「找到的」变成「记住的」

固定字段（结构化 → 易于复用与压缩）：

```
已确认相关文件：path:line（为什么相关，一行）
关键符号：name -> 定义位置 / 被谁调用
已排除：path（为什么不相关）        ← 避免重复探索
未决问题：…
下一步：…
```

**为什么有效**：把 $O(n)$ 的重复搜索变成 $O(1)$ 的查表；同时它是**压缩的锚点**——上下文压缩时优先保留工作集（串 [[cognition-01]] 的上下文工程）。

### 5. 预算与去重

- **检索预算**：例如「最多 12 次检索或 90 秒」；超预算 → 换策略（读地图 → 读候选 → 请人确认）；
- **查询去重**：对查询归一化（小写、去空白、排序关键词）后哈希，命中则直接返回缓存结果；
- **退避**：连续 k 次零命中 → 说明关键词方向错了，改为**从证据出发**（读报错栈/测试）。

### 6. 评测：定位是可测的

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| hit@k | 正确文件出现在前 k 个候选中的比例 | 尽量高（k=5） |
| 到首次编辑的步数 | 从任务开始到第一次 edit 的步数 | **主要指标** |
| 检索 token 占比 | 检索相关 token / 总 token | 下降 |
| 重复查询率 | 重复查询数 / 总查询数 | → 0 |
| 定位成功率 | 最终找到正确位置的任务比例 | 上升 |

**构造评测集**：从历史 PR 里取「改动文件集合」作为正确答案（issue/PR 描述 → 文件集合），量级几十到几百条即可做 A/B。

```python
# 代码定位成本模型：查询命中率、返回粒度、工作集与去重、线索解析的叠加效果
import random
from dataclasses import dataclass, field
from typing import Dict, List, Optional, Set, Tuple

@dataclass
class Repo:
    files: int = 2_000                # 文件数
    target_files: int = 3             # 本任务真正相关的文件数
    symbols: int = 20_000             # 符号数

@dataclass
class Tools:
    """检索能力的开关：每一项对应上面推导里的一层"""
    structured_output: bool = False    # 返回命中行+上下文，而非整文件
    repo_map: bool = False             # 仓库地图（含符号索引）
    scratchpad: bool = False           # 工作集（跨步复用）
    dedup: bool = False                # 查询去重
    clue_parsing: bool = False         # 解析报错栈/测试名/issue 路径

def locate(repo: Repo, t: Tools, seed: int = 4) -> Dict[str, float]:
    """模拟一次"找到相关代码"的过程，返回步数与 token"""
    rnd = random.Random(seed)
    found: Set[int] = set()
    steps = 0
    tokens = 0
    queries: List[str] = []
    seen: Set[str] = set()
    dup = 0
    # 单次查询命中目标文件的概率（取决于能力）
    base_hit = 0.12
    if t.clue_parsing:
        # 线索：直接给出一个候选文件（命中率跃升），但只解一部分
        if rnd.random() < 0.75:
            found.add(rnd.randrange(repo.target_files))
            if t.structured_output:
                tokens += 400
            else:
                tokens += 6_000
            steps += 1
    hit_rate = base_hit
    if t.repo_map:
        hit_rate += 0.35                 # 地图直接指出相关模块
    if t.structured_output:
        hit_rate += 0.05                 # 返回粒度好 -> 更容易看出线索
    if t.scratchpad:
        hit_rate += 0.15                 # 工作集：从"已确认/已排除"出发，少走回头路
    while len(found) < repo.target_files and steps < 40:
        q = f"query-{rnd.randrange(50)}"
        key = q.lower().strip()
        if key in seen:
            dup += 1
            if t.dedup:
                continue                 # 去重命中：不计步数、不计 token
        seen.add(key)
        steps += 1
        tokens += 500 if t.structured_output else 6_000
        if rnd.random() < hit_rate:
            found.add(rnd.randrange(repo.target_files))
    return {"步数": steps, "token": tokens, "重复查询": dup,
            "命中全覆盖": 1.0 if len(found) >= repo.target_files else 0.0}

def run_configs(repo: Repo, n: int = 200) -> List[Tuple[str, Dict[str, float]]]:
    CFGS = [
        ("基线（纯文本搜索）", Tools()),
        ("+ 结构化返回", Tools(structured_output=True)),
        ("+ 仓库地图", Tools(structured_output=True, repo_map=True)),
        ("+ 工作集 + 去重", Tools(structured_output=True, repo_map=True,
                                scratchpad=True, dedup=True)),
        ("+ 线索解析（全部）", Tools(structured_output=True, repo_map=True,
                                 scratchpad=True, dedup=True, clue_parsing=True)),
    ]
    out = []
    for label, t in CFGS:
        agg = {"步数": 0.0, "token": 0.0, "重复查询": 0.0, "命中全覆盖": 0.0}
        for i in range(n):
            r = locate(repo, t, seed=1000 + i)
            for k in agg:
                agg[k] += r[k]
        out.append((label, {k: v / n for k, v in agg.items()}))
    return out

repo = Repo()
print("① 五种配置的定位成本（2,000 文件、3 个目标文件、200 次模拟取均值）")
print(f"  {'配置':<22} {'到首次编辑步数':>13} {'检索 token':>11} {'重复查询':>8} {'覆盖率':>7}")
results = run_configs(repo)
base = results[0][1]
for label, r in results:
    print(f"  {label:<22} {r['步数']:>13.1f} {r['token']:>11,.0f} "
          f"{r['重复查询']:>8.1f} {r['命中全覆盖']:>7.1%}")
print("  读法：**仓库地图是单点收益最大的一项**（直接指出相关模块，命中率跃升）；")
print("        结构化返回主要省 token；工作集 + 去重消掉重复劳动；线索解析让一部分任务一步到位")

print("\n② 相对基线的改进倍数")
for label, r in results[1:]:
    print(f"  {label:<22} 步数 {base['步数']/r['步数']:>5.2f}x  "
          f"token {base['token']/r['token']:>5.2f}x  覆盖率 {r['命中全覆盖']-base['命中全覆盖']:+.1%}")
print("  读法：把「到第一次编辑的步数」当主指标——它同时反映搜索质量与返工；")
print("        token 的下降幅度通常比步数更大（结构化返回是省 token 的主力）")

print("\n③ 地图体积与收益的权衡（大仓库收益更大）")
def map_benefit(repo_files: int, map_tokens: int = 6_000) -> Dict[str, float]:
    """地图的收益随仓库规模上升；成本是固定的一前缀 token（可缓存）"""
    hit_gain = min(0.45, 0.10 + 0.0002 * repo_files)
    saved_steps = hit_gain * 12                      # 少走的步数（示意）
    saved_tokens = saved_steps * 1_200               # 每步省下的检索 token
    return {"命中率提升": hit_gain, "省下步数": saved_steps,
            "省下检索token": saved_tokens, "地图成本token": map_tokens,
            "净收益token": saved_tokens - map_tokens}
print(f"  {'仓库规模':>8} {'命中率提升':>10} {'省下步数':>9} {'省下token':>10} "
      f"{'地图成本':>9} {'净收益':>9}")
for n in (200, 1_000, 5_000, 20_000):
    b = map_benefit(n)
    print(f"  {n:>8,} {b['命中率提升']:>10.1%} {b['省下步数']:>9.1f} "
          f"{b['省下检索token']:>10,.0f} {b['地图成本token']:>9,} {b['净收益token']:>9,.0f}")
print("  读法：小仓库里地图的净收益可能为负（简单 grep 就够），**大仓库才值得建索引** ——")
print("        这与「不要过度工程」是同一件事：先量仓库规模与检索占比，再决定投入")

print("\n④ 检索预算与退避策略（连续零命中就换方向）")
def search_with_budget(repo: Repo, budget: int = 12, miss_limit: int = 3,
                       use_clues: bool = True, targets: int = 6,
                       seed: int = 7) -> Dict[str, float]:
    """难任务（targets=6、基础命中率 0.15）：连续 miss_limit 次零命中后换"从证据出发"（命中率跃升）"""
    rnd = random.Random(seed)
    steps, misses, found, tokens = 0, 0, set(), 0
    switched = False
    hit_rate = 0.15
    while steps < budget and len(found) < targets:
        steps += 1
        tokens += 500
        if rnd.random() < hit_rate:
            found.add(rnd.randrange(targets))
            misses = 0
        else:
            misses += 1
            if misses >= miss_limit and not switched and use_clues:
                switched = True                       # 换成"从报错栈/测试名出发"
                hit_rate = 0.45
                misses = 0
    return {"步数": steps, "token": tokens, "命中数": len(found),
            "是否切换策略": 1.0 if switched else 0.0}

def avg_budget(budget: int, miss_limit: int, use_clues: bool, n: int = 100) -> Dict[str, float]:
    agg = {"步数": 0.0, "token": 0.0, "命中数": 0.0, "是否切换策略": 0.0}
    for i in range(n):
        r = search_with_budget(repo, budget=budget, miss_limit=miss_limit,
                               use_clues=use_clues, seed=2000 + i)
        for k in agg:
            agg[k] += r[k]
    return {k: v / n for k, v in agg.items()}

print(f"  {'配置':<30} {'步数':>6} {'token':>7} {'命中数':>6} {'切换率':>7}")
for label, b, ml, uc in (("预算 12、无退避", 12, 99, False),
                         ("预算 12、3 次零命中换方向", 12, 3, True),
                         ("预算 20、3 次零命中换方向", 20, 3, True),
                         ("预算 6、3 次零命中换方向", 6, 3, True)):
    r = avg_budget(b, ml, uc)
    print(f"  {label:<30} {r['步数']:>6.1f} {r['token']:>7,.0f} {r['命中数']:>6.2f} "
          f"{r['是否切换策略']:>7.0%}")
print("  读法：**预算 + 退避**能在有限步数内提高命中（把「继续瞎搜」换成「从报错栈/测试名出发」）；")
print("        这也是 agent 循环终止条件在检索层的体现（串 [[agents-09]]）")
```

预期输出要点（实跑）：① 五项配置**单调改善**：基线 32.7 步 / 19.6 万 token / 覆盖率 51%；**仓库地图是单点收益最大的一项**（9.8 步、覆盖率 100%）；结构化返回把 token 砍到 1.4 万（约 1/14）；工作集 + 去重与线索解析继续改善；② 相对基线的改进倍数显示 **token 降幅通常大于步数降幅**；③ 地图的净收益**随仓库规模上升**（小仓库里可能为负，所以「不要一上来就建索引」）；④ 在**难任务**（6 个目标文件、基础命中率 0.15）上，「预算 + 连续零命中换方向」能把命中数从 1.56 提升到 2.92（同样的 12 步预算），而单纯加大预算到 20 的收益主要来自切换而非预算本身——这是检索层的终止与退避策略。

## 常见追问

- **追问**：为什么不用语义检索/向量库？
  - 要点：代码是**强结构域**——符号、导入关系、命名约定本身就是最好的索引，符号级检索的精度通常高于嵌入相似度；语义检索适合「用自然语言描述意图」的场景（「这个校验逻辑在哪」），**作为补充而不是主力**，且要用符号检索做二次确认。
- **追问**：地图会不会过时？
  - 要点：会。做法是**增量更新**（按提交/push 触发）+ 标注「地图生成时间与提交号」，并让 agent 在地图与代码冲突时**以代码为准**（不要盲信地图）。
- **追问**：怎么让 agent「知道自己已经找过」？
  - 要点：把工作集写进**固定结构**（相关文件/关键符号/已排除/未决问题），并放在上下文的稳定位置；查询去重则用归一化哈希在工具层拦截（比让模型自觉可靠）。
- **追问**：第一次编辑太晚还有别的原因吗？
  - 要点：有——**过度规划**（先写长计划）、**过度确认**（反复读同一文件确认）、**测试先行但不会跑**（卡在环境）。所以要分别度量「检索步数」与「非检索步数」，否则会误判成检索问题。
- **追问**：如何做 A/B 而不被任务难度干扰？
  - 要点：用**同一批任务**（同 issue、同仓库快照）跑两种配置，比较配对差值；并分层看（小/中/大仓库、不同语言）。**别用不同任务集比较平均值。**
- **追问**：多 agent 扇出检索能解决这个问题吗？
  - 要点：只读扇出（多个搜索子 agent）确实能并行探索，但要注意**成本 ×N**与**上下文交接损失**；更划算的顺序是：先做地图 + 工具粒度 + 工作集（一次投入、持续受益），**再考虑扇出**（串 [[cognition-02]]）。
