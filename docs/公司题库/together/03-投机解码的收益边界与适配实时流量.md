## 一句话答案

> 先给「是什么」的一句话：**用小模型（或 n-gram、或额外的解码头）一次猜 $\gamma$ 个 token，再用大模型一次前向验证，接受前缀、拒绝处回退并重采样**。它的关键性质是**输出分布与直接采样严格等价**（不是近似），所以「质量保持」与接受率无关——接受率低只是慢，不是差。
> 但本题的重点在三个「何时」：
> ① **何时有帮助**：**decode 阶段算力闲置**（小 batch、带宽受限）时，验证 $\gamma$ 个候选几乎不增加这一步的耗时——闲置算力是免费额度。可引用的量级：batch=1 跑 70B bf16 时算术强度约 1 FLOP/byte，H100 上的算力利用率不到 1%。
> ② **何时有害**：三种情况——**算力已饱和**（大 batch / 高 QPS 下验证的 $(\gamma+1)$ 倍 FLOPs 直接变成耗时，吞吐下降）、**接受率过低**（draft 与 target 不同族、领域偏移、温度很高，$\gamma$ 个候选第一轮就被拒，白跑 draft）、**收益被摊薄**（输出只有几个 token，或时延由 TTFT/prefill 主导，省下的 decode 步微不足道）。
> ③ **为什么必须适配实时流量**：**接受率是流量属性，不是模型属性**——同一个 draft/target 组合，在代码补全（高复述、高接受率）和开放式创作（低接受率）上的 $\alpha$ 可能差一倍以上；同一租户在不同时段的任务也不同。因此「选一个固定 $\gamma$ 与固定 draft」必然在某些流量上亏钱（白跑 draft）或在另一些流量上浪费额度（$\gamma$ 太小）。**正确做法是把 $\gamma$（以及是否启用、用哪个 draft）做成在线策略**：按可观测的接受率与当前系统负载（批大小/是否算力饱和）动态调整。
> 一句话判据：**投机解码是把闲置算力换成延迟的手段；一旦算力不闲置或接受率太低，它就从收益变成税。**

## 面试官在考什么

- **等价性是否讲对**：接受规则是 $\min(1,p/q)$ 加残差分布重采样，输出分布**精确等价**于从 target 直接采样。把「温度=0 时等价」或「近似」说出来都是硬伤。
- **收益的三个变量**：接受率 $\alpha$、猜测长度 $\gamma$、draft 相对 target 的代价比 $c$；以及**验证导致的 FLOPs 放大** $(\gamma+1)/(\mathbb{E}[A]+1)$。能写出这两个式子，就说明真懂（串 [[inference-serving-04]] 有完整推导）。
- **危害的三种来源**：算力饱和、低接受率、收益被摊薄——能否结合自己的部署场景说清（例如「我们的 batch 常年 100+，所以投机默认关闭，只在低峰开启」）。
- **「适配实时流量」的具体机制**：这是本题的题眼。能否给出可执行的策略——**在线测量接受率**（接受 token 数 / 草稿 token 数）、按租户/任务类型分桶、动态调 $\gamma$、必要时切换或关闭 draft、以及**与调度器的预算协商**（投机多算的 FLOPs 会挤占 chunked prefill 的预算）。
- **draft 的来源与取舍**：小模型（同族/同 tokenizer 很关键）、n-gram 检索式（复述场景 $c\approx0$，无重复片段时完全失效）、Medusa/EAGLE 式额外头（省掉独立模型但改动模型结构）、MTP（训练进模型）。
- **监控与回归**：接受率的分位（不只是均值）、每租户视角、以及「开启投机后 p99 是否变差」。
- **诚实**：承认在自己的流量分布下投机可能永远不划算——**不做没有收益的优化**也是判断力。

**常见错误答案**

- 「投机解码用近似来加速」——等价性讲错。
- 「接受率越高越好，所以把 $\gamma$ 开大」——忽略 FLOPs 放大与算力饱和。
- 「选一个固定的 draft 与 $\gamma$ 就行」——没有适配流量的机制（这正是本题追问点）。
- 忽略 draft 自身的显存与 KV 开销（在显存吃紧时挤压 batch 上限）。
- 只看平均值，不看接受率与收益在租户/时段上的分布。

## 原理与推导

### 1. 收益公式（复习口径，详细推导见 [[inference-serving-04]]）

设接受率 $\alpha$、草稿长度 $\gamma$、draft 相对 target 的每 token 代价比 $c$。一次投机循环期望产出 $\mathbb{E}[A]=\frac{1-\alpha^{\gamma+1}}{1-\alpha}$ 个 token，耗时约 $1+c\gamma$ 个 target 步的等效时间，因此

$$\text{speedup}\approx\frac{\mathbb{E}[A]}{1+c\gamma}$$

**结论**：$c$ 越小（n-gram 几乎为 0）、$\alpha$ 越高，越值得加大 $\gamma$；反之 $\gamma$ 大就是纯浪费。验证带来的 FLOPs 放大为 $\frac{\gamma+1}{\mathbb{E}[A]+1}$——**这就是「算力饱和时投机变税」的定量来源**。

### 2. 接受率是流量属性：为什么会漂移

| 流量类型 | 典型 $\alpha$ | 原因 |
| --- | --- | --- |
| 代码补全 / 摘要改写（复述多） | 高（0.7–0.9） | 输出大量来自输入，n-gram 都能猜中 |
| 结构化输出（JSON/SQL） | 高 | 模板化、低熵 |
| 开放式创作 / 头脑风暴 | 低（0.3–0.5） | 高熵，draft 与 target 分歧大 |
| 高温度采样 | 低 | 分布被摊平，接受概率下降 |
| 多语言/领域外 | 低 | draft 训练分布不匹配 |

**关键**：一个多租户平台**同时**承载以上所有类型；如果按平均 $\alpha$ 配一个 $\gamma$，那么高 $\alpha$ 流量吃亏（$\gamma$ 太小）、低 $\alpha$ 流量被收税（$\gamma$ 太大）。

### 3. 在线适配策略（三件套）

1. **测量**：按请求（或滑动窗口）统计 $\alpha=\frac{\text{被接受的草稿 token}}{\text{草稿 token 总数}}$、以及实际 speedup；
2. **决策**：目标是最大化吞吐且不违反 TPOT SLO。给定当前负载：
   - 若**算力已饱和**（batch 大、GPU 利用率高）→ **关闭投机**（把算力让给更多请求）；
   - 若算力闲置且 $\alpha$ 高 → 调大 $\gamma$（例如 4→8）；
   - 若 $\alpha$ 低（< 盈亏平衡点）→ 调小 $\gamma$ 或换 draft（或关闭）；
3. **分桶**：按租户/任务类型（代码 vs 聊天 vs 结构化）选择不同的 draft 与 $\gamma$，并**按桶监控**。

**盈亏平衡**：由 speedup 公式反解 $\alpha$ 的下界——$c=0.1,\gamma=4$ 时需 $\alpha>0.287$；$c=1/70,\gamma=4$ 时只需 $\alpha>0.054$（口径见 [[inference-serving-04]]）。**这句话应当写进运维手册**：低于阈值就自动关闭。

### 4. 与调度器的相互作用（容易忽略）

投机在每个 decode 步里塞进 $\gamma$ 个候选，意味着**该步的 token 预算被占用更多**：

$$B_{\text{tok}}^{\text{可用}}=B_{\text{tok}}-\sum_{i\in S}\gamma_i$$

在 continuous batching 里，这直接减少能同时跑的序列数（或减少 chunked prefill 的块大小）。所以**投机不是免费的延迟优化**：它把「每步的算力」更多地分给少数序列，从而可能**降低整体吞吐**（在算力饱和时）或**抬高其他请求的 TTFT**。这就是为什么它必须与调度器协商预算（串 [[together-02]]）。

### 5. draft 的选择（按流量类型）

| draft 类型 | 代价 $c$ | 适用 | 失效场景 |
| --- | --- | --- | --- |
| n-gram / 检索式 | ≈0 | 复述、改写、代码补全 | 无重复片段 |
| 小模型（同族同 tokenizer） | 0.03–0.15 | 通用 | 领域外 |
| 额外解码头（Medusa/EAGLE 式） | 低 | 通用（需改模型） | 需训练 |
| MTP（训练进模型） | 最低 | 自研模型 | 不适用第三方模型 |

**工程注意**：draft 与 target **必须共享 tokenizer**，否则接受率会因分词差异无谓下降；draft 也占显存与 KV（例如 1B bf16 约 2 GB，占 80 GB 卡约 2.5%），在显存吃紧的部署里会挤压 batch 上限。

### 6. 监控指标（缺一个就会误判）

| 指标 | 用途 |
| --- | --- |
| 接受率 $\alpha$（按桶/分位） | 决定是否启用与 $\gamma$ |
| 每次循环接受长度 $\mathbb{E}[A]$ | 直接反映收益 |
| 实际 speedup（同负载对照） | 验证收益是否为真（要 A/B） |
| 验证 FLOPs 放大量 | 判断是否在给算力饱和的机器加税 |
| p99 TPOT（开/关对照） | 确认延迟没被个别长尾拖坏 |
| 白跑比例（草稿被拒比例） | 定位 draft 不匹配 |

## 数值与代码验证

### 表 1：投机在四种流量上的收益（$c=0.1$，公式计算）

| 流量 | $\alpha$ | $\gamma=2$ | $\gamma=4$ | $\gamma=8$ | $\gamma=12$ | 判读 |
| --- | --- | --- | --- | --- | --- | --- |
| 代码补全 | 0.85 | 2.14x | 2.65x | 2.85x | 2.66x | $\gamma\le$8 收益最高 |
| 结构化输出 | 0.75 | 1.93x | 2.18x | 2.06x | 1.77x | $\gamma\le$4 收益最高 |
| 开放式创作 | 0.45 | 1.38x | 1.27x | 1.01x | 0.83x | $\gamma\le$2 收益最高 |
| 高温度采样 | 0.25 | 1.09x | 0.95x | 0.74x | 0.61x | $\gamma\le$2 收益最高 |

**读法**：$\alpha$ 越高、$c$ 越小时 $\gamma$ 可以开大；$\alpha=0.45$ 时 $\gamma=8$ 已经贴着盈亏平衡（1.01×），$\alpha=0.25$ 时 **$\gamma\ge4$ 全部亏损**——此时唯一正确的策略是关闭投机，而不是调参。

### 表 3：盈亏平衡的接受率（可直接写进运维手册）

| $\gamma$ | 盈亏平衡 $\alpha$（$c=0.1$） | 盈亏平衡 $\alpha$（$c=1/70$） |
| --- | --- | --- |
| 2 | 0.171 | 0.028 |
| 4 | 0.287 | 0.054 |
| 8 | 0.445 | 0.103 |
| 12 | 0.546 | 0.146 |

**读法**：$c$ 越小（n-gram draft）阈值越低——这就是「draft 越便宜越敢多猜」的量化形态；低于阈值应当**自动关闭**。

### 表 2：固定 $\gamma$ vs 自适应 $\gamma$（非平稳流量，实测）

| 策略 | 相对吞吐 | 白跑草稿比例 | 启用比例 |
| --- | --- | --- | --- |
| 固定 γ=8 | 1.468× | 61.1% | 100.0% |
| 固定 γ=4 | 1.488× | 36.3% | 100.0% |
| 自适应 | 1.542× | 30.1% | 85.0% |

**读法**：固定 $\gamma=8$ 的白跑草稿比例最高（61.1%）且净吞吐最低（1.468×）；自适应策略在高 $\alpha$ 时段加大 $\gamma$、在高负载或低 $\alpha$ 时段关闭，净吞吐最高（1.542×）而白跑比例最低（30.1%）——**这就是「让 speculator 适配实时流量」的收益**。

### 可运行代码

```python
# 投机解码的收益公式 + 在线自适应策略（非平稳流量：代码/结构化/创作/高温度交替）
import math, random
from dataclasses import dataclass, field
from typing import Dict, List, Tuple

def expected_accept(alpha: float, gamma: int) -> float:
    """一次投机循环期望产出的 token 数 E[A]=(1-alpha^(gamma+1))/(1-alpha)"""
    if alpha >= 1.0:
        return gamma + 1
    if alpha <= 0.0:
        return 1.0
    return (1 - alpha ** (gamma + 1)) / (1 - alpha)

def speedup(alpha: float, gamma: int, c: float = 0.1) -> float:
    """相对无投机的加速比；<1 表示亏损"""
    return expected_accept(alpha, gamma) / (1 + c * gamma)

def flops_amplification(alpha: float, gamma: int) -> float:
    """验证导致的 FLOPs 放大 (gamma+1)/(E[A]+1)"""
    return (gamma + 1) / (expected_accept(alpha, gamma) + 1)

print("① 收益的两个公式（c=0.1：draft 每 token 代价为 target 的 10%）")
print(f"  {'流量 alpha':>10} " + " ".join(f"{'γ='+str(g):>8}" for g in (2, 4, 8, 12)))
for alpha in (0.85, 0.75, 0.45, 0.25):
    row = " ".join(f"{speedup(alpha, g):>7.2f}x" for g in (2, 4, 8, 12))
    print(f"  {alpha:>10.2f} {row}")
print("  读法：alpha 高时 γ 越大越好；alpha=0.45 时 γ=8 已经开始亏；")
print("        alpha=0.25 时任何 γ 都亏（此时唯一正确的策略是关闭投机）")

print("\n② 盈亏平衡的接受率（speedup=1 时反解 alpha，二分法）")
def breakeven_alpha(gamma: int, c: float = 0.1) -> float:
    lo, hi = 0.0, 0.999
    for _ in range(60):
        mid = (lo + hi) / 2
        if speedup(mid, gamma, c) < 1.0:
            lo = mid
        else:
            hi = mid
    return hi
for g in (2, 4, 8, 12):
    print(f"  γ={g:>2}: 需要 alpha > {breakeven_alpha(g):.3f}（c=0.1）；"
          f"c=1/70 时只需 > {breakeven_alpha(g, 1/70):.3f}")
print("  读法：这两行应当写进运维手册 —— 低于阈值自动关闭，而不是靠人盯")

print("\n③ 非平稳流量下的策略对照（4 个时段交替，每段 1000 个请求）")
@dataclass
class Phase:
    name: str
    alpha: float
    load: float            # 0-1：算力饱和度（1=满载）
    share: float           # 请求占比
PHASES = [Phase("代码补全", 0.85, 0.35, 0.30),
          Phase("结构化输出", 0.75, 0.45, 0.20),
          Phase("开放式创作", 0.45, 0.60, 0.35),
          Phase("高温度采样", 0.25, 0.75, 0.15)]

def throughput(strategy: str, c: float = 0.1) -> Dict[str, float]:
    """返回相对无投机的吞吐、白跑草稿比例、启用比例。
    关键约束：算力已饱和（load 高）时，验证的额外 FLOPs 会挤占其他请求 -> 净收益要打折。"""
    total_req = 0
    gain = 0.0
    wasted_draft = 0.0
    drafted = 0.0
    enabled = 0
    for ph in PHASES:
        n = int(1000 * ph.share)
        total_req += n
        if strategy == "fixed8":
            gamma = 8
        elif strategy == "fixed4":
            gamma = 4
        else:                                    # adaptive
            if ph.load > 0.7:                    # 算力饱和 -> 关闭
                gamma = 0
            else:
                # 选择使 speedup 最大的 γ（不超过 12），并要求超过盈亏平衡
                cands = [g for g in (0, 1, 2, 4, 8, 12) if g == 0 or alpha_ok(ph.alpha, g, c)]
                gamma = max(cands, key=lambda g: 1.0 if g == 0 else speedup(ph.alpha, g, c))
        if gamma == 0:
            gain += n * 1.0
            continue
        enabled += n
        sp = speedup(ph.alpha, gamma, c)
        # 算力饱和惩罚：额外 FLOPs 挤占其他请求，净收益 = 1 + (sp-1)*(1-load)
        net = 1 + (sp - 1) * (1 - ph.load)
        gain += n * max(net, 0.5)                # 下限 0.5 表示严重时反而变慢
        drafted_tokens = n * gamma
        accepted = n * expected_accept(ph.alpha, gamma)
        wasted_draft += max(0.0, drafted_tokens - accepted)
        drafted += drafted_tokens
    return {"吞吐": gain / total_req, "白跑比例": wasted_draft / drafted if drafted else 0.0,
            "启用比例": enabled / total_req}

def alpha_ok(alpha: float, gamma: int, c: float) -> bool:
    return speedup(alpha, gamma, c) > 1.0

print(f"  {'策略':<12} {'相对吞吐':>9} {'白跑草稿比例':>13} {'启用投机的请求占比':>18}")
for st, label in (("fixed8", "固定 γ=8"), ("fixed4", "固定 γ=4"), ("adaptive", "自适应")):
    r = throughput(st)
    print(f"  {label:<12} {r['吞吐']:>8.3f}x {r['白跑比例']:>12.1%} {r['启用比例']:>17.1%}")
print("  读法：固定大 γ 在低 alpha 与高负载时段被收税（白跑比例高）；")
print("        自适应策略在高 alpha 时段加大 γ、在高负载/低 alpha 时段关闭 —— 这才是「适配实时流量」")

print("\n④ 与调度器的预算冲突：投机占用的 token 预算")
def batch_with_speculation(token_budget: int, gamma: int, seqs: int) -> int:
    """每步预算 B 里被投机占掉 gamma*seqs 后，还能跑多少序列（示意模型）"""
    per_seq = (gamma if gamma else 1)
    return max(0, token_budget // per_seq)
for gamma in (0, 4, 8):
    print(f"  γ={gamma}: 预算 256 时可同时进行的序列约 {batch_with_speculation(256, gamma, 8)} 条")
print("  读法：投机把每步算力更多地分给少数序列 —— 算力饱和时它会降低并发（吞吐），")
print("        所以必须和调度器（chunked prefill 的预算）一起决策，而不是各自优化（串 [[together-02]]）")

print("\n⑤ 在线测量：接受率的分桶统计（平台视角）")
@dataclass
class Bucket:
    name: str
    alpha: float
    reqs: int
buckets = [Bucket("代码", 0.86, 12000), Bucket("结构化", 0.74, 5000),
           Bucket("创作", 0.42, 20000), Bucket("多语言", 0.30, 3000)]
avg = sum(b.alpha * b.reqs for b in buckets) / sum(b.reqs for b in buckets)
print(f"  {'桶':<8} {'alpha':>6} {'请求占比':>9} {'建议 γ':>7}")
for b in buckets:
    best = max([0, 1, 2, 4, 8, 12], key=lambda g: 1.0 if g == 0 else speedup(b.alpha, g))
    print(f"  {b.name:<8} {b.alpha:>6.2f} {b.reqs/sum(x.reqs for x in buckets):>9.1%} {best:>7}")
print(f"  全体平均 alpha = {avg:.2f} —— 若按平均值配一个 γ，会让高 alpha 桶吃亏、低 alpha 桶被收税；")
print("  所以监控必须**按桶**看，策略也必须**按桶**决策")
```

预期输出要点（实跑）：① 收益表显示 $\alpha=0.85$ 时 $\gamma=8$ 有 2.85× 收益，$\alpha=0.45$ 时 $\gamma=8$ 已贴着盈亏平衡（1.01×），$\alpha=0.25$ 时 $\gamma\ge4$ 全部亏损——**低接受率下唯一正确的策略是关闭投机**；② 盈亏平衡表给出可直接写进运维手册的阈值（$c=0.1$、$\gamma=4$ 需 $\alpha>0.287$；$c=1/70$ 只需 $>0.054$）；③ 非平稳流量对照显示**固定 $\gamma=8$ 白跑草稿 61.1%、净吞吐 1.468×，固定 $\gamma=4$ 为 36.3%/1.488×，自适应为 30.1%/1.542×**——自适应同时取得最高吞吐与最低浪费；④ 预算冲突显示投机把每步算力集中到少数序列上（预算 256、$\gamma=8$ 时可并行的序列数明显下降）——**这就是「投机必须与调度器共同决策」的原因**；⑤ 分桶统计显示全体平均 $\alpha$ 会把决策带偏（代码桶该用大 $\gamma$、创作桶该用小 $\gamma$ 或不启用）。

## 常见追问

- **追问**：温度=0（greedy）时投机还等价吗？
  - 要点：greedy 是分布退化的特例，接受规则仍成立（草稿 token 与 target argmax 一致即接受），等价性不破坏；但**温度=0 时残差重采样退化为取 argmax**，实现要小心（串 [[llm-internals-12]]）。
- **追问**：n-gram draft 什么时候最有用？
  - 要点：输出大量复述输入时（摘要、改写、代码编辑、RAG 引用、工具参数拼接）——$c\approx0$ 且接受率高；一旦没有重复片段（自由创作）就完全失效，因此它适合**按桶启用**，不适合全局默认开启（串 [[together-03]] 的分桶策略）。
- **追问**：如何在线测接受率而不引入额外开销？
  - 要点：接受率天然是引擎里的计数器（接受 token / 草稿 token），只需按请求/按桶聚合上报；不要另做采样评估（那会引入偏差与成本）。
- **追问**：为什么开启投机后 p99 反而变差？
  - 要点：三个可能——① 算力饱和时验证挤占预算，其他请求的 TPOT 变慢；② 低接受率时白跑的 draft 延长了这一步；③ draft 模型的显存挤占了 batch 上限（并发下降）。诊断方法是按桶看接受率、并对同一负载做开/关对照。
- **追问**：如何在多租户下公平？
  - 要点：把投机视为**按租户可选的加速档**（并在定价上体现），或对低接受率租户自动降级；同时监控「某租户的投机是否在消耗共享算力而没有收益」（串 [[together-04]] 的定价与 [[together-06]] 的共享池治理）。
- **追问**：Medusa/EAGLE/MTP 与「小模型 draft」相比怎么选？
  - 要点：小模型 draft 不需要改模型、最易落地但多占显存；额外解码头省掉独立模型但要训练且改结构；MTP 训练进模型（自研场景最优）；选择依据是**你能改模型吗 + 显存预算 + 目标流量的接受率**。
