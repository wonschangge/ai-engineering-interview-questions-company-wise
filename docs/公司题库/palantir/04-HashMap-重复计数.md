## 一句话答案

> **"重复计数"这个说法本身就是线索**——**真正的 bug 通常不是"多加了 1"，而是"键的同一性判断错了"**：**可变键、归一化缺失、状态污染、溢出。**
> **★ 量化一：可变键（mutable key）—— 条目"永久不可达"**
> | 情形 | 查询结果 |
> | --- | --- |
> | **插入 1 个条目后修改 key 的字段** | **查得 0（应为 1）** |
> | 不可变键（对照） | **查得 1（正确）** |
> **读法**：**哈希值依赖可变字段 → 改字段后条目落在错误的桶里 → 任何等值键都查不到**。**它不报错**（**字典里确实有 1 个条目，只是永远访问不到**）——**这是"计数凭空少了"最典型的来源**。**修法**：**key 用不可变类型**（**字符串、元组、冻结的 dataclass**）。
> **★ 量化二：归一化缺失 —— 键数膨胀 4 倍**
> 输入 `['Alice','alice','Alice ','ALICE','alice']`（5 条记录）
> | 处理 | 不同键数 | 最高频项计数 |
> | --- | --- | --- |
> | **未归一化** | **4** | **`alice` = 2** |
> | **归一化（strip + casefold）** | **1** | **`alice` = 5** |
> **读法**：**键数膨胀 4 倍，而"最高频项"也判错了（2 vs 真值 5）**——**所以"去重"与"top-k"都会错**。**归一化必须在计数之前**；**常见来源**：**大小写、首尾空白、Unicode 组合字符（NFC/NFKC）、全角/半角**。
> **★ 量化三：状态污染 —— 一个实体的数据出现在另一个实体的报告里**
> | 实现 | userB 的报告 |
> | --- | --- |
> | **复用调用方的 map** | **`{'apple': 2, 'banana': 1, 'cherry': 1}`（含 userA 的 banana）** |
> | 每个实体独立 | **`{'apple': 1, 'cherry': 1}`（正确）** |
> **读法**：**"复用传入的 map"会让实体的数据互相污染**——**在 pipeline 里表现为"越跑越多"**（**串 [[palantir-06]]**）。
> **★ 量化四：计数器溢出**
> | 项 | 值 |
> | --- | --- |
> | **int32 上限** | **2,147,483,647** |
> | **加 1 之后** | **−2,147,483,648（回绕成负数）** |
> | 日活 1 亿的计数器 | **约 21.5 天后溢出** |
> **读法**：**"总数突然变负"是溢出的典型症状**——**修法**：**int64/大整数**，或**定期落库并重置（分桶计数）**。
> **★ 排查清单（按"最可能"排序）**：
> | # | 嫌疑人 | 症状 | 修法 |
> | --- | --- | --- | --- |
> | ① | **归一化缺失** | **键数比预期多** | **计数前 `strip().casefold()` + NFC** |
> | ② | **可变键** | **计数比预期少、查不到** | **用不可变 key** |
> | ③ | **状态污染** | **越跑越多、跨实体串数据** | **每次调用新建 map** |
> | ④ | **溢出** | **总数变负** | **int64 / 分桶** |
> | ⑤ | **遍历时修改** | **跳过/重复处理** | **先收集再修改** |
> | ⑥ | **并发写入** | **随机丢失更新** | **加锁 / `ConcurrentHashMap` / 原子计数** |
> 一句话判据：**"先问'预期的键数是多少' → 对比实际键数（多了是归一化、少了是可变键）→ 查跨调用状态 → 查溢出与并发"**。

## 面试官在考什么

- **★ 是否先问"预期的键数"**：**能否用"键数对比"快速定位方向**（**多了 → 归一化；少了 → 可变键**）。
- **★ 是否知道可变键的坑**：**能否指出"改字段后条目不可达"**（本机：**查得 0**）。
- **★ 是否想到归一化**：**能否指出"大小写/空白/Unicode"**（本机：**键数膨胀 4 倍**）。
- **是否检查跨调用状态**：**能否指出"复用 map 导致污染"**。
- **是否考虑溢出**：**能否说出 int32 的 21.5 亿上限**。
- **是否考虑并发**：**能否指出"`HashMap` 非线程安全"**。
- **是否考虑遍历时修改**：**能否指出"要先收集再修改"**。
- **是否写测试**：**能否给出"键数与计数都要断言"的测试**。
- **是否区分"计数"与"去重"**：**能否指出归一化影响两者**。
- **诚实**：**承认"这类 bug 往往需要看真实数据才能定位"**。

**常见错误答案**

- **只盯着"`+1` 写了几次"**（**不查键的同一性**）。
- **不检查归一化**（**键数膨胀看不出来**）。
- **用可变对象当 key**（**Java 里常见于实体类**）。
- **复用调用方的 map**（**状态污染**）。
- **不考虑溢出**（**"总数变负"当成业务异常**）。
- **在多线程里用普通 `HashMap`**（**丢失更新**）。
- **遍历时删除/添加**（**`ConcurrentModificationException` 或静默跳过**）。
- **测试只断言"计数"不断言"键数"**（**漏掉归一化 bug**）。

## 原理与推导

### 1. ★ 键的同一性

| 要素 | 要求 |
| --- | --- |
| **`hashCode`** | **稳定**（**插入后不变**） |
| **`equals`** | **与 `hashCode` 一致** |
| **可变性** | **不可变**（**或插入后不再修改**） |
| **归一化** | **在计数前完成** |

**读法**：**"`hashCode` 稳定"是硬要求**——**一旦 key 可变，条目就会"消失"**（**本机：查得 0**）。

### 2. ★ 归一化的四个来源

| 来源 | 例子 |
| --- | --- |
| **大小写** | **`Alice` / `alice` / `ALICE`** |
| **空白** | **`Alice ` / ` Alice`** |
| **Unicode 组合** | **`é`（1 码点）vs `e`+`´`（2 码点）** |
| **全角/半角** | **`Ａ` vs `A`** |

**读法**：**"Unicode 组合字符"是最隐蔽的**——**两个视觉相同的字符串可能不相等**（**要 `unicodedata.normalize('NFC', s)`**）。

### 3. 状态污染的三种形态

| 形态 | 表现 |
| --- | --- |
| **复用传入的 map** | **跨实体污染**（本机：**userB 报告含 userA 的项**） |
| **模块级全局 map** | **跨请求污染** |
| **可变默认参数** | **跨调用污染**（**Python 的经典坑**） |

**读法**：**"可变默认参数"是 Python 特有的**——**`def f(m={})` 会在多次调用间共享同一个字典**。

### 4. 溢出与精度

| 类型 | 上限 | 备注 |
| --- | --- | --- |
| **int32** | **2.1e9** | **日活 1 亿 → 21.5 天** |
| **int64** | **9.2e18** | **实际够用** |
| **float32** | **1.7e38（但精度 24 位）** | **计数超过 1.6e7 后无法精确表示整数** |
| **float64** | **精度 53 位** | **计数到 9e15 仍精确** |

**读法**：**"用浮点做计数"是一个隐藏的溢出**——**float32 在 1,677 万之后就不能精确表示每个整数了**（**串 [[palantir-06]] 的浮点累加**）。

### 5. 并发

| 做法 | 安全性 |
| --- | --- |
| **`HashMap`** | **不安全**（**丢失更新**） |
| **`ConcurrentHashMap` + `merge`** | **安全**（**推荐**） |
| **`LongAdder`** | **高并发下更快** |
| **加锁** | 安全但慢 |

**读法**：**"`map.merge(k, 1, Integer::sum)` 是原子的"**——**而 `get` + `put` 不是**（**两步之间有窗口**）。

### 6. 测试要点

| 测试 | 内容 |
| --- | --- |
| **键数断言** | **`len(counts) == expected_distinct`**（**抓归一化 bug**） |
| **总数守恒** | **`sum(counts.values()) == len(records)`**（**抓丢失/重复**） |
| **归一化用例** | **大小写、空白、Unicode** |
| **边界** | **空输入、单元素、全相同** |
| **并发** | **多线程写入后总数守恒** |

**读法**：**"键数 + 总数"两个断言能抓住绝大多数计数 bug**——**前者抓归一化、后者抓丢失/重复**。

### 可运行代码

```python
print('① 可变键（mutable key）：插入后改字段 -> 条目"消失"')
class BadKey:
    def __init__(self,name): self.name=name
    def __hash__(self): return hash(self.name)          # 依赖可变字段
    def __eq__(self,o): return isinstance(o,BadKey) and self.name==o.name
class GoodKey:
    def __init__(self,name): self.name=name
    def __hash__(self): return hash(self.name)
    def __eq__(self,o): return isinstance(o,GoodKey) and self.name==o.name
    def __repr__(self): return f'GoodKey({self.name})'
bad={}; k=BadKey('alice'); bad[k]=1; k.name='bob'        # 改了字段
print(f'  可变键：插入 1 个条目后改字段 -> 用新值查得 {bad.get(BadKey("bob"), 0)}（**应为 1**）')
print(f'         字典里实际有 {len(bad)} 个条目，但**无法用任何等值键查到**（哈希桶位置变了）')
good={}; g=GoodKey('alice'); good[g]=1
print(f'  不可变键：查得 {good.get(GoodKey("alice"), 0)}（**正确**）')
print("  读法：**「用可变对象当 key」会导致条目永久不可达** —— 计数「凭空少了」，")
print('        而且**不报错**（这是最典型的"重复/丢失计数"来源）；修法：key 用不可变类型')
print()
print('② 归一化缺失："Alice" / "alice" / "Alice " 被当成 3 个键')
raw=['Alice','alice','Alice ','ALICE','alice']
naive={}
for x in raw: naive[x]=naive.get(x,0)+1
norm={}
for x in raw:
    k=x.strip().casefold()
    norm[k]=norm.get(k,0)+1
print(f'  原始 {len(raw)} 条记录')
print(f'  未归一化：{len(naive)} 个不同键（{dict(naive)}）')
print(f'  归一化后：{len(norm)} 个不同键（{dict(norm)}）')
print(f'  **键数膨胀 {len(naive)/len(norm):.0f} 倍**，而"最高频项"也判错了（naive 给 alice=2，真值 5）')
print("  读法：**归一化必须在「计数之前」** —— 否则「去重」与「top-k」都会错；")
print('        常见来源：大小写、首尾空白、Unicode 组合字符（NFC/NFKC）、全角/半角')
print()
print('③ 复用同一个 map：跨实体污染（这才是真正的 bug）')
def count_items(items, m=None):
    m = {} if m is None else m        # **bug：复用了调用方传入的 map**
    for x in items: m[x]=m.get(x,0)+1
    return m
batches=[('userA',['apple','banana']),('userB',['apple','cherry'])]
shared={}
for ent,items in batches: count_items(items, shared)
print(f'  复用同一个 map：userB 的报告 = {shared}（**含 userA 的 banana**）')
reports={}
for ent,items in batches: reports[ent]=count_items(items)
print(f'  每个实体独立：userB 的报告 = {reports["userB"]}（**正确**）')
print('  读法：**"复用调用方的 map"会让一个实体的数据出现在另一个实体的报告里** ——')
print('        本机 userB 的报告多出 banana（属于 userA）；在 pipeline 里表现为"越跑越多"')
print()
print('④ 计数器溢出：int32 在 21.5 亿处回绕')
MAX32=2**31-1
print(f'  int32 上限 = {MAX32:,}；再加 1 -> {-2**31:,}（**回绕成负数**）')
print(f'  真实场景：日活 1 亿的计数器，累计 {MAX32/1e8:.1f} 天后溢出')
print('  读法：**"总数突然变负"是溢出的典型症状** —— 修法：用 int64/大整数，')
print('        或**定期把计数落库并重置**（分桶计数）')
```

预期输出要点（实跑）：① **可变键**：插入 1 个条目后改字段 → **查得 0（应为 1）**，不可变键对照查得 **1**；② **归一化**：5 条记录 → **未归一化 4 个键（最高频项 `alice` = 2）** vs **归一化 1 个键（`alice` = 5）**，**键数膨胀 4 倍**；③ **状态污染**：复用 map 时 **userB 的报告含 userA 的 `banana`**（`{'apple': 2, 'banana': 1, 'cherry': 1}`）vs 独立时 **`{'apple': 1, 'cherry': 1}`**；④ **溢出**：**int32 上限 2,147,483,647 → 加 1 得 −2,147,483,648**。

## 常见追问

- **追问**：怎么定位"到底哪一步重复计数"？
  - 要点：**三步二分**：① **在函数入口断言"键数 + 总数"**（**先确认输入没问题**）；② **在函数出口再断言一次**（**确认是本函数的锅**）；③ **在中间步骤打点**（**如果是多阶段聚合**）。**读法**：**"入口与出口都断言"是最有效的二分**——**它能立刻区分"上游数据脏"与"本函数有 bug"**。
- **追问**：Java 里可变键的典型场景是什么？
  - 要点：**三类**：① **用实体对象当 key 但 `equals`/`hashCode` 基于可变字段**（**如 `User` 的 `name`**）；② **用 `Date`/`Calendar` 当 key 然后 `setTime()`**；③ **用数组当 key**（**数组的 `hashCode` 是身份哈希，不是内容**）。**读法**：**"用数组/列表当 key"是另一类经典 bug**——**两个内容相同的数组不相等**。
- **追问**：归一化会不会"过度合并"？
  - 要点：**会，所以要谨慎**：① **`casefold()` 会把 `ß` 变成 `ss`**（**德语场景可能过度**）；② **`strip()` 会去掉有意义的空白**（**如代码/文本**）；③ **所以要按业务定义"同一性"**（**并写进文档**）。**读法**：**"归一化规则是业务决策"**——**不是技术细节**（**比如"Alice"与"alice"是不是同一个人**）。
- **追问**：并发下怎么保证计数正确？
  - 要点：**三条**：① **`ConcurrentHashMap.merge`**（**原子**）；② **`LongAdder`**（**高并发**）；③ **分片累加再合并**（**map-reduce**）。**注意**：**"分片合并"要求合并操作是结合的**（**加法满足**）。**读法**：**"分片 + 合并"是可扩展的做法**——**它同时解决并发与单点瓶颈**（**串 [[palantir-06]]**）。
- **追问**：怎么测"溢出"？
  - 要点：**两条**：① **单元测试直接构造接近上限的值**（**断言行为**——**是抛异常还是回绕**）；② **监控线上计数器的量级**（**接近上限就告警**）。**读法**：**"用接近上限的值做测试"**——**很多语言默认静默回绕**（**所以要显式选择"抛异常"或"用大整数"**）。
- **追问**：这道题与"三源客户去重"有什么关系？
  - 要点：**同一个"同一性"问题**：① **计数的 key 是"值"，去重的 key 是"实体"**；② **两者都要求"归一化规则明确"**；③ **实体解析还需要"模糊匹配"**（**串 [[palantir-07]]**）。**读法**：**"什么是同一个"是数据工程的核心问题**——**它在计数、去重、join 里反复出现**。
