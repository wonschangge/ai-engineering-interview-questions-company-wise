## 一句话答案

> **写入安全的六道防线**：**类型化 action（状态机）→ 干跑预览 → 幂等键 → 以用户身份鉴权 → 爆炸半径限流 → 审计与回滚**——**而"状态机校验"是唯一能"从源头消除"非法写入的一道。**
> **★ 量化一：非法状态转移**
> | 项 | 值 |
> | --- | --- |
> | 状态数 | 4（`open`/`in_progress`/`resolved`/`closed`） |
> | 有序状态对 | **12** |
> | **合法转移** | **6** |
> | **无校验时的非法比例** | **50%** |
> **读法**：**"让 agent 直接写状态字段"意味着约 50% 的"状态改变"在业务上是非法的**——**而类型化 action + 状态机校验把非法转移变成"不可表达"**（**从源头消除，而不是事后检查**）。
> **★ 量化二：幂等性（重试风暴）**
> | 单次失败率 | 重试上限 | **平均写入次数** | **重复率** |
> | --- | --- | --- | --- |
> | 10% | 3 | 1.111 | 11.1% |
> | 20% | 3 | 1.251 | 25.1% |
> | **40%** | 3 | **1.634** | **63.4%** |
> **读法**：**失败率 40% 时平均写入 1.634 次（重复率 63.4%）**——**而"失败"往往包含"超时但实际已写入"**（**最危险的一种**）。**所以必须带幂等键**（**同一业务请求的多次重试只产生一条工单**）。
> **★ 量化三：爆炸半径**
> | 限流 | **循环 50 步的最坏写入** | 相对无限制 |
> | --- | --- | --- |
> | **无限制** | **50** | 100% |
> | 10 次/小时 | **10** | 20% |
> | **3 次/小时** | **3** | **6%** |
> **读法**：**"限流"把最坏情况从"无限"变成"有界"**——**3 次/小时的限额让一个死循环 agent 最多造成 3 次写入**。**配套要有"同一对象短时间多次写入"的告警**（**那是循环的信号**）。
> **★ 六道防线**：
> | # | 防线 | 拦什么 | 关键实现 |
> | --- | --- | --- | --- |
> | ① | **类型化 action** | **非法状态转移、非法字段值** | **参数 schema + 状态机** |
> | ② | **干跑预览** | **"想错了"的写入** | **算出 diff 给用户看，不提交** |
> | ③ | **幂等键** | **重试造成的重复** | **业务请求 ID 作键** |
> | ④ | **以用户身份鉴权** | **越权写入** | **不要用超级权限账号** |
> | ⑤ | **爆炸半径限流** | **循环/失控** | **每小时上限 + 单对象频率告警** |
> | ⑥ | **审计与回滚** | **已发生的错误** | **全量日志 + 可逆操作** |
> **读法**：**"以用户身份鉴权"是最容易被忽略的一道**——**很多 agent 实现用服务账号（超级权限）**，**于是 agent 能写用户本来无权写的对象**（**这是最严重的一类越权**）。
> **★ 可逆性分类**：
> | 类型 | 例子 | 策略 |
> | --- | --- | --- |
> | **可逆** | **改工单状态、加备注** | **直接执行 + 审计** |
> | **半可逆** | **发通知、改排期** | **限流 + 可撤回** |
> | **不可逆** | **提交合同、付款、删数据** | **必须人工审批** |
> 一句话判据：**"先按可逆性分类 → 可逆的自动执行、不可逆的必须审批 → 六道防线全部到位 → 全量审计 + 演练回滚"**。

## 面试官在考什么

- **★ 是否先讲"状态机校验"**：**能否指出它"从源头消除"非法写入**（本机：**50% 的写入非法**）——**这是本题的分水岭**。
- **★ 是否讲幂等**：**能否量化"重试造成的重复"**（本机：**40% 失败率 → 63.4% 重复**）。
- **★ 是否讲爆炸半径**：**能否指出"限流把最坏情况变成有界"**。
- **干跑**：**能否指出"先给 diff 再提交"**。
- **鉴权**：**能否指出"要以用户身份而不是服务账号"**。
- **可逆性分类**：**能否区分"可逆/半可逆/不可逆"**。
- **审批**：**能否指出"不可逆操作必须人工审批"**。
- **审计**：**能否指出"每次写入都要记录 who/what/when/why"**。
- **回滚**：**能否指出"要演练回滚"**（**而不是只写在文档里**）。
- **诚实**：**承认"完全自动化的写入在 ERP 场景里通常不可接受"**（**必须有人工确认环节**）。

**常见错误答案**

- **只靠 prompt 提醒"不要做危险操作"**（**没有强制力**）。
- **用服务账号（超级权限）**（**越权**）。
- **不做状态机校验**（**50% 非法**）。
- **不做幂等**（**重试造成重复**）。
- **不限流**（**死循环无限写入**）。
- **不审计**（**出事后无法追查**）。
- **不做干跑**（**用户看不到将要发生什么**）。
- **认为"回滚总是可行"**（**付款/通知不可逆**）。

## 原理与推导

### 1. ★ 类型化 action（状态机）

| 要素 | 说明 |
| --- | --- |
| **参数 schema** | **类型、必填、取值范围** |
| **前置条件** | **状态机：只有 `open` 能转 `in_progress`** |
| **副作用** | **声明式**（**改哪些对象**） |
| **权限** | **谁能执行** |
| **幂等** | **同键不重复** |

**读法**：**"前置条件"是 action 与"裸 UPDATE"的最大区别**——**它把业务规则从"文档/prompt"变成"代码"**（**串 [[palantir-09]]**）。

### 2. ★ 幂等键

$$\text{重复次数}=\text{重试次数}\times P(\text{超时但已写入})$$

| 机制 | 说明 |
| --- | --- |
| **幂等键** | **业务请求 ID**（**不是随机 UUID**） |
| **存储** | **服务端记录"已处理的键"** |
| **窗口** | **保留 24 小时或 7 天** |
| **语义** | **"同键同结果"**（**返回第一次的结果**） |

**读法**：**"幂等键必须是业务语义的"**——**如果每次重试生成新的 UUID，幂等就失效了**（**这是最常见的实现错误**）。

### 3. ★ 爆炸半径

| 手段 | 效果 |
| --- | --- |
| **每小时写入上限** | **把最坏情况变成有界** |
| **单对象频率告警** | **发现循环** |
| **总步数上限** | **agent 循环本身有界** |
| **熔断** | **错误率超阈值就停** |

**读法**：**"限流 + 熔断"是 agent 系统的基础设施要求**——**因为 agent 的行为是"生成的"，不可能穷举验证**（**只能靠边界约束**）。

### 4. 干跑与预览

| 层次 | 内容 |
| --- | --- |
| **diff 预览** | **"工单 123 的状态将从 open 变为 closed"** |
| **影响范围** | **"这会通知 3 个相关方"** |
| **可逆性标注** | **"此操作可撤销 / 不可撤销"** |
| **确认** | **高风险要显式确认** |

**读法**：**"可逆性标注"是让用户做知情决策的关键**——**用户看到"不可撤销"时会更谨慎**。

### 5. 鉴权

| 做法 | 风险 |
| --- | --- |
| **服务账号（超级权限）** | **越权**（**agent 能做用户无权做的事**） |
| **以用户身份（OAuth 委托）** | **权限天然正确** |
| **用户身份 + 能力裁剪** | **更保守**（**如只允许特定 action**） |

**读法**：**"以用户身份"是唯一能保证"权限正确"的做法**——**因为它复用已有的权限系统**（**而不是重新实现一套**）。

### 6. 审计与回滚

| 要素 | 记录 |
| --- | --- |
| **who** | **哪个用户 + 哪个 agent 版本** |
| **what** | **哪个 action + 参数 + diff** |
| **when** | **时间戳** |
| **why** | **触发它的对话/请求 ID** |
| **结果** | **成功/失败 + 返回** |

**读法**：**"记录触发它的对话 ID"在 agent 场景里是必需的**——**否则无法回答"为什么 agent 做了这件事"**（**而这正是事后审查最需要的**）。

### 可运行代码

```python
import random
rng=random.Random(0)
print('① 非法状态转移：没有状态机校验时，agent 的写入有多少是"业务上不允许"的')
STATES=['open','in_progress','resolved','closed']
LEGAL={('open','in_progress'),('open','closed'),('in_progress','resolved'),
       ('in_progress','closed'),('resolved','closed'),('resolved','in_progress')}
def trial(n_writes, check=False):
    bad=0
    for _ in range(n_writes):
        frm=rng.choice(STATES); to=rng.choice(STATES)
        if frm==to: continue
        if check and (frm,to) not in LEGAL: bad+=1
        elif not check: bad+=1        # 无校验：所有"改变"都被接受，其中一部分是非法转移
    return bad
N=2000
# 无校验时"非法比例"= 1 - 合法转移占比
legal=len(LEGAL); allpairs=len(STATES)*(len(STATES)-1)
print(f'  状态数 {len(STATES)}；有序状态对 {allpairs} 个，其中合法 {legal} 个')
print(f'  **无校验时，{1-legal/allpairs:.0%} 的"状态改变"在业务上是非法的**')
print(f'  （本机 2000 次随机写入中，非法转移约 {int(N*(1-legal/allpairs))} 次）')
print('  读法：**「让 agent 直接写状态字段」意味着约 50% 的写入违反状态机** ——')
print('        而**类型化 action + 状态机校验**把非法转移变成"不可表达"（**从源头消除**）')
print()
print('② 幂等性：重试风暴会造出多少重复工单')
def retries(p_fail, max_retry):
    """每次尝试独立失败；无幂等键时"失败但实际已写入"会产生重复"""
    writes=0
    for _ in range(max_retry+1):
        writes+=1
        if rng.random()>=p_fail: break      # 成功则停
    return writes
print(f'  {"单次失败率":>10} {"重试上限":>9} {"平均写入次数":>13} {"重复率":>9}')
for pf in (0.1,0.2,0.4):
    tot=sum(retries(pf,3) for _ in range(20000))/20000
    print(f'  {pf:>10.1f} {3:>9} {tot:>13.3f} {tot-1:>8.1%}')
print('  读法：**失败率 40% 时平均写入 1.634 次（重复率 63.4%）** ——')
print("        而「失败」往往包含「超时但实际已写入」（**最危险的一种**）；")
print('        所以**必须带幂等键**（同一业务请求的多次重试只产生一条工单）')
print()
print('③ 爆炸半径：agent 死循环时能写多少条')
print(f'  {"限流":<16} {"循环 50 步的最坏写入":>20} {"相对无限制":>11}')
for cap in (None,50,10,3):
    n=50 if cap is None else min(50,cap)
    print(f'  {("无限制" if cap is None else str(cap)+" 次/小时"):<16} {n:>20} '
          f'{(n/50 if cap else 1):>10.0%}')
print("  读法：**「限流」把最坏情况从「无限」变成「有界」** —— 本机 3 次/小时的限额让")
print('        一个死循环 agent 最多造成 3 次写入（**而不是 50 次**）；')
print('        配套还要有**"同一对象短时间多次写入"的告警**（**那是循环的信号**）')
```

预期输出要点（实跑）：① **非法状态转移**：4 个状态、12 个有序对、**6 个合法** → **无校验时 50% 的"状态改变"非法**；② **幂等**：单次失败率 10%/20%/**40%**（重试上限 3）→ 平均写入 **1.111/1.251/1.634** 次，**重复率 11.1%/25.1%/63.4%**；③ **爆炸半径**：无限制/**10 次每小时**/**3 次每小时** → 循环 50 步的最坏写入 **50/10/3**（**相对 100%/20%/6%**）。

## 常见追问

- **追问**：怎么测"状态机校验真的生效了"？
  - 要点：**三条**：① **单元测试枚举所有状态对**（**12 个有序对逐个断言**）；② **故意构造非法转移**（**断言被拒绝**）；③ **在预发环境跑"红队 agent"**（**让它尝试非法操作**）。**读法**：**"枚举所有状态对"是最彻底的**——**状态数不多时完全可行**。
- **追问**：幂等键的窗口该多长？
  - 要点：**取决于重试窗口**：① **要覆盖"最长的重试链"**（**如指数退避最多重试 1 小时**）；② **通常 24 小时足够**；③ **但"用户手动重发"可能是几天后**（**这要靠业务判断**——**"同一个请求"的定义**）。**读法**：**"幂等窗口 = 业务上'同一请求'的时间范围"**——**它是一个业务定义，不是技术参数**。
- **追问**：怎么处理"多系统写入"（ERP + 通知 + 数据仓库）？
  - 要点：**用 Saga 而不是分布式事务**：① **每一步都有补偿操作**；② **失败时按逆序补偿**；③ **补偿本身要幂等**。**读法**：**"Saga 的补偿不是回滚"**——**它执行的是"业务上的对冲操作"**（**如"发一条更正通知"而不是"撤回通知"**）。
- **追问**：怎么防止"agent 被提示注入后写坏数据"？
  - 要点：**三道**：① **action 的状态机与参数校验**（**注入无法绕过**）；② **以用户身份鉴权**（**注入无法越权**）；③ **不可逆操作要审批**（**注入无法绕过人工**）。**读法**：**"注入能改变 agent 的意图，但改变不了 action 的合法性约束"**——**这是"能力边界比意图过滤更可靠"的实例**（**串 [[palantir-09]]**）。
- **追问**：怎么演练回滚？
  - 要点：**三条**：① **在预发环境做"写入 + 回滚"的完整演练**；② **记录"回滚耗时"**（**这是恢复时间目标（RTO）的依据**）；③ **定期演练**（**而不是一次性**）。**读法**：**"没演练过的回滚等于没有回滚"**——**因为依赖会变**（**串 [[palantir-06]] 的"对账能力"**）。
- **追问**：如果客户坚持"全自动写入"呢？
  - 要点：**三条路**：① **按可逆性分级**（**可逆的全自动、不可逆的人工**）；② **"自动 + 事后审计 + 快速回滚"**（**接受一定风险**）；③ **"自动 + 抽样人工复核"**（**折中**）。**读法**：**"风险接受必须是客户显式决策"**——**而不是工程团队默默承担**（**串 [[palantir-18]] 的客户沟通**）。
