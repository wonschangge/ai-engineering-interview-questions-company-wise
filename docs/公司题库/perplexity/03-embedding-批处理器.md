## 一句话答案

> **这是一个装箱问题**：**"固定批大小"会浪费容量，因为文本长度是重尾的、而约束是 token 上限**——**FFD（长优先）能把批数降到最少。**
> **★ 量化一：为什么"固定批大小"会浪费**
> | 项 | 值 |
> | --- | --- |
> | 文本长度中位数 | **245 token** |
> | p90 | **1,139 token** |
> | 最大 | **8,000 token** |
> | **条数上限 × 中位数** | **$256\times245=62{,}720$** |
> | **token 上限** | **20,000** |
> **读法**：**$256$ 条 × 中位数 $245$ token 就已经 $62{,}720$ token，远超 $20{,}000$ 的上限**——**所以约束是 token 而不是条数**。**这正是"固定批大小"会浪费的原因**（**长文本会让批次提前撑满，短文本填不满**）。
> **★ 量化二：三种装箱策略**
> | 策略 | **批数** | **token 利用率** | 相对最少 |
> | --- | --- | --- | --- |
> | 固定批大小（原始顺序） | 527 | **94.1%** | 1.05× |
> | **FFD（长优先）** | **502** | **98.8%** | **1.00×** |
> | 升序贪心（短优先） | 527 | 94.1% | 1.05× |
> **读法**：**FFD（长优先）批数最少、利用率最高**——**因为长文本先放、短文本填空隙**；**而"短优先"反而更差**（**短文本先占满批次，长文本无处可放**）。**本机的收益是 5%**（**真实场景中长度分布更极端时收益更大**）。
> **★ 量化三：批数 = 请求数 = 成本**
> | 策略 | 批数 | 若每请求 50ms 的串行耗时 |
> | --- | --- | --- |
> | 固定批大小 | 527 | **0.4 分** |
> | **FFD** | **502** | **0.4 分** |
> **读法**：**批数直接等于"对 embedding 服务的请求数"**——**而请求数决定成本与排队时间**。**本机最优 502 批；若每请求 50ms，串行要 0.4 分钟**（**所以必须并发**）。
> **★ 实现要点**：
> | # | 要点 |
> | --- | --- |
> | ① | **先算 token 数**（**不要用字符数估算**——**串 [[llm-internals-01]]**） |
> | ② | **FFD 排序**（**长优先**——**批数最少**） |
> | ③ | **并发发送**（**批数多，串行太慢**） |
> | ④ | **背压**（**生产快于消费时要有界队列**） |
> | ⑤ | **重试与幂等**（**串 [[perplexity-01]]**） |
> | ⑥ | **顺序无关但要可对齐**（**结果要能映射回原文本**） |
> **读法**：**第 ⑥ 条最容易被忽略**——**因为 FFD 打乱了顺序**（**所以要记录"每个文本属于哪个批、批内哪个位置"**）。
> **★ 三种"快"的层次**：
> | 层次 | 手段 | 收益 |
> | --- | --- | --- |
> | **减少请求数** | **FFD 装箱** | **5%（本机）** |
> | **提高并发** | **流水线：算批 + 发送重叠** | **数倍** |
> | **减少 token 数** | **截断/去重/跳过已嵌入** | **取决于数据** |
> 一句话判据：**"先精确算 token → FFD 装箱最小化批数 → 并发发送 + 流水线 → 有界队列背压 → 记录映射关系"**。

## 面试官在考什么

- **★ 是否识别"这是装箱问题"**：**能否指出"约束是 token 不是条数"**——**这是本题的分水岭**。
- **★ 是否知道 FFD**：**能否给出"长优先"的策略**（本机：**502 vs 527**）。
- **是否知道"短优先更差"**：**能否指出"短文本占满批次"**。
- **token 计数**：**能否指出"要用真 tokenizer 而不是字符估算"**。
- **并发**：**能否指出"批数多，串行太慢"**。
- **背压**：**能否指出"要有界队列"**。
- **映射关系**：**能否指出"FFD 打乱顺序，要记录映射"**。
- **重试幂等**：**能否指出"批次失败要能重试"**。
- **去重**：**能否指出"已嵌入的文本要跳过"**（**数百万块里可能有重复**）。
- **诚实**：**承认"装箱的收益取决于长度分布的离散度"**。

**常见错误答案**

- **按"条数"切批**（**忽略 token 上限**）。
- **按原始顺序切**（**不做装箱**）。
- **用字符数估 token**（**误差大，会超限**）。
- **串行发送**（**太慢**）。
- **无界队列**（**内存爆**）。
- **不记录映射**（**结果对不上原文**）。
- **不做重试**（**一批失败全丢**）。
- **不去重**（**重复文本重复付费**）。

## 原理与推导

### 1. ★ 为什么是装箱问题

$$\text{目标：最小化批数}\quad\text{约束：}\sum_{\text{批内}}\text{tokens}\le T,\ \text{条数}\le B$$

| 策略 | 近似比 |
| --- | --- |
| **首次适应（FF）** | $\le1.7\cdot\text{OPT}$ |
| **降序首次适应（FFD）** | **$\le\frac{11}{9}\text{OPT}+\frac{6}{9}$** |
| **最优（NP-hard）** | 1.0 |

**读法**：**"FFD 的近似比是 11/9"**——**即最坏情况比最优多 22%**——**而实际数据上通常只差几个百分点**（**本机 5%**）。

### 2. ★ 为什么"长优先"更好

| 原因 | 说明 |
| --- | --- |
| **长文本更难安置** | **先放难的，留小的空隙** |
| **短文本灵活** | **能填任何剩余空间** |
| **反之会浪费** | **短文本先占满"条数"配额** |

**读法**：**"先放大的"是装箱的通用启发式**——**它同样适用于"内存分配"与"任务调度"**。

### 3. token 计数

| 方法 | 精度 |
| --- | --- |
| **字符数 / 4** | **粗略**（**英文约 4 字符/token，中文差很多**） |
| **真 tokenizer** | **精确**（**但慢**） |
| **预计算 + 缓存** | **精确且快**（**推荐**） |

**读法**：**"用字符估算"会导致超限**——**而超限的批次会被服务端拒绝**（**重试成本更高**）。**所以"预计算 token 数并缓存"是必需的**。

### 4. 并发与流水线

$$\text{总耗时}\approx\frac{\text{批数}}{\text{并发度}}\times\text{单批耗时}$$

| 手段 | 效果 |
| --- | --- |
| **并发发送** | **线性加速（直到限流）** |
| **流水线**（**算批与发送重叠**） | **隐藏装箱时间** |
| **批内并行**（**如 8 个并发**） | **受服务端限流约束** |

**读法**：**"并发度由服务端的限流决定"**——**所以要先测"服务端允许多少并发"**（**否则会被 429**，**串 [[perplexity-01]]**）。

### 5. 背压

| 机制 | 说明 |
| --- | --- |
| **有界队列** | **生产者满了就等** |
| **流式消费** | **边读边发，不载入全部** |
| **进度记录** | **支持断点续传** |

**读法**：**"数百万文本块不能全载入内存"**——**所以要流式**（**本机 20,000 条只是示例，真实是数百万**）。

### 6. 去重与跳过

| 优化 | 收益 |
| --- | --- |
| **跳过已嵌入的** | **取决于重复率** |
| **批内去重** | **小**（**但免费**） |
| **短文本合并** | **可能改变语义**（**要谨慎**） |

**读法**：**"跳过已嵌入的"在增量场景下收益最大**——**因为重复跑一遍的成本是线性的**。

### 可运行代码

```python
import random
rng=random.Random(0)
MAX_BATCH=256; MAX_TOK=20_000
lens=[min(8000, int(rng.lognormvariate(5.5,1.2))) for _ in range(20000)]
lens.sort()
print('① 为什么"固定批大小"会浪费：文本长度是重尾的，且 token 上限是紧约束')
print(f'  文本长度：中位数 {lens[len(lens)//2]:,}、p90 {lens[int(len(lens)*0.9)]:,}、最大 {lens[-1]:,} token')
print(f'  约束：每批最多 {MAX_BATCH} 条、**总 token 最多 {MAX_TOK:,}**')
print(f'  注意：**{MAX_BATCH} 条 x 中位数 {lens[len(lens)//2]} token = {MAX_BATCH*lens[len(lens)//2]:,} token > 上限** ->')
print('        所以**约束是 token 而不是条数**（**这正是"固定批大小"会浪费的原因**）')
print()
print('② 三种装箱策略（同一批 20,000 个文本）')
def naive(seq, bs, tok):
    batches=[]; cur=[]; curtok=0
    for x in seq:
        if len(cur)>=bs or curtok+x>tok:
            if cur: batches.append(curtok)
            cur=[]; curtok=0
        cur.append(x); curtok+=x
    if cur: batches.append(curtok)
    return batches
def ffd(seq, bs, tok):
    bins=[]
    for x in sorted(seq, reverse=True):
        for b in bins:
            if b[1]<bs and b[0]>=x: b[0]-=x; b[1]+=1; break
        else: bins.append([tok-x,1])
    return [tok-b[0] for b in bins]
def asc(seq, bs, tok):
    bins=[]
    for x in sorted(seq):
        for b in bins:
            if b[1]<bs and b[0]>=x: b[0]-=x; b[1]+=1; break
        else: bins.append([tok-x,1])
    return [tok-b[0] for b in bins]
res={}
for name,fn in (('固定批大小（原始顺序）',naive),('FFD（长优先）',ffd),('升序贪心（短优先）',asc)):
    used=fn(lens,MAX_BATCH,MAX_TOK)
    res[name]=(len(used), sum(used)/(len(used)*MAX_TOK))
print(f'  {"策略":<26} {"批数":>7} {"token 利用率":>12} {"相对最少批数":>13}')
best=min(v[0] for v in res.values())
for name,(nb,util) in res.items():
    print(f'  {name:<26} {nb:>7,} {util:>11.1%} {nb/best:>12.2f}x')
print('  读法：**FFD（长优先）批数最少、利用率最高** —— 因为长文本先放、短文本填空隙；')
print('        而**固定批大小与"短优先"都更差**（**短文本先占满批次，长文本无处可放**）——')
print("        所以「batcher 要足够快」的正确含义是**「在约束下最小化批数」**（**这是一个装箱问题**）")
print()
print('③ 换算成请求数与成本（批数 = 对 embedding 服务的请求数）')
print(f'  {"策略":<26} {"批数":>7} {"相对":>8} {"若每请求 50ms 的总耗时":>20}')
for name,(nb,util) in res.items():
    print(f'  {name:<26} {nb:>7,} {nb/best:>7.2f}x {nb*0.05/60:>18.1f} 分')
print('  读法：**批数直接等于请求数** —— 而请求数决定成本与排队时间；')
print(f'        本机最优 {best:,} 批；**若每请求 50ms，串行要 {best*0.05/60:.1f} 分钟**（**所以要并发**）')
```

预期输出要点（实跑）：① **约束分析**：长度中位数 **245**、p90 **1,139**、最大 **8,000**；**$256\times245=62{,}720>20{,}000$** → **约束是 token 不是条数**；② **装箱**：固定批大小/FFD/升序贪心 → **527/502/527 批**、利用率 **94.1%/98.8%/94.1%**；③ **吞吐**：批数 = 请求数，本机最优 **502 批**。

## 常见追问

- **追问**：如果文本长度分布很均匀呢？
  - 要点：**装箱收益趋近于 0**：① **长度均匀时"原始顺序"已经接近最优**；② **所以"要不要装箱"取决于分布的离散度**；③ **可以先算"长度的变异系数"**（**大于 1 才值得装箱**）。**读法**：**"装箱的收益 = 长度分布的离散度"**——**这是决定"要不要做"的判据**。
- **追问**：怎么处理"单个文本超过 token 上限"？
  - 要点：**三条**：① **截断**（**但要记录"被截断"**——**否则嵌入质量下降且无人知道**）；② **分块**（**把长文本切成多块分别嵌入**）；③ **拒绝并告警**（**如果业务不允许截断**）。**读法**：**"超长文本必须显式处理"**——**否则它会单独占一个批，浪费整个批次的容量**。
- **追问**：怎么保证"结果能对回原文"？
  - 要点：**三条**：① **每个文本有稳定 ID**（**如内容的哈希**）；② **批次记录"批 ID + 批内顺序"**；③ **结果按 ID 落库**（**而不是按位置**）。**读法**：**"按 ID 而不是按位置对齐"**——**因为 FFD 打乱了顺序，而且重试会改变批次组成**。
- **追问**：怎么测 batcher 的正确性？
  - 要点：**四类用例**：① **约束**（**每个批都不超 token 与条数**）；② **覆盖**（**所有输入都被处理且只处理一次**）；③ **对齐**（**结果与原文一一对应**）；④ **边界**（**空输入、单条超长、全部相同**）。**读法**：**"覆盖 + 对齐"是核心**——**它们能抓住"漏处理"与"错位"这两类严重 bug**。
- **追问**：服务端限流怎么办？
  - 要点：**三条**：① **自适应并发**（**AIMD：遇到 429 就降，成功就升**）；② **读 `Retry-After`**；③ **多端点**（**如果有多个 embedding 服务**）。**读法**：**"自适应并发"是生产环境的标配**——**因为服务端的限流阈值会变**（**串 [[perplexity-01]] 的"429 不重试"**）。
- **追问**：这道题与"LLM 推理服务"有什么关系？
  - 要点：**同一个"批处理"问题**：① **embedding 的批是"token 上限 + 条数上限"**；② **LLM 推理的批是"KV cache 显存 + 算力"**；③ **两者都要"在约束下最大化吞吐"**（**串 [[inference-serving-03]]**）。**读法**：**"批处理的核心是'约束下的装箱'"**——**这个思想跨越 embedding 与 LLM 推理**。
