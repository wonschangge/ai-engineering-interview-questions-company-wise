# Perplexity 面试题库

这一家的题有一个共同的主语：**答案引擎**——**用户问一个问题，3 秒内拿到带引用的流式答案**。
所有题目都是这个约束的推论：**3 秒决定了模型能多大、上下文能多长、重排能做几级**。

准备这一家时，建议把**"先算预算，再谈架构"**当成习惯动作：
**3 秒怎么分给检索、重排、prefill、生成？** 答案要多少 token？
**70B 单序列要 3.75 秒**——那就得换小模型或上推测解码。

第二个反复出现的主题是**"分流"**：
**时效权重不能全局统一**（常青查询要 0.0、突发查询要 1.0）、
**查询类型决定胜负**（导航型结构性输给传统搜索）、
**端侧与云端要按"数据敏感性"而不是"延迟"分**。
**这一家的面试官明显更在意"你的方案有没有对不同的输入给出不同的处理"。**

第三个主题是**"低成本信号的边界"**：
**LLM 评委一致率 80% 就要 2.78 倍样本**、
**引用校验器在 8% 幻觉率下标记精确率只有 42.5%**、
**隐式信号一致率 70%**。
**"用一个便宜信号替代人工"这件事本身要被量化验证。**

## 准备建议

1. **先把"3 秒预算"算熟**：它是 08 的主线，也是 05、06、14 的隐含约束。**任何方案都要先问"它在 3 秒里占多少"。**
2. **05 与 06 是一对**：**06 的算力模型正好解释了 05 的根因**（LLM 重排 50 篇要 1.77 秒）。把这两道连起来看，就能理解"为什么发版会让 TTFT 恶化"。
3. **02、03、04 是三道"实现题"，但考点都在量化**：LSH 的 $(b,r)$、装箱的利用率、beam 的长度偏置。**不要只写算法，要写出数字。**
4. **07、09、10 是检索的三层**：**09 解决"候选从哪来"、10 解决"多路怎么合"、07 解决"怎么选进上下文"。** 三者的预算串起来正好是一条 3 秒链路。
5. **11 与 12 都在考"分流"**：**11 按数据敏感性分流、12 按查询意图分流。** 这一家对"用一个全局策略处理所有输入"非常警惕。
6. **13 与 14 是"信号质量"的两面**：**13 问"你的评估信号可信吗"、14 问"你的校验信号可信吗"。** 共同的答案是**先用人工校准，再量化它的误差。**
7. **15 不要留到最后**：它考的是**产品判断**，而**判据要具体**（"第一句就是答案"）、**发布要有取舍**（不能三个都做）。
