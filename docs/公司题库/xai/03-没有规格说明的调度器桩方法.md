## 一句话答案

> **核心原则：不要先写实现——先用三十分钟把「契约」从代码里挖出来，并把它写成可执行的测试。**
> **因为没有规格时，测试就是规格**（tests are the spec）：**别人 review 一份测试，比 review 一份「我以为应该这样」的实现快得多**。
> **三十分钟的五个阶段（时间盒）**：
> | 阶段 | 时间 | 做什么 | 产出 |
> | --- | --- | --- | --- |
> | **① 找调用点** | 0–5 min | `grep _admit_requests`、看调用者传什么/拿返回值做什么/在什么时机调 | **一份调用时序图**（谁、何时、期待什么） |
> | **② 推契约** | 5–12 min | 列出输入/输出/副作用/错误/并发/复杂度六项，**模糊处标为开放问题** | **契约清单 + 开放问题列表** |
> | **③ 找不变量** | 12–18 min | 「什么永远不能发生」（**KV 预算不超、批大小不超、同一请求不重复准入**…） | **不变量列表** |
> | **④ 写性质测试** | 18–26 min | 把不变量写成**随机负载下自动检查的测试**（不需要知道正确输出） | **可运行的性质测试** |
> | **⑤ 最小实现 + WIP 提交 + 提问** | 26–30 min | 写**最朴素的正确版本**（不是最优），提交为 WIP，把开放问题写成清单发出去 | **WIP commit + 提问清单** |
> **为什么这个顺序（而不是先写代码）**：
> $$\text{猜错的代价}=(\text{发现得越晚})\times(\text{返工面越大})$$
> **`_admit_requests` 这类「调度核心」的语义错误不会立刻暴露**——它会表现为「偶发 OOM」「某些请求永远不被调度」「吞吐莫名下降」。**等上线后才发现，返工面是整条调度链路。**
> **本轮的可运行验证（性质测试确实能抓错）**：
> | 实现 | KV 预算违反 | 批大小违反 | 重复准入 | 违规组数 |
> | --- | --- | --- | --- | --- |
> | **契约版（参考）** | 0 | 0 | 0 | **0/100** |
> | **不看 KV 预算** | **100** | 0 | 0 | **100/100** |
> | **重复准入** | 0 | 0 | **92** | **92/100** |
> **读法**：**三条不变量 + 随机负载**，就能把两类典型错误实现**全部抓出来**——而这三条不变量**不需要知道「正确的调度顺序是什么」**（那正是规格缺失的部分）。**这就是「没有规格时最该写的那类测试」。**
> 一句话判据：**「先推断契约、把不变量写成测试、用最朴素的实现满足它、把开放问题写下来发出去」**——**三十分钟结束时你应该有一份可运行的测试和一份待确认的清单，而不是一堆猜出来的代码。**

## 面试官在考什么

- **是否抵制「马上写代码」的冲动**：这是本题的第一考点——**没规格就动手，等于把假设藏进代码里**。
- **是否有系统化的推断方法**：能否给出**找调用点 → 推契约 → 找不变量 → 写测试 → 最小实现**这样的步骤，而不是「读读代码就懂了」。
- **是否知道「性质测试」**：**不需要知道正确输出，只需要知道什么永远不能发生**——这是规格缺失场景下最有力的工具。
- **能否列出具体的契约维度**：输入（类型/范围/不变量）、输出（类型/语义）、**副作用**（改了哪些状态、发了什么指标）、**错误行为**、**并发假设**、**复杂度期望**。
- **能否识别「调度类」的核心不变量**：**资源上限（KV/批大小）、公平性/无饥饿、幂等性（不重复准入）、顺序语义（FIFO/优先级）**。
- **是否区分「阻塞性问题」与「可先假设的问题」**：能否给出**保守默认值**（例如「资源上限绝不超」是硬约束，而「优先级策略」可以先用 FIFO 并标注）。
- **是否有交付物意识**：三十分钟结束时交付什么（**WIP 提交 + 可运行测试 + 提问清单**），而不是「我还在读代码」。
- **沟通与协作**：能否把「我推断的契约」**写成别人能 review 的形式**（测试 + 清单），并**主动暴露假设**。
- **务实**：承认三十分钟**做不完**，重点是**把不确定性收敛成明确的问题**。

**常见错误答案**

- **直接开始写实现**（把假设埋进代码，review 时看不出来）。
- 花全部时间读代码，**不产出任何可执行的东西**。
- 自己发明一套规格，**不标注哪些是假设**。
- 追求最优算法（**契约还没定，优化是浪费**）。
- 不找调用点（**语义主要来自调用方**，不是方法名）。
- 不写测试就提交实现。
- 把开放问题憋着（**应该写下来发出去**）。
- 忽略副作用与并发假设（调度器的错误往往出在这两处）。

## 原理与推导

### 1. 为什么不能先写实现

**「没有规格」意味着每一个未言明的假设都会变成代码里的一个决定**——而这些决定**在 review 时不可见**（因为代码看起来是「合理的」）。后果：

| 假设错在哪 | 表现 | 何时暴露 |
| --- | --- | --- |
| **资源上限语义**（硬约束 vs 软目标） | 偶发 OOM / 显存被打满 | 上量后 |
| **公平性**（FIFO vs 优先级 vs 加权） | 某些请求**永远不被调度**（饥饿） | 用户投诉后 |
| **幂等性**（重复调用是否安全） | 同一请求被重复准入 → 重复计算/重复计费 | 重试逻辑上线后 |
| **时机**（每步调一次 vs 事件驱动） | 吞吐下降 / 延迟尖峰 | 压测时 |
| **副作用**（是否更新指标/统计） | 监控缺失或重复计数 | 观测时 |

**读法**：**这五条里有四条不会立刻报错**——所以「先写实现」的代价是**把 bug 推迟到最难查的时候**。**三十分钟的价值在于把它们变成「明确的问题」。**

### 2. 阶段①：找调用点（语义来自调用方）

**具体动作**：

| 动作 | 想得到什么 |
| --- | --- |
| `grep -rn 「_admit_requests」` | **谁在调、在什么条件下调** |
| 看调用者的**上下文** | 是在「每步调度循环」里调，还是在「新请求到达」时调？ |
| 看**返回值**被怎么用 | 返回 None（纯副作用）还是返回被准入的列表？ |
| 看**调用频率** | 每步一次 / 每次事件一次 / 定时一次 |
| 看**同类方法** | 有没有 `_preempt`、`_evict`、`_finish_request` 之类的兄弟方法（**它们共同定义了状态机**） |
| 看**状态字段** | `self.waiting`、`self.running`、`self.kv_budget`——**方法要维护哪些不变量** |

**本机的示例契约**（从调用点推断）：

```python
def _admit_requests(self):
    """把 waiting 里的请求按顺序移入 running，直到批大小或 KV 预算用满"""
```

**读法**：**方法名只给了「准入」这个动词，语义全在调用点与状态字段里**——所以第一步必须是找调用点。

### 3. 阶段②：契约清单（六项）

| 维度 | 要写下来的问题 |
| --- | --- |
| **输入** | 参数有哪些？**隐式输入**是哪些状态字段？它们的类型/范围/不变量？ |
| **输出** | 返回什么？**纯副作用**还是返回值？ |
| **副作用** | 改了哪些字段？**顺序**如何？是否更新指标/日志？ |
| **错误行为** | 什么情况下抛异常？**资源不足**时是「不准入」还是「驱逐已有请求」？ |
| **并发** | 是否假定单线程调用？**与请求完成/取消的竞态**如何处理？ |
| **复杂度** | 期望每次调用 $O(1)$、$O(\text{batch})$ 还是 $O(\text{waiting})$？（**决定数据结构**） |

**关键**：**把「不知道」明确写出来**。例如：

> **开放问题 1**：KV 预算是**硬约束**（绝不超）还是**软目标**（可短暂超）？
> **保守默认**：按硬约束实现（**超了会 OOM，代价更高**）。
> **开放问题 2**：等待队列的顺序是 FIFO、优先级、还是按大小装箱？
> **保守默认**：FIFO（**最简单、无饥饿**），并在代码里标注「待确认」。

**读法**：**「保守默认值 + 明确标注」比「猜一个聪明的策略」好得多**——因为前者只需要改一个策略，后者要重写测试。

### 4. 阶段③：不变量（「什么永远不能发生」）

**这是规格缺失场景下最有价值的一步**——因为**不变量不依赖具体策略**：

| # | 不变量 | 为什么是硬约束 |
| --- | --- | --- |
| ① | **$\sum$ 运行中请求的 KV 需求 $\le$ 预算** | 超了会 OOM（**物理约束**） |
| ② | **运行中请求数 $\le$ 最大批大小** | 超了会拖慢每步延迟（**SLO 约束**） |
| ③ | **同一请求不会被重复准入** | 重复计算/重复计费（**正确性约束**） |
| ④ | **被准入的请求一定来自等待队列** | 状态一致性 |
| ⑤ | **等待队列里的请求最终会被准入或明确拒绝**（无饥饿） | 公平性（**较弱，需策略保证**） |
| ⑥ | **调用幂等性**：连续调用两次与调用一次效果相同（若已无空间） | 重试安全 |

**读法**：**①–④ 是「无论什么策略都必须满足」的**，所以可以**先写成测试**；⑤⑥ 依赖策略，**先标注为开放问题**。

### 5. 阶段④：性质测试（不需要知道正确输出）

**性质测试（property-based test）的核心**：

$$\text{断言「对所有随机负载，不变量都成立」}\quad\text{而不是}\quad\text{断言「给定输入得到给定输出」}$$

**本机的测试骨架**：

```python
def check(scheduler):
    used = sum(r.kv_bytes for r in scheduler.running)
    assert used <= scheduler.kv_budget          # 不变量 ①
    assert len(scheduler.running) <= scheduler.max_batch   # ②
    ids = [r.rid for r in scheduler.running]
    assert len(ids) == len(set(ids))            # ③
```

**用随机负载跑 100 组**（每组 50 个随机请求，prompt 长度与生成长度都随机）——**本机结果**：

| 实现 | KV 预算违反 | 批大小违反 | 重复准入 | 违规组数 |
| --- | --- | --- | --- | --- |
| **契约版（参考）** | 0 | 0 | 0 | **0/100** |
| **不看 KV 预算** | **100** | 0 | 0 | **100/100** |
| **重复准入** | 0 | 0 | **92** | **92/100** |

**读法**：**三条不变量就把两类典型错误全部抓出**——而写这三条断言**完全不需要知道「正确的调度策略是什么」**。**这就是「没有规格」时最该做的事。**

### 6. 阶段⑤：最小实现 + WIP 提交 + 提问清单

**最小实现的原则**：**写最朴素的正确版本**（不是最优）：

```python
def _admit_requests(self):
    while self.waiting:
        r = self.waiting[0]
        need = (r.prompt_tokens + r.max_new) * self.bytes_per_token
        used = sum(x.kv_bytes for x in self.running)
        if len(self.running) >= self.max_batch: break          # 不变量 ②
        if used + need > self.kv_budget: break                 # 不变量 ①
        self.waiting.pop(0)
        r.kv_bytes = need
        self.running.append(r)                                 # ③ 出队+入队是原子的
```

**注意它的复杂度是 $O(\text{batch}^2)$**（每次重算 `used`）——**这没关系**：**契约未定时优化是浪费**，而且**这个实现显然满足不变量**（便于当参考模型）。

**交付物（三十分钟结束时）**：

| 交付物 | 为什么重要 |
| --- | --- |
| **WIP 提交**（朴素实现 + 性质测试） | 别人可以 review **测试**（= 契约）而不是猜你的意图 |
| **提问清单**（阻塞性 vs 可假设） | 把不确定性**收敛成明确的问题** |
| **待确认标注**（策略相关处） | 明确「我知道这里是假设」 |
| **调用时序图/契约清单** | 让下一个人不用重新推断 |

**读法**：**三十分钟做不完一个调度器，但足够把「我不知道什么」变成「一份清单 + 一组测试」**——**这才是「没有规格」时的正确交付。**

### 7. 反模式清单

| 反模式 | 为什么坏 |
| --- | --- |
| **先写实现再补测试** | 测试会写成「实现做了什么」，而不是「契约要求什么」 |
| **自己发明策略并当作事实** | 假设被埋进代码，review 看不见 |
| **追求最优数据结构** | 契约未定，优化对象可能是错的 |
| **不找调用点** | 语义主要来自调用方，不看会推错 |
| **不写「开放问题」** | 不确定性留在脑子里 → 变成隐性风险 |
| **只写单元测试（给定输入→给定输出）** | 规格缺失时**无法写出正确输出**；性质测试才可行 |
| **不区分硬约束与软目标** | 把 SLO 当物理约束（或反之）都会做错 |

# 没有规格说明时怎么做：契约推断 + 性质测试（不变量）+ 两种错误实现的抓取
import random
from dataclasses import dataclass
from typing import List, Tuple

@dataclass
class Req:
    rid: int
    prompt_tokens: int
    max_new: int
    kv_bytes: int = 0

class Scheduler:
    """最小 LLM 推理调度器：把 waiting 里的请求移入 running，受 KV 预算与批大小约束"""

    def __init__(self, kv_budget: int, max_batch: int, bytes_per_token: int = 4096) -> None:
        self.kv_budget = kv_budget
        self.max_batch = max_batch
        self.bytes_per_token = bytes_per_token
        self.waiting: List[Req] = []
        self.running: List[Req] = []

    def add(self, r: Req) -> None:
        self.waiting.append(r)

    def _admit_requests(self) -> None:
        # ★ 待推断契约的方法：契约版（朴素但显然满足不变量）
        while self.waiting:
            r = self.waiting[0]
            need = (r.prompt_tokens + r.max_new) * self.bytes_per_token
            used = sum(x.kv_bytes for x in self.running)
            if len(self.running) >= self.max_batch:      # 不变量 ②
                break
            if used + need > self.kv_budget:             # 不变量 ①
                break
            self.waiting.pop(0)
            r.kv_bytes = need
            self.running.append(r)                       # ③ 出队与入队成对出现

class BuggyNoBudget(Scheduler):
    """错误实现 A：只看批大小，不看 KV 预算"""

    def _admit_requests(self) -> None:
        while self.waiting and len(self.running) < self.max_batch:
            r = self.waiting.pop(0)
            r.kv_bytes = (r.prompt_tokens + r.max_new) * self.bytes_per_token
            self.running.append(r)

class BuggyDup(Scheduler):
    """错误实现 B：有时不出队，导致同一请求被重复准入"""

    def _admit_requests(self) -> None:
        rng = random.Random(0)
        while self.waiting and len(self.running) < self.max_batch:
            r = self.waiting[0]
            need = (r.prompt_tokens + r.max_new) * self.bytes_per_token
            if sum(x.kv_bytes for x in self.running) + need > self.kv_budget:
                break
            r.kv_bytes = need
            self.running.append(r)
            if rng.random() < 0.3:          # ✗ 有时不 pop，于是重复准入
                continue
            self.waiting.pop(0)

def random_workload(cls, seed: int, n: int = 50,
                    kv_budget: int = 64 * 1024 * 1024, max_batch: int = 16):
    rng = random.Random(seed)
    s = cls(kv_budget, max_batch)
    for i in range(n):
        s.add(Req(i, rng.randint(64, 4096), rng.randint(16, 512)))
    s._admit_requests()
    return s

def check_invariants(s) -> Tuple[bool, bool, bool]:
    """三条不变量：不依赖具体策略，所以没有规格也能写"""
    used = sum(x.kv_bytes for x in s.running)
    v1 = used <= s.kv_budget                          # ① KV 预算不超
    v2 = len(s.running) <= s.max_batch                # ② 批大小不超
    ids = [x.rid for x in s.running]
    v3 = len(ids) == len(set(ids))                    # ③ 不重复准入
    return v1, v2, v3

## 常见追问

- **追问**：三十分钟真的够吗？
  - 要点：**不够写完，但够「把不确定性收敛」**。三十分钟结束时的正确状态是：① **一份可运行的测试**（性质测试，抓得住典型错误）；② **一份 WIP 提交**（朴素实现，便于 review）；③ **一份提问清单**（阻塞性 vs 可假设）。**「我还在读代码」不是合格的交付**——因为没有把不确定性变成可传递的东西。
- **追问**：为什么不直接问同事？
  - 要点：**要问，但要带着「推断结果」去问**——这有三个好处：① **问题更精确**（「KV 预算是硬约束吗」比「这个方法是干什么的」好回答得多）；② **不打断别人**（异步提问 + 清单）；③ **留下可 review 的资产**（测试与清单能被更多人复用）。**正确顺序是：先自己推断（三十分钟）→ 把推断写成测试与清单 → 带着清单去确认。**
- **追问**：如果调用点也看不出来呢（比如是死代码）？
  - 要点：**那就先确认「它是否还被使用」**：① **搜索范围扩大**（反射、动态派发、配置驱动的调用）；② **看 git 历史**（最后一次修改、谁改的、commit message）；③ **看监控/日志**（线上是否还有这条路径的痕迹）。**若确认是死代码 → 直接删掉（附上证据）比补实现更有价值**。**这也是三十分钟能交付的结论之一。**
- **追问**：性质测试能替代单元测试吗？
  - 要点：**不能，两者互补**：① **性质测试**擅长「规格模糊但有不变量」的场景（本题），能**用少量断言覆盖巨大输入空间**；② **单元测试**擅长「精确语义」的场景（例如「FIFO 顺序」——这需要给定输入→给定输出的断言）。**实践**：**先写性质测试（抓结构性错误），契约明确后再补单元测试（锁语义）**。**本机的例子**：三条不变量抓出了两类错误实现，但「顺序是否正确」必须等策略确定后才能测。
- **追问**：怎么保证性质测试真的在测东西？
  - 要点：**变异测试（mutation testing）的思路**：**故意写错实现，看测试是否失败**。本机就是这么做的——**两类错误实现（不看预算、重复准入）分别被 100/100 与 92/100 抓到**。**如果错误实现也能通过测试，说明测试没测到东西。** 另外要检查：① **随机负载的分布**（要覆盖「刚好放不下」「空队列」「单个超大请求」等边界）；② **随机种子固定**（可复现）；③ **失败时打印现场**（哪一组、哪个请求、预算多少）。
- **追问**：什么时候可以开始优化？
  - 要点：**契约明确 + 测试通过之后**。本机的朴素实现是 $O(\text{batch}^2)$（每次重算 `used`）——**这在契约未定时是对的**（显然正确、便于当参考模型）。**优化方向**：① 维护**增量 `used`**（准入/完成时更新）→ $O(\text{batch})$；② 若需要**按大小装箱**，用有序结构（如按 KV 需求排序的堆）→ $O(\log n)$；③ 若等待队列很大，避免 `pop(0)`（$O(n)$）→ 用 `deque`。**但每一步优化的前提都是「契约已经定下来」。**
