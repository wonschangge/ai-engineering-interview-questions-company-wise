## 一句话答案

> **按 token 计费与按请求计费的本质差别：请求的成本在准入时是未知的**（输出长度事先不知道）。所以设计核心是**两阶段：预扣（reserve）→ 结算（settle）**。
> **四个必须解决的机制，每个都有量化依据**：
> | # | 机制 | 不这么做会怎样（本机实测） |
> | --- | --- | --- |
> | ① | **预扣 + 结算（多退少补）** | 只按 `max_tokens` 预扣 → **误拒率 28.7%**（本可服务却被拒）；完全不预扣 → **超发 1.2%** |
> | ② | **原子预扣**（检查+扣减不可分割） | 并发 64 时朴素「读-判断-减」把配额用到 **1.28 倍**，并发 128 时 **2.56 倍** |
> | ③ | **加权 token**（输出权重 = 单价比） | 按原始 token 计数，长输出负载下**低估成本 77%**（等效权重 **4.33×**） |
> | ④ | **终态结算**（成功/失败/取消都要结算）+ 预留 TTL + 后台对账 | 取消率 20% 时**有效配额只剩 80%**；一次崩溃可永久吃掉配额 |
> **推荐设计（六条）**：
> 1. **桶按「加权 token」计量**：`cost = input_tokens + w × output_tokens`，$w=\text{输出单价}/\text{输入单价}$（本仓库常数下 $w=15/3=5$）；
> 2. **准入时原子预扣**：`reserve = input_tokens + w × min(max_tokens, cap)`——**用 `min` 把预扣收紧**（否则误拒率高）；
> 3. **生成中增量结算**：每产出 $n$ 个 token 就**原子扣减**并释放对应预留（**流式场景下必须能中途判断**）；
> 4. **结束时结算差额**：`settle = 实际用量 - 已扣`，**多退少补**；失败/取消也要走同一条路径（**预扣按已生成部分计费**，因为 prefill 已经花了算力）；
> 5. **预留 TTL + 后台对账**：超时未结算的预留自动释放，并定期与用量表对账（防崩溃泄漏）；
> 6. **桶的形状**：令牌桶**以 token/秒 补充**（不是请求/秒），并明确**突发额度**——本仓库在 [[cohere-01]] 的实测：令牌桶在 60 秒窗口内可达配额的 **1.97 倍**（这是设计属性，不是 bug；固定窗口的 2.00 倍才是可避免的）。
> **超发时怎么办（三选一，按产品取舍）**：
> | 策略 | 优点 | 缺点 |
> | --- | --- | --- |
> | **硬停**（生成中掐断） | 严格不超发 | **用户体验差 + 已花的 prefill 算力浪费** |
> | **允许透支**（记账为欠费） | 体验好、实现简单 | 需要**欠费追缴**与风控（恶意用户可刷） |
> | **收紧 `max_tokens`** | 从源头让预扣准确 | 限制能力（长输出任务受影响） |
> **读法**：**实践是「收紧 max_tokens + 允许有限透支 + 事后结算」**——三者结合，把误拒率与超发都压到可接受范围。
> 一句话判据：**"桶按加权 token 计、准入原子预扣、生成中增量结算、结束多退少补、失败取消也要结算、预留要能超时释放"**——**六条缺一条，配额就会被超发或泄漏。**

## 面试官在考什么

- **是否意识到「成本未知」这个根本差别**：**按请求限流只需数请求；按 token 限流必须在输出未知时做决定**——这是本题的题眼。
- **能否提出「预扣 + 结算」**：这是标准答案；**能否同时说清「预扣太多会误拒、太少会超发」**（本机：28.7% vs 1.2%）。
- **原子性**：**「检查+扣减」必须是原子的**——能否给出实现方式（Redis Lua 脚本、数据库条件更新、单点协调）并量化竞态后果（本机 1.28×/2.56×）。
- **输入/输出单价差异**：能否指出**输出更贵**（本仓库常数 \$3 vs \$15），因此要用**加权 token** 或**双桶**（本机：按原始 token 低估 9%–77%）。
- **终态结算**：能否想到**取消/失败也要结算**（prefill 已消耗），以及**预留 TTL**（防崩溃泄漏）。
- **限流器形状**：令牌桶 / 固定窗口 / 滑动窗口的取舍；**能否给出突发倍数的量级**（本仓库 [[cohere-01]]：令牌桶 60 秒窗口内 1.97×）。
- **用户体验**：能否讨论「生成中掐断」vs「允许透支」的取舍，以及**配额可见性**（用户需要知道还剩多少）。
- **可观测性**：能否说出要监控什么（拒绝率、超发率、结算延迟、泄漏量、按租户的用量分布）。
- **诚实**：承认**预扣与结算之间必然存在不一致窗口**，工程目标是「把窗口做小 + 能对账」，而不是「完全避免」。

**常见错误答案**

- **按请求数限流**（完全没答到题：长输出请求会吃掉大量算力）。
- 只做「准入时检查一次」（**不预扣 → 并发下必然超发**）。
- 预扣 `max_tokens` 后不结算（**误拒率高**，本机 28.7%）。
- 用非原子的「读-判断-减」（**并发 64 就 1.28× 超发**）。
- 按原始 token 计数（**忽略输出单价 5×**，低估 9%–77%）。
- 忘了取消/失败路径（**配额泄漏**，取消率 20% 时有效配额剩 80%）。
- 不考虑流式生成（**无法中途判断**）。
- 不提配额可见性与对账机制。

## 原理与推导

### 1. 根本差别：成本在准入时未知

| 计费维度 | 准入时已知？ | 限流器要做什么 |
| --- | --- | --- |
| **请求数** | 已知（1 个请求 = 1 单位） | 简单的计数器/令牌桶 |
| **输入 token** | **已知**（prompt 长度可数） | 精确扣减 |
| **输出 token** | **未知**（取决于模型与采样） | **预扣 + 结算** |

**读法**：**只有「输出 token」是未知的**——所以设计围绕它展开。**注意**：输出长度是**随机变量**（受 `max_tokens` 截断），所以预扣必须基于**上界或估计**。

### 2. 机制一：预扣策略的取舍

设请求的真实成本为 $c$（生成结束后才知道），预扣额为 $r$：

$$\text{若}\ r\ \text{过大}\Rightarrow\text{误拒}\qquad\text{若}\ r\ \text{过小}\Rightarrow\text{超发}$$

**三种策略（本机模拟：配额 100k token、400 个随机请求）**：

| 策略 | 服务数 | 实际用量 | 超发 | **误拒率** |
| --- | --- | --- | --- | --- |
| **预扣 `prompt + max_tokens`** | 11 | 96,532 | **0.0%** | **28.7%** |
| **预扣 `prompt + 估计值`（300）** | 20 | 102,147 | **2.1%** | **0.0%** |
| **不预扣输出** | 20 | 101,152 | 1.2% | 0.0% |

**读法**：① **预扣上界最安全但误拒率 28.7%**（近三成请求本可服务却被拒——**这是真实的收入损失与体验损失**）；② **不预扣会超发**（1.2%，看起来小，但**在配额敏感的企业客户上不可接受**）；③ **「估计值」是折中**（本机超发 2.1%，比不预扣略高，但**它把风险从「无界」变成「有界」**），但需要**估计准确**。

**工程折中**：

$$r=\text{prompt}+w\times\min(\texttt{max\_tokens},\ \text{cap})$$

**用 `cap` 把预扣收紧**（例如 `cap=512`），超出部分走「透支/结算」。**这样误拒率下降，超发有界。**

### 3. 机制二：原子预扣（并发竞态）

**朴素实现**：

```python
if used + reserve <= quota:      # ← 多个请求同时看到同一个 used
    used += reserve              # ← 竞态：都通过了检查
```

**本机模拟**（每个请求预扣 2000 token、配额 100k）：

| 并发数 | 原子预扣 | 朴素实现 | 超发倍数 |
| --- | --- | --- | --- |
| 8 | 16,000 | 16,000 | 0.16× |
| 32 | 64,000 | 64,000 | 0.64× |
| **64** | **100,000** | **128,000** | **1.28×** |
| 128 | 100,000 | 256,000 | **2.56×** |

**读法**：**并发越高超发越严重**（所有 worker 基于同一个过期快照判断）。**修法**：

| 实现 | 机制 |
| --- | --- |
| **Redis + Lua 脚本** | 检查与扣减在服务端原子执行（最常用） |
| **数据库条件更新** | `UPDATE ... WHERE used + r <= quota`（靠行锁/乐观锁） |
| **单点协调器** | 内存计数器 + 定期持久化（简单但有单点风险） |
| **分片配额** | 把配额切成 $k$ 份分给 $k$ 个实例（**允许一定浪费，换取无协调**） |

**读法**：**分片配额是「用浪费换简单」**——每个实例只管自己那份，**代价是热点实例可能拒绝而其他实例还有余额**（需要动态再平衡）。

### 4. 机制三：加权 token（输入/输出单价不同）

**本仓库统一常数**：输入 **\$3** / 输出 **\$15** 每百万 token → 输出单价是输入的 **5 倍**。

$$\text{cost}=\text{input}+\frac{\text{price}_{\text{out}}}{\text{price}_{\text{in}}}\times\text{output}=\text{input}+5\times\text{output}$$

**本机算例**（按原始 token 计数的低估程度）：

| 负载（输入:输出） | 真实成本 | 按原始 token 计 | **低估** | 等效权重 |
| --- | --- | --- | --- | --- |
| 1000:200 | \$0.00600 | \$0.00360 | **40%** | 1.67× |
| 200:1000 | \$0.01560 | \$0.00360 | **77%** | **4.33×** |
| 4000:100 | \$0.01350 | \$0.01230 | 9% | 1.10× |
| 100:100 | \$0.00180 | \$0.00060 | 67% | 3.00× |

**读法**：**低估程度取决于负载形状**（9%–77%）——**「短输入长输出」的用户可以用 1 份配额消耗 4 份成本**。**所以必须用加权 token，或给输入/输出各一个桶**（后者更直观但用户体验更复杂）。

### 5. 机制四：终态结算与配额泄漏

**每个请求都必须走到一个终态**：成功 / 失败 / **取消** / 超时。

**关键**：**取消与失败也要按「已生成部分」计费**——因为 **prefill 与已生成的 token 已经消耗了算力**（串 [[moonshot-05]]：预填充是算力受限的，不能白送）。

**泄漏的量化**（本机）：

| 取消率 | 未结算的预留比例 | 有效配额 |
| --- | --- | --- |
| 0% | 0% | 100% |
| 5% | 5% | 95% |
| **20%** | **20%** | **80%** |
| 50% | 50% | **50%（严重）** |

**读法**：**泄漏与取消率成正比**。**两道防线**：① **预留 TTL**（超时自动释放，例如 2× 最大生成长度的时间）；② **后台对账**（定期扫描「有预留无结算」的记录并修正）。**没有这两道防线，一次进程崩溃就能永久吃掉一批配额。**

### 6. 限流器形状：桶里装的是 token

| 形状 | 突发行为 | 实现 |
| --- | --- | --- |
| **固定窗口** | 边界处可达 **2× 配额**（窗口重置） | 最简单 |
| **滑动窗口** | 平滑，但需要记录时间戳 | 中等 |
| **令牌桶**（**按 token/秒 补充**） | 允许突发，**60 秒窗口内可达 1.97×**（本仓库 [[cohere-01]] 实测） | 简单且常用 |
| **漏桶** | 严格平滑，无突发 | 会削峰 |

**读法**：**「桶里装 token 而不是请求」**是本题的关键转换——补充速率是 **token/秒**，容量（burst）是**允许多大的突发**。**注意突发额度是产品决策**：它决定了「用户能不能在短时间内跑一个 128K 的长请求」（串 [[xai-04]]：一个 128K 请求就要 40 GiB KV，突发额度要与之匹配，否则会出现「配额够但资源不够」）。

### 7. 超发时的三个策略

| 策略 | 实现 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **硬停** | 生成中检测超限 → 立即停止 | 严格不超发 | **体验差 + 已花的 prefill 浪费**（用户拿到半截答案） |
| **允许透支** | 记账为欠费，事后追缴 | 体验好、实现简单 | 需风控（恶意用户可刷欠费） |
| **收紧 `max_tokens`** | 从源头限制预扣上界 | 预扣准确、误拒率低 | 限制长输出任务 |

**推荐组合**：**收紧 `max_tokens`（默认值小）+ 允许有限透支（例如配额的 10%）+ 事后结算**。**并且要监控「透支率」**——它高说明预扣策略需要调。

### 可运行代码

```python
# 按 token 计费的限流器：预扣策略、并发原子性、配额泄漏、加权 token
import random
from dataclasses import dataclass
from typing import Dict, List, Tuple

QUOTA = 100_000          # 每窗口的加权 token 配额
N_REQ = 400
USD_IN, USD_OUT = 3.0, 15.0     # 每百万 token（仓库统一常数）
W_OUT = USD_OUT / USD_IN        # 输出相对输入的权重 = 5

rng = random.Random(0)
REQS: List[Tuple[int, int]] = [(rng.randint(200, 2000), rng.randint(50, 1500))
                               for _ in range(N_REQ)]

print("① 预扣策略的取舍（配额 100k 加权 token、400 个随机请求）")
print(f"  {'策略':<26} {'服务数':>7} {'实际用量':>9} {'超发':>7} {'误拒率':>7}")
def simulate_reserve(mode: str, max_tokens: int = 1500, estimate: int = 300) -> Dict[str, float]:
    used = 0.0
    served = false_reject = 0
    for prompt, out in REQS:
        if mode == "max":
            reserve = prompt + W_OUT * max_tokens
        elif mode == "estimate":
            reserve = prompt + W_OUT * estimate
        else:
            reserve = prompt
        if used + reserve > QUOTA:
            if used + prompt + W_OUT * out <= QUOTA:
                false_reject += 1          # 本可服务却被拒
            continue
        used += reserve
        served += 1
        if mode == "estimate" and out > estimate:
            used += W_OUT * (out - estimate)      # 超出估计部分事后补记
        elif mode == "none":
            used += W_OUT * out
    return {"served": served, "used": used,
            "overshoot": max(0.0, used - QUOTA) / QUOTA,
            "false_reject": false_reject / N_REQ}
for mode, name in (("max", "预扣 prompt + max_tokens"), ("estimate", "预扣 prompt + 估计值"),
                   ("none", "不预扣输出")):
    r = simulate_reserve(mode)
    print(f"  {name:<26} {r['served']:>7} {r['used']:>9,.0f} "
          f"{r['overshoot']:>6.1%} {r['false_reject']:>6.1%}")
print("  读法：**预扣上界最安全但误拒率 28.7%（本可服务的请求被拒 = 真实损失）**；")
print("        不预扣会超发；估计值是折中 —— 工程上还要用 min(max_tokens, cap) 收紧预扣")

print("")
print("② 并发原子性：朴素读-判断-减 vs 原子预扣（每请求预扣 2000）")
def concurrent(n_workers: int, atomic: bool, per_req: int = 2000) -> int:
    if atomic:
        used = 0
        for _ in range(n_workers):
            if used + per_req <= QUOTA:
                used += per_req
        return used
    snapshot = 0                       # ★ 所有 worker 都基于同一个过期快照判断
    served = sum(1 for _ in range(n_workers) if snapshot + per_req <= QUOTA)
    return served * per_req
print(f"  {'并发数':>7} {'原子预扣':>10} {'朴素实现':>10} {'超发倍数':>9}")
for w in (8, 32, 64, 128):
    a, b = concurrent(w, True), concurrent(w, False)
    print(f"  {w:>7} {a:>10,} {b:>10,} {b/QUOTA:>8.2f}x")
print("  读法：**并发 64 时朴素实现用到 1.28 倍配额、128 时 2.56 倍** ——")
print("        所以「检查 + 扣减」必须原子（Redis Lua / 条件更新 / 分片配额）")

print("")
print("③ 终态结算：取消/失败未结算 -> 配额泄漏")
print(f"  {'取消率':>7} {'泄漏比例':>9} {'有效配额':>9} 影响")
for c in (0.0, 0.05, 0.2, 0.5):
    note = "可忽略" if c < 0.05 else ("需处理" if c < 0.3 else "严重")
    print(f"  {c:>7.0%} {c:>9.0%} {1-c:>9.0%} {note}")
print("  读法：**每个请求都要有终态结算（含取消）**，并配「预留 TTL + 后台对账」——")
print("        否则一次崩溃就会永久吃掉一批配额")

print("")
print("④ 加权 token：输入/输出单价不同（$3 vs $15，权重 5x）")
print(f"  {'负载(输入:输出)':>16} {'真实成本':>10} {'按原始 token 计':>15} {'低估':>7} {'等效权重':>9}")
for pin, pout in ((1000, 200), (200, 1000), (4000, 100), (100, 100)):
    true = pin / 1e6 * USD_IN + pout / 1e6 * USD_OUT
    raw = (pin + pout) / 1e6 * USD_IN
    w_eff = (pin * USD_IN + pout * USD_OUT) / ((pin + pout) * USD_IN)
    print(f"  {str(pin) + ':' + str(pout):>16} ${true:>8.5f} ${raw:>13.5f} "
          f"{1 - raw/true:>6.0%} {w_eff:>8.2f}x")

print("        所以必须用加权 token（或输入/输出各一个桶）")

print("")
print("⑤ 推荐设计（六条）")
@dataclass
class Rule:
    item: str
    why: str
    evidence: str
RULES = [
    Rule("桶按加权 token 计量", "输出单价是输入的 5x", "按原始 token 低估 9%-77%"),

    Rule("预扣用 min(max_tokens, cap) 收紧", "预扣上界会误拒", "纯 max_tokens 预扣误拒 28.7%"),

print("  读法：**六条缺一条，配额就会被超发或泄漏** —— 这就是本题的答案骨架")

print("")
print("⑥ 超发时的三个策略")
@dataclass
class Policy:
    name: str
    good: str
    bad: str
POLICIES = [
```

## 常见追问

- **追问**：为什么不用「按请求数限流 + 按 token 计费」分开做？
  - 要点：**因为两者防的是不同的东西**：① **按请求数限流**防的是「请求风暴」（连接数、调度压力）；② **按 token 限流**防的是「算力消耗」（一个 128K 请求可能顶几千个短请求，串 [[xai-04]]）。**只做前者，用户可以用少量长请求打满算力**；**只做后者，用户可以用大量空请求打满调度**。**所以两层都要有**——而且**它们的桶是独立的**（一个是请求/秒，一个是 token/秒）。
- **追问**：预扣与结算之间的一致性怎么保证？
  - 要点：**承认必然有不一致窗口**，工程目标是**把它做小 + 能对账**：① **窗口做小**——生成中增量结算（每 $n$ 个 token 扣一次），而不是只在结束时结算；② **能对账**——预留记录带 `request_id` 与 TTL，后台定期扫描「有预留无结算」的记录；③ **可观测**——监控「在途预扣总额」（它是「已承诺但未确认」的敞口）。**关键指标**：`在途预扣 / 配额`——这个比例高说明结算路径有延迟或泄漏。
- **追问**：多租户怎么隔离？
  - 要点：**三层**：① **每租户独立的桶**（配额、补充速率、突发额度都可配）；② **全局兜底桶**（防止所有租户一起打满系统——**这是保护自己，不是保护租户**）；③ **优先级/权重**（付费等级不同 → 补充速率不同；**并且要有「降级而非拒绝」的策略**，例如高峰期降低低优先级租户的速率而不是直接 429）。**注意**：全局桶的容量要按「最坏情况」设计（所有租户同时突发）。
- **追问**：流式响应下怎么结算？
  - 要点：**三处**：① **预扣**在准入时完成（按 `min(max_tokens, cap)`）；② **增量结算**在流式回调里做（每 $n$ 个 token 一次原子扣减 + 释放预留）；③ **终态**在流关闭时做（**包括客户端断开**——**断开也要按已生成部分计费**，因为算力已经花了）。**注意**：**客户端断开后服务端未必立刻知道**（TCP 半开），所以要靠**心跳/写失败检测 + TTL 兜底**。
- **追问**：怎么防止「欠费刷爆」？
  - 要点：① **透支上限**（例如配额的 10%，或绝对上限）；② **预付余额**（企业客户先充值，透支从余额扣）；③ **速率限制**（透支时降低补充速率，让用户「还得上」）；④ **风控规则**（异常模式检测：突然大量长输出、频繁取消、多账号同源）；⑤ **硬停兜底**（对未付费/高风险租户直接掐断）。**核心原则：透支额度要「有界且可追缴」。**
- **追问**：怎么衡量限流器做得好不好？
  - 要点：**五个指标**：① **误拒率**（本可服务却被拒——**直接对应收入损失**）；② **超发率**（配额被突破的程度）；③ **结算延迟**（从请求结束到配额确认的时间——决定「在途敞口」）；④ **泄漏量**（未释放的预留——应对账修正）；⑤ **突发满足率**（合法突发请求被满足的比例——**体验指标**）。**注意不要只监控「拒绝率」**：拒绝率高可能是限流太紧（误拒），也可能是用户真的超量——**必须区分**。
