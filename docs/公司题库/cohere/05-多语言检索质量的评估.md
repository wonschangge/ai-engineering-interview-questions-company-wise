## 一句话答案

> **先分清三种「多语言」**——评估方法完全不同：
> | 场景 | 查询语言 | 文档语言 | 关键依赖 |
> | --- | --- | --- | --- |
> | **跨语言检索（CLIR）** | 法语/韩语 | 英文 | **共享向量空间对齐质量** |
> | **单语言检索** | 韩语 | 韩语 | 该语言的语料覆盖与分词 |
> | **混合语料检索** | 任一 | 多语言混合 | 语言识别 + 每语言的分析器 |
> 题目描述的是**第一种**（法语/韩语查询、英文为主的文档），所以核心问题是：**embedding 空间在「跨语言」上对齐得怎么样**。
> **评估的五条纪律**：
> ① **评测集必须反映真实的语言构成**（从日志里统计各查询语言的占比与意图分布），**不能只用英语评测再外推**；
> ② **按语言分群报告，永不只看聚合值**——聚合平均会把韩语的严重退化掩盖成「整体还行」（这是本题最重要的一条，也是本仓库反复出现的主题）；
> ③ **同时报告「查询侧」与「文档侧」的语言矩阵**（$3\times3$ 表），才能定位是「查询理解差」还是「文档表达差」；
> ④ **要有基线对照**：① 多语言 embedding 直检、② **查询先翻成英文再检索**、③ 文档离线翻成英文再建索引、④ 每语言各自建索引 + 词法兜底——**「直接多语言」不一定赢**，取决于语料构成与翻译质量；
> ⑤ **端到端也要按语言评**（答案正确率、引用正确率、是否用正确语言回答），因为**检索指标不等于答案质量**。
> **可诊断的三个量化信号**（本轮的「可算」部分）：
> - **语言鸿沟** $\text{gap}=\text{metric}(\text{en})-\text{metric}(\text{lang})$——把它当成 **SLO 门禁**（例如「任何语言的 recall@20 不得比英语低 10 个百分点以上」）；
> - **对齐度**：取一批句子及其人工翻译，测 $\cos(f(\text{src}), f(\text{tgt}))$ 的分布——**低对齐 = 共享空间对该语言弱**（这是「能不能跨语言」的直接体检）；
> - **脚本规范化**：Unicode NFC/NFD、全角/半角、韩文谚文组合（한글 자모）会导致**同一文本产生不同向量**——必须统一规范化后再入库（否则召回率被「看起来一样」的重复项吃掉）。
> 一句话判据：**「哪种语言的用户受到了伤害、伤害有多大、是检索的哪一段造成的」**——三个问题都答得上来，才叫评估了多语言检索。

## 面试官在考什么

- **是否先分清场景**：CLIR / 单语言 / 混合语料三者的评估重点不同；能否主动指出题目属于 CLIR。
- **分群纪律**：能否坚持按语言分组报告，并用「聚合掩盖」的例子说明为什么要这样（这是最能体现评估素养的一点）。
- **矩阵思维**：能否同时看查询语言与文档语言（$3\times3$），而不是只看一个维度。
- **基线设计**：能否想到「翻译后再检索」这条常被忽略的强基线，以及它在什么条件下更好。
- **可诊断的信号**：对齐度（翻译对余弦）、语言识别错误、分词/脚本问题——能否给出**能定位到具体环节**的指标，而不是只有一个总分。
- **Unicode/脚本工程**：NFC/NFD、全角半角、韩文组合、CJK 无空格分词——**这些细节往往是「韩语效果差」的真实原因**。
- **评测集构建的现实约束**：多语言标注成本高 → 抽样策略、LLM 裁判 + 人工校验、按语言分层、以及**判官一致性报告**。
- **端到端与生成侧**：低资源语言上模型更容易幻觉/答错语言；能否把「答案质量」也按语言评。
- **可执行的门禁**：语言鸿沟能不能写进上线门禁与回归测试（串 [[databricks-07]]）。

**常见错误答案**

- 只跑英语评测集，然后说「多语言模型应该没问题」。
- 只报一个总体 nDCG（聚合值掩盖分群崩溃）。
- 不做「翻译后检索」的对照（可能它更好）。
- 不做 Unicode 规范化（同一韩文文本两种编码，索引里出现重复项）。
- 用英语 LLM 裁判直接评法语/韩语答案，且不校验一致性。
- 忽略生成侧（检索对了但答案用错语言/幻觉更多）。
- 没有把语言鸿沟变成可回归的指标（下次发布又退化）。

## 原理与推导

### 1. 跨语言检索的成立条件（对齐）

设共享编码器 $f$，理想情况下同一语义的不同语言表示应接近：

$$\cos\big(f(\text{「退款流程」}),\ f(\text{「refund process」})\big)\approx1$$

**这是「能否跨语言检索」的充分必要条件**——若对齐差，法语查询与英文文档在向量空间里就是「远」的，任何 ANN 都救不回来。

**度量对齐度**：取 $n$ 对人工翻译句，统计 $\cos$ 的分布（均值、P5、以及「跨语言最近邻命中率」= 用源语言句在目标语言句集中找最近邻，命中的比例）。**跨语言最近邻命中率**是最直观的指标（也叫 translation retrieval accuracy）。

### 2. 评估矩阵（按语言两维）

$$\text{Recall@}k^{(\ell_q,\ell_d)}=\frac{|\text{top-}k\cap R|}{|R|}\quad\text{对查询语言}\ \ell_q\ \text{与文档语言}\ \ell_d$$

**典型形态**（示例）：英语→英语 ≈ 0.95；法语→英语 ≈ 0.88；韩语→英语 ≈ 0.70。**只看「平均 0.84」会以为没问题**，但韩国员工的实际体验是「搜不到」。

**加权问题**：聚合值取决于**查询语言的占比**。若韩语查询只占 5%，聚合值几乎不受影响——**这正是「聚合掩盖」的机制**。所以：

$$\text{聚合}=\sum_{\ell_q} w_{\ell_q}\cdot\text{metric}^{(\ell_q)}\quad\Rightarrow\quad\text{必须同时报告}\ w_{\ell_q}\ \text{与分群值}$$

### 3. 两条基线的取舍

| 方案 | 机制 | 优势 | 劣势 |
| --- | --- | --- | --- |
| 多语言 embedding 直检 | 共享空间 | 无翻译延迟、可索引 | 依赖对齐质量（低资源语言弱） |
| **查询翻译后检索** | 查询 → 英语 → 英文索引 | 复用最强的英文检索 | **翻译错误直接损失召回**（专名/缩写） |
| 文档离线翻译 | 全库译成英语再建索引 | 检索质量接近英语 | 成本 ×N、翻译错误永久化、更新困难 |
| 每语言独立索引 | 各语言自己的模型 | 单语言质量最优 | 跨语言查询无法直接命中 |

**判据**：当「翻译质量 × 英文检索增益 > 对齐损失」时，翻译后检索更好。**所以要用实测决定，而不是默认**。

### 4. 脚本与规范化（最容易被忽略的工程细节）

| 问题 | 例子 | 后果 |
| --- | --- | --- |
| NFC vs NFD | 韩文「각」可以是 1 个组合字符或 2–3 个 jamo 序列 | **相同文本被当成不同字符串** → 索引重复、召回下降 |
| 全角/半角 | `ＡＢＣ` vs `ABC`、`１２３` vs `123` | 查询命中不到文档 |
| 大小写/变音符号 | `café` vs `cafe`、德语 ß | 词法检索（BM25）失配 |
| CJK 无空格 | 中文/日文需分词，韩文有空格但助词黏着 | 分词错误 → 词法召回差 |
| 零宽字符/不可见字符 | 从 PDF/网页复制带来 | 精确匹配失败 |

**对策**：入库与查询**走同一条规范化管线**（NFKC 或 NFC + 大小写折叠 + 全角转半角 + 去零宽），并把它写进**契约测试**（串 [[databricks-09]] 的契约测试清单）。

### 5. 判官与标注（多语言下的现实做法）

- **人工标注**：每种语言需要母语者；成本高 → **分层抽样**（按语言 × 意图 × 难度），每种语言至少几百条查询才能检出 5 个百分点的差距（见下）；
- **LLM 裁判**：便宜、可扩展，但**必须按语言校验**——用一小批人工标注算一致性（Cohen's κ / 一致率），κ 低就不能用；
- **池化（pooling）**：相关文档集合来自多个系统的 top-k 并集，避免「只标注自己系统返回的结果」造成的偏差。

### 6. 端到端也要分语言

低资源语言的常见失败模式（检索对了但答案错）：
- **答错语言**（用户问法语，回答英语）→ 需要**语言一致性指标**；
- **幻觉更多**（模型在低资源语言上更弱）→ 需要**引用正确率**与**拒答率**；
- **格式退化**（结构化输出在非英语下更易违反 schema）→ 需要**契约测试按语言跑**。

```python
t1 = unicodedata.normalize("NFC", "각")
t2 = unicodedata.normalize("NFD", "각")
print(f"  直观演示：同一个「각」—— NFC 长度 {len(t1)}、NFD 长度 {len(t2)}，两者相等？{t1 == t2}")
print("  读法：**规范化管线必须「入库与查询一致」，且要选对形式** —— 韩文要用 NFC/NFKC 统一，")
print("        全角/兼容字符要用 **NFKC**；否则同一段文本会产生两套向量（索引重复、召回被稀释），")
print("        词法检索（BM25）更会因为码点不同而完全失配（这是「韩语/日语效果差」的常见真凶）")

# ---------- 4) 需要多少标注才能检出语言鸿沟 ----------
def n_paired(delta: float, sd_diff: float = 0.35, alpha: float = 0.05,
             power: float = 0.8) -> int:
    return math.ceil((z(1 - alpha/2) + z(power)) ** 2 * sd_diff ** 2 / delta ** 2)
print("\n④ 每个语言要标多少条查询（配对设计：同一批查询跑新旧两版，sd=0.35）")
print(f"  {'要检出的鸿沟':>12} {'需要查询数':>10} {'含义':<20}")
for d in (0.10, 0.05, 0.03):
    n = n_paired(d)
    note = "小规模即可" if n <= 400 else ("需要上千条" if n <= 1500 else "不现实（改判据）")
    print(f"  {d:>12.0%} {n:>10,} {note:<20}")
print("  读法：**检出 5 个百分点的语言鸿沟约需 385 条查询/语言**（配对设计），3 个百分点要 1,069 条——")
print("        对只有几十个员工的语种不可行 → 此时改用「LLM 裁判 + 人工抽检」并**明确标注置信度不足**")

# ---------- 5) 语言鸿沟作为上线门禁 ----------
@dataclass
class Gate:
    lang: str
    recall20: float
    gap_limit: float = 0.10
    def status(self, en_recall: float) -> Tuple[bool, str]:
        gap = en_recall - self.recall20
        return gap <= self.gap_limit, f"鸿沟 {gap:+.3f}（上限 {self.gap_limit:.2f}）"
print("\n⑤ 语言鸿沟门禁（英语 recall@20 = 0.970；允许鸿沟 0.10）")
for g in (Gate("法语", 0.873), Gate("德语", 0.854), Gate("韩语", 0.698), Gate("日语", 0.728)):
    ok, note = g.status(0.970)
    print(f"  {g.lang:<6} recall@20 {g.recall20:.3f} -> {'通过' if ok else '**不通过（阻塞发布）**'}  {note}")
print("  读法：**把语言鸿沟写成发布门禁**（而不是「以后优化」）—— 这样每次换模型/换索引/换量化")
print("        都会被同一把尺子量一遍，低资源语言的退化不会悄悄溜过去")
```

预期输出要点（实跑）：① 分群召回矩阵显示**英语 0.97、法语 0.87、韩语 0.70**，而**加权聚合值 0.92 看起来「整体不错」**——因为英语占 62% 权重，韩语掉 25 个点只把聚合拉低 2.5 个点，**这就是聚合掩盖分群崩溃的机制**；② 两条基线对照显示**胜负取决于「对齐质量」与「翻译质量」的相对关系**（对齐差的低资源语言上翻译后检索常反超）；③ Unicode 演示（真实行为）显示韩文 `각` 的 NFC 与 NFD 是**不同长度的不同字符串**，全角/变音符号同理——**未规范化会让同一文本产生两套向量**；④ 样本量显示**检出 5 个百分点的语言鸿沟约需 385 条查询/语言**（3 个百分点要 1,069 条），小语种不具备这个样本量时要**明确标注置信度不足**；⑤ 语言鸿沟门禁（上限 0.10）把**韩语（0.272）、日语（0.242）、德语（0.116）**都标成**阻塞发布**——只有法语（0.097）勉强通过。

## 常见追问

- **追问**：如果某种语言没有足够的标注数据怎么办？
  - 要点：① **LLM 裁判 + 人工抽检**（用 100–200 条人工标注校验一致性，κ 达标才用）；② **翻译复用**：把英语评测集**人工翻译**成目标语言（保留原判定的相关性），这是多语言评测的常见做法；③ **对齐度作为代理指标**（翻译对余弦/最近邻命中率）——它能快速发现「这个语言的共享空间坏了」；④ **明确标注置信区间**，不要把「没数据」说成「没问题」。
- **追问**：怎么判断问题出在检索而不是生成？
  - 要点：**分层量**——① 检索层：recall@k / nDCG@n（按语言）；② 上下文层：喂给模型的文档里**是否含正确答案**（oracle 对比：把金标文档强制塞进去看答案正确率）；③ 生成层：语言一致性、引用正确率、拒答率。**如果 oracle 条件下答案仍错 → 问题在生成；若 oracle 大幅提升 → 问题在检索。**
- **追问**：Unicode 规范化会不会改变语义？
  - 要点：**NFKC 会**（它做兼容性折叠：全角→半角、`①`→`1`、`㍿`→`株式会社`），对检索通常有利但对「必须原样保留」的字段（代码、密码、化学式）**有害**。所以常见做法是**保留原文用于展示**，另存**规范化字段用于检索**；并对不同类型字段用不同规则（NFKC 用于普通文本，NFC 用于标识符）。
- **追问**：多语言 embedding 与「每语言一个模型」怎么选？
  - 要点：① 需要**跨语言检索**（法语查英文文档）→ 必须共享空间（多语言模型）；② 只做**单语言检索**且资源充足 → 每语言专用模型往往更强；③ 现实折中：**一个多语言模型 + 每语言微调/适配器**，或**路由**（按查询语言选模型/索引）。**评估时要按这两种形态分别量。**
- **追问**：混合语言文档（英文文档里夹法语术语）怎么处理？
  - 要点：① **按 chunk 检测语言**（文档级检测会错）；② 索引里存**多语言字段**或用多语言模型编码（共享空间天然处理混合）；③ 词法侧对混合 chunk **两种分析器都建索引**（或按 chunk 语言路由）；④ 评测集里**必须包含混合语言样本**，否则这类失败不会被发现。
- **追问**：语言鸿沟该设多大？
  - 要点：按**业务后果**定：内部知识库可接受 10 个百分点；对外客服/合规场景可能只允许 3–5 个。**关键是写进 SLO 并回归**，而不是追求「零鸿沟」（低资源语言的绝对质量有客观上限）。
- **追问**：怎么持续监控线上多语言质量？
  - 要点：① 按语言的**点击/采用率、追问率、人工接管率**（隐式信号）；② **零结果率**与**低分率**（按语言）；③ 定期（每周/每月）跑**分语言回归集**；④ **查询语言识别的错误率**（识别错会让分析器用错）；⑤ 把「语言鸿沟」和「零结果率」放进同一块看板。
