## 一句话答案

> **排查的第一步不是看检索，而是「固定生成侧」**——这是本题最关键的方法论：
> **把同一份上下文分别喂给「变差前后」的生成链路**；若答案质量一致 → 问题在**检索/上下文组装**；若不一致 → 问题在**生成侧或数据本身**。**先做这个二分，再往下钻**，否则会在错误的层里浪费几天。
> **然后按四层分解「变差」**（每一层都有可测指标）：
> | 层 | 10 倍扩容后典型变化 | 可测指标 |
> | --- | --- | --- |
> | **① 索引/量化** | 为了控成本换了索引类型或量化（HNSW→IVF-PQ），**召回下降**；IVF 的 `nlist/nprobe` 未随 $N$ 调整；聚类中心过期 | recall@k、nprobe 曲线、量化前后对照 |
> | **② 检索竞争（top-k 稀释）** | **同样的 k 要从 10 倍候选里选**，正确 chunk 被挤出 top-k 的概率上升 | recall@k 随 $N$ 的变化曲线 |
> | **③ 上下文组装** | top-k 里噪声/近重复变多，真正有用的内容被挤出上下文预算；新旧版本同时被检索到 → **矛盾信息** | 上下文里「有效内容占比」、重复率、冲突率 |
> | **④ 数据质量** | 新增的 9 倍数据里混入**过期/重复/样板文本**；元数据缺失导致过滤掉 | 去重后规模、元数据覆盖率、时效分布 |
> **「top-k 稀释」是本轮最值得讲清的机制**（也是它在数学上必然发生的原因）：
> 相关 chunk 的分数是 $s_{\text{rel}}\sim\mathcal N(\mu,\sigma)$，而要进 top-$k$ 就得超过其余候选的**第 $k$ 大值**——这是个**极值**问题，候选越多，这个门槛越高：
> $$\text{门槛}\approx\sigma\,\Phi^{-1}\!\Big(1-\frac{k}{N_{\text{eff}}}\Big),\qquad N_{\text{eff}}=\frac{N}{c}\ (c\ \text{为聚类系数})$$
> **注意 $N_{\text{eff}}$**：真实语料里 chunk 彼此高度相似，**不是 $N$ 个独立竞争者**（本机模型取 $c=2000$）。即便如此，$N$ 增大仍会抬高门槛——**要保持同样的召回，$k$ 必须随 $N$ 增长**（实测：10 万→1000 万，维持召回 0.90 所需的 $k$ 从 2 涨到 200，即 **100 倍**）。
> **修复清单（按发现的问题对号入座）**：
> 1. **索引参数重调**：IVF 的 `nlist ≈ √N`、`nprobe` 按召回目标调；换量化方案后**必须重跑召回评估**（串 [[cohere-04]]）；
> 2. **k 与 reranker 一起调**：k 从 20 提到 100–200，**用 reranker 把噪声压回去**（串 [[cohere-03]]）——这是「扩容后仍保住精度」的标准解；
> 3. **近重复去重**（内容哈希 + 语义近重复）+ **时效/权威度加权**；
> 4. **元数据与 ACL 覆盖率**补齐（新数据的过滤字段不能为空）；
> 5. **上下文预算重新分配**：按 rerank 分数截断、去重、必要时提高上下文长度；
> 6. **冲突消解**：同一主题多版本时**只保留最新/最权威**（在检索侧做，而不是让模型自己判断）。
> 一句话判据：**「10 倍数据」不会让检索变差，但「10 倍的候选竞争 + 为省钱改的索引参数」会**——所以排查要盯住这两件事，而不是怀疑模型变笨了。

## 面试官在考什么

- **是否先定义「变差」**：能否要求具体例子、时间点、影响范围、以及「和什么比」（基线是扩容前还是某个版本）——**没有定义的「变差」无法排查**。
- **分阶段隔离的能力**：能否提出「固定生成侧、只换上下文」的对照实验（这是把问题二分的最快手段）。
- **是否想到 top-k 稀释**：能否从数学上说明「同样的 k 在更大库里召回更低」（极值/噪声最大值），这是本题区分度最高的一点。
- **索引与量化的联动**：扩容往往伴随「为控成本而换索引类型/量化」，能否把两者联系起来（串 [[cohere-04]]）。
- **数据质量视角**：新增数据是否引入重复/过期/样板，元数据是否齐全——**很多「检索变差」其实是数据变脏**。
- **上下文侧**：噪声变多、重复占位、冲突信息——能否把「模型答错」归因到「上下文被污染」。
- **可诊断的指标**：能否给出每层的量化指标（recall@k、nprobe 曲线、重复率、有效内容占比、冲突率），而不是只看端到端。
- **修复的优先级与验证**：先做便宜且高收益的（k + reranker、去重），再做贵的（重建索引）；并且**每个修复都要有前后对照**。
- **沟通**：能否给客户一个「48 小时内的初步结论 + 一周内的修复计划」，以及临时缓解（回退索引版本、限流重建）。

**常见错误答案**

- 直接怀疑「模型变笨」（LLM 版本未变就不该先怀疑它）。
- 只看端到端分数，不做分层测量（无法定位）。
- 忽略「扩容时的索引参数变更」（最常见的技术原因之一）。
- 认为「数据更多 = 召回更高」（忽视候选竞争与噪声）。
- 不去重（10 倍数据里往往有大量重复 chunk）。
- 不设临时缓解，直接开始长期重构（客户在等）。
- 不做修复前后对照（无法证明修好了）。

## 原理与推导

### 1. top-k 稀释：为什么扩容会降低召回

设相关 chunk 的打分 $s_{\text{rel}}=\mu+\epsilon_{\text{rel}}$，无关 chunk $s=\epsilon_i$，$\epsilon\sim\mathcal N(0,\sigma^2)$。相关 chunk 进入 top-$k$ 的条件是「它在 $N$ 个无关 chunk 中排进前 $k$」：

$$P(\text{recall@}k)\approx P\Big(\mu+\epsilon_{\text{rel}}>\ \text{第 }k\text{ 大的噪声}\Big)$$

$N$ 个噪声的第 $k$ 大值期望约为 $\sigma\,\Phi^{-1}\!\big(1-\tfrac{k}{N+1}\big)$。**当 $N$ 增大而 $k$ 固定时，这个阈值上移**：

$$\Delta_{\text{阈值}}\approx\sigma\Big[\Phi^{-1}\big(1-\tfrac{k}{10N}\big)-\Phi^{-1}\big(1-\tfrac{k}{N}\big)\Big]$$

**直观版本**：噪声最大值 $\approx\sigma\sqrt{2\ln N}$，$N\to10N$ 时上移 $\sigma\sqrt{2\ln10}\approx2.15\sigma$。**若相关 chunk 的信号裕度 $\mu$ 只有 1–2$\sigma$，扩容后它就会被噪声淹掉**——这正是「10 倍数据让回答变差」的数学根源。

### 2. 要保持召回，k 需要增多少

由 $\Phi^{-1}(1-k/N)$ 的关系：**要让阈值不变**，需要 $k/N$ 保持不变，即 **$k$ 也应 ×10**。但 k 增大带来：延迟线性上升、上下文噪声变多。**所以正确做法不是无限增大 k，而是「增大 k + reranker 收窄」**：

$$k_{\text{retrieve}}=100\text{–}200\ \xrightarrow{\ \text{rerank}\ }\ n=5\text{–}20$$

**这就是扩容后仍能保住精度的标准解法**（串 [[cohere-03]]）。

### 3. IVF 的参数为什么必须随 N 重调

IVF 把向量聚成 `nlist` 个簇，查询只扫 `nprobe` 个簇：

$$P(\text{命中正确簇})\approx 1-\Big(1-\frac{nprobe}{nlist}\Big)^{?}\ \text{（取决于分布）},\qquad \text{扫描量}\propto\frac{nprobe}{nlist}\cdot N$$

**经验规则**：`nlist ≈ √N`（$N=10^6\to10^3$，$N=10^7\to3.2\times10^3$）。**若扩容后沿用旧的 `nlist`**，每个簇变得过大、簇内噪声增多，同时 `nprobe` 未调 → **召回与延迟同时恶化**。另外**聚类中心必须用新数据重训**（旧中心在 10 倍数据上分布失配）。

### 4. 近重复与上下文稀释

设去重前有 $N$ 个 chunk，其中比例 $\rho$ 与其他 chunk 近重复。有效候选多样性为 $(1-\rho)N$，但**top-k 名额被重复占掉**：

$$\text{有效信息量}\approx k\,(1-\rho)$$

若 $\rho=0.3$、$k=10$ → 实际只有 7 条不同信息。**修复**：内容哈希（精确重复）+ MinHash/embedding 近重复（语义重复）→ **在检索后做 MMR/去重**（既省上下文又提质）。

### 5. 上下文里的「有效内容占比」

$$\text{精度@top-}k=\frac{\text{相关 chunk 数}}{k}$$

扩容 + 固定 k → 精度下降 → 上下文里「有用的比例」下降。而模型对长上下文的使用是**非均匀的**（中间位置容易被忽略，串 [[rag-01]] 的「lost in the middle」）。所以：

$$\text{答案质量}\approx f(\text{精度},\ \text{位置},\ \text{总长度})$$

**推论**：与其把 k 从 20 加到 200 直接喂给模型，**不如加 k 后用 reranker 收窄到 5–20**——同样的召回，更干净的上下文。

### 6. 数据侧：扩容常见的三类污染

| 污染 | 表现 | 检测 |
| --- | --- | --- |
| **重复**（同一文档多次入库/多版本） | top-k 全是同一内容的不同版本 | 内容哈希重复率、embedding 近重复率 |
| **过期**（旧政策未删） | 答案引用已废止的条款 | 时效分布、与权威源的冲突率 |
| **样板/噪声**（页眉页脚、导航、OCR 垃圾） | 检索命中「目录/免责声明」 | 长度异常 chunk 占比、模板检测 |

**这三类在「10 倍扩容」里极常见**——因为新数据往往来自自动化导入（多来源、多格式）。

import math
from dataclasses import dataclass
from typing import Dict, List, Tuple

def norm_cdf(x: float) -> float:
    """标准正态分布函数"""
    return 0.5 * (1 + math.erf(x / math.sqrt(2)))

def norm_ppf(p: float) -> float:
    """标准正态分位数（Acklam 近似）"""
    a = [-3.969683028665376e+01, 2.209460984245205e+02, -2.759285104469687e+02,
         1.383577518672690e+02, -3.066479806614716e+01, 2.506628277459239e+00]
    b = [-5.447609879822406e+01, 1.615858368580409e+02, -1.556989798598866e+02,
         6.680131188771972e+01, -1.328068155288572e+01]
    c = [-7.784894002430293e-03, -3.223964580411365e-01, -2.400758277161838e+00,
         -2.549732539343734e+00, 4.374664141464968e+00, 2.938163982698783e+00]
    d = [7.784695709041462e-03, 3.224671290700398e-01, 2.445134137142996e+00,
         3.754408661907416e+00]
    if p < 0.02425:

        return (((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q+c[5]) / ((((d[0]*q+d[1])*q+d[2])*q+d[3])*q+1)

        return -(((((c[0]*q+c[1])*q+c[2])*q+c[3])*q+c[4])*q+c[5]) / ((((d[0]*q+d[1])*q+d[2])*q+d[3])*q+1)

# ---------- 1) top-k 稀释 ----------
SIGMA = 0.30          # 打分噪声
MU = 0.91             # 相关 chunk 的信号裕度（以分数为单位）
CLUSTER = 2000        # ★ 有效干扰项折算：embedding 聚类使独立竞争者远少于 N
def recall_at_k(N: int, k: int, mu: float = MU, sigma: float = SIGMA) -> float:
    """相关 chunk 的分数 ~ N(mu, sigma)；要进 top-k 需超过 N_eff 个噪声的第 k 大值。
    N_eff = N / CLUSTER：真实语料里大量 chunk 彼此高度相似，**不是 N 个独立竞争者**。"""
    n_eff = max(2.0, N / CLUSTER)
    p = min(0.5, k / n_eff)
    thresh = norm_ppf(1 - p) * sigma
    return 1 - norm_cdf((thresh - mu) / sigma)

print(f"  {'N':>12} {'有效干扰项':>10} " + " ".join(f"{'k=' + str(k):>9}" for k in KS))

    n_eff = max(2.0, N / CLUSTER)
    print(f"  {N:>12,} {n_eff:>10,.0f} " + " ".join(f"{recall_at_k(N, k):>9.3f}" for k in KS))
print("  读法：**固定 k=10 时，库从 10 万增到 1000 万会让召回明显下滑** —— 因为噪声的第 k 大值")

print("        注意这里用的是**有效干扰项数**：真实语料里 chunk 高度相似，不是 N 个独立竞争者")

def k_needed(N: int, target: float = 0.90, mu: float = MU) -> int:
    for k in range(1, 200001):
        if recall_at_k(N, k, mu) >= target:
            return k
    return -1

# ---------- 3) 扩容时的量化叠加 ----------
@dataclass
class Config:
    name: str
    nlist_ok: bool
    pq_m: int
    k: int
    def effective_recall(self, N: int, mu: float = MU) -> float:
        r = recall_at_k(N, self.k, mu)
        if not self.nlist_ok:
            r *= 0.82                      # 簇过大 + 中心过期（示例惩罚）
        if self.pq_m:
            pq_loss = {64: 0.02, 32: 0.10, 16: 0.25, 8: 0.40}.get(self.pq_m, 0.5)
            r *= (1 - pq_loss)
        return max(0.0, r)

    Config("扩容后：N=1000 万、k=10、沿用旧 nlist、PQ m=16", False, 16, 10),
    Config("修复 A：重调 nlist/nprobe", True, 16, 10),
    Config("修复 B：A + k 提到 100", True, 16, 100),
    Config("修复 C：B + PQ 提到 m=64", True, 64, 100),
]
print("")
print("③ 扩容常伴随「为省钱换索引/量化」：两重损失叠加")

for c in CONFIGS:

    r = c.effective_recall(N)
    prec = min(1.0, 2 * r / 10)

# ---------- 4) 修复组合：加 k + 重排 + 去重 ----------
@dataclass
class Fix:
    name: str
    k_retrieve: int
    rerank: bool
    dedup: bool
    n_relevant: int = 2
    n_final: int = 10
    dup_ratio: float = 0.30
    def context_precision(self, N: int) -> float:
        """上下文精度 = min(1, 相关条数/名额) × 信息密度 × 重排增益"""
        r = recall_at_k(N, self.k_retrieve)
        density = 1.0 if self.dedup else (1 - self.dup_ratio)   # 重复项白占名额
        gain = 1.15 if self.rerank else 1.0                     # 重排把相关的排到前面
        base = min(1.0, self.n_relevant * r * gain / self.n_final)
        return min(1.0, base * density + 0.0)

print(f"  {'修复':<40} {'候选召回':>9} {'信息密度':>9} {'上下文精度':>11}")
for f in (Fix("什么都不做（k=10，无重排，无去重）", 10, False, False),
          Fix("只去重", 10, False, True),
          Fix("k=100 + 重排", 100, True, False),
          Fix("k=100 + 重排 + 去重（推荐）", 100, True, True)):

print("        重复项与噪声抵消）；注意去重同时提高信息密度 —— 这是 ROI 最高的一步")

## 常见追问

- **追问**：怎么区分「检索没返回」和「返回了但答错」？
  - 要点：**oracle 对照**——把金标文档强制塞进上下文，看答案是否正确。若 oracle 下正确 → 问题在检索（recall@k 不够）；若仍错 → 问题在生成或上下文组装（噪声、冲突、长度、位置）。这是最快、最便宜的分层手段（也在 [[cohere-05]] 里出现过）。
- **追问**：为什么不直接把 k 加到 500？
  - 要点：① 延迟与成本线性上升（rerank 与上下文 token）；② **上下文变长会让模型更差**（「lost in the middle」、噪声干扰）；③ 却不一定提高端到端质量。**正解是「大 k 召回 + 重排收窄」**——用算力换精度，而不是把噪声塞给模型。
- **追问**：扩容时换 IVF-PQ 是「错」的吗？
  - 要点：**不是错，是取舍**——10 倍数据下全精度 HNSW 的内存成本可能不可接受（串 [[cohere-04]]）。**错的是「换了不改评估」**：换索引/量化必须重跑召回评测，并**重调 `nlist/nprobe`、用新数据重训聚类中心**。
- **追问**：近重复怎么检测？
  - 要点：三层——① **精确哈希**（同文档多次入库）；② **MinHash/SimHash**（近似重复的文本）；③ **embedding 近邻**（语义重复，例如同一政策的不同措辞）。检索后还可以做 **MMR**（最大边际相关性）在多样性上取舍。**去重既省上下文又提质，通常 ROI 最高。**
- **追问**：客户说是「模型变差了」怎么办？
  - 要点：先用**版本证据**排除——prompt/模型/索引/数据的版本号与变更时间线（串 [[databricks-09]] 的版本化能力）。若模型未变，把取证结果给客户看：**「同一份上下文，新旧两版答案一致；差别在于检索返回的内容」**。**用对照实验说话，比争论有效。**
- **追问**：怎么防止下次扩容再出问题？
  - 要点：① **扩容走同一套评测门禁**（recall@k 与端到端质量都要过）；② **索引参数随规模自动重算**（`nlist≈√N`）；③ **数据入库做去重、元数据校验、时效标记**；④ **上线前跑「扩容演练」**（用 10 倍数据量做影子测试）；⑤ 把 **k 与重排配置**纳入按规模的配置模板。
- **追问**：临时缓解能给什么？
  - 要点：① **回退到扩容前的索引快照**（如果客户能接受「搜不到新数据」）；② **临时提高 k 并开启重排**（几小时内可生效）；③ **对高频失败 query 建立人工/规则兜底**；④ **明确时间线与下一步**（48 小时结论、一周修复）。**临时缓解 + 透明沟通**是排查期最重要的交付物之一。
