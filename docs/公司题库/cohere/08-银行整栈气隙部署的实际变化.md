## 一句话答案

> **先摆清部署谱系**——「私有化」不是一个点，而是一段区间，气隙是最右端：
> ```
> SaaS → VPC/PrivateLink → BYOC（客户云上你的控制面）→ 本地部署（on-prem，可出网）→ 气隙（完全无外网）
> ```
> **越往右，你失去的是「可观测性与可达性」，客户得到的是「控制与隔离」**。气隙的关键变化可以归成八条：
> | # | 维度 | SaaS | 气隙 |
> | --- | --- | --- | --- |
> | ① | **交付** | 持续部署 | **签名制品包（权重 + 容器 + 索引 + 许可）经物理介质**进入客户离线仓库 |
> | ② | **升级** | 每周 | **季度级**，走客户变更委员会（CAB），且必须**可回滚** |
> | ③ | **许可** | 在线校验 | **离线签名许可文件**（含有效期/额度），用量**本地计量 + 定期导出** |
> | ④ | **可观测性** | 你直接看 | 客户本地监控栈 + **可审阅的诊断包导出**（脱敏后人工交接） |
> | ⑤ | **支持** | 你直接改 | **「远程之手」**：客户操作员按你的 runbook 执行，你在旁边指导 |
> | ⑥ | **容量** | 你扩容 | **客户自己买卡**，你提供选型与压测方法（串 [[cohere-02]]） |
> | ⑦ | **模型更新** | 你切换 | 客户驱动的**刷新节奏**（大文件物流 + 重新评测） |
> | ⑧ | **能力降级** | A/B、灰度、自动升级 | 在线实验难做、升级滞后、故障复现依赖客户配合 |
> **三个必须量化的代价**（本轮的「可算」部分）：
> - **升级税**：每次发版要额外付出「打包 + 安全评审 + CAB 窗口 + 预演 + 回滚演练」的固定成本 → **发布节奏从每周掉到每季度**，而未修复的缺陷会**累积**；
> - **MTTR 变长**：检测 → 上报 → 复现 → 修复 → 打包 → CAB → 部署，链条里多了客户环节，**平均修复时间可能翻数倍**；
> - **过度配置**：客户要自己扛峰值与高可用，**N+1 冗余 + 峰值余量**让他们通常比 SaaS 多买 30%–100% 的 GPU。
> 一句话判据：**气隙卖的不是「同一个软件的离线版」，而是「一整套交付、升级、支持、计量的新流程」**——报价与承诺必须按这套流程重写。

## 面试官在考什么

- **是否先摆谱系**：能否区分 SaaS / VPC / BYOC / on-prem / 气隙，而不是笼统说「私有化」。
- **交付工程**：能否说出制品包内容（权重/容器/索引/许可）、**签名与校验**、离线仓库、SBOM 与 CVE 扫描如何在离线环境完成。
- **升级的真实约束**：能否指出**客户的 CAB 流程**才是节奏的决定因素（技术上一周能发，流程上一季度才放一次），以及**回滚必须演练**。
- **离线许可与计量**：能否给出「签名许可文件 + 本地计量 + 定期导出」的组合（而不是「没法计费」）。
- **可观测性的替代方案**：能否设计**可审阅的诊断包**（客户能先看内容再给你），以及在**看不到真实数据**时如何排障（合成复现 + 客户执行脚本）。
- **支持模式的变化**：能否提出「远程之手」协议（指定客户操作员 + runbook + 变更窗口），以及 SLA 语义要改（响应 ≠ 修复）。
- **容量规划的责任转移**：客户买卡 → 你要给**选型指导、压测方法、峰值与 HA 余量**（串 [[cohere-02]] 的显存算术）。
- **能力降级要诚实**：A/B 实验、自动模型升级、用量计费精度都会变差——**主动说清**比承诺做不到的事专业。
- **商业条款**：气隙通常意味着**订阅/许可制**（而非按量），且**每次升级都是项目**（要算人天）。

**常见错误答案**

- 说「我们打包一个 Docker 镜像就行」（忽略权重、索引、许可、SBOM、离线仓库、回滚）。
- 承诺「和 SaaS 一样的升级频率」（流程上不可能）。
- 不提供离线许可方案（结果无法计费/续期）。
- 想要「回传日志」却没设计脱敏与客户审阅（合规上过不去）。
- 假设你能 SSH 进客户的机器（气隙环境通常不允许）。
- 忽略客户要自己承担峰值与 HA（容量规划甩给客户）。
- 不承认能力降级（A/B、自动升级、计费精度）。

## 原理与推导

### 1. 交付物：一个「制品包」要装什么

| 内容 | 说明 | 常见体积 |
| --- | --- | --- |
| 模型权重 | 生成模型（可能多个尺寸）+ embedding + reranker | 数十 GB 到数百 GB |
| 容器镜像 | 推理服务、编排、向量库、UI、监控 | 数 GB（含基础镜像） |
| 索引/码本 | 若预置（通常客户自建） | 视语料 |
| 许可文件 | 签名 + 有效期 + 额度 | KB |
| 清单与证明 | **SBOM、签名、CVE 扫描报告、测试报告、版本说明** | MB |
| 安装与升级 runbook | 含**回滚步骤**与验收清单 | MB |

**校验链**：介质 → 校验和 → 签名 → SBOM 比对 → 离线仓库导入 → 部署 → 验收测试（客户执行）。**每一步都要可审计**。

### 2. 升级税：为什么节奏会塌到季度级

设 SaaS 一次发布的边际成本 $c_{\text{saas}}$（自动化流水线，≈ 人力几小时），气隙一次发布要叠加：

$$c_{\text{air}}=c_{\text{build}}+c_{\text{sign}}+c_{\text{sec-review}}+c_{\text{staging}}+c_{\text{CAB}}+c_{\text{deploy}}+c_{\text{rollback-drill}}$$

**每一项都是固定成本，与改动大小无关**——这就是「小修小补也要走完整流程」的原因。**推论**：

$$\text{发布频率}\downarrow\ \Rightarrow\ \text{每次发布的改动量}\uparrow\ \Rightarrow\ \text{单次风险}\uparrow\ \Rightarrow\ \text{需要更多测试}$$

**这是一个正反馈**：流程越重 → 越倾向「攒一批再发」 → 单次跳跃越大 → 越需要重流程。**破局手段**：把改动**分级**（安全补丁走加急通道、功能走季度通道），并为加急通道**预先演练**。

### 3. MTTR 分解：链条上多出来的环节

$$\text{MTTR}=\underbrace{t_{\text{detect}}}_{\text{客户发现}}+\underbrace{t_{\text{report}}}_{\text{上报/分级}}+\underbrace{t_{\text{reproduce}}}_{\text{无数据访问}}+\underbrace{t_{\text{fix}}}_{\text{开发}}+\underbrace{t_{\text{bundle}}}_{\text{打包签名}}+\underbrace{t_{\text{CAB}}}_{\text{客户审批}}+\underbrace{t_{\text{deploy}}}_{\text{窗口内安装}}$$

对比 SaaS：后三项几乎为零（持续部署）；气隙下**后三项常常占据总时长的 60%–80%**。所以：

- **要投资「快速通道」**：安全/严重缺陷的**加急发布协议**（预先签好框架、预授权窗口）；
- **要投资「自助诊断」**：把常见故障的**自检脚本与决策树**交给客户运维，让 $t_{\text{reproduce}}$ 不依赖你；
- **要投资「可复现的合成数据」**：你拿不到客户数据，就必须有**合成语料 + 复现脚本**（串 [[cohere-09]] 的「无标注数据」问题）。

### 4. 容量规划：客户买卡，但你要给方法

客户自建时要提供：

$$\text{GPU 数}=\Big\lceil\frac{\text{权重显存}+\text{KV 显存}+\text{激活/工作区}}{\text{单卡显存}\times\text{可利用率}}\Big\rceil\times(1+\text{HA 余量})\times(1+\text{峰值余量})$$

**典型参数**：$1+\text{HA}=1.25$（N+1）、$1+\text{峰值}=1.3$–$2.0$。**注意 KV 与并发**：

$$\text{KV 显存}=2\times L\times H_{\text{kv}}\times d_{\text{head}}\times b\times\text{tokens}\times\text{并发}$$

**这解释了为什么「能装下权重」远不等于「能服务」**——长上下文 + 高并发时 KV 会成为主项（串 [[inference-serving-08]]）。

### 5. 可观测性与诊断包（在看不到数据的前提下排障）

设计原则：**客户能审阅内容，你才能拿到它**。

| 层 | 内容 | 脱敏 |
| --- | --- | --- |
| 指标 | 延迟/吞吐/错误率/队列/显存/命中率 | 无 PII，可直接导出 |
| 配置 | 版本、参数、拓扑、许可状态 | 无 PII |
| 日志 | 结构化错误码 + 时间线 | **必须脱敏**（正则 + 哈希） |
| 检索片段 | 命中的文档 id 与分数（**不含正文**） | 只给 id 与元数据 |
| 合成复现 | 客户用你的脚本在本地跑出最小复现 | 数据不出域 |

**关键**：把「诊断包」做成**客户可一键生成并先自行审阅**的东西——否则法务流程会拖上几周。

### 6. 能力降级（要主动说清）

| 能力 | SaaS | 气隙 |
| --- | --- | --- |
| A/B 与影子流量 | 容易 | 困难（需要客户环境里的实验框架与统计能力） |
| 灰度发布 | 按租户/按比例 | 只能按环境/按机房 |
| 自动模型升级 | 无感 | 客户驱动的项目 |
| 计费精度 | 实时准确 | 本地计量 + 导出，存在延迟与偏差 |
| 车队学习（fleet learning） | 跨客户聚合 | **不可能**（这恰恰是客户要的隔离） |

```python
# 气隙部署 vs SaaS：升级税、发布节奏、MTTR 分解、容量与 HA 余量、诊断包脱敏
import math
from dataclasses import dataclass, field
from typing import Dict, List, Tuple

# ---------- 1) 升级税：单次发布成本与年度节奏 ----------
@dataclass
class ReleaseCost:
    name: str
    build_h: float            # 构建与测试
    sign_h: float             # 签名与制品校验
    sec_review_h: float       # 客户安全评审（离线 SBOM/CVE）
    staging_h: float          # 客户预演环境验证
    cab_h: float              # 变更委员会流程
    deploy_h: float           # 窗口内安装
    rollback_drill_h: float   # 回滚演练
    hourly: float = 120.0     # 内部人力成本（美元/小时）
    def total_h(self) -> float:
        return (self.build_h + self.sign_h + self.sec_review_h + self.staging_h
                + self.cab_h + self.deploy_h + self.rollback_drill_h)
    def cost(self) -> float:
        return self.total_h() * self.hourly
SAAS = ReleaseCost("SaaS（持续部署）", 4, 0, 0, 0, 0, 0.5, 0)
AIR = ReleaseCost("气隙（单客户单站点）", 16, 4, 20, 24, 12, 8, 8)
print("① 升级税：单次发布的固定成本（含客户侧流程）")
print(f"  {'形态':<24} {'人力小时':>9} {'单次成本($)':>12} {'年次数':>7} {'年成本($)':>12}")
for r, per_year in ((SAAS, 52), (AIR, 4)):
    print(f"  {r.name:<24} {r.total_h():>9.1f} {r.cost():>12,.0f} {per_year:>7} "
          f"{r.cost() * per_year:>12,.0f}")
print(f"  节奏差距：{SAAS.total_h():.1f} 小时 vs {AIR.total_h():.1f} 小时 -> "
      f"发布频率从每年 52 次降到 4 次（**13 倍**）")
print("  读法：**固定成本与改动大小无关**，所以气隙下「攒一批再发」是理性选择 —— 但单次改动变大，")
print("        风险上升，于是需要更多测试（正反馈）。破局：**给安全补丁单独的加急通道并预先演练**")

# ---------- 2) 未修复缺陷的累积（发布节奏的后果） ----------
@dataclass
class DefectAccum:
    arrival_per_month: float = 6.0     # 每月新发现的缺陷数
    fix_lag_months_saas: float = 0.25  # SaaS：约一周进生产
    fix_lag_months_air: float = 3.0    # 气隙：一个季度
    severity_weight: float = 1.0
    def steady_state_open(self, lag_months: float) -> float:
        """稳定状态下"已修复但未上线"与"未修复"的暴露量（近似：到达率 × 时延）"""
        return self.arrival_per_month * lag_months * self.severity_weight
d = DefectAccum()
print("")
print("② 发布节奏的直接后果：缺陷暴露窗口")
print(f"  {'形态':<12} {'修复上线时延':>12} {'稳定暴露量（缺陷数）':>20}")
for name, lag in (("SaaS", d.fix_lag_months_saas), ("气隙", d.fix_lag_months_air)):
    print(f"  {name:<12} {lag:>11.2f} 月 {d.steady_state_open(lag):>20.1f}")
print(f"  气隙暴露量是 SaaS 的 {d.steady_state_open(d.fix_lag_months_air)/d.steady_state_open(d.fix_lag_months_saas):.1f} 倍")
print("  读法：**同样的缺陷到达率，气隙下「已知但未上线」的缺陷会累积 10 倍以上** —— 这就是为什么")
print("        气隙合作必须谈**加急通道**（安全/严重缺陷不走季度节奏），并把演练做在前面")

# ---------- 3) MTTR 分解 ----------
@dataclass
class MTTR:
    name: str
    detect: float
    report: float
    reproduce: float
    fix: float
    bundle: float
    cab: float
    deploy: float
    def total(self) -> float:
        return self.detect + self.report + self.reproduce + self.fix + self.bundle + self.cab + self.deploy
S = MTTR("SaaS", 0.5, 0.5, 1.0, 6.0, 0.0, 0.0, 0.25)
A = MTTR("气隙", 2.0, 6.0, 16.0, 6.0, 8.0, 72.0, 12.0)   # CAB 以小时计：3 天窗口
print("")
print("③ MTTR 分解（小时；气隙下 CAB 与部署窗口是主项）")
print(f"  {'环节':<12} {'SaaS':>8} {'气隙':>8}")
for label, sv, av in (("检测", S.detect, A.detect), ("上报", S.report, A.report),
                      ("复现", S.reproduce, A.reproduce), ("修复", S.fix, A.fix),
                      ("打包签名", S.bundle, A.bundle), ("客户审批(CAB)", S.cab, A.cab),
                      ("窗口部署", S.deploy, A.deploy)):
    print(f"  {label:<12} {sv:>8.1f} {av:>8.1f}")
print(f"  {'合计':<12} {S.total():>8.1f} {A.total():>8.1f}  -> 放大 {A.total()/S.total():.1f} 倍")
tail_s = S.bundle + S.cab + S.deploy
tail_a = A.bundle + A.cab + A.deploy
print(f"  链条尾部（打包+审批+部署）占比：SaaS {tail_s/S.total():.0%}，气隙 {tail_a/A.total():.0%}")
print("  读法：**气隙下「流程尾部」占了大头** —— 所以优化重点不是「修得更快」，而是①加急通道、")
print("        ②客户自助诊断（压缩复现时间）、③可合成复现（你没有客户数据）")

# ---------- 4) 容量与 HA：客户自己买卡时的余量 ----------
@dataclass
class Sizing:
    weights_gb: float = 186.0        # MoE 100B/10B bf16（串 cohere-02）
    kv_gb: float = 120.0             # 目标并发与上下文下的 KV（示例）
    workspace_gb: float = 40.0       # 激活/通信缓冲/框架
    gpu_gb: float = 80.0
    usable: float = 0.9              # 可用比例
    ha_extra: float = 0.25           # N+1
    peak_extra: float = 0.5          # 峰值余量
    def min_gpus(self) -> float:
        per_gpu = self.gpu_gb * self.usable
        base = math.ceil((self.weights_gb + self.kv_gb + self.workspace_gb) / per_gpu)
        return base * (1 + self.ha_extra) * (1 + self.peak_extra)
s = Sizing()
base = math.ceil((s.weights_gb + s.kv_gb + s.workspace_gb) / (s.gpu_gb * s.usable))
print("")
print("④ 气隙客户的容量规划（权重 186 GB + KV 120 GB + 工作区 40 GB、80 GB 卡）")
print(f"  最小可服务卡数（无余量）：{base} 张")
print(f"  加 N+1 冗余（+25%）与峰值余量（+50%）后：**{s.min_gpus():.0f} 张**"
      f"（相当于多买 {s.min_gpus()-base:.0f} 张）")
print(f"  若把峰值余量降到 +20%：{base * 1.25 * 1.2:.0f} 张；若 KV 翻倍（长上下文/高并发）：")
s2 = Sizing(kv_gb=240.0)
print(f"    {math.ceil((s2.weights_gb + s2.kv_gb + s2.workspace_gb) / (s2.gpu_gb * s2.usable))} 张（无余量）"
      f" -> 含余量 {s2.min_gpus():.0f} 张")
print("  读法：**「能装下权重」不等于「能服务」** —— KV 与余量往往决定最终采购量；客户自建时")
print("        你必须提供这套算术与压测方法（否则要么买少、要么过度配置）")

# ---------- 5) 诊断包：脱敏规则与可审阅性 ----------
@dataclass
class DiagPack:
    layer: str
    contains_pii: bool
    redaction: str
    can_auto_share: bool
PACK = [
    DiagPack("指标（延迟/吞吐/错误率/显存）", False, "无需脱敏", True),
    DiagPack("配置与版本（含许可状态）", False, "无需脱敏", True),
    DiagPack("结构化日志（错误码+时间线）", False, "去参数化，仅保留错误码", True),
    DiagPack("检索命中（文档 id 与分数，无正文）", False, "只导出 id/元数据", True),
    DiagPack("原始请求/响应文本", True, "正则+NER 脱敏 + 哈希替换", False),
    DiagPack("向量与索引片段", False, "不含原文时可直接导出", True),
]
print("")
print("⑤ 诊断包设计：哪些能自动共享、哪些必须客户先审阅")
print(f"  {'层':<38} {'含 PII':>7} {'脱敏':<28} {'可自动共享':>9}")
for p in PACK:
    print(f"  {p.layer[:36]:<38} {('是' if p.contains_pii else '否'):>7} {p.redaction[:26]:<28} "
          f"{('是' if p.can_auto_share else '否（需审阅）'):>9}")
print("  读法：**把诊断包做成「客户一键生成并自行审阅后再交付」** —— 这是气隙环境下唯一可持续的排障路径；")
print("        含 PII 的层默认不外传，改用合成复现（客户在域内跑你的脚本）")
```

预期输出要点（实跑）：① **升级税**让发布频率从每年约 52 次塌到 4 次（13 倍），原因是固定成本与改动大小无关；② 因此**「已知但未上线」的缺陷暴露量在气隙下累积到 SaaS 的十余倍**——必须谈加急通道；③ **MTTR 分解**显示气隙下「打包 + CAB + 窗口部署」这条**流程尾部占到总时长的大多数**（而 SaaS 只有几个百分点），所以优化重点是流程而不是修复速度；④ 容量算例说明**「装下权重」远不等于「能服务」**：加 N+1 与峰值余量后采购量显著上升，KV 翻倍还会再上一层；⑤ 诊断包按层给出「是否含 PII、如何脱敏、能否自动共享」，把**客户先审阅**作为默认路径。

## 常见追问

- **追问**：客户要求「绝不出网」，那怎么做许可与计量？
  - 要点：**离线签名许可文件**（含有效期、节点数/GPU 数、功能开关），到期需**新的许可文件**（可通过介质更新）；用量在**本地计量**（token 数、调用数、并发峰值），以**加密签名的用量报告**形式定期导出（或经数据二极管单向传出）。**关键是把它设计成「客户能自己验证、你也能核账」的双向可信格式。**
- **追问**：你怎么在看不到客户数据的情况下排障？
  - 要点：三层——① **自检与决策树**（客户运维按脚本定位）；② **可审阅诊断包**（指标/配置/错误码/命中 id，不含正文）；③ **合成复现**（用合成语料与客户的最小复现脚本在本地重现）。**同时准备好「远程之手」协议**：指定操作员、共享屏幕、按 runbook 执行。
- **追问**：为什么不干脆做成「客户云上的 BYOC」，既能隔离又能升级？
  - 要点：**能否出网**是关键分界。BYOC 下你的控制面可以出网（能遥测、能推更新），隔离度靠 IAM/网络策略；**气隙是「物理无连接」**，常见于金融/国防/医疗的特定场景。**若客户只是要数据驻留，BYOC 往往更划算**——先问清「到底要隔离什么」（数据出域？还是连远程管理都不允许？）。
- **追问**：气隙下还有必要做 A/B 吗？
  - 要点：能做但要改造——① **按机房/按用户组**切分（而非按比例随机）；② 依赖客户环境的实验框架与统计能力；③ 更现实的是**离线对照 + 小范围试点**（串 [[databricks-09]] 的 shadow/canary 思路）。**别承诺 SaaS 式的在线实验能力。**
- **追问**：升级这么大的成本，怎么减少改动量？
  - 要点：① **模块化解耦**（索引/提示/工具配置可独立更新，不必整包升级）；② **把配置与模型分离**（策略改动走配置通道，不重发权重）；③ **分级发布**（安全补丁加急、功能季度）；④ **把评测与回滚做成客户可自助**（降低每次发布的验证成本）。
- **追问**：客户买卡买错了（显存不够/互联差）怎么办？
  - 要点：**售前就要给硬性约束与压测方法**（显存算术 + 并发压测 + 互联要求，串 [[cohere-02]]）。若已买错：① 降级方案（更小的模型/更短的上下文/更低的并发）；② 量化（代价是质量，要重评测）；③ 混合（把部分负载放回客户的其他集群）。**这是「责任转移」后最容易出纠纷的地方，必须书面确认选型建议。**
- **追问**：支持 SLA 怎么写才实际？
  - 要点：区分**响应时间**与**修复/绕过时间**，并显式列出**客户侧责任**（提供诊断包、执行 runbook、提供变更窗口）。加急通道要有**预授权协议**（避免每次走完整 CAB）。**承诺「4 小时响应」而不是「4 小时修复」**，并写清升级路径依赖客户配合。
