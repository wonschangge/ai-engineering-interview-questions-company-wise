## 一句话答案

> **核心手段：前缀缓存（prefix caching）——把已算过的前缀 KV 留下来复用，只预填充新增的 token。**
> **为什么收益巨大（可算）**：朴素实现每轮都重发全部历史，所以 $K$ 轮对话的总预填充量是
> $$\text{朴素}=\sum_{i=1}^{K}iT=\frac{TK(K+1)}{2}=O(K^2)\quad\text{vs}\quad\text{缓存}=KT=O(K)$$
> **本机算例**（每轮新增 $T=800$ token）：**20 轮对话朴素要 168,000 token 的预填充，缓存后只需 16,000——10.5×**；50 轮时是 **25.5×**。**轮数越多收益越大**（这正是长对话的痛点）。
> **坑（按踩到的概率排序）**：
> | # | 坑 | 后果 | 对策 |
> | --- | --- | --- | --- |
> | ① | **易变字段插在历史前面**（时间戳、用户 ID、动态 system prompt） | **该位置之后全部失效**——放最前面等于**完全没缓存**（本机：20 轮仍是 168,000 token，0% 复用） | **稳定内容放前面、易变内容放后面**；本机算例：放到最后面可得 **10.5×**，放中间只剩 1.83× |
> | ② | **RoPE 的绝对位置**：缓存里的 KV 带着位置信息 | **只能在尾部追加，不能在前面插入**——插入会让所有位置偏移、缓存全废 | 检索结果/工具输出**放在历史之后**；或预留位置区间 |
> | ③ | **前缀必须逐 token 完全一致** | 一个空格、一次模板改版、分词器版本变化都会导致**从该点起全部 miss** | 固定模板、版本化 system prompt、**缓存 key 里带上模板版本** |
> | ④ | **缓存池的容量**：并发 × 长度线性增长 | 本机算例：1000 个 32K 会话的 KV 是 **1151 GB** | **分层**（HBM/DRAM/SSD）+ **前缀树淘汰**（先淘汰叶子） |
> | ⑤ | **跨用户复用导致数据泄漏** | 若前缀里含**每请求私有状态**，复用会把 A 的上下文暴露给 B | **缓存 key 必须包含租户/权限维度**；私有内容不进可共享前缀 |
> | ⑥ | **缓存感知的路由造成热点** | 要命中缓存就得把请求路由到持有它的 worker → 某些 worker 过载 | 前缀树 + 负载感知路由（串 [[moonshot-05]] 的 KV-centric 调度） |
> | ⑦ | **只缓存 KV 而忘了 logits/采样状态** | 若把「上一轮的 logits」也缓存，位置变化后**不再有效** | **只缓存 KV**（logits 与位置强相关） |
> **收益量化（本机算例）**：每 1000 次 20 轮对话，朴素预填充 **56,000 GPU·s（≈16 GPU·h ≈ \$31）** → 缓存后 **5,333 GPU·s（≈\$3）**，**省 90%**。
> 一句话判据：**"前缀缓存是几乎纯收益的优化（无近似），但它把'重算'的问题换成了'前缀稳定性 + 缓存池管理'的问题"**——**收益取决于前缀有多稳定，成本取决于缓存池管得多好。**

## 面试官在考什么

- **能否给出 $O(K^2)\to O(K)$ 的量化**：本机算例 20 轮 10.5×、50 轮 25.5×——**能把「为什么长对话最痛」算出来**。
- **是否知道前缀稳定性的第一纪律**：**稳定内容在前、易变内容在后**（本机：放最前面 = 0% 复用）。
- **RoPE 位置这个坑**：能否指出**缓存只能在尾部追加**，插入会让位置偏移（这是最容易被忽略的结构性限制，串 [[moonshot-04]] 的位置编码知识）。
- **逐 token 一致性**：能否指出模板/分词器/空格都会破坏命中，以及**缓存 key 要带版本**。
- **缓存池的容量与淘汰**：能否算出容量（1000 个 32K 会话 = 1151 GB）并给出**分层 + 前缀树淘汰**的方案。
- **安全坑**：能否主动提到**跨用户复用的数据泄漏风险**（这是很多团队上线后才发现的）。
- **与 PD 分离的关系**：缓存放在哪一侧（解码池 / KV 池 / 远端），以及**缓存感知路由**带来的负载不均（串 [[moonshot-05]]）。
- **正确性**：能否指出「前缀缓存**没有近似**」（与量化、稀疏注意力不同）——所以它应当是**默认开启**的。
- **诚实**：承认收益依赖工作负载（**短对话、前缀频繁变化时收益很小**），且缓存池本身要占显存。

**常见错误答案**

- 只说「用前缀缓存」（不给 $O(K^2)\to O(K)$ 的量化与命中条件）。
- 把易变内容（时间戳、检索结果）放在 system prompt 里（**等于关掉了缓存**）。
- 忽略 RoPE 位置约束（以为「任意位置都能复用」）。
- 认为「前缀相同就行」（忽略逐 token 一致性、模板版本、分词器版本）。
- 不提缓存池容量与淘汰（**以为缓存是免费的**）。
- 忽略跨用户复用的安全问题。
- 把前缀缓存与「KV 量化/稀疏注意力」混为一谈（**前者无近似，后者有**）。
- 不提缓存感知路由的负载不均问题。

## 原理与推导

### 1. 为什么是 $O(K^2)$：朴素实现的代价

第 $i$ 轮要处理 $iT$ 个 token（历史 + 新增），所以 $K$ 轮总计：

$$\text{朴素}=\sum_{i=1}^{K}iT=\frac{TK(K+1)}{2}\approx\frac{TK^2}{2}$$

**前缀缓存**下每个 token 只预填充一次：

$$\text{缓存}=KT$$

$$\text{加速}\approx\frac{K+1}{2}$$

**本机算例**（$T=800$）：

| 轮数 $K$ | 朴素 token | 缓存 token | 加速 | 朴素 KV 峰值 |
| --- | --- | --- | --- | --- |
| 5 | 12,000 | 4,000 | 3.0× | 422 MB |
| 10 | 44,000 | 8,000 | 5.5× | 1546 MB |
| **20** | **168,000** | **16,000** | **10.5×** | 5903 MB |
| 50 | 1,020,000 | 40,000 | **25.5×** | 35,839 MB |

**读法**：**加速比随轮数线性增长**——所以「长对话」是前缀缓存最大的受益者；而**朴素实现的 KV 峰值也随 $K^2$ 增长**（若每轮都重算并保留），这是显存侧的同一问题。

### 2. 坑①：前缀稳定性决定一切

设易变字段位于历史的 $p$ 比例处（$p=0$ 最前、$p=1$ 最后），则第 $i$ 轮可复用的是 $p\cdot(i-1)T$：

$$\text{总预填充}(p)=\sum_{i=1}^{K}\big[(1-p)(i-1)T+T\big]$$

**本机算例**（$K=20$、$T=800$）：

| 易变字段位置 | 可复用比例 | 总预填充 token | 相对朴素 | 相对最优 |
| --- | --- | --- | --- | --- |
| **最前面** | 0% | 168,000 | 1.00×（**等于没缓存**） | 10.50× |
| 前 1/4 | 25% | 130,000 | 1.29× | 8.12× |
| 中间 | 50% | 92,000 | 1.83× | 5.75× |
| 后 1/4 | 75% | 54,000 | 3.11× | 3.38× |
| **最后面** | 100% | **16,000** | **10.50×** | 1.00× |

**读法**：**「把易变内容往后放」是第一条工程纪律**——一个放在 system prompt 里的时间戳，就能让整个缓存失效。**实践做法**：稳定内容（system prompt、工具定义、少样本示例）在前，易变内容（时间戳、用户 ID、检索结果、工具输出）在后。

### 3. 坑②：RoPE 的绝对位置——只能追加，不能插入

缓存的 KV 是**在特定绝对位置**上算出来的（RoPE 把位置编进了 $k$）。若在缓存块**前面**插入 token，则缓存块的所有位置都要 $+n$——**KV 全部作废**。

**推论**：
- **只能在尾部追加**（追加不改变已有位置）；
- **检索结果必须放在历史之后**（否则每轮都会让历史的位置偏移）；
- 若确实需要「动态前缀」，要么**预留位置区间**，要么**接受失效**。

**读法**：这是**结构性的限制**，不是实现细节——它直接决定了 prompt 的编排方式（**这也是为什么「把 RAG 内容放最后」既是缓存友好、也是工程上更简单的做法**）。

### 4. 坑③：逐 token 完全一致

缓存命中要求**逐 token 完全相同**。破坏因素：

| 因素 | 例子 |
| --- | --- |
| 空白/换行差异 | 模板里多一个 `\n` |
| **模板版本变化** | system prompt 改了一句话 |
| **分词器版本变化** | 升级模型/分词器后同一文本的 token 不同 |
| 动态字段 | 时间戳、请求 ID、随机少样本选择 |
| 工具输出 | 每次调用结果不同（**应放在历史之后**） |

**对策**：① 固定模板并**版本化**；② **缓存 key 里带上模板/分词器版本**；③ 把动态字段**移到尾部**；④ 上线前做**命中率监控**（见第 6 节）。

### 5. 坑④：缓存池的容量与淘汰

**容量需求**（本机算例，MLA FP8）：

| 并发会话 | 平均 8K | 平均 32K | 平均 128K |
| --- | --- | --- | --- |
| 100 | 28.8 GB | 115.1 GB | 460.5 GB |
| **1000** | 287.8 GB | **1151.3 GB** | 4605.3 GB |
| 10000 | 2878 GB | 11513 GB | 46054 GB |

**读法**：**缓存池的容量随「并发 × 长度」线性上升**——所以**不可能全部常驻 HBM**。真实系统必须：

| 层 | 存什么 | 权衡 |
| --- | --- | --- |
| HBM | 活跃会话的 KV | 最快、最贵 |
| DRAM | 暂存/排队 | 中等（**Mooncake 的核心层**） |
| SSD/远端 | 冷前缀、可共享前缀 | 便宜、慢，**用于跨请求复用** |

**淘汰策略**：把缓存组织成**前缀树（radix tree / prefix trie）**——共享前缀只存一份，淘汰时**优先淘汰叶子**（因为它们被复用的概率最低）。**这比「按会话 LRU」更高效**，因为多个会话可能共享同一段前缀（如相同的 system prompt）。

### 6. 坑⑤⑥⑦：安全、路由与「只缓存 KV」

**⑤ 跨用户泄漏**：若可共享前缀里**含有每请求私有状态**（用户信息、权限过滤后的检索结果），复用会把 A 的内容暴露给 B。**对策**：① **缓存 key 包含租户/权限维度**；② **私有内容绝不进可共享前缀**（放到尾部）；③ 审计「哪些内容会进共享前缀」。

**⑥ 缓存感知路由的负载不均**：要命中缓存，请求必须路由到**持有该前缀 KV 的 worker**。热门前缀（如默认 system prompt）会让某些 worker 过载。**对策**：① **前缀树 + 负载感知路由**；② 热门前缀**多副本**；③ 接受一定比例的 miss 来换负载均衡（**命中率与均衡是一对权衡**）。

**⑦ 只缓存 KV，别缓存 logits**：logits 与**绝对位置**强相关，位置一变就无效。**缓存的内容应当是「与位置无关地可复用」的部分**——即 KV（在追加语义下）。

### 7. 收益量化与监控

**本机算例**（每 1000 次 20 轮对话）：

| 方案 | 预填充 GPU·s | 折算 | 成本 |
| --- | --- | --- | --- |
| 朴素 | 56,000 | 16 GPU·h | ≈ \$31 |
| **前缀缓存** | **5,333** | **1 GPU·h** | **≈ \$3** |

**节省 90%**——而且**没有近似**（正确性不受影响），所以它应当是**默认开启**的。

**必须监控的指标**：

| 指标 | 含义 | 异常信号 |
| --- | --- | --- |
| **前缀命中率** | 复用 token / 总 token | 突然下降 → 模板/动态字段被改坏 |
| **平均复用长度** | 命中的前缀有多长 | 变短 → 易变内容前移了 |
| **缓存池命中/淘汰比** | 淘汰是否过快 | 淘汰率高 → 容量不足 |
| **TTFT 分布** | 用户可见延迟 | 命中率下降会直接抬高 TTFT |

### 可运行代码

```python
# 前缀缓存：O(K^2)->O(K) 的收益、易变字段位置的影响、缓存池容量与成本
import math
from dataclasses import dataclass
from typing import Dict, List, Tuple

GB = 1e9
KV_PER_TOKEN = 576 * 61 * 1        # MLA、61 层、FP8：每 token KV 字节
T_TURN = 800                       # 每轮新增 token（示例）
PF_TPS = 3000.0                    # 每卡预填充吞吐（tokens/s，示例）
USD_PER_GPU_HOUR = 2.0

def naive_tokens(K: int, T: int = T_TURN) -> int:
    """朴素：第 i 轮处理 i·T 个 token"""
    return T * K * (K + 1) // 2

def cached_tokens(K: int, T: int = T_TURN) -> int:
    """前缀缓存：每个 token 只预填充一次"""
    return T * K

print("① 朴素重算 vs 前缀缓存：总预填充量")
print(f"  {'轮数 K':>6} {'朴素(ΣiT)':>12} {'缓存(KT)':>10} {'加速':>7} {'朴素 KV 峰值':>13}")
for K in (5, 10, 20, 50):
    n, c = naive_tokens(K), cached_tokens(K)
    print(f"  {K:>6} {n:>12,} {c:>10,} {n/c:>6.1f}x {n*KV_PER_TOKEN/1e6:>11.0f}MB")
print("  读法：**总预填充量是 O(K^2)，缓存后 O(K)，加速约 (K+1)/2** —— 20 轮 10.5x、50 轮 25.5x；")
print("        轮数越多收益越大，这正是长对话的痛点")

print("")
print("② 坑①：易变字段的位置决定命中率（20 轮对话）")
def total_prefill(p: float, K: int = 20, T: int = T_TURN) -> float:
    """易变字段位于历史的 p 比例处：之前可复用、之后（含）每轮都要重算"""
    tot = 0.0
    for i in range(1, K + 1):
        hist = (i - 1) * T
        tot += (hist - p * hist) + T
    return tot
best = total_prefill(1.0)
naive = total_prefill(0.0)
print(f"  {'易变字段位置':>12} {'可复用比例':>10} {'总预填充 token':>15} {'相对朴素':>9} {'相对最优':>9}")
for p, label in ((0.0, "最前面"), (0.25, "前 1/4"), (0.5, "中间"), (0.75, "后 1/4"), (1.0, "最后面")):
    t = total_prefill(p)
    print(f"  {label:>12} {p:>10.0%} {t:>15,.0f} {naive/t:>8.2f}x {t/best:>8.2f}x")
print(f"  朴素 {naive:,.0f} | 全缓存 {best:,.0f} | 最优加速 {naive/best:.1f}x")
print("  读法：**易变字段放最前面 = 等于没缓存（0% 复用）**；放最后面才有 10.5x ——")
print("        所以纪律是：稳定内容（system prompt/工具定义）在前，易变内容（时间戳/检索结果）在后")

print("")
print("③ 坑④：缓存池容量（并发 × 长度 × KV/token）")
print(f"  {'并发会话':>8} {'平均 8K':>10} {'平均 32K':>11} {'平均 128K':>12}")
for C in (100, 1000, 10000):
    print(f"  {C:>8} {C*8192*KV_PER_TOKEN/GB:>8.1f}G {C*32768*KV_PER_TOKEN/GB:>9.1f}G "
          f"{C*131072*KV_PER_TOKEN/GB:>10.1f}G")
print("  读法：**容量随「并发 × 长度」线性上升**（1000 个 32K 会话 = 1151 GB）——")
print("        所以必须分层（HBM/DRAM/SSD）+ 前缀树淘汰（先淘汰叶子）")

print("")
print("④ 成本收益（每 1000 次对话、20 轮）")
gpu_s_naive = naive_tokens(20) * 1000 / PF_TPS
gpu_s_cached = cached_tokens(20) * 1000 / PF_TPS
for label, g in (("朴素", gpu_s_naive), ("前缀缓存", gpu_s_cached)):
    print(f"  {label:<10} {g:>10,.0f} GPU·s ≈ {g/3600:>5.1f} GPU·h ≈ ${g/3600*USD_PER_GPU_HOUR:>6.0f}")
```

## 常见追问

- **追问**：前缀缓存有近似吗？会影响质量吗？
  - 要点：**没有近似**。在**全注意力 + 尾部追加**的语义下，前缀的 KV **与重新计算的结果完全一致**（数学上等价）。这与 **KV 量化、稀疏注意力、滑窗注意力**不同——后者有近似、要评质量。**所以前缀缓存应当是默认开启的**。**唯一的例外**：若用了**滑窗/稀疏注意力**，只有窗口内的部分真正影响输出，复用规则要相应调整（**可以复用更多，但要保证窗口语义正确**）。
- **追问**：多轮对话里 RAG 的检索结果该放在哪？
  - 要点：**放在历史之后（靠近当前问题）**。理由有两条：① **缓存友好**——放前面会让历史的位置偏移，缓存全废（本机：放最前面 = 0% 复用）；② **质量更好**——检索内容靠近问题通常效果更好（也符合 lost-in-the-middle 的结论，串 [[moonshot-01]]）。**唯一例外**：如果检索结果**跨轮稳定**（同一份文档反复用），可以把它放到**稳定前缀区**里复用。
- **追问**：缓存池该多大？怎么淘汰？
  - 要点：**容量按「并发 × 平均长度 × KV/token」估**（本机：1000 个 32K 会话 = 1151 GB），**不可能全放 HBM**。方案：① **分层**（HBM 放活跃、DRAM 放暂存、SSD 放冷前缀）；② **前缀树组织**（共享前缀只存一份）；③ **淘汰优先级**：先淘汰**叶子**（复用概率最低）、再按 LRU/频率；④ **预留比例**（例如 HBM 的 20%–30% 给缓存，其余给活跃请求）。**注意缓存与活跃请求争显存**——命中率提升的收益要能覆盖这部分显存的机会成本。
- **追问**：怎么衡量前缀缓存有没有效果？
  - 要点：**四个指标**：① **前缀命中率**（复用 token / 总 token）——最直接；② **平均复用长度**（易变内容是否前移）；③ **TTFT 的 p50/p99**（用户可见收益）；④ **单位 token 成本**（GPU·s / 1M tokens）。**注意区分「缓存命中」与「缓存有用」**：命中一段很短的公共前缀（如默认 system prompt）收益有限，**真正有价值的是长历史的复用**。
- **追问**：跨用户共享前缀安全吗？
  - 要点：**默认不安全**，除非**前缀里没有任何私有状态**。风险场景：① system prompt 里带了用户信息；② 检索结果按用户权限过滤后拼进前缀；③ 工具输出含敏感数据。**对策**：① **缓存 key 必须包含租户/权限维度**（不同权限的请求永不共享）；② **私有内容放到尾部**（不进可共享前缀）；③ **审计「哪些内容会进共享前缀」**；④ 对敏感场景**直接禁用跨用户共享**（只做同会话内的复用）。
- **追问**：前缀缓存与 PD 分离怎么配合？
  - 要点：**缓存放在哪一侧是个设计决策**：① **解码池持有**（KV 就在解码节点上，命中即用）；② **独立 KV 池**（Mooncake 式，跨节点共享，但要走网络）；③ **预填充侧也缓存**（避免重复预填充）。**权衡**：本地命中快但容量小、共享命中容量大但要传输。**另外缓存感知路由会造成负载不均**（热门前缀集中在少数 worker），所以需要**负载感知路由 + 热门前缀多副本**，并接受一定比例的 miss 来换均衡（串 [[moonshot-05]]）。
