## 一句话答案

> 换的不是优化算法，而是**奖励从哪来**：把「学出来的偏好打分器」换成**可程序化验证的确定性函数**（数学答案精确比对、代码跑单测、格式与约束用规则校验）。在数学与代码上它更受青睐有四个机制上的理由：① 奖励**精确**——0/1 由规则给出，不存在 RM 在分布外的误判；② 奖励**不可被优化器在代理上刷高**——没有「把分数刷上去但不满足真实意图」的通道；③ **不需要人类偏好标注**，题库与测试集本身就是数据，可规模化；④ 奖励**确定可复现**，同一答案永远同一分，便于调试与回归。
> 但稀疏 0/1 奖励本身不给梯度，得靠组内相对优势把它变成信号（GRPO）：$A_i=(r_i-\operatorname{mean}(r))/\operatorname{std}(r)$。代价同样明确：只覆盖可验证的任务，**验证器自己会成为新的被钻空子对象**，窄域优化还会带来能力偏移。

## 面试官在考什么

- **三个东西必须分清**：reward model（学出来的偏好打分器）、value model（PPO 的 critic）、verifier（人写的确定性判定函数）。把 RLVR 说成「GRPO 的另一种叫法」是最常见的降级答案——RLVR 描述奖励来源，GRPO 描述优势怎么估，两者正交（Tulu 3 的 RLVR 用 PPO 优化，同样成立）。
- 能否讲清「为什么 verifier 比 RM 难被 hack」的**机制**，而不是口号：RM 是一个可微代理，优化器可以沿着它的梯度走到训练分布之外；verifier 是规则，优化器只能通过**规则本身的漏洞**得分（例如测试用例过拟合、把答案抄进推理过程）。
- 能否说出奖励的**稀疏性怎么补救**：组内标准化（GRPO）、奖励塑形（格式分与正确性分拆开）、难度均衡采样（避免整组全对/全错）。
- 是否知道它的**边界**：可验证域之外（写作、共情、风格）用不了；窄域 RL 会让模型在别的域变差（串 [[finetuning-07]]）；题库与评测集必须去重否则是自己给自己出题（串 [[evaluation-06]]）。
- 能不能给出**配方顺序**而不是单点：SFT 冷启动 → RLVR 提能力 → 偏好数据修风格（Qwen3 与 Tulu 3 都是这个骨架的变体）。

**常见错误答案**

- 「RLVR 不需要 reward model，所以训练更简单」——它把复杂度从「训 RM」搬到了「写验证器 + 防作弊 + 造题」，总复杂度未必更低。
- 「有 verifier 就不会 reward hacking」——verifier 同样会被钻空子，只是攻击面从「分布外打分」变成「规则漏洞」。
- 「答案对就说明推理对」——答案对可能是蒙的；长链推理要额外看过程是否可复用、能否泛化到同类题。

## 原理与推导

### 1. 定义边界：三种「打分的东西」

| | 输入 | 输出 | 需要训练吗 | 能被优化器刷高吗 |
| --- | --- | --- | --- | --- |
| reward model（RLHF 用） | prompt + 回答 | 标量偏好分 | 需要（偏好数据训） | 能——沿代理的梯度走到分布外 |
| value model（PPO 用） | 前缀 | 期望回报估计 | 需要（在线拟合） | 不直接，但拟合误差污染优势估计 |
| verifier（RLVR 用） | prompt + 完整回答 | 常为 0/1 的规则判定 | 不需要，是人写的函数 | 只能通过规则漏洞 |

本题的比较对象是**第一行与第三行**：奖励来源的替换。优化器可以是 PPO（带 value model）也可以是 GRPO（去掉 value model），这与「奖励从哪来」是两件独立的事。

### 2. 目标函数同形，只换奖励项

RLVR 的目标与标准 KL 约束 RLHF 完全同形：

$$J(\theta)=\mathbb{E}_{x\sim D,\;y\sim\pi_\theta}\big[v(x,y)\big]-\beta\cdot \mathrm{KL}\!\big(\pi_\theta(\cdot\mid x)\,\big\|\,\pi_{\text{ref}}(\cdot\mid x)\big)$$

差别只在 $r_\phi(x,y)\to v(x,y)$：前者是学出来的连续分，后者是规则给出的离散判定。KL 项的作用不变——把策略约束在参考模型附近，防止为了拿分而崩语言质量。

### 3. 稀疏奖励怎么变成梯度：组内相对优势

纯 0/1 奖励下，序列级分数不给 token 级信用分配，所以主流做法是**同 prompt 采一组 $G$ 个回答**，用组内统计量做基线：

$$A_i=\frac{r_i-\operatorname{mean}(r_1,\dots,r_G)}{\operatorname{std}(r_1,\dots,r_G)},\qquad \mathcal{L}=-\frac{1}{G}\sum_i \min\!\Big(\rho_i A_i,\ \operatorname{clip}(\rho_i,1-\epsilon,1+\epsilon)A_i\Big)+\beta\,\mathrm{KL}$$

这一步有一个直接后果，必须自己算清楚：**当组内奖励全同（全对或全错）时 $\operatorname{std}=0$，整组优势为 0，这一批数据不产生任何梯度**。0/1 奖励下无效组的比例是

$$P_{\text{无效}}=p^{G}+(1-p)^{G}$$

$G=8$ 时：通过率 $p=0.05$ 有 **66.3%** 的组全错，$p=0.9$ 有 **43.1%** 的组全对。两端都是白烧算力——这就是为什么 RLVR 工程上必须做**难度均衡采样**（按实时通过率动态挑题，把 $p$ 维持在 0.2–0.8），而不是拿一个固定题库从头刷到尾。

### 4. 为什么在数学与代码上它明显更好

1. **奖励的量纲问题消失了**：RM 的分数是任意尺度的连续值，需要归一化、需要 KL 约束防漂移；verifier 的 0/1 天然有界，且组内标准化后与尺度无关。
2. **没有代理-目标错配的通道**：学出来的 RM 只能近似人类偏好，优化器会找到它在训练分布外的漏洞（串 [[finetuning-11]] 的 reward hacking 与过度优化曲线）；verifier 的「漏洞」是具体可枚举的工程缺陷，可以逐个堵。
3. **数据成本结构不同**：RM 要人写成对偏好（昂贵、慢、标注者之间不一致）；verifier 要题库与测试（可自动生成、可复用、可版本化）。数学题有唯一答案、代码有执行结果，这两类任务的验证是**免费的监督信号**。
4. **可复现**：同一个答案今天和明天得分一样，回归测试与 A/B 才有意义；RM 分数会随模型、版本、采样漂移。
5. **奖励可以塑形而不失真**：把「格式合规」与「答案正确」拆成两项加权，比在 RM 里混进一堆偏好更可控。

### 5. 代价与新的攻击面

- **可验证域的边界**：写作、共情、风格、开放式事实性没有可靠 verifier，只能用 RM 或人工。所以 RLVR 是**补充**不是替代。
- **验证器被钻空子**（这一条是本题的区分点）：① 过拟合可见测试用例（只跑公开用例就通过）；② 格式对但内容错（格式分给太高）；③ 把答案抄进推理过程（prompt 里泄露了答案，模型学会复述）；④ 数值容差被利用（`1e-6` 容差下输出近似值）。
- **能力偏移**：只在数学上做 RL，模型在通用对话上会变得啰嗦、爱拒答、格式僵硬——窄域优化的常见副作用，靠混入通用数据与偏好数据修（串 [[finetuning-07]]）。
- **污染与自证**：训练题库里混进评测集，分数就是自欺；必须做去重与留出（串 [[evaluation-04]] 的红线集与 [[evaluation-06]]）。

### 6. 配方顺序（工程上怎么排）

SFT 冷启动（学会格式与基本推理）→ **RLVR**（在可验证域上把能力拉起来）→ 偏好数据（DPO/PPO 修风格与拒答边界）→ 通用 RL 兜底。Qwen3 的四段配方与 Tulu 3 的公开配方都是这个骨架的变体：能力先由可验证信号顶上去，风格再由偏好数据收口——顺序反了会互相打架。

## 数值与代码验证

### 表 1：无效组比例（GRPO，0/1 奖励）

| 单题通过率 $p$ | $G=4$ | $G=8$ | $G=16$ |
| --- | --- | --- | --- |
| 0.05 | 81.5% | **66.3%** | 44.1% |
| 0.30 | 25.0% | 5.8% | 0.3% |
| 0.50 | 12.5% | 0.8% | 0.0% |
| 0.90 | 65.6% | **43.1%** | 18.5% |

口径：$P=p^{G}+(1-p)^{G}$，只统计「全对或全错」的组。解读：$p$ 太难题会全错、太易题会全对，**两个方向都在烧钱**，所以要在 0.2–0.8 之间动态调难度。

### 表 2：奖励塑形的分值口径

| 项 | 分值 | 依据 |
| --- | --- | --- |
| 通过验证器（答案正确） | $+10$ | Tulu 3 的 RLVR 配方（$\alpha=10$） |
| 未以 EOS 结尾（生成不完整） | $-10$ | 同上，与「答案错」同量级，视不完整为同等失败 |
| 格式合规但答案错 | $0$ | 常见做法：格式分单独加权，不与正确性混在一起 |

### 表 3：一次 RLVR 的算力量级（仓库统一常数）

以「8B 学生、$G=8$、每题采 8 条、平均 6k token 轨迹、10 万道题、2 个 epoch」为例：

| 项 | 算式 | 结果 |
| --- | --- | --- |
| 采样 token 总量 | $10^5\times8\times6{,}000\times2$ | $9.6\times10^{9}$ token |
| 采样（仅前向） | $9.6\times10^{9}\times2\times8\times10^{9}$ | $1.54\times10^{20}$ FLOPs |
| 训练（前向+反向） | $9.6\times10^{9}\times6\times8\times10^{9}\times0.3_{\text{有效比例}}$ | $1.4\times10^{20}$ FLOPs |
| 合计（MFU 40%，989 TFLOPs） | $(1.54+1.4)\times10^{20}/(989\times10^{12}\times0.4\times3600)$ | ≈ **206 GPU·h** |

注意第三行的「有效比例 0.3」是本题最关键的工程系数：按表 1，只有一部分组能产生梯度；再叠上被丢掉的全错/全对组，实际有效算力占比通常远低于 100%。算 RLVR 预算时把这个系数写出来，比只报总 token 数可信得多。

### 可运行代码

```python
# 复算表 1 的无效组比例，以及一个最小 verifier 的行为
from fractions import Fraction

def dead_group_ratio(p, G):
    return p**G + (1 - p)**G

print("表 1：无效组比例 P = p^G + (1-p)^G")
print(f"{'p':>6} {'G=4':>9} {'G=8':>9} {'G=16':>9}")
for p in (0.05, 0.30, 0.50, 0.90):
    row = " ".join(f"{dead_group_ratio(p, G):>8.1%}" for G in (4, 8, 16))
    print(f"{p:>6.2f} {row}")

# 组内标准化：全同组的标准差为 0，优势必须显式判零，否则会得到 nan
def group_advantages(rewards, eps=1e-8):
    m = sum(rewards) / len(rewards)
    var = sum((r - m) ** 2 for r in rewards) / len(rewards)
    sd = var ** 0.5
    if sd < eps:
        return [0.0] * len(rewards), True          # 无效组：无梯度
    return [(r - m) / sd for r in rewards], False

for rewards in ([0]*8, [1]*8, [1,0,0,1,0,0,0,1]):
    adv, dead = group_advantages(rewards)
    print(f"rewards={rewards} -> 无效组={dead} 优势={[round(a,3) for a in adv]}")

# 最小 verifier：数学答案精确比对（含常见等价写法）
import re
def normalize(s):
    s = s.strip().lower().replace(" ", "")
    s = re.sub(r"\\left|\\right|\\,|\\!|\\$", "", s)
    s = s.replace("\\dfrac", "\\frac").replace("\\tfrac", "\\frac")
    return s

def math_verifier(pred, gold):
    return 1.0 if normalize(pred) == normalize(gold) else 0.0

cases = [("\\frac{1}{2}", "\\dfrac{1}{2}"), (" 42 ", "42"), ("0.5", "\\frac{1}{2}"), ("42", "43")]
for pred, gold in cases:
    print(f"pred={pred!r:>16} gold={gold!r:>16} -> reward={math_verifier(pred, gold)}")

# 单测型 verifier 的骨架（真跑代码要放沙箱；这里只演示判定口径）
def code_verifier(run_tests):        # run_tests() -> (passed, total)
    passed, total = run_tests()
    return 1.0 if total > 0 and passed == total else 0.0
print("code_verifier 全过 =", code_verifier(lambda: (5, 5)), " 部分过 =", code_verifier(lambda: (4, 5)))
```

预期输出要点：$p=0.05,G=8$ 打印 `66.3%`，$p=0.9,G=8$ 打印 `43.1%`；全 0 与全 1 的两组都被标为「无效组」且优势全为 0；`0.5` 与 `\frac{1}{2}` 被判为不等（**字符串归一化到不了语义等价**，这正是 verifier 需要专门工程的原因）；`code_verifier` 部分通过时给 0 分，对应「测试全过才算成功」的口径。

## 常见追问

- **追问**：RLVR 和 GRPO 是什么关系？
  - 要点：正交。RLVR 说的是奖励来源（确定性 verifier 替代 RM），GRPO 说的是优势估计（用组内统计量替代 value model）。可以 RLVR + PPO（Tulu 3 就是这么做的），也可以 RM + GRPO。
- **追问**：有 verifier 之后还需要 reward model 吗？
  - 要点：需要，但分工不同。verifier 管可验证域（对错），RM 管不可验证域（风格、有用性、拒答边界）。生产配方通常是两者同时在线、加权求和，并用 KL 约束防漂移。
- **追问**：怎么防止模型钻验证器的空子？
  - 要点：多重化验证（可见测试 + 隐藏测试 + 人工抽检）、把格式分与正确性分拆开并压低格式权重、检查推理链里是否出现答案复述、对测试用例做留出与轮换、并对奖励分布做监控（分数突然普遍变高就是信号）。
- **追问**：为什么一定要采一组而不是一条？
  - 要点：0/1 奖励下单条没有基线，方差极大；组内统计量提供了几乎无成本的基线（不用训 value model），代价是采样量放大 $G$ 倍，且全同组不出梯度。
- **追问**：RLVR 会把模型练「窄」吗？
  - 要点：会。只在数学/代码上做 RL 会让通用对话变差（啰嗦、爱拒答、格式僵硬）。缓解是混入通用数据与偏好数据，并在通用评测集上做回归门禁（串 [[evaluation-04]]）。
- **追问**：题库从哪来，怎么防止自己给自己出题？
  - 要点：竞赛题、教程题、合成题都可以，但**必须与评测集做去重与时间切分**，并保留一份从未进入训练的私有留出集。用训练题当评测集，分数只是记忆的度量（串 [[evaluation-06]]）。
