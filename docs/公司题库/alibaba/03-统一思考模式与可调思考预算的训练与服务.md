## 一句话答案

> 训练是四段串行：Long-CoT 冷启动 SFT 只装推理格式、样本与步数刻意做小；可验证奖励的 Reasoning RL（3,995 条 query-verifier 对 + GRPO）把推理能力推上去；思考模式融合 SFT 把 thinking 与 non-thinking 数据混进同一批；General RL 用三类奖励补通用能力。两种模式共用一组权重，机制是 chat template 里一段空的 thinking 块——`enable_thinking` 是硬开关（默认 True），`/think` 与 `/no_think` 是逐轮生效的软开关。
> 思考预算不是训练出来的 loss，而是推理期的手动中断：思考长度到达调用方阈值就插入收尾指令，模型基于已积累的推理直接作答；直接截断 token 会把答案一起切掉。服务侧要把它做成准入与配额把手——模式与预算做成请求级字段、思考与非思考分池各自定 SLO、用 goodput 验收、给思考池设硬上界。

## 面试官在考什么

- 能不能把四段配方讲成**串行依赖**而不是四个并列技巧：每段的监督信号从哪来、数据怎么造、为什么不能换序、为什么 Stage 1 必须做小。
- 会不会算「预算即显存」：KV 单价 $k=2LH_{kv}d_{\text{head}}\cdot\text{bytes}$、并发上限 $b_{\max}\approx M_{KV}/(kS)$、$E2E\approx TTFT+TPOT\times(O-1)$，以及由这三个式子推出的「思考模式下优化 TTFT 没有意义」。
- 是否理解统一两种模式是**模板机制**而不是第二套权重，并且知道代价：两种输出分布互相干扰，要给出实测 delta，不能只说融合更好。
- 能不能把思考预算讲成工程约束（硬上界、给答案留空间、撞窗口后压预算或开 YaRN），而不是「让模型想短一点」这种愿望。
- 服务侧是否落到 SLO 与队列：请求级字段、分池、goodput、预算命中率、预算耗尽作为降级路径。

**常见错误答案**

- 「预算到了就把 token 截断」——截断会把答案一起切掉，只剩半句话；正确做法是插入收尾指令让模型基于已有推理作答。
- 「预算可控是训练出来的能力，要额外加一个 budget loss」／「`enable_thinking=False` 时还能用 `/no_think` 控制」／「两种模式混在一个池子里最省」。三句都是把机制与策略混为一谈。

## 原理与推导

### 1. 四段串行配方：每段的监督信号不同

**Stage 1：Long-CoT 冷启动 SFT。** 题目覆盖数学、代码、逻辑推理与通用 STEM，每题必须配可验证答案或测试用例——没有 verifier 的题进不了这条流水线。数据要过两道过滤：

- **query 过滤**：用 Qwen2.5-72B-Instruct 剔除不易验证的多子问题题与开放写作题，并剔除不用 CoT 就能答对的题。后者常被忽略：把「直接猜也能对」的题留在训练集里，等于教模型跳过推理。
- **response 过滤**：用 QwQ-32B 对每题采样 $N$ 条，按六条准则剔除——最终答案错、大量重复、无推理的直猜、thinking 与 summary 不一致、语种与风格混杂、疑似与验证集相似；只保留 Pass@N 为正的轨迹。

这一步的目标只是把推理格式与习惯装进模型，所以样本数与训练步数刻意小，提升空间留给 Stage 2。冷启动做太大反而会锁死探索空间，让后续 RL 学不动。

**Stage 2：Reasoning RL。** 用 3,995 条 query-verifier 对做可验证奖励的 RL，算法是 GRPO：对同一 prompt 采样一组回答，用组内均值与标准差把奖励标准化成优势

$$A_i=\frac{r_i-\operatorname{mean}(\{r_1,\dots,r_G\})}{\operatorname{std}(\{r_1,\dots,r_G\})}$$

组内相对优势不需要 value network，省掉与策略同规模的 critic（细节与显存账见 [[finetuning-03]]）。工程上靠大 batch、每题多 rollout、允许 off-policy 来提高样本效率。可复算的量级：Qwen3-235B-A22B 的 AIME'24 在 170 个 RL step 内从 70.1 升到 85.1。RL 能在可验证域上独立激励推理，最强证据是 DeepSeek-R1-Zero 连 SFT 冷启动都没有、纯 RL 就涌现出自我反思与验证行为（延伸来源）。

**Stage 3：思考模式融合。** 在 Stage 2 的模型上继续 SFT，把 thinking 与 non-thinking 数据混进同一批。两类数据的来源不同：

- thinking 数据由 Stage 2 模型对 Stage 1 的 query 做拒绝采样生成——用自己产出的高质量轨迹，保证思考能力不回退。
- non-thinking 数据覆盖代码、数学、指令跟随、多语、写作、问答、角色扮演，用自动 checklist 打分，并提高低资源语言翻译的配比。

**Stage 4：General RL。** 20+ 任务、三类奖励：规则奖励（指令跟随、格式）、带参考答案的模型奖励（裁判是 Qwen2.5-72B-Instruct）、无参考答案的偏好奖励模型。其中格式奖励明确要求模型遵守 `/think` 与 `/no_think`，并用指定 token 分隔思考与回答——这一步才是把软开关变成可依赖接口的地方。

### 2. 统一两种模式的机制：模式是模板里的一段文本

`enable_thinking` 是硬开关，默认 True，由 chat template 拼一段空的 thinking 块来决定模型是否产出思考内容；`/think` 与 `/no_think` 是软开关，逐轮生效，多轮对话里以最后遇到的那个 flag 为准（训练数据会在多轮里随机插入多个 flag，专门练这个行为）。API 兼容细节必须点出：

- `enable_thinking=True` 时即使写了 `/no_think`，模型仍会输出 think 块，内容可以为空；
- `enable_thinking=False` 时软开关完全失效。

**为什么值得统一。** 省掉一份权重和一次部署：显存、版本对齐、运维各少一份。更关键的是 Qwen3 的观察——两种模式都熟练的模型在不同思考预算下表现稳定，这是预算可控的前提。**代价**是两种输出分布互相干扰，所以必须报实测 delta 而不是只讲收益（明细见「数值与代码验证」的表 5）：Stage 2 到 Stage 3，Qwen3-32B 的 thinking 模式 LiveBench 68.6 → 70.9、Arena-Hard 86.8 → 89.4、CounterFactQA 50.4 → 61.3（+10.9），non-thinking 模式从无到有（LiveBench 57.1、Arena-Hard 88.5），报告也明确接受在专用能力上让一点以换通用性。取舍一句话：不融合就要维护两个 checkpoint 并做请求级模型路由，融合是「一组权重同时守住两种分布不退化」。

### 3. 思考预算：训练期与推理期两侧，且它不是硬截断

**推理期**的做法是手动中断：思考长度达到调用方给定阈值时，插入一条 stop-thinking 指令

```text
Considering the limited time by the user, I have to give the solution based on the thinking directly now.
```

其后紧跟 `</think>` 与两个换行，模型基于已经积累的推理直接给答案。直接截断 token 会把答案一起切掉，只剩半句话，这是最常见的错误答法。

**训练期**：这个能力不是显式训练出来的，而是思考模式融合的自然结果——模型在融合阶段同时见过带空 thinking 块的 non-thinking 样本与长思考样本两端，因此能处理中间态（基于不完整推理作答）。所以预算可控性应当作为融合阶段的设计目标，而不是额外加一个 loss。

预算档位与证据（来源口径）：常见档位是 1,024、8,192、32,768；测试时计算越大越准——AIME'24 上 GPT-4o 约 12%、o1 约 74%、o1 加 64 路多数投票约 83%、1,000 路重排约 93%（OpenAI 公开口径经该来源转述），但输出成本按 token 线性增长。工程结论是生产必须设硬上界：多数路径 8,192，只有真正难的才放到 32,768，自适应思考不能替代上界。预算还要给答案留空间——输出上限 32,768，竞赛级难题 38,912。

8,192 这个档位同时是长输入的运维手段：RULER 长上下文评测就把思考预算设成 8,192，避免思考挤爆上下文。原因是长 prompt 加预算会一起撞上 32,768 的原生窗口——config 里的 `max_position_embeddings=40,960` 正是按 32,768 输出加 8,192 prompt 给的余量，而 8,192 输入加 32,768 预算合计就是 40,960。此时要么压预算，要么开 YaRN（factor 4.0，32,768 × 4 = 131,072），并说明静态 YaRN 会损伤短文本质量。

### 4. 服务侧：预算是准入与配额的把手

量级差先摆出来（来源口径）：普通 LLM 请求 100–500 token、1–3 s；LRM 请求 5,000–50,000 token、10–120 s、单次成本高 10–30×。混池时思考请求会支配成本与尾延迟。

机制在 continuous batching 里：长思考请求在 decode 阶段长期占住一个 slot，每一步都要为它读一遍 KV，边际成本恒定（LLaMA-3-70B、8×H100、TP=8、4k 上下文下 0.050 ms/条，roofline 口径见 [[inference-serving-09]]）。于是同池短请求的 TTFT（被 prefill 抢占）与 ITL（出现台阶）一起恶化——同为 8×H100、$b=48$、$S=4096$ 口径时，不切块的 4k prefill 会让同批请求多等 188 ms，换成 2048 token 的 chunk 是 92.3 ms，512 token 是 22.8 ms。

落地做法：

1. 把模式与预算做成**请求级字段**，带默认值、硬上界与每租户配额；
2. 思考与非思考**分队列或分池**，思考池单独设 TPOT／ITL 门禁与并发上限；
3. 验收用 **goodput**（满足 TTFT／TPOT 约束的吞吐）而不是裸吞吐，并统计思考 token 占比与预算命中率；
4. 预算耗尽的强制收尾本身就是一条天然降级路径——过载时把预算调小，而不是直接失败。

取舍要讲清：混池利用率高但尾延迟差，分池稳 SLO 但牺牲利用率，按流量里难例占比与 SLO 严格程度决定。这部分与 [[inference-serving-02]] 的调度机制、[[inference-serving-09]] 的指标口径直接衔接。

### 5. 流式输出、解析与多轮上下文

**解析。** 服务端必须把思考与答案分成两路返回：vLLM 用 `--enable-reasoning --reasoning-parser deepseek_r1`，SGLang 用 `--reasoning-parser qwen3`，对外给 `reasoning_content` 与 `content` 两个字段；Qwen-Agent 用 `thought_in_content` 决定是否把思考并回 `content`。切分靠 `</think>` 特殊 token（Qwen3-8B 模型卡的示例是从右往左找 token id 151668）。为什么必须分：草稿里有错值、自我纠正与猜测，用户不该看到原始 trace。

**多轮上下文。** 官方要求丢掉历史轮次的思考内容、只保留最终回答，Jinja2 chat template 已经这么实现。三条理由：上下文逐轮膨胀；把错误的中间步骤喂回模型；prefix cache 命中率会崩——思考内容是自回归生成的，第一轮的思考 token 本身不可缓存，只有历史里不含思考，多轮前缀才能稳定复用。

**流式策略。** 思考阶段不要逐 token 朗读，给摘要或进度即可，否则长思考段会把 p99 ITL 与体感一起拖垮：同一条回答内部（LLaMA-3-70B、8×H100、TP=8、固定 $b=48$ 口径），ITL 随上下文从 4k 的 7.63 ms 涨到 32k 的 24.46 ms，3.2 倍。

### 6. 训练／推理一致性与生产坑

- **一致性**：rollout 的推理引擎要与训练侧共用 tokenizer、chat template、kernel 与精度。logprob 对不齐会让 GRPO 的 ratio 全部被 clip，训练看起来在跑但梯度是错的。
- **采样参数**：思考模式不要用 greedy 解码。官方建议 thinking 模式 temperature=0.6、top-p=0.95、top-k=20，non-thinking 模式 temperature=0.7、top-p=0.8、top-k=20；greedy 会退化并出现无限重复。
- **数据侧**：GRPO 的退化组会白烧算力。$G=8$ 时单次通过率 $p=0.05$ 的题有 66.3% 的组全错，$p=0.9$ 时有 43.1% 全对——两端都产生零优势组。所以要按通过率动态采题、做难度课程（退化组的完整推导见 [[finetuning-10]]）。
- **评测侧**：公开榜单上的模式、思考预算、采样参数必须一起锁定并随版本记录，否则同一套权重分数不可比，这是「评测过拟合」的一种形态；线上还要记录实际思考 token 数、是否触发强制收尾、预算命中率。
- **小模型上线**优先走强到弱蒸馏：on-policy 蒸馏相对直接 RL 只要约 1/10 的 GPU 小时就拿到更高分（Qwen3-8B：17,920 GPU 小时对 1,800 GPU 小时，AIME'24 67.6 → 74.4、AIME'25 55.5 → 65.5），代价是预算可控性受教师轨迹覆盖度约束。

## 数值与代码验证

### 表 1：KV 单价与「预算即显存」

口径 $k=2LH_{kv}d_{\text{head}}\cdot\text{bytes}$，bf16（2 B）、head_dim 128，与仓库统一常数一致：

| 模型 | $L$ | $H_{kv}$ | 每 token KV | 32k token 思考轨迹 |
| --- | --- | --- | --- | --- |
| LLaMA-3-70B | 80 | 8 | $2\times80\times8\times128\times2=327{,}680$ B = **320 KiB** | $320\ \text{KiB}\times32{,}768=10$ GiB |
| Qwen3-32B | 64 | 8 | $2\times64\times8\times128\times2=262{,}144$ B = **256 KiB** | $256\ \text{KiB}\times32{,}768=8$ GiB |
| Qwen3-8B | 36 | 8 | $2\times36\times8\times128\times2=147{,}456$ B = **144 KiB** | $144\ \text{KiB}\times32{,}768=4.5$ GiB |
| LLaMA-3-8B（对照） | 32 | 8 | $2\times32\times8\times128\times2=131{,}072$ B = **128 KiB** | $128\ \text{KiB}\times32{,}768=4$ GiB |

并发上限 $b_{\max}\approx M_{KV}/(kS)$，每卡留 60 GiB 给 KV、$S=32\text{k}$：

| 配置 | 算式 | $b_{\max}$ |
| --- | --- | --- |
| Qwen3-32B，TP=1 | $60\times1024^3/(262{,}144\times32{,}768)=7.5$ | 7 条 |
| Qwen3-32B，TP=2（每卡 $k$ 减半到 128 KiB） | $60\times1024^3/(131{,}072\times32{,}768)=15.0$ | 15 条 |
| Qwen3-8B，TP=1 | $60\times1024^3/(147{,}456\times32{,}768)=13.3$ | 13 条 |
| LLaMA-3-70B，TP=1 | $60\times1024^3/(327{,}680\times32{,}768)=6.0$ | 6 条 |

一条 32k 的思考轨迹在 Qwen3-32B 上就是 8 GiB KV，单卡只装得下 7 条并发。预算不是「风格参数」，它是显存与并发数。

### 表 2：E2E 拆解（TTFT=400 ms，TPOT=25 ms，$E2E\approx TTFT+TPOT\times(O-1)$）

| 负载 | $O$ | E2E | TTFT 占比 |
| --- | --- | --- | --- |
| 非思考模式，答案 200 token | 200 | $400+199\times25=5{,}375$ ms ≈ **5.38 s** | 7.4% |
| 预算 8,192 + 答案 500 | 8,692 | $400+8{,}691\times25=217{,}675$ ms ≈ **217.7 s** | 0.18% |
| 预算 32,768 + 答案 500 | 33,268 | $400+33{,}267\times25=832{,}075$ ms ≈ **832 s** | 0.05% |

思考段独占 $8{,}192\times25\ \text{ms}=204.8$ s（≈205 s），占 E2E 的 94.1%。$O=200$ 时 TTFT 占 7.4%，$O\approx8{,}692$ 时不到 0.5%——**思考模式下优化 TTFT 没有意义**，只能压预算或改善 TPOT／并发。

### 可运行代码

第一段是服务端的预算收尾与两路解析骨架（vLLM 风格的伪代码，`STOP_THINKING` 就是上文那条指令，`tokenize`／`sample`／`decode` 由引擎提供）：

```python
STOP_THINKING = ("Considering the limited time by the user, I have to give "
                 "the solution based on the thinking directly now.")
THINK_END_ID = 151668          # Qwen3 的 </think> 特殊 token id
BUDGET_HARD_CAP = 8192         # 生产硬上界：多数路径 8192，难题才 32768

def next_prompt_ids(output_ids, budget, hard_cap):
    """每生成一步后调用：返回需要追加的 token 序列（空表示不干预）。"""
    thinking_len = len(output_ids)          # 简化：全部算作思考
    if thinking_len < min(budget, hard_cap):
        return []
    # 手动收尾：插入指令 + </think> + 两个换行，然后让模型直接作答
    return tokenize(STOP_THINKING + "\n\n</think>\n\n")

def split_reasoning(output_ids):
    """从右往左找 </think>，切出 reasoning_content 与 content 两路。"""
    for i in range(len(output_ids) - 1, -1, -1):
        if output_ids[i] == THINK_END_ID:
            return output_ids[:i], output_ids[i + 1:]
    return output_ids, []                   # 未收尾：整段都是思考

def serve(req):
    budget = min(req.budget or BUDGET_HARD_CAP, BUDGET_HARD_CAP)
    out, forced = [], False
    for _ in range(req.max_tokens):
        out.append(sample(out))
        if not forced:               # 收尾只插一次，否则每一步都会重复插入同一段指令
            extra = next_prompt_ids(out, budget, BUDGET_HARD_CAP)
            if extra:
                out.extend(extra); forced = True
        if out[-1] == EOS_ID:
            break
    reasoning, answer = split_reasoning(out)
    return {"reasoning_content": decode(reasoning), "content": decode(answer),
            "budget_hit": forced, "thinking_tokens": len(reasoning)}
```

第二段复算表 1 到表 3，常数与仓库一致（KiB = 1024 B，bf16）：

## 常见追问

- **追问**：预算到了直接截断 token 行不行？
  - 要点：不行。截断会把答案一起切掉，用户看到半句话。正确做法是插入 stop-thinking 指令并紧跟 `</think>` 与两个换行，让模型基于已积累的推理直接作答；代价是答案质量下降而不是格式崩坏，这也是它适合当降级路径的原因。
- **追问**：`enable_thinking=False` 时写 `/no_think` 还有用吗？多轮里哪个 flag 生效？
  - 要点：没用，软开关在硬开关关闭时完全失效。`enable_thinking=True` 时即使写了 `/no_think` 也仍会输出 think 块（内容可为空）。多轮里以最后遇到的那个 flag 为准，训练数据专门在多轮里随机插入多个 flag 来练这个行为。
- **追问**：为什么不干脆训两个模型，各管一种模式？
  - 要点：要多一份权重与一次部署（显存、版本对齐、运维各一份），还要在请求层做模型路由。融合的收益是「一组权重同时守住两种分布不退化」，实测 Qwen3-32B 融合后 thinking 的 LiveBench 68.6 → 70.9、CounterFactQA +10.9，non-thinking 也从无到有。代价是两种分布互相干扰，报告明确接受在专用能力上让一点换通用性。
- **追问**：生产上预算该设多少，怎么定？
  - 要点：先定硬上界再谈自适应。多数路径 8,192，只有真正难的请求才放到 32,768；还要给答案留空间（输出上限 32,768，竞赛级 38,912）。定档依据是显存与延迟：Qwen3-32B 上 32k 预算单条就占 8 GiB KV、单卡只装 7 条并发，$O=8{,}692$ 时 E2E 217.7 s。档位用线上预算命中率与 goodput 反推，不靠拍脑袋。
- **追问**：多轮对话里历史轮次的思考内容要不要保留？
  - 要点：丢掉，只保留最终回答，官方 chat template 已这么做。保留会让上下文逐轮膨胀、把错误的中间步骤喂回模型，而且第一轮的思考 token 不可缓存，prefix cache 命中率会崩。
- **追问**：混池还是分池？
  - 要点：混池利用率高但尾延迟差——长思考请求长期占 slot、每步读一遍 KV（0.050 ms/条），同池短请求的 TTFT 被 prefill 抢占、ITL 出现台阶（4k 不切块 188 ms，512 chunk 22.8 ms）。分池稳 SLO 但牺牲利用率。判据是流量里难例占比与 SLO 严格程度；无论哪种，模式与预算都要是请求级字段，并用 goodput 而不是裸吞吐验收。
