## 一句话答案

> 哈希树 = 叶子放内容哈希、内部节点放 $H(\text{子哈希} \,\|\, \text{元数据})$ 的内容寻址结构：仓库数据的实现先定粒度（文件级 / 内容定义块级 / 语法级）与扇出，再定节点哈希的字节布局。
> 收益集中在增量路径：根哈希一次比较就能判定整个仓库有没有变，不等时只沿哈希不等的子树下降，一次编辑重写从叶到根的 $O(\log_f N)$ 个节点、其余子树按哈希直接复用——6,000 个文件在 256 叉树下深度 2，一次改动只重写 1 个 blob 加 2 个 tree 节点；同规模下二进制 Merkle 树深度 13、包含证明只有 $13 \times 32 = 416$ B。
> 分块粒度是去重率与 diff 粒度的总开关：固定 4 KiB 分块在文件开头插一个字节会让 16 个块全部换哈希，内容定义分块只换 1 块（实测 11 块中 10 块不变）。
> 边界要主动说：哈希树证明的是字节一致，不是索引正确——chunker、embedding 模型、哈希算法任何一项变了，同一个内容哈希就对应到另一个向量，索引元数据必须一起版本化。

## 面试官在考什么

- **先定粒度与扇出，再写代码**：粒度决定一次编辑要重写多少节点（整文件、一个 CDC 块、还是一个函数），扇出决定深度与证明大小的取舍。会上来就写 `class Node` 的候选人，通常答不出「重命名要不要重写 blob」。
- **节点哈希的字节布局是否说得具体**：条目哈希必须是 `mode + name + \0 + 子哈希`。只哈希子哈希会漏掉重命名，只哈希名字不哈希 mode 会漏掉 chmod；而 blob 哈希不含路径，正是「重命名不重写内容」的来源。
- **增量是否写成「根哈希短路 + 沿树下降」**：而不是遍历所有文件比内容。要能说清 mtime/size 只能给「可能变了」、内容哈希才精确但读放大一到两个数量级，以及两级判定的代价是 $O(\text{变更路径} \times \text{分支因子})$。
- **工程落地三件套**：不可变节点、copy-on-write（结构共享）、原子根切换；快照就是一个根哈希，两个快照的差异靠两棵树同时下降、哈希相等即剪枝。
- **有没有主动划边界**：包含证明只证明字节归属；索引正确性还要靠 `(model_id, dim, normalize, chunker_version, index_version)` 一起版本化，否则会出现「哈希没变、检索结果悄悄变差」这种不报错的故障。
- **坑位覆盖度**：大文件与二进制、空目录与符号链接、大小写不敏感文件系统、ignore 与密钥过滤、不可信 DAG 的遍历方式、内存按字节记账。

常见错误答案：

- 「树是 $O(\log N)$ 的所以很快」——给不出方向性数字：256 叉树深度 2、二进制树深度 13，证明大小差 39 倍，一次编辑重写的对象数是 3 比 14。
- 用固定大小分块 + 把「文档 id + 序号」当 chunk id：去重率归零，而且开头插入一段会让后面所有 chunk 序号平移、整篇被判为变更。

## 原理与推导

### 1. 粒度、扇出与节点哈希的字节布局

| 粒度 | 叶子是什么 | 一次编辑的影响面 | 去重单元 |
| --- | --- | --- | --- |
| 文件级（Git 形态 blob → tree → commit） | 整个文件的内容哈希 | 1 个新 blob + 到根的 tree 节点 | 整个文件相同才去重 |
| 内容定义块级（CDC） | 变长块的哈希 | 被影响的块 + 到根的路径（实测 64 KiB 插 1 B 只换 1 块） | 亚文件级，跨文件也能命中 |
| 语法级（函数 / 类） | 语法单元的哈希 | 被改函数所在单元 + 摘要节点 | 按语义单元复用，最适合代码索引 |

节点哈希是链式构造。Git 的 tree 条目实际字节是 `<mode> <name>\0<raw hash>`，mode 用 ASCII 八进制（`100644` 普通文件、`100755` 可执行、`40000` 目录），条目按原始字节排序，三个字段各管一件事：

$$h_{\text{node}} = H(\text{mode} \,\|\, \text{name} \,\|\, \texttt{0x00} \,\|\, h_{\text{child}})$$

- 缺 `name`：`a.ts` 改名为 `b.ts`、内容不变时，条目集合里的子哈希多重集完全一样，目录哈希不变，重命名在树里不可见。
- 缺 `mode`：`chmod +x` 之后哈希不变，权限变更丢失。
- `name` 参与哈希、blob 哈希不含路径，于是重命名只改从该条目到根的一条路径，blob 一个字节都不重写。实测 6,000 文件、路径 `src/m0007.ts`：改内容新写 3 个对象（1 blob + 2 tree），chmod 与重命名各新写 2 个对象。

扇出决定深度与一次编辑的重写量（6,000 个文件、32 B 摘要）：

| 扇出 | 深度 | 一次编辑重写 | 包含证明（最坏情况） |
| --- | --- | --- | --- |
| 2 | $\lceil \log_2 6000 \rceil = 13$ | 14 个对象（1 blob + 13 tree） | $13 \times 32 = 416$ B |
| 16 | 4 | 5 个对象 | $4 \times 15 \times 32 = 1{,}920$ B |
| 256 | $\lceil \log_{256} 6000 \rceil = 2$ | 3 个对象（1 blob + 2 tree） | $2 \times 255 \times 32 = 16{,}320$ B |

$256^2 = 65{,}536$，所以 256 叉树两层就能装下 6,000 个条目。读法是：扇出越大，深度与 IO 次数越少（一次编辑写 3 个对象而不是 14 个），但包含证明越大（16,320 B 对 416 B，39 倍）——证明大小重要用低扇出，IO 次数重要用高扇出。

两个容易混的深度来源要分开说：Git 形态的树深度由路径段数决定（`src/m0007.ts` 是 root tree → `src` tree → blob，2 层 tree），不是由扇出决定；固定扇出的多层索引树才用 $\lceil \log_f N \rceil$。两者都必须满足「改动只影响从条目到根的一条路径」，这要求**分组键是名字（路径段），不是排序位置**：实测把 6,000 个条目按排序位置切成 24 组，表头插入 1 个文件会连锁重写 24/24 个目录节点，末尾追加只重写 1/24 个。

### 2. 分块策略是去重率与 diff 粒度的总开关

按固定 4 KiB 切块，在文件开头插入一个字节会让后续所有块的边界平移、块哈希全部改变：去重率归零，diff 全部误报「变了」。内容定义分块（CDC）用滚动哈希在内容里找边界，插入只影响一块：

| 方案 | 块数 | 插 1 个字节后不变的块 | 说明 |
| --- | --- | --- | --- |
| 固定 4 KiB | 16 | 0 | 边界由偏移决定，插入把后面全部推走 |
| CDC（gear 滚动哈希） | 11 | 10 | 边界由内容决定，插入点之后自动重新对齐 |

CDC 的实现要点：滚动哈希逐字节更新（gear 或 Rabin 指纹），`h & mask == 0` 时切块，mask 位数决定平均块大小（12 bit 约 4 KiB），再配 min/max 约束防止极端块（实测 min 1 KiB、max 16 KiB，块大小 9394/6794/10021/3404/5864/3942/2656/2488/4620/2160/14193 B）。二进制与大文件必须走 CDC：100 MB 的权重改一个字节，整文件哈希会让整个 blob 重写。同一个原则平移到索引侧，就是 **chunk id 必须是内容哈希，而不是「文档 id + 序号」**。否则在文档开头插一段，后面所有 chunk 序号平移、整篇被判为变更，增量 embedding 退化成全量：一篇 50 chunk 的文档改一段，文档级 diff 要 50 次前向、chunk 级只要 1 次（实测输出 `[1, 1]`，见 [[rag-11]]），差 50 倍；文档只有 25 块时这个倍数就是 25。

叶子数量级（口径沿用 [[system-design-02]]）：$6{,}000 \times 400 \times 4.2 = 1.008\times10^7$ token；按 500 token/chunk、12% 重叠（步长 440 token）得 $1.008\times10^7 / 440 \approx 22{,}909$ 个 chunk；每个 chunk 一个 768 维 fp16 向量是 $22{,}909 \times 768 \times 2 = 3.5\times10^7$ B $\approx$ 33.6 MiB。哈希树的叶子（chunk 哈希 + 向量）就是这个量级，代码用语法级切分比 CDC 更合适（[[coding-10]]）。

### 3. 增量检测写成「根哈希短路 + 沿树下降」

mtime/size 轮询只能看到「可能变了」：mtime 精度有限、跨机时钟不一致、只改内容不改 mtime 的写入都会漏。内容哈希才能精确判定，代价是必须读全文——读放大比 stat 高一到两个数量级（[[rag-11]]）。所以正确姿势是两级判定：

1. **先比根哈希（一次比较）**：相等就是「整个仓库没变」，直接返回，不碰任何文件。
2. **不等时沿树下降**：只对哈希不等的子树递归，代价 $O(\text{变更路径} \times \text{分支因子})$，而不是 $O(\text{仓库大小})$。

实测两个快照之间变了 2 个文件（1 个改内容 + 1 个新增），只做 3 次哈希比较就列出了变更列表；逐文件比内容要读 6,000 个文件。诚实的边界：同一目录内的条目仍需线性扫描（6,000 个文件挤在一个目录里就是 6,001 次名字对比），要让成本真正按变更路径缩放，得给目录加扇出（按名字前缀分桶）或按字节序做跳跃。

可复算的收益（H100 bf16 稠密 989 TFLOPs、MFU 30%、2 美元/GPU·h，encoder 前向 2P、$P = 0.1\text{B}$）：

| 路径 | token 数 | FLOPs | 时间 | 成本 |
| --- | --- | --- | --- | --- |
| 全量重嵌 | $1.008\times10^7$ | 2,016 TFLOPs | 6.79 s | \$0.0038 |
| 增量（30 个脏文件 → 反向 import 闭包 120 个文件） | $2.016\times10^5$ | 40.3 TFLOPs | 135.9 ms | \$0.00008 |

相差 50 倍，而且这 120 个文件是哈希树加依赖图告诉你的，不是靠逐文件比内容找出来的。两个口径要分清：30/6,000 = 0.5% 是直接改动的文件比例，120 是沿反向 import 闭包扩散后的重嵌集合（4 倍放大）；闭包大小随语言与架构变化，TypeScript 与 Python 的爆炸半径完全不同。

### 4. 不可变节点、copy-on-write 与原子根切换

内容寻址天然产生不可变节点：对象的名字就是它的哈希，改一个字节就是另一个对象，旧对象永远有效。由此得到三件事：

- **更新 = 重写叶到根的 $O(\log_f N)$ 个节点**，其余子树按哈希直接复用（结构共享）。6,000 文件的一次编辑只写 3 个新对象，剩下的 5,999 个 blob 一个字节都不动。
- **快照 = 一个 32 B 的根哈希**；「两个快照之间哪些文件变了」= 两棵树同时下降、哈希相等就剪掉整棵子树，不需要比较任何文件内容（同批第 2 题 Merkle diff 的做法）。
- **一致性靠原子根切换**：新对象先全部写齐并 fsync，再用一次原子 `rename` 或 CAS 把根指针从 A 切到 B。读端要么看到旧快照、要么看到新快照，永远不会看到半新半旧的树。

在线索引的同构做法是蓝绿索引 + 别名切换（[[rag-11]]）：新索引在后台建好、跑完校验，再把读别名一次切过去。代价是重建期间双份存储：$10^7$ 条 768 维 fp32 的 HNSW，向量本体 28.61 GiB 加 M=16 的图结构 1.19 GiB 合计 29.8 GiB，蓝绿就是 59.6 GiB，48 GiB 内存的机器直接放不下，只能按分片滚动切换。

### 5. 哈希树证明的是「字节一致」，不是「索引正确」

Merkle 包含证明让你不读内容就能验证某个文件属于某个快照：二进制树只要 13 个 32 B 哈希（416 B）就能从叶子重算出根。但它证明的只是字节归属，和「这份字节被索引成了什么」是两件事：

- **索引元数据必须一起版本化**。`chunker_version`、`model_id`、`tokenizer`、`dim`、`normalize`、量化方案任何一项变了，同一个内容哈希就对应到不同向量。把这些字段写进 chunk 记录与索引 manifest，并在检索时校验；否则故障形态是「哈希没变、检索结果却悄悄变差」，没有任何报错。
- **缓存 key 必须含 `index_version`**。检索缓存与 prefix cache 都要带（[[inference-serving-05]]），否则旧上下文会一直供应到缓存自然过期。
- **哈希算法本身也要进版本**。SHA-1 已被构造出前缀碰撞，新系统用 SHA-256 或 BLAKE3；换算法等于整棵树作废，只能像 Git 的 SHA-256 迁移那样做仓库级切换。另外序列化必须 canonical（键排序、无多余空白），否则同一份内容在不同机器上算出不同哈希。

### 6. 生产坑清单

- **大文件与二进制**：100 MB 权重动一个字节就重写整个 blob，必须 CDC 加单独阈值（超过阈值走块级，小于阈值保持整文件）。
- **空文件、空目录、符号链接、子模块的语义要显式定义**：目录哈希要不要包含空目录（Git 不跟踪空目录）；符号链接哈希目标字符串还是目标内容；子模块哈希 commit id 而不是内容。
- **大小写不敏感文件系统**（macOS / Windows）下 `Foo.ts` 与 `foo.ts` 会撞进同一个树条目。条目名必须用原始字节，冲突时报错而不是静默覆盖。
- **`.gitignore` / `.aiignore` 与密钥文件必须在入树之前过滤**：否则哈希树加向量索引会变成凭据的持久副本，安全边界在采集阶段而不是检索阶段。
- **解析不可信 DAG 要迭代而不是递归**（远程仓库、插件提供的快照），并限制深度与单对象大小，否则构造出的深树会打爆调用栈。
- **内存要按字节记账**：tracemalloc 实测裸 `dict` 80.4 B/条、手写链表（含 `__slots__`）160.4 B/条（[[coding-06]]），100 万文件就是 76.7 MiB 与 153.0 MiB。10 万文件级的 monorepo 不可能把树全常驻内存，要按目录分片或落盘索引。

### 7. 接回 Cursor 的场景

这道题会出现在 60 分钟、基于真实代码库的实现轮里，追问方向偏「索引新鲜度与增量路径」。仓库索引的成本几乎全不在算力——全量一次 6.79 s、\$0.0038——瓶颈是索引过期，而索引过期比索引缺失更糟（返回已删除的旧签名会让模型生成编译不过的代码）。哈希树之后要接上完整一条链：反向 import 闭包 + tombstone + 原子根切换 + 「保存后 5 s 内可检索」（[[system-design-02]]），删除必须走 tombstone，否则源文件没了索引里还搜得到。跨分支、跨提交复用是哈希树白送的收益：同一个 blob 在不同分支下哈希相同，索引可以按 blob 哈希共享，只有树路径不同。被追问技术路线时先声明口径再给可复算设计：Cursor 的公开叙述是 chunk embedding 加向量索引、服务端不保留源码文本；Claude Code 的公开叙述是不建仓库索引，靠 Grep/Glob 按需搜索。

## 数值与代码验证

口径：6,000 文件 × 400 行 × 4.2 token/行（沿用 [[system-design-02]]）；chunk 500 token、12% 重叠；embedding 768 维 fp16；encoder 前向 2P、P = 0.1B；H100 bf16 稠密 989 TFLOPs、MFU 30%、2 美元/GPU·h；单位 1024 进制。下面每个数字都由本节代码跑出。

**表 1：扇出 → 深度 / 一次编辑重写量 / 包含证明**

| 扇出 | 深度 | 一次编辑新写对象 | 包含证明（最坏） |
| --- | --- | --- | --- |
| 2 | 13 | 14 | 416 B |
| 16 | 4 | 5 | 1,920 B |
| 256 | 2 | 3 | 16,320 B |

树的核心实现：路径分段建树、条目哈希含 mode 与 name，`edit` 的返回值就是「从叶到根重写了几个对象」。

```python
import hashlib

def h(*parts):
    return hashlib.sha256(b''.join(parts)).digest()

def blob(content):
    return h(b'blob', str(len(content)).encode(), b'\0', content)

def build(files, store):
    """返回根哈希；store 收集全部对象：tree 的条目表与 blob 的内容。"""
    def tree(entries):
        entries = sorted(entries)                      # 条目按名字的原始字节排序
        # 条目字节 = <mode> <name>\0<raw hash>，与 Git 的 tree 条目布局一致
        payload = b''.join(m.encode() + b' ' + n.encode() + b'\0' + ch
                           for n, m, ch in entries)
        nh = h(b'tree', payload)
        store[nh] = entries
        return nh

    def descend(prefix, paths):
        entries = []
        for p in sorted(paths):
            if len(p) == 1:
                full = f'{prefix}/{p[0]}' if prefix else p[0]
                mode, content = files[full]
                bh = blob(content)
                store[bh] = content
                entries.append((p[0], mode, bh))
        for name in sorted({q[0] for q in paths if len(q) > 1}):
            sub = [q[1:] for q in paths if len(q) > 1 and q[0] == name]
            nxt = f'{prefix}/{name}' if prefix else name
            entries.append((name, '40000', descend(nxt, sub)))
        return tree(entries)

    return descend('', [tuple(k.split('/')) for k in files])

def edit(files, mutate):
    """改一个条目：返回新写对象数——即从叶到根重算的那条路径。"""
    old, new = {}, {}                              # build 把对象写进传入的 store
    build(files, old)
    changed = dict(files)
    mutate(changed)
    build(changed, new)
    return len(set(new) - set(old))

files = {f'src/m{i:04d}.ts': ('100644', f'export const v{i} = {i}\n'.encode())
         for i in range(6000)}
store = {}
root = build(files, store)
print(root.hex()[:8], len(store) - len(files), 'tree +', len(files), 'blob')
print(edit(files, lambda fs: fs.__setitem__('src/m0007.ts', ('100644', b'v7 = 8\n'))))  # 3
print(edit(files, lambda fs: fs.__setitem__('src/m0007.ts',
                                            ('100755', fs['src/m0007.ts'][1]))))       # 2
print(edit(files, lambda fs: fs.__setitem__('src/moved.ts',
                                            fs.pop('src/m0007.ts'))))                  # 2
```

扇出、重嵌成本与固定分块 / CDC 的复算（CDC 用固定种子的 gear 滚动哈希，可复现）：

```python
import hashlib, math, random

N, tokens = 6000, 6000 * 400 * 4.2
for f in (2, 16, 256):                          # 扇出 → 深度 / 重写量 / 证明大小
    d = math.ceil(math.log(N, f))
    print(f, d, d + 1, d * (f - 1) * 32)        # 2 13 14 416 / 16 4 5 1920 / 256 2 3 16320

chunks = tokens / (500 * 0.88)                  # 500 token/chunk、12% 重叠 → 步长 440
FLOP, EFF = 2 * 0.1e9, 989e12 * 0.30            # 2P 前向、H100 989 TFLOPs、MFU 30%
full, inc = tokens * FLOP, 120 * 400 * 4.2 * FLOP       # 增量 = 闭包 120 个文件
print(round(tokens), round(chunks), round(chunks * 768 * 2 / 2 ** 20, 1))   # 10080000 22909 33.6
print(round(full / 1e12, 1), round(full / EFF, 2), round(full / EFF / 3600 * 2, 5))
print(round(inc / 1e12, 2), round(inc / EFF * 1000, 1), round(full / inc, 1))
# 2016.0 6.79 0.00377 / 40.32 135.9 50.0

rng = random.Random(42)                         # 固定种子：gear 滚动哈希、64 KiB 内容
GEAR, MASK, MIN_C, MAX_C = [rng.getrandbits(64) for _ in range(256)], (1 << 12) - 1, 1024, 16384
text = random.Random(7).randbytes(65536)
raw = b'#' + text                               # 开头插一个字节

def cdc_cuts(buf):
    cuts, hh, start = [], 0, 0
    for i, byte in enumerate(buf):
        hh = ((hh << 1) + GEAR[byte]) & 0xFFFFFFFFFFFFFFFF
        if i - start + 1 >= MAX_C or (i - start + 1 >= MIN_C and (hh & MASK) == 0):
            cuts.append(i + 1)
            hh, start = 0, i + 1
    return cuts + ([len(buf)] if cuts and cuts[-1] != len(buf) else [])

def digests(buf, cuts):
    return [hashlib.sha256(buf[i:j]).digest()[:8] for i, j in zip([0] + cuts[:-1], cuts)]

same = lambda a, b: sum(x == y for x, y in zip(a, b))
fixed = lambda buf: [hashlib.sha256(buf[i:i + 4096]).digest()[:8]
                     for i in range(0, len(buf), 4096)]
print('fixed', len(fixed(text)), same(fixed(text), fixed(raw)),           # fixed 16 0
      'cdc', len(digests(text, cdc_cuts(text))),
      same(digests(text, cdc_cuts(text)), digests(raw, cdc_cuts(raw))))   # cdc 11 10
```

## 常见追问

- **追问**：扇出到底选多大？
  - 要点：看哪个数字重要。IO 次数与深度重要（一次编辑要落几个新对象、客户端要同步几层）就选高扇出，256 叉树装 6,000 个文件只有 2 层；证明大小与验证成本重要（要把「某文件属于某快照」的证据塞进请求）就选低扇出，二进制树 13 个哈希 416 B。生产里的折中是 16 到 32 叉：深度 3 到 4 层，证明 1.9 到 2.9 KiB；再往上（64 叉）深度只降到 3 层，证明却涨到 5.9 KiB。真实 Git 不设扇出，深度由路径段数决定，靠目录本身分层。
- **追问**：为什么不用 mtime/size 做增量，非要读全文算哈希？
  - 要点：mtime/size 只能给「可能变了」，漏报来源包括 mtime 秒级精度、跨机时钟不一致、`rsync` 保留时间戳、脚本只改内容不改 mtime；它唯一的好处是便宜（一次 stat）。内容哈希精确，但读放大比 stat 高一到两个数量级（[[rag-11]]）。正确姿势是两级判定：先比根哈希，不等时只沿哈希不等的子树下降，再对脏文件算内容哈希；热路径上还可以用元数据变化触发内容哈希、哈希相同则判定为假阳性。
- **追问**：删除怎么处理？为什么不能直接从树里摘掉？
  - 要点：删除必须走 tombstone。直接物理删除会让「旧版本已不可见」与「新版本已可见」之间出现空窗，也会让引用了该 chunk 的历史会话失效；正确顺序是写 tombstone 与 `deleted_at`、检索时过滤、再按策略压实（[[rag-11]]）。哈希树这一侧同理：删除一个文件是生成一棵新的树，旧根哈希依然指向完整的历史快照，回滚就是切回旧的根。
- **追问**：同一个文件在多个分支或历史提交里重复出现，索引能不能复用？
  - 要点：能。blob 哈希只由内容决定、与路径和分支无关，所以同一个 blob 在不同分支下哈希相同，索引可以按 blob 哈希共享，树路径不同不影响。这是内容寻址白送的收益：跨分支重复率远高于直觉，规划存储前先用「唯一 blob 数 / 文件数」量一下。
- **追问**：哈希树能保证检索结果正确吗？
  - 要点：不能，它只保证字节一致。`chunker_version`、`model_id`、`tokenizer`、`dim`、`normalize`、量化方案任何一项变了，同一个内容哈希就对应到另一个向量。要把这些字段写进索引 manifest 并在检索时校验，缓存 key 里也要带 `index_version`（[[inference-serving-05]]），否则故障形态是「不报错但结果悄悄变差」。
- **追问**：为什么 Cursor 要建仓库索引，而 Claude Code 选择不建？
  - 要点：公开叙述里的两条路线，各有代价。Cursor 走 chunk embedding 加向量索引，换来「语义相似但词汇不重叠」的召回，代价是必须维护增量索引与新鲜度（[[rag-11]]）；Claude Code 走 Grep/Glob 按需搜索，没有索引过期问题，代价是每次都要真读文件、召回依赖模型的查询构造能力。哈希树在第一条路线里是增量路径的地基，在第二条路线里是文件内容缓存与变更检测的手段——回答时说清自己按哪条路线设计，再给可复算的取舍。
