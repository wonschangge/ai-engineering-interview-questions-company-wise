## 一句话答案

> 评估必须**按任务分层**，因为「tab 补全」与「agent 多文件编辑」的成功定义完全不同：
> | 任务 | 离线判据 | 在线判据 |
> | --- | --- | --- |
> | tab 单点补全 | 精确匹配 / 编辑相似度 / 编译通过率 | 接受率、节省击键、接受后撤销率、延迟 |
> | 单文件编辑 | 补丁应用成功率 + 语法/类型 + 相关测试 | 应用成功率、回滚率、用户手动改动比例 |
> | 多文件任务 | SWE-bench 式：隐藏测试判定 + **不破坏既有测试** | 任务完成率、步数/成本、人工接管率 |
> 三条纪律：
> ① **离线指标必须与在线指标相关**——如果离线涨、线上不动，说明评测分布与真实使用不匹配（这与「离线涨线上不涨」是同一类问题，串 [[evaluation-05]]）；
> ② **必须防污染与过拟合**——基准可能出现在训练数据里，团队也会不自觉地对评测集调参；用私有留出 + 时间切分 + 定期轮换（串 [[evaluation-06]]）；
> ③ **延迟与质量一起报**——代码补全的「好」包含「快」；只报质量指标可以靠多等 300 ms 刷高，产品上却不可接受。
> 一句话：**离线是回归网（防退化），在线是判据（决定发布），人评是仲裁（处理主观质量）**。

## 面试官在考什么

- **任务分层的意识**：能不能说清「三行补全」与「跨 5 个文件的修复」为什么不能共用一个指标；以及各自的样本从哪来（真实编辑日志、issue、合成任务）。
- **判据的可靠性分级**：编译/类型检查/测试（强判据）> 编辑相似度/精确匹配（弱判据，可被「格式相同但语义错」骗过）> 模型判分（需校准）。能否说明「为什么 SWE-bench 用测试判定」——因为它把「看起来对」变成「真的对」。
- **在线指标的设计与陷阱**：接受率是最常用的代理，但**接受率高不等于用户效率高**（提示过多会干扰、接受后又撤销说明质量差）；所以要配「节省击键」「撤销率」「被采纳后的存活时间」等指标，并最终看长期留存。
- **实验设计**：编辑器场景难做传统 A/B（同一用户不同会话可比性差），常用**交错实验（interleaving）**与**会话内随机化**；能否说出这些替代方案及其偏差。
- **人评**：盲评 + 成对比较（pairwise）+ 一致性检验；以及「评审者偏好长度/格式」的偏差控制。
- **回归集建设**：把线上失败样本固化为用例（每起事故一条），这是评测集增长最可靠的来源（串 [[evaluation-04]]）。

**常见错误答案**

- 「跑一下 HumanEval 就行」——函数级合成题与真实编辑器场景差距极大（无仓库上下文、无多轮编辑）。
- 「看接受率就够了」——接受率可被「给很多短提示」刷高，且不反映真实效率。
- 「离线涨了就发」——不做在线验证与延迟对照，会把体验做坏。
- 「基准固定不变便于比较」——会被迭代过拟合（团队会无意中针对它调提示）。

## 原理与推导

### 1. 四类任务与判据

| 任务 | 输入 | 输出 | 强判据 | 弱判据 |
| --- | --- | --- | --- | --- |
| tab 补全 | 光标上下文（含仓库检索） | 若干行 | 编译通过率 | 精确匹配、编辑相似度（归一化编辑距离） |
| 下一处编辑预测 | 最近 diff | 编辑位置 + 内容 | 应用成功率 | 位置命中率、内容相似度 |
| 单文件编辑 | 自然语言 + 文件 | 补丁 | 语法/类型 + 相关测试 | 补丁相似度 |
| 多文件任务 | 自然语言 + 仓库 | 变更集 | **隐藏测试**（SWE-bench 式）+ 不破坏既有测试 | 变更集规模、人工评分 |

**关键设计**：多文件任务的判据必须包含**「不破坏既有测试」**——只看「新测试是否通过」会奖励「删掉旧测试」这类退化行为。

### 2. 离线基线的选择与局限

- **RepoBench**：面向仓库级代码补全，评测「跨文件上下文能否被正确利用」，比函数级基准更接近编辑器场景（可引用的口径：它把补全任务拆成检索与补全两部分来评测）。
- **SWE-bench**：真实 GitHub issue + 仓库测试判定补丁；它的价值在于**判据可执行**，而不是题目难度。
- **CodeRAG-Bench**：研究检索增强对代码生成的影响，指出**检索内容必须真的有用**——这直接支撑「上下文质量」这一维度的评测（串 [[cursor-11]]）。
- **局限**：公开基准会被训练数据污染（时间切分与私有留出是必须的），且无法覆盖真实编辑器的交互（延迟、部分接受、连续编辑）。

### 3. 在线评估：指标与实验设计

| 指标 | 定义 | 陷阱 |
| --- | --- | --- |
| 接受率 | 接受的提示数 / 展示数 | 可被「多展示短提示」刷高 |
| 节省击键 | 接受内容长度 / 用户本来要输入的长度 | 需要归一化（不同语言不同） |
| 撤销率 | 接受后 N 秒内撤销 / 接受数 | **反向指标**，必须与接受率一起看 |
| 存活率 | 接受内容在最终提交中保留的比例 | 最接近「真实价值」的指标 |
| 延迟 p50/p95 | 感知延迟 | 与接受率强相关，必须同时报 |
| 接管率（agent） | 用户中途接管 / 总任务 | 衡量 agent 可用性 |

**本月最佳单一指标**：接受内容在**最终提交中存活的比例**（接受率 × 存活率），因为它同时惩罚「乱提示」与「提示后被改掉」。

**实验设计**：编辑器场景下传统 A/B 的可比性差（用户会学习、会话不同），常用：
- **交错实验**：同一会话内交替展示 A/B 的提示，比较接受/存活差异（方差小，但要注意顺序效应）；
- **会话级随机化** + 用户内配对分析；
- 长期 holdout 看留存与付费。

### 4. 样本量与噪声

接受率这类比例的差异很小（通常几个百分点），需要大样本。按双侧 $\alpha=0.05$、power 80%，

$$n\approx\frac{2(z_{1-\alpha/2}+z_{1-\beta})^2\,p(1-p)}{\delta^2}$$

$\hat p=0.28$、想检测 $\delta=0.02$（2 个百分点）→ 每组约 **7,700** 次展示；检测 1 个百分点需要约 31,000 次。**这意味着评测必须按「展示量」而非「用户数」设计样本**，也要接受「小改动难以验证」这个现实。

### 5. 污染与过拟合的防护

- **时间切分**：用基准发布时间之后的数据做最终验证（必要不充分）；
- **私有留出**：自建一套不参与调参的任务集（从线上失败样本与内部仓库构造）；
- **轮换**：定期替换一部分题目，防止针对性调优；
- **去污染检查**：对训练语料做 $n$-gram 与语义去重并留记录（串 [[evaluation-06]]）。

## 数值与代码验证

### 表 1：离线与在线指标的相关性检查（示意数据）

| 版本 | 离线 EM（tab） | 在线接受率 | 存活率 | 结论 |
| --- | --- | --- | --- | --- |
| A | 0.31 | 0.27 | 0.24 | 基准 |
| B | 0.38（+23%） | 0.28（+1pp） | 0.25 | 离线虚高：可能过拟合基准格式 |
| C | 0.30 | 0.31（+4pp） | **0.29** | 离线略降但线上更好（更符合真实分布） |

**读法**：B 是典型的「离线涨线上不动」；C 说明**离线指标不是目标**——要找到与线上相关的那部分离线信号（例如按任务类型分群的指标，而不是总平均）。

### 可运行代码

```python
# 1) 样本量与「离线涨线上不动」的检测
import math, random
random.seed(131)

def n_per_group(p, delta, alpha=0.05, power=0.8):
    z_a, z_b = 1.959964, 0.841621
    return 2*(z_a+z_b)**2*p*(1-p)/delta**2

p0 = 0.28
print("在线接受率样本量需求（基线 28%）")
for d in (0.01, 0.02, 0.05, 0.10):
    print(f"  检测 +{d:.0%}: 每组 {n_per_group(p0,d):>8,.0f} 次展示")

# 模拟：离线 EM 提升但线上不变（分布错配）
def simulate(dist_shift):
    """dist_shift: 离线上评测集与真实分布的重叠程度（1=一致）"""
    offline_gain = 0.07
    online_gain = offline_gain * dist_shift
    return offline_gain, online_gain
print("\n离线提升 7 个百分点时，线上真实提升随分布重叠度变化：")
for s in (1.0, 0.5, 0.2, 0.0):
    o, on = simulate(s)
    print(f"  分布重叠 {s:>4.1f}: 离线 +{o:.1%}，线上 +{on:.1%}")

# 2) 接受率 vs 存活率：为什么单看接受率会被刷高
def metrics(shown, accepted, survived):
    return accepted/shown, survived/max(accepted,1), survived/shown
strategies = {
    "朴素（多而短）": (10000, 4200, 1800),     # 接受率高但存活低
    "质量优先（少而准）": (10000, 2800, 2400),   # 接受率低但存活高
}
print(f"\n{'策略':<18} {'接受率':>8} {'存活率':>8} {'接受×存活':>10}")
for name, (s, a, sv) in strategies.items():
    acc, surv, prod = metrics(s, a, sv)
    print(f"{name:<18} {acc:>8.1%} {surv:>8.1%} {prod:>10.1%}")
print("接受率高的策略实际价值更低 —— 这就是为什么要把「存活率」当主指标")

# 3) 交错实验的方差优势（同一会话内 A/B 交替）
def ab_variance(between_user_var, within_user_var, n_users, m_per_user):
    """会话间随机化 vs 会话内交错（配对）的均值方差对比（示意）"""
    between = between_user_var/n_users + within_user_var/(n_users*m_per_user)
    interleaved = within_user_var/(n_users*m_per_user)
    return between, interleaved
b, i = ab_variance(0.02, 0.08, 5000, 20)
print(f"\n均值方差：会话间随机化 {b:.2e} vs 会话内交错 {i:.2e}"
      f"（标准误比 {math.sqrt(b/i):.1f}x）→ 交错设计在同样样本下更灵敏，但要注意顺序效应")

# 4) 回归集增长：线上失败样本固化
print("\n回归集建设示例：")
failures = [("tab", "import 后缺换行"), ("agent", "改文件但漏改调用方"),
            ("tab", "缩进为 2 空格的项目按 4 空格补全"), ("agent", "测试通过但破坏既有用例")]
for i, (kind, desc) in enumerate(failures, 1):
    print(f"  用例 {i:>2} [{kind}] {desc}")
print("每起线上事故 → 一条带断言的用例；这是评测集最有价值的增长方式（也是防退化的核心资产）")
```

预期输出要点：样本量表显示检测 1–2 个百分点的接受率提升需要几千到几万次展示；分布错配模拟说明离线增益如何被稀释（重叠度低则线上不动）；「接受率 vs 存活率」对比显示多而短的策略接受率高但真实价值低；交错实验的方差优势量化说明编辑器场景为什么常用它；最后演示回归集的固化流程。

## 常见追问

- **追问**：怎么防止团队对评测集过拟合？
  - 要点：私有留出（不参与调参）+ 定期轮换 + 时间切分 + 把「评测集改动」当作需评审的变更；并监控「离线涨线上不动」的比例作为过程指标。
- **追问**：多文件编辑的正确性怎么评（测试覆盖不全）？
  - 要点：三层——① 可执行判据（测试/类型/构建）；② 结构性判据（是否漏改调用方：用引用图检查）；③ 人工抽样评审（按风险分层）。测试覆盖不足时，第 ② 层尤其重要。
- **追问**：接受率高但用户抱怨提示干扰，怎么定位？
  - 要点：看「展示频率 × 接受率 × 存活率」的组合：展示过密会降低每次提示的价值；引入「干扰度」指标（单位时间的提示次数、被立即忽略的比例），并用交错实验验证密度参数。
- **追问**：延迟对接受率的影响怎么量化？
  - 要点：用同一模型在不同延迟档位（人为注入延迟）的交错实验画「延迟-接受率」曲线；通常存在拐点（例如 p95 超过 200 ms 后接受率明显下滑），这个拐点决定产品预算。
- **追问**：人评怎么设计？
  - 要点：成对盲评 + 随机左右顺序（抵消位置偏差）+ 一致性检验（κ）+ 明确评分维度（正确性/最小改动/风格一致性）；样本按任务类型与语言分层。
- **追问**：如何评估「agent 是否真的解决了问题」而不是「看起来改了」？
  - 要点：以可执行判据为准（测试通过、症状复现消失）；并检查副作用（是否引入新依赖、是否破坏了不相关文件、是否删了测试）。
