## 一句话答案

> 核心是**把「模型的意图」与「缓冲区的当前状态」解耦**，绝不用「整文件覆盖」。
> 做法分四层：
> ① **模型输出的不是文件内容，而是编辑操作**——以「锚点 + 操作」的形式表达（例如「在符号 `verify_token` 的函数体末尾插入这 6 行」「把第 40–52 行替换为 …」），锚点是**符号/结构位置**而不是行号（行号会因用户输入而漂移）。
> ② **应用到缓冲区时走「位置重定位 + 冲突检测」**——用快照哈希与「自上次读取以来该区域是否被改动」判断；冲突则把该操作标为「待确认」，而不是强行写入。
> ③ **流式应用要分批、幂等、可撤销**——按操作单元（一个 hunk）逐步应用，每个 hunk 有唯一 id 且可重放（重放时不重复应用）；用户一次撤销能整体回退这次编辑（一个事务）。
> ④ **界面层给用户控制权**——把冲突的操作呈现为可接受的建议/差异视图，而不是静默覆盖。
> 一句话原则：**并发的正确性靠「操作 + 重定位 + 事务」，不靠「快」**；把协作编辑领域的两套成熟方案（OT 的操作变换、CRDT 的可交换合并）作为参照，但编辑器内的 agent 编辑通常只需**单向应用 + 冲突回退**，不必上完整 CRDT（可引用的机制背景见对应条目）。

## 面试官在考什么

- **是否把编辑建模成操作而不是内容**：这是分水岭。说「覆盖文件」的直接淘汰；说「锚点 + 操作 + 重定位」的进入下一层。
- **并发冲突的具体处理**：能否给出三类冲突与各自的策略——① 区域不重叠（直接应用）；② 区域重叠但语义兼容（三路合并）；③ 区域重叠且语义冲突（交给用户/重新生成）。
- **流式的工程细节**：SSE/流式通道的断线与乱序处理、操作的幂等与去重、以及「模型中途被取消」时已应用部分的回滚（事务）。
- **缓冲区的现实约束**：编辑器有 undo 栈、光标与选区、IME 组合状态（输入法未上屏）、以及未保存修改；应用编辑时必须**不打断 IME、不搬动光标、不污染 undo 栈**（或把一次 agent 编辑合并成一个 undo 单元）。
- **可验证性**：应用后必须跑语法/类型检查（串 [[cursor-08]] 的验证回路），失败则自动回滚并报告。

**常见错误答案**

- 「等模型输出完整文件后一次性写入」——用户输入丢失，且大文件写入慢。
- 「按行号应用」——用户在前面插入一行，后面所有行号全部漂移。
- 「冲突就覆盖用户输入」——最严重的体验事故。
- 「流式过程中每收到一个 token 就写入缓冲区」——会产生大量中间态抖动、污染 undo 栈，还可能写出语法非法的中间状态。

## 原理与推导

### 1. 编辑操作的表达：锚点比行号稳健

三种定位方式，稳健性递增：

| 定位方式 | 例子 | 用户插入 3 行后是否有效 |
| --- | --- | --- |
| 绝对行号 | 第 40–52 行 | ✗ 完全错位 |
| 行号 + 上下文匹配 | 「包含 `def verify_token` 的行起，匹配 5 行」 | ✓（模糊匹配可容忍小改动） |
| 结构锚点 | 「符号 `verify_token` 的函数体末尾」「类 `Auth` 的第一个方法前」 | ✓✓（与行号无关，语义稳定） |

工程实践是**混合**：优先结构锚点，退化到「上下文匹配 + 模糊容错」，最后才用行号（并附带前后若干行做校验）。

### 2. 应用流程（含并发检查）

```
模型流式输出操作序列 O = [o1, o2, ...]（每个 oi 带锚点与目标文件）
读取时记录: snapshot[file] = 内容哈希 + 该区域的片段哈希
对每个 oi（可分批）:
    1) 重定位: 在当前缓冲区里解析锚点 → 得到实际区间 [s, e]
    2) 冲突检查:
         - 区域未被用户改动（片段哈希一致） → 应用
         - 区域被改动但可三路合并（改动在别处） → 合并后应用，标记为「已合并」
         - 区域被改动且语义冲突 → 不应用，转为待确认建议
    3) 应用为单个事务单元（一个 undo 组），并记录 oi.id 以便幂等重放
    4) 每批应用后跑轻量校验（语法/AST），失败则回滚该批
```

**关键点**：把「读取快照」与「应用」分开，正是乐观并发的标准形态（串 [[cursor-08]] 的变更集）。

### 3. 三类冲突与策略

| 冲突类型 | 例子 | 策略 |
| --- | --- | --- |
| 位置漂移（非冲突） | 用户在上面插入了几行 | 重定位后直接应用 |
| 区域重叠、语义兼容 | 用户改了另一个函数，agent 改这个函数 | 三路合并（共同祖先 = 读取快照） |
| 区域重叠、语义冲突 | 用户正在重写 agent 要替换的那段 | 不应用，呈现为建议/差异视图 |

**三路合并的基线**正是「读取快照」——这也是为什么必须保存快照（只有当前内容无法做三路合并）。

### 4. 流式传输与取消

- **通道**：SSE 或双向流；要处理断线重连与乱序（操作带序号，客户端按序号顺序应用，缺号则请求重传）。
- **中途取消**：用户继续输入或按 Esc → 取消生成；已应用的操作要么保留（标记来源）、要么整体回滚——**必须是一个可撤销事务**，否则用户面对半成品状态。
- **幂等**：每个操作带 id，重复投递不重复应用（网络重试的常见场景）。
- **不抖动**：不逐 token 写入缓冲区，而是**按 hunk 完成度**应用（例如括号匹配完整、缩进完整）；中间态只在「预览层」渲染，不进入真实缓冲区。

### 5. 编辑器集成的三个隐形约束

1. **IME 组合状态**：用户正在用输入法打字时不能改动其前方的文本，否则组合串会被打断——需要等待组合结束（compositionend）再应用。
2. **undo 栈**：一次 agent 编辑应合并为**一个** undo 单元，且不能与用户的输入混在同一组里，否则「撤销」行为不可预测。
3. **光标与选区**：应用后要把光标/选区做位置映射（同 OT 的思路），不能让用户的光标跳到文件开头。

## 数值与代码验证

### 表 1：三种定位方式的稳健性

| 用户插入位置 | 行号定位 | 上下文匹配 | 结构锚点 |
| --- | --- | --- | --- |
| 目标区域之前 3 行 | 错位 3 行 | 正确 | 正确 |
| 目标区域之前 50 行 | 错位 50 行 | 正确（若上下文完整） | 正确 |
| 目标区域之内 | 错位 + 冲突 | 冲突检测命中 | 冲突检测命中 |
| 文件被重命名/移动符号 | 失效 | 可能失效 | 仍有效（按符号名） |

### 表 2：流式应用的三种策略对比

| 策略 | 首字节可见时间 | 抖动 | undo 体验 | 失败回滚 |
| --- | --- | --- | --- | --- |
| 逐 token 写入缓冲区 | 最快 | 严重 | 差（undo 栈被污染） | 难（中间态非法） |
| 按 hunk 完成度应用 | 快 | 轻微 | 好（每 hunk 可合并为一个事务） | 容易（回滚该批） |
| 全部完成再一次性应用 | 慢（等全量） | 无 | 最好 | 容易 |

**推荐**：按 hunk 应用 + 事务合并 + 预览层渲染未完成部分。

### 可运行代码

```python
# 1) 操作式编辑 + 锚点重定位 + 三类冲突判定（可直接跑）
import hashlib, difflib

def h(s): return hashlib.sha256(s.encode()).hexdigest()[:12]

def find_anchor(text, anchor):
    """结构锚点：返回目标区间 (start, end)，按函数名匹配"""
    lines = text.split("\n")
    for i, l in enumerate(lines):
        if anchor["symbol"] in l and l.strip().startswith(("def ", "function ", "func ", "class ")):
            # 函数体范围：到下一个同缩进的 def/class 或文件末尾
            indent = len(l) - len(l.lstrip())
            for j in range(i+1, len(lines)):
                s = lines[j]
                if s.strip() and (len(s) - len(s.lstrip())) <= indent and s.lstrip().startswith(("def ", "class ")):
                    return i, j
            return i, len(lines)
    return None

def three_way_ok(base, user, agent):
    """base=读取快照, user=当前内容, agent=应用后内容；返回是否可自动合并"""
    user_changed = user != base
    agent_changed = agent != base
    if not user_changed or agent_changed and user == agent:
        return True, "直接应用"
    # 用行级差异判断是否重叠
    du = [l for l in difflib.unified_diff(base.split("\n"), user.split("\n"), n=0, lineterm="") if l[:1] in "+-" and l[:3] not in ("+++", "---")]
    da = [l for l in difflib.unified_diff(base.split("\n"), agent.split("\n"), n=0, lineterm="") if l[:1] in "+-" and l[:3] not in ("+++", "---")]
    if set(du) & set(da):
        return False, "区域重叠且冲突 → 转待确认建议"
    return True, "改动不重叠 → 三路合并"

BASE = "def add(a, b):\n    return a + b\n\ndef mul(a, b):\n    return a * b\n"
USER = "def add(a, b):\n    return a + b + 0\n\ndef mul(a, b):\n    return a * b\n"     # 用户改了 add
AGENT = "def add(a, b):\n    return a + b\n\ndef mul(a, b):\n    return a * b  # 修好缩进\n"  # agent 改 mul
print("场景一（不重叠）：", three_way_ok(BASE, USER, AGENT))
AGENT2 = "def add(a, b):\n    return a + b + 0  # agent 也改 add\n\ndef mul(a, b):\n    return a * b\n"
print("场景二（重叠冲突）：", three_way_ok(BASE, USER, AGENT2))

# 2) 锚点重定位：用户在前面插入若干行后仍然命中
code = BASE
for ins in (0, 3, 50):
    moved = "\n".join(["# 用户新增"] * ins) + ("\n" if ins else "") + code
    rng = find_anchor(moved, {"symbol": "mul"})
    print(f"  用户插入 {ins:>2} 行 -> 锚点 'mul' 定位到行区间 {rng}")

# 3) 事务与幂等：同一批操作重复投递不重复应用
class Buffer:
    def __init__(self, text): self.text = text; self.applied = set(); self.undo = []
    def apply(self, op):
        if op["id"] in self.applied:
            return "重复投递，已忽略"
        self.undo.append(self.text)
        self.text = self.text.replace(op["old"], op["new"], 1)
        self.applied.add(op["id"])
        return "已应用"
    def rollback(self):
        if self.undo: self.text = self.undo.pop(); return "已回滚该批次"
        return "无可回滚内容"

buf = Buffer(BASE)
ops = [{"id": "op1", "old": "return a * b", "new": "return a * b  # ok"},
       {"id": "op2", "old": "def mul", "new": "def multiply"}]
for op in ops + [ops[0]]:
    print(f"  应用 {op['id']}: {buf.apply(op)}")
print("  结果含 'multiply'：", "multiply" in buf.text)
print("  回滚：", buf.rollback(), "| 回滚后仍含 'multiply'：", "multiply" in buf.text)

# 4) 流式应用的抖动量化：逐 token vs 按 hunk
import random
random.seed(113)
TOKENS, HUNK = 400, 20
token_writes = TOKENS
hunk_writes = TOKENS // HUNK
print(f"\n写入次数对比：逐 token {token_writes} 次 vs 按 hunk {hunk_writes} 次"
      f"（减少 {1-hunk_writes/token_writes:.1%}）")
print("每次写入都会触发渲染与 undo 记录 —— 写次数就是抖动与内存开销的直接来源")
```

预期输出要点：三路合并判定把「不重叠」与「重叠冲突」分开（后者转待确认，不写缓冲区）；锚点重定位在用户插入 50 行后仍然命中同一函数；事务/幂等演示重复投递被忽略、回滚能整体撤销；抖动量化显示按 hunk 应用把写入次数降低一个数量级。

## 常见追问

- **追问**：为什么不用完整的 CRDT 方案？
  - 要点：CRDT 适合**长期并发、双向编辑**的协作场景；编辑器内 agent 编辑是**单向、短时、可回退**的，用「快照 + 操作 + 三路合并」更简单且足够。若产品本身已是多端协作编辑器，则可以复用其 CRDT/OT 基础设施（把 agent 当成一个客户端）。
- **追问**：流式过程中用户按了 Esc，已应用的部分怎么办？
  - 要点：整体回滚为一个事务（用户视角「这次编辑没发生」）；若部分改动已被用户手动保留，则只回滚 agent 之后未被触碰的部分——并把决策交给用户（提供「保留/撤销」两个按钮）。
- **追问**：如何避免打断输入法（IME）？
  - 要点：监听组合状态，`compositionstart` 到 `compositionend` 之间不修改其前方缓冲区；必要时只更新预览层。
- **追问**：多文件编辑时，某个文件被用户关闭/切换了怎么办？
  - 要点：在内存态（模型层）应用并标记为「未落地」，等用户回到该文件时再合并；或直接写入磁盘但保持编辑器状态一致（取决于编辑器架构），关键是**不丢改动、不覆盖用户输入**。
- **追问**：怎么测试这类并发逻辑？
  - 要点：用属性测试/随机操作序列（随机交错用户输入与 agent 操作）验证不变量：不丢用户字符、可回滚、幂等、最终内容与「串行化顺序」一致；把发现的失败序列固化为回归用例。
- **追问**：应用后语法坏了怎么办？
  - 要点：每批应用后跑语法/AST 校验（毫秒级），失败即回滚并报告——不要留给用户去发现（串 [[cursor-13]] 的可靠应用）。
