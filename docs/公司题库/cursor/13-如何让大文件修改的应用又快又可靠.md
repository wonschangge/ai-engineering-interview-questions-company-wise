## 一句话答案

> 把「输出整文件」改成「输出**结构化编辑指令**」，并把应用做成**带校验的搜索替换 + 精确/模糊两级匹配 + 失败回退**：
> ① **指令形式**：模型输出 `{文件, 锚点, 旧片段, 新片段}` 或 unified diff 形式的 hunk，而不是 500 行全文。理由很直接——传输量与出错面正比于「改动大小」而不是「文件大小」（可引用的背景：diff/patch 的经典形式正是为此设计的）。
> ② **两级匹配**：先**精确匹配**旧片段（含空白与缩进）；失败则**模糊匹配**（忽略行尾空白、统一换行符、忽略缩进差异、允许小范围上下文偏差），并给出匹配置信度。
> ③ **失败要可诊断**：匹配失败时把「期望片段 vs 最相近的实际片段」一起返回给模型，让它**基于最新内容重发该 hunk**（而不是整文件重发）。
> ④ **应用是事务 + 校验**：全部 hunk 在一个变更集里原子应用（任一必需 hunk 失败则整体不写），应用后立刻跑语法/AST 校验，失败回滚（串 [[cursor-08]]、[[cursor-12]]）。
> 一句话原则：**让「应用」成为可失败、可诊断、可重试的确定性步骤，而不是把模型的输出当权威内容直接落盘。**

## 面试官在考什么

- **是否理解「改动的信息量」与「文件大小」无关**：500 行文件改 6 行，输出 6 行指令 vs 输出 500 行全文——后者慢、贵、且更容易引入无关改动（格式漂移、丢注释）。
- **匹配策略的分层**：精确 → 空白归一 → 缩进容忍 → 局部相似（可用编辑距离/最长公共子序列）；每层都要有**明确的失败条件**，不能无限放宽（否则会改错位置）。
- **失败处理的工程闭环**：错误信息要包含足够上下文（行号、期望片段、实际片段、差异摘要），使模型能在**一次重试**内修正；重试要有次数上限与降级（转人工确认）。
- **幂等与并发**：同一 hunk 重放不重复应用（带 id）；应用前检查文件是否被用户改动（快照哈希）。
- **性能数字**：能否给出「逐字重写 500 行」与「应用 6 行 hunk」的差异（传输、模型输出 token、应用耗时、出错率）。
- **正确性验证**：语法/类型检查 + 关键测试；并把「应用失败率」作为可观测指标。

**常见错误答案**

- 「让模型输出整个文件，我们直接写」——慢、贵、易丢内容；且一旦输出被截断就写坏文件。
- 「用字符串 `replace` 就行」——空白/缩进/换行差异会让匹配失败或匹配到错误位置。
- 「匹配失败就整文件重写」——把局部问题升级成全局风险。
- 「重试到成功为止」——会掩盖模型的系统性错误（例如它一直在改已经不存在的代码）；必须有上限与升级路径。

## 原理与推导

### 1. 指令形式：为什么 hunk 优于全文

设文件 $L=500$ 行、改动 $d=6$ 行。三种输出的代价对比：

| 形式 | 输出 token（≈12 token/行） | 应用成本 | 出错面 |
| --- | --- | --- | --- |
| 整文件重写 | $\sim6000$ | 写 500 行 + 全文校验 | 全文件（丢注释/换行/缩进漂移） |
| unified diff hunk | $\sim150$（改动 + 3 行上下文） | 搜索-替换 | hunk 附近 |
| 锚点 + 旧/新片段（结构化） | $\sim120$ | 定位 + 替换 | 片段范围 |

**结论**：输出量降 40–50 倍，出错面从「整个文件」缩到「几十行」——这是「快」与「可靠」的同一个来源。

### 2. 两级匹配：精确 + 模糊

```
match(old, content):
  1) 精确子串匹配（含空白/换行规范化后比较）
     ├─ 命中 1 处 → 应用
     └─ 命中 >1 处 → 用上下文/行号消歧；仍歧义 → 报「需更多上下文」
  2) 规范化匹配：忽略行尾空白、统一 CRLF/LF、忽略尾部空行
  3) 缩进容错：把 old 与候选都按最小缩进对齐后比较（处理块被包裹进 if/for 的场景）
  4) 局部相似：在文件上滑窗做 LCS/编辑距离，取相似度 > 阈值（如 0.85）的最佳窗口
     └─ 低于阈值 → 失败，返回「期望片段 vs 最相近片段 + 差异摘要」
```

**歧义与误匹配的风险控制**：模糊匹配必须**同时满足**相似度阈值与「唯一最佳」条件；两个候选得分接近时必须放弃自动应用（宁可让模型重发）。

### 3. 失败即诊断：把错误变成可行动的输入

失败返回结构（示例）：

```json
{
  "status": "match_failed",
  "file": "src/auth.py",
  "hunk_id": "h3",
  "expected": "…6 行片段…",
  "closest": { "start_line": 118, "text": "…6 行片段…", "similarity": 0.72 },
  "diff_summary": "- return token\n+ return verify(token)",
  "hint": "该函数已被重命名/改写，请基于 closest 内容重新生成 hunk"
}
```

有了这个结构，模型重新生成的成功率远高于「重发整文件」；也便于人类快速判断。

### 4. 事务、幂等与并发

- **变更集**：所有 hunk 的 `old` 在**同一份快照**上匹配成功才提交（避免 hunk 之间互相影响导致的错位）；或者按顺序应用并允许后一个 hunk 基于前一个的结果匹配——两种策略都要显式选定并测试。
- **幂等**：hunk 带 id，已应用的 id 再次投递直接跳过（网络重试、流式重放都会触发重复）。
- **并发**：应用前比对快照哈希；不一致就走「重读 → 只重生成冲突 hunk」（串 [[cursor-12]]）。
- **回滚**：一个事务对应一个 undo 单元；失败时整体回滚。

### 5. 性能与可观测性

- 应用本身是**毫秒级**（字符串搜索 + 替换），瓶颈在模型输出与匹配歧义，而不是「写文件」；
- 需要监控：`apply_success_rate`（首次成功率）、`fuzzy_match_rate`（走了模糊匹配的比例）、`retry_count`（平均重试次数）、`rollback_rate`；首次成功率低于某阈值说明**提示/上下文组织**有问题，而不只是应用层问题。

## 数值与代码验证

### 表 1：三种输出形式对比（500 行文件、改 6 行）

| 形式 | 输出 token | 应用耗时 | 首次成功率（示例） | 主要失败模式 |
| --- | --- | --- | --- | --- |
| 整文件重写 | ~6,000 | 写 500 行（毫秒级）但需全文校验 | 低 | 丢注释、缩进漂移、被截断 |
| unified diff | ~150 | <1 ms（精确匹配） | 中高 | 上下文不匹配（文件已变） |
| 结构化 hunk + 模糊匹配 | ~120 | <1 ms + 模糊匹配（~1 ms/候选） | **高** | 歧义（需更多上下文） |

### 表 2：匹配失败的原因分布（工程经验口径，示意）

| 原因 | 占比（示意） | 对策 |
| --- | --- | --- |
| 空白/换行差异 | 35% | 规范化匹配 |
| 缩进变化（被包裹进新块） | 20% | 缩进容错 |
| 目标代码已被用户/其他 agent 改动 | 25% | 快照检查 + 重生成该 hunk |
| 模型记错内容（幻觉） | 15% | 失败诊断回灌 + 重试上限 |
| 歧义（多处相同） | 5% | 要求更多上下文（唯一性约束） |

**读法**：规范化与缩进容错能消掉一半以上的失败——这就是「两级匹配」的价值。

### 可运行代码

```python
# 可靠的 hunk 应用：精确 → 规范化 → 缩进容错 → 模糊（LCS 相似度），并给出诊断
import re, difflib

def norm_lines(s, strip_trailing=True, unify_nl=True):
    if unify_nl:
        s = s.replace("\r\n", "\n").replace("\r", "\n")
    lines = s.split("\n")
    if strip_trailing:
        lines = [l.rstrip() for l in lines]
    return lines

def dedent(lines):
    indents = [len(l) - len(l.lstrip()) for l in lines if l.strip()]
    k = min(indents) if indents else 0
    return [l[k:] if len(l) >= k else l for l in lines]

def similarity(a, b):
    return difflib.SequenceMatcher(None, a, b).ratio()

def find_hunk(content, old, min_sim=0.85):
    """返回 (start_line, end_line, how, similarity) 或 (None,None,'not_found',sim)"""
    c_lines, o_lines = norm_lines(content), norm_lines(old)
    n, m = len(c_lines), len(o_lines)
    # 1) 精确
    for i in range(n - m + 1):
        if c_lines[i:i+m] == o_lines:
            return i, i+m, "exact", 1.0
    # 2) 缩进容错
    o_ded = dedent(o_lines)
    for i in range(n - m + 1):
        if dedent(c_lines[i:i+m]) == o_ded:
            return i, i+m, "dedent", 1.0
    # 3) 模糊：滑窗取最佳相似度
    best, best_i = 0.0, None
    for i in range(n - m + 1):
        s = similarity(c_lines[i:i+m], o_lines)
        if s > best:
            best, best_i = s, i
    if best >= min_sim and best_i is not None:
        return best_i, best_i+m, "fuzzy", best
    return None, None, "not_found", best

class ApplyError(Exception):
    def __init__(self, info): self.info = info

def apply_hunks(content, hunks, min_sim=0.85, strict=True):
    """strict=True：全部 hunk 可匹配才提交（原子）"""
    plan, diag = [], []
    for h in hunks:
        s, e, how, sim = find_hunk(content, h["old"], min_sim)
        if s is None:
            closest = "\n".join(norm_lines(content).__getitem__(slice(max(0,(s or 0)), (s or 0)+len(norm_lines(h["old"])))))
            diag.append({"hunk_id": h["id"], "status": "match_failed",
                         "similarity": round(sim, 3), "expected": h["old"].strip()[:80]})
        else:
            plan.append((s, e, h, how, sim))
    if diag and strict:
        raise ApplyError({"status": "aborted", "diagnostics": diag})
    out_lines = norm_lines(content)
    for s, e, h, how, sim in sorted(plan, key=lambda x: -x[0]):
        out_lines[s:e] = norm_lines(h["new"])
    return "\n".join(out_lines), [{"hunk_id": h["id"], "how": how, "sim": round(sim,3)} for _,_,h,how,sim in plan]

FILE = """def verify(token):
    return token == SECRET

def refresh(token):
    if not token:
        return None
    return issue(token)
"""
HUNKS = [
    {"id": "h1", "old": "def refresh(token):\n    if not token:\n        return None\n    return issue(token)",
     "new": "def refresh(token):\n    if not token:\n        return None\n    return issue(token, ttl=3600)"},
]
new, meta = apply_hunks(FILE, HUNKS)
print("应用成功：", meta)
print(new.split("\n")[-1])

# 空白/缩进差异场景
FILE2 = FILE.replace("    return token == SECRET", "    return token == SECRET   ")     # 行尾空白
new2, meta2 = apply_hunks(FILE2, HUNKS)
print("行尾空白场景：", meta2)

FILE3 = "if True:\n" + "\n".join("    "+l for l in FILE.split("\n"))                  # 整体多缩进一级
new3, meta3 = apply_hunks(FILE3, HUNKS)
print("整体缩进场景：", meta3)

# 失败诊断场景（内容被改写）
FILE4 = FILE.replace("return issue(token)", "return issue_token(token)")
try:
    apply_hunks(FILE4, HUNKS)
except ApplyError as e:
    print("失败诊断：", e.info)

# 成本对比：整文件重写 vs hunk
def tokens(text): return len(re.findall(r"\S+", text))
print(f"\n整文件重写输出 ≈ {tokens(FILE)*3} token（含上下文冗余估计）")
print(f"hunk 输出 ≈ {tokens(HUNKS[0]['old']+HUNKS[0]['new'])*1} token"
      f" → 省 {1 - tokens(HUNKS[0]['old']+HUNKS[0]['new'])/(tokens(FILE)*3):.1%}")
```

预期输出要点：精确匹配直接命中；行尾空白场景走规范化后命中；整体缩进场景走缩进容错命中；内容被改写时抛出**带诊断结构**的失败（而不是静默改错位置）；成本对比显示 hunk 输出比整文件重写省一个数量级以上的 token。

## 常见追问

- **追问**：多个 hunk 之间会互相影响吗？
  - 要点：会。两种策略：① 全部基于同一快照匹配、按位置从后往前应用（互不影响）；② 顺序应用并逐个重新匹配。要显式选择并测试；默认推荐 ①（可预测）。
- **追问**：模糊匹配会不会改错位置？
  - 要点：三道限制——相似度阈值、唯一最佳（次优差距要够大）、以及应用后跑语法校验；不确定就转人工确认，不自动应用。
- **追问**：模型连续多次匹配失败怎么办？
  - 要点：重试上限（如 2 次）+ 每次把诊断（closest 片段 + diff）回灌；仍失败则降级为「展示建议 + 人工应用」，并记录为模型/上下文问题的样本。
- **追问**：为什么不直接让模型输出 patch（unified diff）？
  - 要点：可以，且是常见做法；但 diff 的行号与上下文同样会失效，所以**匹配逻辑仍不可少**。结构化 hunk 的好处是可以携带锚点与语义信息，并能单独重试。
- **追问**：应用性能的瓶颈在哪？
  - 要点：字符串搜索是毫秒级；真瓶颈在**模型输出 token 数**与**匹配失败后的重试**。所以优化方向是「让模型少输出、让第一次就匹配上」（更好的上下文与格式约束）。
- **追问**：怎么衡量「应用」这一环的质量？
  - 要点：首次成功率、模糊匹配率、平均重试次数、回滚率、以及应用后的语法/测试通过率；这些指标与模型质量分开看，才能定位问题在提示、上下文还是应用层。
