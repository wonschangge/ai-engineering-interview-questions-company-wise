## 一句话答案

> 这个问题有三个层次，必须分开答，否则会被追问到崩：
> ① **成本**——上下文是**按 token 计价且每次请求重复计价**的。10 万文件的 monorepo 是亿级 token 量级，每次请求都塞进去，单次成本与延迟都不可接受（下一节的账）。
> ② **质量**——「能塞进去」不等于「能用上」。可引用的实证是 *Lost in the Middle*：当相关信息位于长上下文的**中间位置**时，模型的表现会明显下降（作者在多种输入长度与位置下系统评估了这一现象并给出 U 形曲线），也就是说**把仓库塞满反而可能降低准确率**。
> ③ **工程**——即使不计成本，也要解决「哪一份代码是当下相关的」「改了代码索引怎么跟上」「上下文里放什么形式（原文 / 摘要 / 符号签名）」这些问题；这些正是 retrieval 在做的事。
> 所以正确姿势不是二选一，而是**分层**：检索负责把候选缩到「够小且够准」，长上下文负责在候选内做深度推理；并且用**缓存**（前缀缓存 / 提示缓存）把重复的仓库片段成本摊掉。一句话：**retrieval 的价值不是「省 token」，而是「把注意力放在对的地方」。**

## 面试官在考什么

- 是否会**算成本**而不是只说「太贵了」：给出 token 量级、单次请求成本、以及按 DAU 折算的日成本——这是这道题的第一道分水岭。
- 是否知道**长上下文的质量问题**：能说出 lost-in-the-middle 的 U 形现象及其对工程的含义（重要信息要放头尾、要做重排、不要指望「全塞进去自己找」）。
- 是否理解 retrieval 的**真实职责**：候选生成（召回）、重排（精排）、以及**上下文组装**（按依赖关系排序、去重、裁剪、标注来源）——最后一件事常被忽略，但它是代码场景的关键（改一个函数要带上它的调用方与被调用方）。
- 是否知道**缓存**能把长上下文的成本结构改掉：前缀缓存（同一仓库前缀复用 KV）把「重复部分」的成本从 O(n) 降到接近 O(Δ)（串 [[inference-serving-05]]、[[cursor-06]]）。
- 能否给出**混合策略**：静态索引（仓库级）常驻缓存 + 动态检索（当前任务相关）+ 编辑历史（最近改动）。

**常见错误答案**

- 「上下文便宜了，直接全塞」——没算按 DAU 折算的账，也没考虑 TTFT 与延迟。
- 「长上下文会让 retrieval 消失」——忽略注意力稀释与位置偏差（中间信息利用率低）。
- 「retrieval 就是向量检索」——代码场景里符号级检索（定义/引用/调用图）往往比向量检索更准。
- 「把整个仓库塞进去还能保证一致」——上下文被截断时的行为不可预测（哪里被截掉决定了答案质量）。

## 原理与推导

### 1. 成本账：为什么「全塞」在代码场景最先崩

设 monorepo 有 $F$ 个文件、平均每文件 $L$ 行、每行约 $c$ token。则仓库原文 token 量

$$N_{\text{repo}}\approx F\cdot L\cdot c$$

取 $F=10^5$、$L=200$、$c\approx 8$（代码行平均 token 数取整后偏保守）：$N_{\text{repo}}\approx1.6\times10^{8}$ token ——**一亿六千万 token**，远超任何当前商用模型的窗口。

再按请求计价：假设每次请求都要重新发送 $N$（没有缓存）、单价 \$3/百万输入 token，则单次 **\$480**；若按每天 100 万次请求计，**每天 4.8 亿美元**——这个数量级本身就说明「全塞」不是选项。

用检索把上下文降到 $N'\approx2\times10^4$ token（两个文件 + 相关片段 + 指令），单次成本降到 **\$0.06**，即使算上检索系统的开销（embedding 查询 + 重排）仍便宜三个数量级。**这就是 retrieval 的第一层价值。**

### 2. 质量账：能塞进去 ≠ 能用上

可引用的实证来自 *Lost in the Middle*：模型对上下文**不同位置**的信息利用率不同——放在开头与结尾的信息更容易被用上，放在中间的信息容易被忽略（论文在不同长度与位置组合下系统测量了这一效应）。工程含义有四条：

1. **关键信息放头尾**（指令放开头、最相关代码放结尾）；
2. **不要用「堆量」替代「选准」**——相关但冗余的片段会稀释注意力；
3. **重排（rerank）比扩大召回更重要**：把最相关的排到两端；
4. **要给模型「指针」**：文件路径 + 行号 + 符号名，让它能主动再取（工具调用）而不是被动读完。

### 3. 代码场景里 retrieval 到底在做什么

| 层 | 做什么 | 代码场景的特殊性 |
| --- | --- | --- |
| 符号层 | 定义、引用、调用图、类型关系 | 精确、便宜、可增量更新；**优先于向量检索** |
| 词法层 | 关键词/正则/文件名匹配 | 找配置、找字符串、找日志 |
| 向量层 | 语义相近的代码片段（注释、命名不同但语义相同） | 处理「不知道叫什么」的场景 |
| 结构层 | 目录/模块/包边界 | 决定上下文组装顺序与裁剪优先级 |
| 历史层 | 最近改动、当前 diff、相关 PR/issue | 决定「用户此刻在做什么」 |

**上下文组装（context assembly）**才是最终交付物：按依赖顺序排列（被调用的在前、调用的在后）、去重（同一函数别出现三次）、裁剪（超预算时按相关性降级）、标注来源（可点击的路径/行号）。

### 4. 缓存：把长上下文从「每次付费」变成「一次付费 + 增量」

前缀缓存（prompt caching）让**相同前缀**的 KV 被复用，按 token 计费的系统通常对缓存命中的部分给大幅折扣。在编辑器场景里，前缀往往高度重复（系统提示 + 仓库骨架 + 最近编辑文件的稳定部分），所以：

- 静态部分（仓库摘要、符号表）常驻缓存；
- 动态部分（当前文件、光标附近、检索结果）每次变化；
- 用户连续输入时，前缀几乎不变 → 单位成本与 TTFT 都显著下降（串 [[cursor-06]] 的成本模型与抓手）。

这也解释了为什么「长上下文越来越便宜」这个前提在**交互式、高 QPS** 的场景里并不自动成立：便宜的是**缓存命中的 token**，不是「每次都重新处理的 token」。

### 5. 什么时候真的可以「不检索」

诚实地给出边界条件：

- 仓库很小（例如数千行脚本）→ 全塞确实可行；
- 任务**只依赖当前文件**（格式化、局部重构）→ 不需要仓库级检索；
- 已有强缓存且请求前缀稳定 → 可以把「全仓摘要」放进缓存，但**仍然要选片段**（窗口有限）；
- 任务是「全局理解」（例如「这个仓库的架构是怎样的」）→ 需要**分层摘要**（目录级 → 模块级 → 文件级），而不是把原文塞进去。

## 数值与代码验证

### 表 1：三种上下文策略的成本与质量对照

| 策略 | 上下文 token | 单次成本（\$3/M） | TTFT 影响 | 质量风险 |
| --- | --- | --- | --- | --- |
| 全仓原文 | $1.6\times10^{8}$（不可行） | \$480 | 不可接受 | 截断后行为不可预测 |
| 全仓摘要（目录+符号+签名） | $\sim2\times10^{5}$ | \$0.60 | 秒级 | 细节缺失（实现体不可见） |
| 检索后组装 | $\sim2\times10^{4}$ | \$0.06 | 百毫秒级 | 召回漏掉关键依赖（要靠图补） |
| 检索 + 前缀缓存命中 80% | 有效新增 $\sim4\times10^{3}$ | **\$0.01 量级** | 十毫秒级 | 同「检索后组装」 |

口径：token 单价与缓存折扣为示例值（不同厂商差异大）；仓库规模取 $10^5$ 文件 × 200 行 × 8 token/行。

### 表 2：位置效应（lost-in-the-middle）对组装的启示

| 信息放置位置 | 模型利用率（论文口径：相对首尾更低） | 工程动作 |
| --- | --- | --- |
| 上下文开头 | 高 | 放指令与约束 |
| 中间 | **低** | 不放关键代码；放可跳过的参考 |
| 结尾 | 高 | 放最相关的代码与「请在此处修改」 |

### 可运行代码

```python
# 1) 全塞 vs 检索的成本账（含按 DAU 折算）
TOK_PER_LINE, PRICE_PER_M = 8, 3.0
def repo_tokens(files, lines_per_file=200):
    return files * lines_per_file * TOK_PER_LINE

def daily_cost(tokens_per_req, req_per_day, cache_hit=0.0, cache_discount=1.0):
    eff = tokens_per_req * (1 - cache_hit) + tokens_per_req * cache_hit * cache_discount
    return eff / 1e6 * PRICE_PER_M * req_per_day, eff

reqs = 1_000_000
for name, files, cache in [("全仓原文", 100_000, 0.0), ("全仓摘要", 100_000, 0.0),
                           ("检索组装", 100_000, 0.0), ("检索 + 80% 缓存命中", 100_000, 0.8)]:
    if name == "全仓原文":
        tok = repo_tokens(files)
    elif name == "全仓摘要":
        tok = 200_000
    else:
        tok = 20_000
    c, eff = daily_cost(tok, reqs, cache, 0.1)
    print(f"{name:<20} 上下文 {tok:>12,.0f} token  有效 {eff:>12,.0f}  日成本 ${c:>12,.0f}")

# 2) 上下文预算分配：把固定窗口切成几块（示意权重）
BUDGET = 20_000
ALLOC = [("系统提示与规则", 0.05), ("当前文件（光标附近）", 0.30), ("检索到的相关片段", 0.40),
         ("依赖符号定义", 0.15), ("最近编辑历史/diff", 0.10)]
print("\n上下文预算分配（总额 20,000 token）")
for name, w in ALLOC:
    print(f"  {name:<22} {w:>5.0%}  {int(BUDGET*w):>7,d} token")

# 3) 位置效应的最小模拟：把「最相关片段」放不同位置，观察答案命中的概率假设
import random
random.seed(83)
def hit_prob(pos_frac, base=0.85, dip=0.35, width=0.35):
    """U 形：首尾高、中间低（形状为示意，用途是演示组装策略的影响）"""
    d = abs(pos_frac - 0.5) / 0.5
    return base - dip * (1 - d) ** (1/width)
print("\n位置 -> 命中概率（示意模型）")
for pos in (0.0, 0.1, 0.3, 0.5, 0.7, 0.9, 1.0):
    print(f"  放置在 {pos:>4.0%} 处：命中概率 {hit_prob(pos):.3f}")
print("把最相关片段放在结尾（或开头）而不是中间，是零成本的收益提升 —— 这是组装策略的意义")
```

预期输出要点：成本表显示四种策略相差**四个数量级**（全仓原文日成本 $\sim4.8\times10^8$ 美元，检索 + 缓存约 \$1 万量级）；预算分配表给出一个可直接使用的窗口切分模板；位置效应演示说明「同样内容放在不同位置，命中概率不同」——这是「检索 + 组装」相对「全塞」的第二层价值。

## 常见追问

- **追问**：那长上下文的意义是什么？
  - 要点：在**候选已经收敛**之后做深度推理（例如一次改 10 个文件、跨文件重构），以及承载「摘要 + 符号表」这类中等规模的全局信息。检索负责缩小范围，长上下文负责在范围内推理。
- **追问**：代码检索该用向量还是符号索引？
  - 要点：优先符号索引（精确、可增量、可解释），向量用于「语义相近但命名不同」的场景；两者融合后重排。纯向量在代码上经常输给「grep + 语法树」。
- **追问**：怎么评估「检索 vs 全塞」哪个更好？
  - 要点：用同一批任务做对照（同一模型、同一预算），指标看任务成功率与编辑正确率，同时记录 token 成本与 TTFT；可引用的仓库级补全评测口径见 RepoBench（串 [[cursor-15]] 的离线评测设计）。
- **追问**：如何避免召回漏掉关键依赖？
  - 要点：用调用图/引用图做**一跳或两跳扩展**（改了函数就带上调用方与被调用方）、把当前编译/测试错误信息作为检索信号、并在生成后做静态检查（缺符号就报错重试）。
- **追问**：上下文里放原文还是摘要？
  - 要点：要改的代码放原文（实现体），被依赖的符号放签名 + 简要注释，历史放 diff。放摘要的地方要标注「这是摘要，需要时可展开」——给模型一个取回原文的动作。
- **追问**：缓存会不会导致「用户编辑后模型仍看旧内容」？
  - 要点：会，这是缓存失效问题。做法是按内容哈希切分前缀（编辑使哈希变化的部分自动失效）、只缓存稳定段（规则、仓库骨架）、并在响应里标注所用上下文的版本。
