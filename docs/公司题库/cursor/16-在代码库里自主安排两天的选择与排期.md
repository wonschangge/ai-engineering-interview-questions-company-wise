## 一句话答案

> 这道题考的不是「你有多能干」，而是**在没有指令时你如何选择做什么、如何控制风险、如何把成果交出去**。可辩护的答案是三段式：
> ① **第一天上午：把环境跑起来 + 建地图**——目标是「能让代码在我机器上构建、测试、运行」，并画出三张图：模块边界与依赖方向、数据/请求的主链路、以及 CI 与发布的关卡。**跑不起来就不动手改任何代码**（否则你无法验证自己的改动）。
> ② **第一天下午：找痛点，用四个标准打分**——高频（多少人每天遇到）、高痛（浪费多少时间）、低风险（改动面小、可回滚）、可验证（有明确判据）。然后**只选一个**，写下「我打算证明什么」。
> ③ **第二天：做最小可交付 + 交付说明**——一个小工具/一个测试修复/一段文档/一个已定位的 bug 修复，配 PR 说明（改了什么、为什么、怎么验证、后续建议）；把探索笔记留成对团队有用的东西（runbook、上手文档补丁、失败用例）。
> 一句话原则：**两天里最有价值的产出不是代码量，而是「一个可验证的小交付 + 一份别人能接手的说明」。**

## 面试官在考什么

- **主动性 vs 纪律的平衡**：既不能等任务，也不能一上来就重构。会不会先证明「我能跑通这套系统」，再动手。
- **选择标准是否可解释**：能否给出打分的维度（频率、痛苦、风险、可验证性），而不是凭直觉挑一个「看起来很酷」的东西。
- **工程习惯**：小步提交、可回滚、改动带测试、遵循既有约定（而不是引入个人偏好）；可引用的工程取向来自 Google 的规则清单——先把管道和基线做对，再考虑复杂改动。
- **交付与协作**：会不会写清楚的 PR 说明、留痕、主动同步给相关人；还是自己闷头做完没人知道。
- **对「两天」的现实感**：两天内不可能完成大重构；能主动缩小范围（这也是判断力的体现）。
- **与公司相关**：如果候选人对代码库/产品有具体观察（例如「你们的某文档与代码不一致」「某个测试 flaky」），加分很多；空泛的「我会学习代码库」是最低分答案。

**常见错误答案**

- 「先花两天读代码，读懂了再说」——两天结束没有任何可验证产出。
- 「我要重构 X 模块」——两天做不完，还可能引入风险。
- 「我随便修几个 typo」——没有价值判断，也没有选择标准。
- 「我不知道，等你们安排」——直接暴露主动性不足。

## 原理与推导

### 1. 两天的时间盒（可执行的排期）

| 时段 | 目标 | 产出 |
| --- | --- | --- |
| D1 09:00–11:00 | 环境跑通 | 构建 + 测试 + 本地运行成功（记录踩坑） |
| D1 11:00–13:00 | 建地图 | 模块/依赖图、主链路、CI 关卡（笔记） |
| D1 14:00–16:00 | 找痛点并打分 | 候选清单 + 打分表 + 选定一个 |
| D1 16:00–18:00 | 验证假设 | 复现问题（有判据：测试/脚本/日志） |
| D2 09:00–13:00 | 实现最小修复/工具 | 可运行代码 + 测试 |
| D2 14:00–16:00 | 自测 + 边界 | 通过 CI；记录未覆盖部分 |
| D2 16:00–18:00 | 交付与留痕 | PR + 说明 + 上手文档补丁 + 后续建议 |

**关键约束**：D1 结束前必须有「一个已被复现的具体问题」——复现本身就是最有价值的探索产出（它把主观感受变成客观事实）。

### 2. 痛点打分的四个维度

对每个候选用 1–5 分打分（权重可按团队目标调整）：

$$\text{优先级}=w_1\cdot\text{频率}+w_2\cdot\text{痛苦}+w_3\cdot(6-\text{风险})+w_4\cdot\text{可验证性}$$

**风险**取反是因为两天内不该碰高风险改动（例如核心路径重构、跨服务接口变更）。可验证性单独列出来，是因为**无法验证的改动在两天里等于赌博**。

### 3. 交付物的形态（按价值密度排序）

1. **一个已复现 bug 的最小修复**（带回归测试）——价值明确、可验证、可回滚；
2. **一个开发者效率小工具**（例如「本地一键复现某个 CI 失败」的脚本）——高频痛点、零生产风险；
3. **测试/CI 改进**（修 flaky 测试、补关键路径用例）——直接降低团队未来的时间损失；
4. **文档补丁**（上手文档、runbook）——最容易被忽视，但对新人价值极高；
5. **一份有证据的调研报告**（例如「某模块的性能瓶颈在 X，附 profiling 数据」）——没有代码产出但有决策价值。

**反例**：大型重构、引入新框架、改公共接口——两天内交付不了，且会留下半成品。

### 4. 留痕与协作（决定成果能否被吸收）

- **PR 说明四段**：改了什么 / 为什么（复现步骤与证据）/ 怎么验证（命令与预期输出）/ 后续建议（下一步可以做什么）；
- **同步**：在团队频道说明你在做什么（避免重复劳动）、结束后贴出结论；
- **不制造负担**：改动遵循既有风格与约定；能自动化就不加人工流程。

## 数值与代码验证

### 表 1：候选痛点打分示例（演示打分法，不是真实数据）

| 候选 | 频率 | 痛苦 | 风险（低好） | 可验证性 | 加权分 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| 本地跑不起某个集成测试 | 5 | 5 | 5 | 5 | **高** | 选它（先复现，再修/加脚本） |
| 核心模块重构成新架构 | 2 | 3 | 1 | 2 | 低 | 不选（两天做不完） |
| 文档里的上手步骤过期 | 4 | 3 | 5 | 4 | 中高 | 备选（半天可完成） |
| 引入新框架替换旧工具 | 1 | 2 | 1 | 1 | 极低 | 不选 |

### 表 2：两天产出的价值估算（示例）

| 产出 | 收益估算 | 依据 |
| --- | --- | --- |
| 修一个 flaky 测试 | 每次误报约 15 分钟 × 每周 3 次 × 团队 10 人 ≈ **7.5 人·小时/周** | 需实测误报频率 |
| 一键复现脚本 | 每次排障省 30 分钟 × 每周 5 次 ≈ **2.5 人·小时/周** | 用日志统计 |
| 上手文档补丁 | 每个新人省 4 小时 × 每季度 2 人 ≈ **1 人·小时/周** | 估 |

**读法**：把「两天做了什么」换算成「团队每周省多少时间」，是把个人探索变成可评估贡献的最直接方式。

### 可运行代码

```python
# 用打分法选出两天内该做的事（可复用的决策脚本）
import itertools

CRITERIA = [("频率", 0.30), ("痛苦", 0.30), ("低风险", 0.20), ("可验证性", 0.20)]

def score(cand):
    return sum(cand[k] * w for k, w in CRITERIA)

candidates = {
    "本地跑不起集成测试": {"频率": 5, "痛苦": 5, "低风险": 5, "可验证性": 5, "工时": 10},
    "文档上手步骤过期":   {"频率": 4, "痛苦": 3, "低风险": 5, "可验证性": 4, "工时": 4},
    "flaky 测试修复":     {"频率": 5, "痛苦": 4, "低风险": 4, "可验证性": 5, "工时": 8},
    "核心模块重构":       {"频率": 2, "痛苦": 3, "低风险": 1, "可验证性": 2, "工时": 80},
    "引入新框架":         {"频率": 1, "痛苦": 2, "低风险": 1, "可验证性": 1, "工时": 120},
}
BUDGET_H = 16
print(f"{'候选':<22} {'加权分':>7} {'工时(h)':>8} {'两天内可完成':>12}")
for name, c in sorted(candidates.items(), key=lambda kv: -score(kv[1])):
    ok = "✓" if c["工时"] <= BUDGET_H else "✗"
    print(f"{name:<22} {score(c):>7.2f} {c['工时']:>8} {ok:>12}")
print(f"\n在 {BUDGET_H} 小时预算内、加权分最高的是：",
      max((n for n, c in candidates.items() if c["工时"] <= BUDGET_H), key=lambda n: score(candidates[n])))

# 把产出换算成团队时间收益
def weekly_saving(per_occurrence_min, occurrences_per_week, people=10):
    return per_occurrence_min * occurrences_per_week * people / 60
print(f"\n修 flaky 测试（每次误报 15 min、每周 3 次、10 人）："
      f"{weekly_saving(15, 3):.1f} 人·小时/周")
print(f"一键复现脚本（每次省 30 min、每周 5 次、10 人）："
      f"{weekly_saving(30, 5):.1f} 人·小时/周")
print("面试时把两天产出换算成「团队每周省多少时间」，比说「我修了个 bug」有力得多")
```

预期输出要点：打分脚本自动排除「工时超过预算」的高分候选（例如核心重构即使看起来重要也不该在两天里动），并在预算内选出最高分项；时间收益换算把「两天工作量」翻译成团队可感知的价值（每周若干人·小时）。

## 常见追问

- **追问**：如果两天结束时问题还没修好怎么办？
  - 要点：交付「已验证的复现 + 根因分析 + 修复方案 + 我改到哪一步」——**未完成但有证据的进展**依然有高价值；避免留下半成品代码（用分支隔离，不合并未完成改动）。
- **追问**：你选的东西团队觉得不重要怎么办？
  - 要点：这正是「打分表 + 证据」的价值——把频率与痛苦量化，让讨论基于数据；同时保持小范围（不阻塞别人），并在完成后主动请教是否值得继续。
- **追问**：怎么在两天里避免破坏别人的工作？
  - 要点：小步提交、分支隔离、不碰公共接口与发布流程、改动带测试；高风险动作先问（串 [[cursor-08]] 的隔离与可回滚原则）。
- **追问**：你会先读文档还是先跑代码？
  - 要点：**并行**——先按文档把环境跑起来（文档的正确性本身就是第一个发现），跑不通就读代码找真相；「文档写着能跑但跑不起来」往往就是最高价值的痛点。
- **追问**：如果你发现的是产品/架构层面的问题（两天修不了）怎么办？
  - 要点：写成有证据的短报告（问题、影响、证据、可选方案与代价），交给 owner；这也是交付（决策价值），不是「什么都没做」。
- **追问**：怎么让团队知道你做了什么？
  - 要点：PR 说明 + 团队频道同步 + 更新相关文档/runbook；把成果放进团队已有的流程里，而不是另起一套。
