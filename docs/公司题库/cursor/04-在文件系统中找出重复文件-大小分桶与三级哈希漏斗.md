## 一句话答案

> 契约先于代码：重复 = byte-identical。同一 `(st_dev, st_ino)` 的多条路径是别名而不是重复——本机夹具里 2000 个目录项只对应 100 个 inode，不剔别名会让 2000 条路径全部进候选、被内容哈希报成 100 个各 20 条路径的重复组，剔掉别名后剩 100 个 inode、落进 2 个 size 桶（10 B 桶 10 个、11 B 桶 90 个）、内容哈希后一个重复组都没有；符号链接默认不跟随（要跟随就得带 visited set，本机 3 个自指链接在 5.0 s 内已访问 76,781 个目录项且仍未结束），权限错误与扫描中消失的文件记 skipped 计数，空文件单独定语义（300 个空文件会组成 1 个 0 字节、300 条路径的巨型组）。
> 实现固定为三级漏斗：size 分桶 → 头部哈希（4 KiB，只为剪枝，key 必须带长度）→ 全内容流式哈希（1 MiB 块喂 hashlib，峰值内存与文件大小解耦）。本机合成树（4000 文件 / 117.29 MB / 2805 个不同 size）实测：4000 → 1849（占原本 46.2%）→ 1684（占 42.1%），全量哈希 74.0 ms 得到 602 组、重复字节 30.40 MB（25.9%），读放大 0.605×；同一批实验里若所有文件同尺寸，size 阶段的剪枝率是 0%，所以剪枝率必须实测而不是假设。
> 哈希选型是唯一「选错就静默丢数据」的地方：SHA-1 已有构造性碰撞（SHAttered）、MD5 更早，都只能用于非对抗校验；用 SHA-256 或 BLAKE3 并把 32 B digest 全量存、全量比。64 位截断在 $10^6$ 文件上的生日上界是 $2.7 \times 10^{-8}$，对非对抗输入够用，但 Cursor 的输入是不可信仓库与用户工作区，对抗性构造下截断不成立，而下游动作往往是删掉除代表之外的所有副本。
> 规模要按字节记账：$10^5$ 文件级可以全常驻（本机实测 digest → 计数 13.9 MiB），$10^6$ 走两遍法——第一遍只累计 digest → 出现次数（128.7 MiB，不存路径），第二遍只对 count ≥ 2 的内容重读一遍产出分组。精确哈希只解决 byte-identical，近重复（改一行、vendored 依赖、lockfile）要按内容定义分块，只有语义近重复才上向量；「报告」可以用近似，「删除」必须精确并留一次人工确认。

## 面试官在考什么

- **契约是否先于代码**：什么算重复（byte-identical）、硬链接别名、符号链接是否跟随、权限与消失文件怎么办、空文件算不算、组内谁当 representative、输出怎么排序。这七项没写死，剩下的代码写得再漂亮也是在回答另一个问题。
- **漏斗是不是真的逐级变廉价**：size 只看元数据（0 字节读取）、头部哈希只读 4 KiB、全量哈希才读完整文件；并且剪枝率是量出来的（读放大 = 实际读取字节 ÷ 全库字节），而不是「先用 size 过滤一下总没错」。
- **哈希的正确性边界**：为什么 SHA-1 / MD5 不能用于去重、为什么 digest 不能截断到 8 字节、为什么前缀哈希不能作为相等判据（前缀相同、长度不同的两个文件前缀哈希一致，长度必须进 key）、最终分组为什么只能用全内容哈希。
- **流式读取与失效场景**：大文件按块喂 hashlib 而不是 `read()` 整读；在已打开的 fd 上前后两次 `fstat` 核对 size/mtime（watcher 与用户按键会持续改文件，这不是理论风险）；并发有界（8~32 个 worker）且整条扫描可取消，不阻塞编辑器 UI 或事件循环。
- **内存与落盘的口径**：$10^5$ / $10^6$ 两档的常驻内存、是否落盘（sqlite / RocksDB 存 digest → 路径）、以及「按字节记账而不是按条数记账」。
- **是否把「报告」和「删除」分开**：近似召回漏一个只是少省一点钱，用近似结果去做删除决策会删掉唯一副本。

常见错误答案：

- 上来就「遍历所有文件算 SHA-256，再用 `defaultdict(list)` 按 digest 分组」。它没有契约（硬链接、符号链接、空文件、待删除副本的裁决全缺）、没有漏斗（对几万个唯一 size 的文件白读一遍全量字节）、也没有内存口径（路径表随文件数线性膨胀）。
- 拿便宜的前缀哈希或内置 `hash()` 当判等依据。CPython 对 str 的哈希按进程随机加盐，同一棵树两次运行的 key 不同；而前缀哈希把「前缀相同、长度不同」的两个文件判成相等，等于把一份 JSON 截断版和完整版合并成一组。

## 原理与推导

### 1. 契约：先把「算不算重复」写成规则

| 契约项 | 默认取值 | 不写死会发生什么 |
| --- | --- | --- |
| 重复定义 | 内容 byte-identical（长度相同且每个字节相同） | 「名字一样」「大小一样」「前缀一样」都会被当成重复，静默合并不同文件 |
| 硬链接 | 同一 `(st_dev, st_ino)` 只保留一条路径进候选，其余记为别名 | `cp -l` 铺开的 monorepo 被报成「整仓都是重复」：本机 2000 目录项 / 100 inode 的夹具里，不剔别名时 2000 个目录项 100% 进候选、被内容哈希报成 100 组 × 20 条路径 |
| 符号链接 | 默认不跟随，单独统计 | 跟随就必须带 visited set 与跨挂载点限制：3 个自指链接在 5.0 s 内已访问 76,781 个目录项仍未结束 |
| 权限与竞态 | 记 skipped（errno 13 等）而不是抛异常中断整趟扫描 | 一个 0 权限文件或扫描中消失的文件会让整个索引任务失败 |
| 空文件 | 显式二选一：跳过 size = 0，或单列一类并标记 | 300 个 `.gitkeep` / `__init__.py` 会组成 1 个 0 字节、300 条路径的巨型组 |
| 输出 | 组内路径排序、组间按 `(size, digest)` 排序、显式给 representative | 快照测试与「按内容哈希做缓存键」不可复现 |
| representative | 保留谁：mtime 最新、路径最短、非 symlink（规则可换，但必须写下来） | 删除类动作由遍历顺序决定，同一份报告在两次运行里给出不同建议 |

确定性是可测的：把 `os.scandir` 的目录项 shuffle 之后再跑一遍，602 个分组逐位一致，说明输出只依赖内容与显式排序键，不依赖遍历顺序。

### 2. 三级漏斗：每一级只做减法，只有最后一级能判等

```
size 分桶（只读元数据）→ 头部哈希（4 KiB，只为剪枝）→ 全内容流式哈希（唯一判据）
```

三条实现规则：

1. **用 `os.scandir` + 缓存好的 `DirEntry.stat()`**，不要 `os.walk` 再对每个文件 `os.path.getsize`。本机 20,000 文件实测：scandir 路径 3.95 µs/文件，walk + getsize 5.14 µs/文件（1.30×），外推到 $10^6$ 文件是 3.95 s 对 5.14 s，差的那 1.2 s 完全是重复的 syscall。
2. **头部哈希只用于剪枝**，key 必须是 `(size, sha256(head))`。前缀相同、长度不同的两个文件前缀哈希一致，长度不进 key 就会把它们配对；而即便 key 配对成功，也最多说明「值得继续读」，不能说明相等。
3. **最终分组只用全内容流式哈希**，按 1 MiB 块喂 hashlib，峰值内存是块大小而不是文件大小。

剪枝率是语料形状的函数，不能假设。本机三组语料（同一套代码）：

| 语料 | 形状 | size 阶段 | 头部阶段 | 全量读取 | 读放大 |
| --- | --- | --- | --- | --- | --- |
| A | 4000 文件 / 117.29 MB / 2805 个不同 size，含 602 个精确重复家族 | 4000 → 1849 | 1849 → 1684 | 63.42 MB | 0.605× |
| B | 4000 个 16 KiB 文件，内容两两不同（量化权重分片、批量截图） | 4000 → 4000（0%） | 4000 → 0 | 0 MB | 0.250× |
| C | 4000 个 16 KiB 文件，共享同一个 4 KiB 格式头（日志分片） | 4000 → 4000（0%） | 4000 → 4000（0%） | 65.54 MB | 1.250× |

语料 C 是这道题最该讲的反例：同尺寸 + 同头部时前两级一分钱都省不下来，只能老老实实读完整字节；语料 A 的 0.605× 则说明漏斗在「大量唯一 size 文件」的仓库里确实把读取量砍掉近四成。

### 3. 哈希选型：碰撞在这里等于删数据

hash 相等被当成内容相等之后，下游动作常常是「删掉除 representative 之外的所有副本」，所以一次碰撞就删掉一份唯一内容。

| 选择 | 结论 | 依据 |
| --- | --- | --- |
| MD5 / SHA-1 | 不用于去重 | 两者都有公开的构造性碰撞（SHA-1 的 SHAttered），去重场景的输入来自不可信仓库 |
| SHA-256 / BLAKE3 | 默认选择 | 32 B digest，抗碰撞；SHA-256 有 SHA-NI 硬件加速，本机 1707 MB/s |
| 截断到 8 字节 | 只在非对抗场景可接受 | 生日上界 $(10^6)^2 / 2^{65} \approx 2.7 \times 10^{-8}$，但对抗性构造下不成立，省下的内存不多 |

省下的内存确实不多：8 B digest 相对 32 B 在 $10^6$ 条上省 24 B/条，按本机实测的 134.9 B/条是约 23 MiB（18%），代价是把「几乎不可能」换成「可以被构造」，不划算。

吞吐不是瓶颈，但也别凭直觉选算法。本机 hashlib 实测（512 MiB 缓冲、取三次最好）：

| 算法 | 吞吐 | digest |
| --- | --- | --- |
| SHA-256 | 1707 MB/s | 32 B |
| SHA-1 | 1645 MB/s | 20 B |
| SHA-512 | 795 MB/s | 64 B |
| BLAKE2b | 775 MB/s | 64 B |
| MD5 | 709 MB/s | 16 B |

带 open/read 的端到端实测是 1352 MB/s（1074 MB / 794 ms，warm cache），所以「BLAKE3 一定更快」这类结论必须在目标机器上先测——这台机器上 SHA-256 在硬件加速下反而快过 BLAKE2b 与 MD5。

### 4. 流式读取、TOCTOU 与有界并发

**TOCTOU 不是理论风险。** 文件在 stat 与读之间被改写，会产出一个「哪个版本都不属于」的 digest。本机实测：x.bin 原本是 8192 个 `A`，读到 4096 字节时被改写成 8192 个 `B`，拼接出来的 digest 恰好等于另一个合法文件 z.bin（内容就是 4096 个 `A` 加 4096 个 `B`）的 digest——漏斗会把 `{x, z}` 报成一个重复组，而 x 在磁盘上的真实内容与 z 不同，删除 z 就是删掉唯一副本。

正确姿势是在同一个 fd 上做两次 `fstat`：读之前取 size/mtime，读完之后再核对，不一致就重试或标 unstable。**但时间戳本身有粒度**：本机实测 mtime 的粒度是 1 ms（相邻两次写入的 mtime_ns 增量只出现 999,999 ns 与 1,000,000 ns 两档），同一档内的两次写入拿到完全相同的 mtime 与 ctime——TOCTOU 夹具里 x 被整份改写前后 mtime_ns 一个数都没变，所以「前后 mtime 一致」不能证明文件没变。对不可信工作区的稳妥做法是：读完后重读一次头部或整份 digest 做交叉确认，或者对 size 没变但 mtime 落在最近一个 tick 内的文件直接重试。

**并发必须有界。** 扫描是 I/O 密集，但线程数不是越多越好：本机 1684 个候选文件 / 63.42 MB（warm cache，与表 1 里被全量哈希的是同一批文件）实测：1 个 worker 68~71 ms（约 900 MB/s），加到 8 / 16 / 64 个 worker 反而升到 115~139 / 118~161 / 125~162 ms（三次运行的区间，最优值都在单线程）——热 cache 的小文件场景里瓶颈是每次 `open`/`read` 的 syscall 与 GIL 切换，加线程只会加调度开销。所以线程池取 8~32 并按机器与介质调参，价值主要在冷 cache、网络盘与大文件上。

**取消与让出。** Cursor 的扫描跑在编辑器进程里：必须可取消（`CancelledError` 一类的显式检查点）、按批让出事件循环，绝不阻塞 UI 线程，也不要在一次按键的预算里塞进整棵树的全量哈希。

### 5. 内存与规模：$10^5$ 常驻，$10^6$ 两遍法

CPython 3.10.12、tracemalloc 口径下的每条目增量（与 [[coding-06]] 同口径：裸 `dict[int → int]` 在 $10^5$ 上是 80.4 B/条，本题实测复现同一个数）：

| 结构 | $10^5$ | $10^6$ |
| --- | --- | --- |
| `dict[int → int]` | 80.4 B/条 → 7.7 MiB | 69.9 B/条 → 66.7 MiB |
| `dict[digest32 → count]` | 145.4 B/条 → 13.9 MiB | 134.9 B/条 → 128.7 MiB |
| `dict[digest32 → 44 字符路径]` | 210.4 B/条 → 20.1 MiB | 199.9 B/条 → 190.7 MiB |
| 60 字符路径折算 | — | 215.9 B/条 → 205.9 MiB |

结论是两档口径：$10^5$ 文件级可以把 digest → 路径整表常驻（约 20 MiB，加上目录项缓存与队列仍在几十 MiB 量级）；$10^6$ 级必须先声明上界，再走两遍法——第一遍只累计 digest → 出现次数（128.7 MiB，不存路径），第二遍只对 count ≥ 2 的内容重读一遍字节来产出路径与分组，用「重复读那一部分字节」换掉整张路径表。再往上就把 digest → 路径落到 sqlite / RocksDB，按字节记账并给单条路径长度上限。

### 6. 近重复：固定块会归零，内容定义分块才兜得住

「copy 之后改一行」「vendored 依赖」「多份 LICENSE」用精确哈希完全无解，这时候要看块级 digest 的倒排表。分块方式决定一切：固定 4 KiB 在文件头部插入 1 个字节，后面所有块的边界全部错位，块级共享字节直接归零；内容定义分块（CDC，滚动哈希找边界）在改动点之后会重新对齐，共享率保持在 97% 以上。

| 变体（0.951 MB 基文件） | 固定 4 KiB 共享字节 | CDC（2K/8K/32K）共享字节 |
| --- | --- | --- |
| 头部插入 1 字节 | 0.00% | 99.09% |
| 中间改 1 行 | 49.97% | 97.69% |
| 尾部追加 1 行 | 99.93% | 99.98% |
| 删掉中间 400 字节 | 49.99% | 97.73% |

有了块级倒排表（block digest → 文件列表），找出「共享大量块」的文件对只需要对文件对算 Jaccard，再用 MinHash 之类的签名把候选压到可接受规模——这比走 embedding 便宜好几个数量级，也和 [[rag-11]] 的 chunk 级 diff 是同一套结构。

### 7. 接回 Cursor：三个去处要的「重复」定义不同

1. **索引去重（精确）**：内容哈希就是 cache key，同一份文件在 20 个分支、多个 workspace 快照里只编码一次。去重必须发生在采集与索引之前，否则省下的只是存储、省不掉算力。这一层要接 [[system-design-02]] 的仓库索引，且表要能增量维护、能失效、能原子切换（否则第一次扫描很准、之后全是陈旧分组）。
2. **近重复（块级）**：上面第 6 节的 CDC + 倒排表，用来找「共享大量块」的文件对，产出的是相似度而不是相等。
3. **语义近重复（向量）**：只有「改一行但语义相同」这类问题才需要向量。按 [[coding-11]] 的口径，$10^8 \times 768$ 维 fp32 是 $4Nd = 307.2$ GB，每次查询都要读一遍，算术强度只有 0.5 FLOP/byte，比 H100 的 roofline 拐点 295 FLOPs/byte 低 590 倍，是彻底的带宽题（3.35 TB/s 上读一遍 91.7 ms，单卡 10.9 QPS）；int8 量化把实测的 0.102 GB 压到 0.026 GB（4 倍），单用量化分数的 recall@10 掉到 0.933，必须 shortlist + fp32 回表重排才回到 1.000。

关键取舍是不对称的：ANN 漏召回只是少省一点钱；用近似结果去做删除决策会删掉唯一副本。所以「报告」可以用近似，「删除」必须精确，并且保留一次人工确认。

### 8. 验收：不变量、夹具与指标

不变量三条：① 组内文件两两 SHA-256 相等（小组上用逐字节比对做 oracle，必须全对：本机 602 组、0 处失败）；② 同一 inode 不重复上报（别名单列）；③ 目录项 shuffle 后输出逐位一致。

夹具至少七类：同内容不同 mtime / 权限 / 路径、同 size 不同内容、同前缀不同长度、空文件、硬链接、符号链接环、读取中被改写。指标必须打出来：读放大（实际读取字节 ÷ 全库字节）与各级候选的文件数与字节数，否则剪枝率一变差没人知道。

复杂度与规模口径：时间 $O(\text{总字节})$ 读取 + $O(\text{文件数})$ 次 stat + $O(\text{文件数} \log \text{文件数})$ 排序（真正的常数项是每文件固定开销，本机 3.95 µs/文件），空间 $O(\text{候选数} \times (\text{digest} + \text{元数据}))$。把 $10^5$（全常驻约 20 MiB）与 $10^6$（两遍法、必要时落盘）两档讲清楚，比背一句「O(n)」有说服力得多。

## 数值与代码验证

全部数字由本机 CPython 3.10.12 复算（32 核、NVMe、warm page cache，单位 1 MB = 1000 × 1000 B、1 MiB = 1024²；漏斗耗时为单轮完整运行的实测，重复运行波动约 ±10%，吞吐与内存为三次取最好），脚本在仓库根 `.work/lane-d/` 下（`funnel.py` 三级漏斗与语料构造、`bench.py` stat/哈希/内存、`cdc.py` 分块对比、`fixtures.py` 边缘夹具）。

**表 1：语料 A 的三级漏斗（4000 文件 / 117.29 MB / 2805 个不同 size）**

| 阶段 | 候选文件数 | 相对原始 | 本阶段读取 | 耗时 |
| --- | --- | --- | --- | --- |
| stat / 枚举 | 4000 | 100% | 0 | 19.8 ms |
| size 分桶 | 1849 | 46.2% | 0 | 1.7 ms |
| 头部哈希（4 KiB） | 1684 | 42.1% | 7.57 MB | 30.8 ms |
| 全内容哈希（1 MiB 块） | 602 组 | — | 63.42 MB | 74.0 ms |

重复字节 30.40 MB，占全库 25.9%；读放大 0.605×（没有任何剪枝、直接全量哈希的朴素做法是 1.0×）。头部哈希那一级的 30.8 ms 里有大半是 1849 次 open 的固定开销（平均 246 MB/s，远低于纯哈希的 1707 MB/s），这正是漏斗要靠 size 先砍一刀的理由。

**表 4：夹具的实测结论**

| 夹具 | 结果 |
| --- | --- |
| 硬链接（2000 目录项 / 100 inode） | 不剔别名：2000 个目录项 100% 进候选，内容哈希报成 100 组 × 20 条路径（整棵树都是「重复」）；剔别名后剩 100 个 inode、落进 2 个 size 桶（10 B 桶 10 个、11 B 桶 90 个），内容哈希后 0 个重复组 |
| 符号链接环（3 个自指链接） | 不跟随 1 个文件 / 0.1 ms；跟随 + visited set 只访问 2 个 inode；跟随无 visited set 在 5.0 s 内访问 76,781 个目录项且未结束；纯链接环报 ELOOP（errno 40）记 skipped |
| 空文件（300 个） | 1 组、300 条路径、0 字节；跳过 size = 0 后候选 0 个 |
| 权限错误 | `PermissionError`（errno 13）记 skipped，扫描继续 |
| TOCTOU（读一半被改写） | 拼接 digest 与合法文件 z 完全相同 → 假的重复组；x 的真实内容与 z 不同，删 z 就是删唯一副本；`fstat` 前后 size 相同、mtime_ns 也完全相同（本机 mtime 粒度 1 ms，改写落在同一档），这次改写用元数据检测不出来 |
| 并发（1684 个候选文件 / 63.42 MB，warm） | 1 worker 68~71 ms（约 900 MB/s）；8 / 16 / 64 workers 115~139 / 118~161 / 125~162 ms（三次运行的区间，线程越多越慢） |

```python
# 三级漏斗：每一级只做减法，最后一级才是判据
import hashlib, os
HEAD, CHUNK = 4096, 1 << 20

def scan(root):
    # os.scandir 递归；DirEntry.stat() 走目录项缓存，不重复打 syscall
    out, stack = [], [root]
    while stack:
        with os.scandir(stack.pop()) as it:
            for e in it:
                if e.is_dir(follow_symlinks=False):
                    stack.append(e.path)
                elif e.is_file(follow_symlinks=False):
                    out.append((e.path, e.stat(follow_symlinks=False)))
    return out

def funnel(root):
    entries, stats = scan(root), {'skipped': 0, 'aliases': 0}
    seen = set()
    by_size = {}
    for path, st in entries:                      # 契约：同一 inode 只保留一条路径
        key = (st.st_dev, st.st_ino)
        if key in seen:
            stats['aliases'] += 1
            continue
        seen.add(key)
        by_size.setdefault(st.st_size, []).append((path, st))
    cand = [x for ps in by_size.values() if len(ps) > 1 for x in ps]   # 阶段 1
    by_head = {}
    for path, st in cand:                         # 阶段 2：只为剪枝，key 必须带长度
        with open(path, 'rb') as f:
            head = f.read(HEAD)
        by_head.setdefault((st.st_size, hashlib.sha256(head).digest()), []).append(path)
    cand = [p for ps in by_head.values() if len(ps) > 1 for p in ps]
    groups = {}
    for path in cand:                             # 阶段 3：唯一判据
        h = hashlib.sha256()
        n = 0
        with open(path, 'rb') as f:
            for chunk in iter(lambda: f.read(CHUNK), b''):
                n += len(chunk)
                h.update(chunk)
        groups.setdefault((n, h.digest()), []).append(path)
    dups = {k: sorted(v) for k, v in groups.items() if len(v) > 1}
    # 口径与实测：4000 文件 / 117.29 MB -> 1849 -> 1684 -> 602 组
    # 重复字节 30.40 MB（25.9%），读放大 0.605x
    return dups, stats
```

## 常见追问

- **追问**：为什么不用 `st_size` 加 `st_mtime` 当去重键，省掉整趟读取？
  - 要点：mtime 相同的两个文件内容可以不同（改回原样、复制时保留时间戳、`touch -r` 之后重新 checkout），而 mtime 不同的文件内容可能完全相同（重新 copy）。元数据只能做剪枝，不能做判等；在 Cursor 的场景里同一份文件在 20 个分支被 checkout，mtime 各不相同而内容一致，用 mtime 判等会把该省的省掉。
- **追问**：$10^6$ 文件、$10^{11}$ 字节的仓库怎么跑完，还不把编辑器拖死？
  - 要点：先声明上界与档位。枚举 + stat 4 s 量级（3.95 µs/文件），第一遍只算 digest → 计数（128.7 MiB），第二遍只重读 count ≥ 2 的内容；扫描分片、可取消、可在两次运行之间落盘续跑；对 UI 的承诺是「首屏只跑 size + 头部，全量哈希降到后台低优先级」。
- **追问**：硬链接为什么不算重复，别名要不要上报？
  - 要点：硬链接是同一份数据的两个名字，删除其中一个不省任何字节，把 2000 个目录项报成 2000 个重复文件只会误导用户（本机夹具就是 100 个 inode）。正确输出是「重复组」只含不同 inode，别名单独列成 aliases 字段。
- **追问**：并发跑多少合适，为什么实测 1 个 worker 反而最快？
  - 要点：测出来的结论要跟着口径走。warm cache 的小文件场景瓶颈在 syscall 与 GIL 切换，多线程只增加调度开销（1 worker 约 70 ms 对 16 workers 118~161 ms）；换成冷 cache、网络盘或大文件，I/O 并行才会体现出来。所以取 8~32 并按介质调参，同时保留「可取消、可让出」的硬约束。
- **追问**：为什么不能把 digest 截断到 8 字节省内存，64 位碰撞概率不是极低吗？
  - 要点：$10^6$ 文件上 64 位生日上界 $2.7 \times 10^{-8}$ 只对随机、非对抗输入成立；仓库内容由用户提供，可以刻意构造出一对前缀相同的文件，而一次碰撞就意味着一份唯一内容被当成副本删掉。省下的 24 B/条（约 23 MiB，18%）不值得。
- **追问**：近重复（改一行）怎么处理，别上 embedding 行不行？
  - 要点：行。用粗粒度滚动的块级倒排表（本机实测 CDC 在头部插 1 字节后仍共享 99.09%，固定 4 KiB 是 0.00%），先按共享块数找候选文件对，再算 Jaccard / MinHash 排序。这条路的成本是块哈希，比 embedding 便宜几个数量级；只有要答「语义上是不是同一件事」时才需要向量，并按 coding-11 的 shortlist + fp32 回表口径控制召回。
- **追问**：扫到一半文件被改了、或者被删了怎么办？
  - 要点：删了记 skipped 并让这一轮结果带上 `unstable` 标记；改了要按 fd 上的前后两次 `fstat` 判断（size 与 mtime 任一变化就重试或标 unstable）。注意本机 mtime 粒度约 1 ms，同一 tick 内的改写检测不出来，所以对不可信工作区要在读完后重读一次头部或 digest 复核，再把结果原子写入索引。
