## 一句话答案

> 先定契约再选结构。同一份缓冲区里同时存在三套坐标：磁盘与内容哈希侧是 UTF-8 字节，VS Code 扩展 API 与 LSP 是 UTF-16 code unit，用户与行索引看到的是「行/列」；Cursor 是 VS Code fork，三套坐标只能有一个换算出口（`positionAt` / `offsetAt`），字节入口只能走有状态增量解码器，行尾必须先归一化，不变量要写成断言（区间无缝覆盖 $[0, \mathrm{len})$、`lines == content.count('\n') + 1`、`positionAt(offsetAt(line, col)) == (line, col)` 往返），单行上限 $2^{20}$ 字符。
> 结构按编辑模式选，不是按「谁最快」选：单光标局部输入用 gap buffer（洞在光标处，局部编辑均摊 $O(1)$）；要 undo、版本快照、并发读、AI 一次改多处就用 piece table（原文只追加不改写，正文永不复制）；超大文件且要 $O(\log n)$ 随机访问与可持久化就用 rope。判据是「一次编辑要动多少数据」：1 MiB 文档下一次编辑，rope 只重写路径上 11 个节点共 704 B，gap buffer 最坏要把 1 MiB 整个搬一遍，差 $1.5\times10^3$。
> 行索引必须与插入/删除解耦：把行数写进结构本身（piece 带 `line_count`、rope 节点存子树行数与字符数），或者至少上 Fenwick 树。「每行起点有序数组 + 二分」查询确实是 $O(\log L)$，但更新要在击键路径上平移 $O(L)$；生产上真正难的是编辑的原子性与并发：AI 一次应用 500 行必须是一个事务（一次 Ctrl+Z 撤掉），位置要用 anchor + affinity 表达而不是 offset，用户同时手改时用内容哈希做乐观并发，失败返回 conflict 而不是抛异常把渲染进程打崩。

## 面试官在考什么

- **坐标系统有没有想清楚**：三套坐标谁在用、单位是什么、换算出口是不是唯一。字节边界不是字符边界（汉字 3 B、emoji 4 B），UTF-16 offset 落在代理对中间会产生孤立代理项，行/列只在行尾口径固定后才有意义。这一条答错，后面结构写多快都白搭。
- **会不会把契约写成断言**：区间无缝覆盖 $[0, \mathrm{len})$、`lines == count('\n') + 1`、往返一致、单行超限报错。能主动列出不变量的人，通常真写过缓冲区。
- **三个结构的取舍是否按编辑模式**：gap buffer / piece table / rope 的机制、复杂度与失效场景逐个说清，包括「光标大跳」「undo 要整份复制」「多光标下没有唯一的洞」「piece 元数据膨胀」，而不是背一句「rope 是 $O(\log n)$ 所以最好」。
- **行索引会不会把 $O(L)$ 拖进击键路径**：把行数写进结构，或用 Fenwick 树；同时报得出「有序数组」在 100 万行上平移一次要多少微秒。
- **工程账**：piece 头与树节点的内存开销、compaction 放在哪里、哨兵消掉哪些特判、摊还还是最坏、持久化与崩溃丢失窗口、buffer 产物进模型时的 token 记账。

常见错误答案：

- 「rope 每个操作 $O(\log n)$，所以选 rope」。没算常数与元数据，也没看到单光标本地输入时 gap buffer 的均摊 $O(1)$ 更便宜。正确答法是先问编辑模式，再给结构和它的失效场景。
- 「行号查找就用二分查每行起点数组」。查询对、更新错：在最前面插一个换行要平移后面全部行起点，$O(L)$ 直接进击键路径。

## 原理与推导

### 1. 先钉死契约：三套坐标、一个换算出口

UTF-8 字节是磁盘、内容哈希与按字节切分的内容定义分块的单位；UTF-16 code unit 是 VS Code 扩展 API 与 LSP 的单位；行/列是用户、诊断、断点与 diff 的单位。实测「中文字符🙂ünïcode」是 12 个字符、25 个 UTF-8 字节、13 个 UTF-16 unit；`🙂ab` 里的 `a` 是 char@1、utf8_byte@4、utf16@2——三套坐标可以全不相等，所以缓冲区内部只允许存在一种 offset，换算只出现在 `positionAt` / `offsetAt` 两个函数里，任何地方出现第二种 offset 都是 bug 源。UTF-16 侧还要拒绝落在代理对中间的偏移。字节入口用**有状态增量解码器**：`codecs.getincrementaldecoder('utf-8-sig')()` 把跨 chunk 的半字符留在解码器内部，下次补齐，顺带按规范吃掉流开头的 BOM。实测按 1/2/3/4/5/7/16 B 固定切分与 2000 次随机长度（1–11 B）切分喂入，还原全部逐字节一致（不一致 0/2000）；逐字节独立 `decode()` 在严格模式下直接抛 `UnicodeDecodeError`（切在 emoji 首字节上），放宽到 `errors='replace'` 则产生 20 个 U+FFFD。这条压力测试要原样搬进 buffer 的加载入口。

### 2. 行尾、BOM 与四条不变量

LF、CRLF 与单独 CR 都是合法行尾（WHATWG 的 Server-sent events 规范口径，[[coding-09]] 的行切分同源）。要么加载时归一化成 LF（代价是保存要还原、diff 显示整文件变更），要么把 CRLF 当单个换行符存进行索引（代价是每次切分前瞻一个字符、跨 chunk 要记住「刚见过 CR」）；不能两头都要。实测未归一化文本 `a\r\nb\rc\nd`：`splitlines()` 是 4 行而 `count('\n') + 1` 只有 3；把 `'A\r'` 与 `'\nB'` 两块分别归一化会得到 3 行，用 `skip_lf` 前瞻一个字节才是正确的 2 行。

契约写成断言：①piece/叶子区间无缝覆盖 $[0, \mathrm{len})$（块间空白归前一块，口径同 [[coding-10]]）；②`lines == content.count('\n') + 1`（归一化之后才成立）；③`positionAt(offsetAt(line, col)) == (line, col)` 且偏移永不落在代理对或字符中间；④单行上限 `max_line_chars = 2^20`（1,048,576 字符，CJK 下 3 MiB、emoji 下 4 MiB）——无换行的 minified JS 一行就是几 MB，要显式报错而不是吃光内存。

### 3. 三种结构按编辑模式取舍

| 结构 | 编辑路径 | 定位与随机访问 | undo / 快照 / 并发 | 主要失效场景 |
| --- | --- | --- | --- | --- |
| gap buffer | 洞在光标处，局部插入删除均摊 $O(1)$ | $O(1)$ | 要整份复制缓冲区 | 光标大跳、多光标、多用户（没有唯一的洞） |
| piece table | 原文只追加不改写，插入删除只改 piece 列表，均摊 $O(1)$ | $O(P)$，把行数挂平衡树可到 $O(\log P)$ | 追加日志天然可重放 | 元数据膨胀、$P$ 无界时定位退化 |
| rope / 平衡树 | 叶子 + 节点聚合，$O(\log n)$ | $O(\log n)$ | 结构共享，天然可持久化 | 实现复杂、每节点开销、编译期常数大 |

**gap buffer**：光标处留洞，插入写洞并移动洞边界。光标大跳要把洞搬过去——10 MiB 文件按 10 GB/s 内存带宽是 $10 \times 2^{20} \div 10^{10} \approx 1.05$ ms，本机实测 6.1 GB/s（1.71 ms）。按 8 键/秒，每次击键有 125 ms 预算（补全 p95 预算是 250 ms，[[system-design-02]]），1.7 ms 只占 1.4%，偶发跳转可忍；但 AI 在 10 MiB 文件里一次改 500 处就是 500 次搬运约 0.86 s，且 undo/快照/协作要整份复制、多光标下没有唯一的洞。

**piece table**：原文 buffer 只追加不改写，新内容进 add buffer，`piece = (source, start, length)`，插入删除只改列表与偏移，正文永不复制（VS Code 的基线；它后来改成 piece tree，把线性定位修成 $O(\log P)$）。代价是随机访问 $O(P)$ 与 piece 头线性膨胀。**rope**：正文切定长叶子，节点存子树字符数与行数。1 MiB 按 1 KiB 叶子是 1024 个叶子；经典实现（内部节点单独成对象）是 $2 \times 1024 - 1 = 2047$ 个节点，按 64 B/节点约 128 KiB，占正文 12.5%。一次编辑只重写根到叶路径上的 11 个节点，$11 \times 64 = 704$ B，对比 gap buffer 最坏的 1,048,576 B，比值约 $1.5\times10^3$。

**选择口径**：单光标局部输入选 gap buffer；要 undo/版本/并发快照、编辑位置任意（AI 一次改多处）选 piece table；超大文件 + $O(\log n)$ 随机访问 + 可持久化选 rope。三者不是「谁最快」，是「哪种编辑模式主导」。

### 4. 行索引必须与插入/删除解耦

「有序数组存每行起点 + 二分」查询是 $O(\log L)$，更新是 $O(L)$：100 万行 × 4 B = 3.8 MiB，在最前面插一个换行要平移 10^6 条。口径要说清——memmove 口径（4 MB ÷ 10 GB/s）约 0.4 ms，C 逐元素写（10^6 × 1 ns）约 1 ms；本机 Python 实测 `list.insert(0, x)` 在 10^6 条上是 624 µs，逐条改行号是 69 ns/条、10^6 条约 69 ms，而击键预算只有 125 ms。[[coding-06]] 有同类证据：用 `list` 记 LRU 顺序时单次 `get` 在 $N=$ 2000/8000/32000 是 10.9/43.6/190.9 µs，容量 ×4 耗时 ×4.0～×4.4，属线性项。

两条正确做法：①把行数写进结构本身——piece 带 `line_count`（行查找 $O(P)$，同源相邻 piece 合并后挂平衡树到 $O(\log P)$），rope 节点存子树行数与字符数（$O(\log n)$）；②若坚持独立数组就上 Fenwick 树，update/query 都是 $O(\log L)$：$\log_2 10^6 \approx 19.9$，约 20 步对 10^6 步，步数差 $5\times10^4$，本机实测点更新 3.00 µs、找第 $k$ 个字符所在行 3.86 µs，对照上面的 624 µs 与 69 ms 差两个数量级起。

**批量插入先扫一遍**：AI 一次贴 500 行（500 × 60 = 3×10^4 字符）时，`count('\n')` 实测 24.6 µs，Python 层逐字符数要 669.8 µs（27×）；改成逐字符走结构则是 14.7 µs/字符、整批 440.7 ms——3×10^4 次结构操作换 1 次扫描。

### 5. 元数据账、compaction 与哨兵

一次典型编辑（插入 4 字符）至少产生 2 个新 piece（拆原片 + 新片），10^4 次编辑就是 $2\times10^4$ 个 piece 头：按 [[coding-06]] 的实测量级（带 `__slots__` 的手写链表节点 160.4 B/条）算，约 3.2 MB（$2\times10^4 \times 160.4 = 3{,}208{,}000$ B）只换来 $4\times10^4$ B 正文，比值 80 倍；即便在 C 里把 piece 头压到 24 B，480 KB 仍是正文的 12 倍。只做「同源且区间连续」的相邻合并，效果取决于编辑模式：模拟 10^4 次单字符插入，顺序在光标处输入时列表瞬时只有 3 个 piece、合并后稳定在 2 个；随机位置输入时合并前 19,137 个、合并后仍是 19,137 个（每个新片都落在 add buffer 的不同偏移上），线性扫表定位一次 757 µs，摊到 10^4 次编辑是 7.6 s。所以必须有全量重写的退路，且绝不能出现在按键路径上：实测全量重建 1/8/64 MiB 分别是 4.7/47.8/515.9 ms。口径参照 [[coding-06]] 的有界清扫：20 万条一次清完 575.3 ms，切成单次最多 64 条只要 0.27 ms——把清尾切成有界批次或放后台，并把 compaction 次数与单次耗时做成指标。

**哨兵**照搬 [[coding-06]]：头尾各一个哨兵，`prev`/`next` 永不为空，「空表、删头、删尾、删唯一节点」四类特判全部消失，行索引的首行末行同理。**复杂度要带摊还**：字典是均摊 $O(1)$（rehash 摊还），链表原语严格 $O(1)$，所以准确说法是「piece 结构 + 摊还 compaction 下均摊 $O(1)$，最坏 $O(P)$」，不是「绝对 $O(1)$」。

### 6. 编辑的原子性与并发

**offset 是瞬时量，anchor 才是稳定量**：用户在补全 ghost text 的插入点继续敲键盘时，AI 的插入位置必须用 anchor + affinity（吸左/吸右）表达，否则光标会跳到 AI 插入的 500 行之后；装饰、诊断、断点、diff 高亮都挂 range，必须随 anchor 一起 transform。**一次 AI 应用（500 行 hunk）必须是一个事务**：整段进 undo 栈、一次 Ctrl+Z 撤掉，而不是 3×10^4 次逐字符撤销；编辑前落快照、逐块接受、提交走原子写（临时文件 + rename）。用户同时手改时用内容哈希做乐观并发，不一致就拒绝并让模型在最新内容上重生成（[[system-design-02]] 的 apply 流水线口径）；行号会漂移，hunk 要先按上下文重新定位（与 [[cursor-02]] 的「按内容摘要定位变更」同源）。失败要有正常出口：冲突返回 conflict 与原因，能部分应用就显式标出未应用的块，不要抛异常把渲染进程打崩（[[coding-12]] 的口径：失败必须是可恢复的观察）。

**量级要报出来**：1 万工程师 × 300 次补全/天 = $3.0\times10^6$ 次/天，均值 34.7 QPS、按 15 倍峰均比取峰值 521 QPS（[[system-design-02]]），所以读路径（取行、取 range、读全文）走不可变快照、无全局锁，写走事务，不能让击键与 agent 编辑互相抢锁。

### 7. 持久化、大文件退化与 token 记账

未保存内容必须能恢复：add buffer 追加写 + root 版本号落盘、重启重放，保存时按 piece 顺序拼正文，并保证 CRLF 与 BOM 口径一致（[[coding-09]] 用 `utf-8-sig` 顺带吃掉 BOM 是同一类编码前缀细节）。不能每击键都 fsync，按时间/字节双阈值批量落盘（例如 200 ms 或 64 KiB），把崩溃丢失窗口写进契约。超过阈值（例如 50 MiB）或检测到 NUL 字节的文件直接转只读/分片视图，别把 minified bundle 塞进 rope。**token 记账**：字符数不是 token 数。同一份 1000 字符预算，英文 203 token、中文 783 token（[[coding-10]] 实测 46 字符 = 36 token）；代码口径是 3.05 字符/token（tiktoken 的 `o200k_base`）。AI 一次 500 行约 3×10^4 字符 ≈ $9.8\times10^3$ token，按 LLaMA-3-70B 每 token 320 KiB 的 KV cache 口径（[[llm-internals-02]]）就是 3.0 GiB——这才是它进上下文的真实成本。超预算裁剪必须显式标记 `truncated` / `total` / `next_offset`，悄悄截断等于让模型基于残片推理。

## 数值与代码验证

**表 1：规模回归**（同一编辑在 1/8/64 MiB 文档上的单步耗时；rope 按批量 2000/2000/500 次、朴素整串重写按 100/100/25 次取均值，rope 为下方实现）

| 文档 | 编辑后节点数 | rope | 朴素整串重写 | 比值 | 投影到 10^4 步 |
| --- | --- | --- | --- | --- | --- |
| 1 MiB | 5,022 | 27.6 µs | 284.5 µs | 10× | 0.3 s 对 2.8 s |
| 8 MiB | 12,191 | 32.5 µs | 5,282 µs | 163× | 0.3 s 对 52.8 s |
| 64 MiB | 66,535 | 38.4 µs | 69,598 µs | 1,812× | 0.4 s 对 696 s |

规模涨 64 倍，rope 单步只涨 1.4 倍（27.6 → 38.4 µs），这才叫与规模无关；朴素实现每档涨 13～19 倍，10^4 步在 64 MiB 上是 11.6 分钟。对照 [[coding-06]]：手写 LRU 的 `get` 在 5 万/20 万/100 万条目下是 392.7/390.5/393.0 ns，规模涨 20 倍耗时不变。

行索引三条路的实测放在第 4 节：有序数组二分查询 1.33 µs 但更新要 624 µs 平移（逐条改行号 69 ms）；Fenwick 更新 3.00 µs、找第 $k$ 个字符所在行 3.86 µs；结构内行数在 split/merge 时顺带更新、无额外写。步数口径：$\log_2 10^6 = 19.93$，约 20 步对 10^6 步，差 50,176 倍（≈ $5\times10^4$）。

下面的实现可直接运行：它是一棵定长叶子 + 子树字符数/行数的隐式 treap，`position_at` / `offset_at` 是唯一的坐标出口，末尾在 8 万字符文档上跑 10,000 次随机编辑并与朴素 `str` 参照整体比对。

```python
import codecs
import random

random.seed(5)


def decode_chunks(chunks):                 # 字节入口：半字符留在解码器里，顺带吃掉 BOM
    dec = codecs.getincrementaldecoder("utf-8-sig")()
    return "".join([dec.decode(c) for c in chunks] + [dec.decode(b"", True)])


def normalize(text):                       # 行尾契约：LF / CRLF / 单独 CR 统一成 LF
    return text.replace("\r\n", "\n").replace("\r", "\n")


class Node:                                # 隐式 treap：节点内聚合子树字符数与行数
    __slots__ = ("chunk", "cl", "prio", "left", "right", "b", "l")

    def __init__(self, chunk):
        self.chunk, self.cl, self.prio = chunk, chunk.count("\n"), random.random()
        self.left = self.right = None
        self.b, self.l = len(chunk), self.cl


def _up(t):
    if t:
        t.b = (t.left.b if t.left else 0) + len(t.chunk) + (t.right.b if t.right else 0)
        t.l = (t.left.l if t.left else 0) + t.cl + (t.right.l if t.right else 0)


def merge(a, b):
    if a is None or b is None:
        return a or b
    if a.prio < b.prio:
        a.right = merge(a.right, b); _up(a); return a
    b.left = merge(a, b.left); _up(b); return b


def split(t, k):                           # 前 k 个字符归左；叶子内切开只动元数据
    if t is None:
        return None, None
    lb = t.left.b if t.left else 0
    if k <= lb:
        a, b = split(t.left, k); t.left = b; _up(t); return a, t
    if k >= lb + len(t.chunk):
        a, b = split(t.right, k - lb - len(t.chunk)); t.right = a; _up(t); return t, b
    off = k - lb
    lt, rt, right = t.left, t.right, t.chunk[off:]
    t.chunk, t.cl = t.chunk[:off], t.chunk[:off].count("\n")
    t.left, t.right = lt, None; _up(t)
    return t, merge(Node(right), rt)


class Rope:
    def __init__(self, text, leaf=1024):   # 定长叶子串成一棵 treap
        self.leaf, self.root = leaf, None
        for i in range(0, len(text), leaf):
            self.root = merge(self.root, Node(text[i : i + leaf]))

    def insert(self, pos, s):              # 删除对称：split 两次再 merge
        a, b = split(self.root, pos)
        mid = None
        for i in range(0, len(s), self.leaf):
            mid = merge(mid, Node(s[i : i + self.leaf]))
        self.root = merge(merge(a, mid), b)

    def text(self):
        def walk(t):
            return "" if t is None else walk(t.left) + t.chunk + walk(t.right)
        return walk(self.root)

    def line_start(self, line):            # 第 line 行起点：按左子树行数下降
        off, need, t = 0, line, self.root
        while t is not None and need > 0:
            ll = t.left.l if t.left else 0
            if need <= ll:
                t = t.left; continue
            if need - ll <= t.cl:
                idx = -1
                for _ in range(need - ll):
                    idx = t.chunk.find("\n", idx + 1)
                return off + (t.left.b if t.left else 0) + idx + 1
            off += (t.left.b if t.left else 0) + len(t.chunk)
            need -= ll + t.cl; t = t.right
        return off

    def position_at(self, offset):         # 行号 = 前缀换行数；列 = 偏移 − 本行起点
        cnt, t, k = 0, self.root, offset
        while t is not None and k > 0:
            lb = t.left.b if t.left else 0
            if k <= lb:
                t = t.left; continue
            cnt += t.left.l if t.left else 0
            if k < lb + len(t.chunk):
                cnt += t.chunk.count("\n", 0, k - lb); break
            cnt += t.cl; k -= lb + len(t.chunk); t = t.right
        return cnt, offset - self.line_start(cnt)

    def offset_at(self, line, col):
        return self.line_start(line) + col


S = "中文字符🙂ünïcode"
raw = S.encode()
assert decode_chunks([raw[i : i + 1] for i in range(len(raw))]) == S
filler = "".join(raw[i : i + 1].decode("utf-8", "replace") for i in range(len(raw)))

doc = normalize(("line %d 中文注释🙂\n" % 7) * 5000)
r = Rope(doc)
assert r.text() == doc and r.root.l + 1 == doc.count("\n") + 1
for _ in range(10_000):                    # 随机编辑，改完与朴素参照整体比对
    p = random.randrange(len(doc) + 1)
    s = random.choice(["x", "中", "🙂", "\n", "ab\ncd"])
    r.insert(p, s); doc = doc[:p] + s + doc[p:]
assert r.text() == doc
round_ok = all(r.offset_at(*r.position_at(p)) == p
               for p in (random.randrange(len(doc) + 1) for _ in range(2000)))


def count_nodes(t):
    return 0 if t is None else 1 + count_nodes(t.left) + count_nodes(t.right)

print(f"chars={len(S)} utf8={len(raw)} utf16={len(S.encode('utf-16-le')) // 2}；"
      f"逐字节独立 decode -> U+FFFD x {filler.count(chr(0xFFFD))}（严格模式直接抛错）")
print(f"10,000 次随机编辑后与朴素参照逐字符一致：{r.text() == doc}")
print(f"lines={r.root.l + 1} == count(chr(10))+1={doc.count(chr(10)) + 1}；往返 2000/2000 {round_ok}")
```

18,784 个节点 × 121 B（本机 tracemalloc 实测每节点开销）≈ 2.27 MB 元数据换 83,048 B 正文，比值 27 倍；不做 compaction，元数据会比正文先成为瓶颈。

**与简报口径的两处偏差，按实测写清。** ①「10^4 步 × 10^5 字符在朴素实现里是 10^9 次字符操作、差 5000 倍」只在「每次编辑用 Python 层逐字符搬运」的口径下成立；按 C 层整串切片（`str` 拼接走 memmove）重测，10^5 字符文档上朴素与 rope 已经同量级（本机 17.5 µs/步 对 15.1 µs/步；纯 ASCII 语料上朴素只要 6.0 µs/步，反而比 rope 快），3×10^5 字符才到 6.2×，1 MiB 起才拉开到 10× 以上，64 MiB 上才是 1,812 倍——引用倍数必须带文档大小与实现口径。②内存带宽：10 MiB 的洞搬运按 10 GB/s 理论是 1.05 ms，本机 `bytearray` 实测 6.1 GB/s（1.71 ms）；这台机器上另有负载，1 MiB 档这类受分配器行为影响的数字在不同批次间可差 5 倍以上，所以表 1 只承诺趋势（rope 与规模无关、朴素与规模线性），绝对值当量级看。

最后别过早微优化：[[coding-09]] 把「每行切片」换成「偏移量 + 定期压缩」实测只有 0.84×–1.36× 且方向不稳定。先证明瓶颈是渐进复杂度（每次编辑重扫整个 buffer 就是 $O(n^2)$ 的总代价），再谈常数。

## 常见追问

- **追问**：Cursor 是 VS Code fork，扩展 API 与 LSP 都按 UTF-16 计数，怎么保证 AI 的 edit 不插进 emoji 中间？
  - 要点：编辑入口只接受 (line, col) 或 UTF-16 offset，换算只走 `positionAt` / `offsetAt`；落在代理对中间的 offset 原地拒绝；字节层只走增量解码器。断言写成「任何返回的 offset 都能 `decode` 而不产生 U+FFFD」。
- **追问**：VS Code 为什么用 piece table 而不是 rope？
  - 要点：单文件编辑点是局部的，piece table 的插入删除是常数级元数据操作、正文只追加（对 undo/重放与崩溃恢复友好），代价是 $O(P)$ 定位与元数据膨胀；VS Code 实际是 piece tree（红黑树 + 每片行数），把定位修成 $O(\log P)$，同时保留「正文不改写」。
- **追问**：编辑之后缓存的绝对行号失效了怎么办？
  - 要点：行号只是某个版本上的坐标，不要跨版本缓存。结构里存行数、查询时 $O(\log n)$ 重算；对外用 anchor + version；应用 hunk 前按上下文重新定位。
- **追问**：多光标、多用户下 gap buffer 为什么不行？
  - 要点：洞只有一个，$N$ 个光标要 $N$ 次搬运，且没有不可变快照；协作需要可交换的插入/删除表示，rope 的结构共享与 CRDT/OT 更契合。gap buffer 适合「单光标 + 实现极简」的内核。
- **追问**：AI 一次应用 500 行怎么进 undo 栈？
  - 要点：一次事务对应一个 undo 条目，记 (anchor, 旧文本, 新文本) 或直接记 root 版本；逐块接受是 UI 层概念，落到 buffer 层是一次批量变更（或共享同一事务 id 的多次变更）。一次 Ctrl+Z 整段撤回。
