## 一句话答案

> **多模态服务的三个特有成本**：**① 图像变成 token（可能比一整篇长文还多）；② 视觉编码器的算力；③ 图像 token 进入 LLM 的 prefill 与 KV cache。**
> **★ 量化一：图像 token 成本**
> | 图像 | patch 14 | **2×2 池化** | **4×4 池化** |
> | --- | --- | --- | --- |
> | 224px | 256 | 64 | 16 |
> | 512px | 1,296 | 324 | 81 |
> | **1024px** | **5,329** | **1,332** | **333** |
> | **2048px** | **21,316** | **5,329** | 1,332 |
> **读法**：**1024px 图在 4×4 池化下是 333 token、2×2 下是 1,332 token**；**2048px（2×2）达 5,329 token**——**一张图 = 一整篇长文**。**所以"池化倍率"是容量规划的第一个旋钮**（**它同时决定质量与成本**）。
> **★ 量化二：视觉编码器的算力**
> | 图像 | patch 数 | **编码算力（2ND）** | **H100 上耗时**（MFU 40%） |
> | --- | --- | --- | --- |
> | 224px | 256 | 153.60 GFLOPs | 0.388 ms |
> | 512px | 1,296 | 777.60 GFLOPs | 1.966 ms |
> | **1024px** | **5,329** | **3,197.40 GFLOPs** | **8.082 ms** |
> **读法**：**1024px 图的编码约 3.2 TFLOPs、约 8 ms**——**相比"文本 prefill"（每 token 约 $2\times70$B = 140 GFLOPs）图像编码其实很便宜**。**真正的成本在"图像 token 进入 LLM"**（**本机：把 prefill 从 500 提到 836 token，+67%**）。
> **★ 量化三：容量（数亿 WAU）**
> | 项 | 值 |
> | --- | --- |
> | WAU | **300M** |
> | DAU（5%） | **15M** |
> | 请求/天（10 次/DAU） | **150M** |
> | **平均 QPS** | **1,736** |
> | **峰值 QPS（4×）** | **6,944**（**其中带图 2,778**） |
> | 单请求算力 | **159.04 TFLOPs**（**836 prefill + 300 decode**） |
> | 单卡吞吐 | **2.5 请求/秒** |
> | **峰值所需卡数** | **2,792** |
> **读法**：**"平均够用"远不等于"峰值够用"**——**4× 峰值系数是本机算出的关键乘数**（**这是容量规划最常见的错误**）。
> **★ 架构要点**：
> | 组件 | 设计 |
> | --- | --- |
> | **图像预处理** | **在 CPU/GPU 侧缩放 + 池化**（**决定 token 数**） |
> | **视觉编码器** | **独立部署**（**可批处理、与 LLM 解耦**） |
> | **prefill / decode** | **分离部署**（**串 [[openai-17]]**） |
> | **KV cache** | **图像 token 也要缓存**（**本机 1,332 token 的 KV 不小**） |
> | **流式输出** | **SSE/WebSocket + 首 token 优先** |
> | **降级策略** | **图太多 → 降池化倍率 / 限制图数** |
> **读法**：**"降级策略"是多模态特有的**——**因为"图的数量与分辨率"由用户决定**（**而文本长度至少还有上限**）。
> 一句话判据：**"先算图像 token（池化倍率是旋钮）→ 视觉编码器独立部署 → prefill/decode 分离 → 峰值 4× 定卡数 → 给'降分辨率/限图数'的降级路径"**。

## 面试官在考什么

- **★ 是否知道"图像 = token"**：**能否算出 1024px 图的 token 数**（本机：**333 或 1,332**）。
- **★ 是否知道池化倍率是旋钮**：**能否指出"它同时影响质量与成本"**。
- **容量换算**：**能否从 WAU 推到 QPS 再推到卡数**（本机：**2,792 卡**）。
- **★ 峰值系数**：**能否指出"平均 QPS 不是规划依据"**（本机：**4×**）。
- **TTFT 预算**：**能否拆出"图像编码 + prefill + 首 token"**。
- **解耦部署**：**能否指出"视觉编码器与 LLM 分离"**、**"prefill/decode 分离"**。
- **KV cache**：**能否指出"图像 token 也占 KV"**。
- **流式输出**：**能否指出 SSE/WebSocket 与"首 token 优先"**。
- **降级策略**：**能否给出"降分辨率/限图数"**。
- **成本意识**：**能否给出"每请求成本"与"单位经济"**。

**常见错误答案**

- **只按文本算容量**（**忽略图像 token**）。
- **用平均 QPS 定容量**（**没有峰值系数**）。
- **把视觉编码器和 LLM 混部**（**无法独立扩缩**）。
- **不考虑图像 token 的 KV**（**显存算错**）。
- **不提降级**（**用户传 10 张 4K 图就打爆**）。
- **只讲模型不讲服务**（**没有队列、批处理、缓存**）。
- **忽略"首 token 延迟"**（**流式体验的关键指标**）。
- **不做成本换算**（**不知道每请求多少钱**）。

## 原理与推导

### 1. ★ 图像 token 数

$$\text{tokens}=\left(\frac{H}{p}\right)\times\left(\frac{W}{p}\right)\div\text{pool}^2$$

| 分辨率 | $p{=}14$、无池化 | pool 2 | pool 4 |
| --- | --- | --- | --- |
| 1024² | 5,329 | 1,332 | **333** |

**读法**：**"池化倍率"是"质量与成本"的连续旋钮**——**pool 4 比 pool 2 省 4 倍 token**（**但细节丢失**）。**工程做法**：**按图像内容自适应**（**文字密集的图少池化**）。

### 2. 视觉编码器算力

$$\text{FLOPs}\approx2\times N_{\text{ViT}}\times N_{\text{patch}}$$

| ViT | 参数 | 1024² 的算力 |
| --- | --- | --- |
| ViT-B | 86M | 0.92 TFLOPs |
| **ViT-L** | **300M** | **3.2 TFLOPs** |
| ViT-H | 632M | 6.7 TFLOPs |

**读法**：**"编码一次图"的成本与"prefill 一个 token"量级相当（$10^{11}$ vs $10^{11}$ FLOPs）**——**但一张图会产生几百到几千个 token**（**所以瓶颈在"图 → token"的放大**）。

### 3. ★ 容量换算

| 步骤 | 公式 | 本机 |
| --- | --- | --- |
| WAU → DAU | $\times$ DAU 比例 | 300M → **15M** |
| DAU → 请求/天 | $\times$ 人均请求 | → **150M** |
| → 平均 QPS | $\div 86{,}400$ | **1,736** |
| → **峰值 QPS** | **$\times$ 峰值系数** | **6,944** |
| → 卡数 | $\div$ 单卡吞吐 | **2,792** |

**读法**：**"峰值系数 4×"是本机最关键的一个假设**——**它来自"人类作息"**（**晚间峰值**）。**如果不乘它，会少备 3/4 的容量**。

### 4. ★ 单请求算力拆解

| 阶段 | 算力 |
| --- | --- |
| 图像编码（1024²） | **3.2 TFLOPs** |
| LLM prefill（836 token） | **117 TFLOPs** |
| LLM decode（300 token） | **42 TFLOPs** |
| **合计** | **159 TFLOPs** |

**读法**：**"图像编码只占 2%"**——**96% 的算力在 LLM**（**因为图像 token 要过整个 LLM**）。**所以"降池化倍率"比"换更小的 ViT"更有效**（**前者直接减少 LLM 的 prefill**）。

### 5. 部署拓扑

| 组件 | 扩缩依据 |
| --- | --- |
| **图像预处理** | **CPU 密集**（**独立扩缩**） |
| **视觉编码器** | **可批处理**（**吞吐导向**） |
| **LLM prefill** | **算力密集**（**TTFT 导向**） |
| **LLM decode** | **显存带宽密集**（**TPOT 导向**） |
| **KV cache 存储** | **显存容量** |

**读法**：**"prefill 与 decode 分离"是现代服务的标准做法**（**因为它们的瓶颈不同**：**prefill 是算力、decode 是带宽**）。

### 6. 降级与限流

| 触发 | 降级动作 |
| --- | --- |
| **队列变长** | **降池化倍率（pool 2 → 4）** |
| **图数超限** | **只处理前 N 张** |
| **分辨率超限** | **服务端缩放** |
| **过载** | **排队 + 明确告知延迟** |
| **模型档位** | **小模型兜底**（**串 [[openai-17]]**） |

**读法**：**"降池化倍率"是多模态特有的优雅降级**——**它平滑地降低质量而不是直接拒绝**。

## 常见追问

- **追问**：TTFT 预算怎么分配？
  - 要点：**四段**：① **网络 + 排队**（**100–200 ms**）；② **图像下载 + 预处理**（**100–300 ms**——**取决于图大小与冷启动**）；③ **视觉编码**（**8 ms，可忽略**）；④ **prefill**（**836 token 在 70B 上约 47 ms**，**加上排队与批处理**）。**目标**：**带图的 TTFT 通常给 1–2 秒**（**比纯文本宽松**）。**读法**：**"图像下载"往往比"图像编码"慢得多**——**这是最容易被忽略的一段**。
- **追问**：图像 token 的 KV cache 有多大？
  - 要点：**按统一常数算**：① **LLaMA-3-70B GQA-8 的 KV 是 320 KiB/token**；② **1,332 图像 token → 约 416 MiB**（**单序列**）；③ **所以"多图 + 长对话"会迅速吃满显存**。**对策**：**限制图数、用池化降 token、对旧图做 KV 驱逐**。**读法**：**"图像 token 的 KV 是显存的隐形杀手"**——**算容量时必须算进去**。
- **追问**：怎么处理"同一张图被多个请求引用"？
  - 要点：**缓存编码结果**：① **按图像哈希缓存 ViT 输出**（**省掉重复编码**）；② **注意隐私**（**缓存要按用户隔离或加密**）；③ **命中率**：**热门图（如商品图）命中率高、个人照片几乎为 0**。**读法**：**"图像编码缓存"对"公共图"有效、对"个人图"无效**——**要分开设计**。
- **追问**：流式输出怎么做？
  - 要点：**三条**：① **SSE 或 WebSocket**（**SSE 更简单、够用**）；② **首 token 优先**（**prefill 一完成就发第一个 token**）；③ **分块传输 + 心跳**（**避免中间层超时**）。**注意**：**"多模态输出"（图生图）会破坏流式假设**（**因为图像要整体生成**）。**读法**：**"流式的关键是'首 token 时间'而不是'总时间'"**。
- **追问**：怎么定价/算成本？
  - 要点：**按"token 等价"计费**：① **图像按其 token 数折算**（**本机 333–1,332**）；② **或用"每张图固定价"**（**对用户更可预期**）；③ **成本端**：**\$2/GPU·h、2.5 请求/秒 → 每请求约 \$0.00022 的算力成本**（**再加存储与网络**）。**读法**：**"图像按 token 折算"是主流做法**（**因为它与真实成本成正比**）。
- **追问**：这道题与"ChatGPT 规模的服务栈"有什么区别？
  - 要点：**多模态特有的四点**：① **输入不再是纯文本**（**要处理二进制、要预处理**）；② **图像 → token 的放大效应**（**成本不可控**）；③ **降级策略更丰富**（**降分辨率/限图数**）；④ **隐私面更大**（**图像可能含人脸/证件**）。**读法**：**"输入侧的多态性"是多模态服务的本质区别**（**串 [[openai-17]] 的纯文本版本**）。
