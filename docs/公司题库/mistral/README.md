# Mistral AI 面试题库

Mistral AI 是「前沿 AI 实验室」组里的第一家公司，本目录收录 8 道题，**已全部上线**。

按 [README.zh-CN.md](../../../README.zh-CN.md) 的公开信息，它的流程大致是：招聘官初筛 → 技术面（Python 与 ML 基础）→
结对编程轮，现场构建一个小型 LLM 支撑的服务 → 深入拷问 transformer 与 serving 内部原理 → 应用类岗位的客户场景轮 → 文化轮。
这条流程解释了这 8 道题的形状：**一半是自家模型的内部原理与推理账本，一半是把开源权重交付进客户环境时的工程判断**。
和只问「你用过哪些模型」的公司不同，这里的题面默认你读过 Mistral 7B 与 Mixtral 的配置，并且愿意当场把数字算出来。

## 这家公司在考什么

8 道题按专题分布如下，可以看出它是一套「自家模型 + 客户交付」的组合：

| 专题 | 题号 | 落点 |
| --- | --- | --- |
| [编程与数据结构](../../编程与数据结构/README.md) | 01 | 结对编程：LLM 服务的分层、外部依赖失败处理、流式与可观测 |
| [LLM 内部原理与架构](../../LLM%20内部原理与架构/README.md) | 02、03 | 自家模型的 config 与机制：GQA、滑窗、稀疏 MoE 的账本 |
| [推理、服务与 GPU 性能](../../推理、服务与%20GPU%20性能/README.md) | 04、05 | KV cache 容量规划、量化选型与精度回归 |
| [Agent 与工具调用](../../Agent%20与工具调用/README.md) | 06 | function calling 的机制与生产可靠性 |
| [微调、后训练与对齐](../../微调、后训练与对齐/README.md) | 07 | 客户任务微调后的灾难性遗忘与交付回滚 |
| [AI 系统设计](../../AI%20系统设计/README.md) | 08 | 不能外发数据时的 on-prem 私有化部署 |

**主线一：开源权重与推理效率。** 02、03、04 三题要求的不是「听说过」，而是把 Mistral 7B 与 Mixtral 的配置当成已知量当场推数字：
32 层、32 个 Q head、8 个 KV head、head_dim 128、窗口 4096、8 个专家每 token 取 top-2。
02 与 04 是同一本 KV cache 账的两种问法——前者问机制（GQA 改哪个乘数、SWA 改哪个乘数、代价在哪），后者问容量（每 token 多少字节、一块卡能跑多少条序列、滚动缓冲怎么落）。
03 则要求把「总参数（容量与显存）」和「激活参数（每 token 算力与带宽）」两本账分开，这也是稀疏 MoE 最容易被背结论糊弄过去的地方。

**主线二：量化交付与客户场景微调。** 05 与 07 都是「客户现场出事了」的题型：05 是量化之后质量到底有没有掉，
07 是微调之后通用能力退化。两题共用同一套方法论——先钉死评测 harness，再只改一个变量，报相对差值而不是绝对值。
这类题的分差不在于知道 GPTQ、AWQ 还是 LoRA，而在于有没有把「证明」当成实验设计，以及有没有把交付物说清楚（交哪种量化权重、KV cache 用哪个精度、adapter 怎么合并与回滚）。

**主线三：私有化与合规边界。** 08 把这些线索收在一起：不能外发数据意味着从链路里删掉外部处理者，
容量规划要同时报节点数、功耗与利用率两笔账（on-prem 真正贵在利用率，不在卡数），并且要为无外网环境准备镜像、验签、离线评测与降级阶梯。

**与应用工程的接口。** 01 与 06 是这套题里最「动手」的两道：01 对应结对编程轮，考的是先定接口、把外部依赖的失败分类处理干净；
06 考的是 function calling 的两层机制与把端到端成功率当指数项来算的成本意识。

跨公司专题的重叠（同一考点在别的专题里有更系统的展开）：
[LLM 内部原理与架构](../../LLM%20内部原理与架构/README.md) 覆盖 02、03 的理论前置，
[推理、服务与 GPU 性能](../../推理、服务与%20GPU%20性能/README.md) 覆盖 04、05 的容量与量化，
[评估与可观测性](../../评估与可观测性/README.md) 是 05、07「证明没退化」的度量底座，
[微调、后训练与对齐](../../微调、后训练与对齐/README.md) 展开 07 的四层缓解手段，
[Agent 与工具调用](../../Agent%20与工具调用/README.md) 展开 06 的工具 schema、终止条件与审批，
[编程与数据结构](../../编程与数据结构/README.md) 里有 01 需要的 SSE 解析、限流与异步批处理实现题，
[RAG 与检索](../../RAG%20与检索/README.md) 是 07 里「要新知识就别微调」的替代路线，
[安全、安保与负责任 AI](../../安全、安保与负责任%20AI/README.md) 与 [AI 系统设计](../../AI%20系统设计/README.md) 分别对应 08 的合规边界与端到端部署。

## 建议学习顺序

两条路径都建议从 02 与 04 起步：这两题是后面所有容量与量化讨论的共同语言。

**路径 A：推理 / 研究岗（也是这家的主线）。** `02 → 04 → 03 → 05 → 08`。
先在 02 把 GQA 与滑窗各自改哪个乘数讲清，再用 04 把它算成显存与并发，接着用 03 换到 MoE 的两本账，
然后用 05 把「换 dtype 之后重算同一本账」补齐，最后在 08 里把所有账汇成一次 on-prem 容量与利用率规划。

**路径 B：应用 / 交付岗。** `01 → 06 → 07 → 05 → 08`。
01 给出服务骨架（分层、失败分类、轨迹），06 把这条骨架上的工具调用做到生产可靠（幂等、预算、外部验证器），
07 与 05 是客户交付里的两类高频事故（微调回归、量化回归），08 是端到端的私有化综合题。

只够时间刷一遍的最小集合：`02 → 04 → 05 → 07`。这四题覆盖了 KV cache 账本、量化交付与微调回归，
也是这家公司区分度最高的部分；01 与 06 建议动手写一遍骨架，光看题解收益有限。

## 自测清单

能不看资料回答下面这些问题，说明这个公司题库过关了：

- 一个 LLM 服务你会切成哪四层？`answer()` 的返回结构里放哪四个字段，入口层为什么不写业务逻辑？
- 数据补充用已知字段预取还是让模型通过 function calling 自己查？两种路线的延迟与费用怎么算，循环步数上限从哪里反推？
- 第三方 API 返回 429、400、空结果或超时时，分别该重试、该回灌还是该当事实？为什么超时不能当失败？
- Mistral 7B 的 KV cache 每 token 是多少字节？GQA 相对 MHA 省的是 4× 还是 8×，为什么？滑窗封顶的单序列占用是多少，窗口外的信息靠什么传进来、代价是什么？
- Mixtral 8×7B 的总参数、激活参数、decode 每 token 的权重读取量各是多少？为什么省算力与带宽不等于省显存？
- 报 serving 显存时哪四块账必须分开列？同样约 56 GiB 的 KV 池，窗口满载与 32k 全长分别能跑多少条序列？
- 滚动缓冲区缓存的掩码要挡哪三类位置？K 应该在入槽之前还是之后做 RoPE？
- 量化选型前要问客户哪三件事？per-group 128 加 FP16 scale 实际是多少 bit？W4A16 与 W8A8 省的分别是字节还是算力？
- 怎么证明量化或微调之后质量没有下降？（基线可复现、单变量、相对差值、噪声范围、分层评测加业务集）
- function calling 的约束解码层与运行时层各做什么？工具定义为什么是每轮重发的常驻成本？20 步 agent 的单步正确率从 0.95 提到 0.99，端到端成功率变化多少，上线门槛该看平均成功率还是 pass^k？
- 微调后客户指标涨、通用能力退化，你和权重无关的排查清单有哪些？四层缓解分别落在数据、参数、目标还是流程层？
- 5 万员工每天 6 次的量，均值 QPS 与峰值差多少倍？为什么 on-prem 的单位 token 成本会比满载口径贵一个数量级？
