## 一句话答案

> 这题考的不是「你做过什么厉害的东西」，而是**你有没有把模型接到业务指标上、并且能诚实归因**。所以两段叙述都要给出同一条**价值链的四段**：模型指标（离线）→ 用户行为（点击、完成、时长）→ 业务指标（转化、留存、抽成）→ 财务口径（收入、成本、毛利）。每一段都会衰减，**能说清衰减发生在哪一段，比报出最终数字更重要**。
> 成功案例必答四要素：**基线是什么、增量相对谁、统计上是否显著、有没有把别的指标做坏**（护栏）。
> 失败案例必答三件事：**当时基于什么假设、哪条假设错了、因此改了什么机制**。最后的落点是机制而不是情绪——例如「从此我们上线前强制定义护栏指标」「把标签延迟写进验收窗口」「把代理指标与真实目标的距离做成评审项」。

## 面试官在考什么

- **业务价值的可量化性**：能不能把「提升了体验」翻译成可核算的量（增量 GMV、抽成、留存、成本）。只会说「CTR 提升了 3%」而没有业务口径，说明你离业务太远。
- **增量归因的纪律**：是否知道「上线后的指标上涨」不等于「因为模型」。要能说出对照（A/B、地理对照、switchback）、预注册分析、以及如何排除季节性与其它并发改动。
- **对代理指标距离的自觉**：CTR 是代理，真正的目标是留存与长期价值；能否举出「代理涨了、目标没动」的例子（串 [[consumer-ml-02]]）。
- **失败归因的诚实度**：是归结为自己可控的机制（假设没验证、护栏没设、标签延迟没等、上线链路有损），还是归结为「业务方不支持」「数据质量差」这类外部原因。
- **是否把教训机制化**：优秀的回答会说出**流程上的改动**（门禁、验收窗口、评审清单），而不是「我以后会更小心」。

**常见错误答案**

- 只讲技术难度（「我训了一个两塔模型」）而不讲业务结果，或只讲结果而不讲如何归因。
- 用「上线后 DAU 涨了 10%」当证据——同期的市场活动、竞品宕机、季节性都可能是原因。
- 失败案例挑一个「其实不怪我」的故事（需求被砍、数据没给），这会让面试官怀疑你的复盘能力。
- 把成功案例的增量说得过大且无法解释机制（数字越大越要被追问「为什么不是季节」）。

## 原理与推导

### 1. 价值链四段与常见的衰减点

| 段 | 量 | 常见衰减原因 |
| --- | --- | --- |
| 模型指标 | AUC、NDCG、离线 CTR | 离线评测集与线上分布不一致；离线指标用的是日志回放（有偏） |
| 用户行为 | 点击率、完成率、会话时长 | 位置偏差（模型把好位置给了自己）、展示结构变化、疲劳 |
| 业务指标 | 转化、留存、抽成、投诉 | 代理指标与目标脱节；短期涨长期跌（把用户推走） |
| 财务 | 收入、成本、毛利 | 增量被补贴/成本吃回；单位经济性没算（串 [[consumer-ml-09]] 的算例） |

**面试时最强的表达**：先说一个你亲身经历的衰减（例如「离线 AUC +2%，线上点击没动，因为曝光结构变了」），再说你怎么定位它。这比报一个漂亮数字可信得多。

### 2. 增量归因的三种证据强度

1. **最强：随机化实验**——A/B 或地理随机化，预注册主指标与护栏，跑满预设时长与样本量。注意：切换式实验会被溢出污染（用户/司机跨组迁移），地理随机化更稳（串 [[evaluation-09]]）。
2. **中等：准实验**——中断时间序列、双重差分、倾向得分匹配。要论证「平行趋势」等假设，且必须承认残余混淆。
3. **最弱：上线前后对比**——几乎不能作为因果证据，只能作为线索。用它下结论是行为面里最常见的减分点。

### 3. 失败案例的六类根因（按可控性排序，选一个你真正负责过的）

1. **假设没验证**：默认「用户会喜欢更相关的内容」，但相关性不等于满意度（长会话 vs 快速找到答案）。
2. **代理指标选错**：优化点击导致标题党，短期点击涨、长期留存跌。
3. **约束遗漏**：没考虑库存/供给/合规，模型给出的最优解在业务上不可执行。
4. **上线链路有损**：离线效果好但线上特征延迟、缺失回退、或排序后还有业务重排把效果抹平（串 [[consumer-ml-04]] 的训练-服务偏斜）。
5. **反馈回路**：用自己产生的日志训练自己，模型越来越窄、探索不足；这正是 performative prediction 描述的「部署改变分布」问题——忽略它时表现为莫名其妙的分布漂移，通常被误当作需要重训（串 [[consumer-ml-13]]）。
6. **组织与节奏**：上线时机与业务周期错位（大促后上线）、或没有 owner 跟进后续迭代。

### 4. 把教训机制化的三种做法

- **上线前**：强制写「成功指标 + 护栏指标 + 归因方案」三件套，没有就不给排期（可引用 Google 规则清单里的工程取向：先建立指标与基线，再谈模型复杂度）。
- **上线后**：固定复盘窗口（例如两周后与一个月后各一次），并按价值链四段逐段核对衰减，而不是只看一个总指标。
- **长期**：把失败案例写进团队的评审清单与门禁（例如「标签延迟超过 T 的实验必须等到标签到齐才验收」），让教训变成流程而不是记忆。

### 5. 一个把「业务价值」算清的范例（在你自己的故事里套用）

假设你上线的是 feed 排序模型，效果是人均点击率从 3.0% 提到 3.3%（相对 +10%）。要能当场把它算成业务量：

$$\text{增量 GMV}=\text{DAU}\times\underbrace{\text{人均曝光}}_{\text{注意分母}}\times\Delta\text{CTR}\times\underbrace{\text{转化率}\times\text{客单价}}_{\text{从点击到成交}}$$

**分母陷阱**：CTR 的分母是曝光还是活跃用户？如果模型同时改变了曝光量，用「人均点击」和用「CTR」会得到不同结论。面试里主动指出这个陷阱，比报数字更能体现严谨。

## 数值与代码验证

### 表 1：两段叙述的必答要素对照

| 要素 | 成功案例 | 失败案例 |
| --- | --- | --- |
| 基线与对照 | 与谁比、怎么随机化 | 当时的基线是什么 |
| 增量口径 | 相对提升 + 绝对值 + 置信区间 | 期望的增量与实际观察 |
| 护栏 | 哪些指标没被做坏 | 哪个护栏当时缺失 |
| 时长 | 观察多久、是否覆盖完整周期 | 多久才发现无效 |
| 归因证据 | A/B 或地理随机化 | 事后如何定位 |
| 机制改动 | 如何固化经验 | 因此改了哪条流程 |

### 表 2：样本量直觉（双侧 α=0.05、power=80%）

| 基线 CTR | 想检测的相对提升 | 每组所需样本（曝光量） |
| --- | --- | --- |
| 3.0% | +2%（3.00%→3.06%） | ≈ 1,060,000 |
| 3.0% | +5%（3.00%→3.15%） | ≈ 170,000 |
| 3.0% | +10%（3.00%→3.30%） | ≈ 43,000 |
| 30% | +2%（30%→30.6%） | ≈ 91,000 |
| 30% | +5%（30%→31.5%） | ≈ 14,700 |

口径：两比例检验的正态近似，$n\approx 2(z_{1-\alpha/2}+z_{1-\beta})^2 p(1-p)/\delta^2$。**读法**：想检测 2% 的相对提升需要百万级曝光——这就是为什么「提升 1% 但显著」往往不可得，也是为什么很多团队误把噪声当提升。面试里能报出这个量级，说明你真做过实验。

### 可运行代码

```python
# 1) 业务价值换算：把 CTR 增量算成 GMV / 抽成 / 毛利
DAU, EXPOSURES_PER_USER, CVR_FROM_CLICK, AVG_ORDER, TAKE_RATE = 1_000_000, 40, 0.05, 55.0, 0.20
def business_value(ctr, dau=DAU, exp=EXPOSURES_PER_USER, cvr=CVR_FROM_CLICK):
    clicks = dau * exp * ctr
    orders = clicks * cvr
    gmv = orders * AVG_ORDER
    return clicks, orders, gmv, gmv * TAKE_RATE

base = business_value(0.030)
lift = business_value(0.033)
print(f"基线：点击 {base[0]:,.0f}，订单 {base[1]:,.0f}，GMV {base[2]:,.0f}，抽成 {base[3]:,.0f}")
print(f"新版：点击 {lift[0]:,.0f}，订单 {lift[1]:,.0f}，GMV {lift[2]:,.0f}，抽成 {lift[3]:,.0f}")
print(f"日增量：点击 {lift[0]-base[0]:+,.0f}，订单 {lift[1]-base[1]:+,.0f}，"
      f"GMV {lift[2]-base[2]:+,.0f}，抽成 {lift[3]-base[3]:+,.0f}（相对 {(lift[3]/base[3]-1):+.1%}）")

# 2) 样本量：想检测多大的相对提升需要多少曝光
def n_per_group(p, rel, alpha=0.05, power=0.8):
    from math import sqrt
    z_a, z_b = 1.959964, 0.841621
    p2 = p * (1 + rel)
    d = abs(p2 - p)
    return 2 * (z_a + z_b) ** 2 * p * (1 - p) / d ** 2

print("\n每组所需样本量（双侧 α=0.05，power=80%）")
for p in (0.03, 0.30):
    for rel in (0.02, 0.05, 0.10):
        print(f"  基线 CTR {p:.0%}，检测相对 +{rel:.0%} -> {n_per_group(p, rel):>12,.0f}")

# 3) 陷阱演示：同一批数据，用 CTR 与人均点击给出不同结论
base_imp, new_imp = 40.0, 36.0          # 新模型降低了曝光量
base_ctr, new_ctr = 0.030, 0.033
print(f"\nCTR：{base_ctr:.3%} -> {new_ctr:.3%}（{new_ctr/base_ctr-1:+.1%}）看起来涨了")
print(f"人均点击：{base_imp*base_ctr:.3f} -> {new_imp*new_ctr:.3f} "
      f"({(new_imp*new_ctr)/(base_imp*base_ctr)-1:+.1%}) —— 曝光减少后反而可能下降")
```

预期输出要点：第 1 段把 +10% 的相对 CTR 提升换算成日增 GMV 与抽成（数量级可直接用于面试叙述）；第 2 段显示基线 3% 时检测 +2% 需要每组约百万曝光，而检测 +10% 只需约 4.3 万——**这就是「显著性」的真实价格**；第 3 段演示分母陷阱：CTR 涨 10%、但若曝光从 40 降到 36，人均点击反而下降约 1%——面试里主动讲这个陷阱，比报数字更加分。

## 常见追问

- **追问**：你怎么知道提升不是季节性？
  - 要点：随机化对照（同期并行）、覆盖完整周期（至少一周且包含周末）、以及用**同比**（与上周同日）而非环比辅助判断。若无法随机化，用中断时间序列并论证平行趋势假设。
- **追问**：主指标涨了但护栏指标（例如留存或投诉率）变差，上线吗？
  - 要点：不上。护栏的作用就是「一票否决」；正确动作是定位冲突来源（往往是代理指标选错，例如优化点击导致标题党），修完再评估。要能说出你在真实项目里设过哪条护栏。
- **追问**：失败那个项目如果重来，你会怎么改？
  - 要点：给出**可执行的三步**：先做最小可逆验证（小流量或影子流量确认点击真的会动）、把验收窗口延长到覆盖标签延迟、并把当时的假设写成可检验的判据。落到机制而非决心。
- **追问**：怎么说服业务方接受「更小的短期提升换长期留存」？
  - 要点：把两套口径都算成钱（短期抽成 vs 长期 LTV 与流失率），给出回本周期与风险区间；再用小流量灰度证明长期指标的走向（串 [[consumer-ml-09]] 的短期/长期算例）。
- **追问**：如果模型很好但工程链路拖后腿，你会怎么做？
  - 要点：先量化链路损失（特征延迟、回退率、重排抹平效果、p99 超时），把损失算成业务量再决定优化顺序；很多时候「提升模型」不如「修链路」划算（串 [[consumer-ml-04]]）。
- **追问**：你怎么衡量「没有带来业务价值」这件事本身？
  - 要点：定义清楚评估窗口与对照，区分「无效」（增量在噪声内）、「有效但被成本吃回」、「有效但方向错」（损害长期指标）三种情况；三者的处理动作不同。
