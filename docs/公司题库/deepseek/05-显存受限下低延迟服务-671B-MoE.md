## 一句话答案

> **先把「显存受限」翻译成三个具体数字**，再谈方案：
> $$M_{\text{weights}}=P_{\text{total}}\times b\quad(\text{FP8 时 }b=1)\qquad M_{\text{KV}}=\text{tokens}\times L\times d_{\text{kv}}\times b_{\text{kv}}\qquad M_{\text{act}}+\text{缓冲}$$
> **671B 在 FP8 下权重就是 671 GB**（4-bit 约 335 GB）——所以「显存受限」通常意味着**你必须用 16–32 张卡，或接受卸载**。
> **六个手段，按「性价比」排序**：
> ① **量化**：FP8 权重（671 GB）甚至 4-bit（335 GB）——**收益最大、代价是质量需重评测**；
> ② **MLA 压缩 KV**（V3 的关键设计）：KV 只存**低秩潜向量 + RoPE 分量**，$d_{\text{kv}}=576$ 而不是 $2\times n_h\times d_h$。以 61 层为例：**34.3 KB/token（FP8）**，而同规模 MHA 风格的 70B 是 **320 KiB/token**（本仓库统一常数）——**差 9.3 倍**。这让**长上下文与高并发在显存上变得可行**；
> ③ **专家并行（EP）+ 放置**：256 个路由专家分散到各卡（每卡 $256/\text{EP}$ 个），**共享专家每卡都放**；用**分层 all-to-all**（先节点内、再跨节点）与**热点专家复制**降低跨节点流量；
> ④ **连续批处理 + 分块预填充**：MoE 的解码是**访存受限**的——**同一份专家权重读一次可以服务整个 batch**，所以**批越大、单 token 成本越低**；用 chunked prefill 保证长请求不阻塞解码（保 TTFT 与 TPOT）；
> ⑤ **MTP 投机解码**（串 [[deepseek-03]]）：减少解码步数，接受率决定收益；
> ⑥ **预填充/解码分离**：两个阶段的瓶颈不同（预填充算力受限、解码访存受限），分离后可各自用最合适的并行策略与批大小（串 [[inference-serving-07]]）。
> **实在放不下时的兜底——专家卸载**：把一部分专家放主机内存/NVMe，按需取回。**代价是 PCIe 带宽**：本机算例显示，**卸载 25% 的专家就可能让单步时间增加数倍**（详见下文），所以**卸载只能作为「能跑起来」的兜底，不是低延迟方案**。
> 一句话判据：**「先量化、再压 KV、再分专家、再批处理、最后才谈卸载」**——顺序错了，低延迟就无从谈起。

## 面试官在考什么

- **是否先算账**：能否立刻给出「671B × 1 字节 = 671 GB」这个量级，以及它需要多少张卡。
- **KV 的结构性差异**：能否指出 **MLA 是长上下文可行的前提**（35 KB/token vs MHA 的 320 KiB/token），而不是笼统说「用 PagedAttention」。
- **MoE 解码的本质**：能否说清「**权重读取服务整个 batch**」——所以 MoE 服务**偏好大批**，这与稠密模型一致但更极端（专家权重要读的量更大）。
- **通信的位置**：能否算出 all-to-all 的量级（每 token 每 MoE 层 $2\times k\times d\times b$ 字节），并说明**EP 度、分层通信、热点复制**如何影响它。
- **批与延迟的权衡**：能否指出**吞吐与延迟的最优点不同**（大批提吞吐、小批保延迟），以及 chunked prefill 的作用。
- **卸载的真实代价**：能否用 PCIe 带宽（约 25 GB/s 有效）算出卸载的延迟惩罚——**这是「显存受限」最直接的答案**。
- **量化与质量的取舍**：FP8/4-bit 的显存收益 vs 质量风险；**哪些部分可以更激进地量化**（专家权重 vs 注意力/路由）。
- **预填充与解码分离**：能否解释为什么分离能同时改善 TTFT 与 TPOT。
- **诚实**：承认「低延迟」与「低显存」在极端情况下**不可兼得**，并给出分级方案（满足 SLO 的最小配置）。

**常见错误答案**

- 只说「用张量并行把模型切开」（671B 的瓶颈在**专家权重的总量与通信**，不只是切分）。
- 忽略 KV（在长上下文场景 KV 可能超过权重）。
- 认为「MoE 激活少所以显存需求低」（**权重全都要驻留**，串 [[cohere-02]]）。
- 不做批处理分析（MoE 解码是访存受限，批是核心杠杆）。
- 把卸载当作常规方案（PCIe 带宽比 HBM 低两个数量级）。
- 不算 all-to-all（以为通信可以忽略）。
- 只谈吞吐不谈延迟（本题明确要求 low latency）。

## 原理与推导

### 1. 显存账（三个大头）

| 项 | 公式 | 671B / FP8 示例 |
| --- | --- | --- |
| 权重 | $P_{\text{total}}\times b$ | **671 GB**（4-bit 335 GB） |
| KV | $\text{tokens}\times L\times d_{\text{kv}}\times b_{\text{kv}}$ | MLA：**35 KB/token**（61 层、$d_{\text{kv}}=576$、FP8） |
| 激活与通信缓冲 | 与 batch、序列长度、EP 度相关 | 数十 GB 量级 |

**读法**：**权重是「必须先装下」的硬门槛**（$671$ GB ⇒ 至少 9 张 80 GB 卡**仅放权重**），而 **KV 决定了你能开多长上下文与多少并发**。

### 2. MLA：为什么 KV 能小 9 倍

MHA 风格（每层每 token 存 K 与 V 的完整头）：

$$d_{\text{kv}}^{\text{MHA}}=2\times n_h\times d_h$$

MLA（只存低秩潜向量 + 一个小的 RoPE 分量）：

$$d_{\text{kv}}^{\text{MLA}}=d_c+d_{\text{rope}}\quad(\text{V3 为 }512+64=576)$$

**例**：$L=61$ 层、FP8（1 字节）

| 方案 | 每 token KV | 32K 上下文单序列 |
| --- | --- | --- |
| MHA 风格（70B 级，320 KiB/token） | 320 KiB | **10.0 GB** |
| **MLA（576 × 61 × 1 B）** | **34.3 KB** | **1.1 GB** |

**读法**：**这不是「优化」，而是「可行性」**——320 KiB/token 时，几十路并发的 32K 上下文会把显存吃光。

### 3. 解码步的延迟分解（访存受限的本质）

MoE 解码一步要做三件事，取最大值（理想重叠）：

$$T_{\text{step}}\approx\max\Big(\underbrace{\frac{\text{本卡专家权重字节}}{\text{HBM 带宽}}}_{\text{访存}},\ \underbrace{\frac{\text{FLOPs}}{\text{峰值}\times\text{MFU}}}_{\text{算力}},\ \underbrace{T_{\text{all-to-all}}}_{\text{通信}}\Big)+T_{\text{开销}}$$

**关键**：访存项**与 batch 无关**（同一份权重服务整个 batch），算力项**与 batch 成正比**。所以：

$$T_{\text{step}}\approx\text{常数}\ \text{（小 batch）}\ \to\ \text{随 batch 线性增长（大 batch）}$$

$$\text{吞吐}=\frac{\text{batch}}{T_{\text{step}}}\ \text{先线性上升、后饱和}$$

**这就是「大批提吞吐」的数学**，也是**连续批处理**在 MoE 上尤其重要的原因。

### 4. all-to-all 的量级

每 token 每 MoE 层需要把隐藏状态发给 $k$ 个专家并收回结果：

$$\text{bytes/token/layer}\approx 2\times k\times d\times b$$

**例**（$k=8$、$d=7168$、FP8）：$2\times8\times7168\times1=114{,}688$ 字节 ≈ **112 KiB/token/层**；58 层 → **6.4 MB/token**。

**分摊到每张卡**（EP=32，负载均衡时）：

$$\text{每卡每层}\approx\frac{T\times k\times d\times b}{\text{EP}}$$

**例**：$T=2048$、EP=32 → 每卡每层约 **3.6 MB**；按 IB 有效 50 GB/s 计 → **约 73 µs/层**；58 层 → **约 4.3 ms/批**。**对比同批的算力时间约 0.5 s**（本机算例），即**通信约占 1%**——但注意这是**大 batch** 的情形；**batch 小到 1–8 时通信延迟（几十 µs 的固定开销）无法被算力掩盖**，这正是低延迟场景的难点（串 [[cohere-02]] 的同一机制）。

### 5. 卸载（offload）：显存受限的兜底

把比例 $\phi$ 的专家权重放主机内存，每步按需经 PCIe 取回：

$$T_{\text{extra}}\approx\frac{\phi\times P_{\text{total}}\times b}{\text{BW}_{\text{PCIe}}\times N_{\text{GPU}}}$$

**例**：$\phi=0.25$、$P=671$ GB（FP8）、PCIe 有效 25 GB/s/卡、16 卡 → $0.25\times671/(25\times16)=0.42$ **秒**——**比整个解码步（毫秒级）大两个数量级**（本机算例：卸载 5% 就要 **84 ms**，是纯访存时间的 **47 倍**）。所以：

- **卸载只能「让模型跑起来」**（吞吐降到个位数 token/s）；
- 若必须卸载，要**按热度放**（热专家常驻显存、冷专家卸载）并把**预取与计算重叠**；
- **更好的替代**：降低量化精度（4-bit 让权重减半到 336 GB，**8 张 80 GB 卡就能装下**）、缩小上下文、或**用更小的模型**。

### 6. 分级方案（按 SLO 从紧到松）

| 目标 | 配置 |
| --- | --- |
| **低延迟（TTFT < 1 s、TPOT < 50 ms）** | 16–32 卡、**FP8 权重**、EP 分层通信、连续批处理 + chunked prefill、MTP 投机解码、预填充/解码分离 |
| 高吞吐（离线批处理） | 更大 batch、更大 EP、允许排队；MTP 深度加大 |
| **显存极限（8 卡）** | **4-bit 量化**（336 GB 权重，**8 卡装得下**）+ 缩短上下文 + 限制并发；**不需要卸载** |
| 单机演示 | 4-bit + 小上下文 + 单并发（仅功能验证；若连 4-bit 也不允许，才考虑卸载） |

# 671B MoE 的服务容量与延迟模型：显存账、MLA vs MHA、batch 权衡、all-to-all、卸载代价
import math
from dataclasses import dataclass, field
from typing import Dict, List, Tuple

GB = 1e9                 # 十进制 GB（与显存标称一致：80 GB 卡 = 80e9 字节）
HBM_BW = 3.35e12          # H100 SXM5 HBM 带宽（仓库统一常数）
PEAK = 989e12             # H100 bf16 dense TFLOPs（仓库统一常数）
PCIE_BW = 25e9            # PCIe 4.0 x16 有效带宽（示例）
IB_BW = 50e9              # 每卡跨节点有效带宽（示例）
GPU_MEM = 80e9

@dataclass
class Model:
    name: str
    total_b: float = 671.0        # 总参数（十亿）
    active_b: float = 37.0        # 激活参数
    layers: int = 61
    moe_layers: int = 58
    d_model: int = 7168
    top_k: int = 8
    experts: int = 256
    kv_dim: int = 576             # MLA：d_c + d_rope
    weight_bytes: float = 1.0     # FP8
    kv_bytes: float = 1.0         # FP8 KV
    def weights_gb(self) -> float:
        return self.total_b * 1e9 * self.weight_bytes / GB
    def kv_per_token_kb(self) -> float:
        return self.layers * self.kv_dim * self.kv_bytes / 1024

M = Model("DeepSeek-V3 量级")
print("① 显存账（FP8 权重、FP8 KV、MLA）")
print(f"  权重：{M.total_b:.0f}B × {M.weight_bytes:.0f} B = **{M.weights_gb():.0f} GB**"
      f"（bf16 则 {M.weights_gb()*2:.0f} GB；4-bit 则 {M.weights_gb()/2:.0f} GB）")
print(f"  KV：{M.layers} 层 × {M.kv_dim} 维 × {M.kv_bytes:.0f} B = "
      f"**{M.kv_per_token_kb():.1f} KB/token**")
MHA_KV_KB = 320                # LLaMA-3-70B 风格 MHA（仓库统一常数，KiB/token）
print(f"  对照 MHA 风格（{MHA_KV_KB} KiB/token）：MLA 小 **{MHA_KV_KB/M.kv_per_token_kb():.1f}×**")
print("")
print(f"  {'上下文':>8} {'并发':>5} {'KV 总量':>10} {'权重+KV':>10} {'仅权重卡数':>11} {'含 KV 卡数':>11}")
for ctx, conc in ((8192, 8), (32768, 8), (32768, 32), (131072, 8)):
    kv_gb = ctx * conc * M.kv_per_token_kb() * 1024 / GB
    total = M.weights_gb() + kv_gb
    print(f"  {ctx:>8} {conc:>5} {kv_gb:>9.1f} GB {total:>9.1f} GB "
          f"{math.ceil(M.weights_gb()*GB/GPU_MEM):>11} {math.ceil(total*GB/GPU_MEM):>11}")
print("  读法：**权重是硬门槛（FP8 下 671 GB ⇒ 至少 9 张 80 GB 卡）**；而 MLA 让 32K×32 并发的 KV")
print("        只有十几 GB —— 换成 MHA 风格的 320 KiB/token，同样配置要 **300+ GB**，根本放不下")

# ---------- 解码延迟与吞吐随 batch 的变化 ----------
@dataclass
class Serving:
    n_gpus: int = 16
    ep: int = 16
    mfu: float = 0.30
    def gemm_eff(self, batch: int) -> float:
        """★ 小 batch 下每个专家只拿到极少数 token -> GEMM 很小 -> HBM 带宽利用率低。
        这里用一个随 batch 上升的效率因子（示例假设，实测需按 kernel 校准）。"""
        return min(0.85, 0.20 + 0.65 * (1 - math.exp(-batch / 96.0)))
    def step_time(self, batch: int) -> Dict[str, float]:
        # 访存：每卡读"本卡负责的激活专家权重"（与 batch 无关），再除以小 batch 效率因子
        active_bytes = M.active_b * 1e9 * M.weight_bytes
        per_gpu_bytes = active_bytes / self.n_gpus
        t_mem = per_gpu_bytes / (HBM_BW * self.gemm_eff(batch))
        # 算力：2 × 激活参数 × batch（全系统），再除以卡数
        flops = 2 * M.active_b * 1e9 * batch
        t_comp = flops / (PEAK * self.mfu * self.n_gpus)
        # all-to-all：每卡每层 (batch × k × d × bytes)/EP，58 层
        per_layer = batch * M.top_k * M.d_model * M.weight_bytes / self.ep
        t_comm = per_layer * M.moe_layers / IB_BW
        t_step = max(t_mem, t_comp, t_comm)
        return {"访存(ms)": t_mem * 1e3, "算力(ms)": t_comp * 1e3, "通信(ms)": t_comm * 1e3,
                "GEMM效率": self.gemm_eff(batch),
                "单步(ms)": t_step * 1e3,
                "吞吐(tok/s)": batch / t_step}
S = Serving()
print("")
print(f"② 解码延迟与吞吐随 batch（{S.n_gpus} 卡、EP={S.ep}、MFU {S.mfu:.0%}）")
print(f"  {'batch':>6} {'访存(ms)':>9} {'算力(ms)':>9} {'通信(ms)':>9} {'GEMM效率':>9} "
      f"{'单步(ms)':>9} {'吞吐(tok/s)':>12} {'瓶颈':<8}")
for b in (1, 8, 32, 128, 512, 2048):
    r = S.step_time(b)
    parts = {"访存": r["访存(ms)"], "算力": r["算力(ms)"], "通信": r["通信(ms)"]}
    bottleneck = max(parts, key=parts.get)
    print(f"  {b:>6} {r['访存(ms)']:>9.2f} {r['算力(ms)']:>9.2f} {r['通信(ms)']:>9.2f} "
          f"{r['GEMM效率']:>9.2f} {r['单步(ms)']:>9.2f} {r['吞吐(tok/s)']:>12.0f} {bottleneck:<8}")
print("  读法：**小 batch 时访存主导（单步时间几乎与 batch 无关）→ 吞吐随 batch 线性上升**；")
print("        到某个 batch 后算力接管 —— 这就是「吞吐与延迟最优点不同」的来源。")
print("        注意两点：① 低延迟要的正是小 batch（TPOT 由访存决定）；② 这里的数字是**乐观上界**：")
print("        真实系统在小 batch 下每个专家只拿到几个 token，GEMM 很小、HBM 利用率远达不到峰值，")
print("        再叠加 all-to-all 的固定延迟（见 ⑤），单流 TPOT 会比表中大一个数量级")

# ---------- 卸载的代价 ----------
print("")
print("③ 专家卸载的代价（PCIe 有效 25 GB/s/卡、16 卡）")
print(f"  {'卸载比例':>9} {'每步额外时间':>13} {'相对访存时间':>13} {'结论':<20}")
base_mem = S.step_time(32)["访存(ms)"]
for phi in (0.05, 0.1, 0.25, 0.5):
    extra = phi * M.weights_gb() * GB / (PCIE_BW * S.n_gpus)
    ratio = extra * 1e3 / base_mem
    note = "可接受（配预取）" if ratio < 3 else ("显著变慢" if ratio < 20 else "**吞吐崩塌**")
    print(f"  {phi:>9.0%} {extra*1e3:>12.1f} ms {ratio:>12.0f}x {note:<20}")
print("  读法：**卸载比例 10% 就让单步时间增加一个数量级以上** —— PCIe 比 HBM 慢两个数量级，")
print("        所以卸载是「让它跑起来」的兜底，不是低延迟方案；优先做量化与上下文控制")

# ---------- 分级配置 ----------
print("")
print("④ 分级方案（按 SLO 与卡数）")
CONFIGS = [
    ("低延迟服务（TPOT<50ms）", 32, 1.0, 8192, 16, "FP8 + EP32 + 连续批 + MTP"),
    ("高吞吐离线", 32, 1.0, 8192, 256, "FP8 + 大 batch + MTP 深度加大"),
    ("显存极限（16 卡）", 16, 0.5, 4096, 8, "4-bit + 短上下文 + 限制并发"),
    ("8 卡（4-bit 装得下）", 8, 0.5, 2048, 1, "4-bit + 短上下文 + 单并发"),
]
print(f"  {'场景':<22} {'卡数':>5} {'字节/参数':>10} {'上下文':>7} {'并发':>5} 关键手段")
for name, gpus, bp, ctx, conc, how in CONFIGS:
    m = Model("cfg", weight_bytes=bp, kv_bytes=min(bp, 1.0))
    need = math.ceil((m.weights_gb() + ctx*conc*m.kv_per_token_kb()*1024/GB) * GB / GPU_MEM)
    ok = "✓" if need <= gpus else f"✗（需 {need} 卡）"
    print(f"  {name:<22} {gpus:>5} {bp:>10.1f} {ctx:>7} {conc:>5} {how}  {ok}")
print("  读法：**低延迟的前提是「装得下 + 通信可控」** —— 卡数不足时只能降精度、缩上下文、限并发；")
print("        「低延迟」与「低显存」在极端处不可兼得，要按 SLO 选配置而不是追求极限")

# ---------- all-to-all 的可见性（为什么小 batch 难） ----------
print("")
print("⑤ all-to-all 在小 batch 下为何难以隐藏（固定延迟 vs 带宽）")
print(f"  {'batch':>6} {'通信带宽时间(ms)':>15} {'加固定延迟后(ms)':>16} {'占单步比例':>11}")
FIXED_LAT = 20e-6     # RDMA 往返 + kernel 启动（示例）
for b in (1, 8, 32, 128):
    per_layer = b * M.top_k * M.d_model * M.weight_bytes / S.ep
    t_bw = per_layer * M.moe_layers / IB_BW
    t_tot = t_bw + FIXED_LAT * M.moe_layers
    step = S.step_time(b)["单步(ms)"] / 1e3
    print(f"  {b:>6} {t_bw*1e3:>15.3f} {t_tot*1e3:>16.3f} {t_tot/step:>11.1%}")
print("  读法：**固定延迟（每层 20 µs × 58 层 ≈ 1.2 ms）在小 batch 下无法被算力掩盖** ——")
print("        这是低延迟 MoE 服务的核心矛盾：**要低延迟就得小 batch，而小 batch 通信无法摊薄**；")
print("        缓解手段是**减少跨节点跳数**（专家放置、分层通信）与**重叠**（DualPipe 式流水）")

预期输出要点（实跑）：① **FP8 下权重 671 GB（至少 9 张 80 GB 卡）**，**4-bit 则 336 GB（8 卡装得下）**；**MLA 让 KV 只要 34.3 KB/token**（同规模 MHA 风格 320 KiB/token，**差 9.3 倍**）——32K×32 并发的 KV 仅 36.8 GB，换成 MHA 要 300+ GB；② 解码延迟由**访存主导**：batch=1 时单步 3.34 ms（吞吐 299 tok/s，且这是**乐观上界**），batch=32 时 1.80 ms（17,813 tok/s），batch≥128 转为算力主导（64,151 tok/s 饱和）——**低延迟要的正是小 batch**；③ **卸载代价巨大**：卸载 5% 就要 **84 ms**（纯访存时间的 **47 倍**），所以卸载只是兜底，优先量化与上下文控制；④ 分级配置显示四种场景都能「装得下」，**卡数不足时靠降精度与限并发**——「低延迟」与「低显存」在极端处不可兼得；⑤ **all-to-all 的固定延迟（每层约 20 µs × 58 层 ≈ 1.16 ms）在小 batch 下占单步的 34.9%**，无法被算力掩盖——这正是低延迟 MoE 服务的核心矛盾。

## 常见追问

- **追问**：为什么不用纯张量并行（TP）而要专家并行（EP）？
  - 要点：**TP 每层都要 all-reduce，通信量与层数成正比且延迟敏感**；MoE 的专家是「按 token 路由」的天然分片单元，**EP 只传被路由到的 token**（通信量与激活专家数相关）。实践组合是 **TP 在节点内 + EP 跨节点 + DP 最外层**。**671B 的专家权重总量决定了必须 EP。**
- **追问**：MLA 的代价是什么？
  - 要点：① **计算更复杂**（需要额外的投影与吸收矩阵，训练/推理的 kernel 更复杂）；② **表达能力的近似**（低秩压缩是有损的，但论文显示质量不降反升）；③ **实现依赖**（需要专门优化的 kernel，否则算力开销会吃掉收益）。**它换来的 KV 缩小是长上下文可行性的前提。**
- **追问**：低延迟场景下 batch 该开多大？
  - 要点：**由 TPOT 目标反推**：TPOT ≈ 访存时间（与 batch 无关）+ 算力时间（∝ batch）。若访存 5 ms、算力允许 45 ms，则 batch 可以开到「算力时间 ≈ 45 ms」对应的值。**注意还要留出通信与调度余量**，并用**分块预填充**避免长请求把 TPOT 拉爆。
- **追问**：怎么在 8 卡上跑 671B？
  - 要点：**必须三件事同时做**——① **4-bit 量化**（权重降到约 335 GB，仍然装不下，所以还要）；② **卸载一部分专家**（或只用子集专家，质量受损）；③ **缩短上下文 + 单并发**。**结论是「能跑但很慢」**，适合功能验证而非服务。**更实际的选择是换更小的模型。**
- **追问**：为什么 MoE 服务比稠密模型更依赖批处理？
  - 要点：MoE 每步要读的**激活专家权重更多**（37B vs 同规模稠密的激活量），且**all-to-all 的固定延迟要靠批来摊薄**。所以**批是 MoE 服务的第一杠杆**——这也是为什么「低延迟」与 MoE 天然有张力（串 [[cohere-02]] 的同一结论）。
- **追问**：预填充/解码分离（PD 分离）为什么有用？
  - 要点：**两个阶段的瓶颈不同**：预填充是**算力受限**（大量 token 并行）、解码是**访存受限**。分离后预填充可以用大 batch + 高 MFU 配置，解码用小 batch + 低延迟配置，**互不干扰**（否则长预填充会把解码的 TPOT 拉爆）。代价是 **KV 传输**（把预填充产生的 KV 传给解码节点）与更复杂的调度。
