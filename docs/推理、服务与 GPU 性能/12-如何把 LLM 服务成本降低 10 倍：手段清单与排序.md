## 一句话答案

> 先把成本写成公式：单位成本（美元/1M 输出 token）= GPU 小时单价 / (每 GPU 每秒交付的有效 token × 3600) × 10⁶，再乘「浪费 token 系数」。所有手段都挂到分子或分母上，而分母侧（吞吐 × 利用率）的杠杆比分子侧（单价）大一个数量级。
> 排序原则是风险从低到高：无损的复用与调度 → 低损的精度压缩 → 动质量的模型与路由 → 采购与产品侧。按名义口径可复算出一个组合：batching 2.0× × FP8 权重与 KV 1.8× × prefix caching 1.39× × 60% 流量路由到 8B 2.13× × 输出上限 1.08× ≈ 11.5×；乘 SLO 余量与缓存命中波动 0.72 后 8.3×，把 batching 那一步按端到端口径折算则落到 7–8×。

## 面试官在考什么

- 有没有先把成本写成可分解的公式。列名词谁都会，能把每个手段映射到公式某一项的人才分得清主次。
- 能否给出**排序依据**：收益大小、实施周期、是否损失质量、是否互相重叠，而不是背一遍优化技巧清单。
- 是否知道每个杠杆的**前提与上限**。量化要 kernel 支持、prefix caching 要求前缀逐字节一致、路由要评测兜底——说不出这些就等于没在生产里做过。
- 是否区分延迟优化与成本优化。投机解码、P/D 分离首先是延迟手段，把它们当成省钱手段会算错账。
- 有没有度量与治理：先建指标再优化，优化前后在固定负载与 SLO 下 A/B，防止「省了钱但 p99 爆了、质量掉了」。

常见错误答案：

- 一上来就换更便宜的 GPU、砍单价。分子侧的上限只有 1.5–3×，且换合约的周期以月计；把利用率从 30% 提到 60% 就是 2 倍，且是调度问题。
- 把各杠杆的倍数直接相乘，报出「20 倍」。它们作用在同一份物理上限（带宽与 SLO）上，必须说明重叠与兑现折扣。

## 原理与推导

### 1. 成本公式：所有手段挂在哪里

按「交付 N 个有效输出 token 花了多少 GPU 时间」定义成本：

$$C_{\text{1M}} = \frac{p_{\text{GPU·h}} \cdot G \cdot t}{N_{\text{有效输出}}} \times 10^6$$

把它整理成每个杠杆都能对号入座的形式：

$$C_{\text{1M}} = \frac{p_{\text{GPU·h}}}{3600 \cdot T_{\text{eff}}} \times 10^6, \qquad T_{\text{eff}} = T_{\text{roofline}} \cdot \eta_{\text{MBU}} \cdot \eta_{\text{util}} \cdot \frac{1}{1+w}$$

| 因子 | 含义 | 谁能改它 |
| --- | --- | --- |
| $p_{\text{GPU·h}}$ | 每 GPU 每小时单价 | 采购、预留、spot、跨区域调度 |
| $T_{\text{roofline}}$ | 带宽或算力除以「每 token 要搬的字节数」得到的上限 | 量化（权重/KV 精度）、模型大小、KV 结构（GQA/MLA）、平均上下文长度 |
| $\eta_{\text{MBU}}$ | 实际达到峰值带宽/算力的比例 | batch 大小、continuous batching、chunked prefill、kernel 质量 |
| $\eta_{\text{util}}$ | GPU 有多少时间在做有用功 | 调度、抢占、缓存命中（prefill 直接被跳过）、流量削峰 |
| $w$ | 浪费 token 比例：重试、解析失败、过度生成、prompt 冗余 | 约束解码、max_tokens、stop 序列、prompt 精简 |

展开成两阶段后，每个杠杆的作用点更清楚：

$$t_{\text{req}} = \underbrace{\frac{2 N S_p}{A_{\text{eff}}}}_{\text{prefill：算力受限}} + \underbrace{\frac{S_o}{B} \cdot \frac{\text{bytes/token}}{BW_{\text{eff}}}}_{\text{decode：带宽受限，除以 batch } B}$$

$N$ 是参数量、$S_p$ 是 prompt 长度、$S_o$ 是输出长度。prefix caching 只动第一项，量化主要动第二项的分子，batch 只出现在第二项的分母，输出长度上限只动 $S_o$。**没有哪个杠杆能同时改所有项**，这就是「组合拳」的物理依据，也是不能随便相乘的原因。

### 2. 为什么分母侧优先

同样是 2 倍，两个方向的代价完全不同：

| 方向 | 手段 | 典型上限 | 实施周期 | 风险 |
| --- | --- | --- | --- | --- |
| 分子：降单价 | 预留实例、spot、换型号 | 1.5–3× | 周到月 | 合约、抢占、迁移 |
| 分母：提吞吐与利用率 | batching、缓存、量化、路由 | 5–10× | 天到周 | 工程质量、需评测兜底 |

分母侧还有一个结构性优势：它省的是**同一份硬件上的时间**，因此可以叠加；而单价下降是一次性的线性缩放。生产上的顺序通常是：先把 $\eta_{\text{util}}$ 从 30% 提到 60%（2× 现金流），再做权重与 KV 精度（$T_{\text{roofline}}$ 翻倍），最后才谈采购。

### 3. 排序清单

| 排序 | 分组 | 作用项 | 典型倍数 | 前提与上限 |
| --- | --- | --- | --- | --- |
| ① | 缓存与复用 | $\eta_{\text{util}}$、prefill | 1.3–2×；重复问答可达 10× | 前缀逐 token 一致、命中率由流量结构决定 |
| ② | 调度与批处理 | $\eta_{\text{MBU}}$、$\eta_{\text{util}}$ | 2–4× | 显存够开大 batch；受尾延迟约束 |
| ③ | 精度与量化 | bytes/token | 1.6–1.9×（FP8）、2–4×（INT4） | 需要对应 kernel；量化误差要评测 |
| ④ | 模型与架构 | $N$、KV 结构 | 5–9×（换小模型）、1.5–2.6×（路由） | 动质量，必须评测 + 回退 |
| ⑤ | 解码层 | $S_o$、$w$ | 1.05–1.3×；投机解码对成本中性 | 投机解码在算力饱和时无收益 |
| ⑥ | 容量与采购 | $p_{\text{GPU·h}}$、$\eta_{\text{util}}$ | 1.5–3×（单价）、2×（利用率） | 排队时间随利用率非线性上升 |
| ⑦ | 产品层 | $S_p$、$S_o$、$w$ | 1.05–2× | 影响用户体验，需要产品决策 |

表内倍数是**量级区间**，不是某篇论文的实测值：口径是「同一负载、同一 SLO 下，单位有效输出 token 成本下降的倍数」，区间来自公开工程经验与第 4 节的 roofline 复算。落到具体系统必须自己压测，这组区间只用于排序和沟通。

**① 缓存与复用。** 收益上限是「prefill 占总 GPU 时间的比例 × 命中率」，所以先测命中率再投入。三类：prefix/prompt caching（多轮对话与 agent 负载里 system prompt、工具定义、历史前缀占比高，收益最大）、精确缓存（完全相同的请求直接返回）、语义缓存（embedding 近似匹配，阈值设不好会答错）。注意 exact-prefix 规则：前缀必须从第一个 token 起连续一致，任何动态时间戳、随机 few-shot、按请求拼接的检索结果都会让命中率归零，细节见 [[inference-serving-05]]。

**② 调度与批处理。** continuous batching 消除 static batching「等最长序列」的空转，是分母侧最大的一笔；chunked prefill 把长 prompt 切块混进 decode 步骤，避免 prefill 阻塞 decode 造成的尾延迟尖峰；P/D 分离让两个阶段各自按最优 batch 与并行度扩缩，主要收益在尾延迟与利用率（1.2–1.5×）。抢占策略决定 SLO 内能把 batch 填多满，而 batch 上限往往由 KV 显存决定——所以它和量化、PagedAttention 是联动的。

**③ 精度与量化。** decode 带宽受限时，权重字节数减半几乎直接等于吞吐翻倍：FP8 权重理论上限 2×，考虑 kernel 与反量化开销实测 1.6–1.9×。KV cache 量化同时省显存（允许更大 batch、更长上下文）和每步 KV 读带宽，长上下文下收益比权重量化更明显。W4A16/INT4 把权重压到 1/4，但依赖 weight-only 反量化 kernel；FP4 需要 Blackwell 这一代硬件。前提是 kernel 支持：Hopper 有 FP8 tensor core，若走不到原生 FP8 kernel，量化反而更慢。各档位损失见 [[inference-serving-06]]。

**④ 模型与架构。** 换更小的模型是单点收益最大的一步（70B 到 8B 是近 9 倍），但必须用蒸馏或领域微调把质量补回来。路由与级联是折中：小模型先答，置信度不足或校验失败再回退大模型，收益为

$$G_{\text{route}} = \frac{1}{\alpha/r + (1-\alpha)}$$

$\alpha$ 是路由到小模型的流量比例、$r$ 是大模型与小模型的单请求成本比（按参数量近似取 70B/8B ≈ 8.75，取反会把公式用错）。GQA/MQA/MLA 缩小的是 KV 而不是权重，收益体现在「同样的卡能装更多并发、更长上下文」；MoE 在 decode 阶段只需搬激活专家的权重，但全部专家都要常驻显存，小 batch 下通信与显存会吃掉一部分收益。

**⑤ 解码层。** max_tokens、stop 序列、早停直接砍 $S_o$；结构化输出与约束解码消灭「解析失败 → 重试」这条最贵的浪费（一次重试等于双倍成本）；精简 system prompt 与 few-shot 数量砍的是 $S_p$，按 prefill 时间计价而不是按 token 数计价。投机解码是延迟手段：它增加 FLOPs、减少每 token 的权重读取，低 batch（带宽受限）时顺带提吞吐，大 batch（算力饱和）时被拒绝的 draft 变成纯浪费，成本中性偏负，见 [[inference-serving-04]]。

**⑥ 容量与采购。** 利用率 30% → 60% 正好是 2×，但平均排队时间按 $\rho/(1-\rho)$ 增长（M/M/1 口径）：$\rho=0.6$ 时已是服务时间的 1.5 倍，$\rho=0.8$ 时 4 倍。所以利用率通常停在 0.6–0.7 再往上就要靠加卡而不是压榨。spot 与预留能砍单价，代价是抢占与迁移成本；选型时看「显存带宽每美元」而不是 FP16 峰值算力，因为 decode 是带宽受限的。

**⑦ 产品层。** 限制上下文长度（$S_p$ 与 KV 显存同时线性下降）、按需降级（高峰期返回更短答案或小模型）、Batch API（把延迟不敏感的流量折叠，常见 1.5–2× 折扣）、请求合并、流式输出（不改成本但改感知延迟，所以产品上常做但不算省钱手段）。这一层收益有限，却往往是最容易拿到、也最容易被工程团队忽略的一层。

### 4. 十倍怎么凑出来

以 8×H100 服务 70B、平均 4000 token prompt / 500 token 输出、baseline 每 GPU 187.5 输出 token/s（美元 2.5/GPU·小时 → 3.70 美元/1M tokens）为例，逐项叠加：

| 顺序 | 杠杆 | 倍数 | 累计 | 单位成本 |
| --- | --- | --- | --- | --- |
| 0 | baseline（bf16、static batching、无缓存） | 1.00× | 1.00× | 3.70 |
| 1 | continuous batching + chunked prefill | 2.00× | 2.00× | 1.85 |
| 2 | FP8 权重 + FP8 KV | 1.80× | 3.60× | 1.03 |
| 3 | prefix caching（3000/4000 前缀，60% 命中） | 1.39× | 5.00× | 0.74 |
| 4 | 60% 流量路由到 8B | 2.13× | 10.66× | 0.35 |
| 5 | 输出上限 −20% | 1.08× | 11.51× | 0.32 |
| 6 | 乘 SLO 余量 0.8、缓存命中波动 0.9 | 0.72 | **8.3×** | **0.45** |

单位是美元/1M tokens，名义口径是「每个杠杆都按自身瓶颈的上限、作用于全量成本」。四点必须主动说明：

- **不可简单相乘。** 第 1、2 步都在把 decode 推向同一个带宽上限：baseline 只有 roofline 的约 32%，batching 先把它推到 60% 左右，FP8 再把上限本身抬高，二者的收益部分重叠。更关键的是口径：2.0× 是 decode 口径的上限，而本负载 62% 的时间在 prefill（表 4），按表 4 的账本折算成端到端收益更接近 1.2–1.4×，整条链的名义值随之落到 7–8×。第 3 步只作用于 prefill、第 5 步只作用于 decode，这两项才是互不重叠、可以相乘的。
- **SLO 折扣。** 第 6 行的 0.8 来自「必须留 headroom 才能守住 p99」：利用率越高，排队时间按 $\rho/(1-\rho)$ 上升，再考虑突发流量，实际只能兑现名义收益的八成左右。
- **10× 的落点取决于流量结构，不取决于 kernel（以下同名义口径）。** 把路由比例从 60% 提到 70%（$G_{\text{route}}$ 从 2.13 升到 2.63），名义倍数 14.2×、折扣后 10.2×；只把 prefix 命中率从 60% 提到 75%（1.54×），名义 12.8×、折扣后 9.2×，仍差一点。换句话说，越过 10× 的那几倍来自「哪些请求可以不用大模型答」，而不是来自更底层的优化。

### 5. 度量与治理

先建指标再优化，否则无法判断收益是否真实：

- 单位成本：美元/1M tokens（输入与输出分开记），按租户/模型/路由分支拆开。
- 效率：$\eta_{\text{MBU}}$ 与 prefill/decode 的 GPU 小时占比、MFU（prefill 侧）、batch 填充率。
- 流量结构：prefix cache 命中率、语义缓存命中率、平均输入/输出长度、路由比例、回退率、重试率。
- 质量与体验：任务成功率或人工评分、TTFT / TPOT 的 p50 与 p99、超时率。

治理规则：任何一项优化都在固定负载与固定 SLO 下做 A/B，同时看成本与 p99；量化、路由、蒸馏各自有独立的回归门禁与线上回退开关；「小模型失败再回退大模型」的最坏成本是「小模型浪费 + 大模型重试」，必须把回退率算进账。

## 数值与代码验证

以下按 H100 SXM5 口径复算：HBM3 带宽 3.35 TB/s，bf16 稠密算力 989 TFLOPs（不含稀疏），FP8 稠密算力 1979 TFLOPs，价格取 2.5 美元/GPU·小时。内存单位用二进制（1 GiB = 1024³ B），带宽与权重用十进制 GB。

**表 1：70B 模型的基础换算**

| 量 | 计算 | 结果 |
| --- | --- | --- |
| bf16 权重 | $70 \times 10^9 \times 2$ B | 140 GB（130.4 GiB） |
| FP8 权重 | $70 \times 10^9 \times 1$ B | 70 GB |
| INT4 权重 | $70 \times 10^9 \times 0.5$ B | 35 GB |
| batch=1 decode 上限（bf16） | 3350 ÷ 140 | 23.9 token/s |
| batch=1 decode 上限（FP8） | 3350 ÷ 70 | 47.9 token/s |
| bf16 拐点（roofline knee） | 989 ÷ 3.35 | 295 flops/byte |
| FP8 拐点 | 1979 ÷ 3.35 | 591 flops/byte |

**表 2：KV cache（LLaMA-3-70B：80 层、8 个 KV 头、head_dim 128、bf16）**

| 项 | 计算 | 结果 |
| --- | --- | --- |
| 每 token | $2 \times 80 \times 8 \times 128 \times 2$ | 327,680 B = 320 KiB |
| 单序列 4k | 320 KiB × 4096 | 1.25 GiB |
| 单序列 32k | 320 KiB × 32768 | 10.0 GiB |

| KV 读追平权重读的临界总上下文 | 140 GB ÷ 327,680 B | 42.7 万 token（batch 32 时约 13.4k） |

**表 3：每步字节数与 per-GPU roofline（8×H100、TP=8、平均上下文 4k）**

| 配置 | 每步每卡读取 | 每步时间 | 集群 token/s | 每卡 token/s | MBU / 备注 |

| 项 | 计算 | 结果 |
| --- | --- | --- |
| prefill 4000 token | $2 \times 70 \times 10^9 \times 4000$ ÷（8 × 1979 T × 0.4） | 88.4 ms 集群时间 |
| decode 500 步 | 500 × 3.41 ms ÷ 32（3.41 ms 即表 3 的 FP8 batch 32 每步时间） | 53.3 ms |
| 合计 | | 141.7 ms（prefill 占 62%） |
| 3000-token 前缀 100% 命中 | prefill 降到 1000 token | 75.4 ms，1.88× |
| 命中率 60% | $1 - 0.6 \times 0.75 = 0.55$ 倍 prefill | 101.9 ms，**1.39×** |

命中率 $h$ 与可复用前缀比例 $\sigma$ 的通用式：$G_{\text{cache}} = \dfrac{t_p + t_d}{(1-h\sigma)t_p + t_d}$。缓存与量化作用在公式的不同项上（$t_p$ 与 $t_d$），收益互不抵消，两件都要做；顺序上先做缓存，因为它无损、且能先拿到命中率这份数据，量化则要等 kernel 与评测就绪。

**表 5：利用率与排队（M/M/1 口径）**

| 利用率 $\rho$ | 相对单位成本 | 平均排队时间（× 服务时间） |
| --- | --- | --- |
| 0.3 | 1.00× | 0.43 |
| 0.5 | 0.60× | 1.00 |
| 0.6 | 0.50× | 1.50 |
| 0.7 | 0.43× | 2.33 |
| 0.8 | 0.38× | 4.00 |
| 0.9 | 0.33× | 9.00 |

```python
BW, BF16, FP8, P_GPU, G = 3.35e12, 989e12, 1979e12, 2.5, 8   # H100 SXM5：带宽 / bf16 / fp8 / 单价 / 卡数


def cost_1m(tok_s_per_gpu, p=P_GPU):
    """单位成本 = 单价 / (每 GPU 每秒交付的 token × 3600)"""
    return p / (tok_s_per_gpu * 3600) * 1e6


print(round(cost_1m(187.5), 3), round(cost_1m(1875), 3), round(BF16 / BW))
# 3.704 0.37 295   基线 3.70 美元/1M；10× 等价于每卡 1875 token/s；bf16 拐点 295 flops/byte

w_bf16, w_fp8 = 70e9 * 2, 70e9
print(round(BW / w_bf16, 1), round(BW / w_fp8, 1), round(70e9 * 0.5 / 1e9, 1))
# 23.9 47.9 35.0   batch=1、纯带宽受限时的 token/s 上限；INT4 权重 35 GB

kv_tok = 2 * 80 * 8 * 128 * 2                      # 2·L·H_kv·d_head·bytes
print(kv_tok / 1024, round(kv_tok * 32768 / 1024**3, 2), round(8 * 80e9 / kv_tok / 1e6, 2))
# 320.0 10.0 1.95  每 token 320 KiB；单条 32k 会话 10 GiB；8×80GB 共容 195 万 token


def tok_per_gpu(batch, ctx, w_bytes, kv_bytes_per_tok, bw=BW, gpus=G):
    """一个 decode step 要读「权重/卡 + batch×ctx×KV/卡」，据此算 per-GPU 吞吐上限"""
    return (batch / ((w_bytes / gpus + batch * ctx * kv_bytes_per_tok / gpus) / bw)) / gpus


print(round(tok_per_gpu(32, 4096, w_bf16, kv_tok)),
      round(tok_per_gpu(32, 4096, w_fp8, kv_tok / 2)),
      round(w_bf16 / kv_tok / 1e6, 3))
# 586 1172 0.427   bf16 与 FP8(权重+KV) 的 batch=32/4k 上限；KV 读追平权重读的临界总上下文

t_p, t_d = 88.4, 53.3                                       # 表 4：每请求分摊到的 prefill / decode 集群毫秒
cache_gain = (t_p + t_d) / ((1 - 0.6 * 0.75) * t_p + t_d)    # 60% 命中、可复用前缀占 75%
out_gain = (t_p + t_d) / (t_p + 0.8 * t_d)                   # 输出长度 -20%
print(round(cache_gain, 2), round(out_gain, 2))
# 1.39 1.08

gains = [('continuous batching', 2.0), ('fp8 w+kv', 1.8), ('prefix cache', round(cache_gain, 2)),
         ('60% 流量路由到 8B', 2.13), ('输出上限 -20%', round(out_gain, 2))]
p = 1.0
for name, g in gains:
    p *= g
print(round(p, 2), round(p * 0.8 * 0.9, 2), round(3.704 / p, 3))
# 11.51 8.29 0.322  名义 11.5×；乘 SLO 余量 0.8 与缓存波动 0.9 后 8.3×，0.32 美元/1M
```

与来源对照：NVIDIA 那篇给出的是 KV cache 公式 $2 \cdot L \cdot H \cdot d_{head} \cdot \text{bytes}$（每 token）与 Llama-2 7B（32 层、hidden 4096，即 32 头 × d_head 128）在 batch size 1、4096 上下文下的约 2 GB 算例；用本节公式复算 $1 \times 4096 \times 2 \times 32 \times 4096 \times 2 = 2.0$ GiB，与源文一致（源文按十进制称 2 GB，与 2.0 GiB 差 7%）。两家来源都没有「美元/1M tokens」的成本模型，也没有 10× 的配方，上面这些成本公式、roofline 推演与组合倍数全部是按表内参数自己算的；源文的作用是提供技术清单与 KV 公式。

## 常见追问

- **追问**：为什么先做缓存再做量化？
  - 要点：缓存无损（不改数值、不改模型、不依赖 kernel），收益只取决于流量结构，做完还能顺带拿到「哪些请求真的重复」这份数据，它决定了后面所有杠杆的收益上限；量化要 FP8 kernel、要评测兜底，还可能出现「省了字节但 kernel 不支持所以更慢」。两者作用在公式的不同项上（prefill 与 decode），不冲突，所以先做零风险的那个。
- **追问**：提升利用率与降低单价，哪个优先？
  - 要点：先利用率。同样是 2 倍，砍单价要换硬件或换合约（月级），利用率 30% → 60% 是调度和批处理问题（周级），而且先落到现金流上。但 $\rho$ 超过 0.7 后排队时间按 $\rho/(1-\rho)$ 上升，继续压榨会牺牲 p99，这时再回头谈预留/spot 更划算。顺序：先把 $\rho$ 提到 0.6 附近，再谈采购。
- **追问**：怎么在成本与质量之间设阈值？
  - 要点：用固定评测集（任务成功率、格式合法率、引用正确率）把「质量下限」写成硬 SLO，例如任务成功率不低于基线的 99%；在这个约束下最小化单位成本；路由阈值、量化档位、蒸馏模型各自有回归门禁；线上保留一键回退。注意回退路径的最坏成本是「小模型浪费 + 大模型重试」，要把回退率算进单位成本。
- **追问**：投机解码到底省钱还是费钱？
  - 要点：它用一次前向验证多个 draft token，减少每 token 的权重读取次数，但增加 FLOPs。低 batch（带宽受限）时同时降延迟、提吞吐；大 batch（算力饱和）时被拒绝的 draft 是纯浪费，成本中性偏负。所以它按延迟立项，成本账要单独测，别把它写进省钱清单。
- **追问**：MoE 是不是必然更便宜？
  - 要点：看瓶颈。decode 带宽受限时要搬的是激活专家的权重，激活参数（而不是总参数）决定每 token 字节数，这是它的优势；但全部专家都要常驻显存，同样的卡能装的并发更少，小 batch 下 expert 通信还可能吃掉收益。显存规划按总参数算，成本模型按激活参数算。
- **追问**：prefix caching 什么时候完全无效？
  - 要点：前缀必须从第一个 token 起逐 token 一致。system prompt 里带时间戳或随机 ID、few-shot 示例按请求随机抽取、把每个请求各不相同的检索结果拼在 prompt 最前面、上下文被截断或重排，命中率都会归零；请求被负载均衡到不同副本、缓存 TTL 过期同样会失效。测命中率之前不要把它写进收益预估。

以下按各家公开技术材料与产品形态判断侧重方向，不涉及具体面试流程。

- **Microsoft**：平台与多租户视角（Azure 上的模型服务），偏工程实现加单位经济性：租户配额与计费口径、区域与容量池调度、预留容量与按量付费的配比、把成本拆到租户级做治理。
