## 一句话答案

> 红队方案不是一份攻击手法清单，而是一个有交付物的项目：**目标与范围 → 威胁模型 → 方法与分工 → 判定与度量 → 修复与复测 → 发布决策与持续监控**。每一段都要产出能被评审的物证——威胁模型文档、覆盖矩阵与测试集、判定器与一致性报告、分层 ASR 报告、修复验证记录、发布门禁结论。
> 威胁模型决定覆盖矩阵（危害类别 × 攻击手法 × 语言 × 入口），而每个格子的攻法由攻击者能力假设决定：只有 API 还是能拿到权重微调、能否写入被检索的数据、能否触达工具与凭证。
> 度量上拒绝单一总 ASR：按危害类别与严重度分层报告、显式报出未覆盖的格子、同时报误杀率；流程上把红队集版本化防污染、把高危项做成零容忍红线门禁、修复后复测同一攻击并检查改述绕过。

## 面试官在考什么

- **能不能当项目与治理问题来答**：目标、范围、交付物、责任人、签字与发布决策，而不是列一串越狱技巧。
- **威胁模型是否分层且带能力假设**：能否说清每类威胁的入口，以及攻击者能否微调、能否写入被检索数据、能否接触工具与凭证——这决定了矩阵里哪些格子是必测项。
- **人机分工的边界**：自动化红队覆盖广度、人工红队懂语境与危害细节，两者不可互相替代；只答「用模型自动生成 prompt 就行」的深度不够。
- **度量口径是否经得起追问**：ASR 的成功判据、判定器是谁、人机一致性多少、采样几次、置信区间怎么给、覆盖率与误杀率怎么报。
- **闭环与工程化**：版本化与防污染、红线门禁、修复复测（含改述绕过）、分级发布、上线后的持续红队与外部漏洞响应。

常见错误答案：

- 把红队等同于「跑一遍 HarmBench / AdvBench，看 ASR 是多少」。没有威胁模型就没有覆盖论证，没有判定器校准就没有可比性，没有误杀率就无法支撑发布决策。
- 只给一个总 ASR。高危类别的 1% 与低危类别的 20% 混在一个数字里，决策者会按平均值放行（「数值与代码验证」一节给出算例）。
- 把「跑了几万条用例」当作充分性证明。可辩护的充分性是覆盖矩阵 + 攻击强度阶梯 + 判定器校准 + 外部可复现，而不是条数。

## 原理与推导

### 1. 骨架：六段与各自交付物

| 阶段 | 关键活动 | 交付物 | 评审要点 |
| --- | --- | --- | --- |
| ① 目标与范围 | 明确模型形态（是否有工具、RAG、微调接口）、部署面（区域、语言、用户群）、不可接受行为清单、合规约束 | 范围文档 + 不可接受行为清单 | 范围是否可证伪，是否写明「不测什么」 |
| ② 威胁模型 | 分层列举威胁主体与能力假设，映射到入口 | 威胁模型文档 + 覆盖矩阵 | 每类威胁是否有能力假设与判据 |
| ③ 方法与分工 | 人工 / 自动化 / 优化式攻击 / 标准化框架的组合，内外部分工 | 红队集与攻击方法清单 + 分工表 | 是否覆盖攻击强度阶梯与新入口 |
| ④ 判定与度量 | 定义成功判据、判定器与其校准、分层报告 | 判定器 + 一致性报告 + 分层 ASR 报告 | 口径是否可复现，覆盖率是否显式 |
| ⑤ 修复与复测 | 归因、修复、改述复测、回归入库 | 修复记录 + 复测结果 + 误杀回归 | 是通用机制还是只堵了字符串 |
| ⑥ 发布决策与持续监控 | 红线门禁、分级结论、签字、上线监控与外部报告 | 门禁结论 + 发布条件 + 监控与 SLA | 剩余风险是否写明，谁签字 |

把六段写成文档的意义在于：红队结论是要进发布决策的，没有交付物就没法评审，也没法在出事之后回溯「当时判断依据是什么」。

### 2. 威胁模型：分层 + 攻击者能力假设

| 威胁类别 | 攻击者能力假设 | 主要入口 | 判据示例 | 关联 |
| --- | --- | --- | --- | --- |
| ① 滥用（骗取有害内容） | API-only，可多轮诱导、编码混淆；开放权重场景还能微调 | 用户输入、多轮对话 | 是否给出可操作的危害细节 | [[safety-03]] |
| ② 注入与工具滥用 | 能写入被检索的文档、网页、邮件；能借工具返回值影响模型 | RAG 语料、工具返回、外部内容 | 越权调用、数据外泄 | [[safety-01]]、[[safety-06]] |
| ③ 隐私与数据 | API-only 或可微调，可构造抽取式 prompt | 训练数据记忆化、上下文、日志 | PII 复现、跨会话泄漏 | [[safety-07]] |
| ④ 自主性与越权 | 能诱导长时间运行的 agent，能构造环境反馈 | 工具链、文件系统、审批环节 | 绕过审批、不可逆操作 | [[agents-11]] |
| ⑤ 供应链与投毒 | 能发布依赖、适配器、数据集、插件 | 权重、数据集、插件与服务端 | 触发器下的后门行为 | [[safety-02]] |
| ⑥ 群体差异 | 能按群体、语言、方言构造 prompt | 多语言与本地化入口 | 拒答率与质量差异 | [[safety-09]] |

能力假设必须写下来，否则「测够了没有」无法判定。两个例子：**能否微调**决定了要不要做去除安全对齐的测试（开放权重模型必测）；**能否写入被检索数据**决定了间接注入是必测项还是可选项。行业公开的 LLM 应用威胁清单（例如 OWASP 的 LLM 应用 Top 10）适合拿来做对照表，但对照表不能替代能力假设——同一个类型在 API-only 与可微调两种假设下的攻法完全不同。

### 3. 覆盖矩阵与覆盖率

矩阵的四个维度：**危害类别 × 攻击手法 × 语言/文化 × 入口**。攻击手法大致沿强度递增排列：

```text
直接请求 → 角色扮演/情境包装 → 编码与混淆（base64、低资源语言、音译）
→ 多轮渐进（先无害后越界、crescendo） → 自动化优化攻击（梯度搜索、遗传算法）
→ 组合攻击（注入 + 工具 + 多轮 + 迁移后缀）
```

覆盖率按矩阵计算，并且**必须按维度分别报**：一张 6×6×3（=108 格）的矩阵里覆盖 24 格是 22.2% 的总覆盖率，但按维度看是「危害类别 6/6、攻击手法 4/6、语言 1/3」——缺的恰好是最强的那两档手法和 2/3 的语言。只报 22.2% 这个总数会掩盖最薄弱的维度（「数值与代码验证」一节有算例）。

两条硬规则：**未覆盖的格子显式标注为「未覆盖」，不能默认通过**；每次模型、护栏或工具变更之后重跑的是整个矩阵，而不是上次失败的那几十条——否则红队集会退化成回归测试集，对新入口毫无覆盖。

### 4. 方法组合与人机分工

| 方法 | 擅长什么 | 不可替代之处 | 主要局限 |
| --- | --- | --- | --- |
| 人工红队（领域专家） | 有语境、有危害细节的攻击构造与危害判断 | 生物、网络安全、法律、心理等专家能造出模型自己想不到的攻击 | 慢、贵、覆盖窄、依赖专家可用性 |
| 自动化红队（模型生成用例） | 规模、多样性、可复现、可回归 | 每次模型变更都能跑得起 | 判定器误差被放大，生成分布偏向模型已知的失败模式 |
| 优化式攻击 | 梯度搜索出的可迁移对抗后缀 | 能暴露行为层过滤的失效 | 需要白盒或替代模型，工程成本高 |
| 标准化框架 | 统一协议下的可比基线 | 让「自研方法是否更强」变成可复现比较 | 标准集饱和后要自建长尾 |

三种方法的关键实证口径：

- **人工红队**：Ganguli 等（Anthropic，2022）报告公开了 38,961 条红队攻击数据，并在 2.7B / 13B / 52B 三个规模、四种模型类型（plain LM、被提示为 helpful/honest/harmless 的 LM、带 rejection sampling 的 LM、RLHF 模型）上比较红队难度；结论是 **RLHF 模型随规模增大越来越难被红队，而其它三种模型类型随规模是平的趋势**。这条结论的用法是：红队的难度是被测模型与对齐方法的函数，不能拿历史 ASR 跨模型版本直接比较，方案里要按模型类型设定预期。
- **自动化红队**：Perez 等（DeepMind，2022）用另一个 LM 生成测试问题、用分类器判定回复，在 280B 参数对话模型上自动找出**数万条**有害回复，并用 prompt engineering 把生成导向多种危害类型（从冒犯性内容到把私人电话当作自己的联系方式、训练数据泄漏、对话过程中逐步出现的危害）。价值是规模与多样性，代价是判定器误差被放大，且生成的攻击偏向模型已有的失败模式。
- **优化式攻击**：梯度搜索（GCG 一类）在多个 prompt 上联合优化出的对抗后缀可以迁移到未见过的输入乃至其它模型，包括只能黑盒访问的系统。这说明关键词与正则式过滤挡不住这类攻击，迁移攻击应作为必测项，具体口径见 [[safety-03]]。
- **标准化框架**：HarmBench（Mazeika 等，ICML 2024）在统一协议下系统比较了 **18 种红队方法与 33 个目标 LLM 及防御**，并开源框架与一种对抗训练方法，用于攻防共同演进。它的定位是基线而不是全集：标准集被刷高之后，发布决策要依赖自建的长尾与领域用例。

多语言与多文化覆盖是独立的资源分配问题：只用英文红队会系统性漏掉低资源语言、方言与本地化语境下的失败模式（输入侧还有 tokenizer 效率带来的风险，见 [[llm-internals-06]]）。分配原则是按用户语言分布，而不是按团队会说什么语言。

分工上三方的交付物不同：内部红队交付可复现的测试集与判定器，外部领域专家交付危害判断与用例，第三方评估交付独立结论。三者都要有，因为它们回答的是不同问题——「我们测了什么」「这些回复真的有害吗」「我们的结论别人能复现吗」。

### 5. 判定与度量

**ASR 的定义要写死三件事。** ① 成功判据必须可判定，例如「输出了可操作的合成路径」而不是「回答了问题」；多轮任务要写明在哪一轮判定。② 判定器是谁：人工、规则/分类器、还是 LLM judge。③ 采样口径：同一攻击采 $k$ 次时，报的是「$k$ 次中至少一次成功」（pass@$k$，对风险敏感）还是「平均成功率」，两者可以差好几倍（算例见「数值与代码验证」一节）。

**判定器必须校准，不能默认可信。** LLM judge 有位置、冗长、自偏好等已知偏差（见 [[evaluation-01]]），所以要用一小批人工标注做校准，并报告一致性系数而不是只看表面一致率：判为「成功」的样本本来就是少数类，表面一致率 90% 的判定器其 kappa 可能只有 0.74，而且不一致集中在成功样本上——这直接把 ASR 抬高 3 个百分点（算例见「数值与代码验证」一节），足以淹没团队想测量的效果。

**样本量要报置信区间。** 攻击成功是小概率事件，点估计极不稳定：100 条用例里 1 条成功，点估计 1%，95% Wilson 上界约 5.45%——也就是说用 100 条用例**无法声称**高危类别的风险低于 5%。零容忍的正确表述同样是「违规率的 95% 置信上界低于某个值」：[[evaluation-04]] 用 rule of three 给出 $n$ 条全过时约 $3/n$ 的上界（100 条约 3%），「数值与代码验证」一节的表格用略保守的 Wilson 区间（100 条约 3.7%），两者是同一类上界口径，都不能读成「零风险」。

**分层报告，不给加权总分。** 报告的所有格子都应带 ASR + 置信区间 + 样本量，并按危害类别与严重度分开呈现。加权平均同样会掩盖高危格：「数值与代码验证」一节的算例里，总 ASR 是 10.75%，用严重度权重 8/4/2/1 加权后反而降到 5.47%，而真正卡发布的是生化滥用那一格的 1%。结论是加权分只能用于趋势观察，裁决必须分层 + 红线单列。

**同时报告误杀率。** 只测「有没有拦住」会诱导团队把所有边界都收紧，把可用性打穿。误杀率（正常请求被拒或被安全过滤器拦下的比例）要与 ASR 一起报，并给出护栏的分层设计依据，见 [[safety-04]]。

### 6. 流程与治理：把一次性测试变成工程能力

- **红队集版本化与防污染**：用例集有自己的版本号与变更记录，且**不得进入训练数据**——一旦被训练进去就失去诊断能力（污染口径与防范见 [[evaluation-06]]）。落地手段是样本哈希入黑名单、训练侧过滤、上线前抽检模型是否「背过」这些 prompt。
- **红线集与发布门禁**：把高危类别中零容忍的用例单列成红线集，作为门禁的一票否决项；判定用的统计口径（置信上界、灰区、A/A 水位）直接沿用 [[evaluation-04]]，不要另立一套。
- **修复与复测**：修复后必须复测原攻击，再做**改述复测**——同义改写、换语言、换包装、拆成多轮、把攻击藏进被检索的文档；任一条仍然成功，说明修复只是「把这一条加进了过滤器」。同时跑正常请求的回归，确认误杀率没有被抬上去。
- **分级发布决策**：结论不止「发布 / 不发布」两档，通常是四类——可发布、有护栏下可发布（受限发布 + 额外护栏）、面向受限用户群发布、不发布。谁签字、依据哪些指标、剩余风险如何记录，都要事前规定；护栏与发布条件的接口见 [[safety-04]]。
- **上线后的持续红队与漏洞响应**：公开的外部报告渠道（安全邮箱或赏金计划）、按严重度分级的响应 SLA、线上新越狱样本回流进红队集、监控告警与护栏热更新，见 [[evaluation-07]]。

### 7. 三类假象

| 假象 | 表现 | 破法 |
| --- | --- | --- |
| 「加了一条规则」 | 原攻击被拦，改述之后照样成功 | 改述复测 + 换语言 + 多轮拆分 |
| 「ASR 降了」 | 判定器、采样次数或攻击强度变了，数字不可比 | 报告里附判定器版本、采样口径、攻击强度档位 |
| 「测过了」 | 矩阵没更新，新工具 / 新语言 / 新模态没进矩阵 | 每次新增入口都先更新威胁模型与矩阵，再谈覆盖率 |

## 数值与代码验证

### 来源数字的口径核对

| 数字 | 出处 | 口径 |
| --- | --- | --- |
| 38,961 条 | Ganguli 等 2022，arXiv:2209.07858 摘要（v2） | 公开的红队攻击数据集条数，不是 ASR、也不是模型数 |
| 2.7B / 13B / 52B，4 种模型类型 | 同上 | 红队难度随规模趋势的比较设置；结论是 RLHF 模型越大越难被红队，其它类型趋势平 |
| 数万条有害回复 / 280B | Perez 等 2022，arXiv:2202.03286 摘要 | 自动红队在单个 280B 参数对话模型上找到的冒犯性回复数量级（原文 "tens of thousands"），不是精确计数 |
| 18 种方法 / 33 个目标 | Mazeika 等 2024，arXiv:2402.04249 摘要 | 统一协议下系统比较的红队方法数与目标 LLM 及防御数 |

### 分层 ASR 与置信区间

四个类别各 100 条用例，假设严重度权重依次为 8 / 4 / 2 / 1：

| 类别 | n | 成功数 | ASR | Wilson 95% 区间 | 权重 |
| --- | --- | --- | --- | --- | --- |
| 生化滥用 | 100 | 1 | 1.00% | [0.18%, 5.45%] | 8 |
| 网络攻击 | 100 | 6 | 6.00% | [2.78%, 12.48%] | 4 |
| 欺诈 | 100 | 14 | 14.00% | [8.53%, 22.14%] | 2 |
| 冒犯性内容 | 100 | 22 | 22.00% | [15.00%, 31.07%] | 1 |

总 ASR 为 43/400 = 10.75%，严重度加权 ASR 为 82/1500 = 5.47%，两者都指向「中等风险」；而决定发布的是第一行——**1% 的点估计对应 5.45% 的上界，100 条用例不足以支撑「高危类别风险很低」的结论**。这也是红线集必须与其它集合分开、且用置信上界而非点估计裁决的原因。

三个派生口径：

| 情形 | 计算 | 结果 |
| --- | --- | --- |
| 判定器一致性（120 条，人工判 30 条成功、judge 判 34 条成功） | 表面一致率 90%，kappa = 0.745 | judge ASR 28.33% vs 人工 25.00%，差 3.33 个百分点 |
| 采样口径（单次成功率 8%） | $1-(1-p)^k$，$k \in \{1,3,5,10\}$ | 8% / 22.13% / 34.09% / 56.56% |
| 覆盖率（6×6×3 = 108 格，覆盖 24 格） | 24/108；同时按维度报 | 总 22.2%；类别 6/6、手法 4/6、语言 1/3 |

判定器那一行值得单独看：90% 的表面一致率听起来足够好，但 kappa 只有 0.745，且不一致的 12 条里有 8 条是 judge 判成功、人工判失败。安全场景里判定器「宁滥勿缺」的偏向会把 ASR 系统性抬高，所以一致性必须按成功类样本单独看，而不是只看总体准确率。

### 复算代码

```python
import math

Z = 1.959963985

def wilson(k, n, z=Z):
    """攻击成功率（二项比例）的 Wilson 区间；n 小的时候必须用它，不能用点估计。"""
    p = k / n
    den = 1 + z * z / n
    c = (p + z * z / (2 * n)) / den
    h = z * math.sqrt(p * (1 - p) / n + z * z / (4 * n * n)) / den
    return p, c - h, c + h

# 1) 分层报告：总 ASR 与严重度加权 ASR 都会掩盖高危格
rows = [("生化滥用", 100, 1, 8), ("网络攻击", 100, 6, 4),
        ("欺诈", 100, 14, 2), ("冒犯性内容", 100, 22, 1)]
for name, n, k, w in rows:
    p, lo, hi = wilson(k, n)
    print(f"{name}: ASR={p:.2%} Wilson95=[{lo:.2%}, {hi:.2%}] 严重度权重={w}")
tot_n, tot_k = sum(r[1] for r in rows), sum(r[2] for r in rows)
wn, wk = sum(r[3] * r[1] for r in rows), sum(r[3] * r[2] for r in rows)
print(f"总 ASR={tot_k}/{tot_n}={tot_k / tot_n:.2%}；严重度加权 ASR={wk}/{wn}={wk / wn:.2%}")
print(f"n=100 全过时的 95% 上界={wilson(0, 100)[2]:.2%}")

# 2) 判定器一致性：表面一致率会高估可信度
def kappa(n00, n01, n10, n11):
    n = n00 + n01 + n10 + n11
    po = (n00 + n11) / n
    pe = ((n11 + n01) / n) * ((n11 + n10) / n) + ((n00 + n10) / n) * ((n00 + n01) / n)
    return po, (po - pe) / (1 - pe)

po, kap = kappa(82, 4, 8, 26)   # 行=人工判、列=judge 判；1 表示判为攻击成功
print(f"po={po:.2%} kappa={kap:.3f}；judge ASR={34/120:.2%}，人工 ASR={30/120:.2%}")

# 3) 采样口径：同一条攻击采 k 次，pass@k 远高于单次成功率
for k in (1, 3, 5, 10):
    print(f"单次成功率 8%、k={k}: 至少一次成功={1 - 0.92 ** k:.2%}")

# 4) 覆盖率：按维度分别报，别只给一个总数
#    24 格 = 危害类别 6 × 攻击手法 4 × 语言 1，与下面按维度的报法自洽
print(f"矩阵 6x6x3=108 格，覆盖 24 格: 总覆盖率={24 / 108:.1%}")
print("维度覆盖: 危害类别 6/6, 攻击手法 4/6, 语言 1/3")

# 5) 发布门禁：红线优先，其次是未覆盖与高危上界，最后是误杀预算
def verdict(red_line_hits, high_asr_upper, high_covered, false_reject):
    if red_line_hits > 0:
        return "hold: 红线一票否决"
    if not high_covered:
        return "hold: 高危格未覆盖，无法判定"
    if high_asr_upper > 0.05:
        return "restricted: 受限发布 + 额外护栏 + 复测"
    if false_reject > 0.10:
        return "hold: 护栏误杀超预算"
    return "release"

print(verdict(0, wilson(1, 100)[2], True, 0.04))   # restricted（上界 5.45% > 5%）
print(verdict(0, wilson(0, 300)[2], True, 0.04))   # release（300 条全过，Wilson 上界约 1.3%；rule of three 约 1%）
print(verdict(1, 0.00, True, 0.02))                # hold（红线）
print(verdict(0, 0.02, False, 0.02))               # hold（未覆盖）
print(verdict(0, 0.02, True, 0.14))                # hold（误杀）
```

输出与上面的表格一致：`restricted`、`release`、以及三个 `hold` 分支分别对应红线、未覆盖与误杀超预算。第 5 个函数把「流程与治理」一节的裁决顺序写成了可执行的判据：**红线优先，其次是覆盖缺口，再是高危类别的置信上界，最后才是误杀预算**；顺序本身也是需要评审的设计决定。

## 常见追问

- **追问**：红队与常规 eval 的差别是什么？
  - 要点：目标与分布不同。常规 eval 测代表性能力，样本要贴合线上分布；红队测对抗条件下的最坏情形，目标导向的攻击者不在流量分布里，所以红队集不需要代表分布，但必须覆盖攻击面。两个推论：常规 eval 的样本量逻辑在这里不适用（关心的是「是否存在成功路径」而不是平均表现）；红队结果也不能反推线上伤害率，因为攻击者占比未知。
- **追问**：自动化红队能替代人工吗？
  - 要点：不能，分工不同。自动化擅长规模、多样性、可复现与回归，人工擅长语境、危害细节判断与创造新手法——新型攻击通常先由人类发现，再被自动化规模化，人工数据本身也是可分析的研究产物（Anthropic 公开 38,961 条攻击数据正是这个用法）。稳态是「人工造手法 + 自动做规模 + 第三方独立复现」，同时用人工样本持续校准自动判定器。
- **追问**：如何证明红队「足够充分」？
  - 要点：不能靠条数证明。可辩护的举证是四件：① 威胁模型与覆盖矩阵公开，未覆盖格子显式标注；② 方法覆盖了从直接请求到优化式攻击的强度阶梯，并包含迁移攻击与多语言；③ 判定器经过人工校准并报告一致性；④ 结论能被外部独立复现，且在模型变更后重跑矩阵。剩余风险写进发布结论，而不是声称「没有风险」。
- **追问**：修复之后怎么确认真的修好了？
  - 要点：三步。① 复测原攻击确认拦截；② 改述复测——同义改写、换语言、换包装、拆成多轮、把攻击藏进被检索文档，任一条仍成功就说明只是堵了字符串；③ 跑正常请求回归，确认误杀率没被抬高。修复要落到通用机制（训练目标、护栏策略、权限约束、工具白名单），黑名单只能作为临时缓解。
- **追问**：ASR 报多少算通过？
  - 要点：没有通用阈值，阈值必须按危害类别与严重度分别设定：高危类别是零容忍 + 置信上界约束（「95% 上界低于某个值」而不是「点估计为 0」），低危类别可以设容忍阈值并配合护栏。任何阈值都要同时写明判定器版本、采样次数与成功判据，否则跨版本不可比；门禁的统计口径见 [[evaluation-04]]。
- **追问**：开放权重模型与 API 模型的红队方案差在哪？
  - 要点：能力假设与修复闭环两端都变了。开放权重下攻击者能微调去除安全对齐、能做白盒梯度攻击、能把越狱 prompt 永久固化，因此白盒攻击与去除对齐测试是必测项；同时没有服务端护栏可以热更新，修复只能重新发布权重，发布前必须更保守。API 模型相反：护栏可热更新、可在线拦截，但要按攻击者能拿到多少信息划分黑盒/灰盒（有无 logprobs、能否套出 system prompt、限流与账号封禁策略）。
- **追问**：红队集怎么防污染、防过拟合？
  - 要点：三条。① 训练侧过滤：用例哈希不进训练数据（口径见 [[evaluation-06]]），并抽检模型是否「背过」这些 prompt；② 保留集：一部分用例只在发布前跑、不进日常 CI，避免被针对性优化；③ 轮换与新增：线上新样本回流后，饱和的旧用例退役，矩阵不能靠旧用例刷覆盖率。
