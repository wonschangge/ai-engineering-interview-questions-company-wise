## 一句话答案

> 标准 RAG 是一条固定流水线：query → 检索一次 → 拼上下文 → 生成一次，控制流写在代码里，每一步做什么在部署时就定死了。agentic RAG 把控制流交给模型：由它决定要不要检索、检索什么、用哪个工具、结果够不够、要不要再来一轮，是一个 thought–action–observation 循环，scratchpad 记录每一步。
> 判据只有一条：**下一步的检索是否依赖上一步的结果**。有数据依赖（多跳、跨源、需要澄清或先取数再计算）时循环不可替代；没有依赖时，一轮并发的 multi-query 加重排能拿到大部分收益，代价是 1.8 倍成本而不是 3.4 倍。
> 在本节的成本口径下，3 步检索循环是标准 RAG 的 3.4 倍成本、1.8 倍延迟；因为 scratchpad 每步全量重发，账单随步数二次增长（第 3 步的边际成本已是标准查询的 1.26 倍），而延迟只按步近似线性增加（每步约 +2.2 s）。它换来的不是更便宜，而是把「做不成」变成「做得成」。

## 面试官在考什么

- 能不能用「数据流 vs 控制流」讲清差别，而不是「检索了多次」。固定流水线的检索次数也可以大于 1（multi-query 就是），区别在于**谁决定下一步**。
- 是否知道 agentic 的第二重价值是质量闭环：自评相关性/支撑性、失败重试、换数据源兜底。多跳只是它的一部分。
- 会不会算账：步数 → token → 延迟 → 账单，并说清成本为什么是二次的、延迟为什么只是线性。
- 有没有准入判据：什么任务必须串行多轮（数据依赖），什么任务一轮内增强就够，能不能给出可量化的门槛而不是「看情况」。
- 工程护栏与可观测性：步数与 token 预算、超时、循环检测、无进展退出、完整轨迹落盘。这一条区分「跑过 demo」和「上过生产」。

常见错误答案：

- 把 agentic RAG 讲成「多跑几次检索」或「上多 agent 编排」，说不清停机条件、预算与失败路径。
- 只答「更准但更慢更贵」，给不出比例，也说不清慢和贵分别由什么支配。这两个量的增长阶数不同（延迟约为 $7.6 + 2.2K$ 秒，账单 $\propto K^2$），混在一起讲就答不出该压哪一头。
- 说「agent 会自己决定调用工具」。模型只输出工具名与参数的文本，真正调用、重试、截断结果的是外面的 runtime，这是设计可靠性时的分界线。

## 原理与推导

### 1. 两张流程图

```text
标准 RAG：单轮固定流水线
query ─► [可选改写] ─► retrieve top-k ─► [rerank] ─► 拼 prompt ─► generate ─► answer
         （次数固定、路径确定、控制流写在代码里）

agentic RAG：由模型控制的循环
                    ┌─ 不需要检索（问候 / 闲聊 / 纯写作）─► generate ─► answer
                    │
query ─► [planner] ─┴─► 选工具 + 写查询词 ─► tool call ─► observation
            ▲                                                    │
            │                                                    ▼
            └──── 不够：改写查询 / 换工具 ◄──── [planner 自评：够了吗？]
                                                      │ 够了
                                                      ▼
                                          generate ─► [verify] ─► answer
```

$K$ 步循环的形式化：第 $i$ 步的输入是系统提示与问题 $S_0$，加上前 $i-1$ 步的全部动作与观测。

**本质差别**：标准 RAG 把数据流写死在代码里（改写 → 检索 → 重排 → 生成是若干固定阶段），agentic RAG 把控制流交给模型（检索不再是一个阶段，而是一个可以被反复决策的动作）。源文用图书管理员与研究者作比：管理员按词面匹配取一本书，研究者先想清楚去哪找、读完判断够不够、不够就换个书架再找。

### 2. 循环里的四个能力

- **query planning（拆解与改写）**：把「收购 Acme 的那家公司的 Q4 营收是多少」拆成两跳——先查「谁在 2023 年收购了 Acme」，再用查到的实体去查营收。第一跳的输出构成第二跳查询词的一部分，这就是**数据依赖**。
- **tool use（工具选择）**：向量检索管语义、BM25 与关键词管精确串（编号、报错码、函数名）、SQL 管结构化聚合、图查询管关系、web 管时效、计算器管算术。选错工具与选错查询一样致命：让向量库回答「上个季度营收环比涨了多少」，它只能把两段文本拼给你，算不出差额。
- **self-reflection（自评与兜底）**：两个判断——相关性（片段在讲这个问题吗）与支撑性（片段真的支持我要给的结论吗）。源文把前者对应到 Self-RAG 的自评，把「主源失效就换源」对应到 Corrective RAG（CRAG）。
- **memory / scratchpad**：每步的 thought、action、observation 都留在上下文里，模型才知道自己试过什么、已经知道了什么。这也是后文成本二次增长的直接来源。

一个常考细节：**模型自己不会调用工具**。LLM 只输出「工具名 + 参数」的文本，发起调用、处理超时与重试、截断过长结果、把结果塞回上下文的都是 runtime。所以幂等、鉴权、限流、结果裁剪这些可靠性问题是 runtime 的职责，不该指望 prompt 解决。这一整套就是 ReAct 的 thought → action → observation 循环（[[agents-01]]）。

### 3. 设计空间：三种常见形态

| 形态 | 把哪个阶段变成决策点 | 主要解决 |
| --- | --- | --- |
| ReAct 式 | 每一步的动作 | 多跳、需要换工具 |
| Self-RAG | 检索结果是否可信 | 检索噪声大，宁可不答也不乱答 |
| CRAG | 主数据源失效后去哪 | 单一来源不可靠，需要兜底 |

三者做的是同一件事：挑一个原本固定的阶段，交给模型决定。工程上常叠加使用（先跑 ReAct 循环，再对最终答案做一次支撑性自检）。

### 4. 什么时候值得：只有数据依赖不可替代

按顺序问三个问题，前两个命中才考虑上循环：

1. **下一步的查询是否需要上一步的结果？**「A 收购 B 时 B 的 CEO 是谁」必须先知道 A 是谁；「对比三家供应商的报价差额」必须先取数再算。这类任务的检索词无法只由原问题确定，单轮里无解。
2. **是否需要跨异质来源？** 文档加数据库加实时 API 的联合查询，标准 RAG 只有一条检索通道，选错通道就是零召回。
3. **是否必须自检？** 医疗、法律、金融要求答案可归因、证据不足时拒答，自检与引用链本身就是额外的 LLM 调用（[[rag-12]]）。

| 任务 | 标准 RAG 的失败模式 | 循环的必要性 |
| --- | --- | --- |
| 单跳事实问答 | 基本够用 | 不必要，一轮内增强即可 |
| 多跳（实体链） | 检索词无法确定，recall 直接归零 | **必要**，且必须串行 |
| 跨源（文档 + 库 + API） | 通道单一，选错源 | **必要**，工具选择是核心 |
| 意图不清、需澄清 | 召回一堆无关片段，答案跑偏 | 必要（先澄清再检索） |
| 需要计算/校验 | 数字检索到了但算错 | 必要（取数与计算分离） |
| 高代价错误（医疗/法律/金融） | 无自检，错答直接上线 | 必要（自检加拒答） |

评测集里真正需要多步的比例很低时，这笔复杂度摊不平。量化门槛见「数值与代码验证」的表 5。

### 5. 代价的五个来源

1. **延迟与成本**：每个循环步至少一次 LLM 调用加一次检索，而且每步都要把历史 scratchpad 重新发一遍。
2. **错误累积**：单步成功率 $p$ 时，$K$ 步串行的端到端成功率是 $p^K$（0.8 的命中率走两跳只剩 0.64）。更麻烦的是错误会污染上下文——错的事实留在 scratchpad 里，后续步骤继续在它上面推理，这类错误不会自愈。
3. **不可预测**：同一问题的步数在 1 到 $K_{\max}$ 之间浮动，token 与延迟的方差远大于单轮，容量规划必须按分位数做而不是按均值（[[inference-serving-09]]）。
4. **评测更复杂**：链路不固定，只比最终答案无法区分「检索没找对」与「推理错了」，要评轨迹（步数、工具选择、无效检索率），见 [[evaluation-10]]。
5. **需要护栏**：步数上限、token 预算、超时、循环检测、无进展退出、失败降级，缺任何一条都会出现「无限检索」或成本尖刺。

### 6. 成本模型：账单二次增长，延迟近似线性

记号：$S_0$ 为系统提示与问题，$A$ 为每步动作输出（thought 加工具参数），$O$ 为每步观测（检索回的片段），$K$ 为计划步数，$R_{pre}$ 为 prefill 吞吐，$t_{tok}$ 为 decode 的每 token 耗时。

$$S_{plan}(i) = S_0 + (i-1)(A+O), \qquad \sum_{i=1}^{K} S_{plan}(i) = K S_0 + \frac{K(K-1)}{2}(A+O)$$

第一项线性、第二项二次：**每一步都要把前面所有步的观测重发一次**。这就是账单二次增长的机制，与具体常数无关。

$$\text{cost} \propto S_{in} p_{in} + S_{out} p_{out}, \qquad t \approx \underbrace{K\left(A\,t_{tok} + t_{ret}\right)}_{\text{计划步}} + \underbrace{\frac{S_{fin}}{R_{pre}} + S_{ans}\,t_{tok}}_{\text{最终生成}}$$

延迟里各项都只与 $K$ 成正比（$S_{fin}$ 虽随 $K$ 线性增长，但 prefill 在总延迟里占比很小），所以延迟近似线性；账单里出现了 $K^2$，所以成本是二次的。**这两个阶数不同，是这道题最值得讲的一句话**：压延迟要减步数与输出长度，压账单要砍每步重发的上下文（压缩观测、只留结论、用 prefix caching 抵消重复 prefill 的算力）。

一个口径上的坑：prefix caching 能把重复前缀的 prefill 算力省掉，但**计费按 token 计而不是按 FLOPs 计**，除非服务方对缓存命中的输入 token 打折，否则账单仍然是二次的。

### 7. 工程实践：把循环做成可开关的模式

- **模式与预算参数化**：单轮与 agentic 做成两档，每档带 `max_steps`、`token_budget`、`timeout` 三个参数，默认单轮——回归风险与容量都按默认档评估，升级是显式决策而不是静默发生。
- **用缓存与并发压成本**：prefix caching 抵消重复 prefill 的算力（账单口径见上一节）；同一跳内彼此独立的子查询并发发出，别把并行的活拆成串行步骤（表 3 里 1.21× 与 1.55× 的差别就来自这里）。
- **轨迹落盘**：每步的 query、工具、返回的 chunk id、自评理由、token 数与耗时都记下来，调试与评测共用同一份数据。
- **答案带引用**：最终生成只允许使用 scratchpad 里记了来源 id 的内容，引用不上的结论宁可不输出（[[rag-12]]）。

## 数值与代码验证

口径（下文所有表格都由这一组常数算出）：

| 项 | 取值 | 依据 |
| --- | --- | --- |
| 模型 | 70B、bf16、TP=8 on 8×H100 | 与推理专题的显存/带宽口径一致 |
| prefill 吞吐 $R_{pre}$ | 22,606 tok/s | $989\times10^{12}\times0.4\times8/(2\times70\times10^{9})$，MFU 0.4 |
| decode | 40 tok/s（$t_{tok}=25$ ms） | batch 约 48 的负载口径，不是单流极速 |
| 单次检索 $t_{ret}$ | 80 ms | embed 15 + ANN 10 + rerank 35 + 网络 20 |
| rerank 的 35 ms | $2PNL$ FLOPs | $2\times0.3\times10^{9}\times100\times232=1.39\times10^{13}$ FLOP，单卡有效 396 TFLOP/s |
| 内容规模 | $S_0=400$、$A=80$、$O=800$、答案 300 tok | 每步 4 段 × 200 tok；标准 RAG 走重排后保留 5 段 |
| 单价 | $p_{out}=4p_{in}$ | 主流 API 的输入/输出价差量级，只用于算成本倍数 |

**基准（标准 RAG）**：输入 $400+5\times200=1400$ tok、输出 300 tok，成本当量 2600，延迟 7.64 s（prefill 0.062 s + decode 7.50 s + 检索 0.08 s）。decode 占了 98%，这是后面延迟倍数被压住的原因。

表 1：串行 $K$ 步循环的成本与延迟（相对标准 RAG）

| $K$ | 总 token | 成本倍数 | 延迟 | 延迟倍数 |
| --- | --- | --- | --- | --- |
| 1 | 2,080 | 1.24× | 9.66 s | 1.26× |
| 2 | 4,240 | 2.16× | 11.83 s | 1.55× |
| 3 | 7,280 | 3.42× | 14.04 s | 1.84× |
| 5 | 16,000 | 6.96× | 18.58 s | 2.43× |
| 7 | 28,240 | 11.85× | 23.27 s | 3.05× |
| 3 步加 1 次验证 | 10,020 | 4.52× | 15.16 s | 1.98× |

计划输入的构成印证了二次项：$K=1$ 是 400，$K=3$ 是 3,840（二次项占 68.8%），$K=5$ 是 10,800（81.5%），$K=7$ 是 21,280（86.8%）——步数一多，钱几乎全花在重发历史观测上。口径说明：这里假设最终生成携带全部 $K$ 步的原始观测；若每步只把结构化结论写回 scratchpad（即压缩式记忆，每步观测从 800 tok 压到 150 tok），$K=3$ 的成本倍数会从 3.42× 降到 1.92×，延迟几乎不变——**砍重发上下文的收益大于砍步数**。

表 2：多走一步的边际代价

| 从 $K-1$ 到 $K$ | 成本增量 | 延迟增量 |
| --- | --- | --- |
| 1 → 2 | +0.92× 标准查询 | +2.17 s |
| 2 → 3 | +1.26× | +2.21 s |
| 3 → 4 | +1.60× | +2.25 s |
| 4 → 5 | +1.94× | +2.29 s |

结论很反直觉但很好记：**一次无效检索的价格约等于一次完整的标准 RAG 查询**，而且越往后越贵；延迟增量却几乎是常数（约 2.2 s，其中 2.0 s 是 80 个计划 token 的 decode）。

表 3：一轮内增强与循环的对照

| 方案 | 需要串行依赖 | 成本倍数 | 延迟倍数 | 能解决什么 |
| --- | --- | --- | --- | --- |
| 单轮单查询加重排 | — | 1.00× | 1.00× | 相关度排序 |
| HyDE（先写假设文档再检索） | 否 | 1.38× | 1.49× | 查询与文档表述不对齐 |
| multi-query 3 路并发 | 否 | 1.82× | 1.21× | 召回覆盖不足 |
| agentic 2 步 | **是** | 2.16× | 1.55× | 依赖型两跳 |
| agentic 3 步加验证 | **是** | 4.52× | 1.98× | 多跳加自检 |

multi-query 的延迟倍数（1.21×）低于 HyDE（1.49×）：3 路检索并发只付一次检索时间，而 HyDE 要串行等一次 150 token 的假设文档 decode。这说明一轮内增强的代价主要在**额外的 decode**，不在检索本身。这两行的口径一并写明：HyDE 只多一次改写调用（400 tok 输入、150 tok 输出，1,000 当量 = +0.38×），检索次数不变；multi-query 多一次改写调用（400 tok 输入、60 tok 输出，640 当量 = +0.25×）与一次并发的三路检索，并集去重后比单轮多带 1,500 tok 证据（+0.58×），合计 2,140 当量 = 1.82×。

顺带一条省钱口径：改写、HyDE、自评这类辅助调用不需要 70B。同节点单卡的 7B 做「400 tok 输入 + 60 tok 输出」只要 0.26 s（prefill 28,257 tok/s，decode 4.2 ms/step 约 239 tok/s），而 70B 做同一件事要 1.52 s。

表 4：链式成功率与重试的补偿（每步独立假设）

| 单步成功率 $p$ | $K=1$ | $K=2$ | $K=3$ | $K=5$ | 每步一次重试后的 $K=3$ |
| --- | --- | --- | --- | --- | --- |
| 0.9 | 0.900 | 0.810 | 0.729 | 0.590 | 0.970 |
| 0.8 | 0.800 | 0.640 | 0.512 | 0.328 | 0.885 |
| 0.7 | 0.700 | 0.490 | 0.343 | 0.168 | 0.754 |
| 0.6 | 0.600 | 0.360 | 0.216 | 0.078 | 0.593 |

$p=0.8$ 三跳只剩 0.512，这是串行链路的算术惩罚；但每步允许一次重试就把单步提到 0.96，三跳回到 0.885——**循环的价值不只是「能多跳」，还有「每一步都能重试和自检」**。这个模型是一阶近似：真实系统里各步并不独立，一次没被识别的错误检索会留在 scratchpad 里污染后续，实际衰减比 $p^K$ 更快。

| $f$ | 标准准确率 | agentic 准确率 | 增益 | 成本倍数 | 单位正确答案成本（标准 / agentic） |
| --- | --- | --- | --- | --- | --- |
| 0.05 | 0.870 | 0.890 | +2.0 pts | 1.12× | 1.15 / 1.26 |
| 0.10 | 0.840 | 0.880 | +4.0 pts | 1.24× | 1.19 / 1.41 |
| 0.20 | 0.780 | 0.860 | +8.0 pts | 1.48× | 1.28 / 1.73 |
| 0.30 | 0.720 | 0.840 | +12.0 pts | 1.73× | 1.39 / 2.06 |
| 0.50 | 0.600 | 0.800 | +20.0 pts | 2.21× | 1.67 / 2.76 |

两个结论要一起说：

- **agentic RAG 不会让单位正确答案更便宜**（每一行右边都大于左边），它买的是准确率。所以值不值得取决于错误的代价，而不只是错误率。
- 多跳占比低于约 10% 时，整体增益只有几个点，却要长期维护一条决策链路并承受更高的 p99——「多跳占比低于 10% 先别上 agent」这个门槛就是这么来的。把 $f$ 换成自己评测集里的实测占比再用这张表；注意表中用的是 oracle 路由（已知哪些题是多跳），真实路由器用分数阈值近似，会漏判一部分多跳题，实际增益略低于表中值。

表 6：预算与容量

| token 预算 $B$ | 允许的最大步数 | 该步数的实际用量 |
| --- | --- | --- |
| 8,000 | 3 | 7,280 tok，3.42×，14.04 s |
| 16,000 | 5 | 16,000 tok，6.96×，18.58 s |
| 32,000 | 7 | 28,240 tok，11.85×，23.27 s |

容量为什么不能按均值算：若实测步数分布为 $K=1$ 占 30%、2 占 40%、3 占 20%、4 占 7%、5 占 2%、7 占 1%（**这是要从自己 trace 里量出来的量，不是公开结论**），则均值成本 2.53×、延迟 12.18 s；p50 落在 $K=2$（2.16×、11.83 s），p90 落在 $K=3$（3.42×、14.04 s），p99 落在 $K=5$（6.96×、18.58 s）——**p99 的成本是 p50 的 3.2 倍**。这就是每请求预算必须设硬上限、容量必须按分位数算的原因。

一个可直接落地的降级策略是分数门控：只在检索分数不可信时升级到循环，升级率 $r$ 下的成本倍数是 $1+2.42r$（2.42 是 3 步循环相对单轮的增量），$r=5\%$ 时 1.12×、$r=15\%$ 时 1.36×、$r=100\%$ 时 3.42×。门控的价值是把延迟与成本增量只落在需要它的那部分流量上。

```python
# 复算表 1、表 2、二次项占比与门控倍数：70B / bf16 / TP=8 on 8xH100
N = 70e9
R_PRE = 989e12 * 0.4 * 8 / (2 * N)        # 22,606 tok/s
TPOT, P_OUT, RET = 0.025, 4.0, 0.080      # 25ms/token、输出单价 4x、一次检索 80ms
S0, A, O, ANS = 400, 80, 800, 300

llm = lambda i, o: i / R_PRE + o * TPOT
money = lambda i, o: i + P_OUT * o

std_in, std_out = S0 + 5 * 200, ANS       # 标准 RAG：重排后保留 5 段
std_c, std_t = money(std_in, std_out), llm(std_in, std_out) + RET
print(f"标准 RAG：{std_c:.0f} 当量 {std_t:.2f}s")          # 2600 当量 7.64s

def agent(K, verify=False):
    plan_in = sum(S0 + i * (A + O) for i in range(K))       # scratchpad 逐步增长
    fin_in = S0 + K * O + 100                               # 最终生成的证据
    ver_in = S0 + ANS + min(K * O, 2000) if verify else 0
    ver_out = 40 if verify else 0
    t = sum(llm(S0 + i * (A + O), A) for i in range(K)) + llm(fin_in, ANS) + K * RET
    if verify:
        t += llm(ver_in, ver_out)
    return money(plan_in + fin_in + ver_in, K * A + ANS + ver_out), t

for K in (1, 2, 3, 5, 7):                                    # 表 1
    c, t = agent(K)
    print(f"K={K}  成本 {c/std_c:.2f}x  延迟 {t:.2f}s ({t/std_t:.2f}x)")
print("K=3+验证 成本 %.2fx 延迟 %.2fx" % (agent(3, True)[0] / std_c, agent(3, True)[1] / std_t))
print("二次项占比 K=3/5/7：", [f"{K*(K-1)//2*(A+O)/sum(S0+i*(A+O) for i in range(K)):.1%}"
                            for K in (3, 5, 7)])             # 68.8% 81.5% 86.8%
for K in (2, 3, 4, 5):                                       # 表 2 边际代价
    print(f"{K-1}->{K}: +{(agent(K)[0]-agent(K-1)[0])/std_c:.2f}x,"
          f" +{agent(K)[1]-agent(K-1)[1]:.2f}s")
print("门控 r=0.15：%.2fx" % (1 + 0.15 * (agent(3)[0] / std_c - 1)))   # 1.36x
```

## 常见追问

- **追问**：agentic RAG 与「RAG 加重排加多查询」的边界在哪？
  - 要点：唯一边界是**步骤之间有没有数据依赖**。multi-query 的多个查询词都能只由原问题生成，属于同一跳的并发分支，延迟只多一次改写（表 3 的 1.21×）；只有当第二跳的查询词里必须包含第一跳才能得到的实体时才必须串行。判定方法很直接：试着把子问题写出来，如果每个子问题的查询词都能从原问题抄出来，就不需要循环。
- **追问**：怎么评测一个多轮检索系统？
  - 要点：三层分开测。检索层看每一跳的 recall@k（前提是标注了「标准答案在第几跳的第几段」）；轨迹层看步数分布、工具选择正确率、无效检索率（无效步数 / 总步数）、重复查询率；答案层看最终正确率与引用支撑率。前提是把轨迹当一等公民落盘：每步的 query、工具、返回的 chunk id、自评理由、token 数与耗时。再拿「这题最少需要几步」的标注当参照，实际步数明显高于它就是在烧钱（[[rag-04]]、[[evaluation-10]]）。
- **追问**：怎么防止 agent 无限检索？
  - 要点：五道闸门缺一不可。① 步数上限，由 token 预算反推（表 6：8,000 tok 对应 3 步）；② 每请求的 token 与时间硬预算，超了就用现有证据生成并标注证据不足；③ 循环检测，对「工具 + 归一化参数」做哈希，重复即拒；④ 无进展退出，连续两轮没有新的 chunk id 或新实体就停；⑤ 超时与失败降级。这些是 runtime 的职责，不要指望 prompt 里写「请不要重复检索」（[[agents-09]]）。
- **追问**：为什么很多团队上线后又退回单轮？
  - 要点：三个原因叠加。① 增益只落在少数多跳查询上（表 5：$f=10\%$ 时整体只 +4 pts），而延迟与成本增量落在全部流量上；② 单位正确答案的成本反而变高，如果错误只是体验差一点而不是业务代价高，账算不过来；③ 没有轨迹评测就无法证明收益，一旦出现 p99 投诉或成本尖刺，决策就会回退。能站住的做法通常是路由：简单查询走单轮，只有分数门控触发的流量进循环，再按细分段做 A/B。
- **追问**：多轮会不会把正确答案挤出上下文？
  - 要点：会。$K=5$ 时 scratchpad 加证据已接近 4,000 token，而长上下文对中段信息的注意力本来就更弱（[[llm-internals-13]]）。工程解法是压缩式记忆：每步只把结构化结论（实体、数值、来源 id）写回 scratchpad，原始片段只保留当前步的，最终生成时再按需取回；不要把全部观测一路原样带到第 $K$ 步。
- **追问**：什么信号可以用来决定「要不要检索」？
  - 要点：源文提到 agent 可以先判断问题根本不需要检索（问候、闲聊）。生产上的判据通常是组合：检索分数（top-1 低于阈值，或 top-k 分数挤在一起）、问题类型分类器、以及「答案是否必须来自私有语料」。判断错误的代价不对称——该检索而不检索是幻觉，不该检索而检索只是浪费，所以阈值要偏向检索。
