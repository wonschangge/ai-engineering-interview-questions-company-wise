## 一句话答案

> PDF 只记录「什么画在哪个坐标」，不记录「这是什么」，所以表格、图表、多栏这三类内容坏在同一层：版面解析。管线必须先做 layout analysis，把页面拆成带类型的区块（标题、正文、表格、图、图注），按栏与阅读顺序重排、滤掉页眉页脚，再对每类内容选各自的表示：表格还原成网格后转 Markdown/HTML，整体不切断、表头与标题绑成同一个 chunk；图表把 caption 与 chart-to-text 描述都绑到图所在 chunk；公式转 LaTeX 或带符号的 markup。
> 检索侧分层：结构化表格索引负责数值与聚合问题，文本索引负责语义问题，CLIP/SigLIP 这类图像索引只在真正依赖视觉细节的查询上做补充，不替代前两者。最关键的一条工程原则：**先修解析，再调检索与提示词**——解析阶段丢掉的内容，任何检索策略都召不回来。

## 面试官在考什么

- 是否理解 PDF 是绘制指令流而不是结构化文档，能说出 layout analysis、阅读顺序、OCR 三层各自的失败模式，而不是只报工具名。
- 能否把「表格怎么进索引」拆成四个独立决策：结构还原、表示形式、切分单元、表内检索，并给每个决策配上代价。
- 是否算过 embedding 的 token 上限：整表入库时超出窗口的部分对检索完全不可见，这是可以用数字讲清的问题。
- 有没有把「解析错误」当成独立失败模式去评测和归因，而不是把所有 bad case 都丢给 prompt 工程。
- 多模态架构取舍：文本代理、多模态 embedding、两者混合，各自的适用查询、延迟与存储代价。

常见错误答案：

- 「pdfplumber 抽文本 → 切 chunk → 建向量索引」，把解析当成一行代码。这个答案在双栏论文、财报和扫描件上会直接崩掉。
- 「OCR 准确率 99% 够用了」。字符级 1% 的错误率下，一个 12 字符的术语只有 88.6% 的出现位置完好，BM25 的精确匹配会成片漏召，而且漏召是静默的。

## 原理与推导

### 1. 多栏 PDF 难在哪：PDF 里没有「结构」，只有「位置」

PDF 的内容流是一串绘制指令：在某个坐标画一段字形、画一条线、贴一张图。它没有段落、没有阅读顺序、没有语义标签，抽取器能给你的只有「页号 + 字符/行 + bbox」。所有质量问题都从这个缺口长出来：

- **按行交错读**。文本流往往按 y 坐标排序，同一水平带上左右两栏的字被塞进同一行，句子被剪断。这是多栏 PDF 最典型、也最难在事后修补的错误：一旦交错，模型再强也不知道该怎么切回来。
- **页眉页脚与页码重复**。同一串文本在每页出现一次，会让它在语料里的文档频率虚高，BM25 的 IDF 被压低，同时污染 chunk 的语义。
- **脚注与图注错位**。页底的脚注、图下的 caption 在坐标上离它注释的对象很远，容易和相邻段落粘在一起。
- **连字符断词**。排版把 `transformer` 拆成行尾 `trans-` 加下行 `former`，需要 dehyphenation，否则这个词在索引里根本不存在。
- **扫描件没有文本层**。必须 OCR，而 OCR 错误是检索层的错误而不是展示层的错误：错一个字符，词语就检索不到（「数值与代码验证」一节给出复算）。

对策是一条固定的流水线，顺序不能颠倒：

```text
页面（文本层或渲染图）
  → 版面分析：区块检测 + 分栏判定 + 阅读顺序排序
  → 区块分类：Title / NarrativeText / ListItem / Table / Figure / Caption / Formula
  → 文本清洗：页眉页脚过滤、去连字符、空白归一化
  → 元数据：page、bbox、章节层级、表号/图号
  → 按语义单元切分（表格与「标题+表头」绑定，见 [[rag-01]]）
```

版面分析有两条路线，工程上通常混用：**几何规则**（在版心内做 x 轴投影，找纵向贯穿、宽度超过阈值的空白带作为栏间距 gutter；再做 y 轴投影切行切块）和**模型检测**（版面检测器给出区块框与类型，再用阅读顺序模型排序）。规则路线便宜、可解释，但会被跨栏的宽表、大图和居中标题骗到；模型路线鲁棒，但需要标注数据与额外推理成本。

### 2. 阅读顺序重排：XY-cut 与「跨栏块作分隔符」

最常用的做法是 XY-cut 的递归切分：先在页面上找横向空白带把页面切成上下若干段，再在每段内找纵向空白带切成左右若干块，递归到不可再切的最小单元，然后按「从上到下、从左到右」输出。它等价于一个假设：空白带是语义边界。这个假设在双栏正文上成立，在跨栏元素上不成立。

因此实现上要加一条规则：**先识别跨栏块（宽度接近版心宽度的图或表），把它当作栏序的分隔符**，用它把页面切成若干「栏段」，每个栏段内部再独立做分栏排序。以 US Letter 页面为例可以估出几何量级：页宽 612 pt、左右边距各 72 pt，版心 468 pt，栏间距 24 pt，则单栏宽 $(468-24)/2 = 222$ pt；10 pt 字号、平均字宽约 5 pt 时单栏每行约 44 字符，版心高 648 pt、行距约 12.4 pt 时每栏约 52 行，双栏合计一页正文约 4600 字符。这些数字的意义在于：**分栏阈值必须在自己的语料上标定**，不同期刊与公文的 gutter 宽度差异很大，硬编码一个阈值迟早会切错。

无论走哪条路线，页码、bbox、区块类型这些元数据一定要留到下游。引用定位、原文高亮、以及「把图 chunk 和引用它的正文 chunk 绑在一起」都依赖它们。

### 3. 表格：先把结构还原出来

目标是把一块像素/坐标还原成网格：行、列、合并单元格、表头区域。难点是有无框线、合并单元格、跨页续表、以及旋转 90° 的横排表。工程实现上，分区（partitioning）阶段就应该把表格识别成**带类型的元素**而不是普通文本——这正是 Unstructured 的 partitioning 在做的事：把文档拆成 `Title`、`NarrativeText`、`ListItem`、`Table` 等元素，让下游可以按类型决定保留什么、怎么切；它同时提供了把表格取成 HTML 的路径，用于保住行列结构。

跨页表格用三重信号拼接：重复出现的表头、列数与列宽的一致性、以及「续表 / Table 3 (continued)」这类标记。三个信号都不支持时，宁可拆成两张表分别索引并在元数据里标注相邻关系，也不要赌一把错拼——错拼出的行会静默地污染数值答案。

结构还原的质量要单独度量，最实用的口径是**单元格 F1**：把还原结果与人工标注的网格按行列对齐后逐格比对，并把失败分成「表头丢失」「列错位」「数值串行」「跨页断裂」四类分别计数。只有分开统计，才知道该修检测器还是该修后处理。

### 4. 表格的表示形式：结构、摘要，还是两者都存

同一张表可以有三种入库形态，代价各不相同（「数值与代码验证」一节有实测 token 数）：

| 表示 | 保真度 | token 代价 | 适合的查询 |
| --- | --- | --- | --- |
| Markdown / HTML / CSV（结构化） | 高，可计算、可核验 | 最高（HTML 约为 Markdown 的 1.7 倍） | 数值、聚合、精确单元格 |
| 自然语言摘要 / 线性化 | 中，损失精度与可核验性 | 略高于 Markdown | 语义检索入口、模糊描述型问题 |
| 两者都存 | 高 | 两份存储与两次 embedding | 主流工程选择 |

「两者都存」的标准形态是：结构化表格作为回答阶段的 payload，生成的描述作为检索阶段的代表向量。检索命中描述，回答时把原表喂给模型。这样既不牺牲召回，也不让模型靠一段有损的文字去猜数字。

**检索单元**是第二个决策：

- 整表一条向量：语义完整，但长表会被 embedding 的窗口截断（「数值与代码验证」一节量化）。
- 行级 / 单元格级向量：数值查询命中准，索引规模按行数线性膨胀，需要额外的存储与 ANN 调参（见 [[rag-09]]）。
- 实用折中：先按表级向量（或表名/章节）粗筛出候选表，再在候选集内做行级或单元格级精排，避免对全量行向量建索引。

做行级索引时一定要把**坐标语义拼进文本**：`华东 | Q1 营收 | 128.4 百万元` 而不是 `128.4`。脱离列名的裸数字在向量空间里没有意义，也容易被其他表的相近数值挤掉。

### 5. 切分：表格不切断，表头与标题绑死

切分规则（与 [[rag-01]] 的通用 chunking 策略一致，表格是它的重要特例）：

- 表格作为原子单元，不与相邻正文混切；
- 「章节标题 + 表号表名 + 表头 + 表格 + 脚注」绑成一个 chunk——缺了表头，行数据没有语义；缺了表名，chunk 无法定位；
- 超长表格按「表头 + 连续行块」切片，每片携带同一个表 ID 与行区间，检索后按表 ID 聚合回整表；
- 上下文预算要算清：500 行的同构表格在 cl100k_base 下约 1.16 万 token（「数值与代码验证」一节），8k 窗口一次装不下，必须行块切片或先做列裁剪。

### 6. 图表：caption 是最好的文本代理

1. **把 caption 绑到图**。图号、标题、单位说明是图最可靠的文字代理，必须与图处在同一个 chunk，并保留图号用于交叉引用。
2. **生成 chart-to-text 描述**。用多模态模型输出「坐标轴含义、单位、趋势、极值与异常点」，作为图的可检索表示。这里有一条纪律：**生成的描述用于召回，不能作为事实来源**。VLM 很容易把趋势描述得很像、却把具体数值写错，数值问题必须回到原图或原始数据表核验。
3. **保留引用关系**。正文里的「见图 3」「如表 2 所示」是极强的召回信号：这类句子里往往就是用户的原始问法。做法是把图号归一化（`图 3`、`Fig. 3`、`figure 3` 统一），建立正文引用句与图 chunk 的双向链接——命中引用句时把图 chunk 一起带回上下文。

**公式与符号**是学术 PDF 的另一个坑，因为 PDF 会丢掉数学表达式的语义。Nougat 就是针对这一点提出的：用 Visual Transformer 做 OCR，把学术文档直接转成 markup 语言（论文摘要明确把「PDF 丢失语义信息、尤其是数学表达式」作为动机）。工程上要注意两点：它的设计前提是学术排版（数据集与输出格式都面向学术文档），搬到财报扫描件或中文公文前需要重新评估；它仍然有 OCR 误差，产物要抽检，不能当成无损转换。

### 7. 多模态检索的架构选择

| 架构 | 做法 | 优势 | 代价与失效场景 |
| --- | --- | --- | --- |
| 文本-only | 图/表转成文字描述进文本索引 | 复用现有索引、可解释、便宜 | 丢失视觉细节（示意图结构、图表形状） |
| 多模态 embedding | CLIP/SigLIP 类模型把图像与文本映射到同一空间 | 支持图搜图、文搜图、跨语言 | 对密集文本与具体数字不敏感，不能替代文本索引 |
| 混合 | 文本索引 + 图像索引双路召回后融合 | 覆盖两类查询，可分级降级 | 需要融合与重排策略，延迟与存储更高 |

决策依据是**问题类型**：「华东区 Q4 营收是多少」必须走表格/文本索引；「这个架构图里编码器和解码器之间有几种连接」才需要图像通道。多模态 embedding 的弱点是结构性的：对比学习的目标是图文整体匹配，不是细粒度数值识别，所以它天然擅长「找出与这张图相似的图/这段描述的图」，不擅长「读出图里的 1658.1」。融合策略与双路召回的具体做法接 [[rag-02]]。

### 8. 评测与迭代：把解析质量单独度量

建一个专门的「表格/图表/多栏」测试集，覆盖数值问答、跨页表格、图注检索、跨栏阅读顺序四类问题，然后分三层度量：

- **解析层**：表格结构还原率（单元格 F1）、阅读顺序正确率、页眉页脚过滤率、OCR 字符准确率。
- **检索层**：recall@k 与 nDCG@k（口径与 [[rag-04]] 一致）。
- **端到端**：答案正确率、引用正确率。

归因实验比指标本身更有用：对同一批失败样本，用人工修正过的解析结果重跑一遍检索与生成。如果答案正确率显著跳升，问题在解析层，此时调 prompt 是浪费时间。这条实验是所有「RAG 答不准」排查的第一步。

## 数值与代码验证

### 1. 同一张表格，四种表示形式的 token 代价

口径：12 行 × 5 列（地区 × Q1–Q4 营收，单元格为中英混排短串）；token 数用 tiktoken 的 `cl100k_base` 编码实测，不是按字符数估算。自然语言摘要的形态是每行一句「华东四个季度营收依次为 128.4、141.2、155.8、190.3 百万元」。

| 表示 | 字符数 | token 数 | 相对 Markdown |
| --- | --- | --- | --- |
| Markdown | 508 | 355 | 1.00× |
| CSV | 330 | 266 | 0.75× |
| HTML | 1013 | 595 | 1.68× |
| 自然语言摘要 | 483 | 443 | 1.25× |

表头与数据行的 token 统计：表头 30 token，数据行平均 23.0 token（22–26），整表 355 token 与二者之和的差额 49 token 是 Markdown 表头分隔行、管道符与换行等表格标记开销（30 + 12 × 23.0 + 49 = 355）。所以**行级 chunk = 表头 + 1 行 ≈ 53 token**；12 行切 12 个 chunk 共 636 token，是整表 355 token 的 1.8 倍——行级索引的存储放大就来自这个重复的表头。

### 2. 整表入库会被 embedding 窗口静默截断

把上面这张表放大到 500 行，口径同为数据行 23.0 token、固定开销 79 token（表头 30 + 表格标记 49），整表 $500 \times 23.0 + 79 = 11579$ token。常见 embedding 上限是 512 token：

| embedding 窗口 | 覆盖行数 | 覆盖率 | 后果 |
| --- | --- | --- | --- |
| 512 token | 18.8 / 500 | 3.8% | 96.2% 的行对检索完全不可见 |
| 8192 token | 352.7 / 500 | 70.5% | 仍有 29.5% 的行不可见 |

这就是「整表一条向量」不能作为长表默认方案的原因：截断不报错，只是让表尾静默消失。

### 3. 复现双栏按行交错读

```python
# 一页双栏：左栏 3 行、右栏 3 行。PDF 文本流按 y 排序，同一 y 上按 x 排序。
left = ["左栏第 1 行：本季度毛利率", "左栏第 2 行：提升 2.4 个百分点", "左栏第 3 行：主要来自规模效应"]
right = ["右栏第 1 行：研发费用同比", "右栏第 2 行：增长 18%", "右栏第 3 行：集中于推理优化"]
naive = " ".join(x for pair in zip(left, right) for x in pair)   # 按 y 行合并
correct = " ".join(left) + " " + " ".join(right)                # 按栏重排
print("naive  :", naive)
print("correct:", correct)
```

```text
naive  : 左栏第 1 行：本季度毛利率 右栏第 1 行：研发费用同比 左栏第 2 行：提升 2.4 个百分点 右栏第 2 行：增长 18% 左栏第 3 行：主要来自规模效应 右栏第 3 行：集中于推理优化
correct: 左栏第 1 行：本季度毛利率 左栏第 2 行：提升 2.4 个百分点 左栏第 3 行：主要来自规模效应 右栏第 1 行：研发费用同比 右栏第 2 行：增长 18% 右栏第 3 行：集中于推理优化
```

naive 版本把「本季度毛利率」和「研发费用同比」缝成了一个句子，句子级 embedding 会得到一个两边都不像的向量，任何 reranker 都救不回来。

### 4. 用 x 投影找栏间距（最小可运行版）

```python
import pdfplumber
def gutter_candidates(page, min_gap=12, min_cover=0.6):
    """在版心内找纵向贯穿的空白带，作为栏间距候选（坐标单位 pt）。"""
    words = page.extract_words()
    if not words:
        return []                                   # 无文本层：扫描件，转 OCR 分支
    x0 = min(w["x0"] for w in words)
    x1 = max(w["x1"] for w in words)
    top, bottom = page.height * 0.1, page.height * 0.9
    body = [w for w in words if top <= w["top"] <= bottom]
    if not body:
        return []
    span = int(x1 - x0)
    occupied = [False] * span                       # 逐 pt 标记「这一列有字」
    for w in body:
        for i in range(int(w["x0"] - x0), min(int(w["x1"] - x0), span)):
            occupied[i] = True
    gaps, run = [], 0
    for i, hit in enumerate(occupied + [True]):     # 尾部哨兵，冲掉最后一段空白
        if not hit:
            run += 1
            continue
        if run >= min_gap:                          # 宽度阈值
            gaps.append((x0 + i - run, x0 + i, run))
        run = 0
    kept = []                                       # 纵向覆盖：两侧文本都要铺开足够高度
    for gx0, gx1, width in gaps:
        left = [w for w in body if w["x1"] <= gx0]
        right = [w for w in body if w["x0"] >= gx1]
        if not left or not right:
            continue
        cover = lambda ws: (max(w["bottom"] for w in ws) - min(w["top"] for w in ws)) / (page.height * 0.8)
        if min(cover(left), cover(right)) >= min_cover:
            kept.append((gx0, gx1, width))
    return kept
```

判据是「空白带宽度 ≥ 阈值 且 纵向覆盖足够多的行」。阈值要在自己的语料上标定：US Letter（612 × 792 pt）左右边距 72 pt、栏间距 24 pt 时单栏宽 222 pt，而单栏排版里词间空格只有几 pt，两者差一个量级，所以栏数可以从「候选带数量 + 1」粗判；但跨栏宽表会把覆盖度打下来，这正是上面第 2 小节说的「跨栏块作分隔符」必须单独处理的原因。

### 5. OCR 字符错误如何放大成检索失败

设字符准确率为 $1-p$，则长度 $L$ 的词条在某次出现中完好无损的概率为

$$P(\text{完好}) = (1-p)^{L}$$

| 词条长度（行）与字符错误率（列） | 0.1% | 0.5% | 1% | 2% | 5% |
| --- | --- | --- | --- | --- | --- |
| 5 | 0.995 | 0.975 | 0.951 | 0.904 | 0.774 |
| 8 | 0.992 | 0.961 | 0.923 | 0.851 | 0.663 |
| 12 | 0.988 | 0.942 | **0.886** | 0.785 | 0.540 |
| 16 | 0.984 | 0.923 | 0.851 | 0.724 | 0.440 |
| 24 | 0.976 | 0.887 | 0.786 | 0.616 | 0.292 |

对数值单元格更严苛：一张 12 × 4 的表有 48 个数值，单元格级错误率 0.5% 时「全部正确」的概率只有 0.786，1% 时降到 0.617；200 个数值时 1% 错误率下全对概率只剩 0.134。所以数值型问答必须把 OCR 置信度当元数据用：低置信单元格在回答时显式标注不确定，或走「结构化抽取 + 校验」而不是纯文本检索。

### 6. 图表入库的一次性成本

chart-to-text 是一遍离线批处理，量级可以直接算：每张图生成 120 token 描述。

| 图片数量 | 单流吞吐 | batch | 耗时 |
| --- | --- | --- | --- |
| 100k | 200 tok/s | 1 | 16.7 h |
| 100k | 200 tok/s | 32 | 0.52 h |
| 1M | 200 tok/s | 32 | 5.2 h |
| 1M | 1500 tok/s（聚合） | 32 | 0.69 h |

口径：耗时 $= N \times 120 / (\text{吞吐} \times \text{batch})$，假设生成是唯一瓶颈、忽略排队与图片预解码。结论是**离线描述生成完全可行**（1M 图在单机批处理下是小时级），真正的成本在存储与索引，而不是生成。

### 7. 索引内存：图向量与行向量的规模

索引内存 $M = N \cdot d \cdot b$，$N$ 是向量条数，$d$ 是维度，$b$ 是每维字节数（fp32 为 4、fp16 为 2、int8 为 1、PQ 按 64 B/条计）。图向量（$d = 768$，CLIP ViT-L/14 量级）：

| 图数量 | fp32 | fp16 | int8 | PQ（64 B） |
| --- | --- | --- | --- | --- |
| 1M | 2.86 GiB | 1.43 GiB | 0.72 GiB | 0.06 GiB |
| 10M | 28.6 GiB | 14.3 GiB | 7.2 GiB | 0.60 GiB |

换成 $d = 1152$（SigLIP so400m 量级）时 10M 条 fp32 是 42.9 GiB，int8 是 10.7 GiB。对比行级表格索引：10 万张表 × 30 行 = 300 万条行向量只要 8.6 GiB（fp32），而 100 万张表 × 30 行 = 3000 万条的行向量 fp32 要 85.8 GiB、int8 也要 21.5 GiB——这就是上面第 4 小节建议的「表级粗筛 + 候选内行级精排」的直接原因。索引类型与 recall@k、latency 的权衡见 [[rag-09]]。

## 常见追问

- **追问**：扫描件和手写件怎么办？
  - 要点：没有文本层就必须 OCR/HTR，版面分析要在渲染图上做（检测器路线优先，几何规则在图像上同样可用但阈值更脆）。OCR 置信度必须写进元数据，低置信 region 在回答阶段显式标注不确定；关键数值字段走确定性抽取 + 校验（正则、单位一致性、行合计校验），不要依赖模型「读图读数」。
- **追问**：表格问答为什么常常是「检索 + 计算」两步？
  - 要点：检索只能给出行，聚合（求和、同比、排序、跨表比较）交给代码执行器或带工具的模型做，让 LLM 心算长表格的算术是不可靠的。这条链到 [[rag-06]] 的 agentic 路线：retrieval 负责取数，计算工具负责算数，模型只负责规划与表述。
- **追问**：图片能不能直接喂给多模态 LLM，不做转文字？
  - 要点：两者都要，但分工不同。转文字（caption）进索引是为了召回，原图进上下文是为了回答。原图的视觉 token 成本显著高于等长文本，而且塞多了会挤占上下文，所以只在「问题确实依赖视觉细节」时才在生成阶段带原图，并且要限制张数。
- **追问**：几百行的大表格怎么 chunk？
  - 要点：表头 + 连续行块切片，每片带表 ID、行区间、表名；表级或摘要向量负责粗筛，行级向量负责定位；回答前先按列裁剪与条件过滤（例如只取某地区、某季度）再喂模型。绝不把 500 行整表塞进一次生成。
- **追问**：双栏里的跨栏宽表、大图怎么处理？
  - 要点：先把跨栏块识别出来（宽度接近版心宽度），用它把页面切成若干栏段，栏段内再做分栏排序；跨栏块单独成一个 chunk，并挂到它所在的章节与页号上。否则宽表会把两栏内容按行缝合，产生最难排查的一类错误。
- **追问**：怎么保证「见图 3」这类引用不会断？
  - 要点：图号归一化后建立引用句与图 chunk 的双向链接。用户的问题经常就是正文那句话的改写，命中引用句时必须把图 chunk 一起带进上下文，否则召回的是「见图 3」这句无信息量的话。
