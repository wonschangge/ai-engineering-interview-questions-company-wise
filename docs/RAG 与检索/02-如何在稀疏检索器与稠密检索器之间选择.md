## 一句话答案

> 两者不是新旧替代关系，而是两种互补的召回器：BM25 用词项精确匹配打分（倒排索引、无需训练、可解释，但完全无法处理同义改写与跨语言），稠密双塔把 query 与 chunk 编码进同一向量空间做近似最近邻检索（对语义改写与口语化查询鲁棒，但对 ID、错误码、型号、内部代号这类精确串不敏感，且需要选型/训练与更大的索引内存）。选择看查询分布与语料形态：专有名词与精确串多、领域窄、需要可解释排序，先上 BM25；同义改写、口语化、跨语言查询为主，用稠密。生产 RAG 的默认答案是 hybrid 召回（RRF 融合）+ cross-encoder 重排 + 元数据过滤，因为两类失败在真实流量里同时存在；代价是第二套索引与一路并行召回延迟。

## 面试官在考什么

- 能不能把两者的打分机制写成式子：BM25 的 $k_1$、$b$、IDF 各自控制什么；稠密检索的一次内积背后是什么训练目标、什么索引结构。只答「一个查词、一个查语义」区分不出水平。
- 会不会对称地讲失败模式：BM25 输在词汇不匹配（lexical gap），稠密输在精确匹配与域外泛化。能说出「哪类查询走哪一路」比背结论值钱。
- 融合是否会算：为什么两路分数不能直接相加，RRF 与「归一化 + 加权」各解决什么问题，RRF 的 $k$ 在数学上做了什么。
- 有没有成本意识：倒排与向量索引的内存、更新、一致性成本完全不同，候选数级联与延迟预算怎么分配。
- 能不能给出可执行的决策：给定语料规模、查询分布、延迟预算、权限模型，选一路还是两路，并说清观察到什么指标会改主意。

**常见错误答案**

- 「稠密检索全面优于 BM25。」BEIR 的口径（18 个数据集、9 类检索任务、10 个系统覆盖 lexical / sparse / dense / late-interaction / reranking 五类架构、零样本跨域、主指标 nDCG@10）结论恰好相反：BM25 是强基线，dense 与 sparse 模型常常不如它，只有 reranking 与 late-interaction 平均更强但计算代价高。引用时也要带上论文自陈的限制：这些数据集的标注过程可能引入 lexical bias（候选多由词项匹配召回），对非词项方法不利。
- 「hybrid 就是把 BM25 分数和向量相似度相加。」两者量纲不可比：BM25 分数是 query 各词项贡献之和，上界随 query 长度与 IDF 变化；cosine 落在 $[-1,1]$。直接相加的实际效果约等于只用 BM25 排序。
- 「先上 hybrid，反正是标配。」两套索引意味着两条写入路径、两套一致性检查、一份额外延迟。语料小、查询分布单一时，单路更划算。

## 原理与推导

### 稀疏侧：BM25 的三项各解决一个退化问题

Lucene / Anserini 系实现的标准形式：

$$
\text{score}(q,d)=\sum_{t\in q}\text{IDF}(t)\cdot\frac{f(t,d)\,(k_1+1)}{f(t,d)+k_1\left(1-b+b\,\frac{\lvert d\rvert}{\text{avgdl}}\right)}
$$

其中 $f(t,d)$ 是词项 $t$ 在文档 $d$ 中的出现次数，$\lvert d\rvert$ 是文档长度（token 数），$\text{avgdl}$ 是语料平均长度，$N$ 是文档数，$n_t$ 是含 $t$ 的文档数。

- **IDF 解决「常见词没有区分度」**：$\text{IDF}(t)=\ln\!\left(1+\frac{N-n_t+0.5}{n_t+0.5}\right)$。$+0.5$ 是平滑，外层 $+1$ 保证 IDF 非负（$n_t=N$ 时不至于把分数拉成负数）。罕见词的 IDF 大，靠一个罕见词命中就能把文档顶上去。
- **词频饱和解决「重复堆分」**：分子含 $f(k_1+1)$、分母含 $f$，当 $f\to\infty$ 时这一项趋于 $k_1+1$，是硬上限。$k_1$ 越小饱和越快，语义上就是「同一个词出现第 10 次不该比第 2 次多 5 倍分」。
- **长度归一化解决「长文档占便宜」**：$b=0$ 完全不归一化，$b=1$ 完全按 $\lvert d\rvert/\text{avgdl}$ 缩放。长文档命中 query 词的概率天然更高，不归一化就会偏向长文本；归一化过头则会误伤「长而专」的文档（API 手册、法律条款）。
- **查询执行**：倒排索引按 term 取 postings list，用 WAND / block-max 一类上界剪枝跳过不可能进 top-$k$ 的文档。这一路不需要 GPU、不需要训练、不需要 embedding 模型，冷启动当天就能上；排序理由可以直接讲给人听（命中了哪些词、哪个词罕见）。

### 稠密侧：双塔编码 + 近似最近邻

- **结构**：query encoder 与 document encoder 相互独立（bi-encoder），各自输出 $d$ 维向量（常见 384 / 768 / 1024 / 1536），相似度取内积或 cosine。文档向量离线算好入库，在线只需编码一次 query，检索退化为最近邻搜索。
- **训练目标**：对比学习。正例是 (query, 相关文档)，负例是 in-batch 随机负例加从 ANN 索引里回挖的 hard negative，目标是让 $s(q,d^+)$ 比 $s(q,d^-)$ 高出一个 margin。这部分工作（数据、选型、迭代）正是 BM25 不需要的。
- **泛化从哪来**：语义相近的表述在训练分布里共现过，向量空间把它们拉近，所以「怎么改密码」能命中「凭据重置流程」。
- **精确串为什么丢**：整段文本被池化成一个定长向量，$d$ 个维度要同时装下主题、实体、语气；ID / 错误码 / 型号这类低频 token 在预训练里几乎不出现，其信号被高频语义平均掉。子词切分还会把 `SKU-48217` 拆成若干子词，编号本身近似随机，模型学不到「48217」与「48218」的差别。这不是调参能修好的，是表示粒度的上限。

### 失败模式对照

| 查询形态 | BM25 | 稠密检索 | 谁更好 |
| --- | --- | --- | --- |
| 精确串（`ERR_500`、工单号、函数名、型号） | 字面命中，IDF 高、排得前 | 被池化平均，常进不了 top-$k$ | 稀疏 |
| 同义改写（「怎么改密码」vs「凭据重置流程」） | 词项不重叠，分数为 0 | 语义近邻，稳定命中 | 稠密 |
| 跨语言（中文问、英文文档） | 词项完全不同 | 多语言模型可对齐语义 | 稠密 |
| 罕见专业术语（新药名、内部代号） | 只要字面命中，IDF 极高 | 训练中未见过，向量近似随机 | 稀疏 |
| 域外/新领域（模型没训过的语料） | 无需适配 | 零样本跨域明显退化 | 稀疏 |
| 口语化长问句、含大量停用词 | 噪音词项污染打分 | 语义更稳 | 稠密 |
| 长文档（几百到上千 token） | 依赖长度归一化 | 超出最大长度的部分不进入向量 | 都要处理，见 [[rag-01]] |

### 为什么 hybrid 有效：两个召回器的错误不相关

融合有效的前提不是「两个模型都强」，而是「一个错的地方另一个往往对」。单路 recall@k 的上界是它自己，并集的上界是 $\min(1, R_1+R_2)$，实际值取决于两路命中集合的重合度：重合度越低，融合收益越大。因此工程上要单独测「并集召回」——gold chunk 是否落在任一路 top-$k$ 内。这个数字同时是 reranker 的上限（[[rag-03]]）。

### 三种融合方式

**① 分数归一化 + 加权求和。** $s(d)=\alpha\,\hat{s}_{\text{sparse}}(d)+(1-\alpha)\,\hat{s}_{\text{dense}}(d)$，归一化常用 min-max $\hat{s}=\frac{s-s_{\min}}{s_{\max}-s_{\min}}$ 或 z-score $\hat{s}=\frac{s-\mu}{\sigma}$。两个坑：只在单路出现的文档缺另一路的分数，补 0 会把「只在稠密榜里靠前」的文档直接压死，常见做法是只在交集上归一化或补该路最低分；min-max 对离群值敏感，一个 BM25 分数异常高的文档会把其余分数压到 0 附近。

**② RRF（Reciprocal Rank Fusion）。** 只用排名，不碰原始分数：

$$
\text{RRF}(d)=\sum_{r\in\{1,2\}}\frac{1}{k+\text{rank}_r(d)}
$$

$k$ 取 60 是文献与主流实现（Elasticsearch / OpenSearch 的 `rank_constant`）的默认值。它处理的是「分数量纲不可比」：rank 1 在两路里含义相同，而 9.1 与 0.88 不可比。RRF 唯一可调的就是 $k$，所以它几乎不需要调参，适合做默认。

$k$ 的作用可以算出来：$k$ 越大，榜内高名次的优势越被抹平——$k=60$ 时 rank 1 与 rank 100 的分差只有 2.62 倍，$k=0$ 时是 100 倍——于是「两路都靠前」相对「一路第一」更值钱。定量地，双榜同 rank $r$ 的文档能击败「单榜 rank 1」的条件是 $2/(k+r)>1/(k+1)$，即 $r<k+2$；$k=60$ 时 $r\le 61$。这就是「共识优先」的准确含义。

**③ 级联。** 稀疏先召回（便宜、可解释）+ 稠密向量或 cross-encoder 在后段重排。级联的代价集中在后段：cross-encoder 要对每个候选做一次完整前向，复杂度是 $O(N\cdot L)$，而不是双塔的「每文档一次离线编码 + 每 query 一次在线编码」（数字见下一节）。

### 决策树

```text
语料 < 10^5 chunk 且查询以专有名词/ID 为主？
  └─ 是 → 先上 BM25（配字段权重与同义词表），把它当 baseline 量出来
查询多为自然语言问句，同义改写/跨语言明显？
  └─ 是 → 上稠密（选多语言或领域适配模型），配元数据过滤
两类查询都有，或线上 badcase 里两类都出现？
  └─ 是 → hybrid：两路各取 50–100 → RRF(k=60) → 20–50 → cross-encoder 重排 → 5–10 送 LLM
端到端检索延迟预算 < 50 ms？
  └─ 是 → 只保留一路，或降 ANN 的 efSearch/nprobe，用 recall 换延迟
语料每天高频变更？
  └─ 是 → 先算清两套索引的写入与一致性成本（[[rag-11]]）
有权限/多租户？
  └─ 是 → 过滤条件下推到两路召回，融合后再过滤会把候选打空（[[rag-08]]）
```

### 工程约束：两套索引、一份延迟预算、一个分词器

- **更新成本不同**：倒排是 term → postings 的可变长结构，支持分段刷新与后台合并；向量索引的插入往往触发图结构重连或聚类重训，删除通常只能标记删除后重建。两者的一致性语义要分别设计（[[rag-11]]）。
- **延迟预算**：两路召回并行执行时，端到端约等于较慢的那一路加上融合开销，而不是两者相加；但如果两路串行（例如稀疏先召回、稠密再重排），预算就是求和。这决定了要不要在同一跳里并发两路。
- **中文与中英混排**：BM25 的召回完全由分词器决定。中文按空格切分等于把整句当一个 token，BM25 直接失效；常见做法是分词器（jieba / IK 一类）或字符 bigram。字符 bigram 对分词错误更鲁棒，但 posting 数量随字符数线性增长（256 字符的 chunk 约 255 个 bigram，与英文 256 词的量级相当）。稠密侧用多语言模型补语义，但两路必须共享同一套 chunk 边界（[[rag-01]]）。

## 数值与代码验证

统一口径：$N=10^6$ 个 chunk，$\text{avgdl}=200$ token 每 chunk（英文按空格分词并去停用词；中文按分词器或字符 bigram，见上文），$k_1=1.2$、$b=0.75$（Lucene 默认）。以下数字均由公式直接复算。

### BM25 词项级算例

query 为 `refund policy`，某个 chunk 长度 500 token（2.5 倍 avgdl）：

| 词项 | 含该词的文档数 $n_t$ | IDF | 该 chunk 内频次 $f$ | 词频+长度因子 | 词项贡献 |
| --- | --- | --- | --- | --- | --- |
| refund | 1000 | 6.907 | 3 | 1.189 | 8.214 |
| policy | 100000 | 2.303 | 1 | 0.620 | 1.427 |
| 合计 | | | | | **9.641** |

同一 chunk 若长度正好是 avgdl（200），两词因子分别变成 1.571 与 1.000，合计 **13.157**——长度归一化把总分压低 26.7%。这也说明 BM25 分数是「每 query 内部可比、跨 query 不可比」的量：query 词项越多、IDF 越大，总分越高，量纲随 query 变化。

### 词频饱和（长度取 avgdl）

| $f$ | 1 | 2 | 3 | 5 | 10 | 100 | $\to\infty$ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 因子 | 1.000 | 1.375 | 1.571 | 1.774 | 1.964 | 2.174 | 2.200 |
| 占理论上限 $k_1+1=2.2$ | 45.5% | 62.5% | 71.4% | 80.6% | 89.3% | 98.8% | 100% |

读法：从第 1 次到第 3 次命中只多 57%，从第 3 次到第 100 次再多 38%——收益递减得很快，这是 $k_1$ 的语义。

### 长度归一化（固定 $f=3$）

| 长度 / avgdl | 0.25 | 0.5 | 1 | 2 | 2.5 | 5 | 10 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 因子 | 1.872 | 1.760 | 1.571 | 1.294 | 1.189 | 0.846 | 0.537 |
| 相对 avgdl | ×1.19 | ×1.12 | ×1.00 | ×0.82 | ×0.76 | ×0.54 | ×0.34 |

$b=0$ 时整行变成常数 1.571（完全不看长度）；$b=1$ 时 10 倍长的文档因子降到 0.440，惩罚过重。$b$ 的取值本质上是在「惩罚长度堆分」与「保护长而专的文档」之间选位置，BEIR 用的 Anserini 默认是 $k_1=0.9$、$b=0.4$，比 Lucene 默认更弱地惩罚长度。

### RRF 复算：$k=60$ 与源文 $1/\text{rank}$ 简化版的差异

沿用「BM25 榜：Doc-7、Doc-2、Doc-9；向量榜：Doc-3、Doc-7、Doc-5」这个排序结构：

| 文档 | BM25 名次 | 向量名次 | RRF($k=60$) | 源文 $1/\text{rank}$ 简化版 |
| --- | --- | --- | --- | --- |
| Doc-7 | 1 | 2 | **0.032522** | 1.500 |
| Doc-3 | — | 1 | 0.016393 | 1.000 |
| Doc-2 | 2 | — | 0.016129 | 0.500 |
| Doc-9 | 3 | — | 0.015873 | 0.333 |
| Doc-5 | — | 3 | 0.015873 | 0.333 |

两种算法给出的第一名相同（两榜都靠前的 Doc-7），但相对差距不同：$k=0$ 时 Doc-7 只领先 Doc-3 50%，$k=60$ 时领先 98%——引入 $k$ 之后，单榜第一的「独占优势」被削弱，跨榜一致变成了主导信号。附带的复算性质：单榜 rank 1 得 0.016393，双榜 rank 1 得 0.032787；$k=60$ 时 rank 1 与 rank 100 的分差仅 2.62 倍（$k=0$ 时 100 倍）。源文只给了 $1/\text{rank}$ 的直觉版并文字说明「真实公式会在名次上加一个常数」，上表按 $k=60$ 复算，量级以本表为准。

### 归一化的必要性（示意数值，非任何来源的实测结果）

四个候选文档，两路分数直接相加 vs min-max 归一化后按 $\alpha=0.5$ 加权：

| 文档 | BM25 原始 | cosine | 直接相加 | BM25 归一化 | cosine 归一化 | 加权融合 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 9.10 | 0.88 | 9.98 | 1.000 | 0.892 | **0.946** |
| B | 6.40 | 0.95 | 7.35 | 0.667 | 1.000 | 0.833 |
| C | 4.20 | 0.30 | 4.50 | 0.395 | 0.000 | 0.198 |
| D | 1.00 | 0.81 | 1.81 | 0.000 | 0.785 | 0.393 |

直接相加时排序与「只用 BM25 排序」完全相同（A > B > C > D）：cosine 的取值范围只有 0.65（0.30–0.95），BM25 的范围是 8.10（1.00–9.10），加和后排序完全由 BM25 决定；归一化加权后 D 反超 C，因为 C 的 cosine 是四个里最低的（归一化后为 0），而 D 的 cosine（0.81）明显高于 C（0.30）。这张表就是「不能直接相加」的完整论证。

### 索引内存（$10^6$ 个 chunk，每 chunk 256 token，向量维度 768）

索引口径按 chunk 名义长度 256 token 计；上文 BM25 打分用的 $\text{avgdl}=200$ 是语料平均长度，两者只差一个常数因子，不影响下面的倍数关系。

| 索引 | 计算口径 | 规模 |
| --- | --- | --- |
| BM25 倒排 | token 总量 $2.56\times10^8$；同 doc 内同 term 折叠为一条 posting，按去重后 50%–100% 计，delta 压缩后约 1.5–2 字节/posting | 0.19–0.51 GB |
| 稠密 fp32 | $10^6\times768\times4$ B | 3.07 GB |
| 稠密 fp16 | $10^6\times768\times2$ B | 1.54 GB |
| 稠密 int8 | $10^6\times768\times1$ B | 0.77 GB |
| HNSW 图（M=32） | level 0 每点 $2M$ 个 4 字节邻居 id；level $\ge 1$ 的期望额外开销为 $M\sum_{\ell\ge1}M^{-\ell}=\frac{M}{M-1}\approx1$ 个 id（只有 $1/M$ 的点出现在上一层） | 0.26 GB |
| HNSW 图（M=16） | 同上 | 0.13 GB |

结论：768 维 fp32 的向量数据（3.07 GB）是倒排索引的 6–16 倍，连图结构一起是 3.33 GB；量化到 int8 后总量降到 1.03 GB，与倒排的差距缩到 2.0–5.3 倍，代价是 recall 与重排裕度。维度翻到 1536 则向量内存直接翻倍（6.14 GB fp32）。这是「什么时候不该上稠密」的最硬理由，索引选型与 recall-latency 权衡见 [[rag-09]]。

### 重排与编码的算力对比（解释级联的成本结构）

$N=100$ 个候选、每条 $L=32+256=288$ token，cross-encoder 取 110M 参数：

$$
\text{FLOPs}\approx 2\cdot P\cdot N\cdot L = 2\times1.1\times10^8\times100\times288 = 6.34\times10^{12}
$$

A100 的 bf16 dense 峰值 312 TFLOP/s，理论上限 $6.34\times10^{12}/3.12\times10^{14}\approx 20.3$ ms；按 30%–50% MFU 折算是 41–68 ms。H100（989 TFLOP/s bf16 dense）理论上限 6.4 ms。对照双塔的在线成本：只编码一次 32 token 的 query，约 $2\times1.1\times10^8\times32=7.0\times10^9$ FLOPs，理论上限 22.6 μs 量级。也就是说级联的开销几乎全在重排与 ANN 随机访存，不在 query 编码——这解释了为什么「两路召回」本身便宜，「两路召回 + 重排」才是延迟预算的主要消耗项。口径：前向 FLOPs 用 $2PL$ 估，忽略 attention 的 $L^2$ 项与 kernel 效率，100 条候选可合批处理，实际吞吐取决于 batch 组织与长度分布；参数规模按 110M（BERT-base 量级）取，换成 BEIR 用的 6 层 MiniLM（约 22M）时按 $2PL$ 线性缩到约 1/5（重排细节见 [[rag-03]]）。

### 可运行片段：BM25 因子与 RRF

```python
import math

def bm25_term_factor(freq, doc_len, avgdl, k1=1.2, b=0.75):
    """BM25 中单个词项的词频 + 长度归一化因子，上限是 k1 + 1。"""
    return freq * (k1 + 1) / (freq + k1 * (1 - b + b * doc_len / avgdl))

def idf_lucene(n_docs, doc_freq):
    """Lucene 口径的 IDF：恒为非负。"""
    return math.log(1 + (n_docs - doc_freq + 0.5) / (doc_freq + 0.5))

def rrf(rankings, k=60):
    """rankings 是若干 {doc_id: 名次} 的字典，名次从 1 开始。"""
    scores = {}
    for ranking in rankings:
        for doc, rank in ranking.items():
            scores[doc] = scores.get(doc, 0.0) + 1.0 / (k + rank)
    return dict(sorted(scores.items(), key=lambda kv: -kv[1]))

print(round(bm25_term_factor(3, 500, 200), 4))      # 1.1892  长度 2.5 倍 avgdl
print(round(bm25_term_factor(3, 200, 200), 4))      # 1.5714  长度正好 avgdl
print(round(idf_lucene(10**6, 1000), 4))            # 6.9073  refund
print(rrf([{"Doc-7": 1, "Doc-2": 2, "Doc-9": 3},
           {"Doc-3": 1, "Doc-7": 2, "Doc-5": 3}]))
# {'Doc-7': 0.032522..., 'Doc-3': 0.016393..., 'Doc-2': 0.016129..., 'Doc-9': 0.015873..., 'Doc-5': 0.015873...}
```

## 常见追问

- **追问**：$k_1$、$b$ 各控制什么，需要调吗？
  - 要点：$k_1$ 控制词频饱和速度（上限 $k_1+1$），越小则第 2、3 次命中几乎不再加分；$b$ 控制长度归一化强度（0 关闭、1 完全归一化）。Lucene 默认 $k_1=1.2$、$b=0.75$，BEIR 用的 Anserini 默认是 $k_1=0.9$、$b=0.4$。chunk 长度分布越均匀，$b$ 越不敏感；真正需要精细控制长度权重时应上字段权重（标题/正文分别打分，BM25F），而不是全局调 $b$。
- **追问**：为什么长文档要归一化，会不会误伤？
  - 要点：不归一化时长文档既更容易命中 query 词、又能靠重复堆分，排序整体偏向长文本；但 $b$ 太大又会压死「长而专」的文档。另外长 chunk 的语义更稀释，向量的表示质量也会下降，所以长度问题要在 chunking 阶段一起解（[[rag-01]]）。
- **追问**：embedding 维度与检索成本是什么关系？
  - 要点：内存与带宽成本 ∝ 维度 × 每维字节数（768 维 fp32 = 3 KB/向量，$10^6$ 条就是 3.07 GB）；检索延迟主要由 ANN 的 efSearch/nprobe 与随机访存决定，点积本身的算力可忽略（768 维单次点积 1536 FLOPs）。降维或量化省内存，代价是 recall 与后续重排的裕度。
- **追问**：hybrid 的权重怎么调？
  - 要点：用带标注的检索集离线网格搜索；指标同时看 recall@k（决定 reranker 上限）与 nDCG@10（决定排序质量）。RRF 只有一个 $k$、通常固定 60，鲁棒且几乎不用调；加权法要同时定归一化方式和 $\alpha$，注意开发集过拟合与线上查询分布漂移。调参顺序是先定每路候选数，再定融合，最后调重排。
- **追问**：中文、中英混排怎么办？
  - 要点：BM25 完全依赖分词器，中文没有空格，按空格切分等于整句一个 token；用分词器或字符 bigram，bigram 对分词错误更鲁棒但索引更大。稠密侧用多语言模型对齐跨语言语义。最便宜的替代方案是在 query 侧加同义词/术语表来补 BM25 的词汇不匹配，成本远低于维护第二套索引。
- **追问**：什么情况下明确不该上 hybrid？
  - 要点：语料规模小（$<10^5$ chunk）时两种索引的延迟差异不显著，收益主要来自排序而非召回；查询分布单一（全是自然语言问句，或全是 ID 检索）时另一路是纯成本；端到端检索预算极紧时第二路与重排都要让位；索引高频变更时两套索引的一致性运维成本可能超过收益。

## 公司变体

- **Microsoft**：搜索与云检索平台的取向偏工程实现。公开产品线（Bing、Azure AI Search）把 BM25 与向量检索放在同一条查询管线里作为两个召回源，再叠语义重排，因此常见问法是「两路各取多少候选、怎么融合、延迟预算怎么分」「多租户与权限过滤放在哪一层」「倒排与向量索引的更新和一致性怎么处理」，也会问到 $k_1$、$b$、字段权重这类可运营的旋钮。原理层面通常停在「RRF 为什么不需要分数归一化」这一层，不要求手推 BM25。
- **Perplexity**：检索驱动的产品形态，对线上延迟、索引规模与新鲜度格外敏感，偏工程。常见问法：网页/新闻语料上 BM25 与稠密各自贡献什么、候选数与重排预算怎么砍、索引多久刷新一次、股票代码/版本号/域名这类精确串为什么不能只靠向量。数学推导一般不会追到 IDF 的平滑项。
- **Glean**：企业搜索。语料是内部文档、工单与聊天，查询里大量出现人名、项目代号、工单号与缩写——正好是稠密检索最弱、BM25 最强的一类；同时企业查询又需要语义泛化与权限过滤，所以 hybrid 基本是默认答案。这家偏工程实现与数据治理：连接器与 ACL 同步、元数据过滤下推、增量索引、企业术语与同义词表。

以上是依据三家公司的公开技术输出与产品形态做的判断，不是对具体面试流程的描述。
