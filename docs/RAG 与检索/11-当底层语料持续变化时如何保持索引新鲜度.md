## 一句话答案

> 先把「新鲜度」拆成三个可验收的 SLO：变更到**可被检索到**的延迟、到**旧版本不可见**的延迟、到**删除生效**的延迟。
> 再用源系统能力允许的最强手段捕获变更（CDC / 事件流 > webhook > mtime 轮询，全量重扫只做纠偏），
> 把流水线写成幂等的「去重排序 → chunk 级 diff → 增量 embedding → upsert → tombstone」，
> 最后用蓝绿索引 + 别名切换把「重建」和「在线服务」解耦。
> 成本几乎全在 embedding 和删除压实上，写入 IO 不是瓶颈。

## 面试官在考什么

- 你会不会**把「新鲜度」定义成可度量的东西**。只答「定时重建」等于没答；能给出「源变更 → 可检索」这条链路上每一段的预算分配，才算入门。
- 你知不知道**三个 SLO 是三件事**：新版本可见、旧版本退休、删除生效。绝大多数人只做第一个，结果就是「文档更新了，但答案里还是旧段落」以及「源系统删了，索引里还搜得到」。
- 你是否理解**三种索引的更新代价完全不同**：倒排索引近实时且便宜（refresh 出一个新 segment 就可见），HNSW 的删除是标记删除、节点仍占内存和遍历预算，IVF 的聚类中心是训练出来的、数据分布漂移就要重训。
- 你能不能算出**「增量」到底省多少**：如果只想着「把变了的文档重新嵌一遍」，你就漏掉了 chunk 级 diff —— 一篇 50 个 chunk 的文档改一段，应该只重嵌 1~2 个 chunk。
- 常见错误答案：
  - 「每隔 X 分钟全量重建一次索引」——说不出 X 怎么定、重建期间服务怎么办、双份存储从哪来、删除为什么仍然不生效。
  - 「源系统删掉文档，RAG 自然就搜不到了」——索引、检索缓存、prefix cache、生成层引用四层都可能残留旧内容。

## 原理与推导

### 1. 先把「新鲜度」变成三个 SLO

「新鲜度」不是形容词，是三个可以画在监控面板上的时间差。设源系统提交变更的时刻为 $t_{\text{commit}}$：

| SLO | 定义 | 对应机制 | 漏掉会怎样 |
| --- | --- | --- | --- |
| $T_{\text{visible}}$ | 新版本首次可被检索到的时刻 $-\,t_{\text{commit}}$ | 增量写入 + refresh | 用户搜不到刚发布的内容 |
| $T_{\text{retire}}$ | 旧版本最后一次可被检索到的时刻 $-\,t_{\text{commit}}$ | 版本覆盖写 / 别名切换 | 答案里引用了已被修订的旧段落 |
| $T_{\text{delete}}$ | 删除请求到彻底检索不到的时刻差 | tombstone + 压实 + 缓存失效 | 合规事故：已删除内容仍能出现在答案里 |

端到端延迟可以按流水线分解，这是回答这道题的骨架：

$$ T_{\text{visible}} = T_{\text{capture}} + T_{\text{queue}} + T_{\text{parse}} + T_{\text{embed}} + T_{\text{index}} + T_{\text{refresh}} $$

每一段都可以单独优化，而且每段的「价格」差好几个数量级：$T_{\text{refresh}}$ 是配置项（改 refresh 间隔即可），$T_{\text{embed}}$ 要花 GPU，$T_{\text{queue}}$ 是吞吐与延迟的取舍。面试时先报预算再报手段，比直接罗列技术名词高一个档次。

### 2. 变更捕获：四种来源与各自的一致性保证

| 方式 | 典型延迟 | 一致性 | 会怎么失效 |
| --- | --- | --- | --- |
| mtime / size 轮询 | = 轮询周期 | 弱：只能看到「可能变了」 | mtime 精度、跨机时钟、只改内容不改 mtime 的写入；扫全量成本随语料线性增长 |
| 内容 hash 轮询 | = 轮询周期 | 中：能精确判定变没变 | 必须读全文，读放大比 stat 高一到两个数量级 |
| CDC（binlog / WAL） | 秒级 | 强：按事务边界有序 | 只覆盖库内数据，覆盖不到对象存储与第三方系统；快照与增量需要衔接位点 |
| webhook / 事件流 | 亚秒级 | 至少一次投递，可能乱序、重复 | 源系统不一定提供；事件丢失时无人发现，必须配重扫兜底 |

三个关键点：

1. **CDC 的起点必须是「快照 + 位点」**。先做一次全量快照并记录当时的 binlog 位点，再从位点开始消费增量；否则快照期间发生的变更会永久丢失。这是 CDC 面试题最常见的追问。
2. **「至少一次」+ 幂等 = 可见结果等价于「恰好一次」**。不要试图在传输层做到 exactly-once，把幂等做在应用层：事件携带 `(doc_key, seq, updated_at)`，流水线只接受比已应用版本更新的写入。
3. **轮询的成本要算清**。对 100 万份文档做一次 `stat`，按每次 0.1 ms 计是 100 s/轮；想维持 60 s 的轮询周期，单 worker 根本追不上（需要 ≥2 个并行 worker），1000 万份文档则需要 ~17 个。所以轮询只适合小语料或作为兜底，不适合当主链路。

### 3. 更新流水线：幂等 + chunk 级 diff

一条变更事件的完整旅程：

1. **去重与排序**：按 `(seq, updated_at)` 取最大版本，迟到事件（版本小于已应用版本）直接丢弃，不能反过来覆盖新内容。
2. **重新解析与切分**：这一段的粒度由切分策略决定（见 [[rag-01]]）。要让 diff 有意义，chunk 的 id 必须是**内容哈希**而不是「文档 id + 序号」——否则在文档开头插一段，后面所有 chunk 的序号都平移，全部被判为「变了」。
3. **增量 embedding**：这是流水线里唯一的重活。文档级 diff 与 chunk 级 diff 的差距是数量级的：一篇 50 chunk 的文档改一段，文档级要算 50 次前向，chunk 级只要 1 次，相差 50 倍。
4. **upsert**：向量索引与倒排索引都要写。顺序上**先写新版本、再删旧版本**，让窗口期内是「新旧都能搜到」而不是「都搜不到」——前者是排序问题，后者是可用性问题。
5. **删除旧版本**：不是立即物理删除，而是打 tombstone（`deleted_at` 标记 + 检索时过滤），再按策略压实。

### 4. 索引层的现实约束

#### HNSW：删除是标记删除，节点仍占内存和遍历预算

HNSW 的内存由两部分组成：

$$ M_{\text{vec}} = N \cdot d \cdot b_v, \qquad M_{\text{graph}} \approx N \cdot 2M \cdot 4\ \text{B} $$

其中 $d$ 是向量维度、$b_v$ 是每维字节数、$M$ 是每节点的邻居数（layer 0 存 $2M$ 条双向边，每条边一个 4 字节 id）。$N=10^7$、$d=768$、fp32 时：向量本体 28.6 GiB，$M=16$ 的图结构再加 1.19 GiB，合计约 29.8 GiB。

被标记删除的节点**不会释放内存，也不会从图里摘掉**，搜索时仍然会访问它们然后过滤。设删除占比为 $p$，要把遍历预算维持在同一水平，需要把 `ef_search` 放大：

$$ ef' \approx \frac{ef}{1-p} $$

$p=20\%$ 就是 1.25 倍，同时还白付了 6.0 GiB 内存。所以「标记删除 + 定期压实」是必须的，压实的实现就是重建索引片段。

#### IVF / IVF-PQ：聚类中心是训练出来的

IVF 先用 k-means 把向量空间切成 $n_{\text{list}}$ 个桶，检索时只扫 $n_{\text{probe}}$ 个最近的桶。工程上常用的经验量级是 $n_{\text{list}} \sim \sqrt{N}$ 到 $16\sqrt{N}$（$N=10^7$ 时约 3.2k 到 50k，具体要按 recall/latency 实测调）。

麻烦在于：**桶边界是训练时定下的，新增数据不会让它变好**。语料分布大幅漂移（新领域、新语言、新文档类型）后，桶会失衡——少数桶塞进大量向量，$n_{\text{probe}}$ 覆盖不到，recall 静默下降。这时只能重训聚类中心并重建，属于「不重建就慢慢变差」的索引类型。IVF-PQ 的好处是可以用 PQ 把向量压得很小（768 维 fp32 是 3072 B，$m=96$ 个 8 bit 子量化器只有 96 B，压缩 32 倍，$10^7$ 条约 0.96 GB），代价是量化误差本身会吃掉一部分 recall，重建时还要重新训练码本。

#### 倒排索引（BM25）：近实时且便宜，但有全局耦合

BM25 是稀疏检索的默认打分：

$$ \mathrm{score}(q,d)=\sum_{t\in q}\mathrm{IDF}(t)\cdot\frac{f(t,d)\cdot(k_1+1)}{f(t,d)+k_1\left(1-b+b\cdot\dfrac{|d|}{\mathrm{avgdl}}\right)}, \qquad \mathrm{IDF}(t)=\ln\!\left(1+\frac{N-n(t)+0.5}{n(t)+0.5}\right) $$

它的更新之所以便宜，是因为 posting list 是追加的。Elasticsearch 的 near real-time 机制给了这条路线的现实参照：新文档先落在内存索引缓冲，**refresh** 时写出并打开一个新 segment（segment 类似一个倒排索引，index 是 segment 集合加一个 commit point），此时文档就可被搜索，而真正的落盘（commit）要贵得多，所以延后做。默认每 1 秒 refresh 一次，且只对最近 30 秒内收到过搜索请求的索引生效；改变这一行为的方式有三种：等 refresh 间隔、请求时带 `?refresh` 参数、调用 Refresh API（`POST _refresh`）。

这解释了为什么 `refresh_interval` 是「新鲜度 vs 写入吞吐」的旋钮：调小它可见延迟下降，但每个 refresh 都产生一个新 segment，合并（merge）要不断把数据重写一遍，写放大上升。

但要注意 BM25 的隐含代价：$\mathrm{IDF}$ 里含有全局的 $N$（Lucene 实现里 $N$ 是分片内的文档数，写同一分片才会互相影响）。语料从 1000 万涨到 2000 万后，一个 df=5 万的词 IDF 从 5.298 涨到 5.991，涨了 13.1%。也就是说**任何一次写入都在轻微改变同分片内所有词的打分**。这不影响增量写入的可行性，但意味着「打分完全可复现」在持续变化的索引上不成立，排序的稳定性要靠固定快照或定期重排来保证。

**混合检索在新鲜度上有结构性优势**：倒排那一路可以做到秒级可见，稠密那一路要等 embedding（见 [[rag-02]]）。所以「刚发布的文档先靠 BM25 兜住、等向量补齐后自然被稠密召回接管」是一个很实用的降级设计。

### 5. 无停机切换、版本绑定与缓存失效

- **蓝绿 / 别名切换**：新索引在后台建好、回填、跑一遍校验指标（recall@k、canary query 集），然后把读别名原子切过去，旧索引延迟下线。避免「原地重建」期间一半查询打到半成品索引上。
- **重建期间的双份存储**：上面算出的 29.8 GiB 单份 HNSW 索引，蓝绿要 59.6 GiB。单机 48 GiB 内存的节点根本放不下，只能换大内存机型或**按分片滚动切换**（每次重建一个分片，用副本承接流量）。
- **索引版本绑定 embedding 模型版本**：索引元数据里记录 `(model_id, dim, normalize, chunker_version)`。切模型时如果新旧向量混在一张表里，同一个 query 会在两套语义空间里各召回一半，这就是语义漂移的一种（见 [[rag-07]]）。切换必须整索引重建 + 别名切换，不能增量「打补丁」。
- **缓存必须按索引版本失效**：检索缓存与 prefix cache 的 key 里要含 `index_version`（以及权限指纹）。否则「文档更新了但缓存里还是旧答案」会持续到缓存自然过期（见 [[inference-serving-05]]）。

### 6. 成本模型与取舍

$$ C_{\text{total}} = \underbrace{c_{\text{embed}}\cdot N_{\text{tok}}}_{\text{算力，主要项}} + \underbrace{c_{\text{io}}\cdot N_{\text{chunk}}\cdot(1+\text{写放大})}_{\text{索引写入}} + \underbrace{c_{\text{store}}\cdot V\cdot \Delta t_{\text{rebuild}}}_{\text{蓝绿双份存储}} $$

三档新鲜度的现实映射：

| 目标 | 手段 | 代价 |
| --- | --- | --- |
| 秒级 | CDC/事件流 + chunk 级 diff + `refresh_interval=1s` + 删除 tombstone 立即过滤 | embedding 服务常驻，流式小批量（吞吐换延迟），segment 写放大最高 |
| 分钟级 | 事件流 + 微批（60 s 攒一批）+ 定期压实 | 主要档位，绝大多数场景的性价比最优 |
| 小时级 / 天级 | 定时增量 + 夜间全量重建 | 最省，但删除与权限变更的生效延迟同样被拉长 |

判断标准一句话：**用户能否察觉「内容变了但答案没变」**。面向外部的时效敏感场景（新闻、客服、代码库）必须做到分钟级以内；内部知识库小时级通常够用；而**删除和权限收回不受这个判断影响**——它们由合规要求决定，通常要求与安全侧的权限变更同节奏。

**写入侧**（口径：每 chunk 3072 B 向量 + 2 KB 元数据 = 5120 B；写放大 $W\approx 1+\log_{10}S$，$S$ 为每日新增 segment 数）：

| refresh 间隔 | 可见延迟 p50 / p99 | segment 数/天 | 写放大估计 |
| --- | --- | --- | --- |
| 1 s | 0.5 s / 1 s | 86,400 | 5.9× |
| 5 s | 2.5 s / 5 s | 17,280 | 5.2× |
| 30 s | 15 s / 30 s | 2,880 | 4.5× |

间隔从 1 s 放宽到 30 s，可见延迟差 30 倍，写放大只从 5.9× 降到 4.5×（省 24%）：**这条曲线是明显递减的，靠调 refresh 换吞吐的收益有限**，真正的大头在别处。全量回填的写入量：$10^7\times5120\ \text{B}\approx51.2$ GB payload，乘 5.9× 写放大约 302 GB，NVMe 顺序写 2 GB/s 下约 151 s——相比 2.87 GPU-h（约 10,300 s）的 embedding，**写入 IO 只占 1.5%**。结论：优化顺序应该是「少算 embedding」> 「少写索引」> 「调 refresh」。

HNSW 单次插入的内存流量：$\text{ef\_construction}=200$ 个候选 × 768 维 × 4 B ≈ 600 KB 随机访问；按 20 GB/s 有效随机带宽算是 ~31 µs/次（约 3.2 万次/s 的**上限**，实际受锁竞争与 visited 集合管理拖累会低不少）。$10^7$ 次插入按 3 万次/s 算是 333 s ≈ 5.6 min，仍然远小于 embedding 的 2.87 GPU-h。

```python
import math

def bm25_idf(n, N):
    return math.log(1 + (N - n + 0.5) / (n + 0.5))

def bm25_tf(f, dl, avgdl, k1=1.2, b=0.75):
    return f * (k1 + 1) / (f + k1 * (1 - b + b * dl / avgdl))

N, avgdl = 10_000_000, 400.0
print([round(bm25_idf(n, N), 3) for n in (1, 100, 10_000, 50_000, 500_000, 5_000_000)])
# [15.713, 11.508, 6.908, 5.298, 2.996, 0.693]
print([round(bm25_tf(f, avgdl, avgdl), 3) for f in (1, 2, 5, 10, 100)])
# [1.0, 1.375, 1.774, 1.964, 2.174]
print(round(bm25_idf(50_000, 20_000_000) / bm25_idf(50_000, N) - 1, 4))  # 0.1308
```

```python
import hashlib

def chunk_id(text: str) -> str:
    """chunk id 必须来自内容，而不是「文档 id + 序号」，否则插入一段会让后续全部失效。"""
    norm = " ".join(text.split()).lower()
    return hashlib.blake2b(norm.encode(), digest_size=16).hexdigest()

def should_apply(event: dict, applied: dict) -> bool:
    """幂等闸门：至少一次投递 + 版本单调 = 可见结果等价于恰好一次。"""
    cur = applied.get(event["doc_key"])
    ver = (event["seq"], event["updated_at"])
    return cur is None or ver > cur

def diff_chunks(new_chunks: list[str], old_ids: set[str]):
    """chunk 级 diff：返回需要重新 embedding 的 chunk 和需要打 tombstone 的旧 id。"""
    new_ids = [chunk_id(c) for c in new_chunks]
    new_set = set(new_ids)
    added = [(cid, c) for cid, c in zip(new_ids, new_chunks) if cid not in old_ids]
    removed = [cid for cid in old_ids if cid not in new_set]
    return added, removed

# 一篇 50 chunk 的文档改一段：文档级要 50 次前向，chunk 级只需 1~2 次，差 25~50 倍。
old, docs = {chunk_id(f"chunk {i}") for i in range(50)}, [f"chunk {i}" for i in range(50)]
print(len(diff_chunks(docs, old)[0]))  # 0：完全相同，全部复用
docs[7] = "chunk 7 edited"
print([len(x) for x in diff_chunks(docs, old)])  # [1, 1]：只重嵌 1 个 chunk，旧版本打 1 个 tombstone
```

流水线每段的延迟预算（p99 量级，口径：CDC 采集 → 队列 → 解析 → 微批 embedding → upsert → 等一次 refresh）：

| 阶段 | CDC/事件流 | 说明 |
| --- | --- | --- |
| 采集 | 1.0 s | binlog/事件流消费滞后 |
| 队列 + 去重窗口 | 5.0 s | 去重窗口必须 ≥ 最大乱序延迟，是延迟的主要来源之一 |
| 解析 + 切分 | 0.2 s | 单文档，含 PDF/HTML 抽取 |
| embedding（批 64 或 200 ms 超时） | 0.3 s | 微小批摊薄成本，同时不把延迟拉爆 |
| upsert | 0.5 s | 向量 + 倒排双写 |
| 等 refresh | 1.0 s | `refresh_interval=1s` 的最坏情况 |
| **合计** | **≈ 8.0 s** | 秒级档位可达；压到 1 s 以内必须动采集和去重窗口 |

对账（验证增量没漏数据）：源系统文档数（按 `updated_at` 分组）vs 索引中 live chunk 数（按 `doc_key` 去重），差异按小时对齐；再抽 1% 的文档做「重算 chunk id 集合」比对，任何非零差异告警。这套对账是唯一能发现「事件永久丢失」的手段——延迟指标发现不了数据缺失。

## 常见追问

- **追问**：删除一个文档后，怎么保证它再也不出现在答案里？
  - 要点：四层都要清。① 索引层打 tombstone 并在检索时过滤（HNSW 标记删除会继续占内存，建议按删除占比，例如 >20%，触发一次压实）；② 检索缓存按 key 精确失效；③ prefix cache 的 key 必须含 `index_version`，否则旧上下文还能命中；④ 生成层对引用做校验，chunk 已被删除时拒绝输出该段落。只做第一步，剩下三层会一直到缓存自然过期才干净。
- **追问**：权限变更怎么同步？源系统把某人的访问权收回了，索引怎么办？
  - 要点：权限不能只在写入时烘焙进 chunk 元数据，那样收权要等重嵌入。正确做法是把 ACL 作为独立的过滤维度（见 [[rag-08]]），权限变更走单独的短延迟通道（秒级/分钟级），与内容索引解耦；同时权限指纹要进缓存 key，权限一变，相关缓存立即失效。
- **追问**：怎么验证增量流水线没有漏数据？
  - 要点：三个层次的断言。① 计数对账：源文档数 vs 索引 live chunk 数，按小时对齐；② 内容对账：抽样 1% 文档重算 chunk id 集合做集合比对；③ 端到端 canary：放一份「每分钟更新一次」的探针文档，用固定 query 检查最新内容是否可检索，并把延迟做成 SLO 面板。计数对账能发现丢失，canary 能发现延迟劣化。
- **追问**：回填一个 1000 万 chunk 的新索引时，怎么保护在线流量？
  - 要点：物理隔离。回填走独立集群/独立副本集，或至少在倒排侧把 `refresh_interval` 设为 -1 走批量模式、限制 merge 的 IO 配额；向量侧控制并发插入数避免 CPU/内存带宽被吃满。切换时只切读别名，不做双写（双写会引入两个索引不一致的窗口，除非有幂等去重）。
- **追问**：变更风暴（比如上游做了一次全量重导）怎么扛？
  - 要点：按 `doc_key` 做服务端合并（同一文档的多个待处理事件只保留最大版本），把「事件数」压成「待处理文档数」；再按文档优先级排队（被高频检索的文档优先），给流水线加背压而不是无限缓冲；极端情况下把这次风暴识别为「批量重建」，直接走蓝绿路径，别让它污染增量通道。
- **追问**：怎么论证新鲜度做这么高是值得的？
  - 要点：把新鲜度当成一个可以定价的维度：算出「秒级 / 分钟级 / 小时级」三档各自的月算力与存储成本（上面的表），再对应到业务指标（客服首答准确率、代码补全的建议是否过时）。如果业务方说不出「用户能察觉内容过时」的场景，就退到分钟级——但**删除与权限的 SLO 不能跟着退**，它们由合规决定。

## 公司变体

`asked_at` 覆盖的两家在公开材料与岗位方向上都是**偏工程实现**的，但具体侧重不同：

- **Perplexity**：语料是持续被重写、删除、新增的网页，索引新鲜度就是产品本身。追问方向偏「抓取到可检索的端到端延迟怎么压」「按时间分层的索引与抓取调度」「旧版本网页必须不可见的语义」。准备重点：三个 SLO 的度量、变更捕获来源的取舍、以及在大规模网页语料上的成本曲线。
- **Cursor**：语料是高频率、小改动的代码库。代码语料的特征是「每次提交只动几个文件、文件内只动几行」，所以追问方向偏 chunk 级 diff 的粒度与哈希去重、按分支/提交隔离索引、以及 embedding 模型升级时的整索引重建与别名切换。准备重点：增量流水线的幂等与 chunk id 设计，以及蓝绿切换的成本。

以上是基于两家公开技术材料与岗位方向的侧重判断，具体题目以实际面试轮次为准。
