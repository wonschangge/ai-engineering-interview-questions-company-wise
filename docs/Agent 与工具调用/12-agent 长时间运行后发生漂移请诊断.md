## 一句话答案

> 「漂移」不是一种故障，是六类可分别观测的机制：**目标漂移**（子任务取代原任务）、**上下文污染**（一次错误观察或幻觉结论进入上下文，之后被每一步当既定事实引用）、**记忆污染**（错误事实写进长期记忆并跨会话复用）、**环境/工具漂移**（API、返回格式、权限或数据分布变化）、**提示/模型漂移**（模型版本升级、系统提示被工具描述与历史挤占或截断）、**误差累积**（每步正确率 $p$、$n$ 步整体成功率约 $p^n$：$0.95^{20}\approx 35.8\%$，半衰期只有 13.5 步）。
> 诊断的题眼是**先定位第一次偏离的那一步**，而不是解释最后一步为什么错：拿可回放 trace 与成功轨迹对齐 diff，或对「状态从哪一步开始不对」做二分回放，$m$ 步最多 $\lceil\log_2 m\rceil$ 轮（40 步 6 轮）就能收敛。
> 修复必须与病因一一对应：静默错误靠外部验证器与检查点，上下文问题靠结构与位置，接口问题靠契约与版本锁定。换更大的模型是排除法之后的最后一步，不是第一步。

## 面试官在考什么

- 能不能把「它变笨了」翻译成可观测、可复现、可归因的具体现象。这一题的分水岭就在这里：初级候选人描述感受，资深候选人先给分类再给观测面。
- 有没有误差累积的数量感：说得出 $p^n$、半衰期与反解出的每步精度要求，知道「每步再准一点」和「多跑几步」在数量级上完全不对等。
- 是否具备排障方法论而不是调 prompt 的直觉：可回放 trace、第一次偏离、最小复现、版本 A/B。顺序是**先定位、后修复**，不是把能想到的手段都试一遍。
- 会不会区分「模型能力不足」与「上下文管理不当」——这两类病因的修复方向一个是换路径/换模型，一个是改上下文结构，混在一起就会一直做无用功。
- 有没有把一致性纳入工程闭环：pass^k、成功率随步数的衰减曲线、工具错误率、回归门禁、记忆写入与回滚策略。

常见的错误答案：

- 「换个更强的模型，或者把温度调到 0」。AgentBench 的结论是长期推理、决策与指令遵循才是 agent 的主要失败来源，而不是某个单点能力；换模型还会顺手引入新的一类漂移（提示/模型漂移），把原有归因全部搅乱。温度调到 0 只压掉采样噪声，对目标漂移、工具漂移、记忆污染完全无效。
- 「加大上下文窗口，把历史全留着」。上下文更长有四项代价：注意力被稀释（位置偏差）、单次 prefill 的计算量对序列长度 $L$ 是 $O(L^2)$、压缩时关键约束被丢、无关观察增多使污染面变大。「数值与代码验证」一节给出这些数字的口径。

## 原理与推导

### 六类漂移：机制、最先能观测到的信号、修复方向

| 类别 | 机制 | 最先能观测到的信号 | 修复方向 |
| --- | --- | --- | --- |
| ① 目标漂移 | 子任务取代原任务（「先把测试跑通」慢慢变成「重构整个模块」），越做越偏 | 最近 $k$ 步的工具调用与初始验收标准的重合度下降；出现原任务不需要的写操作 | 结构化任务清单 + 显式验收标准，每段结束复述目标 |
| ② 上下文污染 | 一次错误观察或幻觉结论进入上下文，之后每一步都把它当已确认事实（self-conditioning） | trace 里同一句未经工具确认的结论被反复引用；后续动作不再产生新证据 | 证据与断言分离，未验证结论显式标注；纠错时写入显式「撤销」而不是静默改口 |
| ③ 记忆污染 | 错误事实被写进长期记忆，跨会话被检索并复用（[[agents-07]]） | 记忆写入没有验证环节；检索命中率上升但任务成功率下降 | 只写已确认事实，记忆带来源、版本与有效期，可回滚 |
| ④ 环境/工具漂移 | 下游 API 变更（字段改名、返回由对象变数组、分页语义变化）、权限与配额变化、数据分布变化 | 工具错误率与 schema 校验失败率上升；同一参数的返回结构变化 | 契约测试 + 返回归一化层 + schema 版本校验，失败可见化 |
| ⑤ 提示/模型漂移 | 模型版本升级改变行为；系统提示被工具描述与历史挤占、被截断 | 同一 trace 重放的行为差异；关键段落 token 位置后移或整段消失 | 锁定模型与提示版本，建回归集，关键约束后置并定期重申（[[llm-internals-13]]） |
| ⑥ 误差累积 | 每步都有失败概率，长链条上「至少错一次」接近必然 | 成功率随步数单调衰减；同一任务多次运行方差大 | 缩短任务链、设中间检查点、加外部验证器 |

把这六类混成一句「模型漂移了」是这题最常见的失分点：①⑤ 改提示结构，② 改上下文治理，③ 改记忆写入策略，④ 修管道，⑥ 改任务划分与验证，五个方向互不替代。

### 误差累积：$p^n$ 的推导与它的两个边界

分步推导：

1. 把任务切成 $n$ 个**必须都对**的决策点（一次工具调用的选择，加上对返回结果的解读，算一步）。
2. 链式法则给出整体成功率
   $$P(A_1\cdots A_n)=\prod_{i=1}^{n}P\!\left(A_i \mid A_1\cdots A_{i-1}\right)$$
3. 假设各步条件正确率都等于 $p$ 且相互独立，条件概率退化为常数，得到
   $$P(\text{整体成功})=p^n$$
4. 半衰期由 $p^n=1/2$ 解出：
   $$n_{1/2}=\frac{\ln 2}{\ln(1/p)}$$
   $p=0.95$ 时是 13.51 步，$p=0.99$ 时是 68.97 步。
5. 反解「想达到整体成功率 $r$，每步至少要多准」：
   $$p_{\text{req}}=r^{1/n}$$
   20 步要做到 90% 整体成功率，每步需要 0.9948；要做到 95%，需要 0.9974。把每步错误率降低 10 倍（0.95 → 0.995），20 步的整体成功率才从 35.8% 升到 90.5%。

两个边界决定了 $p^n$ 只能当数量级模型用：

悲观一侧：每步的 $p$ 是在干净状态下测出来的，一旦某一步不可逆地改坏了状态（写库、删文件、提交、发出消息），后续步骤即使「每步都对」也是在错误状态上做对的事，真实成功率低于 $p^n$。乐观一侧：后一步有机会发现并纠正前一步（self-correction），此时整体成功率高于 $p^n$。

工程含义很硬：$p=0.95$ 时 20 步任务只有 35.8% 的整体成功率，这不是「模型不够强」的问题，而是「任务链太长」的问题。诊断长任务时先问 $n$ 是多少，再问 $p$ 是多少。

### 让错误可恢复：$r$ 比 $p$ 更值得优化

把轨迹建成二状态链：OK 与 Broken。每步从 OK 跌到 Broken 的概率 $e=1-p$；处于 Broken 时，每步被检出并修复的概率是 $r$（需要验证器 + 可逆操作，[[agents-10]]）。转移矩阵为 $\begin{pmatrix}1-e & e\\ r & 1-r\end{pmatrix}$，特征值是 $1$ 与 $1-e-r$，不动点分布是 $\pi=\frac{r}{e+r}$，从 OK 出发经过 $n$ 步仍在 OK 的概率是

$$P_n(\text{OK})=\pi+(1-\pi)(1-e-r)^n$$

口径 $e=0.05$、$n=20$：$r=0.1$ 时 68.0%，$r=0.3$ 时 85.7%，$r=0.5$ 时 90.9%，无修复时 35.8%。

读法：**有可靠验证器时成功率收敛到 $\pi=r/(e+r)$，不再随 $n$ 衰减**；没有验证器时衰减项 $(1-e-r)^n$ 才是主导，$n=20$ 就把 95% 打到 36%。所以长任务的优化目标不是「每步更准」，而是「把 $r$ 做上去」。$r$ 的瓶颈是**静默错误**：接口调用成功但语义错、删了不该删的文件、把算错的数字写进报告——它们不产生任何信号，只能靠外部状态比对（单测、数据库终态、不变量断言）变成可检出的。这就是「验证器必须比对外部状态，而不是让模型自评」的量化理由。

把检查点落到任务划分上：20 步拆成 4 段 × 5 步，段末验证器以概率 $q$ 抓到失败段并允许一次重试（假设段内独立、验证器无假阳性、只重试一次），单段成功率 $s=0.95^5=0.7738$，带验证的单段成功率是

$$s'=s+(1-s)\,q\,s$$

$q=1$ 时段成功率 0.9488、整体 81.1%；$q=0.9$ 时整体 75.2%；$q=0.7$ 时整体 64.5%；对照无检查点的 35.8%。代价是 $q=0.9$ 时期望多跑 4.1 步（约 +20% 步数）。真正的成本不在重试，而在段末要拿到一个可信的判据。

### pass^k：把「一致性」变成可测的量

τ-bench 的口径是：同一任务跑 $n$ 次、成功 $c$ 次，则

$$\text{pass}^{k}=\mathbb{E}_{\text{task}}\!\left[\binom{c}{k}\middle/\binom{n}{k}\right],\qquad
\text{pass@}k=1-\mathbb{E}_{\text{task}}\!\left[\binom{n-c}{k}\middle/\binom{n}{k}\right],\qquad
\text{pass}^{1}=\mathbb{E}[c/n]$$

pass@k 回答「给 $k$ 次机会能不能解出来」（适合发现型、可并行采样的场景），pass^k 回答「能不能稳定解出来」（适合客服、下单、发邮件这类线上不可重试的场景）。两者不可互换。

τ-bench 报告 gpt-4o 在 τ-retail 的 pass^1 约 61%、τ-airline 约 35%，τ-retail 的 pass^8 约 25%（摘要口径为 < 25%）。

这组数字本身就是诊断工具。均匀独立假设下 pass^8 应该等于 $0.61^8=1.9\%$，而观测到的 25% 比它高 13 倍。由于 $x^k$ 在 $[0,1]$ 上是凸函数，Jensen 不等式给出

$$\mathbb{E}_{\text{task}}\!\left[p_{\text{task}}^{k}\right]\ \ge\ \left(\mathbb{E}_{\text{task}}[p_{\text{task}}]\right)^{k}$$

也就是说 pass^k 高于 $(\text{pass}^1)^k$ 只可能来自**任务间成功率的方差**：一部分任务稳定可解，一部分稳定失败。据此分流：

- $\text{pass}^k\approx(\text{pass}^1)^k$：失败以步骤级随机性为主（采样、上下文顺序敏感），优化结构化状态、减少无关上下文、固定关键顺序。
- $\text{pass}^k\gg(\text{pass}^1)^k$：失败是任务分层的系统性失败，重点是找出「必失败的任务簇」，补工具、改路径或明确拒答，而不是继续调 prompt。

使用口径有个常见误用：从 $n$ 次试验估 pass^k 必须 $n\gg k$，否则 $\binom{c}{k}/\binom{n}{k}$ 在 $c<k$ 时恒为 0——用 8 次试验估 pass^8 只能得到 0 或 1。

### 上下文是有限资源：增长、压缩与位置

口径：system 提示加工具定义 4.0k token，每步新增 1.2k token（模型输出、工具参数与返回的合计），40 步。

- 上下文长度：第 10 / 20 / 30 / 40 步分别是 16k / 28k / 40k / 52k。
- 无 prefix caching 时累计 prompt token 是 $\sum_{i=0}^{39}(4000+1200i)\approx1.10\text{M}$，是最后一步上下文（52k）的 21 倍——这里 $n$ 指步数，累计 token 按 $O(n^2)$ 涨；prefix caching 把它拉回 $O(n)$（[[inference-serving-05]]）。
- 位置偏差：关键约束通常写在 system 提示开头，离生成点最远，而长上下文里中段信息最容易被忽略（[[llm-internals-13]]）。「约束在开头、证据在结尾」是最差布局。
- 压缩代价：上限 16k、40 步的模拟里发生 3 次压缩（第 11、24、37 步），累计 51.4k token 被压掉，每次约 17.1k token 换成 1.5k 摘要（单次保留比 8.8%）。设每次压缩保留某条关键约束的概率为 $s$，$c$ 次压缩后它仍在上下文里的概率是 $s^{c}$：$s=0.9,c=3$ 时 73%，$s=0.7$ 时 34%。把上限从 8k 提到 16k，压缩次数从 7 次降到 3 次（$s=0.7$ 时存活率从 8% 升到 34%）——上下文预算是一个可以直接调、且效果可算的旋钮。

三条合起来就回答了「为什么上下文更长不一定更好」：收益是信息还在，代价是注意力稀释、成本按平方增长、压缩丢约束。这三条要跟「多留历史能减少漂移」的直觉一起算。

### 用 MAST 当诊断清单

MAST 把多 agent 系统的失败归纳为 3 大类 14 种模式（分类法由 150+ 条、每条平均 1.5 万行以上的轨迹归纳，3 位标注者在 15 条轨迹上达到 $\kappa=0.88$；数据集覆盖 7 个框架、1600+ 条轨迹，正文口径 1642 条；LLM 标注器与人类一致率 $\kappa=0.77$，在两个未见过的系统上 0.79）。

| 类别（论文编号） | 失败模式 | 对应到本轮六类漂移时的排查动作 |
| --- | --- | --- |
| 系统设计（FM-1.x） | 违背任务说明、违背角色说明、步骤重复、丢失对话历史、不知道终止条件 | 多为①目标漂移与⑤提示漂移：查任务清单、角色边界、终止条件是否在上下文中且位置靠后 |
| agent 间不对齐（FM-2.x） | 对话重置、不澄清就动手、任务脱轨、信息不共享、忽略其他 agent 的输入、推理与动作不一致 | 多为②上下文污染与③记忆污染：查交接时传递的是原始证据还是被压缩的结论 |
| 任务验证（FM-3.x） | 过早终止、没有或验证不完整、验证错误 | 对应⑥误差累积与 $r$ 过低：查验证器比对的是外部状态还是模型自评 |

这 7 个框架的失败率区间是 41%–86.7%，而论文报告的一个干预案例（调整流程让 CEO agent 拥有最终决定权）带来 +9.4% 的任务成功率——**相当一部分失败是系统设计缺陷，不是模型能力缺陷**。诊断时按这张表逐项排查，比凭印象猜「是不是模型变笨了」收敛快得多。

### 诊断流程：像排障一样二分

1. **先固定变量**：记录模型 id 与版本、提示版本哈希、工具 schema 版本、采样参数、代码 commit。缺了这些，后面每一步都无法归因。
2. **拿可回放轨迹**：每一步的 prompt 分段（各段 token 数）、完整工具调用与参数、原始返回（不是模型转述后的版本）、耗时、重试次数、当时生效的模型版本。可回放的含义是「能用同一状态重跑这一步」（[[agents-10]]）。
3. **找第一次偏离**：与已知成功轨迹做对齐 diff（按工具名 + 参数序列对齐，比较参数与返回），或对状态做二分回放——把第 $m$ 步的状态还原、从那里重跑，检查「状态是否已经不对」。前提是有一个**外部**的判据（文件系统 diff、数据库终态、单测、schema 校验、不变量断言），$m$ 步最多 $\lceil\log_2 m\rceil$ 轮回放。
4. **对偏离点分类**：落到上一节的六类里，逐类看信号——工具 schema 与版本号是否变、返回分布是否变（分布漂移的检测口径可借 [[rag-07]]）、上下文增长曲线与压缩历史里是否丢了关键约束、记忆里是否躺着旧错误。
5. **最小复现**：固定第 $m-1$ 步的状态，把第 $m$ 步独立重跑 $k\ge 8$ 次，用 pass^k 看它是否稳定失败。稳定失败 → 确定性缺陷（状态、提示或工具变了，与采样无关）；时好时坏 → 采样噪声或上下文顺序敏感。
6. **版本 A/B**：同一批轨迹在旧模型 + 旧提示上重放，若不复现，就是提示/模型漂移（回归），把这条抽成回归用例。
7. **对症修复并预防**：把一致性做成常驻指标（pass^k、成功率-步数衰减曲线）与线上监控（步数分布、工具错误率、任务完成率、人工介入率、单任务 token 成本），每次模型或提示变更跑回归门禁（[[agents-09]]）。对不可逆操作保留审批与回滚路径（[[agents-11]]）。

| 已知确实出错时，首次偏离的平均步号 | 截断几何分布的条件均值 | 8.82（中位数 8） |

最后两行是诊断的含义：20 步里平均只有 1 个错误步，但「至少错一次」的概率是 64%——**长任务里某一步出错是常态而不是异常**，所以解释「最后一步为什么错」通常毫无意义，要找的是第一次偏离。

$s$ 是「某条关键约束在单次压缩后仍留在上下文里」的假设概率，属于模型化口径；它的用途是说明压缩次数 $c$ 是可以直接控制的量，而不是宣称真实的摘要保真度。下面三个函数把 trace 对齐、二分回放与 pass^k 估计做成可复用的小块。

```python
from math import comb

def pass_hat_k(c, n, k):
    """论文口径：n 次试验中成功 c 次，pass^k 的无偏估计 C(c,k)/C(n,k)"""
    return comb(c, k) / comb(n, k) if c >= k else 0.0

def pass_at_k(c, n, k):
    return 1 - comb(n - c, k) / comb(n, k)

def first_divergence(trace, golden, key=lambda s: (s["tool"], tuple(sorted(s["args"].items())))):
    """按工具名与参数对齐两条轨迹，返回第一次分歧的步号（1-based）；完全一致返回 None，
    前缀一致但长度不同时返回分叉点，表示一方多做了动作。"""
    i = 0
    while i < min(len(trace), len(golden)):
        if key(trace[i]) != key(golden[i]):
            return i + 1
        i += 1
    return None if len(trace) == len(golden) else i + 1

def bisect_first_bad(n, is_bad):
    """回放定位：is_bad(m) 表示「回放到第 m 步时状态已经不对」，要求该谓词单调。
    返回 (第一次变坏的步号, 回放次数)，回放次数不超过 ceil(log2 n)。"""
    lo, hi, calls = 1, n, 0
    while lo < hi:
        mid = (lo + hi) // 2
        calls += 1
        if is_bad(mid):
            hi = mid
        else:
            lo = mid + 1
    return lo, calls
```

在这个实现上验算：$n=8$ 次试验中成功 6 次时 `pass_hat_k(6, 8, 2) = 0.5357`、`pass_hat_k(6, 8, 4) = 0.2143`、`pass_hat_k(6, 8, 8) = 0.0`（正是 $n\gg k$ 那条口径的体现），`pass_at_k(6, 8, 8) = 1.0`；若第 8 步开始变坏，`bisect_first_bad(20, ...)` 返回 `(8, 4)`，即 4 次回放就定位到步号，而不是逐步重放 20 次。

## 常见追问

- **追问**：为什么「上下文更长」不一定更好？
  - 要点：四项代价都要算。① 位置偏差：关键约束在开头、离生成点最远，中段信息最容易被忽略（[[llm-internals-13]]）；② 成本：40 步、每步 +1.2k 的口径下，无 prefix caching 的累计 prompt token 是 1.10M，为末步上下文的 21 倍，按 $O(n^2)$ 增长（[[inference-serving-05]]）；③ 压缩：16k 上限下 40 步触发 3 次压缩，每次约 17.1k token 换成 1.5k 摘要（单次保留比 8.8%），关键约束的存活率是 $s^c$；④ 污染面：无关观察与错误结论留在上下文里会被持续引用。正确做法是按需检索 + 结构化状态，而不是单调堆积历史。
- **追问**：怎么区分「模型能力不足」和「上下文管理不当」？
  - 要点：做反事实重跑。固定第 $m-1$ 步的状态，把第 $m$ 步放进**干净上下文**（只给任务说明、当前状态摘要与该步所需的工具）重跑 $k\ge 8$ 次：成功率显著回升 → 上下文管理问题（污染、位置、压缩丢约束）；仍然稳定失败 → 能力或状态问题（该步信息不足、工具不够、状态已经被改坏）。第二种情况再继续往下分：把同一状态给更强的模型或人工，若仍失败，说明缺的是信息或工具，不是算力。
- **追问**：记忆污染已经发生，怎么清理？
  - 要点：三步。① 隔离：立刻停止向长期记忆写入，把可疑记忆置为只读；② 按 provenance 回滚：记忆条目要带来源（哪次 trace、哪一步、由哪个工具确认）与版本，删除不是删一条，而是回滚所有由它派生的条目与下游写入（[[agents-07]]）；③ 审计与规则：对已污染窗口做只读审计，找出错误进入记忆的那一步，然后改写入侧规则——只写经工具确认的事实、写入前过校验、给条目加有效期与置信来源。已经进入外部系统的副作用（发出的邮件、提交的订单）只能靠补偿操作处理，这也是可逆性设计的意义（[[agents-10]]）。
- **追问**：pass^k 和 pass@k 分别在什么时候用？
  - 要点：pass@k 衡量「$k$ 次机会里至少成功一次」，适合可并行采样、可重试发现答案的场景；pass^k 衡量「$k$ 次全部成功」，适合线上不可重试的可靠性场景。τ-bench 报告 gpt-4o 在 τ-retail 的 pass^1 约 61%、pass^8 约 25%，而独立假设下应为 1.9%——这个 13 倍的差距说明失败是任务分层的，诊断重点应转向「哪些任务必失败」。另外，从 $n$ 次试验估 pass^k 必须 $n\gg k$，否则估计量在 $c<k$ 时恒为 0。
- **追问**：没有成功轨迹可以对照，怎么找第一次偏离？
  - 要点：自己造判据，不依赖 golden trace。① 为每个阶段写不变量断言（余额不能为负、文件不变量、schema 必填字段、权限边界），每步快照状态并算哈希；② 对每个分叉点 $m$ 从该状态重跑 $k$ 次，画「从第 $m$ 步起的重跑成功率」曲线：曲线在某步之后骤降，骤降点就是污染点（这与 [[agents-09]] 里终止条件的判据共用同一套外部状态）；③ 用同一批轨迹在旧版本上重放做 A/B，区分「本来就难」和「版本回归」。
- **追问**：为什么不直接换个更强的模型？
  - 要点：三个理由。① AgentBench 的结论是长期推理、决策与指令遵循是 agent 的主要失败来源，且论文报告「用代码数据训练」对不同 agent 任务的影响是好坏参半的，不存在「换个更强的就都好了」；② 换模型同时改变了变量（提示/模型漂移），原有归因全部失效；③ 误差累积的数学说明瓶颈常在 $n$ 与 $r$ 而不在 $p$——$p$ 从 0.95 提到 0.995 只把 20 步成功率从 36% 抬到 90%，而加一个 $q=0.9$ 的段末验证器在 $p$ 不变时就能到 75%，两者可以叠加。把换模型当 A/B 实验做，而不是当修复手段。

## 公司变体

**Cognition（Devin、Windsurf）**：这题的「出现于 Cognition」标注来自仓库 README（README.zh-CN.md）的跨公司高频题清单中 Agent 与工具调用一节，Cognition 公司段落里另列了几道题。从公开信息看它偏**工程实现与线上排障**，而不是数学推导：Cognition 的产品形态就是长时间异步运行的 coding agent（README 的 Cognition 系统设计题以「等待 CI 长达四十分钟」为例），跨文件编辑、等待、重试是常态——「跑着跑着自信地做错事」正是这类产品的核心故障模式。面试流程也包含一轮实战的 agent 构建或调试，因此准备重点应放在可操作的部分：trace 里该记什么、怎么二分定位第一次偏离、怎么构造最小复现、看到哪类信号归到哪类病因、修复手段的代价。

另一个值得注意的公开立场：Cognition 曾发表文章反对多 agent 架构，强调单一上下文与上下文工程。这与本题的②⑤两类漂移直接相关——多 agent 的每一次交接都是信息压缩，压缩丢掉的约束无法在后续步骤被恢复；准备时可以把「交接时传原始证据还是传结论」作为一个具体讨论点。公开信息里没有更多轮次细节，也不必假设它考推导：这题更可能要求你现场给出一套可执行的排障流程与优先级。
