## 一句话答案

> 记忆不是「存得多」，而是一个四类内容 × 四层存储的分层系统：按内容分工作记忆、情节记忆、语义记忆、程序记忆；按存储层分上下文窗口内、向量库、关系/KV 库、文件与对象存储。四类的读写频率、容量、寿命都不同，所以单一向量库覆盖不了全部：任务态要强一致，用户偏好要唯一有效版本，失败记录要能被精确命中，工具用法要随代码发版走。设计落点是三个决策——写入判据（只存对未来决策有用、可检索、可更新的信息，并区分事实与推测）、写入时机与压缩策略（每轮/任务边界/显式记忆工具触发，滚动或层级摘要）、取回时的多路召回与冲突消解（新事实覆盖旧事实，且结果受 token 预算约束）。

## 面试官在考什么

- 能不能先给框架再谈细节。四类内容 × 四层存储是这道题的骨架；上来就说「用向量库存历史对话」是没读完题的答案。还要能把记忆与 RAG 分开：RAG 检索外部语料，记忆检索这次交互与这个用户的经历，两者常共用向量基础设施，但生命周期与隔离要求不同。
- 「存什么」有没有判据。要听到反面清单（原始全文、冗长工具返回值、未验证的模型结论不直接进长期记忆），而不是「尽量多存，反正检索会挑」。
- 是否理解记忆的失效模式：记忆污染、陈旧事实、检索漏召、跨用户泄漏。长期任务的故障大多是静默的——不报错，只是悄悄答错。
- 冲突消解与一致性：新偏好如何覆盖旧的，为什么「并存两个矛盾条目」是设计缺陷而不是数据问题。
- 工程与合规是否闭环：写入成本、读取延迟、保留期限与删除权、多租户隔离、审计。这是高阶题与普通题的分水岭。

**常见错误答案**

- 「窗口开到 128k 就不需要外部记忆了。」窗口是容量口径，不是注意力利用率口径，成本还随长度上升（见 [[llm-internals-13]]）。而且长任务的关键信息分布在几百轮交互里，装不进任何窗口。
- 「长期记忆 = 一个向量库。」向量库只擅长模糊语义召回；「用户 id 下的当前时区」「任务是否已完成」这类需要精确、唯一、强一致的读写，用向量库实现会引入不必要的错误面。

## 原理与推导

### 分类一：按内容分四类，读写模式完全不同

| 类型 | 存什么 | 载体 | 寿命 | 主要失效模式 |
| --- | --- | --- | --- | --- |
| 工作记忆 | 计划、当前步骤、中间结果、待办 | 上下文窗口内 | 单次任务/会话 | 溢出后被截断，关键约束滑进中段 |
| 情节记忆 | 历史交互、执行轨迹、成功与失败记录 | 轨迹库 + 向量库 | 周/月，可衰减 | 越积越多，检索被自己的历史淹没 |
| 语义记忆 | 用户偏好、约束、已确认事实 | KV/关系库（带唯一键） | 长期，需显式删除 | 陈旧事实不覆盖，版本并存 |
| 程序记忆 | 工具用法、调用惯例、领域技能 | 文件/仓库（随代码发版） | 跟代码同寿命 | 与线上工具 schema 脱节 |

判据是「读写频率 × 一致性要求 × 寿命」。工作记忆每轮读写、要求零丢失；语义记忆写少读多、要求唯一有效版本；情节记忆写多读少、可以慢；程序记忆几乎所有写都来自发版流程而非 agent 运行时。把它们塞进同一个表，就得用同一套一致性模型服务四种需求。

### 分类二：按存储层分四层，写入靠「晋升」而不是复制

```text
上下文窗口内   → 摘要（会话级/任务级）→ 向量库（情节+语义）→ 结构化库（KV/关系）→ 对象存储（原始产物）
   每轮可变          每 N 轮或任务边界        语义召回              精确查询            只存指针
```

- **上下文窗口内**：唯一被模型直接读到的一层，因此其他三层的价值都必须通过它兑现。窗口里通常同时活跃着系统提示、工具定义、检索回来的记忆、工作记忆、当前输入。
- **摘要层**：滚动摘要（把最近 $m$ 轮折叠成一段）与层级摘要（按任务/天/周分层，上层只存结论）。摘要是有损压缩，必须保留「结论 + 关键证据 + 来源指针」，否则回溯时无据可查。
- **向量库**：承载情节记忆与语义记忆的模糊召回，写入时可给每条打 `importance`、`valid_from`、`source`。
- **结构化库**：承载需要精确等值查询与唯一约束的部分（用户 id、任务 id、状态机、有效期），是冲突消解的执行者。
- **对象存储**：大块原始产物（日志、diff、长文档）只存指针，正文放对象存储；记忆里留一条「去哪找」的索引，取回时按需拉取，避免把冗长工具返回值直接写进记忆。

写入触发点有四个：每轮结束（工作记忆与候选语义记忆）、任务完成或失败（情节记忆总结）、显式记忆工具调用（模型主动决定记住什么）、用户纠正（最高优先级的覆盖写入）。MemGPT 的做法可以引用：它把上下文分成 main context 与 external context，让模型自己通过函数调用在两层之间搬运数据，并用中断在模型与用户之间切换控制流，实现「虚拟上下文管理」——这正是「上下文窗口内 / 窗口外」这组划分的机制化版本（<https://arxiv.org/abs/2310.08560>）。

### 存什么：写入判据与反面清单

对每条候选记忆问三个问题，全过才写：

1. **对后续决策有用吗**（换一个会话、换一天还成立吗）？
2. **可检索吗**（有没有稳定的检索键：用户 id、任务 id、实体名、时间）？
3. **可更新吗**（新信息到来时，能不能明确地覆盖它）？

能过判据的：用户偏好与约束、已确认的事实（带来源与时间戳）、任务状态与进度、失败过的尝试、工具使用经验。热路径上的写入信号是「用户纠正」——一次纠正应该同时落一条覆盖写入和一条反对旧值的理由。

明确不写的：原始全文与整段对话、冗长的工具返回值、未经验证的模型结论、低信息量的寒暄。原因是记忆污染——一旦把模型的推测当成事实写进长期记忆，它会在后续每个会话里被当作前提引用，且因为不再带有「这是推测」的标记而无法被发现（见 [[agents-12]]）。对策是记录时保留类型标记：`fact`（有外部来源）/ `inference`（模型推断）/ `user_stated`（用户口述），取回时对 `inference` 降权并要求模型复述时标注不确定。事实条目要带来源，让结论可回溯到具体的一手证据，这与 [[rag-12]] 的归因思路一致。

### 存在哪里：字段设计与两条经典路线

一条可落地的记忆记录长这样（字段本身就是要讲的内容）：

```python
from dataclasses import dataclass, field
from typing import Literal

@dataclass
class MemoryRecord:
    id: str                                  # 全局唯一
    kind: Literal["episodic", "semantic", "procedural"]
    scope: tuple[str, str | None, str | None]  # (user_id, task_id, session_id) 三级隔离
    key: str                                 # 语义记忆的唯一键，如 "pref.code_language"
    text: str                                # 供检索与注入的短文本，20-40 token
    etype: Literal["fact", "inference", "user_stated"]
    source: str                              # 一手证据指针：消息 id / 工具调用 id / URL
    created_at: float
    valid_from: float
    valid_to: float | None = None            # None 表示当前有效
    superseded_by: str | None = None         # 冲突消解留痕
    importance: int = 5                      # 1-10，写入时由 LLM 打分
    access_count: int = 0
    last_used_at: float | None = None
    embedding: list[float] = field(default_factory=list)
```

两条经典路线各自解决了一半问题：

- **Generative Agents**：记忆流存完整的自然语言观察记录，随时间把观察合成为更高层的反思（reflection），检索时用新近性、重要性、相关性三项加权打分（<https://arxiv.org/abs/2304.03442>）。它给出了「写什么 + 什么时候升华成结论 + 怎么排序」的完整闭环，是把情节记忆升格为语义记忆的机制化描述。
- **MemGPT**：虚拟上下文管理，分层搬运 + 中断控制流。它给出了「窗口装不下时怎么办」的机制答案：不是截断，而是把数据移到外部层级、需要时再换回来。

两者的共同前提都是：窗口内只放当前决策需要的部分，其余进外部层级。

### 压缩策略

- **滚动摘要**：每 $N$ 轮把最早的 $m$ 轮折叠成一段结构化摘要（目标、已完成、未决问题、约束）。$N$ 太大则窗口先溢出，太小则摘要次数与成本上升。
- **层级摘要**：任务级摘要 → 会话级摘要 → 天/周级总结，上层只保留结论与指针。检索时可逐层下钻，避免一次拉回整段历史。
- **轨迹折叠**：把长轨迹压成「结论 + 关键证据 + 失败分支」。失败分支不能省——它正是避免重复踩坑的那部分（这条直接支撑累积成功率的论证，见下节）。
- **何时压缩**：上下文占用超过阈值（例如 70%）时触发，而不是等溢出；压缩后必须重申硬约束（首尾各一次），否则约束会滑进中段弱区。

### 如何取回：多路召回 + 排序 + 冲突消解 + 预算

取回是一条流水线，四步都不能省：

1. **多路召回**：语义相似度（embedding）+ 关键词/BM25（对数字、报错码、函数名这类字面量更稳，也是 embedding 召回漂移时的兜底，见 [[rag-07]]）+ 结构化条件（`user_id` 必带，`task_id`/时间范围可选）。
2. **打分排序**：新近性 + 重要性 + 相关性加权。
3. **冲突消解**：同一 `key` 只保留当前有效版本；历史版本保留在版本表里可查，但默认不参与注入。
4. **预算截断**：按 token 预算取 top-$r$，剩余额度留给生成与工具返回值。

排序打分（Generative Agents 的形式）：

$$
\text{score}(m) = \alpha_{\text{rec}}\,\text{rec}(m) + \alpha_{\text{imp}}\,\frac{\text{imp}(m)}{10} + \alpha_{\text{rel}}\,\cos(\mathbf{q}, \mathbf{e}_m)
$$

其中新近性用指数衰减 $\text{rec}(m) = e^{-\lambda \cdot \text{age}(m)}$，$\text{age}$ 是距该条目**上次被检索**的小时数（对应记录里的 `last_used_at`；从未被取回过的条目从写入时刻起算）。原实现逐小时乘 $0.995$，即 $0.995^h = e^{-0.0050125h}$，下面统一用 $\lambda = 0.005$ 近似，两者绝对差小于 $0.001$。三项各自 min-max 归一化到 $[0,1]$ 再加权，这一步不能省：不归一化时量纲差异会让权重失去意义。

这个分数有一个必须讲清的副作用：**新近性会把长寿命的稳定偏好挤出榜单**。以 $\lambda = 0.005$ 计算，30 天前（720 小时）的记忆 $\text{rec} = 0.027$，一年前的 $\text{rec} \approx 0$——一条 30 天前的用户偏好，在等权打分下几乎与一年前的条目同分（1.527 vs 1.500，见下节表格）。所以加权分只能用于「情节记忆召回」，语义记忆必须走结构化通道按 `key` 精确命中并覆盖，否则用户偏好会随时间自动失效。这是「不能只用一个向量库解决所有问题」的最硬的理由：同一个打分函数对两类记忆的最优解是相反的。

冲突消解的实现方式是有效期区间而不是删除：写入新值时把旧版本的 `valid_to` 设为新值生效时间、`superseded_by` 指向新条目。这样「当前值查询」唯一，而「三个月前用户偏好什么」也能答对——审计与回溯都需要后者（版本化、可回放的审计手段见 [[agents-10]]）。

## 数值与代码验证

### 累积成功率：为什么长任务的瓶颈是「避免重做」

口径：每步独立、给定步内成功率 $p$、步骤之间无纠错、无重试，则 $n$ 步任务端到端成功率 $= p^n$。

```python
for p in (0.90, 0.95, 0.99):
    print(p, [f"{p**n*100:5.1f}%" for n in (5, 10, 20, 50, 100)])
```

| 单步成功率 $p$ | $n=5$ | $n=10$ | $n=20$ | $n=50$ | $n=100$ |
| --- | --- | --- | --- | --- | --- |
| 0.90 | 59.0% | 34.9% | 12.2% | 0.5% | 0.0% |
| 0.95 | 77.4% | 59.9% | **35.8%** | 7.7% | 0.6% |
| 0.99 | 95.1% | 90.4% | 81.8% | 60.5% | 36.6% |

$0.95^{20} = 0.358486$，即 **35.85%**。把单步从 0.90 提到 0.95，同长度的 20 步任务从 12.2% 提到 35.8%，只提升到 2.95 倍——真正改变量级的是「不让失败的步骤被重做」。记忆在这里的作用不是提高单步正确率，而是让第 12 步不再重新发现「方案 B 在上周已经失败过」。这也解释了长任务 agent 为什么不优化「更聪明」，而优化「不重复踩同一个坑」。

### pass^k 的口径

pass^k 用在同一任务上独立跑 $k$ 次全部成功的比例，衡量的是**可靠性**而不是单次能力。若单次成功率 $p$，则 $P(\text{pass}^k) = p^k$：$p = 0.95$ 时 $k=1$ 为 95.0%、$k=5$ 为 **77.38%**、$k=10$ 为 59.9%、$k=20$ 为 35.8%。口径必须写清楚三点：是否允许重试（允许重试就不是 $p^k$）、$k$ 次是否真的独立（记忆写入会让后续尝试受前次影响）、以及「成功」的判定来自规则还是 LLM judge。$p^k$ 失效时该指标仍有意义，但只能实测。

### 记忆的总成本：把「记忆太多」也算成钱

| 项目 | 口径 | 结果 |
| --- | --- | --- |
| 工具定义常驻 | 量级假设：系统提示起价 600 token + 每个工具 180 token | 5 个 1500、20 个 4200、60 个 11400 token |
| 记忆条目的向量 | 1536 维 float32 × 10 万条 | 约 586 MiB |
| 二进制量化后 | 1024 维 binary × 10 万条 | 约 12.2 MiB（约 1/48） |
| 一次全量 embedding | 30 token/条事实 × 10 万条 | 约 0.06 美元（单条约 0.0000006 美元） |

三条结论：第一，**工具定义与记忆争同一块预算**——60 个工具定义占掉 11400 token，比任何合理的记忆配额都大，所以「工具太多」和「记忆太多」是同一个上下文预算问题的两面（见 [[agents-04]]）。第二，向量的存储成本可以忽略，真正的账单是**每轮把记忆塞进 prompt 的输入 token 成本**（随调用次数线性放大）和换 embedding 模型时的全量重算（约百倍于单次写入）。第三，**写记忆的成本远低于读记忆**：读写比通常在一个数量级以上，所以优化重点在取回侧。

### 检索预算

口径：8k token 上下文记作 8000 单位，system + 工具定义 1200、工作记忆 800、用户当前输入 200、生成预留 800，共 3000 单位固定开销。

| 记忆预算 | 每条记忆预算（取 7 条） | 7 条占整窗 |
| --- | --- | --- |
| 5000 | 714 | 62.5% |
| 3000 | 428 | 37.5% |

按每条 714 单位算，取 5 条占整窗 44.6%，取 10 条 89.2%，取 20 条 **178.5%**——装不下。这就是「记忆太多同样会挤爆上下文」的算术形式，也是必须有硬预算而不是「尽量多召回」的原因（终止与成本上限见 [[agents-09]]）。

```python
def allocate(budget, fixed):
    """fixed 是固定开销（已含生成预留）；返回 (记忆预算, 每条预算)。"""
    mem = max(0, budget - fixed)
    return mem, mem // 7

for fixed in (3000, 5000):
    print(8000, fixed, allocate(8000, fixed))
# 8000 3000 (5000, 714)
# 8000 5000 (3000, 428)
```

### 打分排序：自己算一遍

$\lambda = 0.005$ 时衰减项（下表与代码按「写入后未被再次取回」计 `age`）：1 小时 0.9950、1 天 0.8869、7 天 0.4317、30 天 0.0273、90 天 0.0000、365 天 0.0000（四位小数下已归零）。

```python
import math
LAM = 0.005
mem = [("M1 偏好 Go（30 天前, imp=8, sim=0.70）", 720, 8, 0.70),
       ("M2 偏好 Python（1 天前, imp=8, sim=0.70）", 24, 8, 0.70),
       ("M3 寒暄 1 天前, imp=1, sim=0.35）", 24, 1, 0.35),
       ("M4 旧决定 365 天前, imp=8, sim=0.70）", 8760, 8, 0.70),
       ("M5 失败尝试 3 天前, imp=6, sim=0.85）", 72, 6, 0.85)]
for name, h, imp, sim in mem:
    rec = math.exp(-LAM * h)
    print(f"{name:<34} rec={rec:.4f}  score={rec + imp / 10 + sim:.4f}")
```

等权 $(\alpha_{\text{rec}}, \alpha_{\text{imp}}, \alpha_{\text{rel}}) = (1,1,1)$ 的输出：

| 记忆 | age | rec | score |
| --- | --- | --- | --- |
| M2 偏好 Python（1 天前, imp=8） | 24h | 0.8869 | 2.3869 |
| M5 失败尝试（3 天前, imp=6, sim=0.85） | 72h | 0.6977 | 2.1477 |
| M1 偏好 Go（30 天前, imp=8） | 720h | 0.0273 | 1.5273 |
| M4 旧决定（365 天前, imp=8） | 8760h | 0.0000 | 1.5000 |
| M3 寒暄（1 天前, imp=1） | 24h | 0.8869 | 1.3369 |

三个可复用的结论：

1. **M2 只赢 M1 0.86 分**（2.3869 vs 1.5273），而 M1 与一年前的 M4 只差 0.027。也就是说，在等权打分下「30 天前的偏好」几乎等于「一年前的偏好」，靠打分来决定用哪个版本的偏好是不可靠的——必须由 `key` + 有效期覆盖来保证唯一性。
2. **寒暄被压到最后一名的原因是重要性而不是新近性**：M3 的新近性最高（0.8869），但 `imp=1` 让它垫底。这说明重要性打分是「不存垃圾」的执行者，写入时给 1-2 分的条目就不该入库。
3. **把权重改成 $(2,1,1)$ 时 M3 会反超 M1**（2.2238 vs 1.5546）——加权方案不是中性的，调参就能让噪声挤掉稳定事实。权重必须按记忆类型分别配置，而不是全局一组。

## 常见追问

- **追问**：128k 长上下文能不能取代外部记忆？
  - 要点：不能替代，只能减少记忆的注入频率。窗口是容量口径，注意力利用率是另一个口径，关键信息放在中段会掉分（见 [[llm-internals-13]]）；成本随长度上升，每轮都塞满历史等于每轮都为全部历史付费；而且长期任务的会话边界、跨会话身份、多租户隔离是存储层的问题，窗口再大也不提供这些语义。正确用法是长窗口 + 压缩 + 外部记忆三层配合。
- **追问**：如何评测记忆效果？
  - 要点：四组指标。长期任务成功率与步数（端到端，对比无记忆基线）、重复提问/重复劳动率（同一信息被再次询问或同一步骤被重做的比例）、跨会话一致性（同一问题在不同会话的答案是否矛盾，可直接用矛盾对做回归集）、pass^k（$k$ 次独立运行全成功的比例，衡量可靠性而非单次能力）。再加一组负向指标：注入但未被使用的记忆比例（说明检索精度差）与记忆写入后被纠正的比例（说明写入判据太松）。
- **追问**：记忆被污染了怎么清理？
  - 要点：三件事。第一，隔离与回滚：每条记忆带 `source` 与 `etype`，污染可按来源批量吊销（一次工具调用或一次会话写入的全部条目）。第二，降级而非删除：把 `fact` 降为 `inference` 并加 `revoked_at`，让审计链完整。第三，加写入闸门：把「外部内容里的指令」当作不可信输入，写入前做来源检查与人工确认，防止间接注入把攻击者文本变成永久记忆——这条比事后清理重要得多，因为被污染的记忆会在每个后续会话里被当作前提（见 [[agents-12]]）。
- **追问**：记忆与 RAG 有什么区别？能直接复用 RAG 的向量库吗？
  - 要点：检索对象不同——RAG 检索外部语料（共享的、只读的、由数据管道维护），记忆检索这次交互与这个用户的经历（私有的、可写的、由 agent 自己维护）；生命周期与隔离要求也不同：语料可以全库共享，记忆必须按用户隔离且支持删除权。向量库本身还不擅长记忆的三类需求：唯一性（同一 `key` 只能有一个当前值）、强一致（任务状态机不能读到上一版）、精确等值（按 `user_id` + `task_id` 取全部相关条目）——它擅长的模糊语义召回正好对应情节记忆。工程上常见组合是：结构化库做真值与约束，向量库做索引，写入先落结构化库再异步同步索引，索引可随时重建；共用同一套 ANN 组件与 embedding 服务没问题，但集合、命名空间与权限模型必须分开，否则一次 `user_id` 过滤的疏漏就是跨租户泄漏（见 [[rag-08]]）。
- **追问**：写入放在响应前还是响应后？
  - 要点：同步写入会进用户可见的延迟；异步写入有丢失窗口（进程崩溃时最后几条记忆丢失）和顺序问题（覆盖型写入乱序会导致旧值胜出）。可落地的折中：影响下一步决策的写入同步（任务状态、用户纠正），可延迟的写入异步（情节总结、embedding 生成）并用版本号保证幂等与顺序。
- **追问**：用户要求删除数据，怎么落地？
  - 要点：删除必须是多副本的：结构化库物理删、向量库删向量、摘要与层级摘要里的内容要重写（这一层最容易漏，因为摘要里混着多个来源）、缓存与日志按保留期清理、审计日志保留「何时因何请求删除」但不保留内容。工程上依赖「来源指针」——能按 `user_id` 反查全部写入点，否则无法证明删干净。

## 公司变体

- **Anthropic**：偏工程实现与系统设计取舍。这家公司的公开技术写作长期围绕长任务 agent 的上下文管理（上下文压缩、agent 的记忆与状态如何跨会话持久化、工具设计）与 MCP 这类把外部资源接进模型的方式展开，因此这题的落点通常在「你会怎么搭」：分层存储的选型、写入与压缩的触发点、检索预算怎么切、失败记录怎么用起来、以及隐私与删除权怎么实现。原理侧会追问打分函数与冲突消解的具体口径，但一般不会停在那里，而是继续往「这套设计在长时间运行的场景下哪里会先坏」推进。回答时把三条主线（存什么/存哪里/如何取回）分开讲，并在每条上给出可验证的口径，比堆术语有效。
