## 一句话答案

> 没有魔数，只有三条预算。**上下文预算**：每个工具的名字加描述加 JSON schema 是几百 token 的固定开销，实测良好 schema 均值 224 tok，20 个工具就是 4,473 tok，而且在 $K$ 步循环里每一步都要重发一遍（20 步共 89,467 tok）。**干扰预算**：候选工具越多，语义相近的工具越容易互相抢调用。**返回值预算**：一次返回 2,000 tok 的原始 JSON，等价于又暴露了 9 个工具。
> 可落地的经验区间是**单次决策暴露给模型的工具控制在 10–20 个以内**；超过就分层：按命名空间分组、按任务检索工具（tool retrieval）、两阶段选择（先选工具族再选具体工具），或延迟加载。
> schema 设计的判据是「一个不会追问的新同事照着能不能用对」：写清做什么、什么时候用、**什么时候不该用**；参数名自解释；枚举内联进 schema；返回值结构化、可截断、带单位；副作用显式声明；一个工具做一件事，再配 1–2 个调用示例。这题的**量级**：每步工具选择正确率从 0.95 提到 0.99，20 步任务的成功率从 35.9% 升到 81.8%——工具选择上的 4 个点，在长任务里被放大成 46 个点。

## 面试官在考什么

- 能不能用判据而不是魔数回答「多少算太多」。三条预算都能落到自己系统的数字上，并且承认区间是从自己的消融实验里量出来的，不是查表查来的。
- 是否理解工具定义是**每一步都重发的固定成本**，而不是一次性开销。这是工具爆炸在 agent loop 里被放大的机制，也是 prefix caching 与动态加载这些工程手段的动机。
- schema 设计能不能给出可执行的清单。答「描述要写清楚」是正确的废话；能说出「什么时候不该用」「返回值怎么设计」「副作用怎么声明」才是分界线。
- 有没有把返回值与错误信息当成设计对象：可截断、带单位、带来源、错误可操作。工具调用的返回值同样是进入上下文的文本，它的质量决定后续步骤能不能推理。
- 会不会用评测证明改动有效：工具数消融、混淆矩阵、描述改写 A/B。这一条区分「调过 prompt」和「维护过一套工具集」。

常见错误答案：

- 直接甩魔数（「最多 20 个」「某家 API 上限是多少就是多少」），或者反过来答「现在上下文窗口很大，工具多几个没关系」——忽略每步重发、注意力稀释与返回值占用。
- 只谈语法层面的 schema 正确性（类型对、加 `required`、用 `enum`），谈不到语义层面：边界、示例、返回值、副作用、命名空间冲突。
- 把工具选错归因为「模型不够强」，不去查描述歧义、命名空间缺位、返回值缺字段这些可改的工程变量。

## 原理与推导

### 1. 三条预算，而不是一个魔数

**(a) 上下文预算。** 工具定义（名字 + 描述 + JSON schema）出现在每一次 LLM 调用里，它在单次请求内是常量，在整个会话里随步数线性累加：

$$\text{tok}_{\text{tools}}(K, n) = K\sum_{i=1}^{n} t_i \approx K\,n\,\bar{t}$$

其中 $K$ 是循环步数，$n$ 是暴露的工具数，$\bar{t}$ 是单个工具定义的平均 token 数。这一项与任务难度无关，纯粹是「带着多少把锤子走路」的费用。

**(b) 干扰预算。** $n$ 个工具在一次决策里互相竞争。真正有害的不是总数，而是**语义相邻**的邻居数：`search_docs`、`search_files`、`search_code`、`search_wiki` 放在一起，模型必须在没有额外信息的情况下猜「用户说的『文档』是哪一个」。同一个 $n$，命名空间分组前与分组后的干扰是完全不同的量级。

**(c) 返回值预算。** 工具的返回值也进上下文。一个返回 2,000 tok 原始 JSON 的 `list_transactions`，一次调用就吃掉相当于 9 个工具定义的预算；如果循环里调十几次，返回值才是主要开销，工具定义反而是零头。三条预算共同决定阈值，所以正确的口径是：**当工具定义的 token 占比、选择准确率的下降、返回值占用中的任何一条开始让你的评测指标变差时，就已经太多了。** 10–20 是缺少细粒度评测时的工程经验起点，不是物理常数。

### 2. 为什么选择准确率随候选数上升而下降

机制可以从两侧讲：工具集本身有歧义，模型侧的注意力又被稀释。

- **划分维度不重合**。「写一份上周的发版周报」要读 issue、读代码、读文档，但工具集是按功能维度切的（`search_issues` / `search_code` / `search_docs`），任务维度与工具维度不重合，模型要在多个都「部分正确」的工具间做选择。
- **描述互相包含或互相矛盾**。两个工具的 when-to-use 段落覆盖同一个场景时，模型只能靠措辞的偶然差别决策，这种差别对 prompt 改动极其敏感（描述里换一个词就可能翻转选择）。候选越多，所有工具定义又是同一个 prompt 前缀里的长列表，单个描述获得的注意力权重越低，这与长上下文里中段信息被忽略是同一类现象（[[llm-internals-13]]）。

把每个语义相邻工具带来的相对干扰记为 $\delta$（必须用自己的消融实验标定，不是公开常数），一阶模型是：

$$A(n) \approx (1-\delta)^{\,n_{\text{adj}}-1}$$

$n_{\text{adj}}$ 是**语义相邻**的工具数，不是总工具数——这正是分层方案有效的数学表达：命名空间分组不减少总数，减少的是 $n_{\text{adj}}$。

### 3. 超过阈值后的四种分层方案

| 方案 | 做法 | 50 工具口径下的定义开销 | 代价与风险 |
| --- | --- | --- | --- |
| 命名空间分组 | 按服务或资源加前缀（`asana_search` / `jira_search`） | 不减 token，只减少歧义 | 模型要能理解前缀语义；前缀式与后缀式效果因模型而异，必须自己评测 |
| 两阶段选择 | 先选工具族，再只暴露该族的具体工具 | 2,269 tok（−79.7%） | 多一次 LLM 往返；第一层选错族就直接失败 |
| 检索式 tool retrieval | 用 query 向量检索工具描述，取 top-$k$ 注入 | 1,238 tok（−88.9%） | 漏检即失败，必须留逃生通道 |
| 延迟加载 | 只给一个 `search_tools` 元工具，命中后再注入对应 schema | 首轮最低 | 需要 runtime 支持动态改工具列表；多一轮 |

两句容易被忽略的工程约束：

- **检索式路由必须配逃生通道。** 检索漏掉唯一正确的工具时，模型手里没有别的选择；要给一个 `search_tools` 元工具，并把「没有合适工具」当成合法输出——否则模型被迫在错误的候选里挑一个，比拒答更糟。工具检索与文档检索同源：描述就是语料，query 就是用户请求，评价指标同样是 recall@k 而不是 top-1 精确率（[[rag-02]]）。
- **MCP 的动态发现是同一个问题的另一个入口。** 客户端接上多个 server 后工具数以百计时，模型看到的是一张不断变长的平铺清单；命名空间前缀通常由客户端按 server 名自动加上，但「暴露哪些、何时暴露」仍是应用侧的设计决策（[[agents-04]]）。

### 4. schema 设计清单（题眼）

| # | 要求 | 反例 | 正例 |
| --- | --- | --- | --- |
| ① | 描述按**模型的视角**写：做什么、什么时候用、什么时候**不该**用 | 「搜索文档。」 | 「需要内部知识库事实时使用；实时数据或代码仓库内容改用 query_metrics / search_code。」 |
| ② | 参数名自解释，不用缩写 | `uid`、`dt` | `user_id`、`start_date` |
| ③ | 枚举优于自由文本，合法取值写进 schema 而不是描述里 | `type: string`，描述里写「取值是 p0/p1/p2」 | `type: string, enum: [p0, p1, p2]` |
| ④ | 必填与可选明确，默认值写清楚 | 全部字段可选 | `required: [query]`，且 `top_k` 描述里写「默认 5」 |
| ⑤ | 参数粒度：宁可多个明确字段，不要一个万能 JSON 字符串 | `payload: string` | 拆成 `project_key`、`title`、`labels`、`priority` |
| ⑥ | 返回值同样设计：结构化、可截断、带单位与来源 | 返回整表原始 JSON | 分页 + 金额带币种 + 时间带时区 + `doc_id` 可回溯 |
| ⑦ | 副作用显式声明：是否写数据、是否幂等 | 只写「创建 issue」 | 「会写数据；非幂等，重试前先用 search_issues 去重」（[[agents-10]]） |
| ⑧ | 一个工具做一件事，避免 god tool | `do_task(action, payload)` | `create_issue`、`search_issues` 各自独立 |
| ⑨ | 给 1–2 个调用示例，往往比加长描述更有效 | 用三百字解释参数格式 | 描述里放一条真实调用示例 |

前四条让模型的输出能被机器解析，⑥⑦ 让模型的下一步有信息可依，⑧⑨ 让它选得准。九条里最容易漏的是 ①（不该用的场景）与 ⑥（返回值设计），而这两条恰恰是长任务里错误累积的主要来源。一个正反例对照，注意 `do_task` 的 52 tok 并不是优点——它把选择成本全部转嫁给了模型：

```json
{
  "name": "do_task",
  "description": "执行任意后端操作。",
  "parameters": { "type": "object", "required": ["action", "payload"], "properties": {
    "action": { "type": "string" },
    "payload": { "type": "string", "description": "JSON 字符串。" } } }
}
```

```json
{
  "name": "create_issue",
  "description": "在工程看板创建一个 issue。会写数据：创建成功后返回 issue_key。非幂等——重复调用会创建多个 issue；重试前先用 search_issues 按标题去重。当任务只需要记录待办而不需要跟踪时不要使用，改用 append_note。",
  "parameters": { "type": "object", "required": ["project_key", "title"], "properties": {
    "project_key": { "type": "string", "enum": ["ENG", "OPS", "DATA"] },
    "title": { "type": "string", "description": "一句话标题，不要包含 issue key。" },
    "labels": { "type": "array", "items": { "type": "string" }, "maxItems": 5 },
    "priority": { "type": "string", "enum": ["p0", "p1", "p2"] } } }
}
```

### 5. 返回值与错误信息也是 schema 的一部分

- **详略由模型选。** 隐藏底层标识符（`uuid`、`256px_image_url`、`mime_type`），保留能直接驱动下一步的字段（`name`、`file_type`）。源文的做法是暴露一个 `response_format` 枚举，让模型在 `detailed`（206 tok）与 `concise`（72 tok）之间选，后者只有约 1/3 的 token：需要下游调用时取 detailed 拿 id，只需要读内容时取 concise。
- **必须有截断与分页。** 源文提到 Claude Code 默认把工具返回值限制在 25,000 tok。截断时要给出明确指令（「结果已截断，请用更精确的过滤条件重查，不要用同一个 query 重试」），否则模型只会重复调用同一个工具。
- **错误信息要可操作。** 「错误码 4001」模型无法自愈；「`start_date` 必须是 ISO 8601（如 2026-01-31），你传的是 01/31/2026，请重新调用」模型下一步就能改对——错误响应本身就是一次 prompt。
- **把任意 UUID 换成语义化标识**（人名、标题、0 起始的序号）能显著降低检索类任务里的幻觉，源文把这条列为提高 precision 的手段之一；返回值里同时给自然语言标识与下游调用需要的技术 id，就是一个 `response_format` 开关的事。

### 6. 失败模式对照表

| 症状 | 根因 | 修法 |
| --- | --- | --- |
| 选错工具 / 漏选工具 | 候选过多、命名空间缺位、描述互相覆盖 | 分层、按任务检索、加 when-not-to-use、检查混淆矩阵 |
| 参数填错（尤其 id、日期、枚举） | 描述含糊、格式不在 schema 里、参数名是缩写 | 枚举内联、格式写进描述并给示例、改自解释的参数名 |
| 同一个工具被反复调用 | 返回值被截断却没有指示、缺去重提示 | 截断说明 + 分页游标 + 结果里带「已返回前 N 条」 |
| 后续步骤「失忆」 | 单次返回几万 token 把上下文吃光（[[agents-02]]） | 分页、过滤、`response_format`、把长结果落盘只回摘要 |
| `search_docs` 与 `search_files` 混用 | 命名太像、职责重叠 | 合并成一个工具，或按资源加前缀划清边界 |
| 出错后无法恢复 | 错误信息只有错误码或 traceback | 错误里给出期望格式、合法取值与下一步建议 |
| 长任务后半段开始「自信地做错」 | 工具描述与实际行为不一致，模型建立了错误的世界模型（[[agents-12]]） | 让描述成为实现的一部分：改行为必须同时改描述，并跑回归评测 |

### 7. 评测：把工具集当产品维护

三个指标分开测，混在一起就无法定位：**工具选择准确率**（是否调了正确的工具，允许多条正确路径）、**参数正确率**（调对了工具，参数是否合法且语义正确，这是枚举与示例的直接收益）、**端到端成功率**（任务是否完成，它把工具错误、推理错误、上下文溢出混在一起，只能当总账）。

三个必须做的实验：

- **工具数消融**：同一批任务在 5 / 10 / 20 / 50 个工具下各跑一遍。这条曲线是自己系统阈值的来源，比任何公开数字都有说服力。
- **混淆矩阵**：统计「期望工具 × 实际工具」，矩阵里最热的非对角元就是下一对要合并或改名的工具。
- **描述改写 A/B**：把「加 when-not-to-use」「加示例」「加返回值说明」当独立变量，不要一次改五处。

源文的方法论可以直接借用：任务要来自真实工作流（真实项目、文档、消息），而不是玩具沙盒；一个任务可能包含几十次工具调用；每条任务配可验证的结果，verifier 不要严到因为格式或标点差异就判错；除准确率外同时记录单次工具耗时、工具调用次数、token 消耗与工具错误数——重复调用多说明分页参数没调好，非法参数多说明描述或示例不够。held-out 测试集是防止把描述「背」到评测集上的必要手段。

| 0.90 | 0.9000 | 0.5905 | 0.3487 | 0.1216 |
| 0.83 | 0.8300 | 0.3939 | 0.1552 | 0.0241 |

两个好记的换算：$0.95^{20}=0.3585$，$0.99^{20}=0.8179$，差 45.9 个百分点；$p=0.95$ 等价于「平均每 20 步出现一次失败」（$1/(1-p)$）。**工具选择准确率不是一个可以「差不多就行」的指标，它是指数项的底数。**

表 4：干扰模型 $A(n)=(1-\delta)^{n-1}$ 的敏感性（$n$ 为语义相邻工具数，$\delta$ 需自行标定）

| $\delta$（每增加一个语义相邻工具的相对干扰） | $n=5$ | $n=10$ | $n=20$ | $n=50$ |
| --- | --- | --- | --- | --- |
| 0.01 | 0.9606 | 0.9135 | 0.8262 | 0.6111 |
| 0.02 | 0.9224 | 0.8337 | 0.6812 | 0.3716 |
| 0.05 | 0.8145 | 0.6302 | 0.3774 | 0.0810 |

把表 4 的选择准确率当作每步正确率代进表 3 的 20 步：

| 暴露的语义相邻工具数 | 每步选择准确率（$\delta=0.01$） | 20 步端到端 | 每步选择准确率（$\delta=0.02$） | 20 步端到端 |
| --- | --- | --- | --- | --- |
| 5 | 0.9606 | 0.4475 | 0.9224 | 0.1986 |
| 10 | 0.9135 | 0.1638 | 0.8337 | 0.0263 |
| 20 | 0.8262 | 0.0219 | 0.6812 | 0.0005 |

$\delta=0.01$ 时从 5 个工具扩到 20 个，单步只掉 13 个点，20 步却从 44.8% 掉到 2.2%。分层收益不是「好一点点」就是这个原因；反之，**把这些工具拆进 4 个命名空间、每次只暴露同族 5 个，就把 $n_{\text{adj}}$ 从 20 拉回 5。**

表 5：50 个工具时的分层方案对比（token/请求，均价 $\bar{t}=223.7$）

| 方案 | 计算 | token | 相对全量 |
| --- | --- | --- | --- |
| 全量平铺 | $50\bar{t}$ | 11,183 | — |
| 两阶段（8 个族摘要 + 族内 8 个工具） | $8\times60+8\bar{t}$ | 2,269 | −79.7% |
| 检索式 top-5（+ 检索器开销 120） | $5\bar{t}+120$ | 1,238 | −88.9% |

表 6：`pass^k` 与 `pass@k` 的差别（$k=3$，同一任务独立跑 3 次）

| 任务级单次成功率 $p$ | `pass^3` $=p^3$ | `pass@3` $=1-(1-p)^3$ |
| --- | --- | --- |
| 0.8179（20 步 × 0.99） | 0.5471 | 0.9940 |
| 0.3585（20 步 × 0.95） | 0.0461 | 0.7360 |
| 0.1638（10 工具、$\delta=0.01$ 的 20 步） | 0.0044 | 0.4153 |

`pass^k` 要求 $k$ 次尝试**全部**成功，衡量可靠性；`pass@k` 只要求至少一次成功，衡量能力上限。同一个系统可以 `pass@3` 高达 0.74 而 `pass^3` 只有 0.046——**agent 工具集的问题经常不是「做不到」，而是「不稳定」，所以工具规模这类改动应该看 `pass^k` 而不是 `pass@k`。**

```python
# 复算表 1 的「良好」样本与表 2-表 6：token 成本、累积成功率、干扰模型、分层收益、pass^k
import json, tiktoken
enc = tiktoken.get_encoding("cl100k_base")
tok = lambda o: len(enc.encode(json.dumps(o, ensure_ascii=False, separators=(",", ":"))))
good = {"name": "search_docs",
        "description": "在内部文档库中做语义检索，返回最相关的文档片段。当问题需要来自内部知识库的事实（政策、设计文档、会议纪要）时使用；当问题涉及实时数据、结构化聚合或代码仓库内容时不要使用，改用 query_metrics / search_code。返回按相关度排序的片段，每个片段带 doc_id 与 char_range。",
        "parameters": {"type": "object", "properties": {
            "query": {"type": "string", "description": "自然语言检索词，使用文档中可能出现的术语，不要用布尔语法。"},
            "scope": {"type": "string", "enum": ["all", "engineering", "product", "people_ops"], "description": "检索范围，默认 all。"},
            "top_k": {"type": "integer", "minimum": 1, "maximum": 20, "description": "返回片段数，默认 5；先用 5，不够再放大。"},
            "response_format": {"type": "string", "enum": ["concise", "detailed"], "description": "concise 只返回片段正文；detailed 额外返回 doc_id 等下游调用需要的字段。"}}, "required": ["query"]}}
print("表 1 的「良好」schema：", tok(good), "tok")     # 291 tok
T_BAR, R_PRE = (291 + 181 + 199) / 3, 989e12 * 0.4 * 8 / (2 * 70e9)  # 均值 223.7 tok（表 1 的三个「良好」样本）；prefill 22,606 tok/s
for n in (5, 10, 20, 50):                           # 表 2
    print(f"n={n:2d} 单次 {n*T_BAR:6.0f} tok  20 步累计 {n*T_BAR*20:7.0f} tok  TTFT +{n*T_BAR/R_PRE*1000:.0f} ms")
for p in (0.99, 0.95, 0.90, 0.83):                  # 表 3
    print(f"p={p:.2f} " + " ".join(f"K={K}:{p**K:.4f}" for K in (1, 5, 10, 20)))
for d in (0.01, 0.02):                              # 表 4 与 20 步折算
    for n in (5, 10, 20):
        a = (1 - d) ** (n - 1)
        print(f"delta={d} n={n:2d}: 每步 {a:.4f} -> 20 步 {a**20:.4f}")
full, two_stage, retrieval = 50 * T_BAR, 8 * 60 + 8 * T_BAR, 5 * T_BAR + 120   # 表 5
print("两阶段省 %.1f%%，检索式省 %.1f%%" % (100*(1-two_stage/full), 100*(1-retrieval/full)))
p20 = 0.95 ** 20                                    # 表 6
print("pass^3=%.4f  pass@3=%.4f" % (p20**3, 1 - (1 - p20)**3))
```

## 常见追问

- **追问**：工具太多时，是删工具还是加一层路由？
  - 要点：先做减法，再做路由。判据是「这个工具在混淆矩阵里有没有被正确选中过」——从没被选中、或被误选远多于正确选中的工具直接删；剩下的如果仍超过 10–20 个，才加路由。路由的代价是固定的：两阶段多一次 LLM 往返，检索式多一次向量检索并承担漏检风险。删工具的收益是永久的（省 token、减少干扰），路由的收益是局部的。另外，很多「工具」其实该合并：`list_users` + `list_events` + `create_event` 合成 `schedule_event`，既减少数量又省掉中间输出占用的上下文。
- **追问**：怎么让模型知道工具的边界——「不该用」的场景怎么表达？
  - 要点：写进描述，而不是指望模型自己推断。三种写法按效果排序：① 直接点名替代品（「涉及实时数据时改用 query_metrics」）；② 说明前置条件（「只在已拿到 customer_id 时使用；手上的标识符是邮箱就先调 resolve_customer」）；③ 说明拒答条件（「查不到时返回空列表，不要编造 doc_id」）。第 ① 种最有效，因为它在做选择的那一刻就给了模型另一条路。描述里的边界必须与实现一致，否则会制造错误的世界模型（[[agents-12]]）。
- **追问**：多 agent 分工能不能缓解工具爆炸？
  - 要点：能缓解，但换来的是一致性问题。把 50 个工具按域拆给 5 个子 agent，每个只看到 10 个，$n_{\text{adj}}$ 确实降下来了；代价是子 agent 之间不共享上下文，一个 agent 拿到的事实要经过一次有损的摘要才能传给下一个，长任务上容易各自为政。折中做法是「同一上下文的主循环 + 动态工具集」：不拆 agent，只拆工具的暴露范围，用检索或两阶段选择控制每次决策的候选数（[[agents-06]]）。
- **追问**：工具描述长度与上下文成本的取舍怎么算？
  - 要点：把描述当一次投资来算账。一个良好 schema 比一句话描述贵约 250 tok（表 1：291 对 44），20 个工具就是 5k tok/请求；它买来的是参数正确率与选择准确率的提升。换算方式是把准确率提升代进表 3：如果加 when-not-to-use 让每步正确率从 0.95 到 0.96，20 步任务的成功率从 35.9% 到 44.2%，这 8 个点值不值 5k tok 取决于单次失败的代价。反过来，冗长描述多出的 174 tok 只讲实现沿革，对选择没有帮助，是最该砍的部分（[[inference-serving-09]]）。
- **追问**：模型是「漏选工具」还是「选错工具」，两者的修法一样吗？
  - 要点：不一样。漏选（该调工具却直接回答）通常是描述里的触发条件写得太窄，或工具名与用户实际会用的词不匹配，修法是补 when-to-use；选错（调了另一个相近工具）是候选之间的边界问题，修法是合并、改名、加命名空间前缀或减少同族候选。混淆矩阵对角线整体偏低 → 漏选；非对角元集中 → 选错。症状不同，别用同一个补丁。

## 公司变体

- **Anthropic**：偏工程实现。公开的工程文章《Writing Tools for Agents》把工具写作讲成一套可迭代流程——先搭原型，再建基于真实工作流的评测与 held-out 测试集，然后用 agent 读轨迹反向改工具，最后落到命名空间、返回值 token 效率、描述 prompt-engineering 这些具体手段。按这条线索，追问大概率落在「你的工具有没有评测」「怎么衡量返回值 token」「工具集怎么随业务增长而不失控」这类可量化、可复现的问题上，而不是让候选人推公式。准备时把钱花在：拿得出一次工具数消融实验，讲得清一次描述改写的 A/B 结果。
- **Cognition**：偏工程实现，约束来自长时程 agent 产品（Devin 这类编码 agent）。这类系统的工具面相对收敛——编辑文件、跑命令、看浏览器、读写记忆——真正的难题不是工具数量本身，而是长任务里的上下文工程：工具描述与真实行为一旦不一致，错误会随步数累积成漂移；返回值过长会挤掉早期关键信息。因此追问更可能围绕「工具描述如何与实现保持同步」「返回值怎么裁剪」「多个子任务之间工具上下文怎么共享」展开（[[agents-12]]、[[agents-06]]）。
