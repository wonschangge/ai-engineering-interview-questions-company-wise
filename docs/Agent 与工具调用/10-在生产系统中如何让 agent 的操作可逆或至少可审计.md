## 一句话答案

> 默认把每个写操作设计成可逆的：dry-run 预演 + 确认、事务、软删除、版本快照、补偿事务、幂等键、write-ahead intent log。真正不可逆的操作（对外发送、下单、物理动作、生产变更）不靠"小心"来控制，而是推到审批、限额与沙箱后面，并把不可逆步骤尽量后移到流程末尾。所有操作都落一条以 correlation id 串起「用户请求 → 会话 → 步骤 → 工具调用 → 数据变更」、追加写且可校验篡改的轨迹。可逆性降低事故的期望损失，审计决定事故能否被界定、复现与追责；两者都是工具上线评审项，不是事后补的。

## 面试官在考什么

- **先分级，再让分级落到工具层**：把操作按风险分成「纯读 / 可自动执行且可回滚 / 需事前审批 / 禁止自动」并说清每一档的默认动作，而且风险等级必须是**工具声明的一部分**（[[agents-05]]）——模型只看得见 schema，靠调用侧的 if-else 兜底迟早会漏；同一个工具在不同参数下风险也不同（改 1 条记录 vs 改 10 万条）。只答"加个确认按钮"和只答"全部记日志"的候选人，都停在单点上。
- **可逆性原语的完成度**：PREVIEW/COMMIT 两阶段、事务、软删除、版本快照、saga 补偿、幂等键、intent log 能说出几种，以及各自的失效条件（TOCTOU、补偿自身失败、幂等键过期）。
- **审计是链路而不是日志**：有没有相关 id 把一次用户请求和最终那条数据变更串起来、能不能回答「这条记录是谁在什么授权下基于哪个版本的输入改的」、能不能重放、能不能证明没人改过。
- **权限与合规**：agent 以谁的身份执行、日志里的 PII 怎么处理、保留多久、审计日志本身的访问是否也被审计。
- **算得清取舍**：dry-run 多花的一次调用值不值、审计记录一年占多少存储、回滚覆盖率用什么指标度量。这题是「高阶」，分水岭就在这里。

常见错误答案：

- "不可逆的操作让模型再检查一遍自己的计划"——模型自评是概率性的、和它的错误同源，不构成控制；换成独立验证器或人工审批才有意义。
- "所有步骤都打日志就等于可审计"——没有相关 id 串联、不追加写、不记模型与 prompt 版本、不能重放的日志，出事时既界定不了影响范围也复现不了，等于一堆文本。

## 原理与推导

### 1. 分级先于机制：四档风险

| 档位 | 判定 | 默认动作 | 典型例子 |
| --- | --- | --- | --- |
| L0 纯读 | 无副作用 | 自动执行，只记轨迹 | 检索、查询、读文件、拉指标 |
| L1 可逆写 | 有逆操作，且逆操作成本低、窗口足够长 | 自动执行 + 事后审计；高风险参数走 dry-run | 建草稿、改标签、写内存/工作区、可回滚的配置变更 |
| L2 不可逆但有界 | 不可撤销，但影响范围可以先验限死 | 事前审批 + 限额 + 灰度 | 发对外邮件、提交工单、写生产库、调用付费/下单接口 |
| L3 高危 | 不可逆且影响面大、合规敏感 | 禁止自动执行（人或独立流水线执行）；agent 只产出方案 | 资金划转、删库/删数据、权限授予、生产流量切换、物理动作 |

两条落地要求：

1. 等级写在工具定义里（是否幂等、能否 dry-run、逆操作是什么、单次影响上限、需要几级授权）。工具描述的读者是模型，风险声明同时也在教模型"什么时候不该用"（[[agents-05]]）。
2. 分级可配置、可按租户与场景覆盖，且判据是「工具 + 参数」而不是工具：同一个 `update_records` 改 1 条记录是 L1、改 10 万条自动升到 L2；风险判据可写成 $R = f(\text{工具},\ \text{影响对象数},\ \text{金额},\ \text{是否跨组织边界})$，用参数化阈值（影响超过 100 条记录自动升档）代替人工判断。

### 2. 可逆性的七种原语

**① 两阶段执行（PREVIEW → COMMIT）**。预演必须产出**结构化 diff**（改哪些对象、字段、前后值、影响条数），而不是一句"我将要更新数据"。两个容易做错的点：预演要只读，且走**与真实执行相同的校验代码路径**（否则预演通过、真实执行失败）；COMMIT 时必须带上预演时的对象版本（`etag` / `version` / `updated_at`），版本不一致就作废重来——否则用户在审查 diff 期间目标已被别处修改，确认的是过期状态，这是典型的 TOCTOU。预演的收益是可以用盈亏平衡算的（见「数值与代码验证」）。

**② 事务与两阶段提交**。同一数据库内的多表写放进一个事务，是最便宜的可逆性；跨系统没有免费的分布式事务，XA 的可用性代价通常不可接受，工程上用「本地事务 + saga」替代。

**③ 软删除与回收站**。删除改成写 `deleted_at` / `status=deleted`，读路径默认过滤，物理删除延迟到保留窗口之后（30 天是常见量级）。要点：读路径不能有例外（导出、统计、后台任务最容易漏），以及回收站本身要有明确的到期清理任务，否则软删除会变成永久保留。

**④ 版本化与快照**。每次变更产生不可变的新版本，`rollback` 就是指向旧版本。配置文件、策略、prompt、数据集这类对象特别适合；配合分支可以让 agent 在「草稿分支」上改、由人或流水线合并——把不可逆性留到最后一次合并动作上。

**⑤ 补偿事务（saga）**。为每个写操作定义逆操作，失败时按逆序补偿。补偿的工程细节是考点：逆操作自身要**幂等**（补偿可能重试多次）、要能处理"原操作部分成功"、不可逆步骤尽量放在链尾、补偿失败要进人工兜底队列。补偿链不是免费的，整体回滚成功率随链长指数衰减（见「数值与代码验证」），所以链越短越好。

**⑥ 幂等键 + 去重表**。写操作带 `idempotency_key`，服务端在事务内先查去重表：已存在就返回首次结果，不重复执行副作用。分布式里没有免费 exactly-once，能做到的是 **at-least-once + 幂等消费**。键的作用域必须包含业务对象（`租户:工具:业务对象:请求 id`），只按请求 id 去重会漏掉业务层的重复（用户点两次、两个任务收敛到同一个动作）；过期时间必须覆盖最长重试与重放窗口（消息队列死信重投、人工重放），否则"过期后重放"就是重复副作用（[[agents-02]]）。

**⑦ write-ahead intent log**。执行前先把意图（工具、参数、目标、幂等键、发起者）持久化并置为 `in_flight`，执行成功后改成 `done` 并回填下游变更 id。崩溃恢复时，扫 `in_flight` 的记录去查下游实际状态，决定重试、补偿还是转人工。数据库的 WAL 是同一思路：先写意图，再改状态，让"不知道做没做"这个状态可判定。

通用补充：

- **用可逆动作模拟不可逆动作、用限额换取部分可逆**：对外发送先建草稿、下单先建预留单/报价单、发布先做影子运行、把「立即执行」改成「定时 + 取消窗口」（比如 10 分钟内可撤回），这类改写往往比事后补偿便宜一个数量级；做不到可逆时，就用单次影响上限 $N$ 条记录、单日累计金额上限、并发写同一对象串行化，把最坏情况压到"人工收拾得完"的规模。

### 3. 审计：记什么、怎么串、怎么防篡改

**① 记什么。** 每条工具调用一条记录，覆盖四组字段：身份与版本（trace/span id、时间戳、租户、发起者、代理对象、模型 id 与版本、prompt/工具 schema 版本）、输入（工具名、参数、模型决策摘要、被引用的上下文摘要）、结果（返回摘要、错误码、是否重试、耗时）、以及成本与影响（token/费用、受影响的业务对象 id 列表、`change_id`）。**不记全量上下文**：上下文里有 PII、有越权内容风险、体积还大一个数量级（「数值与代码验证」表 1）；需要时记可寻址的引用（对象 id + 版本 + 摘要 hash），让取证按需回源。

**② 怎么串。** id 层级要一路继承下去，并且在被改系统里回填：

```text
request_id   网关生成，贯穿整个用户请求（req-7f3a）
└─ session_id   会话，跨多次 run
   └─ run_id   一次任务执行 = 一次 agent 循环的生命周期
      └─ step_id    第 n 次模型调用
         └─ tool_call_id   工具调用，参数/返回/耗时/成本落在这一层
            └─ change_id  下游系统生成的数据变更 id，执行后回填
```

最容易被忽略的是最后一条：`change_id` 必须由被改系统生成并回填。没有它，审计链在数据库边界断掉，事后只能凭时间戳猜"这次变更是不是那个 agent 干的"，而时间戳在并发下没有分辨力。工具网关应当拒绝不回填 `change_id` 的写操作。

**③ 追加写与防篡改。** 审计存储只允许 append：应用侧账号没有 `UPDATE`/`DELETE` 权限，删除走独立的保留期任务。防篡改用哈希链：

$$h_i = H(h_{i-1} \parallel \text{body}_i), \qquad h_0 = 0^{256}$$

篡改会向后传播：只改 `body_i` 而不重算 `h_i`，第 $i$ 条校验失败；连 `h_i` 一起重算，第 $i+1$ 条失败，因为它的哈希是用旧 $h_i$ 算出来的，攻击者必须一路重算到链尾（成本 $O(n)$，且需要持续的写入权限）。要挡住"有存储写权限的人重算全链"，再叠一层**外部锚定**：每小时把链头写到独立的 WORM 存储、另一个账号或第三方时间戳服务，篡改窗口就被压缩到一个锚定周期，而锚定本身的存储开销可以忽略（「数值与代码验证」表 2：768 B/天）。

**④ 保留期、脱敏与访问控制。** 保留期由合规与可追责需求决定，不由存储成本决定（存储很便宜）。三个要点：自由文本参数与返回摘要要脱敏，但**主体标识要保留可追责性**——用假名 id + 单独强管控的映射表，而不是把用户信息抹掉；审计日志本身是新的泄露面，读它需要有权限、并且"谁查看了哪段时间的审计日志"也要被记录（meta-audit）；到期删除要能**被证明**，用「按时间窗分段 + 每段根哈希 + 删除墓碑」说明删了哪些窗口，而不是只留一句"已过期清理"。

**⑤ 支持回放。** 轨迹要能重放才能定位问题（[[agents-12]]），前提是记录全了版本维度：模型 id 与版本、prompt 与工具 schema 版本、温度/采样设置、工具返回（重放默认用**录制结果**而不是真实调用，重放绝不能再次产生副作用）、以及随机性来源。能做到"同输入同版本重放得到同一轨迹"时，调试才从考古变成实验。

**⑥ 人工审批链。** 审批记录是审计的一半：谁、在什么时刻、批准了**哪个版本的参数**、依据什么信息、有没有修改后再批准。审批后参数若被改动必须重新审批，否则审批就成了形式（[[agents-11]]）。

**⑦ 三类措施的框架（Visibility into AI Agents）。** 该文把提升 agent 可见性的措施分成三类，并指出每类都有侵入性与信息量的取舍，应随风险决定收集程度：

| 措施 | 内容 | 侵入性 | 在什么部署形态下最有效 |
| --- | --- | --- | --- |
| agent 标识 | 按需在 agent 的输出上带身份（API 请求加 header、文本/图片加水印、交易带标识），让下游能区分人与 agent 并据此施加约束；可附「agent card」说明底层系统、本次实例的目标与权限、相关责任主体 | 低（一个头部/凭据），但需防冒充 | 集中式与去中心化都需要；去中心化下是唯一能在第三方侧生效的措施 |
| 实时监控 | 在执行过程中分析行为并拦截，而非事后看日志；速度与规模决定了它必须自动化 | 中到高（要看到行为流，可能需要看内容） | deployer 自己运行 agent 时最有效（输入输出天然可见） |
| 活动日志 | 记录与外部服务、其他 agent 的交互，用于事后归因与取证；细节程度可分层 | 中（存储与隐私成本） | 所有形态；去中心化下由工具/服务提供方在各自边界上记 |

该文对部署形态的区分直接对应工程选择：**集中式**（deployer 自己跑 agent，能看到输入输出）三类措施都能落地；**去中心化**（用户自建脚手架、调第三方模型与工具）时 deployer 看不到全貌，监督点转移到算力提供方与工具/服务提供方。对系统的直接含义是：不要把审计与拦截押在「模型侧」或「agent 自觉」上，而要押在**工具/服务网关**这个所有副作用都必经的边界上——这也解释了为什么上面 ① 的字段清单要以工具调用为记录单位。

### 4. 权限、身份与合规

- **工具级最小权限**：每个工具一个 scope，凭据按工具下发并支持吊销；不要给 agent 一把覆盖全部系统的超级 key。
- **以用户身份代理，而不是服务账号超级权限**：agent 的每次调用携带发起者身份并向下游透传（on-behalf-of），下游按该身份做授权判定。否则 agent 就是一个提权通道：用户没权限的操作，只要能让 agent 去做就成功了（[[rag-08]]）。
- **敏感操作双人复核**：L3 档位要求两个不同主体各自批准，且两个批准都要进审计链。
- **不可信输入不能提升权限**：工具返回、检索到的文档、网页内容都是数据，不能改变风险等级或授权判定；提示注入的后果在这里体现为"诱导 agent 调用越权工具"，防线是工具网关侧的确定性校验，检测手段是审计里的越权尝试告警。
- **留存还要满足辖区与行业规则**：数据出境限制、行业留档年限（金融、医疗常见更长）与个人的删除请求都会改变保留策略，所以保留期按租户所在辖区与行业配置，而不是一套全局值；日志分区域存放以回避跨境传输，删除请求要能穿透备份与冷存，并把「哪个窗口被删」写进删除墓碑。
- **治理框架**：NIST AI RMF 用 GOVERN / MAP / MEASURE / MANAGE 四类职能把「风险识别—度量—管理—治理」组织成一个循环，并且是自愿采用的性质（AI RMF 1.0 于 2023-01-26 发布；面向生成式 AI 的 profile NIST-AI-600-1 于 2024-07-26 发布）。把 agent 放进这套循环时，**可逆与审计是可治理的前置条件**：不能回滚就无法"管理"风险，不能复现与界定范围就无法"度量"风险，四项职能都会退化成纸面工作。

### 5. 工具上线前的六问

- **最坏情况是什么**：明确受影响的对象、数量上限、金额上限，以及是否可撤销。答"应该不会出事"就不许上线。
- **能否 dry-run**：要么提供只读预演并给出结构化 diff，要么说明为什么不能（以及用什么替代控制）。
- **失败后如何补偿**：有幂等键 + 明确的逆操作，或有明确的人工兜底队列与负责人。
- **谁看得到这条记录**：列出具体角色与字段级可见范围，而不是"有权限的人"。
- **保留多久**：给出保留期与到期删除的可证明机制。
- **能不能被回放**：轨迹是否含模型/prompt/工具版本，重放是否不产生副作用。

| 相对一次 1 s 的工具调用 | 2.1 μs ÷ 1 s | $2.1\times10^{-6}$ |
| 全链校验 10^4 / 10^6 / 10^7 条 | $n \times 2.1\ \mu s$ | 0.02 s / 2.1 s / 21.3 s |
| 每小时外部锚定链头（32 B） | 24 × 32 B | 768 B/天，0.28 MB/年 |

本机 Python 实测（含解释器开销，20000 条 × 2128 B）：0.031 s，即 1.56 μs/条，比 1 GB/s 的假设更快（hashlib 经 OpenSSL 已可用上 SHA 扩展，有 SHA-NI 的机器还会更快），说明 1 GB/s 是保守口径。防篡改的代价相对 LLM 调用可以忽略；真正的工作量在**验证**——百万级重算约 2 s，十亿级才需要分段的 Merkle 结构，普通规模用不着。

**表 3：saga 补偿链的整体回滚成功率（口径：单步补偿成功率 $q$，链长 $n$，各步独立，整体成功率 $q^n$）**

| 单步补偿成功率 $q$ | 链长 3 | 链长 5 | 链长 10 | 链长 20 |
| --- | --- | --- | --- | --- |
| 0.99 | 97.03% | 95.10% | 90.44% | 81.79% |
| 0.999 | 99.70% | 99.50% | 99.00% | 98.02% |

这张表解释了三条实践：链要短；补偿自身必须幂等可重试（把 0.99 拉回 0.999 靠的是重试而不是祈祷）；以及不可逆步骤要放在链尾——放在中间，整条链的回滚成功率就成为它的上界。

**表 4：可回滚覆盖率（口径：12 个写工具、10,000 次写调用/天）**

| 口径 | 可自动回滚 | 含人工审批回滚（累计，含前项） | 不可逆仅审计 |
| --- | --- | --- | --- |
| 工具数 | 5 → 41.7% | 9 → 75.0% | 3 |
| 调用量（加权） | 8,200 → 82.0% | 9,500 → 95.0% | 500 → 5.0% |

$$C_{\text{tool}} = \frac{|\text{可逆工具}|}{|\text{写工具}|}, \qquad C_{\text{call}} = \frac{\sum_{i \in \text{可逆}} n_i}{\sum_{i \in \text{写}} n_i}$$

两个口径能差一倍（41.7% vs 82.0%），所以覆盖率必须**按调用量加权**，并按「不可逆且高影响」的**绝对次数**设 SLO（这里 5%，约 500 次/天都要有审批与审计记录）。只看工具数会高估不可逆操作的占比（非自动回滚：按工具数 58.3%，按调用量 18.0%）。

**表 5：dry-run 的盈亏平衡（口径：$p^* = c_{\text{dry}} / L$，把预演代价与一次错误的事后收拾代价对比）**

| 口径 | 预演代价 $c_{\text{dry}}$ | 一次错误的收拾代价 $L$ | 盈亏平衡 $p^*$ |
| --- | --- | --- | --- |
| 成本 | 0.01 美元（一次额外的模型调用 + 只读校验） | 500 美元 | $2.0\times10^{-5}$（0.002%） |
| 延迟 | 1.5 s（用户等待预演） | 1800 s（人工 30 min 收拾） | $8.3\times10^{-4}$（0.083%） |

只要这个操作的出错或结果不可接受概率高于 0.083%，dry-run 在延迟上就是划算的；写操作的实际错误率远高于此，所以 L1 的高风险参数与 L2 档默认走预演。口径说明：$L$ 只算事后收拾的直接人力，不含业务损失，因此真实的 $p^*$ 更低——这张表给出的是**上界**。

**幂等去重表的规模**（口径：10 万写操作/天、每行 200 B）：TTL 取 1 / 7 / 30 天时分别是 20 MB / 140 MB / 600 MB。去重表便宜到"应该选长 TTL"，唯一的硬约束是 $T_{\text{idem}} > T_{\text{retry,max}} + T_{\text{replay}}$：键的过期必须晚于所有可能的重放路径关闭（队列重投、人工重放、对账补偿）。

```python
import hashlib
import sqlite3

# ---- ① 幂等键 + 去重表：重放不产生重复副作用 ----
db = sqlite3.connect(":memory:")
db.execute("CREATE TABLE idem(key TEXT PRIMARY KEY, state TEXT, result TEXT, expires_at INT)")
SIDE_EFFECTS = []

def write_once(key, effect, now):
    old = db.execute("SELECT state,result FROM idem WHERE key=? AND expires_at>?",
                     (key, now)).fetchone()
    if old:
        return "replayed", old[1]             # 命中幂等键：返回首次结果，不重复执行
    db.execute("INSERT INTO idem VALUES(?,?,?,?)", (key, "in_flight", None, now + 7 * 86400))
    db.commit()                               # 先落 in_flight：崩溃后留下可补偿的意图
    out = effect()
    db.execute("UPDATE idem SET state='done',result=? WHERE key=?", (out, key))
    db.commit()
    return "executed", out

k = "t-42:refund:order-9001:req-7f3a"         # 作用域：租户:工具:业务对象:请求 id
run = lambda: (SIDE_EFFECTS.append(k), "refund-ok")[1]
print(write_once(k, run, now=1_700_000_000), write_once(k, run, now=1_700_000_005))
print("实际执行副作用次数 =", len(SIDE_EFFECTS))   # 2 次调用，1 次副作用

# ---- ② 追加写 + 哈希链：篡改可被检测 ----
class AuditLog:
    def __init__(self):
        self.rows, self.head = [], b"\x00" * 32

    def append(self, rec):
        body = repr(sorted(rec.items())).encode()
        h = hashlib.sha256(self.head + body).digest()
        self.rows.append({"prev": self.head.hex()[:8], "hash": h.hex()[:8],
                          "rec": rec, "_body": body, "_hash": h})
        self.head = h

    def verify(self):
        prev, bad = b"\x00" * 32, []
        for i, r in enumerate(self.rows):
            if hashlib.sha256(prev + r["_body"]).digest() != r["_hash"]:
                bad.append(i)             # 重算不一致 = 该条或它的前驱被改
            prev = r["_hash"]             # prev 取存储值，篡改会向后传播
        return bad


audit = AuditLog()
for rec in ({"trace": "req-7f3a", "tool": "refund", "args": {"order": "9001", "amt": 120}},
            {"trace": "req-7f3a", "tool": "send_email", "args": {"to": "u@x.com"}},
            {"trace": "req-7f3a", "tool": "close_ticket", "args": {"id": "T-88"}}):
    audit.append(rec)
print([(r["prev"], r["hash"]) for r in audit.rows], "verify =", audit.verify())

audit.rows[1]["rec"]["args"]["to"] = "attacker@x.com"          # 改记录内容
audit.rows[1]["_body"] = repr(sorted(audit.rows[1]["rec"].items())).encode()
print("改内容但不重算哈希，verify =", audit.verify())           # 命中第 2 条
audit.rows[1]["_hash"] = hashlib.sha256(audit.rows[0]["_hash"] + audit.rows[1]["_body"]).digest()
print("连哈希一起重算，verify =", audit.verify())               # 传播到第 3 条
```

输出（本机 Python 运行；哈希值由输入唯一决定，这里把同一段的两行打印合并展示）：

```text
2 次调用 → ('executed', 'refund-ok') ('replayed', 'refund-ok')，实际执行副作用次数 = 1
链头 [('00000000', 'afbf42dc'), ('afbf42dc', '8af6e56d'), ('8af6e56d', '54ff9915')] verify = []
改内容但不重算哈希，verify = [1]；连哈希一起重算，verify = [2]
```

口径与不确定性：表 1 的字段字节数是自定口径的典型值（参数与返回截断上限是设计选择，不是实测）；表 2 的 1 GB/s 是保守假设，本机实测 1.56 μs/条更快，但生产上的瓶颈会是日志写入 I/O 而不是哈希；表 3 假设各步补偿独立同分布（现实中相关失败会让多步一起挂——同一个下游出问题往往同时失败，尾部因此比独立假设更厚：不是均匀地差一点，而是容易出现「多步一起进人工队列」；再加上 $q$ 的真实值少有演练验证、通常偏乐观，这张表只当量级参考）；表 4 与幂等表的调用量、行宽是示例口径，真实值要从自己的网关埋点统计；表 5 的 $L$ 只计人工收拾成本。表中没有来自参考资料的机械结论：NIST AI RMF 提供的是四类职能的治理框架，Visibility into AI Agents 提供的是三类措施与部署形态的分析，两者的具体量化均为自行推导。

## 常见追问

- **追问**：分布式下怎么做到"真正幂等"？
  - 要点：放弃 exactly-once，做 at-least-once + 幂等消费。三件事缺一不可——幂等键的作用域含业务对象（不然用户重复提交、两个任务收敛到同一动作都拦不住）；去重表与副作用在**同一事务**里写（仅当副作用与去重表在同一存储；跨系统做不到原子，就要靠 intent log 记意图 + 下游去重 + 对账，否则"插了键但没执行"或"执行了但键没落"都会漏）；TTL 覆盖最长重试与重放窗口，并对超过 TTL 的重放设外部对账（用业务状态查一遍"这笔退款是否已存在"，即"重试前先查询状态"）。跨系统时把幂等键透传给下游，让下游也能去重。
- **追问**：审计日志本身会不会成为新的泄露面？
  - 要点：会。参数和返回摘要里可能有 PII、密钥、越权内容。对策是四层——字段级脱敏（保留可追责的主体假名 id，自由文本脱敏）、访问控制与最小权限（读审计日志本身要授权，且读操作也记 meta-audit）、保留期与到期删除、以及不落全量上下文（表 1 的 14 倍体积差本身就是风险差）。另外缓存与 trace 系统常常是同一份数据的第二副本，容易漏。
- **追问**：如何度量「可回滚覆盖率」？
  - 要点：$C_{\text{tool}}$ 看治理进度（有多少工具声明了逆操作），$C_{\text{call}}$ 按调用量加权看真实风险敞口，二者一起报（表 4 里差了近一倍）。再补两个尾部指标：「不可逆且高影响」调用的绝对次数与占比，以及这些调用中有审批记录的比例。指标要能按工具、租户、场景下钻，否则无法定位是哪个工具在拖后腿。
- **追问**：回滚与外部副作用（邮件已发出、订单已提交）怎么办？
  - 要点：区分「撤回」与「修正」——发出去的邮件撤不回，但可以发更正、可以在内部系统里标记作废并记录对外状态。所以设计上要把不可逆的那一步尽量后移（先建草稿、先预留、最后才发送），并给它加取消窗口与幂等的催促逻辑。真的无法撤回时，控制手段换成"事前审批 + 限额 + 对账 + 对外沟通预案"，并在审计里明确标注该动作不可逆——让事后处理的人知道边界在哪。
- **追问**：dry-run 的成本增加怎么说服团队？
  - 要点：用表 5 的盈亏平衡，把"多一次调用"和"可能的收拾成本"放到同一单位（成本或延迟）。再补一句工程上的不对称：预演的代价是确定的、可预测的，错误的代价是长尾的、发生在最不方便的时候。真正要优化的是预演本身（只读、复用已取到的数据、结果缓存），而不是取消它。
- **追问**：提示注入诱导 agent 调用越权工具，这套体系里怎么发现？
  - 要点：防线在工具网关的确定性校验（按发起者身份判权限、参数限额），不在模型；发现手段在审计——把"权限拒绝""参数越界""与用户请求语义不符的调用""短时间内同类写操作激增"做成告警规则，它们都是审计链上的可查询模式。trace 里还要记下被引用的上下文来源，才能回溯到是哪段被注入的内容影响了这次决策。

## 公司变体

以下按公开技术材料与产品形态判断侧重方向，不涉及具体面试流程。

- **Palantir**：偏「可审计性与权限是平台一等能力」这一路，工程实现与治理并重。其公开材料里反复出现的能力是权限标记（marking）式的强制访问控制、数据血缘（lineage）与变更提案/审批（proposal + branch 式的先审后合），以及把「谁在什么依据下批准了这次变更」做成可查询的记录。因此这题在这家公司的问法更容易从「每个写入都要能归属到人、数据与审批，并且能被独立复现」切入：agent 的写操作要先落成待审的变更而不是直接生效，不可逆动作必须有人工签核，日志与血缘要能回答影响范围。相对地，公式推导（比如 saga 成功率、盈亏平衡点）不是这类岗位的首要考察点，能把分级、审批链与血缘讲清楚更关键。
