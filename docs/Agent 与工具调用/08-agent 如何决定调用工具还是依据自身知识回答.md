## 一句话答案

> 这不是模型内部的一个开关，而是每一步上的**路由决策**：在「用参数化知识直接答」与「调工具取外部信息或执行动作」之间选一条路。function calling 的 `tool_choice: auto` 明确允许模型**不调用任何工具**直接回复，所以「不检索」本身就是一条合法动作，路由质量由工具描述里的适用/不适用条件、提示里的判定步骤、以及模型之前那层便宜的规则或分类器共同决定。
> 判据压成五个维度：时效性、事实性（专有或内部数据）、可验证性要求、是否涉及私有状态或写操作、模型自身的不确定性。前四条客观可判，第五条（知道自己不知道）最难，不能单独依赖模型自省。
> 两类错误代价不对称：漏检索换来幻觉与过时信息，在事实性场景里是致命的；过度检索只是噪声、延迟与成本。所以阈值要偏向检索，高风险主题由**产品策略**强制兜底，而不是交给模型的自觉。

## 面试官在考什么

- 能不能把「要不要用工具」讲成路由问题，并给出可操作的判据；而不是用「模型会自己判断」解释「模型如何判断」。
- 是否知道 `tool_choice: auto` 下「什么都不调、直接生成文本」是一条合法路径，因此 agent 循环的终止条件与路由决策是同一个机制的两面（[[agents-01]]）。
- 能不能把学术路线与工程分层对上：Self-RAG 的反思 token、Adaptive-RAG 的复杂度分类器，分别对应工程里的哪一层，各自适用面在哪。
- 会不会算两类错误的账：漏检索与过度检索的代价如何传导到端到端准确率、平均检索次数与账单。
- 有没有评测与运维方案：混合评测集、路由混淆矩阵、平均每问检索次数、路由决策的缓存与失效。

常见错误答案：

- 答成「模型自己知道该不该调用工具」，给不出机制、判据与阈值；或者反向极端，认为必须靠 prompt 写死「回答前先判断是否需要检索」。
- 只谈准确率不谈成本，或者不区分**路由错**与**工具错**。路由准确率很高但检索质量差，端到端一样差；把两者混在一个「效果不好」里，就找不出该修哪一层。

## 原理与推导

### 1. 把问题形式化成一次路由

设某一步的上下文为 $c$（历史消息、工具列表、检索候选），模型可选的动作集合是

$$
\mathcal{A}(c) = \{\text{直接答},\ \text{调工具},\ \text{追问澄清}\}
$$

「决定调用工具还是依据自身知识回答」就是在这个集合上做一次选择。它有几个容易讲错的性质：

- **它是逐步的，不是一次性的**。同一会话里第一问可以直答，第二问必须检索；工具返回后模型还要再判一次「够了没有」。所以路由是循环内的每个决策点都要执行的动作，而不是入口处的一次分类（[[agents-01]]、[[rag-06]]）。
- **动作空间不对称**。直答只花生成 token；调工具要花一次往返、可能多一轮 LLM 调用、还要把结果 token 塞回上下文。所以「不确定性中等」时最优解往往不是二选一，而是先问一个澄清问题或先调一个便宜的工具。
- **它是概率行为**。模型输出的是一段文本（工具名 + 参数，或普通回答），路由准确率是一个统计量，可以被测量、被策略覆盖，但不能被假定为 1。

判断维度的清单，工程上按这五条走：

| 维度 | 触发外部信息/动作的信号 | 典型例子 |
| --- | --- | --- |
| 时效性 | 答案随训练截止之后的时间变化 | 「今天」「最近」「现在几点」、股价、赛事、版本号 |
| 事实性 | 专有、内部、长尾实体，参数化知识覆盖不到 | 公司内部制度、客户订单、私有代码库、SKU 库存 |
| 可验证性要求 | 输出要给出处、要能被审计或复核 | 法务条款、医疗剂量、财务口径、带引用的答复 |
| 私有状态与写操作 | 要读用户态数据或产生副作用 | 查我的日历、发邮件、下单、改配置、退款 |
| 模型自身不确定性 | 同一问题多次采样答案发散、首 token 概率低 | 生僻实体、多跳算术、含糊指代 |

前四条可以从 query 与元数据**客观判定**：命中时间词与版本号就查，命中内部实体白名单就查，租户开了「必须引用」就查，工具属于写操作就必须走确认。第五条是唯一需要模型自省的，也是最容易失效的一条，见「两类错误的代价不对称」与常见追问。

### 2. 机制：`auto` 允许「什么都不调」

function calling 的完整回路是：把工具列表（name + description + parameters 的 JSON schema）和用户消息一起送进模型；模型要么输出普通文本，要么输出一个结构化的工具调用请求；runtime 执行工具、把结果作为一条消息追加回上下文；模型再决定是继续调工具还是给出最终答复。循环在模型输出**不带任何工具调用的文本**时结束。源文把这个分工讲得很清楚：模型只输出 JSON 请求，真正执行的是应用代码，模型不碰外部系统。

于是「要不要调工具」这件事在协议层由 `tool_choice` 控制：

| 取值 | 语义 | 路由由谁决定 |
| --- | --- | --- |
| `auto`（默认） | 模型可以选任意工具，也可以一个都不选、直接回答 | 模型 |
| `required` | 本轮必须产生至少一个工具调用 | 策略（模型只能选调哪个） |
| `none` | 本轮禁止调工具，只能生成文本 | 策略 |
| 指定工具名 | 强制调用某一个工具 | 策略 |

关键推论：**在 `auto` 下，「不调用工具」不是一个需要额外配置的分支，而是默认存在的分支**。模型在工具列表和提示词的联合作用下选它，因此提升路由质量的手段只有三类，全都在提示词与 schema 层面（[[agents-05]]）：

- 在工具 description 里写清**什么时候不该用我**。「查询订单状态」之外补一句「闲聊、写作、代码解释不要使用本工具」，比只写正向能力更能压住误触发。
- 用**决策步骤**把隐式判断变成显式输出：要求模型先给出一个判定字段，例如 `{"need_external_info": true, "reason": "..."}`，再据它选择工具调用或直接回答。判定字段与 function calling 是同源能力（都靠模型按 schema 产出 JSON，[[agents-03]]），但两者是不同机制：结构化输出约束的是这一轮文本的形状，工具调用产出的是交给应用执行的请求，部分接口还要求同一轮里二选一。所以实践上要么把判定拆成独立的一轮（或做成一个专用的路由工具 `route_decision`），要么把判定写进工具调用的参数里，不要指望同一轮既出 JSON 判决又出工具调用。代价是每问多几十个输出 token，收益是决策可观测、可落盘、可评测。
- 用**两阶段路由**把判定挪到更便宜的模型上：小分类器或小模型只吃 query（有时加检索分数），输出「不检索 / 单步检索 / 多步迭代」三档，再由大模型在指定档位内执行。

「模型自主判断」与「产品策略」是两件事。前者是概率行为，后者是确定性约束：写操作、金额、法务与医疗主题应当由策略强制检索或强制走审批，模型只保留「检索什么」的自由度，不保留「要不要检索」的自由度。这一层兜底与工具调用本身的安全边界是同一个思路——模型只能提出请求，执行与拒绝都在应用侧（[[agents-05]]）。

### 3. 学术路线：让模型学会「不值得检索」

Self-RAG（Asai et al., ICLR 2024）出发点是源文摘要里点明的问题：不管需不需要检索、检索到的段落相不相关，都固定取回固定数量的段落，会削弱模型的多面性，甚至产出无用回答。它的做法是训练同一个 LM 在生成时输出**反思 token（reflection token）**：一类决定检索行为（这一轮要不要检索、要不要继续检索），一类批判内容（检索段落是否相关、生成内容是否被段落支撑、整体回答是否有用）。这些 token 让模型在**推理期可控**——按任务要求调节检索频率与严格程度，而不是全局写死。论文口径：7B 与 13B 的 Self-RAG 在开放域 QA、推理与事实验证任务上超过 ChatGPT 与检索增强的 Llama2-chat，在长文本生成上对事实性与引用准确率有显著提升。

Adaptive-RAG（Jeong et al., NAACL 2024）从另一头切入：现有方案要么用不必要的算力处理简单查询，要么处理不了复杂的多步查询，而真实请求并不整齐地落在「简单」或「复杂」两端。它训练一个**较小的 LM 做复杂度分类器**，在「不检索 / 单步检索 / 多步迭代检索」三档之间选，标签是从模型的实际预测结果与数据集自身的归纳偏置里自动收集的（而不是人工标复杂度）。在覆盖多种复杂度的开放域 QA 数据集上，它同时提升了效率与准确率，优于包括自适应检索在内的基线。

两条路线的共同结论，也是这道题最该说出口的一句：**并非所有查询都值得检索**。过度检索会引入噪声、延迟与成本；而「要不要检索」这件事可以被学习、被蒸馏进一个小模型，也能被推理期的控制 token 调节，不必全靠提示词许愿。

### 4. 工程分层：从便宜到贵

生产系统通常四层串起来，前面能拦住的流量不要进后面：

| 层 | 判定手段 | 增量成本 | 判错的代价 | 适用面 |
| --- | --- | --- | --- | --- |
| ① 规则与缓存 | 关键词/意图白名单、语义缓存命中、prefix 缓存复用系统提示与工具 schema（[[inference-serving-05]]） | 接近零（语义缓存命中时连一次 LLM 调用都省掉；prefix 缓存只降低命中部分的 prefill 单价） | 规则写错会稳定地错，需要灰度与回滚 | 闲聊、格式化/翻译/改写、高频重复问题 |
| ② 小分类器/小模型 | query 复杂度或意图分类、检索分数门控 | 一次小模型调用的 token 与延迟 | 分类错只影响路由，不直接影响答案；可用混淆矩阵量化 | 流量大、延迟敏感、路由模式稳定的场景 |
| ③ 大模型自主 function calling | `tool_choice: auto` + 工具描述里的适用条件 + 决策步骤 | 一次完整 LLM 轮次；工具调用再加一次往返与工具结果 token | 误触发浪费一次调用；漏触发直接落到「两类错误的代价不对称」那一节说的高危区 | 开放域、工具多、问法多样 |
| ④ 策略强制 + 人工复核 | 主题/租户/工具白名单强制检索；写操作强制确认（先出确认步骤，批准后才执行，执行侧带幂等键防重试重复扣款） | 延迟与成本必然上升，吞吐下降 | 牺牲效率换确定性，宁可多查不可漏查 | 法务、医疗、金额、权限与不可逆写操作 |

顺序不能反：把 ③ 放在 ① 前面，就等于让最贵的一层承担最廉价的分流工作。分层的收益也很容易算错——「数值与代码验证」一节会看到，路由器本身有成本，只有当它省下的工具调用多于它自己花的钱时才划算。

### 5. 两类错误的代价不对称

用混淆矩阵写清楚：真实「需要外部信息」但走了直答，是**假阴性（漏检索）**；真实「不需要」却调了工具，是**假阳性（过度检索）**。

- 漏检索的后果是幻觉与过时信息，而且模型往往**语气自信**，用户没有能力分辨；在事实性、合规、对外发布的场景里这是事故级代价。
- 过度检索的后果是延迟上升、token 变贵、上下文被噪声填充。还有一条常被忽略：检索结果与参数化知识冲突时，模型未必选对——它可能被错误片段带偏，把本来答得对的题答错。「数值与代码验证」一节的口径里「不需要检索的题被强制检索后答对率从 0.95 掉到 0.85」就是这个效应。

因为两类代价不对称，工程上的默认取向是**阈值偏向检索**：拿不准就查。但偏向检索不等于一律检索——一律检索要把全部流量都付出工具成本，而自适应路由可以用一半的检索量换到同等甚至更高的准确率，前提是路由准确率过得了「数值与代码验证」里算出的盈亏平衡点。

## 数值与代码验证

以下数字全部按本节口径自行推导，不是任何来源的实测结论。口径：混合评测集里「确实需要外部信息」的题占 $p$；路由准确率 $a$ 表示「该查的查、不该查的不查」的比例，两类错误的条件错误率都取 $1-a$（即假设路由在两个类上一样不准，合计错误率也是 $1-a$）；在需要外部信息的题上，走了检索答对率 0.90、硬答答对率 0.40；在不需要外部信息的题上，直接答对率 0.95、被强制检索后答对率 0.85。

表 1 是错误分解（取 $p=0.5$、$a=0.9$）：

| 路由结果 | 比例 | 后果 |
| --- | --- | --- |
| 正确：需要 → 检索 | $p \cdot a = 45\%$ | 正常 |
| 正确：不需要 → 直答 | $(1-p) \cdot a = 45\%$ | 正常 |
| 假阴性：漏检索 | $p(1-a) = 5\%$ | 幻觉、过时信息 |
| 假阳性：过度检索 | $(1-p)(1-a) = 5\%$ | 延迟、成本、可能带偏 |

路由准确率从 0.9 提到 0.95，两类错误各从 5% 降到 2.5%——**两类错误的绝对值相等，但业务代价差一个量级**，这就是阈值偏向检索的定量理由。

表 2 是平均每问检索次数 $r$（决定账单的那一项）：

$$
r = p \cdot a + (1-p)(1-a) = (1-p) + a(2p - 1)
$$

| $p$ | $a=0.6$ | $a=0.7$ | $a=0.8$ | $a=0.9$ | $a=1.0$ |
| --- | --- | --- | --- | --- | --- |
| 0.3 | 0.46 | 0.42 | 0.38 | 0.34 | 0.30 |
| 0.5 | 0.50 | 0.50 | 0.50 | 0.50 | 0.50 |
| 0.7 | 0.54 | 0.58 | 0.62 | 0.66 | 0.70 |

$p=0.5$ 那一行是反直觉的：在两类错误对称的假设下，检索次数**恒为 0.5，与路由准确率无关**——每修好一个漏检索，就会多出一个过度检索。由此得到两条口径说明：① 混合评测集越接近五五开，检索量的节省上限就只有 50%；想省得更多，只能让真实流量分布偏向「不需要外部信息」（$p \to 0$ 时 $r \to 1-a$）。② 表 2 是**下限**：把阈值偏向检索会压低漏检率、同时抬高过度检索率，$r$ 只会比表里的值更大，那是拿钱换漏检，不是省钱手段。

表 3 是端到端准确率（$p=0.5$，按上面口径）：

| 策略 | 端到端准确率 | 平均检索次数 |
| --- | --- | --- |
| 从不检索 | 0.675 | 0 |
| 一律检索 | 0.875 | 1.00 |
| 路由 $a=0.7$ | 0.835 | 0.50 |
| 路由 $a=0.8$ | 0.865 | 0.50 |
| 路由 $a=0.8333$ | 0.875 | 0.50 |
| 路由 $a=0.9$ | 0.895 | 0.50 |
| 路由 $a=1.0$ | 0.925 | 0.50 |

在本口径下，路由族随准确率线性变化：$e2e(a) = 0.625 + 0.3a$。截距 0.625 对应 $a=0$，也就是**完全反着路由**（该查的硬答、不该查的强制检索），它比「从不检索」的 0.675 还低——强制检索会伤到本来答得对的题。与「一律检索」持平的盈亏平衡点是 $a^{*} \approx 83.3\%$：**路由准确率低于约 83% 时，一律检索在准确率上反而更好**；高于它才开始既准又省。这条可以当门槛背下来：测不出 83% 以上的路由准确率，省下的那半检索量换不回掉下去的准确率。

成本侧的不等式同样直接。记一次工具调用的全成本为 $C_{tool}$（工具往返 + 追加的一轮 LLM 生成 + 工具结果占用的输入 token），路由器成本为 $C_{route}$，则分层方案划算的条件是

$$
C_{route} + r \cdot C_{tool} < C_{tool}
\quad\Longleftrightarrow\quad
C_{route} < (1-r) \cdot C_{tool}
$$

$p=0.5$、$a=0.9$ 时 $r=0.5$，要求 $C_{route} < 0.5\,C_{tool}$；$p=0.3$、$a=0.9$ 时 $r=0.34$，要求 $C_{route} < 0.66\,C_{tool}$。用大模型自己做决策步骤时，这一项不能按零算：多输出的判定字段与多出的思考 token 就是 $C_{route}$，把 $C_{route}$ 当作 0 是常见的高估收益来源。

工具定义本身的 token 成本，也可以用源文的 `get_weather` schema 估一下。那段 JSON 是 2 空格缩进，共 14 行、302 个字符（不含末尾换行）；英文按约 4 字符/token 粗略折算约 76 token（字符法估算，不是 tokenizer 实测）。每个工具的 name、description、parameters 都会常驻在每次请求的输入里：

| 工具数 | schema 输入的粗略 token 量 |
| --- | --- |
| 1 | ~76 |
| 5 | ~378 |
| 10 | ~755 |
| 50 | ~3,775 |

两个推论：其一，工具越多，固定前缀越贵，这本身就是「工具数量多少算太多」的一个量化切口（[[agents-05]]）；其二，这段前缀逐字不变，prefix caching 能把重复部分从全价 prefill 降成缓存读价，但写入那次通常溢价、TTL 到期与实例驱逐都会让它重新按全价写入（[[inference-serving-05]]）——所以把工具 schema 放在提示词最前面、且保证字节级稳定，是把路由成本压下来的前提。

下面这段 Python 复算表 2 与表 3，输出与本节的数字一致：

```python
p = 0.5                            # 混合评测集里「确实需要外部信息」的比例
hit_ret, hit_no = 0.90, 0.40       # 需要检索时：走了检索 / 硬答
hit_dir, hit_forced = 0.95, 0.85   # 不需要检索时：直接答 / 被强制检索

def e2e(a):
    need = a * hit_ret + (1 - a) * hit_no
    free = a * hit_dir + (1 - a) * hit_forced
    return p * need + (1 - p) * free

def rate(a):                       # 平均每问检索次数
    return p * a + (1 - p) * (1 - a)

never = p * hit_no + (1 - p) * hit_dir        # 全部直答：该检索的也硬答
always = p * hit_ret + (1 - p) * hit_forced   # 全部检索：不需要的也检索
print("从不检索 %.3f | 一律检索 %.3f | 完美路由 a=1 %.3f | a=0（反着路由）%.3f"
      % (never, always, e2e(1), e2e(0)))
for a in (0.7, 0.8, 0.8333, 0.9):
    print(f"a={a:.4f} -> 端到端 {e2e(a):.4f}, 检索率 {rate(a):.3f}")
```

路由本身可以写成「便宜规则 → 小模型 → 大模型决策步骤 → 策略覆盖」的四段函数。判定结果落盘成结构化字段，是后续算路由准确率与平均检索次数的前提：

```python
FORCE_RETRIEVAL_TOPICS = {"法务", "医疗", "账单", "权限"}
GREETING = ("你好", "谢谢", "你是谁")

def route(query, *, topic, tenant_requires_citation, cache_hit, complexity_clf):
    if query in cache_hit:                       # ① 语义缓存命中：直接答
        return "answer", "cache"
    if query.strip() in GREETING:                # ① 规则：闲聊无需工具
        return "answer", "rule"
    if topic in FORCE_RETRIEVAL_TOPICS or tenant_requires_citation:
        return "retrieve", "policy"              # ④ 策略强制，模型无权跳过
    if complexity_clf(query) >= 0.5:             # ② 小模型：先分流再做
        return "retrieve", "classifier"
    return "auto", "llm"                         # ③ 交给 tool_choice=auto 自主决定
```

`route` 返回 `"auto"` 时，把工具列表与一句可判定的适用条件交给模型即可；显式决策步骤版本如下（返回 `"retrieve"` 或 `"auto"` 都适用）：

```json
{
  "tool_choice": "auto",
  "messages": [
    {"role": "system", "content": "可用工具：search_docs（内部制度与产品文档，含版本号）、get_order（需要订单号，属读操作）、refund（写操作，必须先确认）。回答前先判断：问题是否涉及内部数据、训练截止之后的事实、或用户私有状态；是则先调用相应工具，否则直接回答并在回答中说明依据来自通用知识。"}
  ]
}
```

这段提示的作用不是「要求模型自觉」，而是把前面那张表的五条判据翻译成模型能匹配的条件，从而把 `auto` 分支的分流质量从随机水平抬到可用水平。真正的下限仍由策略层守住。

## 常见追问

- **追问**：模型能可靠地「知道自己不知道」吗？怎么量化不确定性？
  - 要点：三种信号各有硬伤。① token logprob：校准差，模型可以对错误答案给出高概率，且采样温度与 top-p 会改变这个量的含义；② 自评（让模型给自己的答案打分或回答「是否确定」）：与生成同源，倾向于过度自信，对长尾事实尤其不灵；③ 多次采样一致性：答案发散确实指示不确定，但要多花几倍算力，而且在「稳定地错」的题目上完全失效。工程做法是**不把不确定性当作唯一触发器**：用规则与元数据兜住客观可判的四条维度，把不确定性只用于「要不要追加一次验证或澄清」，并且始终让阈值偏向检索。
- **追问**：检索结果与模型自身知识冲突时怎么办？
  - 要点：默认**优先证据**，但必须显式标注分歧而不是静默覆盖。可以要求模型在冲突时输出「检索片段说 X，通用知识说 Y，以 X 为准，因为来源是 <版本/日期>」；如果证据本身置信度低（分数低、来源旧、多来源互相矛盾），就降级为「需要人工确认」而不是硬选一边。反过来也要防另一头：把检索片段当作绝对真值、模型明明知道它过期了也照抄，是另一类真实事故。
- **追问**：路由决策要不要缓存？什么时候失效？
  - 要点：分两层。服务层的 prefix caching 缓存的是「系统提示 + 工具 schema」这段逐字不变的前缀，字节不变时命中部分按缓存读价计费、不再全价 prefill，但它有厂商侧 TTL（默认 5 分钟档）、会被 LRU 驱逐、滚动发布也会清空，不是「设一次永久有效」（[[inference-serving-05]]）；应用层的语义缓存缓存的是「问题 → 判定结果/答案」，必须按用户、租户与权限隔离，并在语料更新、工具版本变化、权限变更、时效性问题（含「今天」「最近」）上立即失效。把路由结论缓存得比答案更久是常见错误——路由对了但检索源更新了，等于稳定地给出旧答案。
- **追问**：为什么工具描述写好了，模型还是频繁误触发？
  - 要点：先看是不是这几类问题：工具之间描述重叠（模型无法区分，只能靠猜）；只写了正向能力、没写不适用条件与前置条件（缺订单号时不该调 `get_order`）；工具的 `parameters` 里必填项过多，模型为凑参数而乱填；`tool_choice` 被设成了 `required` 或指定工具名——这时不触发才是不正常的（[[agents-05]]）。排查方法是把「工具选择正确率」单列成一个指标，而不是混在端到端准确率里。
- **追问**：路由质量怎么评测？
  - 要点：先建**混合评测集**，需要外部信息的与不需要的各占一半（比例可调，用来模拟真实流量分布 $p$），两部分分别看指标：路由层算混淆矩阵、路由准确率、平均每问检索次数 $r$；端到端层算最终正确率、引用支撑率与延迟分位；再单列一个「无效检索率」，即检索了但结果没被用上的比例。注意别用端到端准确率倒推路由好坏：检索质量差会把路由的收益吃掉，两个变量必须解耦。
- **追问**：多轮 agent 里，路由决策是每轮都做吗？
  - 要点：是，且每轮的信息更多——上一步的工具结果、已确认的实体、剩余预算都可以作为判据。但要做三件事防退化：① 已经确定的事实不要重复检索，对「工具 + 归一化参数」做去重；② 把「证据是否足够」作为显式的终止判断，而不是靠模型感觉；③ 给路由设总预算（工具调用次数与 token 上限），超限就基于现有证据作答并标注证据不足（[[agents-01]]、[[rag-06]]）。
