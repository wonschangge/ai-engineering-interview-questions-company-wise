## 一句话答案

> 先分级、再审批、后兜底。风险判据落在 **(工具, 规范化参数, 影响范围)** 这个三元组上，而不是「这个 agent 危不危险」，据此给出四档默认动作——自动执行 / 自动执行 + 事后审计 / 事前审批 / 禁止自动执行——把审批量压进人工队列容量以内。
> 事前审批的请求必须自带决策信息：要做什么、为什么、影响范围多大、有哪些候选动作、不确定性在哪；只给一个「是否批准」的按钮等于让审批者盲签。
> 实现上它是一台持久化状态机：挂起要 checkpoint、批准要绑定参数指纹、一次批准只执行一次、超时必须有默认动作、全过程可审计。

## 面试官在考什么

- 能否把「重大操作」写成可判定的策略，而不是交给模型自我评估。判据要落到工具与参数：不可逆或高影响、合规要求、置信度低或连续失败、超出预算、涉及敏感数据。
- 是否理解审批本质是**信息设计问题**。请求里没有影响范围与备选方案，审批者只能盲签，机制会在两周内退化成橡皮图章。
- 能不能比较事前阻塞、事中打断、事后复核三种干预点，并按风险与时效给出选择，以及审批超时的默认策略。
- 有没有考虑人因与容量：审批疲劳、批量合并、审批队列的排队行为、谁有资格批、审批人不在时怎么办。
- 工程闭环是否完整：长事务如何挂起与恢复、幂等键怎么设计、批准后参数被改（TOCTOU）怎么防、审计怎么留存。

常见错误答案：

- 「高风险动作弹个窗让用户点确认」。没有分级判据、没有默认动作、没有超时策略；用户点两次之后就只会无脑同意。
- 把 HITL 做成同步阻塞的 UI 调用：agent 进程 sleep 等回调，进程一重启状态就丢，回调重投还会把同一个动作执行两遍。

## 原理与推导

### 1. 先定「什么时候必须人工介入」

判据要能从调用现场取到值，否则无法自动化判定：

- **不可逆或高影响**：工具风险元数据 + 参数中的金额、记录数、目标环境。付款、删除记录、对外发送、生产变更。
- **合规要求**：受监管的动作类别与数据类别。向患者/客户发送通知、导出个人信息。
- **不确定性**：模型置信度、同一工具连续失败次数、参数缺失。例如同一工具第 3 次重试同一个失败调用。
- **资源**：单次与累计的成本、步数预算。超出 run 预算的全量抓取。
- **数据敏感度**：参数与上下文中命中的敏感类别。把 PII 写到外部 webhook。

四档默认动作：

| 档位 | 触发条件 | 默认动作 | 延迟代价 | 审计要求 | 例子 |
| --- | --- | --- | --- | --- | --- |
| T0 自动执行 | 只读、幂等、无敏感数据 | 直接执行 | 无 | 普通日志 | 搜索、读文件、查询记录 |
| T1 自动执行 + 事后审计 | 可逆写操作、影响范围有界 | 先执行，进入审计队列抽样复核并触发告警 | 无（异步） | 完整动作日志 + 回滚入口（见 [[agents-10]]） | 建草稿、打标签、发内部通知 |
| T2 事前审批 | 不可逆、超阈值、涉及合规、置信度低 | 挂起等待人工决策 | 分钟级（量级见「数值与代码验证」第 3 小节） | 完整审批记录：谁、何时、看到哪版信息 | 付款、对外发送、改生产配置 |
| T3 禁止自动执行 | 法规禁止、无权限、不可审计 | 拒绝，交回原生系统由人工执行（T3 不是审批更严，而是 agent 不执行） | 无 | 拒绝事件同样入库 | 转账、删除用户账号、签署合同 |

两个不变量决定了分级能不能落地：

- **参数级判据优先于工具级**。同一个 `send_email`，收件人在租户域内是 T1，域外是 T2；同一个 `update_record`，影响 3 条是 T1、影响 3 万条是 T2。
- **重试不改变档位**。失败重试是同一个逻辑动作，不能因为「这次是重试」就降级，否则重试成为绕过审批的通道（重试语义见 [[agents-02]]）。

分级必须可配置、可按租户与场景覆盖：风险元数据写在工具声明里（见 [[agents-05]]），阈值是数据不是代码，`prod` 与 `staging` 用两套策略，新工具上线即带默认档位（fail-closed，而不是默认 T0）。

### 2. 审批交互：请求里必须有什么

这是本题的题眼。一张合格的审批请求要回答五个问题，缺一个审批者就只能猜：

- **要做什么**：工具 + 参数的自然语言摘要，而不是裸 JSON。例：「把 CRM 中 1 247 条 `status=churned` 的联系人标记为 `do_not_contact`，并从 3 个营销列表移除。」
- **为什么**：触发它的用户原话与推理摘要、引用的证据。例：「你要求停止给已流失客户发促销邮件」+ 2 条检索结果。
- **影响范围**：多少条记录、多少钱、哪些用户、是否可撤销、下游爆炸半径。例：「1 247 条（占该租户联系人 8.3%）；3 个营销列表；移除后需人工重新导入才能恢复；2 个正在运行的营销活动受影响。」
- **候选动作**：批准 / 修改后批准 / 换方案 / 拒绝，四类都要能表达。例：「① 全部批准 ② 只处理 30 天内有互动的 214 条 ③ 只导出名单不写入 ④ 拒绝并说明原因。」
- **不确定性与风险提示**：置信度低在哪、缺什么信息、最坏后果是什么。例：「`status` 字段 4.1% 为空（约 51 条），模型对这批判断置信度低。」

反面示例是 `{"tool":"crm.bulk_update","args":{"filter":"...","patch":"..."}}` 加一个 [批准][拒绝]。审批者拿不到影响范围，5 秒内只能点批准。

三条设计规则：

- **影响范围由服务端确定性代码算出**（dry-run / 预演 / count 查询），不由模型生成。模型可以写「为什么」，但不能写「影响多少条」，否则它会美化自己的破坏面。dry-run 与回滚是 [[agents-10]] 的地基。
- **候选动作必须包含「修改后批准」**。审批者的常见反应是「方向对、范围收窄」，没有这个出口就只剩拒绝，agent 只能从头重来。
- 卡片要能一屏读完，同时保留展开原始参数与证据的入口。信息密度换的是决策质量，不是字数。

### 3. 三种干预点与超时策略

| 维度 | 事前阻塞 | 事中打断 | 事后复核 |
| --- | --- | --- | --- |
| 形态 | 第 $k$ 步执行前挂起，拿到决策才继续 | 循环运行中人工改参数、换工具、接管 | 先执行，异步审计 + 必要时回滚 |
| 安全性 | 最高（动作尚未发生） | 高（可在后续步骤纠正） | 取决于回滚完备性与发现速度 |
| 延迟 | 分钟级，占满整个挂起期 | 分钟级，只影响被介入的那一步 | 无 |
| 实现复杂度 | 中（checkpoint + 恢复） | 高（循环可中断、状态可改） | 低（复用日志与回滚） |
| 适用 | T2 不可逆动作 | 参数需人工微调的多步写入、需人工接管的登录与验证 | T1 可逆写操作 |
| 失败模式 | 队列积压、超时 | 改坏中间状态、并发冲突 | 回滚不完整、出事才发现 |

选择规则：动作不可逆就选事前阻塞；可逆但需要人给方向就选事中打断；可逆且有界就放到事后复核。三种不要都上——每加一个人工环节，端到端时长与人力成本都按「数值与代码验证」第 3 小节的量级上涨。Anthropic 的主张是优先最简单可控的模式，只在复杂度确实提升结果时才加。

审批超时的默认策略按动作性质三选一：**默认拒绝**（不可逆动作的默认值，TTL 到期即作废，agent 收到「审批超时，动作未执行」后改方案重提）、**降级为只读**（可逆动作退化成只生成计划或导出结果，副作用留到人工确认之后）、**转交他人**（SLA 内必须有决策的流程，按代理规则转给下一个有权限的人，转交链写入审计）。不要设「默认批准」，那等于把 TTL 变成自动放行开关。

挂起不是让进程 sleep：必须把会话状态、已完成步骤、外部副作用记录、待执行动作的规范化参数与指纹落库，并释放 GPU 与 KV（量级见「数值与代码验证」第 4 小节），恢复时按状态机重放，记忆的存取方式见 [[agents-07]]。

### 4. 人因与容量

审批疲劳有个可以量化的形态：若某类请求里真正该被拒绝的只占 1%，那么「永远点同意」这个策略的准确率就是 99%。在这种先验下，只提供同意/拒绝的界面必然退化成橡皮图章——审批者的最优策略就是一路同意。对策是改变先验，不是要求审批者更认真：

- **风险分级**（见「原理与推导」第 1 小节）：把低价值审批移出人工队列，这是最有效的一招。
- **批量合并**：同工具、同参数形状、同一批次的请求合成一次决策并附逐条差异。1 000 条同类更新是 1 次决策，不是 1 000 次。
- **差异化默认值**：高风险默认拒绝、低风险默认同意，让「不动手」也表达立场。
- 给每位审批者设定每天的低价值审批量上限，超限自动转入抽样审计。
- **抽样审计代替全量审批**：T1 档按比例抽样，用复核发现的错误率反推自动放行策略该收紧还是放松。

拒绝与修改的理由必须回灌：把结构化的 `{decision, edited_args, reason}` 作为 tool result 写回同一会话，agent 就地改方案；否则它会从头再来，或者反复提交同一个已被拒的请求。回灌理由与约束，不回灌审批人身份。

评测这套机制是否真的有效：

- **审批覆盖率与漏放率**：离线回放历史工具调用，统计「按策略应进 T2」的调用里真的进了审批的比例（覆盖率），漏放率是它的补数。这是最关键的指标。
- **误批率**：被批准的请求中，事后由抽样审计或回滚事件判定为「本不该执行」的比例。
- **批准率 / 修改率 / 拒绝率**：批准率长期高于 99%，说明分级过保守或审批者已疲劳。
- **审批耗时 p50/p95**：直接决定端到端延迟，也是队列容量的观测量。
- **否决后修复率**：被拒后 agent 在同一会话里产出可批准方案的比例；太低说明拒绝理由回灌没做好。

### 5. 状态机与工程实现

```text
proposed ──policy──> auto_executed                            (T0)
        ├─policy──> blocked ──> 人工操作指引                    (T3)
        └─policy──> pending ──approve──> approved ──> executing ──> executed
                        ├──edit─────> approved_with_edits ──> executing ──> executed
                        ├──reject───> rejected
                        └──timeout──> expired ──> (改方案重提 → proposed)
auto_executed / executed ──audit──> verified | rolled_back     (T1)
```

不变量：

- `pending` 期间外部世界不变，不允许「先做了再补审批」。dry-run 只算影响范围用于展示与复核，不产生副作用。
- 只有 `approved` / `approved_with_edits` 能进入 `executing`，且进入时重新校验参数指纹。
- `rejected` / `expired` / `blocked` 的动作不可执行，也不允许 agent 改写参数后复用同一个 `approval_id`。

**幂等**（一次批准只生效一次，重试语义见 [[agents-02]]）：`approval_id` 作为唯一键、动作指纹 `fingerprint = H(工具名 ‖ 规范化参数 ‖ 影响范围摘要 ‖ 目标环境)` 随批准记录落库；执行器用 compare-and-swap 完成 `approved → executing` 的转移，回调重投、移动端点两下、agent 重试都会被第二道约束挡掉。少了这一层，IM 卡片的重试投递就会变成重复付款。

**「批准即绕过」（TOCTOU）的三道防线**：① 批准绑定指纹——审批者批准的是那一刻的确切参数与影响范围，执行前重算，不一致就退回 `pending`；② 执行前复跑策略与预演——权限、配额、影响范围一律重算，人可能已被降权、目标记录可能已被改动；③ 修改后批准只能由审批者写回——agent 不得改写已批准的动作，任何参数变化都是新的 `proposed`。

**多级审批与代理**：金额或权限阈值决定是否需要第二级（例如 5 000 元以下一级、以上两级）；代理规则要显式（谁不在时谁能批、代理有效期多长），并强制职责分离——不得批准自己发起或自己受益的请求。转交与升级都要写进审计，否则事后无法解释「这个人凭什么有权批」。

**通知渠道**：IM 卡片、邮件、工单可以并存，但移动端必须能完成审批请求的四类候选动作；只支持同意/拒绝的移动端等于把审批人逼回桌面。

**审计留存**（见 [[agents-10]]）：每次审批记录「谁、何时、看到哪一版信息、做了什么决定、理由、执行结果」，append-only 存储并按合规要求设保留期。Visibility into AI Agents 把这类可见性拆成三层：agent 标识（谁在跑哪个 agent）、实时监控（此刻在做什么）、活动日志（做过什么）；审批记录属于第三层，前两层决定了事后能否把一次动作还原到具体主体。NIST AI RMF 则把 human oversight 放在治理语境里：明确角色、阈值与记录，而不是只在代码里加一个判断分支。

## 数值与代码验证

以下数字都是按说明的假设自行复算，三篇来源没有给出这些算例；口径逐条标注在表下。

### 1. 自动放行的累积正确率

若把「这一步要不要人工介入」也交给一个每步判对率 $p$ 的自动判定，$n$ 步任务里「一次都没错放」的概率是 $p^{n}$：

| 每步判对率 $p$ | 5 步 | 10 步 | 20 步 |
| --- | --- | --- | --- |
| 0.99 | 0.9510 | 0.9044 | 0.8179 |
| 0.95 | 0.7738 | 0.5987 | 0.3585 |
| 0.90 | 0.5905 | 0.3487 | 0.1216 |

$0.95^{20} = 0.3585$，即 64.1% 的 run 至少发生一次错误放行。口径：各步独立同分布；真实系统的错误是相关的（同一个错参数会被反复使用），这里只用来说明量级——它是把审批放在工具粒度而不是 run 粒度的量化理由。

### 2. 审批队列的容量悬崖（M/M/1）

口径：一位审批者（单服务台），平均 45 秒处理一条，即 $\mu = 1.33$ 条/分钟；8 小时工作窗；到达近似泊松、处理时间近似指数分布。等待时间用 $W_q = \rho/(\mu-\lambda)$ 与 $P(W_q > t) = \rho e^{-(\mu-\lambda)t}$ 直接算出，p50 取 $P(W_q > t) = 0.5$、p95 取 $0.05$。

| 日审批量（8h 内到达） | 利用率 $\rho$ | 平均等待 $W_q$ | 等待 p50 | 等待 p95 |
| --- | --- | --- | --- | --- |
| 448 条 | 0.700 | 1.75 min | 0.84 min | 6.60 min |
| 500 条 | 0.781 | 2.68 min | 1.53 min | 9.42 min |
| 576 条 | 0.900 | 6.75 min | 4.41 min | 21.68 min |
| 600 条 | 0.938 | 11.25 min | 7.54 min | 35.17 min |

日处理量从 448 涨到 600（+34%），p95 等待从 6.6 分钟涨到 35 分钟；到 640 条（$\rho = 1$）队列直接发散。审批队列的容量要按 $\rho \le 0.7$ 留头部空间，而不是按 640 的理论上限。这张表也决定了超时与 TTL 的取值：TTL 必须大于目标 SLO 的 p95，否则大量请求会因为超时作废而被反复重提。

### 3. 人力与 token 成本

口径：每天 50 000 次工具调用，45 秒/条，8 小时/人日。

事前审批占比 1% → 500 条/天 = 6.2 人时 = 0.78 FTE；5% → 2 500 条/天 = 31.2 人时 = 3.91 FTE；100% → 50 000 条/天 = 625 人时 = 78.1 FTE。

规则：在这组参数下，**每 1 个百分点的事前审批占比约等于 0.78 个全职审批人力**。这就是分级必须是「默认自动 + 例外审批」的原因。

延迟同理：agent 单步 3 秒、20 步共 60 秒；按第 2 小节表中 $\rho = 0.78$ 那一行的平均等待 2.68 分钟算，插入一次审批后端到端变成 221 秒，放大 3.7 倍；若等待落到 30 分钟量级，则放大 31 倍。模型侧的成本反而不是瓶颈：按 10% 的审批占比即 5 000 条/天、审批卡片 300 token 计，只有 1.5 M token/天，真正的成本是人的时间与端到端延迟。

### 4. 挂起会话的显存代价

口径：LLaMA-3-70B、GQA 8 个 KV 头、head_dim 128、80 层、bf16，即每 token 320 KiB KV；KV 按 1024 进制，卡按 80 GB = 80 × 10⁹ B 计。

| 场景 | KV 占用 | 折合 80 GB 卡 |
| --- | --- | --- |
| 单会话 8k / 32k 上下文 | 2.50 GiB / 10.00 GiB | — |
| 200 个挂起会话 @ 32k | 2.15 TB | 26.8 张 |

等待审批的长事务不能占着 KV cache：状态落库、显存让出，恢复时重新 prefill（或从 prefix cache 的磁盘副本恢复）。这条也是「事前阻塞」延迟代价的真实来源。

### 5. 策略分级与幂等执行

```python
from hashlib import sha256
import json

# tool = {"name": "crm.bulk_update", "reversible": False, "external_effect": True,
#         "prohibited": False, "auditable": True}       # 工具声明里带风险元数据（同 agents-05）
# call = {"tool": tool, "args": {...}, "environment": "prod", "confidence": 0.55,
#         "consecutive_failures": 0, "est_records": 1247}   # call 是本次调用的现场信息

def fingerprint(call, impact) -> str:
    payload = json.dumps({"t": call["tool"]["name"], "a": call["args"],
                          "e": call["environment"], "s": impact["summary"]},
                         sort_keys=True, ensure_ascii=False, separators=(",", ":"))
    return sha256(payload.encode()).hexdigest()[:16]

def tier(call, policy: dict) -> str:
    tool = call["tool"]
    if tool.get("prohibited") or not tool.get("auditable", True):
        return "T3"                                     # 法规禁止 / 无权限 / 不可审计：不执行
    if not tool["reversible"] and call["environment"] == "prod":
        return "T2"                                     # 不可逆动作：事前审批
    if call["est_records"] > policy.get("t1_max_records", 5000):
        return "T2"                                     # 影响范围超阈值
    if call["confidence"] < policy.get("min_confidence", 0.7):
        return "T2"
    if call["consecutive_failures"] >= policy.get("max_failures_before_review", 2):
        return "T2"                                     # 连续失败后不再自动重试
    if tool["external_effect"] or call["est_records"] > 0:
        return "T1"                                     # 可逆写操作：事后审计
    return "T0"

def execute_approved(store, approval_id: str, call, dry_run, run_tool):
    rec = store.get(approval_id)
    if rec["state"] not in ("approved", "approved_with_edits"):
        raise PermissionError("approval is not in an executable state")
    impact = dry_run(call)                                # 执行前复算影响范围与摘要
    if rec["fingerprint"] != fingerprint(call, impact):    # 防线 1：批准绑定确切参数与影响范围
        store.cas(approval_id, rec["state"], "pending")
        raise PermissionError("args or scope changed after approval, re-approval required")
    if impact["records"] > rec["approved_scope"]:         # 防线 2：影响不得超过批准上限
        raise PermissionError(f"scope grew: {impact['records']} > {rec['approved_scope']}")
    if not store.cas(approval_id, rec["state"], "executing"):
        raise RuntimeError("already executed")            # 幂等：只有一个调用者能赢
    result = run_tool(call["tool"]["name"], call["args"])
    store.cas(approval_id, "executing", "executed")       # 失败则 cas 到 failed 再重抛
    store.append_audit(approval_id, call, impact, result)
    return result
```

## 常见追问

- **追问**：如何避免「审批即绕过」——批准之后参数被改？
  - 要点：批准绑定动作指纹（工具 + 规范化参数 + 影响范围 + 环境），执行前重算比对，不一致就退回 `pending`；执行前复跑权限与影响范围预演；修改后批准只能由审批者写回，agent 不得改写已批准动作。这三条缺一条，审批就只是延迟执行。
- **追问**：高并发下审批成了瓶颈怎么办？
  - 要点：先压量（风险分级 + 批量合并 + 抽样审计），再扩人（多级审批、代理、值班队列），最后才谈改流程。按 M/M/1，$\rho > 0.9$ 之后 p95 会指数上升，加人的收益出现在饱和之前而不是之后。若某类动作的审批量注定超过容量，说明它不该是 T2，应该改造成可回滚可审计的 T1。
- **追问**：怎么测这套机制？
  - 要点：构造对抗性用例集（越权参数、超阈值金额、跨租户目标、域外收件人、连续失败后的重试、批准后篡改参数），断言必须被拦下或必须进审批；再离线回放真实调用算漏放率与误批率；最后用混沌注入测回调重投与并发批准下的幂等。
- **追问**：能不能让模型自己判断这个动作要不要审批？
  - 要点：可以让模型给出风险信号（置信度、缺失参数、可疑目标），但档位判定必须由策略引擎按工具元数据与参数确定性算出。让被监管者自己决定要不要被监管，等于没有监管。
- **追问**：审批超时为什么默认拒绝，而不是默认放行？
  - 要点：TTL 到期说明「在这一刻，没有人对不可逆动作负责」，默认放行等于给攻击者一个免费通道：把审批人拖进会议、制造队列积压，就能等到自动放行。可逆动作才有资格降级为只读或稍后重做。
- **追问**：多 agent 编排里谁申请审批？
  - 要点：申请主体是「发起动作的那个执行单元」，但审批记录里要写清完整的委派链（谁派给它、它的权限来自哪里），否则批的是 A、执行的是 B，责任无法归属。子 agent 不得自行提升档位或代批。

## 公司变体

- **OpenAI**：偏工程实现与产品形态。公开材料强调把人工确认做进产品交互本身：产品在涉及登录、支付一类敏感步骤时把控制权交回用户（接管/确认），以及用审核层与护栏在模型输出与真实动作之间加一道。问法常从「确认卡片上放什么、后端策略与前端交互怎么分工、如何避免用户点成习惯」切入，会要求把审批请求的信息设计落到具体界面元素上。
- **Palantir**：偏治理与可审计。公开材料里的 agent 平台强调 human-in-the-loop、动作要继承底层系统已有的权限模型，且每次写操作都要有可追溯的记录。问法常从「谁有权批准这个动作、权限从哪里继承、审批记录如何进入审计与合规留存」切入，会追问多级审批、职责分离与代理规则。

以上是依据两家公开技术输出的侧重判断，不是对具体面试流程的描述。
