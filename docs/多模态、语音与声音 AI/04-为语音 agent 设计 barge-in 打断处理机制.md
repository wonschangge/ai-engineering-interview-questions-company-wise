## 一句话答案

> barge-in 不是「用户一说话就停」，而是五个必须各自实现的环节：**检测**（分清真打断与背信道）、**停止播放**（本地播放缓冲要能立刻清空）、**取消在途工作**（LLM token、TTS 合成、工具调用都可取消）、**上下文归因**（对话历史只保留用户**实际听到**的部分并标注被打断）、**恢复与转向**（继续原话题还是澄清）。
> 检测要分四层：VAD 给候选事件，**AEC 是前置条件**（否则 agent 会自己打断自己），语义层用 ASR 中间结果把「嗯」「对」这类背信道与「等一下」区分开，最小时长阈值与冷却窗口负责去抖。
> 半双工级联能靠状态机做完这一切，但打断本质上是**检测延迟 × 客户端缓冲**的问题——后半段常比模型本身更贵。

## 面试官在考什么

- 能不能把 barge-in 展开成一条完整的**状态机与生命周期**，而不是一句「VAD 触发就停」。多数候选人只答得出第 1、2 步，答不出第 4 步（历史归因），而第 4 步恰恰是线上最常出 bug 的地方。
- 有没有**从用户听感反推延迟预算**的意识：知道「音频流发出去了」不等于「用户听到了」，知道要跟踪播放位置，知道蓝牙与浏览器播放队列会再加几十到几百毫秒。
- 会不会区分**声学事件与对话行为**：咳嗽、椅子响、背信道（backchannel）、真打断是四件事，前两者不该改变 agent 行为，第三者不该打断，第四者必须立刻让路。
- 是否理解**取消是可传播的**：打断要沿着 orchestrator → LLM → TTS → 客户端播放这条链逐层取消，工具调用未必能取消，于是要用幂等键与预算兜底（链到 [[agents-09]]）。
- 有没有**评测与调参闭环**：打断响应时间、误触发率、漏触发率、打断后任务完成率，以及「误触发比不打断更糟」的取舍。
- 最后看是否知道**两条架构路线的边界**：级联式必须自己工程化整套机制；全双工原生模型把轮次切分去掉了，但客户端清缓冲仍然是自己负责的。

**常见错误答案**

- 「检测到用户说话就停止 TTS」——漏了清客户端缓冲，用户会继续听到已下发但未播完的那段音频（表 1 的缓冲深度 300–800 ms，参考来源给出的经验值约 2 秒）；也漏了历史归因，模型下一轮会以为用户已经听过没播出的内容。
- 「用固定能量阈值做 VAD，超过阈值就打断」——外放场景没有 AEC 就必然自激；没有最小时长与语义门控就会被咳嗽、背信道反复打断，体验比不打断更差。
- 「全双工模型不需要任何打断逻辑」——模型侧不需要，客户端缓冲、播放位置回报、历史截断依然要自己实现。

## 原理与推导

### 1. 先把 barge-in 的语义拆成五个环节

设 $t_0$ 为用户开始发声的时刻，$t_1$ 为「用户实际听到的声音停止」的时刻，则用户感知的打断延迟为 $L_{\text{barge-in}} = t_1 - t_0$。把 $t_0 \to t_1$ 拆开，就得到必须实现的五件事：

1. **检测**：在 assistant 正在说话时判断用户开始说话，并判断这是真打断还是背景声/背信道。
2. **停止播放**：停止产生新音频**并清空已下发但未播放的音频**。只做前者，用户会听到排队的尾音；尾音长度等于客户端缓冲深度。
3. **取消在途工作**：正在生成的 LLM token、正在合成的 TTS、正在跑的工具调用都要能取消或丢弃结果（链到 [[agents-09]]）。
4. **上下文归因**：把 assistant 这一轮发言截到**用户实际听到**的位置写回历史，未播出部分不能留成「已说过」；被打断这件事本身要标注。
5. **恢复与转向**：用户插话是补充（继续原话题）、纠正（改参数）、还是转题（放弃原任务）；「不对」类纠正要先澄清而不是道歉式复读。

下面三节分别展开：第 2 节讲检测（环节 1），第 3 节讲暂停与提交（环节 2、3），第 5 节讲恢复与转向（环节 5）；环节 4 的历史归因在「数值与代码验证」的截断误差表与状态机代码里给出可落地做法。

### 2. 检测分四层：声学、回声消除、语义、去抖

**第一层，VAD。** 对每个 20 ms 音频块（16 kHz 下 320 个采样点）判断「是否有人在说话」，能量阈值版最简单但门响、电视声都会误报，生产上用 Silero VAD 这类小型神经网络（链到 [[multimodal-03]]）。VAD 只是**候选事件发生器**，不是打断决策器。

**第二层，AEC（回声消除），是前置条件而不是可选项。** 外放时麦克风会拾到 assistant 自己的声音，若不消除就会自激：

$$
y[n] = s[n] + \sum_{k=0}^{L-1} h_k\, x[n-k] + v[n]
$$

其中 $x$ 是参考信号（系统正在播放的音频，已知），$h$ 是扬声器—房间—麦克风的冲激响应，$s$ 是用户语音，$v$ 是噪声。AEC 估计 $\hat{h}$ 并构造残差 $e[n] = y[n] - \sum_k \hat{h}_k x[n-k]$，理想情况下只剩 $s + v$。WebRTC 在客户端自带 AEC，电话侧由网络处理；自研客户端必须显式启用。

关键推论：**AEC 是因果的**。参考信号要先缓冲一帧才能做滤波，因此残差里总有一段还没被消掉的自身声音。若 AEC 引入一个 20 ms 块的算法延迟，双讲检测与 VAD 就必须在该延迟之后开始判定，这段延迟会**直接加进 $L_{\text{barge-in}}$**。

**第三层，语义门控。** VAD 只回答「有声音」。用流式 ASR 的中间结果（interim transcript）判断是不是真的在插话：

| 用户输入 | 时长/词数 | 是否打断 | 理由 |
| --- | --- | --- | --- |
| 「嗯」「对」「好的」「mm-hmm」「right」 | < 500 ms，1–2 词 | 否，背信道 | 不改变 agent 的下一步动作 |
| 「等一下」「停一下」 | 短但语义为指令 | 是 | 明确的停止意图 |
| 「不对，我要退的是另一单」 | 长，含否定与替换 | 是 | 改变本轮任务的参数 |
| 咳嗽、椅子响、狗叫 | 无识别词 | 否 | 语义层给不出词 |

工程上的判据是「越短、越常见、越不改变任务状态的输入，越需要语义证据才打断」。

**第四层，阈值与去抖。** 连续若干帧有语音 + 最小时长阈值（200–300 ms）+ 至少 1–2 个真实词，才允许升级为打断；并且要有**冷却保护**：一次打断后的 $N$ 秒内不再次触发，避免「停—停—停」的抖动。误触发的代价高于漏触发：漏触发只是慢半拍，误触发直接毁掉正在说的内容。打断生效后不要再加提示音或「好的，您说」这类语音反馈：**静音本身就是最好的用户可见反馈**，额外声音只会和用户的话重叠。

### 3. 懒打断：把「检查用」和「提交用」分开

一个容易被忽略的优化：**不要把最小时长窗口串在关键路径（hot path）上**。VAD 给出候选事件的瞬间就应该做两件廉价的事：

- 给 TTS 与 LLM 发**暂停**信号（停止产生新 token，但不销毁状态）；
- 停止往客户端发送新的音频块（让缓冲自然抽干）。

然后并行等两个证据：语音持续超过阈值、语义层给出真打断判定。两者都到，才执行**提交**——清缓冲、取消 TTS、截断历史、切到采集。若证据显示是背信道或噪声，就直接丢弃，从未真正打断。代价是提交路径多了一次条件判断（几毫秒），收益是绝大多数背信道不会造成任何可见抖动。

### 4. 两条架构路线

**半双工级联**（VAD → ASR → LLM → TTS）把 barge-in 做成显式状态机：`LISTENING` / `THINKING` / `SPEAKING` / `INTERRUPTED`。可控、可审计、每一步都能打日志，但打断响应受 VAD 阈值与最小时长限制，且天然无法建模重叠语音——用户在 agent 说话时说的前半句会被当成打断噪声丢掉。

**全双工原生**（Moshi 式）换掉了轮次切分这个前提。Moshi 把对话看成 speech-to-speech 生成：把自己的语音流与用户的语音流**并行建模**，从神经网络音频 codec 的 residual quantizer 取 token，并用「Inner Monologue」先预测时间对齐的文本 token 作为音频 token 的前缀。论文明确把「依赖说话人轮次切分、无法处理重叠语音、打断与插话」列为级联架构的核心问题之一，并称该模型是首个实时的全双工 spoken LLM，**理论延迟 160 ms、实际 200 ms**（论文摘要口径）。代价同样明确：

- 训练数据与算力门槛高，可替换性差（做不到单独换 ASR 或音色）；
- 可观测性与可控性差：拿到的是模型「自认为说过」的转写，无法在开口前检查文本；
- 客户端缓冲仍然必须自己清，模型在服务端，播放缓冲在设备端。

工程折中通常是混合：全双工或 S2S 前端负责自然感，后端文本 agent 负责工具与业务逻辑（链到 [[multimodal-05]]）。

### 5. 恢复与转向

打断之后不是简单回到「用户说完再回答」，而要判断意图：

- **补充**（「还有，地址改成公司」）：保留原任务上下文，合并新约束。
- **纠正**（「不对，是另一单」）：撤销上一轮已执行的参数，必要时先澄清「您是指 45678 还是 45679」。
- **转题**（「算了，先帮我查退款」）：丢弃未完成任务，但不丢掉已完成的事实（链到 [[agents-09]]）。

原则：**先澄清再动作**。用户说「不对」时，agent 的默认反应是道歉并复读，这会浪费一个回合，且很可能再次被打断。

| 阶段 | p50 | p95 | 参数来源与口径 |
| --- | --- | --- | --- |

| AEC 帧对齐（参考信号缓冲） | 20 ms | 20 ms | 一个 20 ms 帧；16 kHz 下 320 采样 |
| VAD 与双讲检测最小时长窗口 | 120 ms | 200 ms | 参考来源要求 200–300 ms；p50 用更激进的 120 ms（误触发风险更高），p95 用来源下沿 200 ms |
| 服务端决策（语义门控 + 状态切换） | 40 ms | 60 ms | 2 个 20 ms 块的等待 + 分类器推理；工程假设 |
| 取消信令下行（服务端 → 客户端） | 40 ms | 60 ms | 与上行同量级的网络单程；工程假设 |
| 客户端接收 + 停播执行 | 20 ms | 20 ms | 一个播放帧；工程假设 |
| **客户端播放缓冲清空** | **150 ms** | **400 ms** | 缓冲 300 ms（p50）/ 800 ms（p95），清空后平均还剩一半未播；缓冲深度为工程假设 |
| **合计** | **430 ms** | **840 ms** | 串行相加 |

这张表要读出三个结论：

1. **换掉全部模型也压不动这个数字**。模型不在关键路径上，路径上是采集、门控、信令和缓冲。若只优化「TTS 更快」，$L_{\text{barge-in}}$ 几乎不变。
2. **客户端缓冲占 35%（p50）到 48%（p95）**。缓冲越深播放越稳，但被打断时残留越多——这是流式 TTS 的核心取舍，与 [[multimodal-08]] 的 jitter buffer 是同一个旋钮。
3. **AEC 的 20 ms 是硬性的**，因为它来自因果性，删不掉；能删的是最小时长窗口的下沿（有误触发风险）。

注意 $L_{\text{barge-in}}$ 与端到端 voice-to-voice 延迟是**两个不同的指标**，不要混在一个预算表里报数：前者的窗口只有几百毫秒且不等待静音，后者要等 end-of-turn。

### 表 2：jitter buffer 的分位数估算

设包延迟超过最小值，且超出量服从均值 $\mu = 12$ ms 的移位指数分布，则超出量 $J \sim \text{Exp}(\lambda)$，$\lambda = 1/12\ \text{ms}^{-1}$。缓冲深度 $B$ 能够吸收抖动、不产生丢失的条件是 $J \le B$，于是尾部丢失概率为

$$
P(\text{丢失}) = e^{-\lambda B} = e^{-B/12}
$$

反解给定时延上界 $B$ 对应的分位数：

$$
B = -\frac{\ln P}{\lambda} = -12 \ln P
$$

| 缓冲 $B$ | $P(J > B)$ | 平均每秒丢包（50 包/s） | 主观影响 |
| --- | --- | --- | --- |
| 24 ms | 13.53% | 6.8 | 明显断续 |
| 40 ms | 3.57% | 1.8 | 偶发咔哒声 |
| 48 ms | 1.83% | 0.9 | 接近可接受 |
| 55.3 ms | 1.00% | 0.5 | 常见工程目标 |
| 60 ms | 0.67% | 0.3 | 良好 |
| 82.9 ms | 0.10% | 0.05 | 追求无损 |
| 150 ms | 0.00037% | ≈0 | 过度缓冲 |

口径说明：$\mu = 12$ ms 是**示意性假设**，用来演示「分位数 → 缓冲深度」的换算方法，不是任何来源的测量值；真实抖动分布是重尾的，用指数分布会低估尾部，工程上应换成实测分位数或 $\text{p99} - \text{p50}$。指数分布本身是报文的经典排队模型。

此处有一个必须自己指出的矛盾：**表 1 假设了 300–800 ms 的播放缓冲，而表 2 的 jitter 模型只需要 55–83 ms 就能把丢包压到 1% 以下。** 差额来自缓冲里另一半预算——采样率转换、Opus 解码、蓝牙免提设备的额外缓冲、以及为写入防抖留的余量。所以正确做法是分开记账：**抖动吸收预算**与**渲染/链路预算**各有自己的数，清缓冲时两者一起丢。

### 表 3：清缓冲实际丢弃了多少内容

| 缓冲深度 | 清空时平均未播时长 | 丢弃的 Opus 数据（32 kbps） | 丢弃的 24 kHz PCM 采样 |
| --- | --- | --- | --- |
| 100 ms | 50 ms | 200 B | 1,200 |
| 200 ms | 100 ms | 400 B | 2,400 |
| 300 ms | 150 ms | 600 B | 3,600 |
| 600 ms | 300 ms | 1,200 B | 7,200 |

字节量微不足道，**时长才是全部意义**：600 ms 的残留相当于把「您的订单已发货，预计明天下午五点前送达」的后半句又念了一遍。这就是为什么「清缓冲」必须和「取消 TTS」分开实现——前者省的是用户耳朵里的几百毫秒，后者省的是 GPU 与网络。

### 表 4：历史截断的粒度误差

播放位置由客户端周期回报（`playback_progress`），orchestrator 把「已播放的音频块序号」映射到文本 span。截断误差由回报粒度决定：平均误差 = 粒度 / 2，再按中英混合语速约 5 字/秒折算：

| 回报粒度 | 平均截断误差 | 对应的字数误差 |
| --- | --- | --- |
| 20 ms（每块都回报） | 10 ms | 0.05 字 |
| 40 ms | 20 ms | 0.10 字 |
| 100 ms | 50 ms | 0.25 字 |
| 200 ms | 100 ms | 0.50 字 |

结论：**每 20–40 ms 回报一次播放进度就够了**，误差远小于一个字；真正会出错的是「用已生成的 token 数代替已播放的音频块数」——同等条件下若用户只听了一半，历史里会多留 50% 的内容。

### 代码：可取消的打断状态机

```python
import asyncio
import uuid

class Turn:
    """一次 agent 发言：持有可取消的子任务与文本-音频对齐信息。"""
    def __init__(self, text_spans):
        self.id = uuid.uuid4().hex[:8]      # 轮次 id，历史标注用
        self.text_spans = text_spans        # [(chunk_idx_start, chunk_idx_end, text), ...]
        self.llm_task = None
        self.tts_task = None
        self.cancelled = False
        self.chunks_sent = 0                # 已下发给客户端的音频块数

    def heard_text(self, chunks_played: int) -> str:
        """只保留完整播完的文本片段；播到一半的那段整段丢弃。"""
        heard = []
        for start, end, text in self.text_spans:
            if end <= chunks_played:
                heard.append(text)          # 完整播完
            elif start < chunks_played < end:
                break                           # 播到一半：整段视为未听到
        return "".join(heard)


class Session:
    def __init__(self, history, tts, llm, client):
        self.history, self.tts, self.llm, self.client = history, tts, llm, client
        self.turn = None
        self.last_interrupt_ms = -10_000

    async def on_agent_speak(self, prompt):
        self.turn = Turn(text_spans=[])
        self.turn.llm_task = asyncio.create_task(self.llm.stream(prompt, self.turn))
        self.turn.tts_task = asyncio.create_task(self.tts.stream(self.turn))
        await self.turn.tts_task

    async def on_speech_candidate(self, t_ms: int, interim_words: list):
        """VAD 给出的候选事件：先暂停，不做不可逆动作。"""
        if self.turn is None or self.turn.cancelled:
            return
        if t_ms - self.last_interrupt_ms < 2_000:      # 冷却：2s 内不重复触发
            return
        self.tts.pause(); self.llm.pause()
        if len(interim_words) < 2 and not is_stop_intent(interim_words):
            self.tts.resume(); self.llm.resume()       # 背信道/噪声：撤销暂停，从未真正打断
            return
        await self.commit_barge_in()
        self.last_interrupt_ms = t_ms                  # 生效后才开启冷却窗口

    async def commit_barge_in(self):
        turn = self.turn
        turn.cancelled = True
        self.tts.cancel(); self.llm.cancel()           # 取消在途工作
        if turn.llm_task: turn.llm_task.cancel()
        if turn.tts_task: turn.tts_task.cancel()

        self.client.send("clear_audio_buffer")         # 清客户端未播缓冲
        played = await self.client.playback_position() # 已播块数（来自 playback_progress）
        heard = turn.heard_text(played)

        self.history.truncate_agent_turn(heard)        # 只留听到的部分
        self.history.mark(turn_id=turn.id, interrupted=True, cut_text_len=len(heard))
        # 工具调用已经发出的不撤回，改用幂等键 + 结果丢弃（见 [[agents-09]]）
        self.turn = None
```

三个容易被忽略的细节：`on_speech_candidate` 里**先暂停后判定**是懒打断，但判定为背信道/噪声时必须 `resume()` 撤销暂停，否则 TTS 会一直停着；`heard_text` 在边界上取**保守侧**（宁可少留一句，避免模型以为说过）；工具调用用幂等键而不是「撤回」，因为 HTTP 调用一旦离开进程就无法保证撤销。

## 常见追问

- **追问**：怎么区分背信道与真打断？
  - 要点：三重信号叠加——时长（背信道通常 < 500 ms）、词表（「嗯/对/好/right/yeah」）、以及**是否改变任务状态**。第三个信号最关键：背信道不引入新约束，真打断会带来否定、替换、停止意图。实现上常用一个在短语音片段（< 500 ms）上训练的小分类器，而不是拿完整 ASR 结果去判断。
- **追问**：外放场景如何防止自打断？
  - 要点：双重门控。第一层是 AEC，把参考信号从麦克风信号里减掉，前提是客户端显式启用并保证参考信号与播放时钟同源；第二层是**只在 agent 真正在播放时启用打断检测**，并在播放刚开始的几十毫秒内（AEC 收敛期）提高阈值。没有 AEC 时提高阈值只能减少而不能消除自打断，因为扬声器与麦克风的耦合路径随音量与摆放变化。
- **追问**：全双工模型还需要 VAD 吗？
  - 要点：仍需要，但**职责变了**。轮次切分不再依赖 VAD，所以它不再是打断与轮转的判据；剩下的用途是首轮唤醒/省电（判断是否有人在说话，避免空转）、静音段的带宽与计费裁剪、以及给 TTS 侧提供「用户在说话」的旁路信号。这一条与 [[multimodal-05]] 里对两条路线的对比是同一组论点。
- **追问**：手机端本地打断怎么做？
  - 要点：`listening` 期间双工开启，开工前就预取约 200 ms 的前导静音填充；用 `AudioTrack.pause()+flush()` 立即停播并丢弃未播帧，用 `setBufferSizeInFrames()` 把硬件缓冲调到尽小；蓝牙 SCO 会额外引入数十到上百毫秒，因此**不要在同一个音频路由上假设恒定的打断延迟**。服务端仍要靠 `playback_progress` 回报来知道截断点。
- **追问**：TTS 返回的文本与音频对不齐，怎么把播放位置映射到文本？
  - 要点：三种做法，按可靠度排序：(1) 要求 TTS 返回音素/词级时间戳，直接映射；(2) 自己按标点切句逐句合成，记录每句的首块序号，截断时只保留完整句；(3) 用估算语速（字/秒）做线性映射。前两种精度足够，第三种在数字串、缩写、URL 上会偏。若没有时间戳，**文本侧按整句保留、音频侧按块丢弃**，宁可少留一句也不要多留。
- **追问**：如何评测一次打断参数改动的好坏？
  - 要点：四个指标一起看——打断响应时间（$t_0 \to t_1$ 的 p50/p95，由客户端上报）、误触发率（无 ASR 词却触发打断的会话占比）、漏触发率（用户明确说停但 agent 未停）、以及打断后任务完成率与重试率。同时要记录被打断的轮次与截断位置，用来回放归因（链到 [[evaluation-09]]）。只盯误触发会把阈值越调越高，最后退化成不打断。
