## 一句话答案

> 首音延迟是六段之和：采集分帧 25 ms → VAD 与结束判定 240 ms → ASR final 200 ms（与结束判定并行走）→ LLM 首子句 160 ms → TTS 首包 150 ms → 网络往返与两侧 jitter buffer 150 ms。按源文那张表逐段取上界相加是 1,310 ms，按真实关键路径是 726 ms，把 ASR→LLM→TTS 流水线化并投机启动 LLM 之后是 636 ms；同一条路径的 p95 回到 1,500 ms。
> 时间的大头不在 LLM：结束判定 240 ms、纯传输 150 ms、TTS 首包 150 ms、LLM 首子句 160 ms。所以这题考的是「怎么把串行链路重叠起来」和「怎么把静音窗从关键路径上挪走」，不是「怎么把模型换得更小」。
> 必须分开记账的两个量是首音延迟与整轮时长：前者是 TTFT 加 TTS 首包，用户感受为「反应快不快」；后者的下限就是音频本身要播多久，用户感受为「有没有卡顿、有没有被抢话」。

## 面试官在考什么

- 有没有**预算表意识**：每一段给出数字、口径（从哪个时刻量到哪个时刻）和增长项（固定开销，还是随输入长度、并发、网络质量变化）。只报一个「端到端 800 ms」的答案无法定位瓶颈。
- 知不知道**串行与并行的分界**：结束判定与 ASR final 都从 VAD 报「语音结束」起算，是并行分支取 max，不是相加；而 ASR→LLM→TTS 之间默认是串行的，需要显式流水线化才重叠得了。
- 能不能指出**最大的隐性成本是静音窗**：为了确认「用户说完了」，通常要等几百毫秒静音，这段时间直接进入每一轮的端到端延迟，而且它与打断灵敏度是一对矛盾（见 [[multimodal-04]]）。
- 会不会算 **LLM 那一段**：TTFT 里 prefill 随 prompt 变长（前馈项 $\propto P$、注意力项 $\propto P^2$）、首子句生成随 batch 与上下文增长（$t_{step}=(W+bkS)/BW$，见 [[inference-serving-09]]），而不是笼统地说「LLM 很慢」。
- 有没有**播放侧概念**：jitter buffer 的大小是抖动分布的分位数，不是拍一个固定值；网络往返与两侧缓冲加起来就是 150 ms，占 800 ms 预算的近 1/5（见 [[multimodal-08]]）。

常见错误答案：

- 把各段厂商宣传的首包延迟相加就当预算（「ASR 100 ms + LLM 200 ms + TTS 100 ms = 400 ms」），漏掉结束判定、采集分帧、两侧 jitter buffer 与内部服务跳数——这四项按本文口径是 315 ms（200 + 25 + 70 + 20），是真正的隐性成本。
- 只优化 LLM 并把模型换小。语音轮次里 LLM 首子句只占 160 ms 左右，把它砍半只省 80 ms；同一笔投入放在「投机启动 LLM（把静音窗移出关键路径）」上，源文口径能省 200–400 ms（本文算例是 90–200 ms）。

## 原理与推导

### 1. 依赖图：哪些段是串行的，哪些可以重叠

```
t=0    用户说完最后一个词
 |-- 25 ms  采集与分帧（20 ms 帧 + 设备缓冲）
 |-- 40 ms  上行网络
 |-- 35 ms  网关输入 jitter buffer
 |==> 100 ms   末词到达服务端
      |-- 40 ms  VAD 报「语音结束」                 ==> 140 ms
      |     |-- 200 ms 静音窗 + 语义结束判定         ==> 340 ms  ┐ 并行分支
      |     |-- 200 ms ASR final 可用               ==> 340 ms  ┘ 取 max
      |==> 340 ms   LLM 可以开始（不投机时）
           |-- 80 ms  TTFT（排队 + prefill + 首 token）  ==> 420 ms
           |-- 81 ms  首子句 12 token 生成完             ==> 501 ms
                |-- 150 ms TTS 首包                      ==> 651 ms
                     |-- 40 ms 下行网络
                     |-- 35 ms 播放预填                  ==> 726 ms  用户听到第一个字
```

三条结论直接从图里读出来：**采集/上行/输入缓冲**是纯粹的前置管道延迟（100 ms，与模型无关）；**结束判定与 ASR final** 是并行分支，只能取 max 不能相加；**LLM→TTS** 默认串行，只有把触发点提前才会重叠。

### 2. 分段参数表（p50）

| # | 段 | p50 | 口径 | 随什么增长 |
| --- | --- | --- | --- | --- |
| 1 | 采集与分帧 | 25 ms | 20 ms 帧取半帧期望 10 ms + 设备/OS 采集缓冲 15 ms（上界 35 ms） | 固定；由帧长与设备决定 |
| 2 | 上行网络 | 40 ms | 同区域 one-way delay，取源文 30–80 ms 区间的偏低值（就近部署） | 固定；p95 由路由、重传、无线抖动决定 |
| 3 | 网关输入 jitter buffer | 35 ms | σ=15 ms 按 p99 取 $z\sigma = 2.33 \times 15$，整条音频流被推迟这么多 | 固定；由抖动分布的目标分位数决定 |
| 4 | VAD 静音起始判定 | 40 ms | 2 帧挂起确认「语音结束」；Silero VAD 处理一个 30 ms 音频块在单 CPU 线程上不到 1 ms，模型本身不是瓶颈 | 固定；挂起帧数是设计常量 |
| 5 | 结束判定（静音窗 + 语义模型） | 200 ms | 源文口径：句子完整时约 200 ms，不完整时放宽到 1.5–2 s | **策略量**：随用户停顿习惯与语义完整度变化，是唯一「越保守越贵」的项 |
| 6 | ASR final | 200 ms | 从服务端判定语音结束到 final 可用；源文正文给 100–300 ms，表里那行 50–150 ms 是另一口径 | 随 ASR 的 chunk 与右上下文线性增长；不随句子长度增长（流式边听边出） |
| 7 | LLM TTFT | 80 ms | prefill 52 ms（P=800、8B、1×H100、MFU 0.25）+ 首 token 7.3 ms（b=64、S=1k 的一步 $t_{step}$）+ 服务跳数 20 ms = 79.7 ms | **随 prompt 长度增长**（前馈项线性、注意力项 $\propto P^2$）；开 prefix caching 后只随本轮新增 token 增长 |
| 8 | 首子句生成 | 81 ms | 12 token 首句 = 首 token 之后 11 步 × 7.34 ms（b=64、S=1k） | 随子句 token 数与 TPOT（batch、上下文）增长 |
| 9 | TTS 首包 | 150 ms | 取源文 80–200 ms 区间内偏保守的 150 ms（正文另给 100–200 ms），口径是「请求发出 → 第一个音频块」 | 随首块文本量增长（首块越长越慢） |
| 10 | 下行网络 | 40 ms | 同第 2 行 | 固定 |
| 11 | 播放预填 | 35 ms | 播放侧 buffer 填到目标分位才开始出声，同第 3 行 | 固定 |

第 1、2、3、10 行合计 140 ms 是**纯传输与缓冲**（采集分帧 + 上行 + 输入缓冲 + 下行），与用哪个模型无关；第 5 行 200 ms 是**纯策略等待**，与算力无关。这两类加起来 340 ms，占 800 ms 目标的 42%——这就是「换模型不解决问题」的算术依据。

### 3. 三种记账方式：串行相加、关键路径、流水线

| 记账方式 | 算式（ms） | 结果 |
| --- | --- | --- |
| 源文那张表的两种求和 | 下界行 30+150+50+150+100+80+30；上界行 80+300+150+300+200+200+80 | 590 / 1,310 ms |
| 真实关键路径（段内并行、无跨段流水线） | 25+40+35+40+200+80+81+150+40+35 | **726 ms** |
| 流水线 + 投机启动（推荐口径） | 25+40+35+150+80+81+150+40+35 | **636 ms** |
| 同一条路径的 p95 | 35+70+45+60+max(300,400)+300+225+250+70+45 | **1,500 ms** |

第一行是对源文延迟预算表的校验：它给的「600–1,300 ms」就是该表各行下界与上界之和（590 与 1,310，源文取整成 600 与 1,300）；那张表没有算采集分帧与两侧 jitter buffer，所以真实系统只会更差。第二行与第三行换成本文的 p50 参数，同口径下把结束判定与 ASR final 相加是 926 ms，改成并行分支取 max 后是 726 ms——省下的 200 ms 正好是 ASR final 那一段。第三行把 LLM 的触发点从「final 可用」（340 ms）提前到「末词进入稳定 partial」（250 ms），再省 90 ms；如果在 VAD 报结束的那一刻就起 LLM（140 ms），结果是 526 ms，正是源文说的「投机处理省 200–400 ms」这个区间，代价是被丢弃的 LLM 调用。

p95 那行刻意换了一组参数：上行/下行取源文上界 70 ms，buffer 按 3σ 取 45 ms，VAD 在噪声下多挂起一帧，结束判定取 300 ms，ASR final 在嘈杂电话线上取 400 ms（两者仍是并行分支，取 max 得 400 ms，不相加），TTFT 取 300 ms（排队 + 更长 prompt），首子句 16 token 且 $t_{step}$ 涨到 15.03 ms（b=128、S=2k）。合计正好踩到源文「绝不超过 1.5 s」的上限（源文另要求 p95 低于 1.2 s）——**p50 达标不代表达标**，语音 agent 必须按 p95 定容量。

### 4. 三个分数点

**① 串行链路的延迟是相加的，而人类对话允许重叠。** 人回话的间隔是 200–500 ms（源文口径），级联管线默认「一轮做完再开下一轮」，本文口径下就是 726 ms（源文对级联管线的实测区间是 700 ms–1.2 s，原生全双工路线是 300–600 ms）。真正的优化方向不是把每段都压到极限，而是让下一段在上一段**还没结束时**就开始：ASR 出稳定 partial 就跑 LLM，LLM 吐出第一个子句就合成 TTS，TTS 出第一个块就播放。每一处提前都要求一个「可取消」的语义（生成到一半被丢弃的部分不能污染对话历史，见 [[multimodal-04]]）。

**② VAD 的静音阈值是最大的隐性成本，而且它是个策略旋钮。** 静音起始判定本身只要 40 ms（两帧挂起），真正的开销是「等多久才敢确认这一轮结束」：句末判定为完整时源文用约 200 ms，判定为不完整时最长 1.5–2 s。这个窗直接加在每一轮的端到端延迟上，而它与打断灵敏度是一对矛盾——窗越短，越容易在用户思考性停顿时抢话（[[multimodal-04]]）。所以成熟做法是把它变成动态量：静音窗由语义完整度决定，同时用投机执行把等待移出关键路径。极端场景的账很清楚：同一轮对话里，静音窗从 200 ms 拉到 1,500 ms，关键路径从 726 ms 涨到 2,026 ms，而投机口径仍然是 636 ms。

**③ 首包与总量要分开优化。** 用户感知「快不快」的是首音延迟（TTFT + 首子句 + TTS 首包），感知「顺不顺」的是整轮时长与卡顿。整轮时长有一个无法突破的下限：音频要播多久就是多久。折算 150 wpm、约 1.33 token/词，播放端只以约 3.3 token/s 的速度消耗文本，也就是说**只要 TPOT < 300 ms 就能一直跟上播放**，比文本聊天的 20–50 ms 门槛宽松一个数量级。反过来，一段 30 s 的回答只要 100 个 token，在 b=64、S=2k 的 101 token/s 下 1.0 s 就能生成完，TTS 按 RTF 0.3 需要 9 s 合成——两者都远快于 30 s 的播放，所以流式播放不会饿死；真正会导致卡顿（underrun）的是工具调用阻塞、模型进入长思考链，或者 TTS 的 RTF 超过 1（[[multimodal-08]]）。

### 5. LLM 那一段到底花多少

沿用 [[inference-serving-09]] 的单步耗时 $t_{step}(b,S) = (W + b k S)/BW$，取 8B 级语音 LLM（32 层、GQA-8、head_dim 128、bf16，权重 $W=16$ GB，每 token KV $k = 2 \times 32 \times 8 \times 128 \times 2 = 128$ KiB）、1×H100（bf16 稠密 989 TFLOP/s、HBM3 3.35 TB/s）：

| batch $b$ | 上下文 $S$ | $t_{step}$ | 首子句 12 token | 单流速率 | 系统吞吐 |
| --- | --- | --- | --- | --- | --- |
| 1 | 1,024 | 4.82 ms | 53 ms | 208 tok/s | 208 tok/s |
| 64 | 1,024 | 7.34 ms | 81 ms | 136 tok/s | 8,719 tok/s |
| 64 | 2,048 | 9.90 ms | 109 ms | 101 tok/s | 6,462 tok/s |
| 64 | 4,096 | 15.03 ms | 165 ms | 67 tok/s | 4,257 tok/s |
| 128 | 2,048 | 15.03 ms | 165 ms | 67 tok/s | 8,515 tok/s |
| 256 | 2,048 | 25.29 ms | 278 ms | 40 tok/s | 10,123 tok/s |

prefill 侧（$2NP + 2Ld_{model}P^2$，MFU 0.25）：P=80 是 5.2 ms，P=800 是 52 ms，P=3,200 是 218 ms；随 $P^2$ 走的注意力项在 P=800 时占 1.3%，到 P=3,200 时涨到 5%。两个可直接落地的结论：

- **prefix caching 是语音场景收益最大的一招**。第 10 轮对话的 prompt 约 3,200 token，不缓存时 prefill 要 218 ms，缓存后只有本轮新增的几十个 token 要算，约 5 ms——单这一项就省 200 ms 以上，且不牺牲任何质量（[[inference-serving-09]]）。
- **语音对 TPOT 的要求比文本宽松得多**（3.3 token/s 的播放速率 vs b=256 时的 40 token/s，余量 12 倍），所以并发可以往高放；被 batch 与上下文拖累的是**首子句**那 12 个 token，它从 53 ms 涨到 278 ms。语音的容量规划该守的约束是「首子句生成时间」和 TTFT，不是平均 TPOT。这也是连续批处理与实时音频流的主要冲突点：长 prefill 插队会给同批所有请求的 ITL 顶出一个台阶，而语音的首子句恰好落在最敏感的位置（[[inference-serving-09]] 的 chunked prefill 讨论）。

KV 容量同样要进预算。128 KiB/token 意味着 2,000 token 的会话占 250 MiB、4,000 token 占 500 MiB、8,000 token 占 1 GiB；每卡留 60 GiB 给 KV 时，分别是 245 / 122 / 61 路并发。一通 10 轮的电话大约落在 4,000 token 量级，所以单卡百路上下；KV 一旦打满，并发上限与上下文长度成反比（[[llm-internals-02]]）。

### 6. 播放侧 jitter buffer：大小是分位数，不是拍脑袋

输入侧与播放侧各一个 buffer，两者的口径相同：把「到达时间的离散程度」按目标分位数留成缓冲。RTP 的 jitter 字段（RFC 3550 的 $J$）是到达间隔偏差的平滑绝对均值，只能用来比较网络好坏，不能直接当缓冲深度用；缓冲要取的是抖动分布的一个高分位。若单包相对延迟近似 $\mathcal{N}(0, \sigma^2)$、$\sigma = 15$ ms：

| 目标 | $z$ | buffer |
| --- | --- | --- |
| p95 | 1.645 | 24.7 ms |
| p99 | 2.326 | 34.9 ms |
| 3σ（约 p99.87） | 3.000 | 45.0 ms |
| p99.9 | 3.090 | 46.4 ms |

本文取 p99 的 35 ms。这个模型有两个必须说明的简化：一是真实抖动分布比正态厚尾，按 $\sigma$ 外推会低估高分位；二是 buffer 要覆盖的是**窗口内延迟极差**（一个累积过程），不只是单个包对均值的偏差。另一个常被忽略的点是抖动来源不止网络——流式 TTS 的合成到达时间本身也有抖动。若网络 σ=15 ms、合成 σ=20 ms，独立叠加后 σ=25 ms、p99 要到 58 ms。**每一毫秒 buffer 都是一毫秒端到端延迟**，所以它必须和 [[multimodal-08]] 里「首块小、后续大」的 chunk 策略联合调：首块越小，预填越浅，卡顿风险越高。

### 7. 工程手段的收益与代价

| 手段 | 收益（按本文口径） | 代价 |
| --- | --- | --- |
| 流式 ASR + 稳定 partial | 把 ASR final 移出关键路径，最多 200 ms（实测口径是「稳定 partial 滞后」$\ell_p$，本文取 150 ms） | partial 会翻转；翻转后要么浪费一次 LLM 生成，要么答错后重答 |
| 投机启动 LLM（静音一起就跑，用户再说话就丢弃） | 90–200 ms；长停顿场景最多 1.4 s | 被丢弃的 LLM 调用是纯成本，丢弃率随用户说话习惯变化，要做限流 |
| 增量 LLM：首句短、禁长思考链、greedy 解码 | 首子句从 12 token 降到 5 token，省 (12−5)×7.34 ≈ 51 ms（第 3 节 636 → 584 ms）；首句原本更长时省得更多，16 token 起算是 81 ms | 首句语义可能不完整，需要「先附和再回答」的 prompt 设计；解码参数取舍见 [[llm-internals-12]] |
| 流式 TTS：首块小、后续大 | 首包 150 ms 已在源文 80–200 ms 区间内；首块再压缩收益有限 | 首块太短会伤韵律与自然度，且预填变浅、卡顿风险上升（[[multimodal-08]]） |
| 预热与预合成 | 开场白预合成后首音延迟只剩「播放预填 + 下行」= 75 ms；把 STT/TTS 长连接在通话建立时就开好（源文：临时建连要 100–300 ms） | 需要缓存与失效策略；预合成只覆盖固定文本 |
| 共置与优先级 | 每次内部跳数按 10–50 ms 计，把编排器、ASR、LLM、TTS 放进同一区域并给语音流量独立配额 | 资源利用率下降，成本上升 |
| 降级路径 | 网络差时降采样率（16 kHz→8 kHz）、换更小模型、缩短回答、退回按键/文本 | 分支多，必须提前演练；降级本身要可观测 |

### 8. 可观测性：没有分段埋点就无法定位「慢在哪」

每一段都要落成**分布**指标，而不是平均值，并且口径要写死在埋点定义里（[[evaluation-07]]）：采集分帧延迟、VAD 报结束的时刻、结束判定耗时（静音窗 + 语义模型）、ASR 稳定 partial 滞后与 final 滞后（需要词级时间戳对齐）、LLM TTFT 与 TPOT、首子句生成时间、TTS 首包（TTFB）、端到端首音延迟（以「用户说完」为起点、以「播放器出声」为终点）、打断响应时间（用户开口到音频停止）、underrun/卡顿次数。

分群维度比整体数字更有用：网络类型（4G/5G/WiFi/固话）、设备与浏览器、是否免提或蓝牙（会额外引入几十毫秒的设备侧缓冲，也会改变 AEC 行为）、语言与口音、地区（决定 RTT）、时段（决定排队）。验收用「p50 与 p95 轮次延迟 + 达标率」，与 [[inference-serving-09]] 的 goodput 思路一致：只看均值会被长尾掩盖，只看延迟不看达标率又会通过牺牲尾部来刷指标。

## 数值与代码验证

上面的表格由这段代码复算，硬件与模型常数与仓库其它专题一致（H100 SXM：bf16 稠密 989 TFLOP/s、HBM3 3.35 TB/s；LLaMA-3-70B 每 token 320 KiB 的对照见 [[llm-internals-02]]）：

```python
from statistics import NormalDist

H100, BW = 989e12, 3.35e12                        # H100 SXM 稠密算力与带宽
N, L, H_KV, D_HEAD, BY = 8e9, 32, 8, 128, 2       # 8B 级语音 LLM，GQA-8，bf16
W, K = N * BY, 2 * L * H_KV * D_HEAD * BY         # 16 GB 权重；128 KiB/token KV

step = lambda b, S: (W + b * K * S) / BW * 1e3    # 沿用 inference-serving-09 的 t_step
prefill = lambda P, mfu=0.25: (2 * N * P + 2 * L * 4096 * P * P) / (H100 * mfu) * 1e3

for b, S in ((1, 1024), (64, 1024), (64, 2048), (64, 4096), (128, 2048), (256, 2048)):
    print(f"b={b:4d} S={S:5d}  t_step={step(b,S):6.2f} ms  首子句12token={(12-1)*step(b,S):6.1f} ms")
print([round(prefill(P), 1) for P in (80, 800, 1600, 3200)])   # 5.2 52.4 106.3 217.9

Z = NormalDist().inv_cdf
print([round(Z(p) * 15, 1) for p in (0.95, 0.99, 0.999)])      # 24.7 34.9 46.4 ms
print(round(Z(0.99) * (15**2 + 20**2) ** 0.5, 1))             # 58.2 ms，网络与合成抖动叠加

P50 = dict(dev=25, up=40, jb_in=35, vad=40, eot=200, asr=200, ttft=80, tts=150, down=40, jb_out=35)

def budget(clause, part=None, **kw):
    p = {**P50, **kw}
    audio = p["dev"] + p["up"] + p["jb_in"]       # 末词到达服务端
    onset = audio + p["vad"]                      # VAD 报语音结束
    if part is None:                              # 不投机：等 max(结束判定, ASR final)
        start = max(onset + p["eot"], onset + p["asr"])
    else:                                         # 投机：等稳定 partial
        start = max(onset, audio + part)
    return start + p["ttft"] + clause + p["tts"] + p["down"] + p["jb_out"]

print(round(budget(11 * 7.34)))                   # 726 ms 关键路径
print(round(budget(11 * 7.34, part=150)))         # 636 ms 投机（保守触发）
print(round(budget(11 * 7.34, part=0)))           # 526 ms 投机（静音起始即触发）
print(round(budget(4 * 7.34, part=150)))          # 584 ms 换成 5 token 的 filler 首句
print(round(budget(24 * 7.34, part=150)))         # 731 ms 首句变成 25 token
print(round(budget(11 * 7.34, eot=1500)))         # 2026 ms 长停顿且不投机
print(round(budget(11 * 7.34, eot=1500, part=150)))   # 636 ms 长停顿但投机

P95 = dict(dev=35, up=70, jb_in=45, vad=60, eot=300, asr=400, ttft=300, tts=250, down=70, jb_out=45)
print(round(budget(15 * 15.03, **P95)))           # 1500 ms，正好是源文「绝不超过 1.5 s」的上限
print(round(150 / 60 * 1.33, 2), round(1000 / 3.325))   # 3.33 tok/s 播放速率 -> TPOT 门槛 301 ms
```

与源文对照：源文给的分段表（网络入 30–80、结束判定 150–300、ASR final 50–150、LLM TTFT 150–300、首句 100–200、TTS 首包 80–200、网络出 30–80）与「总计 600–1,300 ms、p50 目标 800 ms、绝不超过 1.5 s、p95 低于 1.2 s」这几个结论都取自该文，第 3 节第一行就是这张表按上界/下界求和的结果。其余数字是本文按自己声明的口径复算的：分段 p50 取值、关键路径与投机口径的差额、p95 那组参数、LLM 的 $t_{step}$ 与 prefill 表、KV 容量、播放速率约束、jitter buffer 分位数表。第 5 节里「prefill 随 prompt 增长、prefix caching 只算新增 token」的算式沿用 [[inference-serving-09]]，模型与硬件常数与该文一致。Silero VAD 的口径（30 ms 音频块、单 CPU 线程不足 1 ms、约 2 MB 的 JIT 模型、支持 8 kHz 与 16 kHz）取自其仓库说明，用于说明 VAD 模型本身不构成延迟瓶颈，本文没有使用其中的精度指标。

## 常见追问

- **追问**：为什么不干脆把 LLM 换小？瓶颈到底在哪？
  - 要点：把表摊开看——纯传输与缓冲 140 ms、结束判定 200 ms、TTS 首包 150 ms、LLM 首子句（TTFT + 12 token）161 ms。LLM 砍半只省 80 ms，而把静音窗移出关键路径能省 90–200 ms，让 ASR final 与结束判定并行又能省 200 ms（926 → 726 ms）。先花在结构与策略上，再考虑换模型；换小模型还会牺牲工具调用与指令遵循，语音 agent 的失败轮次代价更高。
- **追问**：实时语音系统的吞吐与延迟怎么权衡？
  - 要点：语音的 TPOT 需求比文本聊天宽松得多：播放端只消耗约 3.3 token/s，只要 TPOT < 300 ms 就跟得上，所以 batch 可以往高放（b=256、S=2k 时系统 10,123 token/s）。真正要守的是 TTFT 与**首子句**延迟——它随 batch 和上下文从 53 ms 涨到 278 ms。冲突点是长 prefill 插队给同批所有请求的 ITL 顶出台阶，解法是 chunked prefill、给语音请求单独的优先级队列与配额，并把语音的 SLO 写在首子句与 p95 上而不是平均 TPOT 上（[[inference-serving-09]]）。
- **追问**：怎么验证「确实变快了」？
  - 要点：三层缺一不可。① 分段埋点确认省下的是哪一段（否则无法排除「总延迟没变、只是把等待挪了个位置」）；② 轮次延迟的 p50/p95 分布与达标率对比，而不是均值；③ 体验侧指标——抢话率（agent 打断用户的比例，静音窗调短的直接副作用）、打断响应时间、任务完成率、重问率。用在线 A/B 与小流量灰度做因果判断，不要用上线前后对比（[[evaluation-09]]）。另有一个反直觉的验收点：首音延迟下降但用户满意度不升，通常是回答被压短或打断变多导致的。
- **追问**：采样率、帧长、codec 这些常数怎么定？
  - 要点：电话链路 8 kHz、语音模型 16 kHz（源文口径）；16 bit 单声道裸 PCM 是 16,000×16 = 256 kbps，20 ms 一帧是 320 样本 640 字节；Opus 在 24–32 kbps 就能保证语音质量，压缩约 8–10 倍；就算按电话链路 G.711 的每方向 64 kbps 估，10,000 路并发双向也是 10,000 × 2 × 64 kbps = 1.28 Gbps——带宽从来不是瓶颈，GPU 才是。帧长 20 ms 是延迟与包头开销的折中：拉到 40 ms 省一半包量但每个 VAD 判定粒度也粗一倍，且直接多 20 ms 延迟。
- **追问**：静音阈值能不能调成 200 ms 一劳永逸？
  - 要点：不能。它同时决定两件事：确认轮次结束的速度，和用户思考性停顿时被抢话的概率。源文的做法是让静音窗动态化——语义模型判为完整句时约 200 ms，判为不完整时放宽到 1.5–2 s；再用投机执行把这段等待从关键路径上挪走，两边的好处同时拿（[[multimodal-04]]）。
- **追问**：级联管线和原生 speech-to-speech 的预算差在哪？
  - 要点：差在结构，不在参数。级联的六段是串行叠加再加阈值等待，原生模型把 VAD 分段、文本中间模态与轮次切分一起去掉，Moshi 报告的理论延迟 160 ms、实测 200 ms 就是这个结构差异的结果（论文同时把级联管线「几秒的交互延迟」「以文本为中间模态丢失副语言信息」「显式说话人轮次切分无法处理重叠与插话」列为自己要解决的问题）。代价是可控性、可观测性与工具调用的成熟度（[[multimodal-05]]）。

## 公司变体

`asked_at` 里的两家公开产品方向不同，这题的落点也不同：

- **Sarvam AI**：印度语言语音栈（公开的语音模型线包含 Bulbul 语音合成与 Saaras 语音识别），产品形态以电话渠道为主。这会把延迟预算里的固定成本顶得更高：电话是 8 kHz 窄带链路，用户设备与网络质量分布很宽；code-switching（印地语与英语混说）与口音会让 ASR final 更晚、partial 翻转更多，于是「稳定 partial 就起 LLM」这个手段的收益与风险同时变大。这条线偏工程实现：链路常数要张口就来，预算表要能按分钟成本折算，降级路径（换小模型、降采样率、缩短回答）要提前设计。
- **ElevenLabs**：TTS 与语音 agent 平台方向。延迟预算的讨论天然压在 TTS 首包与流式 chunk 策略上——首块小、后续大的取舍，以及首包延迟与韵律自然度的交换；再叠上 barge-in 与端到端轮次延迟的测量口径。这条线同样偏工程实现，但要求把 TTS 侧的数字讲到可复算：首包、RTF、播放 buffer 与 underrun 之间的关系（[[multimodal-08]]）。

两者都不是纯推导型：即便被问到公式，也通常是为了支撑一个工程取舍（首块切多大、静音窗设多长、并发放到多少）。以上是基于公开技术材料与产品方向的侧重判断，具体题目以实际面试轮次为准。
