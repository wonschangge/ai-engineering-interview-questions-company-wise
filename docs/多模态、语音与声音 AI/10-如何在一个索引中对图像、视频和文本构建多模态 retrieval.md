## 一句话答案

> 「一个索引」不是把三种模态塞进同一个向量空间就完事，而是**一个统一的元数据/权限平面 + 多条并行的召回通道**。粗召回用双塔双编码器（CLIP / SigLIP 一类）把图像、视频帧、文本映射到同一空间做跨模态召回；同一份内容同时建「页面/帧图像」与「文本块」两条索引，用只依赖排名的 RRF 融合，避免跨编码器的分数尺度问题；重排用单塔 cross-encoder 或晚交互（ColPali 式的多向量 + MaxSim）；视频额外做帧采样、时序聚合与「粗召回片段 → 多模态模型精读」的两阶段。所有重量级编码必须离线预计算，索引体积的成本主要来自图像与视频这一侧。

## 面试官在考什么

- **能不能给出架构骨架并说清「可预计算性」**：双塔的文档侧可离线编码，单塔必须把 query 与文档拼在一起现场过模型，晚交互介于两者之间（文档侧离线出多向量，打分时还要做 MaxSim）。这一条直接决定了哪条路线能做召回、哪条只能做重排。
- **是否理解「一个索引」在工程上意味着什么**：模态路由、过滤下推、多租户与权限、增量更新、编码器版本一致性。只答「用 CLIP 编码，扔进向量库」区分不出水平。
- **视频有没有被当成「更大的图像」**：帧采样率、时序聚合、检索粒度、两阶段精读、时间定位的单独评测，这几条是本题的分水岭（[[multimodal-02]]）。
- **融合是否知道分数不可比**：CLIP 的 cosine 与 BM25 的分数分布完全不同，直接加权求和约等于只用其中一路；要能说出 RRF 或分位数归一化各自解决什么。
- **成本与合规意识**：图像/视频编码远比文本贵，多向量索引体积比单向量大两个数量级；人脸、声纹、受版权保护的素材检索有额外约束。

**常见错误答案**

- 「用 CLIP 把图像和文本编码到同一个空间，一个向量库就够了。」单向量 + 全局池化撑不起细粒度检索：文档里的表格数字、小字号 OCR 内容会被池化平均掉，这正是晚交互方案要解决的问题。
- 「向量库里加一个 `modality` 字段做过滤就是多模态检索。」过滤是约束不是召回；而且把过滤放在检索之后会把候选打空（见下文的选择率算例）。
- 「视频就是逐帧图像。」逐帧检索没有时间概念，答案里既不会有「第几分钟」，也会被同一镜头的几百个近重复帧淹没排序。

## 原理与推导

### 三条架构路线

**① 统一嵌入空间（双塔 / bi-encoder）。** 图像塔 $f_I$ 与文本塔 $f_T$ 各自输出 $d$ 维向量，训练目标是让配对样本的相似度高于非配对样本。CLIP 的做法是对一个 batch 内的 $B\times B$ 相似度矩阵做对称 softmax 归一化：

$$
\mathcal{L}_{\text{CLIP}}=-\frac{1}{2B}\sum_{i=1}^{B}\left[\log\frac{e^{s_{ii}/\tau}}{\sum_{j}e^{s_{ij}/\tau}}+\log\frac{e^{s_{ii}/\tau}}{\sum_{j}e^{s_{ji}/\tau}}\right]
$$

其中 $s_{ij}=\langle \hat f_I(x_i),\hat f_T(y_j)\rangle$ 是归一化后的内积，$\tau$ 是温度。这个式子要求跨样本的全局归一化，所以损失与 batch size 强耦合：batch 越小，负例越少，梯度越噪。CLIP 的口径是 4 亿（图像、文本）对训练，在 30 多个已有视觉数据集上做零样本迁移（覆盖 OCR、视频动作识别、地理定位与多种细粒度分类），并在 ImageNet 零样本上追平原始 ResNet-50 且不使用它的 128 万训练样本。

SigLIP 把 softmax 换成成对 sigmoid，只在单个 (图像, 文本) 对上算损失，不需要看到全局相似度矩阵：

$$
\mathcal{L}_{\text{SigLIP}}=-\frac{1}{B}\sum_{i,j}\log\sigma\!\left(z_{ij}\,(t\, s_{ij}+b)\right),\qquad z_{ij}=\begin{cases}+1,&i=j\\-1,&i\neq j\end{cases}
$$

$t$、$b$ 是可学的温度与偏置。好处是**解耦了 batch size 与损失**：小 batch 也不退化，大 batch 还能继续加。论文口径是配合 Locked-image Tuning、只用 4 张 TPUv4 训练两天达到 84.5% 的 ImageNet 零样本准确率，并且把 batch 推到 100 万后发现收益迅速递减、32k 已足够。检索视角下这条结论比准确率更重要：**对比学习的目标函数不再逼着你把 batch 堆到显存上限**。

图像侧的机制：原始像素只是颜色数值，不含语义；图像塔的浅层响应边缘、中层响应部件、深层响应物体，末尾把这个层级摘要压成一个定长向量，于是「相似含义的图像落得近」。所以文搜图、图搜图、图搜文共用同一套索引，零样本分类只是把类别名当 query 文本来检索。

**② 单塔融合（cross-encoder）。** 把 query 与文档拼成一个序列过同一个模型，中间层就做了跨模态交互，精度上限最高；代价是**每个 (query, 文档) 对都要一次完整前向**，文档侧无法预计算。$N$ 个候选、每条 $L$ 个 token 的成本是 $O(NL)$ 而不是双塔的「每文档一次离线编码 + 每 query 一次在线编码」。因此它只能接在召回之后做重排（[[rag-03]]），不能当索引本身。

**③ 多向量 / 晚交互。** 文档不再压成一个向量，而是保留 $\lvert d\rvert$ 个 token 级向量，打分时对每个 query 向量取最大匹配再求和：

$$
\text{score}(q,d)=\sum_{i=1}^{\lvert q\rvert}\max_{j=1}^{\lvert d\rvert}\big\langle E_q^{(i)},E_d^{(j)}\big\rangle
$$

这个 MaxSim 让 query 的每个词各自去文档里找最佳落点，池化损失被推迟到打分阶段。ColPali 把这条路线直接用在**文档页面的图像**上：把页面当图像编码成多向量嵌入、用晚交互匹配，并发布了页面级检索基准 ViDoRe（跨领域、跨语言、多种实际场景）。论文摘要的口径是它在 ViDoRe 上大幅超过「先从页面里解析文本再检索」的现代流程，同时**更简单、更快、端到端可训练**。这条路线对表格、多栏、图表密集的文档尤其重要，因为它绕过了脆弱且冗长的版面解析（[[rag-10]]）。

### 索引设计

- **模态到向量的映射。** 图像、视频帧、文本各自有编码器，是否落到同一空间是一个显式选择：图像与文本放同一空间才能文搜图；若还要纳入音频，可参考 ImageBind 的结论——**不必凑齐所有模态的两两配对数据，只用与图像配对的数据就足以把六个模态（图像、文本、音频、深度、热成像、IMU）绑进一个联合嵌入空间**，从而支持跨模态检索与模态的向量算术组合。工程含义是：新增模态的边际成本主要在它自己那一塔与配对数据上，不在重训所有两两组合。
- **同一内容建多路索引。** 一份 PDF 既建「页面图像多向量」索引，也建「解析出的文本块单向量」索引；一段视频既建帧/片段向量索引，也建字幕与转写的文本索引。查询时多路并发召回，再用只依赖排名的 RRF 融合，这样既拿到细粒度版面信息，又保留文本侧的精确串与关键词能力（[[rag-02]]）。
- **过滤与多租户。** 权限、租户、时间范围这类约束必须**下推到每一路召回**，不能融合之后再过滤。设过滤选择率为 $s$，post-filter 在 $k=10$ 时只剩约 $10s$ 条；$s=1\%$ 时期望 0.1 条，要把候选深度放大到 $10/s=1000$ 才凑够，延迟上一个量级（[[rag-09]]、[[rag-08]]）。常见折中是按租户/时间分区成多个小索引再路由。
- **元数据 schema 要一次定好**：模态、来源 URI、父文档 id、页码或帧号与起止时间戳、权限标签、编码器名与版本、内容指纹。前四项决定结果能不能被引用与定位，后两项决定增量更新与回滚（[[rag-11]]、[[rag-12]]）。
- **版本一致性是硬约束**：不同编码器产生的向量不在同一空间，同一索引里混两个版本等于随机排序。「换模型」= 新建索引全量重编码 + 别名切换，不能原地增量。

### 视频检索的特殊处理

- **帧采样率与任务对齐。** 先问「任务需要看到多快的变化」：内容问答 1 fps 常常够用，动作与事件定位需要 4–8 fps。成本对帧率线性，这一刀砍下去最有效。
- **时序聚合。** 帧级向量要聚合成片段级或视频级向量才能跨片段排序：均值/最大池化便宜但会稀释短事件，时序注意力或轻量时序 Transformer 更准但要训练。检索粒度也要选：镜头（shot）、固定时长片段、还是整片——粒度越粗语义越稳、时间定位越糊。
- **两阶段。** 粗召回用便宜的帧/片段向量取候选片段，再用多模态模型精读（[[multimodal-02]]、[[rag-03]]）。三十分钟素材按 1 fps 就是 184 万视觉 token、约 563 GiB KV、单卡 prefill 652 s，把它整段喂给大模型在成本上不可行，下一节的账说明了这一点。
- **时间定位要单独评。** 检索指标（片段是否进了 top-$k$）与定位指标（预测时间区间与真值的 IoU 是否过阈值、区间回归误差）是两件事，混在一起报会掩盖「召回了但定位偏了」的失败模式。

### 跨模态融合的坑

不同编码器的相似度**分数尺度不可比**：CLIP 的 cosine 集中在很窄的区间，BM25 的分数无上界且随 query 长度变化，页面多向量的 MaxSim 分数又随 query 长度与页面向量数增长。直接加权求和会让量纲大的那一路完全主导。两种可行解法：① RRF 只用排名，天然免疫尺度问题；② 分位数/秩归一化后再加权，但要在**同一模态内**做归一化，且注意只在单路出现的文档缺另一路分数时怎么补。此外，同一查询在不同模态上的最优权重不同（「找一张蓝色羽绒服的图」与「找讨论羽绒服保暖性的段落」是两类意图），需要按查询类型路由或在标注数据上学习融合权重，而不是全局固定一组权重。

### 评测、成本与合规

- **评测要分任务**：文搜图、图搜图、文档页检索、视频片段检索、时间定位各自一套集合与指标，按场景分层报告，并用一个 regression gate 决定能否上线（[[evaluation-04]]）。
- **成本结构**：图像/视频编码贵、文本编码便宜；帧向量与页面多向量的索引体积远大于文本向量。因此默认架构是「离线预编码 + 缓存 + 增量更新」，在线只编码 query（[[rag-11]]）。
- **合规**：人脸、声纹、受版权保护的图像与视频在检索与存储上都有额外约束，人脸聚类这类能力不能顺手加进通用检索；结果必须能回溯到来源与权限（[[safety-07]]、[[safety-09]]）。

## 数值与代码验证

统一口径：编码器取 CLIP 的 ViT-B/32（$7\times7+1=50$ 个 token，512 维输出）、ViT-B/16（197 token）与 ViT-L/14（$16\times16+1=257$ 个 token，768 维输出），FLOPs 按「线性层与 attention 矩阵乘的 $2\times$MACs」复算，忽略 LayerNorm、softmax、激活与 patch embed；复算值 4.29 / 80.86 GMACs 与公开实现常报告的 4.4 / 80.9 GMACs 一致，差异来自是否计入 patch embed 与分类头。硬件取 H100 SXM 口径（bf16 稠密 989 TFLOP/s、HBM3 3.35 TB/s、80 GB，与本仓库其它专题一致），MFU 按 **40% 的明示假设**折算，即有效 395.6 TFLOP/s。KV cache 沿用 LLaMA-3-70B（80 层、8 个 KV 头、head_dim 128、bf16）的每 token 320 KiB。视觉 token 按 448×448 输入、14 像素 patch 计，即每帧 $32\times32=1024$ 个 token，与 [[multimodal-02]] 同一口径。晚交互的每页向量数与向量维度按「32×32 patch 网格、每 patch 投影到 128 维」这一**通用记账口径**设定（不取自 ColPali 论文的具体数字，用于说明量级）。

**表 1：单帧编码成本（复算）**

| 编码器 | 每帧 FLOPs | 每帧 MACs | 40% MFU 单帧算力 | 1 万小时 @1 fps 的纯算力下界 |
| --- | --- | --- | --- | --- |
| ViT-B/32@224（512 维） | 8.59 GFLOPs | 4.29 GMACs | 21.7 µs | $3.60\times10^7$ 帧 → 0.22 GPU·h |
| ViT-B/16@224（512 维） | 34.89 GFLOPs | 17.45 GMACs | 88.2 µs | 0.88 GPU·h |
| ViT-L/14@224（768 维） | 161.72 GFLOPs | 80.86 GMACs | 408.8 µs | 4.09 GPU·h |

这张表的读法是：**编码器前向在 Tensor Core 上便宜到可以忽略**（1 万小时视频按 1 fps 抽帧，ViT-B/32 一张 H100 十几分钟就算完），真实成本在视频解码、抽帧、预处理与 I/O 上，必须实测；能确定的只有「帧率与分辨率乘多少，这一侧就乘多少」。

| 表示 | 每帧字节 | 1 fps（$3.60\times10^7$ 帧） | 8 fps（$2.88\times10^8$ 帧） |
| --- | --- | --- | --- |
| 512 维 fp16 | 1 KiB | 36.9 GB（34.3 GiB） | 294.9 GB（274.7 GiB） |
| 512 维 int8 | 512 B | 18.4 GB | 147.5 GB |
| 768 维 fp16 | 1.5 KiB | 55.3 GB | 442.4 GB |
| HNSW $M=32$ 图边（$2M=64$ 个 4 字节邻居 id） | 256 B | 9.2 GB | 73.7 GB |

结论：1 fps 的帧索引刚好压在一台 64 GB 内存机器的边界上，8 fps 直接进入必须分片的规模；**帧采样率是最贵的旋钮**，它同时乘算力、索引体积与后续排序的噪声（同一镜头的近重复帧）。

| 片段 | 帧数 | 视觉 token | KV（70B 口径 320 KiB/token） | prefill $2NL$ | 8×H100 @40% MFU |

单卡口径下 30 s@1 fps 的 prefill 是 10.9 s，KV 是 9.38 GiB；60 s@8 fps 的 KV 已经超过单张 80 GB 卡的可用余量。这就是「两阶段」的量化理由：**精读只能发生在个位数候选上**，粗召回负责把候选从百万级压到十级。

**表 4：单向量与多向量的索引体积（$10^6$ 个页面）**

| 表示 | 每页字节 | $10^6$ 页 |
| --- | --- | --- |
| 单向量 768 维 fp16 | 1.5 KiB | 1.54 GB |
| 多向量 1024 个 × 128 维 fp16 | 256 KiB | 262 GB |
| 多向量 int8 | 128 KiB | 131 GB |

多向量的向量数是 1024 倍、维度是 $1/6$，净结果是**字节数约 171 倍**。这个体积决定了晚交互不能靠图索引兜住：$10^6$ 页 × 1024 个向量是约 $1.02\times10^9$ 个向量，按 $M=32$ 的 HNSW 图边（256 B/向量）再加 262 GB，完全不现实。

**表 5：MaxSim 的带宽账（$\lvert q\rvert=32$，每页 1024 个 128 维向量）**

| 规模 | MaxSim 算力 | 40% MFU 算力时间 | 读全部页面向量 | 纯带宽时间 |
| --- | --- | --- | --- | --- |
| $10^6$ 页（262 GB） | 8.39 TFLOPs | 21.2 ms | 262 GB | 78 ms |
| $10^7$ 页（2.62 TB） | 83.89 TFLOPs | 212.0 ms | 2621 GB | 783 ms |

每页的 MaxSim 是 $32\times1024$ 次 128 维点积，约 8.39 MFLOPs。真正的墙不是算力而是**索引装不进显存**：262 GB 远超 80 GB HBM，按 PCIe 50 GB/s 搬一遍要 5.2 s。所以晚交互也必须两级：先用单向量或质心/PQ 粗排把候选压到 $10^4$–$10^5$ 页（2.6–26 GB，纯带宽 0.8–7.8 ms，走 PCIe 是 52–524 ms），再对候选做 MaxSim。

| 文档 | BM25 原始 | CLIP cosine | 直接相加 | BM25 归一化 | cosine 归一化 | $\alpha=0.5$ 加权 |
| --- | --- | --- | --- | --- | --- | --- |
| A | 18.0 | 0.20 | 18.20 | 1.000 | 0.143 | **0.571** |
| B | 2.0 | 0.32 | 2.32 | 0.000 | 1.000 | 0.500 |
| C | 12.0 | 0.18 | 12.18 | 0.625 | 0.000 | 0.312 |
| D | 6.0 | 0.30 | 6.30 | 0.250 | 0.857 | 0.554 |

BM25 的跨度是 16.0，cosine 的跨度只有 0.14，相差约 114 倍：直接相加的排序与「只用 BM25」完全相同，cosine 这一路等于不存在；归一化加权后 B 从末位升到第三。注意 cosine 的 0.18–0.32 是 CLIP 类模型在真实库上的典型窄区间，这也是 RRF 更省心的原因。

**表 7：同一个页面在两条索引上都靠前时的 RRF 复算（$k=60$，口径与 [[rag-02]] 一致）**

| 页面 | 文本索引名次 | 页面图像索引名次 | RRF | 只用文本索引的名次 |
| --- | --- | --- | --- | --- |
| Doc-7 | 1 | 2 | **0.032522** | 1 |
| Doc-3 | — | 1 | 0.016393 | 未召回 |
| Doc-2 | 2 | — | 0.016129 | 2 |
| Doc-9 | 3 | — | 0.015873 | 3 |
| Doc-5 | — | 3 | 0.015873 | 未召回 |

Doc-3 在文本索引里根本没被召回（表格数字没被解析出来），靠页面图像那一路进了候选并排到第二——这就是多路索引的意义。$k$ 的作用可以量化：$k=60$ 时 rank 1 与 rank 100 的分差只有 2.62 倍（$k=0$ 时是 100 倍），所以「两路都靠前」比「一路第一」更值钱。

**表 9：一条查询的在线延迟预算（串行段相加，并发段取最大）**

| 阶段 | 口径 | 成本 |
| --- | --- | --- |
| query 文本塔编码（110M × 32 token） | 7.04 GFLOPs | 17.8 µs 纯算力；实测由 kernel 启动与批处理支配，毫秒级 |
| query 图像编码（ViT-B/32） | 8.59 GFLOPs | 21.7 µs，同上 |
| 三路召回（文本 / 帧 / 页面多向量） | 并发执行 | 取最慢的一路，不相加 |
| RRF 融合 200–1000 条候选 | CPU 排序 | 小于 1 ms |
| cross-encoder 重排 100 条 × 288 token | 6.34 TFLOPs | 16.0 ms（40% MFU；100% MFU 下界 6.4 ms） |
| VLM 精读 1 个 30 s@1 fps 片段 | 4.30 PFLOPs | 10.9 s，单卡不可交互，必须限流或异步 |

重排那一路的 6.34 TFLOPs 与 [[rag-02]] 用同一公式复算的结果一致，可互相校验。表里的文本塔编码与 cross-encoder 重排都按 110M 参数（BERT-base 量级）口径估，换成 CLIP 文本塔这类更小的编码器时按 $2PL$ 线性缩小。

```python
KiB, GiB, GB = 1024, 1024**3, 1e9
H100_BF16, H100_BW, MFU = 989e12, 3.35e12, 0.40      # H100 SXM 规格 + 明示的 40% MFU 假设
EFF = H100_BF16 * MFU
KV70 = 2 * 80 * 8 * 128 * 2                          # LLaMA-3-70B GQA-8 bf16：327680 B/token

def vit_flops(tok, layers, d, d_mlp, heads):
    per = 3*2*tok*d*d + 2*heads*tok*tok*(d//heads)*2 + 2*tok*d*d + 2*(2*tok*d*d_mlp)
    return layers * per

print(vit_flops(50, 12, 768, 3072, 12) / 1e9)        # 8.59 GFLOPs  ViT-B/32
print(vit_flops(257, 24, 1024, 4096, 16) / 1e9)      # 161.72       ViT-L/14

frames = 10_000 * 3600 * 1                           # 1 万小时 @1 fps
print(frames, frames * 512 * 2 / GB, frames * 4 * 2 * 32 / GB)   # 3.6e7 帧 / 36.9 GB / 9.2 GB 图边

for secs, fps in ((15, 1), (30, 1), (30, 4), (60, 8)):
    tok = secs * fps * 1024                          # 448x448 / 14px patch
    print(secs, fps, tok, tok * KV70 / GiB, 2 * 70e9 * tok / EFF)  # token / GiB / 单卡秒数

page = 32 * 32 * 128 * 2                             # 1024 向量 x 128 维 fp16
print(page / KiB, 10**6 * page / GB)                 # 256 KiB/页  ->  262 GB
macs = 32 * 1024 * 128
print(2 * macs * 1e6 / 1e12, 10**6 * page / H100_BW)  # 8.39 TFLOPs 算力 / 78 ms 带宽

def rrf(rankings, k=60):
    s = {}
    for r in rankings:
        for doc, rank in r.items():
            s[doc] = s.get(doc, 0.0) + 1.0 / (k + rank)
    return dict(sorted(s.items(), key=lambda kv: -kv[1]))

print(rrf([{"Doc-7": 1, "Doc-2": 2, "Doc-9": 3}, {"Doc-3": 1, "Doc-7": 2, "Doc-5": 3}]))
```

## 常见追问

- **追问**：为什么 CLIP 类模型在文档 OCR、表格数字上弱，晚交互却能奏效？
  - 要点：单向量要把页面里所有内容池化进一个定长向量，表格数字、小字号文本、版面位置这些信号在平均中被稀释；而且文字识别本身需要高分辨率细节，全局池化把 patch 级信息丢掉了。晚交互保留每个 patch 的向量，query 的每个 token 各自去页面上找最佳落点，等效于「带着 query 去看局部」。这正是 ColPali 把页面图像直接编码成多向量并用 MaxSim 匹配的动机，它同时省掉了脆弱且冗长的版面解析（[[rag-10]]）。
- **追问**：多模态检索要不要和文本检索共用一个向量库？
  - 要点：按规模与过滤需求决定，而不是按「统一架构更好看」。共用一套的好处是过滤、权限、多租户只实现一遍，融合时排名天然可比；代价是不同模态的向量维度、量化策略、索引参数往往不同（图像 512/768 维，文本可能 1024 维，页面多向量是 $10^3\times128$），硬塞进同一张表会牺牲各自的 recall-latency 工作点。规模到千万级以上、或某一路需要不同的 ANN 结构时，分区/分索引 + 查询时路由更实际。
- **追问**：视频的时间定位怎么评？
  - 要点：与片段检索分开评。检索用「真值片段是否进了 top-$k$」，定位用预测时间区间与真值区间的 IoU 是否过阈值（如 0.3/0.5/0.7 分别报）、以及平均 IoU。分开报才能区分「没召回」和「召回但定位偏」。采样率直接决定定位分辨率的下界：1 fps 抽帧不可能给出亚秒级边界，报指标时必须带上采样率与片段粒度。
- **追问**：帧采样率怎么定？
  - 要点：从任务需要的时间分辨率倒推，而不是从硬件预算倒推。内容问答 1 fps 通常足够，动作识别与事件边界需要 4–8 fps。表 2 给出的账是线性的：帧率翻 8 倍，索引体积、编码算力与近重复帧的数量同时翻 8 倍。折中做法是「低帧率索引 + 命中后按原始帧率回读」。
- **追问**：编码器升级了怎么办？
  - 要点：不能原地增量。向量空间由编码器决定，新旧向量混在一个索引里相似度没有意义，必须新建索引、离线全量重编码、用别名原子切换，并保留旧索引一段时间以便回滚。元数据里要记编码器名与版本，查询时按版本路由；[[rag-11]] 的索引新鲜度机制要覆盖「重编码」这个比增量写入贵得多的操作。
- **追问**：多向量晚交互和「单向量召回 + cross-encoder 重排」怎么选？
  - 要点：看瓶颈在哪。单向量召回 + 重排的实现简单、索引小、延迟可预测，适合语料以自然图像为主、文本语义足够表达查询的场景；晚交互把细粒度能力放进了召回阶段，对版面密集、需要看局部细节的文档更强，代价是索引体积与两步打分（表 4、表 5）。两者可以叠加：单向量粗排 → 晚交互 MaxSim → cross-encoder 精排，每一级的候选数按预算收敛。
