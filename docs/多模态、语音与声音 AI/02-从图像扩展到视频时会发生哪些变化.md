## 一句话答案

> 视频不是「更大的图像」，而是**上下文与显存问题**。token 数等于**帧数 × 每帧 token**：448×448、14 像素 patch 的单帧是 $\lfloor 448/14\rfloor^2 = 32\times32 = 1024$ 个 patch token；8 fps 采 1 秒就是约 8k token，10 分钟视频即使只按 1 fps 也有 600 帧 ≈ 61 万 token。按 LLaMA-3-70B 的 320 KiB/token 口径，这就是 **187.5 GiB KV cache**——单张 80 GB 卡装不下，attention 还随序列长度二次增长。
> 真正变了的是六件事：**时间维度的位置编码与帧间建模、帧采样策略、token 缩减、音视频联合、长上下文训练与推理的系统成本、评测口径从「描述这一帧」变成「推理时间上的顺序与因果」**。
> 工程答案也落在这六处：控帧率、控每帧 token、分层摘要、两阶段检索、预算护栏、视觉前缀缓存——而不是「开一个更长的上下文窗口」。

## 面试官在考什么

- **会不会做 token 与显存估算**（本题的主要分差）：能否一次算出「帧数 × 每帧 token × 每 token KV」，并主动交代口径——patch 边长、是否做了 token 合并、KV 精度、GB 还是 GiB。
- **是否理解时间维度不是「多几张图」**：时间信息通过什么进模型（位置编码 / 文本时间戳 / 3D tube）、帧间关系在哪一层建模。
- **采样率与任务是否对齐**：知不知道采样率的上界由「任务需要看到多快的变化」决定，而不是越高越好。
- **有没有分层与两阶段的意识**：把长视频问题转成文本摘要问题或检索问题，先粗排再精读，而不是把所有帧硬塞进上下文。
- **是否算到系统侧**：prefill 的二次项、decode 的 KV 带宽、长视频对并发数的挤压、以及长上下文训练需要的序列并行。

常见错误答案：

- 「视频就是多了个时间维度，模型多接几帧、上下文开大点就行」——漏掉成本项，也说不清时间信息怎么进模型。
- 只说「上长上下文模型」：128k 窗口按 1 fps、每帧 1024 token 只够 **2.1 分钟**视频，而单条 40 GiB 的 KV 让一个 8×80 GB 节点的并发上限掉到十条上下。
- 把帧率当成单调调优旋钮：动作识别确实要吃 8 fps 量级，但内容问答用 8 fps 只是烧钱——10 秒 8 fps 就已经是 25 GiB KV。

## 原理与推导

### 1. 先算账：从「一张图多少 token」到「一段视频多少 token」

四步，每一步只引入一个变量：

1. **patch 化**：视觉编码器把一帧切成 $P \times P$ 的不重叠 patch，patch 数即 token 数（[[multimodal-01]] 的口径）：

$$N_{\text{frame}} = \left\lfloor \frac{H}{P} \right\rfloor \cdot \left\lfloor \frac{W}{P} \right\rfloor$$

$448 \times 448$、$P=14$ 时 $N_{\text{frame}} = 32 \times 32 = 1024$；换成 LLaVA 式的 $336^2$ 则是 $24 \times 24 = 576$。

2. **时间采样**：以 $f$ fps 采 $T$ 秒，得到 $F = f \cdot T$ 帧。

3. **总量**：

$$N_{\text{video}} = F \cdot N_{\text{frame}} = f \cdot T \cdot \left\lfloor \frac{H}{P} \right\rfloor \left\lfloor \frac{W}{P} \right\rfloor$$

对帧数、对分辨率都是**严格线性**的，没有任何折扣：分辨率翻倍 token 变 4 倍，时长翻倍 token 变 2 倍。

4. **KV cache**：视觉 token 与文本 token 走同一套 attention，就按同一口径计费。LLaMA-3-70B（80 层、GQA 8 个 KV 头、head_dim 128、bf16）单 token KV 是 $2 \times 80 \times 8 \times 128 \times 2 = 327{,}680$ B $= 320$ KiB，与 [[llm-internals-02]]、[[inference-serving-03]] 一致。

代入：$600 \text{ 帧} \times 1024 = 614{,}400$ token $\times 320$ KiB $= 201.3$ GB $= 187.5$ GiB。**单序列就超过一张 80 GB 卡的容量**；取整的 60 万 token 版本是 183 GiB，两者只差四舍五入的口径。这也是为什么 [[multimodal-01]] 把「长视频」列为该专题的核心矛盾。

### 2. 第一步缩减：每帧能压到多少 token

Qwen2-VL 的做法给出一个可复算的参考点：ViT 输出后接一个 MLP，把相邻 $2 \times 2$ 个 token 压成 1 个（pixel-shuffle 式合并）。论文口径：$224 \times 224$、`patch_size=14` 的图像被压缩成 **66 个 token**——按第 1 节的公式是 $\lfloor 224/14 \rfloor^2 / 4 + 2 = 64 + 2 = 66$（2 个是 vision 起始/结束特殊 token），公式与论文数字对得上。同一套算法用在 $448^2$ 上是 $256 + 2 = 258$。

**口径提醒**：下文表格统一按「不含特殊 token」计（$448^2$ 合并后每帧 256）。合并把每帧成本降 4 倍，是视频预算里的第一个旋钮，代价是空间分辨率下降，通常需要至少微调。

### 3. 时间维度：位置编码与帧间建模

把帧直接当成更多 token 拼起来，会先撞上位置编码的问题：1D-RoPE 给第 $k$ 帧的 token 分配连续递增的位置 ID，位置 ID 随帧数线性增长，既超出训练时的 ID 范围，又丢掉了「帧内二维结构」——同一帧里上下相邻与左右相邻无法区分，跨帧同一空间位置与帧内相邻也混在一起。

M-RoPE（Qwen2-VL，论文口径）把 rotary embedding 分解成 **temporal / height / width 三个分量**：

- 文本：三个分量取相同位置 ID，退化成 1D-RoPE；
- 图像：所有视觉 token 的 temporal ID 相同，height / width 按 token 在帧内的位置取值；
- 视频：temporal ID **逐帧递增**，height / width 与图像一致；
- 多模态混排：每个模态的位置编号从前一模态的最大 ID 加一开始。

副产物是图像与视频用到的位置 ID 数值变小，因此更容易外推到比训练更长的序列。另一种同样常见的做法是把时间信息写进 prompt 文本（「第 12 秒处……」）——不占位置编码、可被语言模型直接引用，代价是占 token 且精度受采样率限制。工程上二者常并用：文本给秒级绝对时间戳，位置编码给帧序。

**帧间建模**有三条路线，成本分布不同：

- **3D tube / 3D 卷积**：Qwen2-VL 用 depth-2 的 3D 卷积把 2D patch 变成 3D tube，从而在序列长度不变的前提下多处理帧；
- **时序 attention**：所有帧 token 进同一条序列，帧间建模「免费」，成本全部落在上下文与 KV（见第 1 节）；
- **时序池化/聚合**：把帧级特征池化成片段级或视频级表示，上下文便宜，但需要额外的时序模块，且细节不可回溯。

### 4. 帧采样：采样率由「任务的最快变化」决定

- **均匀采样**：实现最简单，但会 aliasing——瞬时事件（进球、击掌）落在两帧之间就永远看不见。
- **关键帧 / 场景切分**：用帧间差、颜色直方图或帧 embedding 距离做 shot detection，把预算花在内容变化大的位置；对监控类长视频尤其有效。
- **采样率与任务对齐**：动作识别、手语、体育解说的信息在帧间，需要 8 fps 量级的采样；内容问答、视频摘要 1 fps 甚至更低通常够用。Qwen2-VL 训练时按 2 fps 采样每段视频，并动态调整每帧分辨率、把单个视频的总 token 限制在 16384（论文口径）。
- **反向设计**：先由 SLO 和上下文窗口定出 token 预算 $B$，再在帧率、分辨率、合并率之间分配，而不是先定帧率再抱怨窗口不够。

### 5. token 缩减与预算护栏

四个旋钮：**空间合并/池化**（每帧 token ÷ 合并倍率的平方）、**时间合并**（相邻帧特征合并）、**降低每帧分辨率**（动态分辨率下每帧 token 数可变）、**降低帧数**。前三个动一帧的信息量，第四个动时间分辨率，取舍不同。

动态分辨率带来一个工程副作用：**同一批里每条样本的序列长度不同**，按最长样本 padding 会浪费显存与算力，实践中按长度分桶（与 [[inference-serving-10]] 的批处理效率问题同源）。

**预算护栏**：给每次请求设视觉 token 上限 $B$，则帧数上界 $F \le B / N_{\text{frame}}$，超限就降帧或降分辨率；这个「预算 + 超限降级」的思路与 [[agents-09]] 里给 agent 设步数/成本上限是同一套工程习惯。

**两阶段**：先用便宜的帧级/片段级向量检索召回候选片段，再用多模态模型精读。粗排索引是一帧一个向量（几百帧只有 MB 级），精读才付 KV 的账——账见表 3，思路与 [[multimodal-10]] 中的两阶段 retrieval 一致，也把长视频问题转化为文本/片段级的 RAG 问题（[[rag-06]]）。

### 6. 音视频联合：画面不是唯一的信息源

- **便宜路径**：ASR 字幕加时间戳，与帧 token 交错放进 prompt。代价是 ASR 错误会传导到答案，且非语音事件（关门、掌声、警报）字幕里没有。
- **统一嵌入空间路径**：把音频编码到与图像、文本同一空间（[[multimodal-10]] 提到的多模态联合空间思路，ImageBind 式做法），检索与对齐都简单，代价是需要成对的训练数据、且细粒度时序对齐仍要靠时间戳。
- **结论**：字幕是性价比最高的一路先验，但它替换不了声学事件；要做「谁在什么语气下说了什么」，音频编码器与画面帧得同时进模型。

### 7. 系统成本：训练侧与推理侧各有一道坎

**训练侧**（LongVILA 论文摘要口径）：长上下文视觉语言模型需要算法与系统协同设计，其多模态序列并行（MM-SP）在 **256 张 GPU 上训练 200 万 token 上下文且不使用梯度检查点**，把可处理帧数从 **8 帧提升到 2048 帧**；在 **6000 帧（超过 100 万 token）**的 needle-in-a-haystack 上达到 **99.8%** 准确率；MM-SP 比 ring-style 序列并行快 **2.1–5.7 倍**，比 Megatron 的 context + tensor 混合并行快 **1.1–1.4 倍**。

**推理侧**两道坎，都在本节算清楚（复算见下节表 2）：

- **prefill 的二次项**：线性项是 $2PS$（$P$ 为参数量），因果 attention 的二次项约 $2 L S^2 d_{\text{model}}$，两者在 $S^{*} = P/(L\,d_{\text{model}}) \approx 1.07\times10^{5}$ token 处相等。61 万 token 的视频，二次项已占 prefill 的 85%。
- **decode 的 KV 带宽**：每生成一个 token 都要把整份 KV 从 HBM 读一遍。187.5 GiB 对应单卡等效 60.1 ms/token；KV 读取量在 42.7 万 token 处就超过权重读取量（140 GB），也就是说**约 7 分钟以上的视频（1 fps、每帧 1024 token），每步瓶颈从权重变成 KV**。这直接限制了吞吐与并发，机制见 [[inference-serving-03]]。

### 8. 评测：从「描述」到「时序推理」

图像题的评测量的是「看见了什么」，视频题要额外测「先后、因果、计数、定位」：动作顺序、事件因果、跨帧计数、以及 temporal grounding（答案要带时间区间）。描述类指标与人类判断的相关性弱，所以视频对话模型需要专门的量化评测：Video-ChatGPT 的论文口径给出了 **10 万条视频指令对**用于训练，并提出了一套面向视频对话模型的**量化评测框架**，把回答拆成多个维度打分——这也说明「视频理解好不好」不能只看一个数。

评测还要**分层报告**：帧级（这一帧有什么）、片段级（这段发生了什么）、全片级（整体结论）。混在一起报，会把「模型没看到那几帧」（采样问题）和「模型看到了但不会推理」（建模问题）混成一个分数。

## 数值与代码验证

统一口径：KV 按 LLaMA-3-70B（80 层、8 个 KV 头、head_dim 128、bf16）的 327,680 B = 320 KiB / token；算力按 H100 SXM bf16 稠密 989 TFLOPs、HBM3 带宽 3.35 TB/s；prefill 有效算力按 8 卡 × 45% MFU = 3.56 PFLOPS（与 [[inference-serving-15]]、[[multimodal-01]] 同一口径）；$\text{GiB} = 1024^3$ B，带宽用十进制 TB/s。

**表 1：视频的 token 账与 KV 账**（$P=14$；合并行指 2×2 相邻合并，不含 2 个特殊 token）

| 场景 | 帧数 | 每帧 token | 总 token | 单序列 KV |
| --- | --- | --- | --- | --- |
| 单帧 448²，未合并 | 1 | 1,024 | 1,024 | 320 MiB |
| 单帧 448²，2×2 合并 | 1 | 256 | 256 | 80 MiB |
| 8 fps × 1 s | 8 | 1,024 | 8,192 | 2.50 GiB |
| 8 fps × 10 s | 80 | 1,024 | 81,920 | 25.0 GiB |
| 1 fps × 10 min | 600 | 1,024 | 614,400 | **187.5 GiB** |
| 1 fps × 10 min，2×2 合并 | 600 | 256 | 153,600 | 46.9 GiB |
| 0.5 fps × 10 min，2×2 合并 | 300 | 256 | 76,800 | 23.4 GiB |
| 1 fps × 10 min，224² + 合并（66 token/帧） | 600 | 66 | 39,600 | 12.1 GiB |

结论都从这张表出：**单帧 320 MiB 的 KV 听起来很小，乘上 600 帧就是 187.5 GiB**；而把帧降到 66 token 后同一段视频只剩 12.1 GiB——中间 15.5 倍的差距，就是帧率、分辨率与合并这三个旋钮能腾出的空间。表里「未合并」与「合并」两行正好差 4 倍：报预算前必须先声明口径（是否合并、是否含特殊 token），否则同一段视频的 token 与 KV 会对不上。

**表 2：算力与带宽账**（$P = 70\times10^9$，$L=80$，$d_{\text{model}} = 64 \times 128 = 8192$）

| 量 | 公式 | 结果 |
| --- | --- | --- |
| bf16 权重 | $2P$ | 140.0 GB |
| 10 分钟视频 prefill 线性项 | $2PS$ | 86.0 PFLOPs |
| 同上 attention 二次项 | $2LS^2d_{\text{model}}$ | 494.8 PFLOPs（占 85.2%） |
| prefill 合计（8×H100 @45% MFU） | $(86.0+494.8)/3.56$ | **163 s** |
| 二次项 = 线性项的临界长度 | $P/(L\,d_{\text{model}})$ | 106,812 token |
| decode 单步读 KV（单卡等效） | $S \cdot 320\ \text{KiB} / 3.35\ \text{TB/s}$ | 60.1 ms → 16.6 token/s |
| decode 单步读权重 + KV（单卡等效） | $(140 + 201.3)\ \text{GB} / 3.35$ | 101.9 ms → 9.8 token/s |
| TP=8：每卡 KV 25.17 GB + 权重 17.5 GB | $42.67/3.35$ | 12.7 ms → 78.5 token/s（未计 all-reduce） |
| decode attention 算力（每步，8 卡节点口径） | $4LSd_{\text{model}}$ | 1.61 TFLOPs → 0.45 ms（带宽是瓶颈） |
| KV 读取量超过权重读取量 | $140\ \text{GB} / 320\ \text{KiB}$ | 427,246 token ≈ 417 帧 ≈ 7.0 min |

表 2 里最该背下来的一行是 427,246：**视频超过约 7 分钟（1 fps、每帧 1024 token），decode 每步搬的字节里 KV 比权重还多**——这正是长视频在推理侧的根本代价，也是 [[inference-serving-03]] 的 PagedAttention 只能解决碎片、不能解决总量的原因。

**表 3：把 10 分钟视频压进 128k 窗口（131,072 token）的取舍**

| 手段 | 效果 | 总 token | 单序列 KV | 占 128k 窗口 |
| --- | --- | --- | --- | --- |
| 基线：1 fps、448²、不合并 | — | 614,400 | 187.5 GiB | 4.69×（超窗口） |
| 空间 2×2 合并 | 每帧 1024 → 256 | 153,600 | 46.9 GiB | 1.17×（仍超窗口） |
| 合并 + 降到 0.5 fps | 帧数 600 → 300 | 76,800 | 23.4 GiB | 0.59×（进窗口） |
| 合并 + 降分辨率到 224² | 每帧 66 token | 39,600 | 12.1 GiB | 0.30× |
| 两阶段：粗排 600 帧向量 + 精读 top-32 帧 | 索引 1.2 MiB（600 帧 × 1024 维 fp16）；精读 32,768 token | 32,768 | 10.0 GiB | 0.25× |
| 32k 窗口的等价上限 | 32,768 token | 32,768 | 10.0 GiB | 32 帧 = 32 s @1 fps |
| 128k 窗口的等价上限 | 131,072 token | 131,072 | 40.0 GiB | 128 帧 = 2.1 min @1 fps |

最后两行是对「上长上下文模型就行」的直接回答：**128k 窗口在 1 fps、每帧 1024 token 的口径下只装得下 2.1 分钟视频**。容量侧同样不宽松：8 张 80 GB 标称合计 640 GB = 596 GiB，扣掉 140 GB（130.4 GiB）权重后约 466 GiB，40 GiB 的单序列 KV 只能放 11 条（466/40 = 11.6 取整，未扣工作区与碎片）；换成 10 分钟全量视频的 187.5 GiB，整个节点只剩 2 条的位置。要更长的视频，只能动表 3 前三行的旋钮，或者走两阶段。

```python
# 复算表 1、表 2、表 3 的全部数字
P = 70e9                                        # LLaMA-3-70B 参数量
L, HQ, HKV, DH = 80, 64, 8, 128                 # 层数 / Q 头 / KV 头 / head_dim
D_MODEL = HQ * DH                               # 8192
KV_B = 2 * L * HKV * DH * 2                     # 327680 B = 320 KiB / token
BF16, BW, MFU = 989e12, 3.35e12, 0.45           # H100 SXM 规格与本仓库 MFU 口径
NODE = 8 * BF16 * MFU                           # 8 卡有效算力 3.56 PFLOPS
GIB = 1024 ** 3

frame_tokens = lambda h, p=14, merge=1: (h // p) ** 2 // (merge ** 2)
kv = lambda tok: tok * KV_B / GIB

print("448^2 未合并", frame_tokens(448), "合并后", frame_tokens(448, merge=2))
print("224^2 合并 + 2 特殊 token =", frame_tokens(224, merge=2) + 2)   # 66，与论文一致

for frames, tok in [(8, 1024), (80, 1024), (600, 1024), (600, 256), (300, 256)]:
    n = frames * tok
    print(f"{frames:>4d} 帧 x {tok} tok: {n:>9,d} token, KV {kv(n):7.2f} GiB")
#  600 帧 x 1024 tok: 614400 token, KV  187.50 GiB
print("取整 60 万 token 口径:", round(600_000 * KV_B / GIB, 1), "GiB")   # 183.1

W = 2 * P                                       # 140.0 GB
print("KV 读取超过权重读取的长度:", round(W / KV_B), "token")            # 427246
S = 614_400
print("prefill 线性/二次/合计 PF:",
      round(2 * P * S / 1e15, 1), round(2 * L * S * S * D_MODEL / 1e15, 1),
      round((2 * P * S + 2 * L * S * S * D_MODEL) / 1e15, 1),
      "耗时", round((2 * P * S + 2 * L * S * S * D_MODEL) / NODE, 1), "s")
# 86.0 494.8 580.8 163.1
print("二次项 = 线性项的临界长度:", round(P / (L * D_MODEL)), "token")   # 106812

print("decode 单步读 KV:", round(S * KV_B / BW * 1e3, 1), "ms ->",
      round(BW / (S * KV_B), 1), "tok/s")                               # 60.1 ms -> 16.6
print("TP=8 每卡:", round((S * KV_B + W) / 8 / 1e9, 2), "GB ->",
      round((S * KV_B + W) / 8 / BW * 1e3, 2), "ms ->",
      round(BW / ((S * KV_B + W) / 8), 1), "tok/s")                     # 42.67 GB -> 12.74 ms -> 78.5

print("128k 窗口 @1 fps/1024 tok:", 131_072 // 1024, "帧 =",
      round(131_072 / 1024 / 60, 1), "min, KV", round(kv(131_072), 1), "GiB")
# 128 帧 = 2.1 min, KV 40.0 GiB
print("粗排索引(每帧 1024 维 fp16):", round(600 * 1024 * 2 / 1024 / 1024, 2), "MiB； 精读 32 帧 KV",
      round(kv(32 * 1024), 2), "GiB")                                   # 1.17 MiB； 10.00 GiB
```

与源文对照：表 1 的每帧 token 口径、表 2 的算力与带宽、表 3 的压缩比例全部由上面的脚本自行复算；**三张表里唯一直接引用论文的数字是 66 token/帧**（$224^2$、`patch_size=14`、2×2 合并），脚本用同一公式复算得到 66，两者一致。prefill 的 45% MFU 是明示的估算假设，不是厂商数字；attention 二次项按「QK^T 与 AV 各 $2H_qS^2d_{\text{head}}$、因果掩码折半」的稠密口径推导，真实 kernel 的 masked block 会带来偏差。

另外，视觉编码器本身**不是**瓶颈，值得顺手算掉：按 ViT-L/14 口径（24 层、$d=1024$、约 0.3B 参数）处理 1024 个 patch，每帧约 0.73 TFLOPs，600 帧合计 0.44 PFLOPs，比 LLM 侧的 580.8 PFLOPs 低约三个数量级；而且各帧编码互不依赖，可以完全并行。**视频的成本几乎全在「帧变成序列之后」**。

## 常见追问

- **追问**：为什么不把 10 分钟视频的所有帧直接拼进上下文？
  - 要点：三个依次到来的墙。① 容量：614,400 token × 320 KiB = 187.5 GiB，一条序列就超过单张 80 GB 卡；8×80 GB 整机（596 GiB）扣掉 130.4 GiB 权重后只放得下 2 条这样的序列。② 算力：prefill 的二次项占到 85%，8×H100 也要 163 s 才能出第一个 token，谈不上交互；③ 带宽：decode 每步要读完整份 KV，单卡等效 60.1 ms/token。所以正确回答是先降采样与合并，再考虑分层摘要或两阶段检索，而不是加窗口。
- **追问**：流式视频（摄像头实时输入）和离线视频的处理差在哪？
  - 要点：离线视频能全局重排预算（先扫一遍找关键帧）；流式不能回头，只能维持一个滚动窗口：新帧进、老帧出，出窗口前必须先压成摘要（文本或少量 token），否则 KV 会无限增长。此外流式只有一次机会、无重试，SLO 是每段的 p99 延迟而非总吞吐；抽帧率还受采集与编码链路限制。工程上常见做法是「固定帧率的滑窗 + 定期把窗口内内容写成结构化摘要」，把记忆从 KV 挪到文本。
- **追问**：时间戳应该写进 prompt 还是写进位置编码？
  - 要点：两者解决的不是同一个问题。写进 prompt 是**绝对时间、可引用**（「第 12.5 秒发生了什么」），代价是 token 与字符串解析；写进位置编码（M-RoPE 的 temporal ID）**不占 token、帧序天然正确**，但只有离散的帧级精度，精度上限由采样率决定。需要精确时间定位时两者并用：prompt 给秒级时间戳、位置编码保证帧序与跨模态对齐。
- **追问**：帧采样率怎么定？
  - 要点：先问任务需要看到多快的变化。动作识别、手语、体育要 8 fps 量级（代价是一次 10 秒片段就 25 GiB KV）；内容问答、摘要 1 fps 甚至 0.5 fps 够用；监控类长视频用场景切分把预算集中到有变化的位置。更稳的做法是先固定 token 预算 $B$，再解 $f \le B / (T \cdot N_{\text{frame}})$，把帧率当成因变量。
- **追问**：长视频为什么常做成两阶段或分层摘要？
  - 要点：因为便宜的表示与贵的表示差几个数量级。粗排阶段一帧一个向量，600 帧的索引只有 1.2 MiB；精读 32 帧只要 10.0 GiB KV，是全量 187.5 GiB 的 5.3%。分层摘要把长视频先转成分段文本，再对文本做 RAG（[[rag-06]]），好处是可以用现成的文本检索栈、且摘要可复用、可缓存。
- **追问**：音频怎么进模型？
  - 要点：先用 ASR 字幕加时间戳，与帧 token 交错进 prompt——最便宜、也最容易被语言模型使用，但非语音事件（警报、掌声）与语气信息拿不到；需要这些信息时要引入音频编码器并与视觉表示对齐到同一空间（[[multimodal-10]]），代价是对齐数据与额外的预处理延迟。
- **追问**：同一段视频被反复提问，有什么优化空间？
  - 要点：视觉前缀的 KV 可以复用——与 [[inference-serving-05]] 的 prefix caching 完全同构，条件也是「前缀逐 token 一致」：同一段视频的抽帧、分辨率、合并方式、prompt 模板都必须固定，否则缓存全部失效。多轮视频问答里这一项的收益通常比调帧率更大。

## 公司变体

`asked_at` 里只有 Meta 一家，依据其公开技术材料与产品形态，这题在 Meta 的侧重偏向**工程实现与规模**，而不是纯数学推导：

- Meta 的公开工作同时覆盖长上下文语言模型（Llama 系列的长上下文扩展）与多模态模型（早期融合的 token 化多模态模型、视频侧的研究），所以「图像 token 与文本 token 共用一条序列」对它不是新概念，追问更容易落在**规模与成本**上：给定视频时长和帧率，先把 token 与 KV 算出来，再谈抽帧、合并、并行与缓存。
- 与之配套的问题通常是「怎么训」：长序列训练怎么切分、要不要梯度检查点、视觉塔与语言模型的并行策略是否要分开（LongVILA 的口径正是这类问题的公开参考点）。
- 相对地，位置编码的数学细节（M-RoPE 三个分量怎么分配、外推性如何）更可能是**追问**而不是主线；能讲清「为什么 1D-RoPE 在视频上不够用」即可。

以上是依据公开技术材料与产品形态的判断，具体面试形式以实际轮次为准。
