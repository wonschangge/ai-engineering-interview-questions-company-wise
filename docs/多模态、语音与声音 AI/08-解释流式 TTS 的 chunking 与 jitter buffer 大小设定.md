## 一句话答案

> 题干把 chunking 与 jitter buffer 并列，是因为它们各自解决一个不同的问题：**TTS 侧的 chunking 决定「多快能出第一段声音」，是延迟问题；播放侧的 jitter buffer 决定「声音能不能连续不断地播出来」，是稳定性问题。**
> 合成端按文本的韵律边界切块，**首块短、后续块大**：首块短是为了首字延迟，但首块有下界（示意参数下约 135 ms）——短到连初始缓冲都填不满，客户端只能等第二块，首字反而更晚；后续块大是因为每块都有固定开销（文本前端、声学上下文初始化），块太小时合成实时率 $RTF>1$，任何缓冲都会被抽干。
> 播放端的缓冲深度按**抖动分布的目标分位数**设定，不是按固定毫秒数：$B \approx z_p \cdot \sigma_X$，$z_p$ 由「每分钟可接受的卡顿次数」反推（50 包/秒下，1 次/分钟对应 $z=3.40$）；网络变好就收缩，网络变差立刻加深。
> 两个旋钮要联调：首块越大，结构上需要的初始缓冲越小；缓冲越深，barge-in 时残留的尾音越长。

## 面试官在考什么

- 能不能把两个概念**分工**讲清，而不是把它们混成一件事。延迟与连续性是两个目标，各自的失败模式（首字慢 vs 卡顿）与各自的旋钮完全不同。
- 是否知道 chunking 的**下界来自哪里**：文本切分有韵律约束（不能切断韵律单元），工程上有每块固定开销（$RTF$ 约束），所以「切得越小越好」是错的。能给出「首块小、后续块大」的具体策略与数值下界。
- 是否理解流式合成为什么可行：非自回归/并行端到端合成的成熟让「按块合成」成为可能，而不是只能等整句生成完。
- jitter buffer 部分要看两层：**能不能算**（抖动分布 → 目标分位数 → 缓冲深度，并把概率换算成「每分钟卡顿次数」），以及**能不能运维**（自适应升降、时间伸缩、丢包隐藏、与 barge-in 清缓冲的配合）。
- 有没有把 RTP/RTCP 的口径用对：RFC 3550 的 jitter 字段是**均值型的一阶平滑估计量**，可以用来比较网络好坏，但直接拿它乘一个倍数当缓冲深度会系统性低估重尾网络。

常见错误答案：

- 「chunk 切小一点、buffer 设 200 ms」——两个数都答不出依据。切小会让块内 $RTF$ 超过 1（示意参数下小于 180 ms 的块根本追不上播放），固定 200 ms 缓冲要么在好网络上白送延迟，要么在重尾网络上仍然卡。
- 「把 RTCP 报的 jitter 乘以 3 就是 buffer」——RFC 3550 的 $J$ 估的是相邻包相对传输时间之差的平滑绝对均值，与单包偏差的标准差差一个 $\frac{2}{\sqrt{\pi}}$ 因子（$J = 1.1284\sigma_X$）；在 1% 包额外加 100 ms 的例子里，$J$（以 $E|D|$ 计）只从 16.9 ms 涨到 18.6 ms（约 10%），而所需缓冲从 51 ms 涨到 128 ms（2.5 倍）。

## 原理与推导

### 1. 一条链路、两个缓冲

用户的语音走「VAD → ASR → LLM → TTS → 网络 → 播放」这条串行链路，链路上有两处排队：

- **合成侧（chunking）**：文本要攒到多少才能开始合成。攒得多，韵律更准但首字更慢；攒得少，首字快但每块的固定开销占比高、边界处韵律容易断。
- **播放侧（jitter buffer）**：把到达时间不均匀的音频包，变成严格等时（isochronous）的采样流。声卡按固定采样率消费数据，播放又是不可逆的——已经送进 DAC 的音频收不回来，所以任何到达抖动只能在缓冲里提前吸收。

两个目标串在一条延迟预算上：

$$T_{\text{first-audio}} = t_{\text{VAD}} + t_{\text{ASR}} + t_{\text{LLM,TTFT}} + t_{\text{TTS1}} + t_{\text{net}} + B$$

其中前四项是 chunking 与上游决定的（$t_{\text{TTS1}}$ 是首块合成耗时），最后两项是网络与缓冲决定的。$B$ 每多 1 ms，首字就晚 1 ms；$t_{\text{TTS1}}$ 每多 1 ms 同理。所以「buffer 设大点更稳」不是免费的——它直接抵消 chunking 换来的收益。这就是两个旋钮必须联调的原因：**稳态连续播放要求 $B$ 足够覆盖抖动分位数，而交互体验要求 $B$ 尽可能小**。

### 2. chunking：按什么边界切，首块为什么短

文本切分的优先级（高到低）：句末标点 `。！？…`（语调可终止）→ 分句标点 `；：`、`，、`（语调要「延续」，必须知道后面还有内容）→ 连词/介词短语边界（「因为……」「在……之后」不宜断开）→ 兜底：超过最大块长或等待超时则强制切。不许切断的单元包括数字与单位（`3.14`、`20 ms`）、专名、英文缩写（`Dr.`）与成对的 SSML/韵律标记，所以切分必须在**归一化之后的文本**上做，而不是在 LLM 的原始输出上做。

**首块短、后续块大**是标准策略：首块只决定首字延迟，短首块（一句短语）能尽快出声；后续块要摊薄每块的固定开销，并给时长/音高预测器更长的上下文，块越大韵律越稳。

代价是**上下文依赖**：合成要看到后面几个词才能定调与停顿——在逗号处切开时，下一块的第一个词是名词还是动词短语，决定这个逗号读成升调还是降调。切点选定后仍要向后看一个词；更长的 lookahead（整句）音高更准但推迟首字，工程折中是**首块用短 lookahead + 强制超时兜底，后续块用完整句子**。

### 3. 为什么可以按块合成

流式合成的前提是「每块的成本与块内音频时长近似线性，且不必等前面全部生成完」，这一点由非自回归/并行端到端合成奠定：

- FastSpeech 2 明确以非自回归（non-autoregressive）路线缓解 TTS 的一对多映射：直接用 ground-truth 目标训练，并把 pitch、energy、更准确的 duration 作为条件输入；摘要给出的口径是**相对 FastSpeech 约 3 倍训练加速**，其 FastSpeech 2s 变体直接从文本并行生成波形、推理更快；摘要里「可超过自回归模型」说的是 FastSpeech 2 本身，不是 2s。注意「3 倍」是**训练**加速，不要当成推理加速引用。
- VITS 用变分推断 + normalizing flow + 对抗训练做到**单阶段训练与并行采样**，并用随机时长预测器建模节奏的多样性；论文在 LJSpeech 单说话人数据集上的主观 MOS 与真人录音**相当**（comparable to ground truth）——口径是「相当」，不是「超过」。

这两条结论都是整句合成场景下的，流式还要额外满足一个条件：**模型支持带左右上下文的按块条件合成**。把整句模型硬切成互不相干的块，会在块边界产生音高/能量不连续（听感上是拼接感甚至爆音），工程上要么用原生支持流式的模型，要么在边界做 overlap + 交叉淡化，并把上一块的末尾声学状态作为下一块的上下文。

### 4. 块大小的下界：每块固定开销把 $RTF$ 顶上去

设每帧 20 ms 音频，单帧计算耗时 $c$ ms，每块的固定开销 $f$ ms（文本前端、phoneme、声学上下文初始化），块含 $n$ 帧。则这一块产出的音频时长是 $20n$ ms，合成耗时 $f + nc$ ms：

$$RTF(n) = \frac{f + nc}{20n} = \frac{f}{20n} + \frac{c}{20}$$

稳态连续播放的**必要条件**是 $RTF(n) < 1$（否则缓冲只决定什么时候开始卡，不决定会不会卡），于是

$$n > \frac{f}{20 - c}$$

取示意值 $f = 120$ ms、$c = 6$ ms/帧（$RTF_\infty = 0.3$），得到 $n > 8.57$，即**块不能小于 9 帧（180 ms 音频）**。5 帧的块 $RTF = 1.5$，永远追不上播放。

补充两点工程含义：一是这个下界只约束**稳态块**，首块可以小于它——首块在播放开始前完成，$RTF>1$ 只是延迟而不是欠载；但首块欠下的时间债要么由后续块的盈余补回来，要么由初始缓冲垫掉（见第 6 节）。二是 $f$ 可以被流水线摊薄：把下一块的文本前端与当前块的声学合成重叠，等效于把 $f$ 变小，块就能切得更小——这是比调 buffer 更根本的优化。

### 5. 与 LLM 流式输出的衔接

LLM 逐 token 输出，TTS 不能等整段生成完，也不能见到第一个字就发声：

- **触发点是句子/子句边界**：累积到边界（`。！？；，` 或达到最大块长）才提交一次合成请求，避免把 `3` 先读成「三」、等下一个 token 到了才发现是「三十」。
- **LLM 会改主意**：用户可见的流式文本里，后面的 token 可能改变前面的重音或词形（数字、专名、否定词）。做法是区分**稳定前缀**与**可替换尾部**：已播放的音频不可撤回，未播放的部分允许重合成。「已下发但未播放」的余量只有 $t_{\text{net}} + B$ 折算的音频时长（$B$ 只取抖动下限 45 ms 时也只有约 65 ms），太小，所以真正需要的是**服务端的可撤回窗口**：下发前多留一个块（几百毫秒）作为可丢弃尾部，代价是首字延迟增加这么多——chunking 的第一条取舍在 LLM 侧的翻版。
- **不确定性高但影响大的位置**（数字、单位、专名、语气词）不为它推迟整块：先按当前文本合成、只下发稳定部分，等 LLM 给出更多 token 再定尾部怎么读。这与 speculative 式的「先猜后改」同类，区别是音频的撤销成本随已播放时长增长，所以窗口必须显式设界。

### 6. 播放侧：等时播放与非等时到达

包到达时刻由网络决定，播放时刻由音频时钟决定，两者之差就是需要缓冲吸收的部分。这个量的大小决定两种失败模式：$B$ 太小，包在播放时刻之后才到、缓冲被抽干（underrun），听感是断续、咔哒声与重复填充造成的爆音；$B$ 太大，播放要等缓冲填满才开始，端到端延迟按同样的毫秒数增加。RFC 3550 给出了这个抖动量的规范定义（第 6.4.1 节）：

$$D(i,j) = (R_j - R_i) - (S_j - S_i) = (R_j - S_j) - (R_i - S_i)$$

其中 $S$ 是 RTP 时间戳、$R$ 是同一时间单位下的到达时刻，$D$ 就是两包「相对传输时间」之差。规范要求连续按下式更新抖动估计：

$$J(i) = J(i-1) + \frac{|D(i-1,i)| - J(i-1)}{16}$$

1/16 的增益被规范描述为「最优一阶估计量」，兼顾降噪与收敛速度；它的时间常数是 $-1/\ln(1-1/16) \approx 15.5$ 个包，20 ms 包下约 310 ms。

这里有一个必须说准的口径：RFC 3550 的字段描述写的是「interarrival time 的统计方差的估计」，但紧接着的定义是 D 的 **mean deviation（平滑后的绝对值）**，RTCP 字段里放的就是后者的实现（附录 A.8 给了浮点与定点两种写法）。工程上要按公式理解，别按字段描述理解；而且 RFC 自己在 6.4.4 节强调这个字段只是「报告时刻的快照，不适合定量使用」，它的用途是跨报告比较。这个提醒不是学究：把 $J$ 当成 $\sigma_X$ 直接乘倍数，就会低估缓冲。

### 7. 从抖动分布到缓冲深度：σ、J 与「每分钟卡顿次数」

设单包到达偏差 $X$（相对播放锚点的偏移）均值为零、标准差 $\sigma_X$。缓冲深度 $B$ 下，单包晚到的概率是 $P(X > B)$；若要求平均每分钟卡顿不超过 $\lambda$ 次、包间隔 20 ms（50 包/秒），则目标单包概率为

$$p = \frac{\lambda}{60 \times 50} = \frac{\lambda}{3000}, \qquad B = z_{1-p}\,\sigma_X$$

高斯假设下 $J \to E|X_i - X_{i-1}| = \frac{2\sigma_X}{\sqrt{\pi}} = 1.1284\,\sigma_X$，即

$$\sigma_X = \frac{\sqrt{\pi}}{2} J = 0.8862\,J, \qquad B = 0.8862\,z_{1-p}\,J$$

代入 $\sigma_X = 15$ ms：$J \approx 16.9$ ms；$3\sigma_X = 45$ ms $= 2.66 J$；要把卡顿压到 1 次/分钟（$z = 3.403$）需要 $B = 51$ ms $= 3.01 J$。也就是说「3 倍 RTCP jitter」在高斯网络下恰好约等于 1 次/分钟的口径——这个巧合只在近似高斯时成立，不能外推到重尾。

**为什么不能停在「3σ 已经 99.73%」**：音频是每秒 50 个包，按包计的尾部概率要换算成每分钟的卡顿次数才有意义。$3\sigma$ 的单包晚到率是 1.35‰，换算过来是每分钟约 4 次卡顿，对语音 agent 不可接受；把目标从 4 次/分钟改到 1 次/分钟，只多要 6 ms 缓冲（45 → 51 ms）。这一步换算是最容易漏的地方。

重尾网络下分位数更关键。设 1% 的包额外延迟 100 ms（其余为 $\sigma=15$ ms 的高斯），复算的单包偏差分位数是 p95 = 26 ms、p99 = 60 ms、p99.9 = 119 ms；要压到 1 次/分钟需要 $B \approx 128$ ms（同一仿真的 5000 包滑窗给 125 ms，差距来自窗口）。此时 $J$（以 $E|D|$ 计）只从 16.9 ms 变到 18.6 ms，**均值型统计量对尾部几乎没有响应**，所以缓冲必须按实测分布的经验分位数设定（1 次/分钟对应 p99.97 附近，p99.9 只对应 3 次/分钟），$J$ 只用来判断网络是不是在变差。

### 8. 自适应缓冲与配套技术

- **升降策略**：滑窗维护经验分位数，窗口按包数设并与目标分位数匹配（p95/p99 用几百包够用，1 次/分钟对应 p≈0.99967、要上万包；5000 包窗口里只有约 1.7 个样本超出，会把深度估得偏乐观）。目标深度 $B^* = q_p(X) + \Delta_{\text{render}}$。调整要「快升慢降」：抖动变大立刻加深（避免卡顿），变好时每次最多降 5 ms 且间隔 ≥ 1 s（避免振荡）。
- **单位换算先算清**：45 ms 的缓冲在 Opus 32 kbps 下只有 180 B，24 kHz/16 bit PCM 下 2160 B。缓冲的内存开销可以忽略，成本全在延迟——所以不要用「省内存」当缩小缓冲的理由。
- **时间伸缩**：轻量时间伸缩（WSOLA 类）能吸收百分之十几以内的长度偏差而不变调，用来纠正缓慢漂移；大偏差只能靠丢帧或加深缓冲。
- **丢包隐藏与重复填充**：单包晚到或丢失可以靠 PLC（用前一帧外推）/重复上一帧顶过去，这会把「可容忍的晚到率」抬高一个量级——代价是音质，所以目标概率要按「可隐藏的包数」重算。
- **时钟漂移**：采集/播放时钟与服务器时钟的偏差按 ppm 计，100 ppm 即 0.1 ms/s，45 ms 缓冲可吸收 450 s 的漂移。也就是说在几分钟的会话里漂移不是主要矛盾，抖动分布才是；但长会话必须定时校正（丢/补静音或重采样）。
- **静音压缩**：静音段少发包可以省带宽，但静音结束后的第一个包仍要重新填到目标深度，**不能在静音期间把缓冲抽干**，否则话音一起就卡。
- **与 barge-in 的交互**：打断时要能 O(1) 清空缓冲（环形缓冲 + 单调 playout 序号，清空即把读指针追到写指针并丢弃在途旧包），同时向服务端回报「已播位置」用于历史截断。缓冲越深，打断残留的尾音越长——这是同一个旋钮的另一面，详见 [[multimodal-04]]。

### 9. 服务端那一头：批量合成与低延迟的冲突

单路实时合成要求 $RTF < 1$，但服务端还要靠 batching 摊薄成本：batch 越大吞吐越高，排队（TTFT）越差。这是 [[inference-serving-09]] 里的标准取舍，在语音场景多两条约束：

- **播放是硬实时**：上游 LLM 的 token 流与下游播放都不等人，所以语音合成适合「**优先级队列 + 连续批处理**」——按播放 deadline 排序、把同一时刻到达的块拼批，而不是先到先服务地攒大 batch。超时未合成的块宁可降级（更小的模型/更短的上下文）也不能迟到。
- **并发上限由显存与带宽定**：以 LLaMA-3-70B（GQA-8、bf16，每 token KV 约 320 KiB）为例，4k 上下文每序列 1.25 GiB KV，8×80 GB 卡扣掉约 130 GiB 权重后剩约 466 GiB，只放得下约 373 条并发序列——语音 agent 的长会话会持续占着这份 cache，所以「提高并发」与「压低首字延迟」在同一张卡上是直接对立的。

| 首块合成 $t_{\text{TTS1}}$ | 题设参数（首块 5 帧时 $= f + n_1 c = 120 + 30$） | 150 ms |
| 网络单程 $t_{\text{net}}$ | RTT 40 ms 的一半；保守取 40 ms | 20 ms（保守 40 ms） |
| jitter buffer $B$（只算抖动需求） | $3\sigma_X$，$\sigma_X = 15$ ms | 45 ms |
| **合计** | 150 + 20 + 45 | **215 ms**（保守 235 ms） |

这里的 $B$ 只覆盖抖动；结构需求见 表 3，并且更大：首块 5 帧时结构空档 170 ms，而首块的 100 ms 音频连它都填不满，客户端要一直等到第 2 块的音频到达，首字可闻约 440 ms——想压到 250 ms 量级，首块要切到 225 ms 左右。全链路还要加上 VAD 静音判定、ASR 收尾与 LLM 的 TTFT，这三项按 [[multimodal-03]] 的同一套串行相加规则代入自己的 p50/p95 实测值；本节所有参数（$f$、$c$、$\sigma_X$、RTT）都是可测量、可替换的量，结论是**规则**而不是这几个数字。

### 表 3：首块大小 ↔ 结构空档 ↔ 首字可闻（第二块 25 帧、单程 $t_{\text{net}}=20$ ms）

单 worker 顺序合成时，第 2 块要在第 1 块就绪之后才开始，两段音频之间没有任何包到达，初始缓冲必须覆盖这个空档：$B_{\text{struct}} = \max(0,\ f + n_2 c - 20 n_1)$。推导：第 2 块就绪在 $f + n_1 c + f + n_2 c$，第 1 块音频播完在 $f + n_1 c + t_{\text{net}} + B + 20 n_1$，令前者不晚于后者即得——$t_{\text{net}}$ 在两侧同时出现、正好抵消。（为把账算清，这里设每块音频合成完就整段到达；若按 1× 实时发包，空档还要多一个包 20 ms。）

| 首块 $n_1$ | 首块就绪 | 结构空档 $G = 270 - 20n_1$ | $B = \max(45, G)$ | 首字可闻 |
| --- | --- | --- | --- | --- |
| 3 帧（60 ms） | 138 ms | 210 ms | 210 ms | 428 ms（首块填不满，只能等第 2 块） |
| 5 帧（100 ms） | 150 ms | 170 ms | 170 ms | 440 ms（同上） |
| 8 帧（160 ms） | 168 ms | 110 ms | 110 ms | 298 ms |
| 12 帧（240 ms） | 192 ms | 30 ms | 45 ms | 257 ms |
| 15 帧（300 ms） | 210 ms | 0 ms | 45 ms | 275 ms |
| 20 帧（400 ms） | 240 ms | 0 ms | 45 ms | 305 ms |

读法：首块每多 20 ms 音频，结构空档就少 20 ms，但**首块音频本身要够垫满 cushion**（$20 n_1 \ge B$，即 $n_1 \ge 6.75$ 帧 = 135 ms），否则客户端只能等第 2 块的音频，首字可闻跳到 0.4 s 以上。空档降到抖动需求（45 ms）以下后，再加大首块只是白送延迟。**最优首块就是让结构需求与抖动需求相等的那一点**：$n_1 = 11.25$ 帧（225 ms），首字可闻约 253 ms。

### 表 5：包大小的取舍（RTP 12 B + UDP 8 B + IPv4 20 B = 40 B 头）

20 ms 一包是常见折中。Opus 32 kbps 下 20 ms 载荷 80 B，加头 120 B，头部占 33.3%、总码率 48 kbps；切到 10 ms，载荷 40 B、头部占比升到 50%、每秒包数翻倍（CPU 唤醒与丢包粒度都变差）；切到 40 ms，头部降到 20%、总码率 40 kbps，但单包延迟与丢包粒度翻倍。同一 40 B 头在 24 kHz/16 bit PCM（20 ms = 960 B）上只占 4.0%（总码率 400 kbps），所以包时长要和编码一起算——包时长本身也是抖动缓冲的粒度单位。

### 代码：RFC 3550 的 $J$ 估计器、经验分位数与缓冲标定

```python
import math, collections
import numpy as np

ALPHA = 1.0 / 16.0                      # RFC 3550 规定的一阶平滑增益
PKT_MS = 20.0                           # 每包 20 ms 音频
PKT_RATE = 1000.0 / PKT_MS              # 50 包/秒
Z = 3.403                               # 1 次/分钟对应的单包分位数

class JitterTracker:
    """同时维护 RFC 3550 的 J、窗口内 |D| 均值与单包偏差的经验分位数。"""
    def __init__(self, window=5000):                   # 窗口按包数计：5000 包 = 100 s
        self.transit = None                            # 上一包的相对传输时间
        self.j = 0.0                                   # RFC 3550 的 J
        self.x = collections.deque(maxlen=window)      # 单包到达偏差 X
        self.d = collections.deque(maxlen=window)      # |D| = |X_i - X_(i-1)|

    def observe(self, arrival_ms, nominal_ms):
        x = arrival_ms - nominal_ms                    # 相对播放锚点的偏差
        self.x.append(x)
        if self.transit is not None:
            d = abs(x - self.transit)
            self.d.append(d)
            self.j += ALPHA * (d - self.j)             # J(i) = J(i-1) + (|D|-J(i-1))/16
        self.transit = x
        return self.j

    def depth_by_quantile(self, glitches_per_min=1.0):
        """分位数口径：直接量单包偏差的经验分位数。"""
        p = glitches_per_min / (60.0 * PKT_RATE)
        return float(np.quantile(np.array(self.x), 1.0 - p))

    def depth_from_mean_abs_d(self):
        """sigma = sqrt(pi)/2 * E|D| = 0.8862 * E|D|，再乘 z。"""
        return Z * math.sqrt(math.pi) / 2.0 * float(np.mean(self.d))

    def depth_from_rfc_j(self):
        """直接用手上的 J 换算：与上一行的差别只来自 EWMA 的波动。"""
        return Z * math.sqrt(math.pi) / 2.0 * self.j

rng = np.random.default_rng(0)
N = 1_000_000
for name, delay in [
    ("高斯 sigma=15ms", rng.normal(0, 15, N)),
    ("重尾 1% 加 100ms", np.where(rng.random(N) < 0.01,
                                100 + rng.normal(0, 15, N),
                                rng.normal(0, 15, N))),
]:
    tr = JitterTracker()
    for i, d in enumerate(delay):
        tr.observe(arrival_ms=i * PKT_MS + d, nominal_ms=i * PKT_MS)
    print(f"{name:16s} E|D|={np.mean(tr.d):6.2f} J_ewma={tr.j:6.2f} | "
          f"分位数口径 {tr.depth_by_quantile():6.1f} ms | "
          f"E|D| 换算 {tr.depth_from_mean_abs_d():6.1f} ms | "
          f"J 换算 {tr.depth_from_rfc_j():6.1f} ms")
# 输出：高斯 sigma=15ms    E|D|= 17.04 J_ewma= 20.05 | 分位数口径   52.6 ms | E|D| 换算   51.4 ms | J 换算   60.5 ms
#      重尾 1% 加 100ms   E|D|= 18.14 J_ewma= 21.35 | 分位数口径  124.9 ms | E|D| 换算   54.7 ms | J 换算   64.4 ms
```

两种口径在高斯网络下几乎一致（分位数 52.6 ms vs 换算 51.4 ms，解析值 51.0 ms，差值来自窗口：分位数只在最近 5000 包上统计，用满 1e6 样本时就回到 51.0 ms）；重尾网络下差 2.3 倍（124.9 ms vs 54.7 ms）。同一段流量里 $J$ 的 EWMA 值本身有几毫秒的波动（1/16 的增益等效样本量只有约 16 个包，本次运行高斯情形给 20.05 ms，而 $E|D|$ 是 17.04 ms），所以它适合当「网络是否变差」的监控量、不适合当标定量——重尾情形下的偏差是系统性的（54.7 vs 124.9 ms），不是随机噪声。

## 常见追问

- **追问**：为什么不直接固定 200 ms 缓冲？
  - 要点：固定值在好网络上白送 150 ms 以上的首字延迟，在重尾网络上仍然会卡（表 4 里 45 ms 只有 4 次/分钟、51 ms 才到 1 次/分钟，而重尾情形要 128 ms）。而且不同客户端差异极大：浏览器 WebAudio、iOS、Android、蓝牙免提的渲染链路缓冲从几十毫秒到几百毫秒不等。正确做法是按分位数自适应，固定值只能当**上限保护**。
- **追问**：服务端批量合成的吞吐与单路低延迟冲突怎么解？
  - 要点：优先级队列（按播放 deadline 排序）+ 连续批处理（同一时刻到达的块拼批），再叠加块级降级策略（超时就用更小模型/更短上下文）。不要用「先到先服务攒大 batch」；顺带算一下并发上限——LLaMA-3-70B 的 KV 是 320 KiB/token，4k 上下文每序列 1.25 GiB，8 卡服务器扣掉权重只剩约 466 GiB，约 373 条并发（[[inference-serving-09]]）。
- **追问**：首包延迟怎么埋点与验收？
  - 要点：定义成 $TTFB = t_{\text{首块音频到达客户端}} - t_{\text{用户停止说话}}$，在链路上打四个点：end-of-speech（VAD）、首块提交（chunker）、首块合成完成（TTS）、首包到达（客户端）。验收看 p50 与 p95 两条线，并同时记录卡顿率（每分钟 underrun 次数）与缓冲深度均值/最大值——只报 TTFB 会把「缓冲偷偷设大」当成优化（[[evaluation-07]]）。
- **追问**：$RTF$ 大于 1 时加深缓冲能不能救？
  - 要点：不能。缓冲只改变开始播放的时刻，稳态 $RTF>1$ 意味着队列单调下降，最终必然 underrun，只是时间问题（$B / (RTF-1)$）。唯一的解是把稳态块加大、把每块固定开销流水线化，或换更快的模型/更小的块内上下文。
- **追问**：丢包和晚到要分开处理吗？
  - 要点：要。晚到的包如果还在窗口内可以等，超出窗口就得丢；丢包的恢复手段是 PLC/重复填充 + 让解码器平滑过渡，晚到的手段是时间伸缩与缓冲加深。两者的预算（可容忍率、可隐藏包数）不同，混在一起会算错目标分位数。
